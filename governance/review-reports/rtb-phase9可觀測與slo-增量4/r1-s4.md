### F1 補欄位機制用 f-string 表名占位,會讓守衛連「是哪張表」都認不出來
severity: major
blocking: 是
引句:「其他 ALTER(改名、刪欄)一律不准。這是跟 Phase 8 那支唯一不同的地方」
說明:增量 4 說「例外:補欄位流程的『新增欄位』(ALTER TABLE 某表 ADD COLUMN)准許...其他 ALTER 一律不准」,並要求把 f-string 的固定片段拼回完整語句去比對六張表。但執行端資料庫今天既有的補欄位機制(`src/rtb/executor/inbox_store.py:441` `_missing_columns`、`:461` `_migrate_columns`)是**用變數迴圈跑過整個 `_ADDED_COLUMNS` 字典**,實際下的 SQL 是 `inbox_store.py:474`:`self._conn.execute(f"ALTER TABLE {table} ADD COLUMN {ddl}")`。用 `_text_of` 這種手法(main 分支 `tests/executor/test_dead_letter.py:457-459`:JoinedStr 裡非常數的片段一律拼成字面 `"{}"`)拼回來,這一行會變成字面「ALTER TABLE {} ADD COLUMN {}」——表名整個消失,不會是任何一個真實表名。
- 輸入:未來(或這一輪)把「生命週期事件」表(增量 1 新表)登記進 `_ADDED_COLUMNS`,像今天的 `"attempts"` 一樣,靠這個既有的通用迴圈補欄位(而 S607「當執行端資料庫是加事件表與新欄位之前建的,開啟時應補上」正是這個場景)。
- 預期:守衛應該能認出這是對「生命週期事件」表做 ADD COLUMN(允許)、而不是別的動作。
- 實際:守衛掃到的字面根本不含表名,規則式比對(六個真表名接在動詞後面)永遠比不中這一行——不是因為它被正確判定「允許」,而是它從頭就落在偵測範圍外。這代表:同一個通用迴圈以後若被擴充成也能做 `RENAME COLUMN`/`DROP COLUMN`(對任何一張表,包含這六張),表名一樣會被拼成 `{}`,守衛照樣抓不到——這正是「防忘記」宣稱要守住卻守不住的情境,不是設計已排除的「刻意繞過」(用變數組表名的舉例是指刻意規避,這裡是專案既有、非惡意的慣用寫法)。
- 建議改法:六張表裡任何一張若要靠這個通用 `_ADDED_COLUMNS`/`_migrate_columns` 機制補欄位,守衛必須改成直接讀 `_ADDED_COLUMNS` 這個資料結構本身(檢查它的值只含 ADD COLUMN 、且鍵只允許六張白名單表之類的機械檢查),而不能只在原始碼文字層級抓字面;或者禁止六張表走這條通用路徑,強制它們各自用像 `dsp/store.py:260-262` 那種逐行硬寫表名的字面 ALTER(這樣才拼得回真實表名)。

### F2 UPSERT / ON CONFLICT DO UPDATE 這種寫法,規則式比對天生抓不到
severity: major
blocking: 是
引句:「全庫原始碼應沒有任何語句修改、刪除、覆寫、刪除或改名」
說明:守衛沿用 Phase 8 的抓法(main `tests/executor/test_dead_letter.py:446`起的 `TABLE_WRITE`,要求banned動詞後面緊接表名),增量 4 說要「對這六張表比對『修改、刪除、覆寫、刪表、改名』的語句」。但 SQLite 的 upsert 語法是 `INSERT INTO <表> (...) VALUES (...) ON CONFLICT(...) DO UPDATE SET col = ...`——動詞 `UPDATE` 前面接的是 `DO`,表名只出現在最前面的 `INSERT INTO` 後面,不會有任何一段文字是「UPDATE 表名」或「REPLACE INTO 表名」這種鄰接關係。
- 輸入:六張表裡任何一張(例如今天用 `INSERT OR IGNORE INTO write_stops`,`inbox_store.py:870`;或 `approval_uses`,`inbox_store.py:988`)日後改寫成 `INSERT INTO write_stops (...) ON CONFLICT(key) DO UPDATE SET used = used + ?`(這是把「補寫一次用量」改成「原地累加」時很自然會寫出的形式,不是刻意繞過)。
- 預期:這是對既有列做覆寫,守衛應該擋下。
- 實際:`TABLE_WRITE` 式的正則要求「動詞 緊接 表名」,`ON CONFLICT ... DO UPDATE` 整段沒有任何一處把 `UPDATE` 和表名放在一起,規則永遠比不中,守衛完全看不到這一類真正的覆寫。
- 建議改法:偵測邏輯不能只找「動詞+表名」這種鄰接模式,至少要另外抓「這段拼回來的文字裡有沒有出現這張表名,而且同一段裡出現 `ON CONFLICT`」,或者更直接:凡是同一段拼回文字裡同時出現表名與 `DO UPDATE`/`ON CONFLICT` 的,一律當作可疑。

### F3 「唯一不同」的自我描述漏掉了一個差異:很可能變成第二份平行實作
severity: major
blocking: 是
引句:「這是跟 Phase 8 那支唯一不同的地方」
說明:增量 4 認定跟 Phase 8 死信兩張表的結構檢查之間「唯一不同的地方」是多了 ADD COLUMN 例外。但 Phase 8 的 `_text_of`、`_strings`、`TABLE_WRITE` 是定義在 `tests/executor/test_dead_letter.py` 檔案內、名稱帶底線的模組私有函式(main 分支 `test_dead_letter.py:446-479`),沒有被抽成共用模組給別的測試檔匯入。增量 4 的守衛要掃六張表(其中四張根本不在 `inbox_store.py`/`dead_letters` 那組——如 DSP 的 `operations`、attempt_store 的新表),自然會落在一支新測試檔裡,設計文字本身也沒有交代「從 Phase 8 那支匯入共用函式」這一步。
- 輸入:實作者依設計字面「比照 Phase 8...做法」去寫,最快的路是把 `_text_of`/`_strings` 複製一份到新測試檔,只是正則換成六張表版本。
- 預期:設計說「唯一不同的地方」是 ADD COLUMN 例外,暗示其餘完全共用同一套邏輯,理應是同一份程式碼、沒有第二套。
- 實際:出現兩份幾乎相同但物理上分離的 AST 拼字串邏輯,日後 Phase 8 那份若修掉一個邊界案例(例如 f-string 裡出現 `%`格式化字串、或字串乘法 `"x" * 3` 這類目前兩份都沒覆蓋的形式),另一份不會同步得到修正,兩邊的偵測能力會悄悄分岔——這正是設計自稱「唯一不同」時漏看的第二個差異點。
- 建議改法:把 `_text_of`/`_strings` 抽成 `tests/` 下的共用小模組(例如 `tests/_sql_scan.py`),Phase 8 那支與增量 4 這支都改成匯入它;各自只保留自己的 `TABLE_WRITE` 正則與 ADD COLUMN 例外邏輯。
