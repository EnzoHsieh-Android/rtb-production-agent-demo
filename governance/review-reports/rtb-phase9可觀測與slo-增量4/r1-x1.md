### F1 快燒告警在實演收尾時已經解除
severity: major
blocking: 是
引句:「事故時段結束後故障停掉,對帳照常把結果不明的鍵收尾。測試照控制的時鐘推進」
照字面流程，第一次結果不明發生於第 0 秒，縮短後的 10 分鐘期限是第 10 秒，壞事件固定記在第 10 秒；事故於第 20 秒結束並完成第三次送出後才進行調查。此時快燒短窗只有 5 秒，即 `[15,20)`，已不包含第 10 秒的壞事件；依增量 3「短窗無有效事件時燒損率為 0」的規則，快燒告警必為否，與 [S670] 必須為是衝突。

具體例：第一次結果不明 `t=0` → 預期實演收尾 `t=20s` 查到快燒告警 → 實際短窗沒有壞事件，告警已解除。

建議改法：明訂第 1 步必須在 `t=10s+ε`、壞事件仍落在 5 秒短窗時取樣並保存結構化結果，之後才推進到事故結束；或者錯開任務，使評估當下最後 5 秒內仍有新壞事件。

### F2 壓縮後的對帳耗時不可能超過十分鐘
severity: major
blocking: 是
引句:「寫入的 5xx 與逾時上升、對帳耗時的 p95 超過 10 分鐘」
設計把 20 分鐘事故壓成 20 秒，並以測試時鐘實際推進 10 秒、20 秒；增量 2 的延遲是結束時間減開始時間，沒有把輸出的秒數再乘回 60。因此受影響樣本的對帳耗時約為 20 秒，不可能滿足「p95 超過 10 分鐘」。

具體例：`t=0` 進結果不明、`t=20s` 結案 → 預期 p95 `>600s` → 實際樣本約 `20s`。

建議改法：把斷言改成超過縮短後期限 10 秒，並讓顯示結果清楚標示為示範時間；若一定要斷言超過 10 分鐘，就必須讓虛擬時鐘推進 20 分鐘，只縮短燒損評估窗，不能把事故本身壓成 20 秒。

### F3 事故前窗沒有可供比較的對帳耗時樣本
severity: major
blocking: 是
引句:「斷言:告警為是、數字大於事故前的窗」
佈置只描述事故期間的 5xx、逾時及正常對照租戶，沒有在事故前製造任何「先進結果不明、再完成對帳」的樣本。正常一次成功的寫入不屬於對帳耗時樣本；依增量 2 的零樣本規則，事故前 p95 是「無樣本」，不能做大小比較，測試無法照字面撰寫。

具體例：事故前只有一次成功寫入 → 預期有基準 p95 可與事故窗比較 → 實際對帳樣本數為 0、p95 為無樣本。

建議改法：事故前先注入至少一把可快速對帳完成的結果不明鍵，明訂它落在基準窗；或把比較拆開，僅斷言事故窗的樣本數與 p95 超過固定的縮短後門檻，不與無樣本窗比較。

### F4 固定跨表排序無法產生契約要求的因果順序
severity: major
blocking: 是
引句:「斷言時間線依序含:取件、開始一筆、DSP 寫入呼叫(結果類別 5xx)、結果不明、對帳時 DSP 查操作紀錄的呼叫」
增量 1 規定同時間的執行端資料固定按「生命週期事件、嘗試紀錄、DSP 呼叫紀錄」排序。測試控制時鐘且只在輪次間推進，因此一次 HTTP 呼叫前後的「開始一筆」「DSP 5xx」「結果不明」會有相同時間；固定表序會把兩筆嘗試紀錄都排在 DSP 呼叫紀錄之前，得到「開始一筆、結果不明、DSP 5xx」，[S673] 要求的順序必然翻紅。現有執行流程也是收到 DSP 回答後才寫結果。file: `src/rtb/executor/execution.py:846`

具體例：三筆皆為 `t=0` → 預期「開始一筆 → DSP 5xx → 結果不明」→ 實際固定排序為「開始一筆 → 結果不明 → DSP 5xx」。

建議改法：替執行端三張表使用同一個全域遞增因果序號，追蹤以時間加因果序號排序；僅調整固定表優先順序無法解決，因為同一張嘗試表同時含呼叫前與呼叫後的列。

### F5 提交後逾時的兩個時間在受控時鐘下會相等
severity: major
blocking: 是
引句:「提交後逾時那個廣告另斷言反過來的事實:提交時間早於執行端第一次進結果不明」
DSP 的提交後逾時是在提交後用真實時間睡眠，file: `src/rtb/dsp/server.py:223`；受控測試時鐘只有測試主動呼叫 `advance` 才前進，file: `tests/executor/conftest.py:17`。若 DSP 與執行端都依同一個受控時鐘記錄，DSP 提交和逾時返回後寫入結果不明都會標成同一時刻，嚴格的「早於」必然失敗。

具體例：受控時鐘固定在 `12:00:00`，DSP 先提交後真實睡眠 0.6 秒 → 預期提交時間 `<` 結果不明時間 → 實際兩者都是 `12:00:00`。

建議改法：用因果欄位或全域序號斷言提交發生在結果不明之前；若一定要比較時間，測試必須在 DSP 掛住期間明確推進受控時鐘，不能依賴真實睡眠。

### F6 沿用的結構掃描抓不到合法的 SQLite 覆寫語法
severity: major
blocking: 是
引句:「把相鄰字串、用 + 串起來、f-string 的固定片段拼回完整語句,對這六張表比對修改、刪除、覆寫、刪表、改名」
Phase 8 主線守衛只匹配 `UPDATE <表>`、`REPLACE INTO <表>` 等形狀，file: `main:tests/executor/test_dead_letter.py:446`。合法的 `UPDATE OR REPLACE approvals ...`、`DROP TABLE IF EXISTS approvals`，以及 `INSERT INTO write_stops ... ON CONFLICT DO UPDATE` 都不符合該形狀；照「比照 Phase 8」實作會讓覆寫與刪表漏網，即使字串完全沒有刻意拆散。

具體例：輸入 `UPDATE OR REPLACE approvals SET token = ?` → 預期守衛失敗 → 實際既有正規表示式找不到 `UPDATE approvals`，測試通過。

建議改法：把殺傷力配方擴充到 SQLite 完整變體，至少涵蓋 `UPDATE OR <動作>`、`INSERT ... ON CONFLICT DO UPDATE`、`DROP TABLE IF EXISTS`、schema-qualified 表名；比對解析出的 SQL 動詞與目標表，而非只靠「關鍵字緊接表名」的正規表示式。

### F7 無條件放行新增欄位可以追溯改寫稽核語意
severity: major
blocking: 是
引句:「例外:補欄位流程的新增欄位准許,它不動既有資料」
SQLite 的 `ADD COLUMN ... DEFAULT ...` 雖可能不重寫實體列，讀取舊列時卻會呈現新預設值；專案目前就有 `NOT NULL DEFAULT` 的補欄位做法，file: `src/rtb/dsp/store.py:250`。因此無條件放行六張稽核表的所有 `ADD COLUMN`，可以把歷史資料重新解釋成從建立時就帶有某個值，與「不動既有資料」及只增不改的目的衝突。

具體例：`ALTER TABLE approvals ADD COLUMN revoked INTEGER NOT NULL DEFAULT 1` → 預期不得把所有舊核可追溯視為已撤銷 → 實際守衛因為是 `ADD COLUMN` 而放行，舊列讀出 `revoked=1`。

建議改法：只放行明列遷移位置中的 nullable、無 DEFAULT 新欄位；若業務確實需要預設值，逐欄列白名單並加遷移測試，證明舊列的稽核解讀不變。

共 7 條,blocking 7 條。
