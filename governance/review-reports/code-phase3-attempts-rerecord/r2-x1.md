### 1. 交易物件可自行偽造，舊物件也能在其他交易中復活
severity: major
blocking: 是 S19 要求只接受資料庫入口簽發且仍開啟的交易，但目前只檢查公開類別與連線是否碰巧位於任意交易中
引句:「if not isinstance(tx, ExecutorTransaction) or not tx.conn.in_transaction:」
file: `docs/rtb-production-agent-demo-knowledge/Projects/RTB_Phase3外部寫入安全_計劃.md:126`

`ExecutorTransaction` 是可公開建構的 dataclass，沒有入口私有權杖或交易世代識別。因此呼叫端能把自己開的延遲交易包起來，原本「交易物件取代裸連線」的修正仍可被繞過：

輸入：自行建立 SQLite 連線、執行 `BEGIN`，再呼叫 `ExecutorTransaction(conn)` 與 `attempt_store.begin(...)`。  
實際：

```text
forged deferred tx accepted: True 1 in_flight
```

預期：拋出 `NotInTransaction`，因為它不是 `InboxStore.transaction()` 簽發的 `BEGIN IMMEDIATE` 交易。

物件也沒有自己的存活狀態。原交易回滾後，在同一連線另開一個延遲交易，再把舊物件傳給 `latest`，實際仍被接受：

```text
stale wrapper accepted in replacement tx: True in_transaction= True
```

預期：舊交易物件永久失效，不能因同一連線後來進入另一個交易而復活。

這也讓未結案公式的前提沒有真正封住：物件公開暴露 `tx.conn`，呼叫端可直接插入第二個終點列。實測一把已結案的鍵原本計得 `0`；經 `tx.conn` 插入同鍵第二個終點列後，`unresolved_count()` 回傳 `-1`：

```text
valid terminal count => unresolved: 0
same key with second terminal via exposed tx.conn => unresolved: -1
```

在 `attempt_store` 自己的合法狀態轉換中，「恰好一列序號 1、至多一列終點」成立；問題是這次新增的交易能力邊界仍允許偽造、復活及直接寫表，所以修正尚未真正保證該前提。
