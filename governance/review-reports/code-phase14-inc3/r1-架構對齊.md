## 發現 1:型別搬到 investigation 後,investigation 反過來匯入 flow,依賴方向倒轉
severity: minor
blocking: 否 ⚠

【問1 分層與依賴方向】改前:`AiContext`/`AiOutcome`/`QueryMore` 定義在 `rtb.analyzer.flow`,
`rtb.analyzer.investigation` 原本不匯入 `flow` 的任何名字(舊 import 只有
`from rtb.domain._checks import is_id`,見 `git show`前版)。這支檔的舊 docstring 把自己定位成被
`flow`、`ai_judge`、展示流程圖與展示觀察器共同讀取的「調查詞彙」下層模組(`src/rtb/analyzer/investigation.py:4-8`:
「展示流程圖與展示觀察器也讀這裡的列舉,展示伺服器行程因此不會載入模型用戶端」)。這次把三個型別搬進
`investigation.py` 之後,為了讓 `AiOutcome.result: Decision | QueryMore | RuleContinue` 型別成立,
`investigation.py` 新增了
引句:「from rtb.analyzer.flow import Decision, RuleContinue」
file: `src/rtb/analyzer/investigation.py:30`
`flow.py` 本身沒有反向匯入 `investigation`(不構成 import cycle),但方向確實反了:原本「詞彙層
(investigation)不依賴狀態機層(flow)」的既有分工,變成「詞彙層依賴狀態機層」。`tests/test_spawn_boundary.py`
的 `MODEL_FREE` 清單(含 `rtb.analyzer.investigation`、`rtb.analyzer.flow`)只守「匯入閉包不含模型用戶端」,
沒有一條測試守「investigation 不匯入 flow」這件事,所以這不是機械可判的違規,是設計取捨層次的不一致。
評估與分析端的邊界本身沒有被打破:`ai_judge.py` 現在同時從 `flow` 拿 `Decision, NoAction,
ProposalDecision, RuleContinue`、從 `investigation` 拿 `AiContext, AiOutcome, QueryMore`
(`src/rtb/analyzer/ai_judge.py:59-61`,對應 patch 行 74-76),`eval/investigation_eval.py` 也同步改成
兩邊各拿一半(patch 行 5063-5065)——這一步做得一致,問題只在 investigation.py 本身多了一條新的上游依賴。

【問2 命名與錯誤處理】搬移後三個型別名字(`AiContext`、`AiOutcome`、`QueryMore`)全部沒改名,呼叫端改
`from rtb.analyzer.investigation import ...` 就好,沒有引入命名上的不一致;例外處理路徑(`RenewalSkipped`
整支撤除、`_StoreFailed`/`_renewer`/`_call_recorder` 整段刪除)跟著 Phase 13 回退慣例「沒有入口就刪」
一起處理,沒有殘留半吊子的錯誤處理分支,這一段做得乾淨。

【問3 第二種做法】比較保守的做法是:把 `Decision`(`NoAction`/`ProposalDecision`/`NeedsFreshEvidence`
三者的聯集)本身留在比 `flow` 更底層的共用位置(或另開一支雙方都下游的小模組),讓 `flow` 與
`investigation` 都從那裡匯入,而不是讓「詞彙層」直接反向匯入「狀態機層」;或者退一步,`AiOutcome.result`
只需要結構相容(`NoAction`/`ProposalDecision`/`RuleContinue` 都是各自獨立的 frozen dataclass),
不一定要匯入 `flow.Decision` 這個聯集型別本身做型別標註。這次選的是最省事但把依賴方向倒過來的寫法。

## 發現 2:錄製批次改版用了一個非慣用手法,而不是專案既有的 walrus 慣例
severity: major
blocking: 是

【問3 第二種做法優先講】`src/rtb/demo/recordings.py` 的 `proposed_scenarios` 為了在字典推導式裡
只呼叫一次 `reader.scenario_details(demo_id, code)`(既要用它判斷是否為 None,又要用它算
`narrative_json`),寫成
引句:「for code in codes for details in (reader.scenario_details(demo_id, code),)}」
file: `src/rtb/demo/recordings.py:121`
用「把一次呼叫包成單元素 tuple 再用第二層 for 展開」來模擬「在推導式裡綁一個臨時變數」。這支專案對這個
需求已經有現成、讀者一眼就懂的慣用寫法:walrus 運算子,現有碼裡至少四處這樣用,例如
`src/rtb/demo/launcher/child.py:38`
(`if (value := getattr(parsed, name, None)) is not None]`)、
`src/rtb/ops/metrics.py:236`
(`if (value := found.get(kind)) is not None)`)、
`src/rtb/dsp/server.py:305`
(`"state": (result := store.void(key)).state,`)、以及
`src/rtb/demo/driver.py:1586`
(`while stream is not None and (chunk := stream.read(65536)):`)。這四處都是同一類需求(推導式或條件式
裡要重用一次計算結果),都用 `:=` 解決;這次新增的程式碼卻另闢一條「單元素 tuple 迭代」的路,是本次 diff
在既有慣用法之外又立了一種做法,屬於「第二種做法」而不是單純風格差異——下一個要在推導式裡綁臨時變數的人,
現在專案裡同時看得到兩種寫法,不知道要照哪一種。

【問1 分層與依賴方向】這處純粹是 `src/rtb/demo/recordings.py` 檔案內部的推導式寫法,不涉及跨模組匯入或
分析端/評估端邊界,問1 在此不適用。

【問2 命名與錯誤處理】`proposed_scenarios` 取代舊的 `ai_fallback_problems`,命名照「這支函式回什麼」直接
取名(`src/rtb/demo/recordings.py` patch 行 4660-4668),跟專案「函式名說回傳語意」的慣例一致;沒有新增
錯誤處理分支,`reader.scenario_details` 找不到就回 `None`,沿用既有 `TaskReader`/`StateReader` 的
「查不到回 None、不丟例外」慣例,這兩塊沒有問題。
