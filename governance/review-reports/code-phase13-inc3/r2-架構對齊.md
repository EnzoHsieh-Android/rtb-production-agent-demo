## 發現 1:e1「即時錄製不准寫進入庫目錄」另寫了一套路徑判斷，還自己再找一次專案根，沒有放進共用的開錄前目錄檢查
severity: major
blocking: 是

引句:「+    return not Path(folder).resolve().is_relative_to(COMMITTED_ROOT.resolve())」
引句:「+COMMITTED_ROOT = _project_root() / "recordings" / "model"  # 入庫的錄製都在這底下,只供重播」
引句:「+    return next(parent for parent in here.parents if (parent / "pyproject.toml").is_file())」

**既有做法只有一種**
- 「入庫目錄只供重播、即時錄製要給新目錄」原本只靠共用的 `check_recordings_dir` 守:
  - 它看目錄裡有什麼:入庫根目錄有說明檔，所以會被拒。
  - 它的說明寫明，runner、評估執行器和兩支模型入口都共用這一支。file: `src/rtb/modelrecording.py:152`、`src/rtb/modelrecording.py:128`
- 閘道和假說命令列都只呼叫它。file: `src/rtb/analyzer/modelgate.py:117`、`src/rtb/ops/hypothesis.py:329`
- 專案根目錄底下錄製目錄的位置，原本只有門面的 `default_recordings_dir()` 一處在算。file: `src/rtb/modelclient.py:265`

**這次引入第二種做法**
- 評估執行器的 `_fresh` 改成看路徑：路徑落在入庫目錄底下就拒絕。
- 它還用自己的 `_project_root()` 再找一次專案根，沒有用門面的 `mc.default_recordings_dir()`。
- 結果同一條規則有兩套判準：
  - 評估執行器看路徑。
  - 其他三個入口(runner、說明、假說)只看目錄內容，入庫目錄底下還不存在的子目錄照樣放行。
- 「錄製目錄在專案裡的位置」也變成兩處各算一次。

**具體例子**
- 輸入：目錄 `recordings/model/newsub`,現在還不存在。
- 預期：各入口對「是不是入庫目錄」判得一樣。
- 實際：
  - 共用檢查 `check_recordings_dir` 放行。
  - 假說入口的 `recording_refusal` 回 `None`,也就是放行，會把即時錄製寫進入庫目錄底下。
  - 評估執行器的 `_fresh` 回 `False`,拒絕。
- 兩邊的專案根目前算出來一樣(`root same: True`),是同一個錨點算了兩次。

**重現**
1. 把 src、pyproject.toml、recordings/model/README.md 複製到 `/tmp/架構對齊-p13i3r2`。
2. 執行 `PYTHONPATH=src python3`,在裡面:
   - 用 `mc.default_recordings_dir() / "newsub"` 呼叫 `mc.check_recordings_dir(d, "phase13-eval-20260925")`:不丟例外。
   - 呼叫 `ie._fresh(d)`:回 `False`。
   - 呼叫 `hy.recording_refusal(Namespace(recordings_dir=d, batch_id=...), S)`,其中 `S` 是即時模式加錄製的設定：回 `None`。
3. 實測結果:「sub 共用檢查: 放行 | 評估 _fresh: False」,「假說入口 recording_refusal(sub): None」。臨時目錄已刪。

**修法方向**
- 把「解析後的路徑不在 `default_recordings_dir()` 底下」這條加進 `check_recordings_dir`(或閘道的 `open_gate`)。四個入口就共用同一套判準。
- 評估執行器刪掉 `_fresh` 和 `_project_root`,改用 `mc.default_recordings_dir()`。
