severity: major

## F1 信封表沒有可定位的主鍵,重放後第二次死信會與第一次在稽核裡無法分辨

severity: major
blocking: 是 — 照 spec 字面實作,「這筆死信後來怎麼了」在同一提案第二次死信後答不出來,直接違背這個 phase 要解決的 F6 可追溯性目標(交接文件第 16 節、[S509])。

引句:「任務、修訂、內容雜湊、冪等鍵、失敗分類、死信原因、最後卡在哪一步、投遞次數、進死信時間」

死信信封表的欄位清單裡沒有自增 id / 序號這類「這一列本身」的識別欄,稽核表用「信封」欄回指它(見下一引句),但信封唯一能拿來當識別的組合是「任務+修訂+內容雜湊+冪等鍵」。而同一份提案(同一 task_id、revision)被重放放回待處理後,若第二次投遞次數用完再次死信,依 [S502] 的重放動作只清空處置、投遞次數歸零、租約清空,**不改內容**,所以第二次死信寫入的內容雜湊、冪等鍵跟第一次完全相同;投遞次數欄也會相同(都會是耗盡當下的 `MAX_DELIVERIES`=5,見 `src/rtb/executor/inbox_store.py:51,585-588` 的判斷邏輯,重放後重新累加到同一個上限才會再次死信)。這樣兩列信封除了「進死信時間」外全部欄位相同,而 spec 沒有替信封定義任何唯一鍵或序號,稽核表要指向「這一次」死信時,除了拿時間戳去猜之外沒有穩定的參照欄。

引句:「信封與嘗試紀錄、收件表處置、停下紀錄用冪等鍵接得起來」

Section 6 明講查詢靠冪等鍵接,而不是靠信封自己的行識別碼——但冪等鍵在重放前後是同一把(這正是 [S506] 要的行為),所以冪等鍵只能定位到「這個提案身份」,定位不到「這一次死信事件」。對照既有的「只增不改」表都有可以定位單列的欄:`write_stops` 是 `id INTEGER PRIMARY KEY AUTOINCREMENT`(`/Users/enzo/rtb-3b/src/rtb/executor/inbox_store.py:167-172`),`attempts` 是複合鍵 `(key, seq)`、`seq` 專門用來分辨同一把鍵的第幾次(`/Users/enzo/rtb-3b/src/rtb/executor/attempt_store.py:46-52`)。信封表缺這一種欄,是這兩張既有表都有、這張新表沒有的落差。

建議:信封表加一個自增 id(或用「進死信時間+單調序號」),稽核表的「信封」欄存這個 id,而不是任務/修訂/冪等鍵的組合;同時決定重放後再次死信是「新增一列」(目前唯一讀得出來的字面意思,因為信封是「只增不改」,沒有 UPDATE 的选项)还是要在 S500 明文寫「每次死信都新增一列,即使身份重複」。目前 spec 只在字面上寫「同一個交易裡寫一列」,沒有處理「同一身份第二次」的情況,寫的人自然會用類似 `write_stops` 的 `UNIQUE(...) + INSERT OR IGNORE` 去防重複([S500]的用詞跟 `write_stops` 的既有寫法很像),但那個既有寫法是用來讓「同一次評估的重試」去重,不是用來讓「兩次不同的死信事件」去重——如果原封不動照搬,第二次死信會被 `INSERT OR IGNORE` 悄悄吃掉,連一列都不會有,比「兩列」更糟,直接漏稽核。

## F2 新兩張表沒有比照既有停下紀錄表定義索引,成長模式一致但查詢面沒說清楚

severity: minor
blocking: 否 — 不會做出錯的行為,是完整度落差;死信量小(暫用上限 `MAX_DELIVERIES`=5 才會觸發,遠少於 `write_stops` 的每次擋下都寫),沒有索引短期不影響正確性,只影響查詢效能。

引句:「死信佇列重放的業界做法(雲端訊息服務的 redrive:把死信訊息搬回原佇列,照一般流程重新消費,不另開消費路徑)」

計劃開頭 PRIOR-ART 說信封表與稽核表「沿用既有『只增不改、不被清理』的停下紀錄表做法」,但只抄了「只增不改、不被清理」這一半——既有的 `write_stops` 除了這個特性,還定義了三個索引(`write_stops_by_tenant`、`write_stops_by_campaign`、`write_stops_by_time`,見 `/Users/enzo/rtb-3b/src/rtb/executor/inbox_store.py:173-175`)支援「這個租戶/這個廣告/這段時間有哪些停下」的查詢。信封表與稽核表的「最小設計」(第 1、6 節)完全沒提索引,也沒提查「這個任務的死信歷史」「這段時間死信了哪些」要怎麼查。這兩張表確實跟 `write_stops`/`approvals`/`attempts` 一樣不會被清理、會隨時間單調成長(已用 `grep DELETE FROM` 核對過,repo 裡目前只有 `inbox_events` 有按事件代碼上限清理,`write_stops`/`approvals`/`approval_uses`/`attempts` 都是只增不減,見 `/Users/enzo/rtb-3b/src/rtb/executor/inbox_store.py:977` 與周邊程式),所以「只增不改、不被清理」跟現有慣例一致,不是這份 spec 新引入的風險;但既然要回答「這筆死信後來怎麼了」,至少該有 `(task_id, revision)` 或冪等鍵上的索引,不然隨著死信信封表變大,每次查詢都要全表掃描。

## F3 重放指令的「操作人」沒有規定驗證方式或格式,跟既有核可流程的做法不對稱

severity: minor
blocking: 否 — spec 明講威脅模型是「防忘記,不防刻意繞過」,操作人欄目前的定位比較像日誌欄而非授權欄,不驗證不必然是錯的行為;但欄位空白/亂填目前沒有任何字面規則擋。

引句:「比照增量 3 核可工具,命令列,不是執行迴圈的一部分」

Section 3 說重放指令「比照增量 3 核可工具」,但增量 3 的核可工具裡「操作人」(`approver`)是簽進有金鑰保護的核可憑證裡的欄位,而且在 `issue()` 裡有 `is_id(approver)` 格式檢查(`/Users/enzo/rtb-3b/src/rtb/executor/approval.py:79-80`)——不只是稽核用的自由文字,是被簽章綁定、寫入前就驗過格式的欄位。重放指令的「操作人」依 spec 字面只是「輸入任務、修訂、操作人」三個參數之一,沒有提到要不要驗格式(比照 `is_id`)、要不要簽章或任何身份佐證,單純看起來會被原樣寫進死信操作稽核表的「操作人」欄。如果字面照抄實作,這欄可能收到空字串、超長字串或任意文字,「比照增量 3 核可工具」這句話的字面對不上核可工具實際的驗證力度。

建議在最小設計里明講操作人欄至少要過 `is_id` 這類既有格式檢查(不必到簽章等級,合乎「防忘記不防繞過」的宣告威脅模型),否則「稽核裡操作人從哪來」目前的答案是「呼叫端傳什麼就存什麼,沒有查證」。

以下是核對過、跟 spec 或既有程式一致、不構成發現的觀察:

**「只增不改、不被清理」是否跟既有收件口清理慣例衝突**:不衝突,而且 spec 對這件事的描述本身就是精確的。`_purge_finished_tasks`(`/Users/enzo/rtb-3b/src/rtb/executor/inbox_store.py:521-533`)只刪 `proposals` 表裡「沒有待處理也沒有處理中(`OPEN` 巨集,含核可中)、而且最後收件時間超過保留期(2 小時)」的整個任務,死信處置(`disposition = 'dead_letter'`)不算在 `OPEN` 裡,所以死信任務確實會被這個既有清理邏輯連根清掉——跟計劃「現況」段落寫的「死信紀錄不耐久」完全吻合。信封表、稽核表是收件口模組裡另開的獨立表,不在 `_purge_finished_tasks` 的 `DELETE FROM proposals` 範圍內,所以「收件表清掉那份提案之後,信封應仍在」(S500)這個要求在既有清理邏輯下自然成立,不需要額外排除規則。

**[S510] 舊庫重建流程夠不夠**:機制上足夠,而且是已驗證過的既有路徑。新增兩張表(信封、稽核)只是把 `CREATE TABLE IF NOT EXISTS ...` 接進 `SCHEMA` 常數,對任何新舊資料庫在 `connect()` 時都會自動建表,不需要特殊遷移。真正需要遷移的是 `BlockCode` 新增 `policy_version_changed`、`decision_stale` 兩個成員後,`proposals` 表的 `block_code` 欄位 `CHECK` 限制字面值要跟著更新——這一段已有 `_proposals_outdated()`(逐一比對列舉值是否都出現在 `sqlite_master` 存的建表 SQL 裡,`/Users/enzo/rtb-3b/src/rtb/executor/inbox_store.py:385-396`)加 `_rebuild_proposals()`(建新表、搬資料、改名,`inbox_store.py:417-429`)這條路徑處理,而且這正是 Phase 6 增量 3 加 `AWAITING_APPROVAL`、`BUDGET_INCREASE_TOO_LARGE` 兩個新成員(同時新增 `approvals`/`approval_uses` 兩張全新表)時已經走過、目前在 main 上跑著的同一條路徑,不是本次才要新驗證的機制。換句話說 [S510] 對應的實作負擔只是「把新表定義接進 `SCHEMA`、把新成員加進 `BlockCode`」,既有補欄位/重建流程不用改。

**兩張新表會不會無上限成長**:會,但這是既有慣例下的已知取捨,不是這份 spec 特有的新風險。`write_stops`、`approvals`、`approval_uses`、`attempts` 四張既有表全部沒有刪除路徑(用 `grep -rn "DELETE FROM"` 核對過,只有 `inbox_events` 按事件代碼保留最新 200 筆);`proposals` 表本身雖有 `MAX_ROWS`=5000 的總量上限,但那是靠 `_purge_finished_tasks` 定期清理維持的,信封表/稽核表明確選擇不清理(才能撐住「收件表清掉、信封還在」這個合約),所以會單調成長。這跟既有稽核類表的做法一致,不構成單獨的行為錯誤,只是 F2 提到的索引缺口會讓這個成長在查詢面上比 `write_stops` 更早出問題。
