# r2-v2 審查:失敗語意與併發

實驗環境:python3.14 / sqlite 3.53.3(與計劃宣稱的版本一致)。實驗內容與結果見末段「已查證」。

## Findings

### 1. 寫結果沒有 fencing,lease 到期後原 worker 晚到會覆蓋或雙寫
severity: major
blocking: 是 照字面實作,lease 到期後兩個 worker 都能合法寫結果與 ACK,會出現雙寫或對帳結果被覆蓋。

- 問題:計劃只說接手前「要先確認原 owner 的 lease 已到期」,但沒有規定「寫結果」交易要以 owner(或 fencing token / attempt 序號)為條件。原 worker 若只是慢(DSP 延遲回應模式本來就會超過 lease),lease 到期後對帳者接手,原 worker 隨後醒來,照樣提交「寫結果」與 ACK。
- 後果一:對帳者已標成功或已依「查無此鍵」以同鍵重送,原 worker 又寫一筆結果,狀態與事件分岔。
- 後果二:原 worker 的 ACK 會消掉已被重新投遞給別人的訊息。
- 後果三:沒有 lease 續租(heartbeat)機制,延遲回應自己就能把活 worker 變成「疑似當機」。
- 缺口:唯一鍵撞到時「取回舊紀錄」之後,舊紀錄若是 5xx 失敗的暫時性錯誤,合法重試要怎麼把同一列從失敗轉回嘗試中,沒有以 owner 為條件的比較並交換(CAS)轉換規則。
- 佐證:
引句:「紀錄帶 owner 與 lease 到期時間」
引句:「呼叫期間不持有任何交易;結果不明時走對帳」
- file: `/Users/enzo/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md:768`(18.3 節「remote commit 後 timeout」與「concurrent actor」兩題,計劃沒有以此作答)
- 建議:結果寫回與 ACK 一律 `UPDATE ... WHERE key=? AND owner=? AND lease_token=?`,影響列數為 0 就放棄寫入並進對帳;補 lease 續租或規定 lease 必須大於 DSP 呼叫逾時上限加安全邊際。

### 2. 「查無此鍵就等窗口後重送」的窗口無定義,且重送繞過重新驗證
severity: major
blocking: 是 窗口過短會在原請求仍在 DSP 內處理時誤判「沒做」;重送又不經授權閘,會讓過期決定被執行。

- 問題一:窗口沒有定義。安全下限至少是「DSP 單請求最長處理時間(含延遲回應注入)加客戶端逾時加時鐘誤差」;計劃的故障模式含「延遲回應」與「提交後逾時」,DSP handler 可以在客戶端已逾時之後才提交。窗口若短於此,對帳查到「查無此鍵」時原請求其實還在途,同鍵重送雖然被 DSP 冪等擋住,但「維持結果不明、不下結論」這一步(handoff 7.3)被略過,且重送與原請求並行時 DSP 必須對同鍵序列化,計劃只在 Phase 1 驗收提了一句並行。
- 問題二:重送發生在對帳流程內,判定表沒說重送前要不要重新過授權閘(決定有效期、核准有效性、總曝險額度、政策版本)。handoff 第 13 節與 7.3 第 4 步要求比較「policy-valid current state」。等窗口期間核准可能過期,照字面重送就是把過期決定執行。
- 問題三:判定表只有標成功、標失敗、重送、過期、維持不明五種出口,缺 handoff 7.3 第 5 步的 compensate、abandon,以及重送前的「安全重試」資格判斷。
- 佐證:
引句:「不能直接當成沒做(請求可能還在途);等過一個約定的窗口後」
引句:「對帳查詢本身逾時 → 維持結果不明,超過上限升級人工」
- file: `/Users/enzo/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md:226`
- file: `/Users/enzo/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md:360`
- 建議:窗口定為推導式(大於 DSP 最大處理時間與客戶端逾時之和),重送前強制重跑授權閘,並在判定表補 compensate 與 abandon。

### 3. 結果不明期間沒有暫停同範圍寫入,額度預留也沒說明怎麼處理
severity: major
blocking: 是 handoff 7.3 第 2 步明文要求暫停同範圍危險寫入,計劃漏掉;額度處理錯誤會讓並行 worker 超額。

- 問題一:handoff 要求 UNKNOWN_OUTCOME 時「暫停相同 scope 的危險後續寫入,或以明確策略序列化」。計劃的「嘗試中」表只對冪等鍵唯一,沒有對 campaign(或租戶)範圍的互斥。同一 campaign 上另一個 task 產生不同 payload,就是不同鍵,可在前一筆結果不明時照樣送出。若 DSP 版本樂觀鎖沒被寫成必備條件,就沒有任何東西擋它。
- 問題二:總曝險額度預留在單一交易內完成,但結果不明時預留要保留、釋放還是沿用,沒有規定。釋放會讓 DSP 其實已套用的變更不計入曝險,並行 worker 因此超額;這正是 F7 要擋的事。
- 佐證:
引句:「預留要在單一寫入交易內完成」
引句:「結果不明時走對帳。細節見下節。」
- file: `/Users/enzo/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md:226`
- 建議:結果不明時預留維持占用直到對帳結案;對帳期間對同 campaign 加互斥(狀態列或鎖列),並把「寫入必帶預期版本」寫進 Execution 的最小設計。

### 4. 佇列 lease 與「嘗試中」lease 的關係與 attempt 上限未定,可能把結果不明送進 DLQ
severity: major
blocking: 是 兩把 lease 若不一致,或 attempt 計數與 DLQ 只看次數,結果不明的操作會被當一般失敗處理。

- 問題一:佇列訊息有 lease,嘗試中紀錄又有 lease,計劃沒說是同一個還是兩個、誰長誰短。訊息 lease 較短會在 worker 還在等 DSP 時重新投遞,新 worker 撞唯一鍵取回舊紀錄後「下一步做什麼」沒寫:是等、是對帳、還是重送。字面「取回舊紀錄,不新增」可被實作成取回後直接再發一次 HTTP。
- 問題二:每次重新投遞 attempt 加一,超過上限進 DLQ。若那筆操作的嘗試中紀錄尚是結果不明,DLQ 收到的是「失敗」,handoff 第 13 節要求重放時驗證「idempotency／先前 operation outcome」,但計劃沒有規定進 DLQ 前必須先對帳結案,或至少在 DLQ 信封標明結果不明。
- 問題三:ACK 與 durable 結果同一交易只涵蓋本地一半。最危險的窗口(DSP 已提交、本地結果尚未寫)完全不在這個交易內,計劃卻說它讓當機視窗「有可預測的模型」,措辭過度。
- 佐證:
引句:「超過重試上限或永久錯誤進 DLQ 表並保留失敗脈絡與 trace 連結」
引句:「這讓 Phase 4 的當機視窗有可預測的模型」
引句:「第二個 worker 或重送的插入撞到唯一鍵時,取回舊紀錄,不新增」
- file: `/Users/enzo/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md:360`
- 建議:寫明取回舊紀錄後的分支(依狀態:結果不明就走對帳,不得直送);規定結果不明的操作不計入重試上限、不得直接進 DLQ。

### 5. 「同一把鍵的並行請求只套用一次」的驗收斷言可被有競態的實作輕易通過
severity: major
blocking: 是 這條是 handoff 並行安全的核心證據,現有斷言沒有強制重疊,證明力不足。

- 問題:只寫「只套用一次」,沒有規定並行度、如何保證請求真的在 DSP 內重疊(柵欄同步啟動、或用延遲回應模式讓 handler 在提交前暫停)、斷言什麼(歷史長度剛好一筆、版本加一、所有回應內容一致、只有一個非重送回應)、也沒要求像 50 次判準那樣重複執行。ThreadingHTTPServer 加 SQLite 若請求恰好被序列化,先查後插的有競態實作也會過。
- 另一缺口:同鍵不同內容並行(其中一個必須被拒)沒有測試;Phase 1 也沒有 agent 端「兩個 worker 同時插入嘗試中」的唯一約束並行測試,而這是 agent 端雙寫的第一道防線,計劃放在 Phase 4 或以後才驗。
- 佐證:
引句:「同一把鍵的並行請求:只套用一次。」
- file: `/Users/enzo/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md:545`(並行 worker 不能競態超額)
- 建議:驗收改為「N 個(例如 20)請求以柵欄同時放行,並用 DSP 提交前延遲讓它們必然重疊;斷言歷史剛好一筆、版本加一、其餘回應為重送結果;重複 50 次」,並先有一個故意去掉唯一約束的對照實作要能被測出雙寫。

### 6. 冪等鍵含 task_id,DLQ 重放若產生新 task 會得到新鍵而雙寫;同鍵不同內容從 agent 端不可達
severity: minor
blocking: 否 屬 Phase 8 才發作的設計精度問題,現階段可補一句約束解決。

- 問題一:鍵由 `task_id` 等導出,計劃沒說 DLQ 重放與重新領取是否沿用原 task_id。若重放建立新 task,同一邏輯操作就得到新鍵,DSP 冪等擋不住,只剩版本鎖;handoff 第 13 節要求重放要驗「先前 operation outcome」。
- 問題二:鍵已包含 payload 雜湊,agent 自己不可能發出「同鍵不同內容」,所以「agent 端也要有同樣的守衛」只能被人工注入測試觸發,價值是防實作錯誤;應寫明它守的是雜湊碰撞或實作 bug,不是常態路徑。
- 佐證:
引句:「同一個邏輯操作無論重送、重試、重跑,拿到的永遠是同一把鍵。」
引句:「同鍵不同內容在 DSP 端會被拒絕,agent 端也要有同樣的守衛」

### 7. 「先讀後寫」對照實作在 WAL 下不會超額而會報 database is locked
severity: minor
blocking: 否 只影響 Phase 6 測試怎麼寫,不影響 Phase 0 設計結論。

- 問題:計劃要求對照實作「真的超額」。實驗顯示,在 WAL 加 busy_timeout 下,先開延遲交易讀、他人已提交寫入後再嘗試寫,會直接得到 `database is locked`(快照過期的升級失敗,busy_timeout 不會等),不會超額。對照實作必須把讀與寫拆成兩個獨立自動提交才會超額;計劃沒寫清,照字面做出的對照組可能永遠不超額,測試就證明不了原子版比較好。
- 佐證:
引句:「測試必須先有一個故意做成」
