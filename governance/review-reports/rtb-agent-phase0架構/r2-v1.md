### F1 Phase 1 驗收仍證明不了自己列的範圍(原 s1 F2、s2 F5)

severity: major
blocking: 是 — 驗收段自稱每條都是機械斷言,但範圍內四項承諾沒有任何斷言,Phase 1 照驗收過關仍可能漏做,與 r1 指出的缺口同型。

- 問題:
  1. 範圍要求版本單調遞增、記錄收到時間與提交時間,驗收沒有任何一條驗版本單調(連續多次操作)、也沒有驗兩個時間欄位存在且提交不早於收到。
  2. 範圍要求「型別化的錯誤」,驗收沒有斷言錯誤類型(暫時性、永久、版本衝突)可被呼叫端區分。
  3. 「不使用 LLM 做任何確定性計算」只在範圍,驗收沒有機械判準;r1 已指出,r2 仍未補(可用 ruff 匯入規則禁止指標計算模組 import 模型用戶端,並列入驗收)。

### F2 「同鍵不同內容」的 agent 端守衛在新設計下無法發生(新舊銜接矛盾)

severity: minor

- 問題:新補的冪等鍵導出包含正規化 payload 的雜湊,所以 payload 一變鍵就變(計劃同節也這樣寫)。緊接著又要求 agent 端對「同鍵不同內容」設守衛,兩句合起來,agent 端這條守衛要嘛永遠不會觸發、要嘛意指鍵不含完整 payload,與導出公式矛盾。應寫明守衛的實際對象(例如雜湊碰撞、或正規化欄位以外的內容變動)。

### F3 「嘗試中」的 lease 沒有續期,且與佇列的 lease 關係未定(原 s2 F3 所有權部分只修一半)

severity: minor
blocking: 否 — 冪等鍵可擋住雙寫,最壞是多餘的對帳與重送,屬效率與誤判問題,Phase 3 前定稿即可。

- 問題:r1 要的是 owner、lease、heartbeat 或到期時間。r2 補了 owner 與到期時間,但沒有續期(heartbeat),也沒有規定 lease 必須長於 DSP 呼叫逾時加重試上限。慢速但仍活著的 worker 一旦 lease 先到期,別人就把它當成當機接手對帳,這正是 r1 要防的情境。另外佇列訊息有 lease,「嘗試中」紀錄也有 lease,兩者是同一個還是兩個、到期時誰先動,沒說。ACK 規則也沒說「結果不明」算不算已寫入 durable 結果(算的話誰驅動後續對帳,不算的話不能 ACK)。
- 佐證:
- 引句:「要先確認原 owner 的 lease 已到期,才可接手對帳」

### F4 核准表「只能由獨立指令寫入」沒有強制手段,身分驗證也沒寫(原 s3 F6 只修一半)

severity: minor
