# RTB_Agent_Phase0架構

PRIOR-ART: 最小解是「行程內函式加本地檔案」,但它測不出外部寫入的真實失敗;世界上已有現成的至少一次佇列與伺服器型資料庫,但本專案是教學與驗證用 Demo,自建的部分只限「能重現失敗語意」的最小替身。執行期只用 Python 標準函式庫(sqlite3、http.server、urllib);開發期工具 pytest 與 ruff 是明確的例外,見決策 d6、d8。
RETIRE-IF: 若 Phase 1 到 Phase 4 做完後,SQLite 模擬的佇列與獨立行程 DSP 仍抓不到任何一個 F1 到 F3 事故,而換成真實外部系統才抓得到,這套替身就該換掉。
RETIRE-IF: 執行路徑只要 import 了標準函式庫以外的套件,「只有開發工具是例外」這條就失效,該把例外清單重審;Phase 1 起由 ruff 的匯入規則機械檢查。

## 這份計劃在解決什麼

- 名詞:DSP 是廣告需求方平台,也就是真實世界裡實際接受改預算、暫停廣告的外部系統,本專案用模擬器代替;CTR 是點擊率、CVR 是轉換率、ROAS 是廣告投資報酬率、Pacing 是預算花費進度,都由純程式計算。EXTERNALLY-MANAGED 是 Python 安裝目錄裡的標記檔,代表這個 Python 由系統套件管理器管理,不准 pip 直接安裝套件。
- 專案來源是交接文件 `~/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md`(在 repo 之外,計劃引用它的章節號),目標是做一個能在逾時、當機、重送、並行、提示注入、過期 DLQ 決定與總曝險下安全運作的廣告 Agent,並用證據清單加機械式檢查程式證明。
- 這一篇只管 Phase 0:定最小架構、信任邊界、決策紀錄,並約定 Phase 1 的範圍。**不含任何程式碼。**

## 元件與信任邊界

```
   即時流程畫面 / 指標後台(只讀,以唯讀模式開啟資料庫)
                       │ 讀
                       ▼
  ┌──── Agent 系統(自己的 SQLite)────────────────────┐
  │ 佇列表 / 任務狀態 / 檢查點 / 事件 / 稽核 / 風險額度 │
  │ 核准表(只能由獨立的核准指令寫入)                  │
  │                                                    │
  │ 分析端:持有模型金鑰與 DSP 讀取令牌,無寫入權限     │
  │        ↓ 只產出「提案」                             │
  │ 政策與授權閘(純程式,版本化)                        │
  │        ↓ 授權後才交給                                │
  │ 執行端:唯一持有 DSP 寫入令牌                        │
  └──────────────────────┬─────────────────────────────┘
                         │ HTTP(唯一通道,讀寫用不同令牌)
                         ▼
  ┌──── Mock DSP(獨立行程,自己的儲存)────────────────┐
  │ 業務介面:廣告狀態 / 版本 / 操作紀錄 / 冪等鍵紀錄     │
  │ 控制面:故障注入,獨立連接埠,啟動旗標開啟才存在     │
  └────────────────────────────────────────────────────┘
```

- **不可信的輸入**:廣告名稱、素材文字、落地頁、DSP 中繼資料、工具回傳內容。一律當資料,不能變成權限。這條同時管兩個方向:往決策的方向不能變權限;往顯示的方向,進事件表時要帶信任標記,顯示層要跳脫並限制長度,這個格式在 Phase 2 定事件結構時就要固定,不等到 Phase 9。
- **可信的來源**:政策引擎的規則、由授權閘從可信上下文綁定的租戶身分(tenant)、資源身分、金額上限與有效期。
- **權限邊界**:分析端不持有 DSP 寫入令牌;寫入只發生在執行端,且要通過交接文件第 8 節的檢查閘。Mock DSP 會以令牌區分讀與寫,讓「分析端呼叫寫入」能被 DSP 端拒絕、能被測試證明。DSP 的令牌區分放在 Phase 3(Side Effect Gate)之前完成。
- **DSP 是外部事實來源**:agent 只能走公開介面加查詢介面。「不能開 DSP 的儲存檔案、不能 import DSP 的內部模組」要寫成機械檢查:一支測試掃 agent 端程式的匯入與檔案路徑,發現就紅。
- **故障注入控制面**:與業務介面不同連接埠,DSP 要用啟動旗標才開,agent 端的設定與客戶端程式裡不含控制面位址,並有一支測試證明 agent 的 HTTP 客戶端連不到控制面。故障模式以「單一請求」為單位(標頭或參數指定),避免全域狀態讓並行請求互相污染。
- **唯讀怎麼保證**:畫面與後台以唯讀模式(SQLite URI 的 mode=ro)開啟資料庫,搭配 WAL,讓讀者不擋寫入者。核准不走畫面。
- **核准通道(HITL)**:核准是一筆存在核准表裡的紀錄,綁定核准者身分、動作範圍、租戶與資源、金額上限、提案雜湊、政策版本與有效期;只能由獨立的核准指令寫入,畫面沒有寫入路徑。實作在 Phase 6,這裡只定位置。
- **分析端會對外連線**:分析端要呼叫模型 API,所以「agent 不連任何外部網路」只在 Phase 1 之前成立。分析端持有模型金鑰,而且它是處理不可信文字的那一端,所以它的環境變數與可讀檔案範圍要限縮,並列入 Phase 7 的注入測試。

### 七項元件各自的最小設計

- **State store(狀態儲存):** 一個 SQLite 檔。任務狀態用一張明確的轉換表定義哪些轉換合法;檢查點只記「可安全恢復的進度」,不代表外部事實。
- **Queue(佇列):** 用一張資料表模擬至少一次投遞。訊息有 `lease` 到期時間與 `attempt` 計數;worker 領取時寫入 owner 與到期時間;超過重試上限或永久錯誤進 DLQ 表並保留失敗脈絡與 trace 連結。**ACK 規則:把訊息標為已處理,與寫入 durable 結果放在同一個交易裡**,且 lease 到期才會重新投遞。這讓 Phase 4 的當機視窗有可預測的模型。
- **Mock DSP:** 見上圖與 Phase 1。
- **Analysis(分析):** 依交接文件第 4 節分流:確定性計算與規則走純程式;模糊的多證據推理才給 LLM;外部資訊與動作走工具。分析端只輸出符合 schema 的提案,不能產生或擴大權限。LLM 的失敗一律走回退(重試、降級、轉人工),不放行。
- **Policy(政策):** 交接文件第 8 節的檢查,每一道寫成一個有名字的小函式,依序組成流程。總曝險預留是一張以「租戶、批次、時間窗」為鍵的額度表,預留要在單一寫入交易內完成。
- **Execution(執行):** 呼叫前先提交「嘗試中」紀錄;呼叫期間不持有任何交易;結果不明時走對帳。細節見下節。
- **Observability(可觀測):** 每個邏輯任務一個 `trace_id`,由事件表串起;事件表欄位含 `trace_id`、`task_id`、`tenant_id`、`campaign_id`、`decision_id`、`operation_id`、`idempotency_key`、`worker_id`、`attempt`、`policy_version`。稽核表只追加、不修改。指標標籤只用低基數欄位(租戶、工具、錯誤類別、階段),`campaign_id` 與 `trace_id` 留在事件裡不進指標標籤。

## 外部寫入的失敗語意(交接文件 18.3 節的答案要點)

- **冪等鍵怎麼產生:** 由 `tenant_id`、`task_id`、`campaign_id`、動作類型與正規化後的 payload 決定性導出(雜湊),不是隨機值。同一個邏輯操作無論重送、重試、重跑,拿到的永遠是同一把鍵。
- **「嘗試中」表:** 對邏輯操作有唯一約束;第二個 worker 或重送的插入撞到唯一鍵時,取回舊紀錄,不新增。
- **payload 變了:** 重新分析後內容不同,視為新的邏輯操作、新的鍵,舊提案標記為過期。同鍵不同內容在 DSP 端會被拒絕,agent 端也要有同樣的守衛。
- **交易邊界:** 「寫嘗試中」是一個短交易,提交後才發 HTTP 請求;「寫結果」是另一個短交易。**HTTP 呼叫期間不得持有任何開著的交易**,否則延遲回應會鎖住所有其他寫入者,而且回滾會抹掉「嘗試中」紀錄、讓 d3 失效。每個 worker 用自己的連線,設定 WAL、`busy_timeout`,寫入交易用 `BEGIN IMMEDIATE`。
- **誰擁有「嘗試中」:** 紀錄帶 owner 與 lease 到期時間。別的 worker 看到「有開始沒結果」時,要先確認原 owner 的 lease 已到期,才可接手對帳,避免把「仍在等 DSP 的活 worker」誤判成當機。
- **對帳判定表**(細節在 Phase 3 前定稿,並要先答完交接文件 18.3 節的十題):
  - DSP 查得到同鍵且成功 → 標記成功,驗證實際狀態符合意圖。
  - DSP 查得到同鍵且被拒 → 標記失敗,依錯誤類別處理。
  - DSP 查無此鍵 → 不能直接當成沒做(請求可能還在途);等過一個約定的窗口後,以**同一把鍵**重送,由 DSP 冪等擋住重複。
  - DSP 版本已被別人推進 → 舊提案過期,重新讀取並重新分析,不強制覆寫。
  - 對帳查詢本身逾時 → 維持結果不明,超過上限升級人工。
- **來源:** DSP 的操作紀錄與目前狀態是事實來源,不是本地例外類型。

## 決策(細節與四欄在筆記的 decisions 欄位)

- WHY: agent 狀態存 SQLite。因為要靠交易讓「狀態、檢查點、稽核」一起提交,用唯一鍵擋重複冪等鍵,用版本欄位做樂觀鎖。出處:對話 2026-09-21。
- WHY: DSP 用獨立行程加 HTTP,儲存也獨立。因為共用資料庫或行程內呼叫,會讓「DSP 已寫入但 agent 沒收到回應」這個事故測不出來。出處:對話 2026-09-21。
- WHY: agent 呼叫外部系統前,先寫入並提交「嘗試中」紀錄(含冪等鍵)。因為沒有這筆紀錄,行程當掉後 agent 不知道曾經嘗試過,會用新鍵重做。出處:對話 2026-09-21。
- WHY: 即時畫面與後台只讀不寫指令。因為能觸發執行的介面會變成繞過安全檢查的第二條路。出處:對話 2026-09-21。

## 程式結構原則(clean code)

- **純判斷和外部動作分開。** 「這個動作准不准做」是純函式,輸入資料、輸出結果,不碰網路和資料庫;真正去改 DSP、寫資料庫是另一層。
- **依賴方向往內。** 領域規則與政策不 import sqlite3 或任何網路模組;資料庫與 DSP 客戶端透過小介面接進來。ruff 的匯入規則機械檢查這一條。
- **一個模組一件事。** 政策的十一道檢查各是一個小函式;不寫上百行、滿是 if 的大函式。
- **狀態機是資料。** 合法的狀態轉換寫成一張表,不散落在各處的條件判斷。
- **命名說明意圖。** 例如「結果不明」,不叫 flag。
- **不過度抽象。** 只在「確實有兩種實作」或「需要隔離外部世界」時才切介面(交接文件 18.5 節)。
- **驗證方式:** ruff 規定函式長度與複雜度上限,並檢查領域層匯入;命名與切分是否合理留給設計審與代碼審判斷,沒有機械判準。

- 驗收(每條都是機械斷言)
  - 四個必要介面加兩個查詢介面都有合約測試。
  - 每一種故障模式各有一條測試,涵蓋版本衝突、5xx、延遲回應。
  - 「提交前逾時」:呼叫端確實觀察到逾時,且 DSP 的操作歷史長度與版本都沒有增加。
  - 「提交後逾時」:呼叫端確實觀察到逾時,且 DSP 的操作歷史多一筆、版本加一,`getOperationByIdempotencyKey` 查得到成功結果。
  - 同鍵同內容重送:回傳原結果,預算與版本不變,歷史沒有第二筆。
  - 同鍵不同內容:被拒絕。
  - 同一把鍵的並行請求:只套用一次。
  - DSP 重啟後,冪等紀錄仍在。
  - 指標計算有正常值、零分母、缺資料、邊界值測試。
  - 控制面隔離測試:agent 的客戶端連不到控制面;匯入檢查測試:agent 端沒有 import DSP 內部模組。

  - pytest fixture 保證測試失敗與逾時路徑也會關閉伺服器與行程,埠一律由系統動態分配,每個測試用獨立的暫存資料庫。
