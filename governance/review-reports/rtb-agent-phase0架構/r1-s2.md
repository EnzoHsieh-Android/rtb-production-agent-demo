### 交易邊界與「嘗試中」的所有權:DSP 呼叫期間不得持交易,並行 worker 會誤判彼此

severity: major
blocking: 是,d3 加 d5 加 d1 三者合起來的字面實作,會在 DSP 呼叫期間持有寫入鎖,或讓活著的 worker 被別人當成當機。

- 計劃段落:d5、d1、d3。
- 引句:「事件與狀態變更放同一個交易。」
- 引句:「取捨:單一寫入者、非分散式,已列入已知限制。」
- 問題一(持鎖):d5 的取捨只寫「交易變大、寫入變慢」,沒有寫「HTTP 呼叫期間不得持有任何開著的交易」。SQLite 的寫入交易期間持有資料庫級寫鎖。若實作者把「嘗試中、呼叫 DSP、結果」包成同一個交易(這是把 d3 與 d5 字面合併最省事的寫法),Mock DSP 的延遲回應或逾時(常見值數秒到數十秒)期間所有其他 worker 寫入都被擋,busy timeout 一到就 database is locked;更糟的是回滾會抹掉「嘗試中」紀錄,d3 的目的當場失效。計劃必須明寫:兩個短交易,中間是無交易的網路呼叫。
- 問題二(所有權):d3 只說「有開始沒結果」歸結果不明。但 redelivery 與多 worker 並行下,另一個 worker 看到的「有開始沒結果」,可能是原 worker 仍在等 DSP 回應(活著,不是當機)。沒有 owner、lease、heartbeat 或到期時間,就會出現兩個 worker 同時對同一 operation 對帳與重送,或把仍在進行的請求當成結果不明而重複處理。handoff 第 9 節「先以穩定 task_id 去重」需要這個機制落地,計劃沒有。
- 問題三(連線設定):計劃沒提 WAL、busy_timeout、BEGIN IMMEDIATE、每個 worker 獨立連線。sqlite3 預設 journal_mode 在檔案庫為 delete;讀者(即時畫面)在寫入交易期間會被擋或看到舊資料。這些是 Phase 4 與 6 的並行測試能不能成立的前提,應在 Phase 0 列為約束,不必留到出事才發現。
- 佐證:實測 python3 sqlite3 預設 journal_mode(記憶體庫回報 memory,檔案庫預設 delete,未另設 WAL);handoff 第 9 節「只有工作已完成、已安全持久化…才 ACK」、第 11.4 節「不能只在 batch 開始前做一次非原子計數」。file: `/Users/enzo/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md:339`、`/Users/enzo/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md:263`。

### http.server 的並行模型與逾時精確度:假設驗證太弱,退路沒有名字

severity: major
blocking: 是,計劃預設用 http.server 卻沒指定伺服器類別;預設 HTTPServer 為單執行緒,照字面做會讓對帳查詢被擋住,F1 前置能力做不出可重現的結果。

- 計劃段落:「已知、假設、待決」的假設一,與「實務隱患」殘留風險。
- 引句:「標準函式庫的 http.server 足以撐住 Mock DSP 的故障注入需求。」
- 引句:「緩解:Phase 1 開頭先做最小實驗,實驗不過就換做法,不硬撐。」
- 實測(python3 3.14.6):
  - `http.server.HTTPServer` 只繼承 `socketserver.TCPServer`,沒有執行緒混入,一次只處理一個請求。file: `/opt/homebrew/Cellar/python@3.14/3.14.6/Frameworks/Python.framework/Versions/3.14/lib/python3.14/http/server.py:141`。
  - `http.server.ThreadingHTTPServer` 才混入 ThreadingMixIn,daemon_threads 為 True。file: `/opt/homebrew/Cellar/python@3.14/3.14.6/Frameworks/Python.framework/Versions/3.14/lib/python3.14/http/server.py:154`。
  - `request_queue_size` 為 5。file: `/opt/homebrew/Cellar/python@3.14/3.14.6/Frameworks/Python.framework/Versions/3.14/lib/python3.14/socketserver.py:444`。
  - 最小實驗:一個 handler 睡 3 秒模擬「提交後延遲回應」,client 逾時 0.5 秒。HTTPServer 下,隨後對同一伺服器的查詢(等同 getOperationByIdempotencyKey)也逾時,實測 1.0 秒逾時,原因是伺服器仍卡在睡眠的 handler;ThreadingHTTPServer 下同一查詢 0.0 秒即回。也就是說,F1 的對帳步驟正是在 DSP 仍處理前一請求時發出,單執行緒版本會把對帳查詢卡死。另外 client 逾時後 handler 寫回應會 BrokenPipeError,標準函式庫預設把 traceback 印到 stderr,測試輸出會被噪音污染。
- 計劃的缺口:
  1. 沒指明用 ThreadingHTTPServer,也沒提 DSP 儲存在多執行緒下的存取方式(SQLite 連線不能跨執行緒共用,或要序列化,DSP 的「commit」時點就取決於此)。
  2. 「提交前逾時」與「提交後逾時」不該靠 sleep 長短與 client 逾時賽跑;睡眠對逾時的相對時序在負載下會飄,這是不可重現的來源。可行做法要由 handler 端顯式決定:提交後逾時可用「提交完成後不回應或直接關閉連線」,提交前逾時可用「收到請求後不提交,並標記放棄」。計劃沒有寫出機制選擇,只寫「能被精確且可重現地觸發」這個結果。
  3. 「提交前逾時」有一個計劃沒顧及的洞:client 逾時斷線後,handler 若仍照原路徑繼續往下執行就會在斷線後提交,結果變成提交後逾時。故障注入必須讓 handler 在此模式下決定性地不提交。
  4. 退路只寫「換做法」,沒有列候選(ThreadingHTTPServer、asyncio 原生 socket 伺服器、直接操作 socket 提早關閉),也沒有把「判定實驗成敗」的判準寫成可執行斷言,例如:對同一請求在 50 次連續執行中,遠端最終狀態 100% 符合宣告的模式。
- 佐證:handoff 第 6.3 節要求兩種逾時可控;第 17 節 Phase 1 DoD 要求「可被精確控制」。file: `/Users/enzo/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md:198`、`/Users/enzo/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md:585`。
- 建議:把假設改寫成有數字的實驗規格(類別=ThreadingHTTPServer;機制=handler 端決定性控制;判準=N 次重複結果一致;失敗退路=具名)。
