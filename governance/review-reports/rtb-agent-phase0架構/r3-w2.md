severity: major

# r3 審查(鏡頭:拆行程後的信任邊界與權限一致性)

## Findings

### F1 唯讀模式被寫成「分析行程不能改寫額度、嘗試中、稽核」,同一作業系統使用者下不成立
severity: major
blocking: 是 判準:照字面實作會以為分析行程被機械擋住寫入,實際被劫持的分析行程可直接以讀寫模式開執行行程的檔,漏掉 handoff 11.1 要的隔離。
問題:計劃把 SQLite 的唯讀模式當成擋寫入的邊界,但唯讀只是打開連線的參數,不是權限。已知限制只承認「金鑰隔離」不是帳號隔離,沒承認檔案寫入同樣沒有隔離。被劫持的分析行程(決策 d9 自己設定的威脅模型)可以改寫執行行程的提案佇列、額度、稽核,也可以動核准檔(核准檔不要金鑰也能刪或替換)。決策 d9 的 why_chosen 寫「假設分析端已被攻破,它手上仍沒有寫入能力」,這句在同一使用者下不成立:攻破後的分析行程可讀執行行程的環境(Linux 的 /proc/PID/environ 同使用者可讀;macOS 的 ps eww 類似,本機我未能驗證出結果)、可讀任何金鑰檔,以及日誌與核心傾印。「可測的事實」沒有對應的測試與階段。
佐證:
引句:「這樣分析行程不能改寫額度、嘗試中或稽核。」
引句:「讓寫入相關金鑰不在分析端記憶體裡成為可測的事實(假設分析端已被攻破,它手上仍沒有寫入能力)」
引句:「金鑰隔離只靠「只傳給該持有的行程」。」
實測:本機 Python sqlite3 以 mode=ro 開的連線寫入會失敗,但同一使用者另開一條普通連線可直接寫入(已跑過)。
修法方向:限制段要明說「同一使用者下,被劫持的分析行程可讀執行行程的環境、檔案與日誌,可寫其資料庫檔;隔離效果只在『分析行程的正常程式路徑沒有這把金鑰』」;d9 的 why_chosen 改成只主張這個較弱的事實;指定金鑰檔或環境變數的傳法(不由同一個父行程統一繼承、子行程啟動前清環境),並在某個階段訂一條驗收(分析行程的環境與其可讀路徑掃描不到簽章金鑰)。

### F2 租戶身分的可信來源在拆行程後消失
severity: major
blocking: 是 判準:照字面實作,租戶只會來自分析行程擁有的任務佇列與提案,授權閘綁定的租戶身分就成了不可信輸入,漏掉 handoff 11.1 的 capability 綁定 tenant。
問題:r2 寫「可信的來源」包含「由執行端從可信上下文綁定的租戶身分」。拆行程後任務佇列歸分析行程,提案也歸分析行程,執行行程只能從分析行程的檔讀到任務與提案,並登記進自己的提案佇列。計劃沒說執行行程的「可信上下文」在拆分後從哪裡來;唯一來源是分析行程可寫的檔。被劫持的分析行程可以把提案的租戶換成別的租戶,執行行程沒有獨立來源核對,簽發的能力憑證也就綁到錯的租戶。
佐證:
引句:「由執行端從可信上下文綁定的租戶身分、資源身分、金額上限與有效期。」
引句:「任務佇列由分析行程領取,提案佇列由執行行程領取。」
修法方向:指定租戶與金額上限的獨立來源(例如執行行程啟動時載入的租戶設定檔或它自己的檔),提案裡的租戶只當索引,不當授權依據;交接細節的定稿要把這一條列為必答。

### F3 執行行程讀分析行程的檔,計劃沒把這條讀取路徑列為攻擊面
severity: major
blocking: 是 判準:計劃只把提案內容當不可信,沒防提案所在的檔案本身,照字面實作出的讀取程式會被構造的檔或超大內容拖垮或誤導,而執行端是最該穩定的一端。
問題:計劃反覆說提案是不可信輸入,但驗證的對象只是內容語意(重跑政策閘)。它沒有規範讀取這個動作本身:提案欄位大小與列數上限、JSON 深度、只讀固定欄位名的查詢(不吃分析行程可改的 schema、視圖、觸發器,不靠 SELECT *)、不信任 rowid 與序號的單調、SQLite 檔本身被構造(損毀頁、超大 blob、惡意 schema 讓讀取卡死或吃盡記憶體)的處理、讀取失敗時的行為(必須是拒收並記事件,不能當機或放行)。計劃只把「大小限制」留給 Phase 7 且只針對工具回傳。此外對 WAL 檔以唯讀開,需要 -shm 可寫或目錄可寫,唯讀讀者也會拖住 checkpoint,這兩點計劃沒提。更穩的交接是分析行程把提案以有大小上限的訊息交給執行行程(本機 socket 或執行行程自己擁有的收件表),而不是讓執行行程去打開對方的資料庫檔;這個替代方案 d9 沒有評估。
佐證:
引句:「執行行程以唯讀方式讀到提案,把它登記進自己的提案佇列,之後全部以自己的檔為準。」
引句:「工具回傳的型別化解析、大小限制、白名單正規化(交接文件第 12 節)與 Evidence 層的 provenance 與信任分類,留到 Phase 7 補」
修法方向:在行程切分段加一條「跨行程讀取的防守」:固定欄位查詢、欄位與列數上限、超限或解析失敗一律拒收並記事件、開啟時關閉不必要的功能(例如 trusted_schema 關閉);或改成執行行程擁有的收件通道。交接細節的必答清單也要包含這條。

### F4 圖與文字的持有物不一致(讀取令牌、簽章金鑰、核准指令)
severity: major
blocking: 是 判準:憑證持有者是本案最核心的安全宣稱,圖與文字對不上時,實作者無法照字面決定誰拿哪把。
問題:一、文字說執行端「用自己的讀取令牌重新讀 DSP 現況」,圖裡執行行程只列「簽章金鑰、能力憑證簽發」,沒有讀取令牌;同時圖裡分析行程持有讀取令牌,卻沒有任何箭頭指向 DSP,無法看出它讀 DSP 的路徑。兩個行程是共用同一把讀取令牌還是各一把,沒說。二、圖只寫「簽章金鑰」一個詞,但文字有兩把不同的簽章:核准簽章(核准指令與執行端持有)與能力憑證簽發(DSP 驗證)。純標準函式庫下這兩把大概是 HMAC 對稱金鑰,執行行程既能驗簽也能偽造核准,DSP 也要持有同一把才能驗能力憑證;圖與文字沒有交代誰持有驗證端,也沒承認「執行端持有核准金鑰=能偽造核准」這個限制。三、圖裡「核准指令」只出現在括號內,不是元件,沒有它的持有物。四、畫面的「讀 DSP 查詢介面」箭頭在圖上落在執行行程的方框,看起來是讀執行行程而非 DSP。
佐證:
引句:「執行端拿到提案後,用自己的讀取令牌重新讀 DSP 現況,自己重跑整套檢查,通過才發出寫入。」
引句:「每筆核准帶簽章,簽章金鑰只有核准指令與執行端持有,分析端沒有」
引句:「│ 持有:簽章金鑰、能力憑證簽發          │」
修法方向:圖改成列出兩把金鑰各自的持有者與驗證者、讀取令牌歸屬,補分析行程到 DSP 的讀取箭頭,把核准指令畫成元件;已知限制補「對稱金鑰下執行端可偽造核准」(或註明改用非對稱簽章需要非標準函式庫)。

### F5 專案自己的決策清單與 lease 說明留有拆行程前的舊語意
severity: minor
blocking: 否 判準:只是舊文字與新結構不一致,不會單獨導致錯誤實作,但會誤導後讀者。
問題:一、「WHY: 事件與狀態變更放同一個交易」以及 State store 段「狀態、檢查點、稽核一起提交」在拆行程後,提案交接跨兩個資料庫檔,沒有單一交易可用;計劃只說交接細節後補,沒有把這條舊決策標為受影響。二、佇列段說那一把 lease「同時管佇列訊息與嘗試中紀錄」,但任務佇列在分析行程的檔,嘗試中紀錄在執行行程的檔,這句只對提案佇列成立。三、狀態儲存段仍寫「一個 SQLite 檔」。
佐證:
引句:「這把 lease 同時管佇列訊息與「嘗試中」紀錄,不存在兩把。」
引句:「一個 SQLite 檔。任務狀態用一張明確的轉換表定義哪些轉換合法」
修法方向:三處各加一句「僅限執行行程的檔內」或改成兩檔說法,並把 WHY 的事件交易那條註明「跨行程交接不在此交易內,見 Phase 3 定稿」。

### F6 Phase 2 與驗收沒有指明拆行程在哪個階段落地、金鑰隔離無驗收
severity: minor
blocking: 否 判準:Phase 1 範圍不受影響,只是後續階段的驗收缺口,可在 Phase 2 或 3 開審時補。
問題:Phase 1 不含任何 agent 端程式,拆行程確實不影響它。但 handoff 的 Phase 2 是單一 campaign 的 happy path 且要求一條 trace 連得起 Evidence 到 verification;計劃沒說 Phase 2 是否已是兩個行程,以及跨兩個事件表串 trace 的驗收落在哪。d9 說的「可測的事實」(分析行程環境與可讀檔案裡沒有簽章金鑰)沒有指定任何階段的斷言,只有 Phase 7 的注入測試被提到。
佐證:
引句:「交接細節(領取、去重、交接後的分析端如何得知結果)在 Phase 3 開工前定稿,事件入口就是 Phase 3 的設計審。」
引句:「所以「分析行程讀不到簽章金鑰」靠的是金鑰只傳給執行行程」
修法方向:在 Phase 2 或 3 的範圍列入「兩行程啟動與環境掃描斷言」,並註明 Phase 2 是單行程或兩行程。

- Phase 1 範圍與驗收:拆行程不波及 Phase 1(DSP 與指標計算),無需改。
