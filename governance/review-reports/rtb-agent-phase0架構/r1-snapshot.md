# RTB_Agent_Phase0架構

PRIOR-ART: 最小解是「行程內函式加本地檔案」,但它測不出外部寫入的真實失敗;世界上已有現成的 at-least-once 佇列與分散式資料庫,但本專案是教學與驗證用 Demo,自建的部分只限「能重現失敗語意」的最小替身,其餘採用 Python 標準函式庫(sqlite3、http.server、urllib),不引入框架。
RETIRE-IF: 若 Phase 1 到 Phase 4 做完後,SQLite 模擬的佇列與獨立行程 DSP 仍抓不到任何一個 F1 到 F3 事故,而換成真實外部系統才抓得到,這套替身就該換掉。

## 這份計劃在解決什麼

- 名詞:DSP 是廣告需求方平台,也就是真實世界裡實際接受改預算、暫停廣告的外部系統,本專案用模擬器代替;CTR 是點擊率、CVR 是轉換率、ROAS 是廣告投資報酬率、Pacing 是預算花費進度,都由純程式計算。EXTERNALLY-MANAGED 是 Python 安裝目錄裡的標記檔,代表這個 Python 由系統套件管理器管理,不准 pip 直接安裝套件。
- 專案來源是交接文件 `~/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md`,目標是做一個能在逾時、當機、重送、並行、提示注入、過期 DLQ 決定與總曝險下安全運作的廣告 Agent,並用證據清單加機械式檢查程式證明。
- 這一篇只管 Phase 0:定最小架構、信任邊界、決策紀錄,並約定 Phase 1 的範圍。**不含任何程式碼。**

## 已知、假設、待決

- 已知
  - 技術路線是 Python 3.14.6;內建 sqlite3 版本 3.53.3,不需安裝。
  - 專案資料夾原本是空的,lumos 已配好,提交前與推送前的檢查已啟用。
- 假設(還沒驗證)
  - 標準函式庫的 http.server 足以撐住 Mock DSP 的故障注入需求。Phase 1 開頭要先用最小實驗驗證,不行就換。
  - SQLite 的寫入鎖能重現「多 worker 搶總曝險額度」的競態。Phase 6 才會驗證,現在只是預期。
- 待決
  - 指標後台與即時流程畫面的前端技術,留到 Phase 9 前決定。
  - SLO 的具體數值,交接文件要求由我提案、使用者依 Demo 負載判斷,Phase 9 處理。

## 元件與信任邊界

```
                        (只讀)
  即時流程畫面 ─────────────┐
  指標後台      ─────────────┤
                            ▼
  ┌───────── Agent 行程(agent 自己的 SQLite)─────────┐
  │ 佇列表 / 任務狀態 / 檢查點 / 事件 / 稽核 / 風險額度 │
  │                                                  │
  │ 分析端(無寫入權限)→ 提案                         │
  │        ↓                                         │
  │ 政策與執行閘(純程式,版本化)                      │
  │        ↓ 只有這一層持有 DSP 寫入憑證              │
  │ 執行端                                           │
  └───────────────────────┬──────────────────────────┘
                          │ HTTP(唯一通道)
                          ▼
  ┌──────── Mock DSP(獨立行程,自己的儲存)──────────┐
  │ 廣告狀態 / 版本 / 操作紀錄 / 冪等鍵紀錄           │
  │ 故障注入控制面(只給測試,執行路徑不可呼叫)        │
  └──────────────────────────────────────────────────┘
```

- **不可信的輸入**:廣告名稱、素材文字、落地頁、DSP 中繼資料、工具回傳內容。一律當資料,不能變成權限。
- **可信的來源**:政策引擎的規則、由執行閘從可信上下文綁定的資源身分與金額上限。
- **權限邊界**:分析端不持有 DSP 寫入憑證;寫入只發生在執行端,且要通過交接文件第 8 節的檢查閘。
- **DSP 是外部事實來源**:agent 只能走四個公開介面加查詢介面,不能開 DSP 的儲存檔案,也不能 import DSP 的內部模組。

## 決策(細節與四欄在筆記的 decisions 欄位)

- WHY: agent 狀態存 SQLite。因為要靠交易讓「狀態、檢查點、稽核」一起提交,用唯一鍵擋重複冪等鍵,用版本欄位做樂觀鎖。出處:對話 2026-09-21。
- WHY: DSP 用獨立行程加 HTTP,儲存也獨立。因為共用資料庫或行程內呼叫,會讓「DSP 已寫入但 agent 沒收到回應」這個事故測不出來。出處:對話 2026-09-21。
- WHY: agent 呼叫外部系統前,先寫入並提交「嘗試中」紀錄(含冪等鍵)。因為沒有這筆紀錄,行程當掉後 agent 不知道曾經嘗試過,會用新鍵重做。出處:對話 2026-09-21。
- WHY: 即時畫面與後台只讀不寫指令。因為能觸發執行的介面會變成繞過安全檢查的第二條路。出處:對話 2026-09-21。
- WHY: 事件與狀態變更放同一個交易。因為畫面要顯示的是 agent 真正記下的事實,不是事後補的敘述。出處:對話 2026-09-21。

## 已知限制(Demo 與正式環境的差別)

- SQLite 只有單一寫入者、不是分散式;佇列是用資料表模擬的至少一次投遞,不是真的訊息系統。遷移路徑是換成有原生至少一次語意的佇列與伺服器型資料庫,介面層保持不變。
- DSP 是模擬器,沒有真實廣告平台的延遲分布與限流行為。
- REVISIT:2026-10-21 回頭看 SQLite 單寫入者是否已限制 Phase 6 的並行 worker 測試。

## Phase 1 範圍與驗收(待使用者同意)

- 範圍
  - 獨立行程的 Mock DSP,提供四個必要介面加冪等鍵查詢與廣告歷史查詢。
  - 廣告版本單調遞增,記錄操作歷史與冪等鍵結果。
  - 故障注入:正常、提交前逾時、提交後逾時、延遲回應、暫時性 5xx、永久驗證錯誤、版本衝突、同鍵同內容重送、同鍵不同內容。
  - 純程式的指標計算:CTR、CVR、ROAS、Pacing,涵蓋零分母與缺資料。
  - 不使用 LLM 做任何確定性計算。
- 驗收
  - 合約測試涵蓋四個介面。
  - 「提交前逾時」與「提交後逾時」能被精確且可重現地觸發,兩者在 DSP 端的最終狀態不同。
  - 同一冪等鍵搭配不同內容會被拒絕。
  - 指標計算有正常值、零分母、缺資料、邊界值測試。
  - 驗收指令:在專案的 `.venv` 裡執行 pytest(測試框架已定為 pytest,見決策 d6);.venv 在 Phase 1 開頭建立,建好後 lumos 的測試指令要同步改成指向 .venv 內的 pytest。

## 實務隱患

- 已排除:金流:整個專案只有本機的 Mock DSP,沒有任何真實廣告帳戶或金錢,預算數字都是模擬值。
- 已排除:對外送出:DSP 是本機行程、只監聽本機位址,agent 不連任何外部網路;若之後改接真實服務,要重開設計審。
- 已排除:不可逆:本階段只寫文件,沒有資料搬移或刪除;「遷移路徑」一詞只指未來換成正式環境元件時的做法,這裡沒有執行任何遷移。
- 已排除:守衛面:本階段不實作任何守衛或授權程式,只畫出邊界;守衛與授權的實作在 Phase 6,屆時另開設計審。
- 殘留風險:Mock DSP 用標準函式庫的 http.server,它預設不是為並行與精確逾時設計的。若故障注入不夠精確,F1 測出的就不是真的提交後逾時。緩解:Phase 1 開頭先做最小實驗,實驗不過就換做法,不硬撐。
