## Findings

### F1 即時畫面與後台「只讀」沒有任何強制機制,且與 agent 共用同一個 SQLite

severity: major
blocking: 是 — 照字面實作,唯讀只是慣例,決策 d4 的核心保證(不能成為繞過執行閘的第二條路)沒有落地手段。

- 計劃段落:元件與信任邊界的圖,以及決策 d4。
- 問題:圖中畫面與後台的箭頭指進 Agent 行程框、讀 agent 自己的 SQLite。計劃只寫「只讀」,沒說怎麼保證:唯讀開啟模式、獨立唯讀連線帳號、經由投影或複本、還是靠自律。同一個資料庫內還有佇列表、風險額度、稽核。畫面若持有可寫連線,任何 bug 或注入都能改額度或稽核。再者,SQLite 讀者在寫入鎖競爭下會影響單一寫入者;「已知限制」自己承認 Phase 6 靠 SQLite 寫入鎖重現搶額度競態,讀者干擾會污染這個實驗,計劃沒處理。
- 佐證:
  - 引句:「即時畫面與後台只讀,不能下指令。替代方案:畫面可觸發重試或核准」
  - 引句:「SQLite 的寫入鎖能重現「多 worker 搶總曝險額度」的競態」
  - handoff 第 11.1 節要求權限分離;handoff 第 14.3 節要求稽核 append-only 或有防竄改策略。計劃對此完全沒有交代。

### F2 「分析端無寫入權限」只是圖上的方框,同行程同資料庫,沒有可測的邊界,且把憑證機制全部延到 Phase 6

severity: major
blocking: 是 — handoff 第 5 節明說執行端「因 write permission boundary 而獨立」,計劃的切法讓這個邊界在 Phase 1 到 5 完全不存在,無法驗證。

- 計劃段落:元件與信任邊界的圖與「權限邊界」條目,以及實務隱患的「已排除:守衛面」。
- 問題:
  - 分析端、政策閘、執行端都畫在同一個 Agent 行程、同一個 SQLite 裡,沒說憑證怎麼隔離(不同行程、不同連線、還是只是不同函式)。
  - 圖中寫「只有這一層持有 DSP 寫入憑證」,箭頭指的是「政策與執行閘」,文字卻說「寫入只發生在執行端」。誰持有憑證前後不一致。
  - Mock DSP 在 Phase 1 的範圍完全沒有憑證或 capability 驗證,沒有 read 與 write 分離,所以 DSP 端無從拒絕分析端的寫入。
  - 分析端要讀 campaign 與 metrics,但圖中 HTTP 唯一通道只從執行端畫出,讀取路徑與讀取憑證沒畫,handoff 第 11.1 節要求 read 與 write capability 分離,計劃沒有。
  - 分析端對 agent 自己資料庫(額度、稽核、核准)的寫入權限也未定義。
- 佐證:
  - 引句:「只有這一層持有 DSP 寫入憑證」
  - 引句:「分析端不持有 DSP 寫入憑證;寫入只發生在執行端」
  - 引句:「本階段不實作任何守衛或授權程式,只畫出邊界;守衛與授權的實作在 Phase 6」
  - handoff 第 17 節 Phase 3 要實作 Side Effect Gate,早於 Phase 6,計劃把授權全丟到 Phase 6,兩者時序衝突。

### F3 Mock DSP 故障注入控制面「執行路徑不可呼叫」沒有機制

severity: major
blocking: 是 — handoff 第 6.3 節明確要求測試控制面不能被 production execution path 當業務 API 使用,計劃只有宣稱。

- 計劃段落:元件與信任邊界的圖(Mock DSP 框)。
- 問題:agent 與 DSP 之間「HTTP(唯一通道)」,控制面也在同一個 DSP 行程。計劃沒說是不同連接埠、不同 token、還是啟動旗標才開放。執行端與 DSP 走同一條 HTTP,「不可呼叫」在此設計下只是慣例。注入控制面被呼叫,等於能偽造 F1 到 F3 的事實來源。
- 佐證:引句:「故障注入控制面(只給測試,執行路徑不可呼叫)」

### F4 顯示端(畫面與後台)的不可信文字注入沒有處理

severity: major
blocking: 是 — 計劃自己列出的不可信輸入包含廣告名稱,而畫面與後台正是把這些字串渲染給人看的落點,信任邊界少畫一條。

- 計劃段落:元件與信任邊界的「不可信的輸入」條目;待決的前端技術。
- 問題:不可信輸入只被定義為「不能變成權限」,只涵蓋往 agent 決策的方向。廣告名稱、素材文字、DSP 中繼資料會經事件與稽核表流進畫面與後台,渲染時的注入(頁面腳本、日誌偽造、控制字元、過長字串、以及若畫面把事件內容當指令連結)沒被列為邊界。前端技術「留到 Phase 9 前決定」,但事件 schema 與落庫格式在 Phase 2 就固定了,顯示層的跳脫與長度上限若要靠 schema 早做,不能等到 Phase 9。handoff 第 12 節要求「Evidence 保留 provenance 與 trust classification」,計劃的事件表沒提 trust 標記。
- 佐證:
  - 引句:「廣告名稱、素材文字、落地頁、DSP 中繼資料、工具回傳內容。一律當資料,不能變成權限。」
  - 引句:「指標後台與即時流程畫面的前端技術,留到 Phase 9 前決定。」

### F5 「已排除:對外送出」與 handoff 需要 LLM 分析矛盾

severity: major
blocking: 是 — 風險類被用錯誤前提排除,照計劃實作會漏掉資料外送與外呼憑證的邊界。

- 計劃段落:實務隱患的「已排除:對外送出」與「已排除:金流」。
- 問題:計劃說 agent 不連任何外部網路,整個專案只有本機 Mock DSP。但 handoff 第 4.2 節與第 5 節的 Analysis Agent 使用 LLM(以及第 10 階段的 Jev),那必然是對外呼叫,並把 campaign、名稱、指標送出去,還要持有模型 API 金鑰。分析端因此有一條圖上沒畫的外連通道與一把 handoff 第 12 節要求「不可被讀出」的秘密。這也讓「只有執行端有憑證」的敘述不完整:分析端持有模型金鑰,而且它是處理不可信文字的那一端。
- 佐證:
  - 引句:「DSP 是本機行程、只監聽本機位址,agent 不連任何外部網路」
  - 引句:「整個專案只有本機的 Mock DSP,沒有任何真實廣告帳戶或金錢」
  - handoff 第 12 節「必測」:injection 文字包含「透露 credential」。分析端若能讀到任何秘密才會有這個風險,計劃沒說分析端的環境變數與檔案存取範圍。

### F6 核准(HITL)通道沒有定義,而 d4 把操作者推到「另走受控管道」

severity: major
blocking: 是 — HITL 是 handoff 第 8 節第 9 項與第 11.3 節的必備閘,計劃通篇沒有 HITL 與核准,只把它推給一條未定義的管道。

- 計劃段落:決策 d4 的取捨欄;元件與信任邊界。
- 問題:d4 說畫面不能核准,操作者要「另走受控管道」,但圖與文字都沒有這條管道,核准存哪(哪張表)、誰能寫、身分怎麼驗、如何綁 proposal hash、policy version 與有效期,全部缺席。這是第三個信任邊界(人到系統),而且是唯一能放行超額動作的入口,卻沒畫。全文搜不到 HITL、approval 或 tenant 字樣。
- 佐證:
  - 引句:「取捨:操作者要另走受控管道,展示時少一點互動感。」
  - handoff 第 11.3 節:approver identity、proposal hash、expiry 等綁定條件。

### F7 使用者新增的畫面與後台沒有依 handoff 第 19 節處理,且已影響核心交易設計

severity: major
blocking: 是 — 第 19 節要求「先說明原因、最小替代方案與額外成本,再由使用者決定」,計劃兩個都沒做;還讓 UI 需求進入 Phase 0 的核心決策。

- 計劃段落:決策 d4、d5,以及待決的前端技術。
- 問題:
  - 計劃沒有引用第 19 節,沒有寫最小替代方案(例如只讀的文字事件流或靜態報表)、沒有寫額外成本、沒有記使用者的決定。
  - 「使用者要求即時顯示決策與工具流程」被當成前提直接推出 d4 與 d5。d5(事件與狀態同交易)本身對稽核也合理,但計劃的 context 只以畫面為理由,使核心交易形狀的取捨看起來由 UI 驅動。
  - 「待決」只把前端技術延後,沒有把「畫面與後台」整體排在 F1 到 F7 核心語意之後的排程宣告。計劃沒有說明它們屬於哪個 Phase、在哪個核心 Phase 之後才開工。Phase 1 範圍沒有它們是對的,但沒有明文排序,日後容易前插。
- 佐證:
  - 引句:「使用者要求即時顯示決策與工具流程」
  - 引句:「畫面要顯示的是 agent 真正記下的事實,不是事後補的敘述。」
  - handoff 第 19 節第一項:「漂亮 dashboard 或複雜前端」屬於核心安全語意完成前不優先的目標。

severity: major

### F10 多租戶概念在信任邊界與額度中完全缺席

## 風險類逐類作答

- 金流:排除理由成立(全為模擬值)。已讀,無 finding。
- 對外送出:排除理由不成立,見 F5。
- 不可逆:對 Phase 0(只寫文件)成立。但稽核 append-only、事件表不可改是後續的不可逆性要求,計劃在稽核設計上未提,已併入 F1 與 F8 的 observability 缺口。
- 守衛面:計劃自己說只畫邊界、實作留到 Phase 6。畫出來的邊界有多處無機制(F1、F2、F3、F6),且與 handoff 第 17 節 Phase 3 的閘時序衝突,見 F2。
- 殘留風險(http.server 精度):有緩解與實驗前置,已讀,無 finding。

最嚴重 severity:major;blocking 共 10 條(F1 到 F10),blocking:否 共 2 條(F11、F12)。
