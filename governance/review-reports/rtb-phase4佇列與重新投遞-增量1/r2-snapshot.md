# RTB_Phase4佇列與重新投遞_計劃

PRIOR-ART: 這是「至少送一次的佇列 + 可見性逾時 + 確認 + 死信」的標準解(SQS、RabbitMQ、Kafka 的消費者提交都是同一組概念),配上「確認要晚於持久結果」這條老規則。最小解在本專案既有的層就做得到:收件表本身就是一張有狀態的表,加租約欄位與投遞次數就是佇列;不引入外部佇列軟體(零依賴家規),也不自造訊息格式。採用:借用概念,在既有收件表上長出佇列語意。
RETIRE-IF: 若之後換成真的外部佇列(SQS 之類),這層的可見性逾時、投遞次數與死信改由它負責,本專案只留「確認晚於持久結果」與「重新投遞先讀持久狀態」兩條規則。

## 這份計劃在解決什麼

- 事故 F2(交接文件第 16 節):外部寫入與本地持久結果都已完成,工作者卻在送出確認之前當機。佇列沒收到確認就會重新投遞;處理錯的後果是同一筆預算被改兩次。
- 事故 F3:同一則訊息被投遞兩次以上(不同工作者、不同嘗試)。任務識別要穩定、狀態轉換要合法、重複投遞不能重複花分析的錢,也不能繞過執行閘。
- 範圍:交接文件 Phase 4「Queue、Redelivery 與 Checkpoint」。樂觀鎖與並行寫入是 Phase 5;權限、護欄與總曝險是 Phase 6;提示注入是 Phase 7。
- 驗收(交接文件 Phase 4 完成條件):F2、F3 通過;當機點至少涵蓋外部寫入前、DSP 提交後但本地寫入前、持久結果已寫但確認前;重新投遞由持久事實恢復,不靠行程記憶;確認時機有測試與設計說明;佇列重試不造成重複的有害副作用。
- 已登記的預告合約 [[Verification/2026-09-22_事故-F2-工作者在副作用與持久結果都已完成-但送出確認前當機時-重新投遞後新的]] 與 [[Verification/2026-09-22_事故-F3-同一則訊息被投遞兩次以上時-任務識別維持不變-狀態轉換合法-重複投遞]](都最遲 2026-11-30)是這個階段要轉正的合約。

## 使用者情境題(2026-09-23)

- 題目:一則任務訊息被取出,工作者改了 DSP 的預算、成功了,也把結果寫進本地資料庫;正要送出確認時當機。佇列重新投遞,新的工作者拿到它。該怎麼做?a 重跑整個流程;b 先看本地持久狀態,已有結果就直接確認、不碰 DSP;c 先送確認再處理;d 一律用冪等鍵向 DSP 查證後再決定。
- 使用者答 d。回饋:抓到最重要的一點——不能用「訊息又來了」當成「還沒做」。但每次重新投遞都去問 DSP,是把本地已經確定的事也交給網路重問。正確順序是 b 打底、d 補充:**本地持久狀態是第一順位**(嘗試紀錄與結果在同一個交易裡寫下,終點狀態本地說了算),只有本地停在未結案時才走 Phase 3 的對帳去問 DSP。這也省下重複的分析費用(事故 F3 明講)。
- 這一題順帶帶出 Phase 4 真正的判斷點:**什麼時候送確認**。太早(選項 c)等於承認了沒做完的事,當機就沒人重做;太晚則會重複投遞。

## 三個增量(2026-09-23 使用者同意這個排法)

- 增量 1:佇列語意與確認規則。收件表長出租約(可見性逾時)、投遞次數與死信;取件不再等於確認,確認只在「這個邏輯操作有終點或提案被擋下」時才寫。
- 增量 2:重新投遞恢復與事故 F2、F3 端到端。重新投遞先讀持久狀態判定;三個當機點各一個測試。
- 增量 3:多工作者的租約與圍籬。同一則訊息被兩個工作者處理時,只有租約還有效的那個能寫;過期租約的寫入要被擋下,取代 Phase 3 的單一執行者鎖。

## 增量 1 設計:佇列語意與確認規則(2026-09-23,第 2 版:已折入第 1 輪設計審)

- 事故:取件就當成確認,當機在「取件之後、寫入之前」那一段,訊息再也不會被重投,提案默默消失;反過來,確認寫在持久結果之前,當機就會讓已經做完的事被重做一次。
- **第 1 版被第 1 輪設計審推翻的地方**:第 1 版把處置整個延後到嘗試結案才寫,處理期間提案留在「待處理且沒有處置」。七席指出這等於把 Phase 3 的保護拆掉——別的提案送件時觸發的到期標記或取代會把它改成已過期或已取代(並行席用現有模組實驗重現兩種情境),之後確認一律寫不進去,留下一列沒人知道的孤兒;轉人工的嘗試更是永遠等不到確認,連帶讓同任務所有修訂都清不掉(相容性席判 blocker)。所以第 2 版改成**三段式處置**:取件當下就寫「處理中」,提案立刻離開待處理;重新投遞靠租約到期,不靠留在待處理。
- 範圍:收件表的佇列語意(租約、投遞次數、死信)、處理一筆與對帳寫處置的時機、取件後先讀持久狀態的分流。不動 DSP 回應判定表與對帳對 DSP 的判定邏輯(增量 2 做三個當機點的端到端),不做多工作者與圍籬(增量 3)。
- **狀態(2026-09-23):設計中**。

### 處置從兩態變四態

- 處置列舉從兩個成員(已交給執行、已擋下)變成四個,多**處理中**與**死信**。
  - 處理中:取件當下寫,代表「這則訊息已經交出去,租約還沒到期」。它不是待處理(不佔名額、不會被取代、不會被到期標記改、不會被保留期清除),也不是確認(租約到期後還能再被交出去)。
  - 死信:投遞次數用完仍未確認,不再交出去。
- 這解掉第 1 輪最嚴重的一條:處理期間提案不再留在待處理,Phase 3 的 S40 保護照舊生效。
- **處置欄位的資料庫層限制要一起遷移**:既有的處置欄位有 CHECK 約束、只認兩個舊成員,加欄位的做法改不了它。補欄位遷移要照 SQLite 官方的重建表步驟(建新表、抄資料、換名),整段在同一個立即取得寫入鎖的交易裡做,拿到鎖後再查一次(外家席指出舊資料庫第一次寫死信會直接失敗)。
- **死信原因另開一個封閉列舉**,不沿用擋下原因。擋下原因那條合約寫明「每一種都有真實觸發路徑,見執行前檢查」,死信的觸發在收件表的取件,不在執行前檢查;混用會讓那條合約的窮舉測試變成假的(相容性席指出)。死信另存**最後一次處理的結果**(執行迴圈的結果列舉,可空)當失敗脈絡,讓人看得出它是卡在哪一步(外家席指出只記「次數用完」不夠)。

### 收件表長出佇列語意

- 沿用既有補欄位做法,加兩欄:**租約到期時間**與**投遞次數**。取件時間不另存(租約到期時間減可見性逾時就是它)。
- **可取件**的定義:沒有處置的待處理提案,或處置是處理中而且租約已到期。已交給執行、已擋下、死信都不可取件。
- **取件(receive)**:在一個交易裡(拿到寫入鎖之後才讀時鐘,比照既有的收件)挑最舊的可取件提案,寫處置處理中、租約到期時間設成現在加可見性逾時(暫用 60 秒,沒有實測校準)、投遞次數加 1,回傳提案與一張**收據**(任務編號、修訂序號、內容雜湊、這次的投遞次數)。沒有可取件的回空。
  - 60 秒的由來:一輪處理最慢是幾次 DSP 呼叫(用戶端逾時暫用 5 秒)加本地寫入;60 秒給足餘裕,又不會讓當機的訊息卡太久。
  - **跳過被鎖住的廣告**:呼叫端(執行迴圈)先算出「已有未結案嘗試的廣告」清單傳進來,取件的 SQL 直接排除它們——不交出去就不算一次投遞。Phase 3 的 S57(一個廣告被鎖住不會擋住其他廣告)照舊成立,而且排隊等待不會消耗投遞次數(可測性席與並行席指出)。
- **延長租約(extend)**與**確認(ack)**都要帶收據:條件寫入除了任務編號、修訂序號、內容雜湊,還要比對投遞次數等於收據上的值。過期的工作者拿舊收據續租或確認會失敗(並行席與外家席指出這是增量 3 圍籬的地基,不先做增量 3 只能改合約)。
- **死信**:取件時若這份提案的投遞次數已經等於上限(暫用 5)而且仍未確認,就寫死信處置(附原因與最後一次結果),改挑下一份;死信那次不算投遞,投遞次數不再加。所以「上限 5」就是最多交出去 5 次(可測性席與並行席指出邊界沒釘死)。
  - 死信之前先看嘗試紀錄:這把鍵已經有終點結果就直接確認,不寫死信(外家席指出死信會搶在已完成的結果之前)。

### 確認規則(這個增量的核心)

- **確認一定晚於持久結果**:呼叫 DSP 之前,本地一定已經有「嘗試中」那一列(Phase 3 增量 1 的規則);處置寫「處理中」不算確認,只有下面四種是確認:
  - **已交給執行**:這把鍵的嘗試到了已驗證。
  - **已擋下**:執行前檢查沒過(附既有的擋下原因),或這把鍵的嘗試已經是失敗(附「同一操作先前已失敗」)。這一格保留 Phase 3 對失敗鍵的分流,不併進已交給執行(相容性席與外家席指出併掉會讓人工判過失敗的標記消失)。
  - **已過期**:提案自己過期(沿用既有的已過期狀態,不是處置)。
  - **死信**:投遞次數用完。
- **取件後第一件事是讀持久狀態**:重新投遞回來的訊息,先用冪等鍵查嘗試紀錄,不要直接重跑執行前檢查。
  - 有終點結果(已驗證、失敗)→ 直接確認(已交給執行或已擋下),不讀 DSP、不重跑檢查。這解掉「寫入成功後 DSP 版本已變,重跑檢查會把成功記成擋下」(銜接席指出)。
  - 未結案(結果不明、已提交待驗證、轉人工)→ 不確認,延長租約,交給對帳;這一輪不再處理它。
  - 沒有嘗試紀錄 → 照 Phase 3 的流程走(讀 DSP、執行前檢查、取件交易裡開始一筆)。
- **對帳要接上收件表**:對帳結案時(把嘗試推到已驗證或失敗)要同時寫確認,而且每一輪對所有未結案嘗試續租。
  - 嘗試紀錄的第 1 列存了完整的提案快照(Phase 3 增量 1),對帳可以從快照取回任務編號、修訂序號與內容雜湊,不必反查。
  - 續租的對象包含轉人工:轉人工不會被對帳推進(它只能由人工處置離開),但只要它還沒結案,租約就要續下去,否則會被重新投遞、投遞次數一路加到死信——一個還活著、只是等人的嘗試被標成死信(相容性席判 blocker、可測性席與並行席各自指出同一個後果)。
  - 續租用對帳自己那一輪拿到的收據:對帳讀收件表那一列目前的投遞次數當收據,不需要記住取件當下的值。
- **處理一筆在取件的交易裡寫的是處理中**,不是確認。這跟 Phase 3 的差別是:Phase 3 取件當下就寫已交給執行(等於取件即確認),當機在寫 DSP 之前就會讓提案永遠沒人再碰。
- 這會改到 Phase 3 已完成的合約,照「只新增不改既有合約」做不到,所以明寫哪幾條被取代、各自的斷言搬到哪裡(相容性席指出原本只提兩條、底下其實有四個斷言):
  - Phase 3 的「取件、開始一筆與處置標成已交給執行在同一個交易」→ 由 [S104] 取代(同一個交易,但寫處理中);它原本還驗「交易前已被取代就不開始嘗試、不呼叫 DSP」,這個斷言搬到 [S108]。
  - Phase 3 的「鍵已存在就標已交給執行」→ 由 [S105]、[S106] 取代,已驗證走已交給執行、失敗走已擋下並附「同一操作先前已失敗」。
