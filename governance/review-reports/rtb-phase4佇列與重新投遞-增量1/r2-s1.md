### 1. 對帳續租轉人工沒有可用的查詢機制,r1 已修過的「轉人工被死信吃掉」有復發風險

severity: blocker
blocking: 是 這是 r1 被判 blocker 的同一個後果(轉人工提案被重新投遞耗盡投遞次數、進死信),第 2 版只在文字上斷言「要續租」,沒交代讓它成立的機制,照現有函式字面實作會直接重演。

引句:「續租的對象包含轉人工:轉人工不會被對帳推進」

說明:S110 要求「對帳每一輪應替所有未結案嘗試(含轉人工)延長租約」,但對帳目前用來決定「要處理哪些鍵」的查詢函式 `awaiting_reconciliation()` 只選兩種狀態,不含轉人工:

```
"SELECT a.key FROM attempts a WHERE a.state IN (?, ?) AND a.seq = ..."
(AttemptState.UNKNOWN.value, AttemptState.COMMITTED_UNVERIFIED.value)
```

`execution.py` 的 `reconcile_all()` docstring 也明寫「結果不明與已提交待驗證的嘗試(**轉人工不碰**)各對帳一次」,`_reconcile()` 也只有 COMMITTED_UNVERIFIED 與「未知」兩條分支,完全沒有「只續租、不碰 DSP」的第三條路。設計文字只斷言了 S110 這個結果,沒有交代:(a) 要不要擴大 `awaiting_reconciliation()` 的選取範圍、還是另開一支「未結案鍵(含轉人工)」的查詢;(b) 對帳迴圈遇到轉人工的鍵時要新增哪一種分支(只延長收件表的租約,不呼叫 DSP、不動嘗試狀態)。

例子(輸入 → 預期):一把鍵轉人工後,收件表那一列仍是「處理中」、租約 60 秒;下一輪 `reconcile_all()` 若沿用現有 `awaiting_reconciliation()`(不含轉人工)→ 這把鍵完全不會被對帳碰到 → 租約到期 → `receive()` 把它重新投遞、投遞次數加 1 → 迴圈重演 5 次後轉「死信」。但設計要的預期是:它應該被每輪續租,永遠不會因為投遞次數用完而死信,只能靠人工處置離開。

### 2. 「已過期」與「已擋下」在無嘗試紀錄分支沿用舊的 PENDING 條件,處理中之後永遠寫不進去

severity: major
blocking: 是 照字面實作,任何在收件時已過期、或執行前檢查沒過的提案,會被反覆重新投遞、最後誤判成死信,而不是設計要的「已過期」/「已擋下」;也會拖慢死信原因分佈的可信度(S103 的「每一種都有真實觸發路徑」)。

引句:「挑最舊的可取件提案,寫處置處理中、租約到期時間設成現在加可見性逾時」

說明:「取件(receive)」不論這份提案是否已過期、precheck 會不會過,一律先把處置寫成「處理中」(S96)。「沒有嘗試紀錄」分支之後才「照 Phase 3 的流程走」去判過期、跑執行前檢查,這兩個判定各自呼叫 `mark_expired()` / `block()`;但這兩個函式(經 `execution.py._dispose()` 呼叫)底層都是 `inbox_store._dispose()`,條件寫入用的是:

```
PENDING = "state = 'pending' AND disposition IS NULL"
UPDATE proposals SET {assignment} WHERE ... AND {PENDING}
```

一旦「處理中」已經寫進去,`disposition IS NULL` 永遠不成立,這兩個更新的 `rowcount` 永遠是 0,函式回傳 `False`,呼叫端就把它當成 `Processed(Result.DEFERRED)`(等同「已被取代」)。設計說明「這會改到 Phase 3 已完成的合約」那段只明列兩條被取代的合約(S45→S104、S58→S105/S106):「所以明寫哪幾條被取代、各自的斷言搬到哪裡」——完全沒提到 S42(過期→`mark_expired`)與 S43(precheck 失敗→`block`)也要跟著換成收據條件寫法,S95–S110 也沒有一條測試涵蓋「處理中之後才發現過期/擋下」這個情境。

例子(輸入 → 預期):一份提案 `decision_expires_at` 已過、之前從未被處理(沒有嘗試紀錄)→ `receive()` 先把它標「處理中」、投遞次數設 1 → 讀 DSP 前的過期檢查判定「已過期」→ 呼叫 `mark_expired()` → WHERE 子句要求 `disposition IS NULL`,但此刻已是「處理中」→ 寫入失敗、提案原地不動 → 租約 60 秒後到期,被重新投遞,同一套死路再跑一次,5 次後轉「死信」。預期行為應是設計文字所說的「已過期:提案自己過期(沿用既有的已過期狀態,不是處置)」,一次到位、不佔用投遞次數。precheck 沒過(已擋下)是同一個根因,走同一條死路。
