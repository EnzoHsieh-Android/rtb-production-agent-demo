說明:快照把「取件」定義成單一原子動作——挑最舊的「可取件」提案(可取件只看 pending/disposition/lease,不看廣告是否被鎖)、設租約、投遞次數加一、回傳。而 [S97]「當一份提案的租約還沒到期,取件應跳過它、改挑下一份」證實這個動作內部確實會跳過候選項、往下挑。但 Phase 3 已經有另一條完全獨立的跳過規則,活在執行迴圈這一層:`_pick()`(`src/rtb/executor/execution.py:323-329`)會跳過「所屬廣告已有未結案嘗試」的提案,改挑別的廣告較新的提案(對應 Phase3 的 [S57]:「當某個廣告已有未結案嘗試,處理一筆應跳過它的提案、處理其他廣告較新的提案」,`docs/.../RTB_Phase3外部寫入安全_計劃.md:352`,設計理由見同檔 `:256`:「一個廣告被鎖住不會擋住其他廣告的提案」)。這條規則在增量 1 之後只會更重要,因為確認延後了,一個廣告卡住的時間會比 Phase 3 長很多。

問題是:store 層的「可取件」定義完全不知道廣告鎖(那是 attempt_store 的概念),`receive()` 沒有辦法在同一個 SQL 判斷裡把它排除掉。這留下兩條路,快照都沒選也沒排除:
- 如果 `receive()` 真的照字面只看「可取件」挑最舊的一筆並直接鎖定,那麼被同廣告鎖住的提案會擋住佇列前面的位置,後面較新、廣告沒被鎖住的提案反而排不到——直接退回 Phase 3 已修過的問題,打壞 [S57]。
- 如果由 `_pick()` 在 Python 端逐筆呼叫 `receive()`(或等價操作)、拿到廣告被鎖的候選項才跳過改挑下一份,那麼「廣告被鎖住」這件事本身就會讓這份提案的租約被重設、投遞次數被加一——而這份提案根本沒有遺失、沒有當機,只是正常在排隊等同廣告前一筆嘗試結案。只要它排在佇列前面的時間夠久(尤其配合發現 1:靠對帳結案的嘗試本來就會拖長這段時間),投遞次數會在沒有任何真實重新投遞的情況下,單純因為「它是隊伍最前面那筆、又被跳過」而一輪一輪往上疊,最終撞上死信門檻(暫用 5)——一個從未真正遺失、只是排隊等候的提案,會被誤判死信。
