### 1. 「核對收據不過就不寫」在四條既有嘗試寫入路徑上,會落進現有的 ExecutorHalted(整個執行迴圈停機),不是「呼叫端放棄這次寫入」

severity: major
blocking: 是 這條規則就是增量 1 自己要交付與驗收的核心機制(S101/S109/S110 都測它),照字面把收據核對加進 Phase 3 既有程式最自然的落點,得到的行為跟這一版寫的「呼叫端放棄、對帳會接手」剛好相反,增量 1 自己的驗收測試寫不出來,增量 3 多工作者一上線會頻繁互相打停對方的整個行程
引句:「任何一項不符就更新 0 列,呼叫端放棄這次寫入(對帳會接手)」

說明:這一版把「嘗試寫入也受同一把租約管」講成一條放諸四海皆準的規則——「都在同一個交易裡先核對收件表那一列的收據仍有效,再寫嘗試紀錄;核對不過就不寫」——適用於處理一筆與對帳「對嘗試紀錄做的每一個轉換(開始一筆、寫結果、查證逾時、重送)」。但這條規則要接進去的 Phase 3 既有程式,對「這次寫入沒有進展」這件事只有一種既有語意,而且是致命的:

- `execution.py` 的 `_write()`(處理一筆的寫結果、憑證過期鏈、作廢再判失敗都經它):`attempt_store.transition(...)` 回 `None` 時,直接 `raise ExecutorHalted("no_progress")`,註解寫「這把鍵被別的東西改過:單一執行者下不該發生」。
- `_verification_timeout()`(查證逾時,五條路徑之一):`attempt_store.record_verification_timeout(...)` 回 `None` 時,同樣 `raise ExecutorHalted("no_progress")`。
- `runner.py` 的 `_loop()` 抓到 `ExecutorHalted` 就 `return EXIT_HALTED`,整個執行迴圈的行程直接以非零代碼結束,要人工重啟。

五條寫入路徑裡只有「開始一筆」(`_take()`)已經是優雅放棄:核對不過就回 `Processed(Result.DEFERRED)`,不會拋例外。「寫結果」「查證逾時」「憑證過期鏈」「作廢再判失敗」全部只透過 `_write`/`_verification_timeout` 落筆,而這兩個函式目前對「沒有進展」只認得一種原因(攻擊面是攻擊自己那把鍵的樂觀鎖 `expected_seq`),沒有第二個分支給「收據比對不過」。把這一版描述的收據檢查塞進這兩個函式最自然的位置,就是與既有的 `expected_seq` 檢查共用同一個「回 None 就 halt」出口——這正是「照字面實作會做出錯的行為」。

### 2. 「對帳每輪續租」怎麼滿足 Phase 0「續期機制」的推理沒寫出來,靠讀者自己反推

severity: minor
blocking: 否 不影響行為正確性(單一執行者下 owner 永遠是自己,對帳的原子接手條件必然成立,等效於續租),只是這一版沒把這條推理寫清楚,屬於文件精度
引句:「對帳每輪會替仍在處理的訊息續租,所以慢的對帳不會讓活著的訊息過期」

說明:Phase 0 對 owner/lease/fencing 的要求是「lease 必須長於 DSP 呼叫逾時上限加安全邊際,並有續期機制,讓延遲回應不會把活著的 worker 變成疑似當機」。這一版唯一提到的續租動作有兩處:處理一筆結束時「停在未結案就不確認、延長租約」,以及引句這句「對帳每輪會替仍在處理的訊息續租」。但對帳的原子接手條件是「租約已到期、或擁有者就是自己」——在增量 1 單一執行者下,owner 永遠是同一個行程識別,所以這個條件永遠成立,對帳事實上每輪都會幫每一把未結案的鍵續租,這確實達成了 Phase 0 要的續期機制,但這一版沒有把「owner=self 在單一執行者下恆真,所以對帳的原子接手退化成無條件續租」這一步寫出來,讀者要自己反推才看得出這條規則怎麼滿足 Phase 0 的要求。
