### 2. 「所有帶收據的寫入都要求租約還沒到期」跟「取件挑到租約已到期的候選後在同一交易內直接確認」互相矛盾,這個分支照字面實作永遠是死路
severity: major
blocking: 是 — 這條規則被第 3 版自己標成「照 Phase 0 的裁定走」的核心修正(用來堵 x1 席指出的過期收據漏洞),但套用到取件流程自己的第 3 步時會產生一個永遠 0 列生效的寫入,跟「不交出去,改挑下一份」這句指示所暗示的「這一步真的把確認寫進去了」矛盾;若照字面實作,這個分支會變成看似有效、實際上每次都靜默失敗的死程式碼,而且是違反 Phase 0 架構文件自己那條規則(見下)的寫法。
引句:「的條件都是:處置是處理中、租約序號與擁有者等於收據、租約還沒到期」
說明:「取件」步驟 2 挑候選時,允許挑「處置是處理中而且租約已到期的提案」;步驟 3 接著「先看這把鍵有沒有嘗試紀錄」,若已有終點結果就「在同一個交易裡直接確認,不交出去,改挑下一份」。但這個確認寫入,若套用「租約」段落定義的通用規則——「所有帶收據的寫入(延長租約、確認、以及下面講的嘗試寫入)的條件都是:處置是處理中、租約序號與擁有者等於收據、**租約還沒到期**」——那麼恰好在「候選是靠租約已到期才被挑出來」的這個分支裡,「租約還沒到期」這個條件必然為假,寫入必定 0 列生效。步驟 3 的敘述完全沒有交代這個確認要不要先做一次像對帳那樣的「原子接手租約」(S110 明講對帳要「租約已到期、或擁有者就是自己,才把序號加 1、擁有者改成自己」才能接手),還是乾脆不套用「租約還沒到期」這個條件(因為整段仍在 receive() 自己的交易裡,理論上不需要收據)。兩種讀法都沒被寫死,而其中一種(套用通用規則)在这個特定分支下必然失敗。
外部佐證:Phase 0 架構文件明講「寫結果與 ACK 一律以條件更新進行:條件包含 key、owner 與 lease 序號;更新到 0 列就放棄這次寫入並進入對帳」「別的 worker 看到『有開始沒結果』時,**先確認 lease 已到期才可接手**對帳」——也就是說,對一列租約已到期的訊息要直接寫確認,前提是先做一次「接手」把 lease 序號/擁有者換成自己的,而不是拿著舊的(已到期的)收據直接寫。第 3 版的取件步驟 3 沒有做這次接手,卻套用了跟接手寫入同一套「收據」規則,這正是 Phase 0 想避免的寫法本身。
