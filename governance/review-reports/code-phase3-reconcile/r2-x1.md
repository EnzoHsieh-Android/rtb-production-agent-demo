### 1. 共用解析破壞已凍結的查版本介面
severity: major
blocking: 是 違反「既有查寫入後版本介面原樣保留」的設計合約，舊 DSP 的成功回應會被誤判為不可用

r2 把 `operation_version()` 改成必須先解析完整 `OperationRecord`，但舊介面只要求 `version_after`；舊 DSP 的成功回應沒有新增的 `params` 與 `expected_version`。

具體例子：HTTP 200 回傳舊格式 `{"operation_id":1,"campaign_id":"c1","action":"update_budget","version_after":2,"committed_at":"...","replayed":false}` → 預期 `operation_version()` 回傳 `2` → 實際 `_record()` 因缺少 `params` 回 `None`，最後丟出 `DspUnavailable("查詢回 200")`。我以此舊回應形狀直接呼叫目前實作，已重現該例外。

應共用「取得原始操作回應」而不是強迫窄介面走完整紀錄解析，或至少讓 `operation_version()` 仍只驗證合法的 `version_after`。

### 2. 作廢逾時測試無法證明提交前真的沒有作廢
severity: major
blocking: 是 這是假綠測試；把作廢實作改成「先落墓碑、再逾時不回應」後仍會通過，守不住提交前逾時不得提交的語意
引句:「try:  # 前置:DSP 真的沒有作廢成功
        assert store.void(operation_key(prop)).state == "voided"」
file: `src/rtb/dsp/store.py:327`
file: `tests/executor/test_execution_e2e.py:343`

`CampaignStore.void()` 是冪等操作：第一次作廢回 `"voided"`，同鍵再次作廢仍回 `"voided"`。我用記憶體 SQLite 連續呼叫兩次，結果為 `voided voided`。

因此輸入 `timeout_before_commit` 時：

- 預期：用戶端逾時，而且 DSP 沒留下墓碑。
- 錯誤實作：DSP 先寫入墓碑，再延遲到用戶端逾時。
- 實際測試：用戶端仍得到 `(None, None)`；隨後再次 `void()` 也仍得到 `"voided"`，整支測試照樣綠。

測試必須在處理執行緒結束後直接查 `voided_keys` 是否沒有該鍵，或先嘗試同鍵寫入並確認它仍可提交；再次呼叫冪等的 `void()` 無法分辨墓碑何時建立。
