severity: minor

本輪只看程式 patch(`governance/review-reports/code-phase3-reconcile/r1-snapshot-src.patch`),依鏡頭六點逐項核對,並儘量用真的 DSP 子行程與真的簽發器跑實驗(而非光讀程式碼猜)。整體結論:作廢回應對照表、寫入回應對照表的排序、作廢端點的驗證順序與範圍檢查、操作表補欄位遷移、簽作廢的拒簽分類,經真實請求逐一打過都對得上文件與程式碼,沒有找到會做錯行為、破壞合約或資料損壞的問題;只挑出一處驗證邊界的缺口,列為 minor。

### 1. 作廢與寫入共用的 expected_version 格式檢查沒有上界,新端點沿用了這個舊缺口
severity: minor
blocking: 否(實際測過寫入路徑有版本相等閘擋在前面、作廢路徑完全不使用這個值持久化,兩邊都證明不出真的壞行為或資料損壞)
引句:「if not is_plain_int(expected_version) or expected_version < 1:」

`store.py` 把冪等鍵格式檢查抽成共用函式 `validate_key_and_version(key, expected_version)`(`src/rtb/dsp/store.py:140-145`),供既有寫入端點與這次新增的作廢端點共用。它只檢查 `expected_version` 是正整數(`>= 1`),沒有像同一支函式旁邊的 `new_budget` 檢查那樣加上界(`_validate` 對 `new_budget` 是 `0 < budget <= SQLITE_INTEGER_MAX`)。這個缺口在改動前的 `_validate` 就存在,但這次把它抽成共用函式、並讓新的作廢端點也走同一條路徑,是「順手補齊卻沒補」的機會。

實測(真的 DSP 子行程,`.venv/bin/python` + `rtb.dsp.server`):
- 輸入:對 `/campaigns/c1/void` 送出 `{"expected_version": 2**63}`(憑證聲明的 `expected_version` 算同一個值,六項範圍比對照樣通過)→ 預期:應比照 `new_budget` 一樣有上界,超界回 422 `validation_rejected` → 實際:回 `200 {"state": "voided", "operation": null}`,超界值被接受,鍵被真的作廢。
- 對照:對 `/campaigns/c1/budget` 送 `expected_version=10**30`(同樣通過格式檢查)→ 實際回 `409 version_conflict`,因為 `_execute_in_transaction` 會先比對 `current.version != op.expected_version`(真實版本永遠遠小於這個天文數字),所以這個超界值永遠不會真的被 `INSERT INTO operations` 綁進 SQLite 參數、不會觸發 `sqlite3` 的整數溢位例外——這條路徑是安全的,只是巧合被版本比對擋住,不是靠驗證本身擋住。
- 作廢路徑則從頭到尾不會把這個值寫進 `voided_keys` 表(`store.void()` 內部固定傳 `validate_key_and_version(key, 1)`,忽略呼叫端傳入的真實值),所以即使超界也不影響資料完整性。

沒有進一步造成傷害的原因:這個值要通過範圍檢查,前提是呼叫端已經有正確的簽章金鑰(`check_scope` 要求聲明與請求逐位相等),不是外部任意輸入就能觸發的洞;兩條路徑目前都有各自的下游安全網擋著。列為 minor,只是提醒「查完整操作紀錄對回應本文的解析」與「本文驗證」那條線上,`expected_version` 這個欄位的邊界檢查目前只在 `new_budget` 那一側是完整的,`REVISIT:2026-12-31`(design 文件提到的「被作廢的鍵要不要換方式重提」)若之後真的把 `void()` 改成使用呼叫端傳入的真實 `expected_version`,這個缺口就會從「無害」變成需要重新評估。

其餘逐項核對紀錄(均為真實請求或真實訊號驗證,未發現問題):
