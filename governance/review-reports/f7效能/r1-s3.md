severity: major

### F1 已驗證段與未結案段個別加總都沒溢位,兩段相加後仍可能超過欄位可存範圍,導致沒被設計覆蓋的例外型別
severity: major
blocking: 是
引句:「資料庫的整數加總溢位時會丟例外(不會悄悄截斷)」

實測(sqlite 3.53.3,`/tmp/f7review/exp2_segment_combine.py`):兩段各自的 `SELECT SUM(amount)` 都在 SQLite 整數上限(2^63-1 = 9223372036854775807)以內,例如已驗證段 SUM = 6000000000000000000、未結案段 SUM = 6000000000000000000,個別查詢都不會丟「integer overflow」例外。設計描述「兩段分開加總後在程式裡相加」,這一步是 Python 整數相加,本身不會溢位(Python 整數無上限),所以合計出 12000000000000000000,已經超過 SQLite 欄位可存的整數範圍,但這一步完全不會觸發設計裡描述的「資料庫的整數加總溢位丟例外」判斷點——因為那個判斷點只顧到單一段 SQL SUM() 本身。

問題出在下一步:這個合計值 `used` 會原樣寫回 `attempts.aggregate_used`(`file: src/rtb/executor/attempt_store.py:602-605` 的 `aggregate_used` 是 `begin()` 在 `file: src/rtb/executor/attempt_store.py:568-589` 呼叫、算出的 `used` 直接綁進 INSERT 參數,對應欄位宣告在 `file: src/rtb/executor/attempt_store.py:102`)。實測把這個合計值當參數綁進 `INSERT INTO ... VALUES (?)` 時,Python 的 `sqlite3` 模組丟出的不是 `sqlite3.OperationalError`,而是內建 `OverflowError`(訊息:`Python int too large to convert to SQLite INTEGER`)。

具體例:租戶在 24 小時窗內已驗證的預留金額合計 6×10^18、另有未結案預留合計 6×10^18(兩段個別都遠低於 2^63-1,任一段都不會觸發「整數加總溢位」判斷)→ 設計預期:兩段相加得到已用額度,正常寫入這一筆嘗試紀錄的 `aggregate_used`、正常判門檻 → 實際:`begin()` 內的 INSERT 會在綁定參數時丟出未被任何地方接住的 `OverflowError`,整個開始一筆的交易失敗、例外原封不動往外丟(`sqlitekit.immediate_transaction` 的 `except BaseException` 會回滾並重丟,`file: src/rtb/sqlitekit.py:69-72`),而不是設計 [S681] 承諾的「不丟例外、回舊算法的結果」。而且這條路徑舊算法一樣會踩到(舊算法在程式裡累加不限位數,一樣可能算出超過 2^63-1 的 `used` 再被寫進同一個欄位),所以就算真的照字面「溢位就退回舊算法」去接,寫回 `aggregate_used` 那一步仍然會丟出同一種例外——這是設計沒交代、也不是靠「偵測 SQL SUM() 溢位」能擋住的第二個溢位點。

建議改法:INSERT 前針對要寫回的 `used`(不論走新舊哪個算法算出來)先檢查是否落在 SQLite 整數範圍內,超過就用專門的例外類別處理(而不是讓底層 `OverflowError` 直接穿出交易);[S681] 的測試涵蓋範圍要包含「兩段個別都不溢位、相加後超過範圍」這個情境,不能只測單一 SQL SUM() 溢位。

### F2 SQL 端 SUM() 對非整數的 reserved_amount 靜默地不視為毀損,跟舊算法「讀不出來就當毀損」的一貫作法不一致,可能讓總曝險安全檢查悄悄漏算
severity: major
blocking: 是
引句:「讀不出新預算就當毀損」

實測(`/tmp/f7review/exp4_nonint_values.py`):SQLite 是動態型別,`reserved_amount` 欄位雖宣告 `INTEGER` 親和性,實際仍可能存進非整數值(字串、浮點、或非數字文字)。`SELECT SUM(amount)`/`TOTAL(amount)` 對這些值的行為是:浮點值直接累加進去(整數與浮點混合會讓 SQL 端結果變成 REAL,悄悄失去「一定是整數」的保證)、能轉成數字的文字會被解析成數字累加、不能轉成數字的文字(例如 `'abc'`)會被當成 0,整段查詢完全不丟例外,也不會讓呼叫端知道有一列資料算不進去。

對照舊算法的 `_counted`(`file: src/rtb/executor/attempt_store.py:697-709`):對「有租戶」的新列,呼叫端目前是 `int(amount) if owner == tenant and amount is not None else 0`——對浮點與可轉數字字串一樣會悄悄接受(語意跟 SQL 端一致),但對讀不出數字的舊列(沒有租戶的列),明確用 `raise CorruptedAttemptRow(...)`(`file: src/rtb/executor/attempt_store.py:706`)讓「讀不出新預算」變成看得見的毀損,擋下開始一筆或至少讓呼叫端知道資料有問題。這正是整份程式碼一貫的「毀損就要能看見」哲學(`snapshot()`、`_row()` 都用同一招)。

新的資料庫端加總完全繞過這個哲學:凡是有租戶欄位的列(Phase 6 之後寫的),不論 `reserved_amount` 是不是乾淨的整數,SQL 端只會盡量湊出一個數字或把讀不懂的當 0,不會像 `_counted` 對「讀不出來」的情況丟 `CorruptedAttemptRow`。具體例:某一列因先前程式錯誤或手動修資料寫進 `reserved_amount = 'abc'`(非數字文字)→ 設計預期(繼承既有「毀損就要能看見」的精神):這種資料應該讓已用額度的計算能發現、至少不能悄悄漏算 → 實際:SQL 端 `SUM()` 把它當 0 累加,已用額度比真實值少,總曝險門檻可能被穿透而完全沒有任何錯誤或告警——這是設計自己列出的「金流安全檢查」風險項,但 [S680]–[S682] 描述的測試材料(多租戶、24 小時窗邊界、失敗、未結案、轉人工、暫停、減預算、金額接近上限)裡沒有一項會覆蓋到「有租戶列但 `reserved_amount` 不是乾淨整數」這個情境,這個分歧不會被目前列出的合約測試抓到。

建議改法:資料庫端加總前(或用 CHECK 約束、或在查詢裡加 `typeof(reserved_amount) != 'integer'` 之類的偵測)明確篩出型別不對的列,讀到就跟舊列讀不出預算一樣丟 `CorruptedAttemptRow`,而不是讓 SQL 的動態型別轉換替你「善意地」把毀損資料算成別的數字。

### F3 溢位判斷點只描述「丟例外就退回舊算法」,沒有交代要憑什麼把「這是整數溢位」跟其他任何 SQL 例外分開,實作若照字面用寬鬆的例外型別攔截,會把其他 bug 也悄悄吃成「當作溢位退回舊算法」
severity: major
blocking: 是
引句:「丟了就改走舊算法算這一次」

實測(`/tmp/f7review/exp1_overflow_types.py`):SQLite 整數加總溢位丟出的是 `sqlite3.OperationalError`,訊息固定為 `integer overflow`,`sqlite_errorcode` 主碼是 `SQLITE_ERROR`(1)。這跟資料庫忙碌(`SQLITE_BUSY`/`SQLITE_LOCKED`,主碼 5/6)用的是同一個例外類別 `sqlite3.OperationalError`,只是主碼、訊息不同(`file: src/rtb/sqlitekit.py:27-29` 的 `_is_lock_contention` 就是靠檢查主碼把「忙碌」跟其他 `OperationalError` 分開,可見這份程式碼本來就知道要分)。設計全文只說「丟了就改走舊算法」,完全沒提要靠訊息字串、`sqlite_errorcode`,還是別的判準來確認「這一次丟的例外真的是整數溢位」。

具體例:如果實作照字面「捕捉 `sqlite3.OperationalError` 就當溢位、退回舊算法」——之後查詢語法因為欄位改名、索引被使用者手動砍掉、資料庫檔案局部毀損等任何原因丟出別的 `OperationalError`(例如 `no such column`、`no such index`、`database disk image is malformed` 都可能包成 `OperationalError`)→ 設計預期:只有真的溢位才會退回舊算法(效能優化只在極端情境失效)→ 實際:任何跟溢位無關的資料庫錯誤都會被誤判成「溢位」,永久悄悄退回舊算法,程式仍然「正確」但效能優化整個失效而且沒有任何人會發現(不會有測試紅燈、不會有告警,因為退回舊算法算出來的答案本來就是對的)。這種「看起來在跑,其實一直走慢路徑」的情境不會被 [S680]–[S682] 的正確性測試發現,只有專門對「觸發溢位判斷的次數/原因」加遙測或告警才擋得住,但設計裡完全沒提。

建議改法:退回舊算法的判斷要用 `sqlite_errorcode` 的主碼比對 `SQLITE_ERROR`、再核對訊息含 `integer overflow`(或用更嚴謹的方式),不要用裸的 `except sqlite3.OperationalError`;同時比照 [S686] 那樣,替「退回舊算法」的次數留一個可觀測的計數或紀錄,免得效能優化悄悄失效而沒人知道。

### F4 沒有點名「一定要用 SUM(),不能用 TOTAL()」,而兩者行為在溢位情境下完全相反
severity: minor
blocking: 否
引句:「讓資料庫直接加總預留金額,不把列取回程式」

實測(`/tmp/f7review/exp1_overflow_types.py`):`TOTAL()` 在同樣的溢位輸入下完全不丟例外,直接回傳一個精度已經失真的浮點數(範例輸入下回傳 `1.8446744073709552e+19`,不是報錯,也不是原始整數合計)。設計反覆强調「丟了就改走舊算法」的整套溢位安全網,前提是聚合一定用 `SUM()`;如果實作圖方便(或因為某個 ORM/工具函式預設用 `TOTAL()` 以避免拋例外)換成 `TOTAL()`,[S681] 描述的「不丟例外、不回截斷的數」反而會整個顛倒——變成「不丟例外,但默默回一個精度已經跑掉的數」,是更糟的結果(悄悄給錯數字而不是明確失敗退回舊算法)。這只是文件精度問題(該講清楚聚合函式必須是 `SUM()`),但既然 F1、F3 都顯示這條溢位安全網的邊界本來就沒設計得很嚴謹,這裡值得明講以免實作踩錯。

共 4 條,blocking 3 條。
