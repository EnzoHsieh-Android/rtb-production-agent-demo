### F1 SQL SUM 在無符合列時回傳 NULL,設計沒交代要處理
severity: blocker
blocking: 是
引句:「讓資料庫直接加總預留金額,不把列取回程式」

說明:設計把已用額度的判門檻路徑改成「資料庫端 `SUM`」,但完全沒提到「這個租戶目前沒有任何已驗證或未結案的列」這個最常見的情況——SQLite 的 `SUM(x) FROM t WHERE cond` 在沒有任何列符合 `cond` 時回傳 `NULL`,不是 `0`(已用實測驗證,見下)。

具體例:輸入——租戶 `t1` 是全新租戶(還沒開過任何嘗試),這次 `reservation.amount = 50`、`limit = 1000`。預期——`aggregate_used` 回 `0`,`used(0) + 50 = 50 <= 1000`,放行。實際——若照字面把 SUM 結果直接當回傳值,`fetchone()[0]` 是 `None`;`begin()` 裡 `used + reservation.amount`(`attempt_store.py:570`)會丟 `TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'`,整個開始一筆的呼叫炸掉,不是回應「拒絕」而是未捕捉例外。這不是邊角案例,是**每一個租戶第一次被預留額度時**都會踩到的路徑(全新租戶、或現有租戶剛好目前沒有任何計入中的列),照字面實作幾乎必定在測試或上線第一天就翻紅。

實測佐證:
```
conn.execute("SELECT SUM(v) FROM t WHERE tenant = 'zzz'").fetchone()  # -> (None,)
```
(以專案 venv 的 sqlite3 3.53.3 現場驗證,非臆測)

建議改法:每一段 SQL 加總都要 `COALESCE(SUM(...), 0)`,並在 [S680]/[S681] 的測試資料裡明確涵蓋「這個租戶目前沒有任何計入列」這一格,不能只用「有列但金額為 0」代替(兩者在 SQL 語意上不同)。

file: `/Users/enzo/rtb-3b/src/rtb/executor/attempt_store.py:568-573`(`used + reservation.amount` 會在 `used=None` 時炸)

### F3 [S684]「不重跑解析與驗證」沒講用什麼可觀察方式測,實作會被迫發明未定義的內部鉤子
severity: major
blocking: 是
引句:「設定檔內容跟上次驗過的完全相同時,讀取應不重跑解析與驗證」

說明:這條合約的「不重跑」是**負向斷言**(某件事沒發生),沒有一個天然的外部可觀察後果——現有 `load_tenants(path)` 是一支自足的函式(`capability_signer.py:115-116`),快取放進去之後,呼叫端拿到的回傳值(`tuple[Tenant, ...]`)在「重跑」與「不重跑」兩種情況下長得一模一樣,無法從回傳值分辨。要驗證這條合約,勢必得挑一種可觀察手段——數 `_parse_tenants` 的呼叫次數?用 `monkeypatch` 抽換內部函式讓它「被呼叫第二次就丟例外」?比對回傳的 `Tenant` 物件是否為同一個 Python 物件(`is`)?這三種各自的耦合程度不同(最後一種是測快取實作細節、最脆弱),但設計文字完全沒有取捨,也沒點名任何一個現在還不存在的內部符號(例如 `_parse_tenants` 目前就不是給測試用的公開介面)。這正好是使用者交代的審查鏡頭要挑的洞:「要用什麼可觀察的方式測(數呼叫次數?換掉函式?)、會不會測到實作細節」——這份設計沒有答案,實作者只能自己決定,審查迴圈也無從事先判斷這支測試穩不穩。

建議改法:明講採用哪種手段(例如:對外暴露一個可以被 `monkeypatch` 抽換的解析函式名稱,測試用「第二次呼叫就丟例外」逼出不重跑的行為),並說明為什麼這個手段不算測到快取本身的實作細節(例如:這是模組已經公開承諾的「解析與驗證是相對獨立步驟」的介面,不是快取資料結構的內部欄位)。

### F4 「現況」的實驗數字與「CI 最壞約 36 秒」的推估,對不上 Issue 裡唯一可查的實測比值,也沒給出中間換算依據
severity: major
blocking: 是
引句:「CI 平常約是本機的 1.2 倍、慢的那一趟 1.5 到 1.9 倍,推估最壞約 36 秒」

說明:這個 1.2 倍 / 1.5–1.9 倍是全篇唯一支撐「[S340] 的 60 秒上限有餘裕、不用動」這個核心裁定的數字,但兩處都對不起來:
