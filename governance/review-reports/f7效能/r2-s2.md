### F1 快路徑的「偵測舊列/型別異常」步驟沒有查詢方式與成本的合約,自然的字面實作會讓快路徑在乾淨資料上完全不省時間,而且不會被既有合約測試發現

severity: major
blocking: 是
引句:「快路徑的條件(三項都成立才走):這次要算的列裡沒有沒記租戶的舊列(Phase 6 之前寫的);有記租戶、屬於這個租戶的列,預留金額在資料庫裡的實際型別全是整數或空值」

說明:

設計只講「偵測到舊列或型別不是整數、空值的金額,就改呼叫原算法」,但完全沒說**怎麼偵測**——跟「快路徑怎麼算」那一段不同,那段明講兩段加總各自要用會丟例外的資料庫整數加總、每段都有等價合約([S680]-[S683])與「只回語句不執行」的測試用函式;偵測這一步既沒有查詢寫法的規範,也沒有等價的查詢計畫合約或呼叫次數合約。

最自然的字面寫法,就是照設計描述的順序,先把「這次要算的列」實際讀回程式判斷型別與租戶有沒有值——這正是現有 `_first_row_columns`(`file: src/rtb/executor/attempt_store.py:658`)、`aggregate_holdings`(`file: src/rtb/executor/attempt_store.py:608`)已經在做的形狀(同一個 JOIN、同一組欄位)。我在 `/tmp/rtb3b-copy2` 用**production 的 schema 與既有函式**實測(F7 等級規模,10 萬列乾淨資料、全部屬於同一租戶、型別全對):

```
$ /Users/enzo/rtb-production-agent-demo/.venv/bin/python realcheck.py
real original aggregate_used on 100000 clean rows: 0.3584s, used=500000
naive python-side detection reusing existing row-shape query (_first_row_columns): 0.2967s, anomaly=False
SQL-side boolean detection (EXISTS+typeof, no row materialization): 0.0397s, anomaly=0
fast sum query alone: 0.0374s, sum=500000
```

- 用既有查詢形狀把候選列整批讀回程式判斷型別(最自然的字面實作):偵測本身就要 0.2967 秒,幾乎等於原算法整段的 0.3584 秒(83%);偵測完再加上快路徑的加總查詢(0.0374 秒),合計 0.3341 秒——跟原算法幾乎一樣慢,快路徑等於白做。
- 改成資料庫端的布林彙總查詢(`EXISTS(...) + typeof(...)`,不把候選列讀回程式)只要 0.0397 秒,加上加總查詢合計 0.0771 秒,是原算法的 4.6 倍快——這才是設計原本承諾的效果。

輸入→預期→實際的具體例:F7 端到端規模、單一租戶、全部型別乾淨的資料(F340 那種)。**預期**:照設計核心裁定與 [S686] 的 19.2 秒估計,已用額度這段應該顯著快於原算法。**實際**:若實作者照字面把「偵測」寫成讀回候選列逐列檢查型別(而不是刻意設計一條資料庫端布林查詢),已用額度這段的耗時會跟原算法幾乎相同,F7 端到端的整體效益大部分消失,CI 上很可能又逼近甚至超過 60 秒——正是這份設計要解決的事故重演。

更嚴重的是**這種退化不會被任何既有合約抓到**:[S683] 的測試是「把原算法換成一呼叫就丟例外」來確認乾淨資料不呼叫原算法(`file: docs/rtb-production-agent-demo-knowledge`所指 `test_the_fast_aggregate_used_takes_the_fast_path_on_clean_data`,對照 r2-snapshot 合約段)。但上面「naive python-side detection」用的是另一條獨立的 SQL 查詢,根本沒有呼叫 `aggregate_holdings`/原算法本身,所以會通過 [S683] 的測試,卻同時是慢的——測試綠燈,效能目標落空,沒有人會發現。

建議改法:在核心裁定或合約裡明講偵測步驟必須是資料庫端的布林/彙總查詢(例如 `EXISTS` 配 `typeof()`,或用一次 `SUM(CASE WHEN ... THEN 1 ELSE 0 END)` 把偵測跟加總合成一次查詢),不得把候選列以現有的第一列欄位形狀整批讀回程式;並比照 [S683] 的做法,替偵測也加一條可觀測的合約(例如量測呼叫次數或耗時上限,或至少要求偵測與快路徑的加總合併成同一個或同等成本的查詢),否則「乾淨資料完全不呼叫原算法」這件事本身不足以保證真的變快。

共 1 條,blocking 1 條。
