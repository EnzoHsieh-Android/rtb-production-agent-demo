### F1 資料庫端加總在租戶完全沒有落窗預留時回傳 NULL,逐字實作會讓 `begin()` 對每個「第一次預留」的租戶丟未捕捉例外

severity: blocker
blocking: 是
引句:「讓資料庫直接加總預留金額,不把列取回程式;已驗證那一段從已驗證列的時間部分索引出發,依主鍵接回第一列、用第一列的租戶篩」

說明:設計把「有租戶的列」的加總整段改成 SQL `SUM(...)`,但全文(核心裁定、合約 S680–S683、回退段)完全沒有提到「這個租戶在窗內一列都沒有時,SQL 的 `SUM()` 對空集合回傳 NULL,不是 0」。這是 SQLite(以及大部分 SQL 方言)`SUM` 眾所皆知的地雷,親自驗證如下:

```
>>> conn.execute('select sum(v) from t').fetchone()
(None,)
```

對照 `aggregate_used` 的現有入口與呼叫端:

- `file: src/rtb/executor/attempt_store.py:602-605` 舊算法 `sum(holding.amount for holding in aggregate_holdings(tx, tenant, now))`——Python 的 `sum()` 對空產生器回傳整數 `0`,不會是 `None`。
- `file: src/rtb/executor/attempt_store.py:568-573` `begin()` 直接把 `aggregate_used` 的回傳值拿去做算術:`used = aggregate_used(tx, reservation.tenant, now)` 接著 `if used + reservation.amount > reservation.limit:`。

具體例:某租戶第一次呼叫 `begin()` 帶 `reservation.amount > 0`(全新租戶,或這個租戶所有舊預留都已過 24 小時窗且已結案,窗內與未結案都查無列)。

- 輸入:`tenant="new-tenant"`,資料庫裡沒有任何 `tenant='new-tenant'` 的列。
- 預期(照舊算法/照商業邏輯):`aggregate_used` 回 `0`,`0 + reservation.amount` 正常比較門檻,合法放行或依門檻擋下。
- 實際(照設計字面,SQL 的兩段 `SUM` 都直接回傳、不轉 0):`aggregate_used` 回 `None`(或 `None + 合法整數`),`begin()` 執行 `used + reservation.amount` 時丟 `TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'`,整個開始一筆的呼叫未捕捉例外向上炸開,而不是走 `AggregateLimitReached`(合法拒絕)或正常放行——等於每一個「這個租戶目前沒有任何存量預留」的請求(最常見的情況,新租戶上線的第一筆,或流量清淡期窗口內剛好空的租戶)都會壞掉。

這也不是靠 S680 的差分測試就能穩穩接住的洞:S680 的隨機資料清單(「多個租戶、24 小時窗邊界...金額接近整數上限」)沒有明列「這個租戶在這次查詢時窗內外都查無列」這個分支,如果測試資料產生器沒有刻意保留至少一個「全新租戶」情境,這個洞可能連設計審自己要求的性質測試都測不到,直接帶著 CI 綠燈上線,正式環境第一次撞到才炸。

建議改法:在合約(建議併入 S680,或另立一條)裡明寫「租戶在窗內外都查無列時,兩段 SQL 加總都要被視為 0(用 `COALESCE(SUM(...), 0)` 或呼叫端 `... or 0`)」,並在 S680 的隨機資料規格明確加入「至少一個查詢當下完全沒有存量預留的租戶」這個案例,強迫測試覆蓋到這個空集合分支。

### F2 溢位例外的攔截範圍設計沒有界定,寫太寬會讓新算法整個失效卻仍全部測試綠燈

severity: major
blocking: 是
引句:「丟了就改走舊算法算這一次,結果以舊算法為準。舊算法在程式裡用整數累加,不會溢位。」

說明:設計只講「(整數加總)溢位時會丟例外……丟了就改走舊算法」,但沒有講清楚要攔截「多窄」的例外——沒有指定要比對訊息字串(如 SQLite 特定的 `"integer overflow"`)或限定只在特定查詢周圍攔截。這份合約表面上看起來安全(反正一有例外就退回舊算法,答案不會錯),但正是這個「有錯就默默退回舊算法、答案照樣對」的安全網,讓一個過寬的 `except sqlite3.OperationalError:`(甚至 `except Exception:`)可以把「SQL 寫錯、欄位打錯字、查詢計畫真的整表掃描而不是用索引」這類貨真價實的實作 bug,全部偽裝成「正常的溢位保護」,自動吃下、悄悄回退成舊算法。

後果:新算法從頭到尾沒有真的跑起來過,但因為退回舊算法後答案完全正確,S680–S682 的新舊比對測試會全部通過、`lumos`/CI 全綠;唯一可能抓到「新算法根本沒被執行」的是 S683(查詢計畫用索引、不整表掃描),但 S683 的測試名稱是 `test_the_fast_aggregate_used_query_uses_the_verified_time_index`,如果它是直接對「已驗證那一段」的 SQL 字串本身跑 `EXPLAIN QUERY PLAN`,而不是透過 `aggregate_used()` 這個真正的入口在真實有資料的情境下跑一次(F7 規模、正常無溢位資料),它驗的是 SQL 語句本身而不是「這次呼叫實際有沒有落到快路徑」,兩者仍可能各過各的、卻同時掩蓋「快路徑其實每次呼叫都因為某個小 bug 被攔截、默默退回慢路徑」——而這正是這次整個 F7 效能設計唯一要解決的問題(CI 上偶爾超過 60 秒)。換句話說:效能沒達成,但沒有任何一條合約會變紅,回歸只會在下一次 CI 又踩到 60 秒上限時才會被發現,那時候又要走一輪原因調查。

建議改法:合約裡明確要求「捕捉的例外要限定成資料庫回報的整數溢位(比對訊息字串或用資料庫特定的例外子類別),其他例外一律往外丟,不落回舊算法」;並在 S686 的手動量測旁邊,加一條可以機器驗的斷言(例如用 `sqlite3` 的 `set_trace_callback` 或直接斷言「這次呼叫沒有觸發回退」的計數器/旗標),確認 F7 端到端跑的時候快路徑真的有被使用,而不是全靠「答案沒錯」間接推論「快路徑有跑」。
