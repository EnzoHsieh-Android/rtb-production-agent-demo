# r1-s1 審查:共用 HTTP/SQLite 基礎抽出

## 做了什麼檢查
- 在臨時目錄複製專案,舊版取 15bb9fe、新版取 HEAD。
- 舊新版差異測試:對同一組 29 個原始 socket 請求逐位元組比對回應(Date 與 Server 標頭除外)。
  - 涵蓋:Host 錯誤加故障標頭、HTTP/1.0 缺 Host、未知與重複 X-Fault、404、campaign 不存在、空本文、壞 JSON、陣列本文、缺冪等鍵、413、壞與過長 Content-Length、chunked、本文不完整、畸形請求行、PUT、五種故障模式(含 timeout_before_commit 無回應)、歷史查詢、只送一半的標頭。
  - 結果:除了 committed_at 與 received_at 時間戳外完全相同。處理順序(Host、故障標頭、路由、開連線)、錯誤碼、DspError 與一般例外對應、故障 NoResponse 路徑都沒有行為差異。
- 全套測試 421 過;mypy --strict 與 ruff 對 src 與 tests 乾淨。
- 資源釋放:CampaignStore 建構失敗時由 sqlitekit.connect 自己關(既有測試守著);建構成功後由 finally 關。沒有洩漏路徑。
- 變異檢查 18 個(在複本上改 src 後跑全套)。被抓到的:Host 大小寫、HTTP/1.0 放行、408、500 細節寫 stderr、擴充碼低 8 位、忙碌偽裝、WAL、chunked、位數上限、重複標頭、backlog、Content-Length。存活的 6 個列在下面各條(對應 M1、M4、M5、M11、M12、M16)。
- 沒發現會做出錯行為、破壞合約、資料損壞的問題,所以最高等級是 minor。

### 1. map_exception 自己出錯時無聲斷線,破壞「絕不無聲切斷連線」的保證
severity: minor
blocking: 否 目前唯一的覆寫 error_entry 只做查表不會丟例外,是潛在缺口不是現行錯誤;之後的收件口子類別可能踩到。
引句:「mapped = self.map_exception(exc)」
說明:map_exception 在 except Exception 區塊內呼叫,它若丟例外就不會被任何處理攔到。實測(子類別的 map_exception 對 KeyError 丟 ValueError):回應是空的(連線直接關),只有 handle_error 印 stderr。模組文件與 RULE 都宣稱沒預期到的例外一律回 500。建議把 map_exception 呼叫包進 try,失敗就走 500 後備。

### 2. 「故障注入不回應」路徑沒有測試能分辨無回應與延遲後回 500
severity: minor
blocking: 否 行為現況正確(差異測試確認 f_before 回空),缺的是回歸網。
引句:「return  # 故障注入:刻意不回應」
說明:變異 M11(NoResponse 改成回 500)全套 421 個測試都過。tests/dsp/test_server.py:48 的 timeout_before_commit 測試用 0.3 秒客戶端逾時,伺服器睡 2 秒,客戶端在伺服器回 500 之前就走了,分辨不出。kit 的 /silent 路由也沒被任何測試呼叫。這是基礎抽出後才變成共用的合約(呼叫端要分「提交前逾時」)。

### 3. 每個請求結束時關閉 store 連線仍沒有守護,重構後更容易被誤拿掉
severity: minor
blocking: 否 行為正確;圖譜原本就記錄了這個缺口,但抽出後新頁沒有承接這個缺口的說明。
引句:「            store.close()」
說明:變異 M1(finally 改成 pass)全套都過。另外 store 現在在 try 之外建構,新增了一種寫法上的風險:日後在建構與 try 之間插入程式碼就會漏關。建議至少一個測試在 DSP 處理一次請求後斷言連線已關(例如包裝 CampaignStore.close 計數)。

### 4. 本文長度檢查:max_body_bytes 可覆寫但位數上限寫死,且覆寫沒有測試
severity: minor
blocking: 否 只在子類別把上限調到約 100 億位元組以上才顯現,實務上不會發生;但屬於半成品的可設定性。
引句:「if len(raw_length) > MAX_LENGTH_DIGITS or int(raw_length) > self.max_body_bytes」
說明:max_body_bytes 是類別屬性可被子類別覆寫,MAX_LENGTH_DIGITS 卻是模組常數(10 位)。實測把上限調到 10**12 後,11 位的 Content-Length 仍回 413。變異 M4(改回用常數 MAX_BODY_BYTES)全套都過,也就是「上限可設定」這件事沒有測試,kit 的上限測試硬編 64 KiB。

### 5. read_json 重複呼叫會卡到逾時,allow_empty 語意只涵蓋「第一次」
severity: minor
blocking: 否 目前所有呼叫端只讀一次;是易誤用的介面。
引句:「body = json.loads(raw or (b"{}" if allow_empty else b""))」
說明:實測同一個請求呼叫兩次 read_json(allow_empty=True):第二次 rfile 已被讀完,等到 socket 逾時回 408(而不是回空物件或明確錯誤)。allow_empty 預設 False,舊 _read_json 是永遠允許空本文;DSP 兩處已明傳 True,無回歸,但介面文件沒寫「只能呼叫一次」。

### 6. 逾時是逐次接收的閒置逾時,不是整個請求的期限
severity: minor
blocking: 否 與舊版一致(沒有回歸),但共用基礎自己的缺口,之後收件口也會繼承。
引句:「self.connection.settimeout(self.server.socket_timeout_seconds)」
說明:實測逾時設 0.5 秒,每 0.3 秒滴一個位元組的連線活了 2.5 秒以上仍未被放棄(Content-Length 宣告 20,離讀完還遠)。慢速滴入(slowloris)可以無限佔住執行緒,daemon_threads 也不限數量。本機回送位址風險低;建議文件明說取捨並附回頭看的條件。

### 7. KitServer 的 handler_class 型別放得太寬
severity: minor
blocking: 否 mypy 通過,只是型別沒有守住「必須是 JsonHandler」。
引句:「handler_class: type[BaseHTTPRequestHandler],」
說明:傳進不是 JsonHandler 的處理類別,型別檢查通過,但執行時 setup 裡沒有 JsonHandler 行為(Host 檢查與 500 後備全沒有,而且 socket_timeout_seconds 不會被設)。應標成 type[JsonHandler]。

### 8. tests/kit/test_shared_base.py 的測試名稱宣稱「行為不變」,實際只檢查結構
severity: minor
blocking: 否 名稱誤導但不會造成錯誤;行為不變的證據來自 tests/dsp 既有測試。
引句:「def test_the_dsp_server_behaviour_is_unchanged_after_extracting_the_shared_base():」
說明:這個測試只看類別成員名單、字串子串與 AST 有沒有 settimeout,DSP 在別的名字下重寫一份共用行為就會通過。同時,其他有意義的行為沒有測試:變異 M5(本文不完整不再回 incomplete_body)、M12(handle_error 不再靜音客戶端離開)、M16(把故障標頭檢查放到路由之後)全套都過。圖譜 TEST 行寫「涵蓋…各種壞輸入」,實際 incomplete_body 與 408 在 kit 沒有任何測試。建議改名為結構檢查,並補 incomplete_body、408、處理順序三個測試。
