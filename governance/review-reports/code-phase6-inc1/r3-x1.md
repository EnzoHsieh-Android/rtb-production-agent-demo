### 1. 門檻調降後仍重送的測試只看到了第一次送出，拿掉對帳重送仍會綠
severity: major
blocking: 是 測試在被守的「既有預留鍵照常重送」行為移除後仍會通過，無法證明 S337 的重投合約
引句:「assert [w for w in h.dsp.writes if w[1] == operation_key(prop)]  # 照樣送,沒被收回」

第一次 `h.process()` 已經呼叫過 DSP；即使回應是結果不明，`FakeDsp.write()` 仍先把該次呼叫加入 `h.dsp.writes`。因此對帳前這個列表就已有符合冪等鍵的元素。後面的斷言只要求「曾經送過」，沒有證明 `reconcile_all()` 在門檻由 1000 降成 0 後又送了一次。

記憶體實驗把第一次送出後的 `_reconcile_not_found` 重送分支改成直接返回：對帳前寫入次數 1，對帳後仍為 1，但這條斷言仍是 `True`，而 `stops(h) == []` 也照樣成立。

具體例子：第一次送出回應不明、已有一筆預留，之後門檻從 1000 降為 0 → 預期對帳用同一把鍵再次送出，符合鍵的呼叫數由 1 變 2 → 實際若對帳完全不送，呼叫數維持 1，現有測試仍判綠。應先記錄對帳前的匹配呼叫數，再斷言對帳後恰好多一筆，並核對第二筆仍使用原鍵。
