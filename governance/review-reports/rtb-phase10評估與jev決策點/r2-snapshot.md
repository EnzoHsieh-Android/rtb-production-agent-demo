# RTB_Phase10評估與Jev決策點_計劃

PRIOR-ART: 機器學習評估的常規做法——固定且版本化的評估集、事先寫好的評分標準(rubric)、依切片報告精確率與召回率而不只報總平均、每片最少樣本數、評估集與訓練或規則作者隔離以免外洩;模型路由的「只在驗證過的範圍啟用,範圍外退回可靠路徑」。不引入評估套件(零依賴家規)。
RETIRE-IF: 接上真實流量與人工標註之後,這份以合成情境與代理標註做的評估集要換成以正式環境紀錄抽樣、人工標註的版本;或者「值不值得加預算」這個判斷點被移除(例如改成由人工核可)。

## 這份計劃在解決什麼

交接文件 Phase 10:只在有證據的窄決策點評估 Jev。完成條件五項:評估資料與正式提示/測試的外洩風險有記錄;依重要切片報精確率/召回率,不只報總分;跟 LLM/程式基準比品質、成本、延遲;範圍外或信心不足會退回;沒達門檻時明確不採用 Jev,不調低標準。

這個階段要防的事故:因為某個便宜的模型「總體準確率夠高、又快又便宜」就換上去,但它在某一類輸入錯得離譜,總平均把問題蓋掉;而錯的那一類正好是最危險的。

## 使用者裁定(2026-09-24,使用者本人,清醒時)

- Phase 0 已裁定:不導入 Jev、不做假的 Jev 整合;沒有正式環境紀錄與人工標註,這個階段的產出是「評估機制 + 有根據的不採用 + 缺哪些證據」。
- 情境題:候選在總體達標、但某一片不達標時,「只在達標的切片用;看不出屬於哪片的輸入一律退回現行做法」。
- 評估對象:不評整支決策函式(新鮮度、配速門檻、金額都是交接文件 4.1 規定必須由程式處理的,評了只會得到「程式全對」),只評「配速偏低時,這個廣告值不值得加預算」這一個判斷。
- 標準答案:配速偏低、有曝光有點擊、但一小時內零轉換零營收 → 「證據不足、不判」,這類一律不加。所以標準答案是三類:值得加、不值得加、證據不足。

## 現況(2026-09-24 前掃,main e8b26f6)

- 分析端決策函式(src/rtb/analyzer/policy.py 的 decide)只有三種結果:任一筆證據過期 → 退回重新蒐證;配速算不出或不偏低、或曝光點擊不是正數 → 不做;新鮮、配速低於 0.5、曝光點擊都大於零 → 提案調高一成。實質上只有一個是非判斷(提不提案),動作種類與金額都是算術。
- 「值不值得加」現在用一行粗略代理:曝光與點擊都大於零。它不看轉換與營收,也不看廣告狀態(暫停中的廣告最近一小時有殘量也照樣提案,靠執行端護欄擋)。
- 「不做」不帶原因;決策函式目前沒有正式行程呼叫,只在測試與端到端測試裡接線。
- 決策當下分析端有的事實:預算、狀態(啟用/暫停)、版本、最近 1 小時的曝光、點擊、轉換、花費、營收、證據年齡、有無不可信廣告文字。沒有:廣告上線天數(整個系統沒有這個欄位)、租戶(DSP 表有,但分析端用戶端的白名單不收)、動作種類(DSP 也支援暫停,但決策函式只會提案調預算,切不出來)。
- 一次呼叫純程式、零模型成本、零網路;前掃在本機量過一次:提案那條中位約 18 微秒、不做那條約 7 微秒(單次量測,只當量級參考)。

## 評估對象跟 Phase 0 路由表的關係(第 1 輪五席指出,照實寫)

- [[Projects/RTB_Agent_Phase0架構]] 的路由表把「要不要提案調整」那列的未來候選寫成 LLM;標 Jev 的是「證據夠不夠」「下一步查什麼」「繼續或停止」三列,三列都還沒實作,沒有現行程式可以抽判斷點、也沒有退路可比。
- 評估對象照使用者裁定不變。這份計劃因此只能證明「評估機制做得出來、在這個判斷點上怎麼跑」,**不能拿來回答那三列適不適合 Jev**;採用決定與驗收紀錄都要寫這句限制。
- 使用者裁定的評分標準把這個判斷寫成狀態與計數的是非規則,依交接文件 4.1 這類規則本來就該由程式處理。所以這次的「不採用」有兩個理由,都要寫進決定紀錄:①這個判斷點照評分標準可以由程式精確算出,沒有需要模型判斷力的空間(現行規則在某些格不準,是它漏讀了狀態與轉換營收兩類已到手的欄位,是程式缺陷,不是需要換判斷者);②就算要評模型候選,也缺正式環境紀錄、人工標註與候選實測。
- 實作時(不是現在)用決策指令記一筆決策,並在 Phase 0 路由表那列加註指向這份計劃,讓兩份文件看得到對方。要不要改評估對象、要不要把評分標準加入程式答不出來的訊號,列給使用者重新裁定。

## 設計

### 增量 1:把「值不值得加」抽成可插入的判斷點,行為不變

- 判斷點的輸入是一個專用的不可變資料型別,只有決策當下的可信數字欄位:狀態、預算、花費、曝光、點擊、轉換、營收。結構上沒有放廣告文字或整批證據的位置,候選拿不到不可信文字是型別保證,不是呼叫端自律(比照證據型別把「不可信文字只能配不可信信任標記」做在建構式裡的做法)。輸出是四值列舉:值得加、不值得加、證據不足、不知道。
- 現行程式規則照舊:曝光與點擊都是正數就回「值得加」,否則「不值得加」;它不產出「證據不足」。決策函式把「值得加」對應成提案、其餘對應成不做,所以現行規則下對外行為不變。
- 候選介面比照決策函式的介面用型別協定定義(不用裸的可呼叫型別);輸入上面那個型別、輸出上面那個列舉。候選丟例外、回傳不是那個列舉、回「不知道」一律退回現行規則;候選回「證據不足」照「不做」處理。
- 路由閘(程式):先由程式把輸入歸到評分格(見增量 2 的評分表);只有「有候選、而且這格在已驗證清單上」才交給候選,其餘一律走現行規則。歸不了格(欄位缺漏或型別不對)也走現行規則。路由閘只在配速已判定偏低之後才被呼叫,所以「配速算不出」在正式呼叫路徑上走不到;這些退回分支靠直接呼叫路由閘的單元測試證明,不宣稱決策函式的端到端測試涵蓋到。
- 「已驗證清單」是評分格的不可變集合。決策函式的簽名不變(不改流程層的決策協定與既有呼叫端):新增一支帶「候選」與「已驗證清單」兩個關鍵字參數的內部函式,決策函式就是用「沒有候選、空清單」呼叫它。所以正式與測試的每一個呼叫者都走現行規則。
- 「不做的原因」不放進決策結果:另給一支評估用的診斷函式,回「決策結果 + 不做的原因」,決策結果那一半就是決策函式的回傳值;不做的原因是封閉列舉(證據過期、缺可信現況或指標、配速算不出、配速不偏低、判斷點回不值得加、判斷點回證據不足)。不做那個型別不加欄位,相等比較照舊。
- 行為不變的比對基準:改決策函式之前,先用現行決策函式對一批輸入跑一次,把結果存成測試固定資料入庫,這個提交必須早於改動;輸入是既有決策測試的全部輸入,加上依評分格與配速、預算邊界分層造的輸入。改動之後逐筆比對決策結果(用決策型別本身的相等比較,提案逐欄相同)。

### 增量 2:評估集、評分、報告與採用決定

- 放哪:新開 `src/rtb/eval/` 套件,比照維運套件放一份匯入規則:評估套件可以匯入分析端的判斷點與領域層的純計算,分析端、執行端、DSP、領域層、維運套件都不准匯入評估套件——規則作者的程式在結構上讀不到評估集。評估集是這個套件目錄裡入版本控制的資料檔(不寫進任何資料庫,不碰分析端與執行端的資料庫隔離)。新開一篇 Systems 家「評估與Jev決策點」管這個套件,程式落地前先開。
- 評分表(使用者裁定「證據不足」那條與三類答案;其餘格是本輪依審查意見補齊的暫用值,待使用者覆核):「正數」指純整數或純數字且大於零;缺值、零、負數、布林都不算正數。
  - 廣告暫停中 → 不值得加(不看其他欄位)。
  - 啟用中,曝光或點擊不是正數 → 不值得加(沒有可信的投放訊號;含「有曝光沒點擊」「有轉換沒點擊」,待使用者覆核)。
  - 啟用中,曝光點擊都是正數,轉換或營收至少一個是正數 → 值得加。
  - 啟用中,曝光點擊都是正數,轉換與營收都不是正數(零、缺值或負數)→ 證據不足(使用者裁定「零轉換零營收」;缺值與負數比照,待使用者覆核)。
  - 這張表對每一組輸入恰好給一類,由測試窮舉驗證互斥與完整。
- 標準答案由程式照評分表算,不派代理標註:評分表是確定的是非規則,派代理只會多一個誤讀規則的雜訊來源、沒有多任何獨立判斷力。另派一個乾淨的代理(只讀交接文件的業務描述,不看評分表、程式與測試)對一小批情境寫它認為的答案,跟評分表不一致的格列給使用者,檢查的是「評分表是不是使用者的原意」,不是拿來當標準答案。
- 評分格就是切片:狀態 × 曝光點擊是否都是正數 × 轉換營收是否有正數,共 4 格:暫停;啟用但曝光點擊不全是正數;啟用、曝光點擊都是正數、轉換營收有正數;啟用、曝光點擊都是正數、轉換營收都不是正數。暫停那格不再依其他欄位細分。配速區間與預算量級不影響答案,不當切片鍵;改成「無關欄位擾動檢查」:同一格內只改配速(偏低範圍內)或預算,候選的答案應不變。
- 情境生成:生成器依評分格分層造情境,每格同時造配速與預算的變化;生成器只依評分格定義與欄位型別造數字,不讀決策函式與測試;種子固定。
- 指標(每格事先指定,零分母語意寫死):
  - 標準答案是「值得加」的格:報召回率(該加的有加到多少)。
  - 標準答案是「不值得加」或「證據不足」的格:報誤提案率(不該加卻說要加的比例,判錯就是多花錢);兩者都是比例,分母是那一格的樣本數,不會是零。
  - 另報三類混淆表與總平均(只當參考,不當採用依據)。
- 門檻(暫用、待使用者覆核;本輪改過):以 95% Wilson 信賴下界比門檻,不比點估計。「值得加」格的召回率下界 ≥ 0.80;其餘格的「1 − 誤提案率」下界 ≥ 0.95。全對時下界要過門檻所需的最少樣本:0.95 要 73 筆、0.80 要 16 筆;所以每格最少 73 筆(原本 30 筆,30 筆全對下界只有約 0.89,撐不起 0.95)。
- 確定性的現行規則怎麼報:現行規則對同一格的每筆輸入答案都一樣,統計下界對它沒有資訊量。報告對現行規則逐格寫「一致/不一致」與造成不一致的規則差異(例如「不看廣告狀態」「不看轉換營收」);信賴下界與門檻只套在會隨機出錯的候選上。
- 報告與採用決定都是純函式的輸出:輸入是結構化的逐筆評分結果,輸出是結構化的逐格報告與逐格採用決定;人讀的決定紀錄由這份輸出產生,並記下它依據的評估集雜湊。
- 採用決定逐格下:某一格有候選實測、樣本數夠、指標下界過門檻,這格才進已驗證清單;沒有任何候選實測時整體不採用。這次沒有候選,所以已驗證清單是空的、結論是不採用(兩個理由見上一節),並列出缺的證據:正式環境的決策紀錄抽樣、人工標註、候選模型在每一格的實測、上線後逐格監測的機制。
- 比較表是結構化資料:每一格「品質、每次呼叫成本、延遲中位與 p95」各是一個儲存格,帶「有沒有量、數值、沒量的原因」三欄;現行規則實測,LLM 與 Jev 寫「沒量、原因:未導入」。交接文件完成條件「跟 LLM/程式基準比較」在這個階段的完成判準就是這樣,實作時用決策指令記一筆,連到 Phase 0「不導入 Jev」的裁定。
- 外洩紀錄:評估集是誰寫的、看過什麼;規則作者看過逐筆答案後回頭調規則,就要換一批評估集。評估集雜湊由測試釘住;換批要同時用決策指令記一筆理由與時間,測試只驗雜湊,誰有權換靠那筆紀錄留痕。
- 現行規則的評估結果照實報:預期它在「暫停中」與「證據不足」幾格不一致——那是規則缺陷,記進缺陷清單,不改評分表遷就規則,也不在這個階段修規則(修規則會改變 Phase 2 起的既有合約,另開計劃)。
