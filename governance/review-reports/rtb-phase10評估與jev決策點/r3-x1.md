severity: major

### F1 評估必須先把未驗證格冒充成已驗證，候選才有機會被評估
severity: major
blocking: 是
引句:「逐筆評分走跟正式路徑相同的組合:判斷點輸入經路由函式(含包裝、逾時與退回)」

路由函式只有在評分格已位於「已驗證清單」時才呼叫候選，但已驗證清單又必須由這次評估產生，形成循環依賴。照字面拿目前的空清單跑正式抽樣集，所有樣本都走現行規則，候選呼叫數為零，品質、成本與延遲均無法量測；若實作者先把待測格塞進清單，又把尚未驗證的格謊稱成已驗證。

具體例：新候選準備評估「值得加」格、目前已驗證清單為空 → 預期：候選在 16 筆正式樣本上被呼叫並產生品質與延遲資料 → 實際：路由全部選現行規則，候選完全沒被呼叫，採用閘永遠無法取得候選實測。

建議改法：把「允許本次評估呼叫的目標格」與「正式環境已驗證清單」拆成不同型別或不同入口；評估入口可以指定待測格，但不得把它輸出或持久化成已驗證，只有採用閘通過後才能產生正式清單。補一條合約：空的正式已驗證清單下，評估模式仍會呼叫指定候選；正式模式則不會。

### F2 三類標準答案被二元誤提案率壓扁，答錯類別仍可通過採用門檻
severity: major
blocking: 是
引句:「其他三格報誤提案率(不該加卻提案的比例,判錯就是多花錢)」

使用者裁定的標準答案有「值得加、不值得加、證據不足」三類，但除「值得加」外，採用閘只檢查有沒有誤提案。這會把「不值得加」和「證據不足」視為同一答案；混淆表雖會顯示錯誤，卻不參與採用條件，因此評估結論會宣告一個無法產出正確三類答案的候選已驗證。

具體例：暫停格的標準答案全部是「不值得加」，候選卻全部回「證據不足」 → 預期：三類答案全錯，該格不得驗證 → 實際：最後答案都不會提案，誤提案率為 0，73 筆全對二元動作後 Wilson 下界可過 0.95，該格會進已驗證清單。

建議改法：若三類答案都是合約，就讓採用閘同時要求該格的標準類別正確率或對應類別召回率達標，不能只看是否提案；若真正只在乎二元動作，則必須明確把候選輸出與 rubric 改成二類，並將「證據不足」移為診斷原因，而不是保留三類答案卻不驗其中的差異。

### F3 所謂硬逾時沒有可執行的終止語意，永久掛死候選仍可能卡住分析
severity: major
blocking: 是
引句:「另有一層包裝負責硬逾時:候選超過逾時沒回、丟例外」

現有決策介面是同步呼叫，沒有 deadline、取消權杖或隔離行程，佐證見 file: `src/rtb/analyzer/flow.py:73`。設計只寫「包裝負責硬逾時」，沒有規定如何停止仍在執行的候選；Python 執行緒逾時只能讓等待者離開，不能終止工作。有限時間的 `sleep` 測試可以通過，但永久阻塞或忽略取消的候選仍會掛住同步路徑，或在背景持續耗費執行緒與模型費用。

具體例：候選進入不返回的迴圈 → 預期：逾時後候選工作確實終止，路由回現行規則，後續呼叫仍可服務 → 實際：直接同步呼叫永久卡住；若用執行緒包裝，呼叫者雖暫時退回，但每次逾時都留下不能終止的工作，重複 73 次後可耗盡工作池。

建議改法：明定隔離與終止機制，例如每次候選在可終止的子行程執行、逾時即終止並回收；或把協定改成必須接受 deadline，底層網路呼叫也使用同一 deadline。合約測試需包含永不返回的候選及連續多次逾時，驗證沒有殘留工作且下一次路由仍能完成。

### F4 宣稱隱藏的正式評估集放在同一程式庫常數中，候選作者可直接讀答案過擬合
severity: major
blocking: 是
引句:「評估集是評估套件裡的一個 Python 模組(情境與標準答案寫成常數)」

設計後段要求正式環境抽樣集必須與候選開發隔離並保持隱藏，但前段把情境與標準答案存成同一程式庫中的 Python 常數。匯入禁令只能防正式程式碼 `import` 評估套件，不能防候選作者直接開檔、複製常數或用檔案 API 讀取；「看過就換批」也只是事後紀錄，不會讓隱藏性成立。

具體例：正式抽樣集 73 筆及答案提交進 `src/rtb/eval/`，候選作者讀取模組並寫成輸入到答案的查表 → 預期：隱藏集量到未見資料上的泛化能力 → 實際：候選 73/73 全對、通過 Wilson 門檻並進已驗證清單，但任何未列入常數的正式輸入都可能答錯。

建議改法：明確區分可提交的合成合約集與不可交給候選開發者的正式隱藏集。正式集應由獨立、具存取控制的評估執行器在評估時注入；程式庫只保存資料版本、雜湊、抽樣與標註證明及彙總結果，不保存逐筆答案。採用紀錄還要證明候選版本早於隱藏集揭露，揭露後該批不得再驗證新候選。
