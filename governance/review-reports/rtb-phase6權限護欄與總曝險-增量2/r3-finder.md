## F1 寫入守衛只封住現有請求函式，新增第二個共用 HTTP 入口即可漏過

severity: major

blocking: 是 — 設計只追蹤「這個函式名」的取得與使用，卻沒有封閉共用 HTTP 用戶端的匯出面。日後正常新增另一個請求函式時，分析端可在獲准的 DSP 用戶端內用它送 POST，而 S408 仍可能全綠，漏掉「分析行程不能寫」合約。

引句:「在那兩支檔案裡,這個函式名每一次出現都必須是直接呼叫;被賦值給別的名字、當參數傳出去、被偏函式包住,一律紅。」

具體例：在共用 HTTP 用戶端新增 `post_json()`，分析端 `dsp_client.py` 匯入它並呼叫 DSP 的預算寫入端點；現有 `request_json` 的 GET 與收件口 POST 保持不變。輸入「分析流程呼叫新增的 DSP 寫入函式」→ 預期 S408 測試翻紅；照目前文字實作，掃描仍只驗現有請求函式的出現位置與方法，新增的 `post_json()` 不在受管符號內，測試可保持綠燈。

目前共用 HTTP 用戶端只公開一個實際送出請求的入口，因此這個缺口尚未顯現：file: `src/rtb/httpclient.py:45`。既有邊界只禁止分析套件直接匯入網路模組，仍允許它經共用用戶端上網：file: `tests/analyzer/test_boundaries.py:102`。兩支獲准檔案目前也都直接匯入該單一入口：file: `src/rtb/analyzer/dsp_client.py:31`；file: `src/rtb/analyzer/inbox_client.py:18`。

S408 應再封一層：共用 HTTP 用戶端可供分析閉包使用的請求入口集合必須明列且完整；新增或改名入口時先令測試翻紅，或掃描所有從該模組匯入的可呼叫入口並逐一套用方法、網址與標頭限制。

第 2 輪的阻斷修正均已落地：增量 1 合併前提已涵蓋整個增量；版本較舊被歸回擋下側；回退新增歷史相容代碼分類；寫入掃描改為包含函式內匯入的靜態閉包。未看到這些舊問題回歸。
