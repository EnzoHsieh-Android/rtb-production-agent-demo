## 發現

### 1. 符號連結的 repo 路徑讓 mypy 被整批略過,回「沒有新增告警」
severity: major
blocking: 是,同一個型別錯誤僅因為 repo 路徑寫法不同,就從「擋」變成「clean」,這正是本輪修復想消除的「工具沒跑卻說乾淨」。
- 位置:`tools/mypy_sarif.py:72-83`(`select_paths`)與 `tools/mypy_sarif.py:133`(全被過濾就寫空 SARIF 回 0)。
- 引句:「                candidate = candidate.relative_to(ROOT)」
- 引句:「            args.out.write_text(json.dumps(to_sarif([]), indent=2), encoding="utf-8")」
- 問題:`ROOT` 來自 `Path(__file__).resolve()`(已解開符號連結),lumos 傳來的是絕對路徑,字面前綴是呼叫者給的 repo 路徑。兩者不一致(macOS 的 `/tmp`、`/var` 本身就是符號連結,家目錄或專案目錄是符號連結、git worktree 掛在連結底下同理)時 `relative_to(ROOT)` 丟 ValueError,該檔被當成「範圍外」丟掉;全部檔都被丟掉,就寫空 SARIF、回 0。
- 重現:
  - `cd /private/tmp/t1r2/w_typeerr && .venv/bin/python tools/mypy_sarif.py --out /tmp/o.sarif --only-configured-paths /tmp/t1r2/w_typeerr/src/rtb/dsp/errors.py; echo rc=$?` 輸出 `rc=0`,結果 0 條。
  - 同一檔改用 `/private/tmp/t1r2/w_typeerr/...` 路徑:`rc=0`,結果 1 條。
  - 經 lumos:`_lint_new_verdict('/private/tmp/t1r2/w_typeerr','HEAD~1..HEAD')` 得 `blocked True 1 條新增告警`;`_lint_new_verdict('/tmp/t1r2/w_typeerr', ...)` 得 `clean False 沒有新增的告警`,且 `ran` 列出兩條命令都「跑了」。
- 建議:比對前兩邊都 `os.path.realpath`(或 `Path.resolve()`);並把「輸入非空、卻有檔因為在專案根之外而被丟掉」與「在專案內但不在範圍」分開處理,前者至少寫 stderr 警告或回非 0,別悄悄變空報告。
- 佐證:`scripts/lumos` 約 19345 行的 uri 還原用 `os.path.relpath`/`realpath` 已為此處理過同類問題,證明 lumos 自己知道這是實際會發生的情形。

### 2. 接線測試的 CI 剖析仍有多種可繞過寫法(工具「有跑」的判定過寬)
severity: minor
blocking: 否,需要有人改 ci.yml 才會觸發,且文件已承認剖析器是簡易版;但與測試名稱宣稱的「不擋的寫法都抓得到」不符。
- 位置:`tests/test_static_wiring.py:46-65`(`ci_problems`、`runs_tool`)。
- 引句:「    return any(command.split()[:3] == ["python", "-m", tool] for command in commands)」
- 以下寫法我用 `parse_run_commands` / `runs_tool` / `ci_problems` 實跑,全部回「有跑、無問題」(即測試會綠,但 CI 實際不擋或沒檢查):
  - `run: python -m ruff check --exit-zero .`(永遠成功)
  - `run: python -m mypy || exit 0`(`|| true` 有抓,`|| exit 0` 沒抓)
  - `run: python -m mypy | tee log`(GitHub 預設 `bash -e` 沒有 pipefail,管線吞掉結束碼)
  - `run: python -m mypy --help`、`python -m mypy docs`(不檢查任何原始碼)、`python -m pytest --collect-only`、`python -m pytest -k nothing_matches`
  - 區塊寫法中 `exit 0` 放在 `python -m mypy` 之前
  - `uses: x/y@v1` 加 `with:` 底下的 `run: python -m mypy`、或 `env:` 底下的 `run:` 鍵:剖析器只看行首是不是 `run:`,不分是否為 step 的 key,被算成一條執行的指令
  - `on: push:` 底下 `tags: ['v*']`(只在打 tag 時觸發,分支推送不跑):只檢查 `branches` 與 `paths`,`tags` 沒擋
- 沒有繞過、但確認過會被抓或會誤紅的:單行 `|| true`、`if:`(步驟與工作)、`continue-on-error`、行首註解 `# run:`、`echo "python -m mypy"`、`working-directory`/`env: PATH`(這兩者本身不會讓 mypy 靜默成功,因為找不到檔案或命令會非 0,不算繞過)。
- 建議:至少補 `--exit-zero`、`|| exit`、`| tee`、`--help/--version/--collect-only`,以及只認 step 層級的 `run:`(用縮排判斷同一個 `- ` 項目),或改成對 `python -m tool` 之後的參數做白名單。

### 3. 剖析器對合法 YAML 寫法會誤紅(方向是假警報,不是漏抓)
severity: minor
blocking: 否,只會讓未來改 ci.yml 的人被測試擋一下,現有 ci.yml 沒有誤紅(實測 `test_static_wiring.py` 全綠)。
- 位置:`tests/test_static_wiring.py:28-33`。
- 引句:「            if value in ("|", ">", "|-", ">-"):」
- 重現:`run: |+`、`run: |2`、`run: | # 註解` 會被當成單行指令 `'|+'`、`'|2'`、`'| # c'`,底下真正的指令被忽略,`runs_tool` 回 False;`run: "python -m mypy"`(引號字串)同樣回 False;`python3 -m mypy` 回 False;行內流式 `- {if: false, run: ...}` 得到空清單。另 `"branches" in code or "paths" in code` 是子字串比對,任何含 paths 字樣的行(例如 `run: echo paths`)都會被報「推送觸發被分支或路徑限制」。
- 建議:先收斂支援的寫法並在測試訊息講明(現在只在文件裡講),或去掉引號與區塊標頭修飾再比對。

### 4. `select_paths` 沒有正規化路徑,`..` 段可穿過範圍判斷
severity: minor

- 引句:「        relative = LUMOS_TEMP_PREFIX.sub("", candidate.as_posix())  # 判斷範圍前先去掉臨時目錄前綴」

### 5. lumos 推送前不掃測試檔,tests 的 ruff 違規只有 CI 與 pytest 抓
