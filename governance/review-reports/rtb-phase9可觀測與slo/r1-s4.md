### 1. 到期批次掃描不限任務,S600 逐字實作會漏記「其他任務」的已過期事件

severity: major
blocking: 是 這是「漏記」,而且現有測試判準(S601 只驗種類存在真實觸發路徑,不驗有沒有遺漏)抓不到
引句:「執行端應在做那次改變的同一個交易裡寫一列生命週期事件」

`_accept_in_transaction` 開頭那句批次 `UPDATE proposals SET state = 'expired' WHERE ({PENDING}) AND expires_at <= ?` 不帶 `task_id` 條件,只要「待處理且已過期」就整批標記,受影響的往往是跟這次收件完全無關的其他任務(提案收件口.md 已有 PITFALL 明確記載這是「順手」機制)。增量 1 的觸發語意是「這次處置改變的那份提案」寫一列(時間、任務、修訂…),完全沒交代這個「一次 UPDATE 影響多個任務」的批次操作要怎麼逐列補齊任務/修訂欄位。若照字面只在目前這次呼叫的任務身上寫一列,會漏記所有被順手掃到期的「其他」任務的「已過期」事件。

severity: major

### 4. 「讀取函式同時收寫入交易與唯讀交易」沒講清楚怎麼跟既有的三重交易憑證檢查共存

severity: major
blocking: 是 這條防線曾被三輪獨立審查證明容易繞過,設計沒交代新交易型別要怎麼補這個洞
引句:「讀取函式同時收寫入交易與唯讀交易,寫入函式照舊只收寫入交易」

現有機制靠三重檢查擋住「寫入函式被塞進錯的交易物件」:私有 issuer 憑證(`ExecutorTransaction.__init__` 只認 `_EXECUTOR_TRANSACTION_ISSUER`)、型別完全相同(`type(tx) is not ExecutorTransaction`)、連線同一物件(`_own()`/`_conn()` 比對 `tx.conn is self._conn`)。`docs/rtb-production-agent-demo-knowledge/Systems/外部寫入嘗試紀錄.md:16` 記著這套機制是三輪獨立實測(換匯入別名、子類別、物件復活都試過)才收斂出來的,專案自己承認「威脅模型是防忘記,不防刻意繞過」。唯讀連線必然是另一支 `sqlite3.connect(...)`,不可能是同一個 `self._conn`;要讓讀取函式「同時收」兩種交易,勢必要新增第二種交易型別或放寬型別/連線比對,但寫入函式(`begin`、`transition`、`ack_blocked`、`await_approval`…)必須繼續嚴格排斥這個新型別——設計完全沒講這條界線畫在哪、由誰把關。

例:若實作圖方便,把 `_own()` 的比對從「`tx.conn` 是不是這個 `self._conn`」放寬成「`tx.conn` 在已知連線清單裡」,寫入函式(如 `record_stop`、`await_approval`)在跑到 `INSERT`/`UPDATE` 時才會因為 SQLite 本身拒絕唯讀連線寫入而丟出未被特別處理的 `sqlite3.OperationalError`,不會走現有「收據失效」或 `LeaseLost` 的乾淨錯誤路徑,而是讓那一輪處理一筆意外中止。
