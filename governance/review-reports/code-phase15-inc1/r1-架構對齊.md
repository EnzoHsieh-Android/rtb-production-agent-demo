## 1. 版本雜湊自己拼 JSON canonicalization,沒用評估套件已經在用的 `canonical_json`

severity: major
blocking: 是
引句:「json.dumps(document, ensure_ascii=False, sort_keys=True, separators=(",", ":"))」

`rule_mining_prompt.py` 的 `version_sha256()` 為了把評估版本的參數清單、系統提示、真相清單雜湊成一個字串,自己手刻了一段「排序鍵、緊湊分隔、轉 UTF-8 再 sha256」的正規化 JSON 邏輯。但評估套件在匯入白名單裡本來就准許用 `rtb.analyzer.investigation`(Phase 13 已列入 `PHASE13_ALLOWED`),而這支模組已經有一支專門給「雜湊用的正規化 JSON」的既有工具:

file: `src/rtb/analyzer/investigation.py:339`
```
def canonical_json(raw: Mapping[str, Any]) -> str:
    """原始回應的正規化 JSON:照分析端 DSP 用戶端內容雜湊的參數(鍵排序、緊湊、純 ASCII、
    不准 NaN)。"""
    return json.dumps(raw, sort_keys=True, separators=(",", ":"), ensure_ascii=True,
                      allow_nan=False)
```
評估套件自己也已經在用它算雜湊(不是分析端專屬):

file: `src/rtb/eval/investigation_eval.py:83`
```
return hashlib.sha256(inv.canonical_json(payload).encode("ascii")).hexdigest()
```

新程式碼另開一份「json.dumps + sort_keys + compact separators」的正規化寫法(且 `ensure_ascii=False`、沒有 `allow_nan=False` 的防護),等於在同一支評估套件裡多出第二種「雜湊用正規化 JSON」的做法,兩份參數不一致(ensure_ascii、allow_nan)以後容易被誤用混淆。

建議改法:`version_sha256()` 改呼叫既有的 `rtb.analyzer.investigation.canonical_json`(它已在 `PHASE13_ALLOWED` 匯入範圍內,`investigation_eval.py` 已示範同樣用法),不要另開一份 json.dumps 參數組合;如果非 ASCII 逸出真的不能接受,應該去改 `canonical_json` 本身讓兩處共用,而不是各寫各的。

## 2. `diff_text` 重造了 `metrics.percent_text` 的捨入/格式化演算法

severity: major
blocking: 是
引句:「精確分數 half-even 捨入到四位小數;負零寫 0。」

`rule_mining_prompt.py` 的 `diff_text(mean)` 為了把精確分數格式化成「百分點、四位小數、half-even 捨入、負零寫 0」的字串,重新手刻了一次跟 `rtb.domain.metrics.percent_text`完全同一套演算法(乘上刻度後用 `round()` 取整數,靠 `Fraction.round` 內建的四捨五入到偶數,再用整數除法/取餘湊出小數點字串、正負號另外處理負零):

file: `src/rtb/domain/metrics.py:230`
```
def percent_text(value: Exact) -> str:
    """分數寫成百分比刻度、固定 1 位小數、四捨五入到偶數;負零寫 0.0;原因代碼寫 na。"""
    if isinstance(value, Reason):
        return NA
    tenths = round(value * 1000)  # 分數的 round 是四捨五入到偶數
    sign = "-" if tenths < 0 else ""
    return _fits(f"{sign}{abs(tenths) // 10}.{abs(tenths) % 10}")
```

新程式碼的 `diff_text` 只是把小數位數從 1 位換成 4 位,其餘手法(刻度、`round()`、符號分離、取整除餘數拼字串)逐步照抄了一份,而不是把 `percent_text` 參數化(例如多一個小數位數參數)後共用。這正是評估套件本來就有規定「比例格式一律用既有的 `metrics.percent_text` 等函式,不另造統計或格式化做法」的那個口徑(該計劃文件裡也寫了同一句話),但這支新檔的百分比格式(`_row` 裡的 `share`)有照規定呼叫 `m.percent_text`,唯獨差值格式化沒有,自己另開一份。

建議改法:在 `rtb.domain.metrics` 加一個帶小數位數參數的通用版本(或讓 `percent_text` 接受 `places` 參數),`percent_text` 與 `diff_text` 共用同一份 half-even 捨入與負零處理邏輯,不要在 eval 層重刻一次領域層已有的格式化演算法。

## 3. 測試用 `functools.cache` 手刻跨測試共用固定樣本,沒用既有的 `pytest.fixture(scope="module")`

severity: minor
blocking: 否
引句:「固定三種子的整批生成用模組層快取,整個檔只各生成一次」

`tests/eval/test_rule_mining.py` 為了讓三個固定種子的合成歷史與預檢結果在整個測試檔案裡只算一次,直接在測試模組裡用 `@functools.cache` 包裝 `_generated(seed)` 與 `_preflight()` 兩個函式當手工快取。但這個專案的測試套件遇到「一個模組內多個測試共用同一份較貴的產出」時,既有寫法是 `pytest.fixture(scope="module")`:

file: `tests/analyzer/test_narrate.py:38`
```
@pytest.fixture(scope="module")
```
同樣寫法也出現在 `tests/demo/test_ai_page.py:25`、`tests/analyzer/test_f5_end_to_end.py:137`。

這份新測試檔完全沒用 pytest fixture 機制,改用標準庫的 `functools.cache` 在模組層手刻記憶化,是測試組織上的第二種做法。由於种子是參數化輸入,直接用 `scope="module"` fixture 不夠直觀,但仍可用「fixture 回傳一個帶內部快取的 callable」把兩者接起來,維持這個測試套件單一的跨測試共用產出慣例。

建議改法:把 `_generated`/`_preflight` 包進 `@pytest.fixture(scope="module")` 回傳的工廠函式裡,或至少在 PR 說明裡註明為何這裡刻意不用既有 fixture 慣例,避免以後的測試各自選自己順手的快取方式。
