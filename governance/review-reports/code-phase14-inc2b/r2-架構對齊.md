## 發現 1:`check_history()` 核對廣告編號的做法跟同檔 `check_daily()`/`check_adjustments()` 不同款,是另立的第二套

severity: major
blocking: 是

`dsp_client.py` 既有兩支「查詢結果核對這是不是這件任務的廣告」的函式(這次沒改動,不引 patch 原文,
只列現行程式碼佐證)——`check_daily`、`check_adjustments`——`campaign_id` 都是**必填**參數,而且回傳的
字典**保留** `campaign_id` 欄位(欄位本身就在白名單裡):兩支簽章都是 `(body: Any, campaign_id: str)`,
形狀核對都是 `set(body) != {"campaign_id", "rows"}` 連 `campaign_id` 一起驗,核過的 `campaign_id`
也留在回傳值裡(file: `src/rtb/analyzer/dsp_client.py:300,305,312`;`dsp_client.py:315,320,324`)。

這次新加的 `check_history()` 卻是另一套做法:`campaign_id` 改成**選填**、預設 `None` 時整段核對直接跳過
不驗,核過之後還**把這個欄位從回應裡拿掉**才繼續走原本的形狀檢查:

引句:「if campaign_id is not None:」

file: `src/rtb/analyzer/dsp_client.py:342`(緊接著 `body = {k: v for k, v in body.items() if k != "campaign_id"}`,
`dsp_client.py:347`)。

同一份修正的說明文字也承認這是刻意分岔出的另一條路徑:

引句:「不帶的只有評估案例與單元測試的既有形狀」

file: `src/rtb/analyzer/dsp_client.py:344`(對應 `r2-delta.patch` 新增行,`check_history` 的 docstring
與行內註解)。

同一支檔案裡,「驗證回應的廣告編號是不是這件任務的」這件事現在有兩種不相容的簽章與輸出形狀:
`check_daily`/`check_adjustments` 是「必填參數 + 核對後保留欄位」,`check_history` 是「選填參數(None
即跳過)+ 核對後剔除欄位」。呼叫端也因此分岔:`_query()` 對三者一律傳 `campaign`
(file:`src/rtb/analyzer/dsp_client.py:501-507`,`check_history` 與其他兩支同樣被動傳入,不是它自己選擇
跳過),但單元測試與評估路徑(`tests/eval/test_investigation_eval.py:967`、多筆
`tests/analyzer/test_dsp_client.py`/`test_investigation_review.py` 既有呼叫)都靠「不傳第二參數」繼續用
沒有廣告編號核對的舊行為——這個「選填即繞過」的後門是 `check_daily`/`check_adjustments` 從一開始就沒有
給過的選項。

判定為 major:同一檔案、同一類「核對 DSP 回應是不是這件任務的廣告」的問題,`check_history` 用了跟兩個
既有鄰居不同的參數契約與輸出形狀,符合本次嚴重度錨的「第二種做法」。
