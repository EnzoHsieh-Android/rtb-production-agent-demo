## 發現 1:`rule_round.progress()` 直接依賴 `TaskReads` 自己查表,不是照 Phase 13 `investigation.progress()` 的「呼叫端先讀、純函式重算」做法

severity: major
blocking: 是

`investigation.progress()` 的簽章是 `progress(records: Iterable[Any]) -> Progress`,這支檔整份
不匯入 `task_store`、不知道 `TaskReads` 存在(file: `src/rtb/analyzer/investigation.py` 全檔匯入清單,
僅 `hashlib`/`json`/`unicodedata`/`collections.abc`/`dataclasses`/`datetime`/`enum`/`fractions`/
`types`/`typing`/`rtb.domain.*`)。全專案目前呼叫它的每一處都遵守同一個模式——**呼叫端自己先從
store 撈出已提交列,轉成 plain 的 list/tuple/generator 再交給這支純函式**:

引句:「state = inv.progress(record for _seq, record in store.investigation_rounds(task.task_id))」

file: `src/rtb/analyzer/instrumented.py:149`(此行在本次 diff 是未動的上下文行,`rule_source()`
就寫在它旁邊,是新舊寫法的直接對照)。

`rule_round.py` 的 `progress()` 卻反過來,簽章直接吃 `TaskReads` 介面本身,函式體內自己打兩次表:

引句:「照已提交的規則輪步驟與事件重算進度(同 `investigation.progress` 的做法)。」

file: `src/rtb/analyzer/rule_round.py:103-106`

```
def progress(reads: TaskReads, task_id: str) -> Progress:
    """照已提交的規則輪步驟與事件重算進度(同 `investigation.progress` 的做法)。"""
    step_rows = reads.rule_steps(task_id)
    events = reads.rule_events(task_id)
```

docstring 自稱「同 `investigation.progress` 的做法」,但實際簽章與依賴方向不同:`investigation.
progress` 是零 store 依賴的純函式(可用手造的 list 單元測試),`rule_round.progress` 把
`TaskReads` 直接寫進型別簽章,是分析端決策/計算模組首次讓「進度重算」這件事跟儲存層介面耦合。
而且這個耦合不是只發生在 `progress()` 一處,`collect_plan()`(file:
`src/rtb/analyzer/rule_round.py:133-141`)、`decision_inputs()`(file:
`src/rtb/analyzer/rule_round.py:237-252`)、`decide()`(file:
`src/rtb/analyzer/rule_round.py:312-334`)全部直接收 `reads`/`store` 自己查表——`decide()` 甚至
在同一次呼叫裡對 `rule_steps` 查了兩次(一次經 `progress()` 內部,一次自己再查一遍):

引句:「mine = next((record for seq, record in reads.rule_steps(task.task_id) if seq == task.seq),」

file: `src/rtb/analyzer/rule_round.py:316`

對照佐證(呼叫端與測試成本的落差):
- `investigation.progress` 在既有慣例下可以拿手造的 `InvestigationRecord` list 直接單元測試
  (既有 `tests/analyzer/test_ai_judge.py` 的 `inv.progress([])`、
  `inv.progress([InvestigationRecord(...)])` 這類寫法,不需要真資料庫)。
- 這次 `tests/analyzer/test_rule_round.py` 完全沒有對 `rule_round.progress()` 做過手造記錄的單元
  測試;所有覆蓋都要透過真的 `DspServer` + `CampaignStore` + `TaskStore` 整條 E2E 跑
  (file: `tests/analyzer/test_rule_round.py` 新增的 `world`/`step`/`run_until` fixture,`r1-snapshot.
  patch` 對應行號約 5550-5700)。這正是把「進度重算」耦合進儲存介面之後,測試成本從「造幾筆記錄」
  變成「起一個 DB + 假 DSP 伺服器」的直接後果。

判定為 major:這是檔頭自己聲稱要「照 Phase 13 的做法」、卻在依賴方向上另起一套的情形,符合本次
嚴重度錨的「第二種做法」;標 ⚠ 是因為程式行為本身正確(有測試涵蓋、也沒有跨層匯入),不確定
「跟儲存層耦合」在這支檔的定位下算不算刻意權衡(例如規則輪需要同時讀 `rule_steps` 與
`rule_events` 兩張表,`investigation.progress` 只需要一張),因此判不準,盈餘部分留給人裁。
