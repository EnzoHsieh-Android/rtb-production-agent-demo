## 發現 1:錄製模式「沒帶帳本就用暫存帳本並印通知」的邏輯,五個命令列入口各寫一份、沒有共用一處,其中
一個入口(`eval/record.py`)因此漏掉了通知

severity: major
blocking: 是

`modelclient.recorded_scratch_ledger()` 本身是共用的(建暫存帳本這件事只有一處實作,
file:`src/rtb/modelclient.py:1482-1489`),但「什麼時候該呼叫它、呼叫完要不要印
`SCRATCH_LEDGER_NOTICE`」這個決策層,五個命令列入口(評估重播 `investigation_eval.py`、Phase 10 評估
`record.py`、原因假說 `hypothesis.py`、說明 `narrate.py`、分析端驅動 `runner.py`)各自手刻了一份,
沒有收在模型閘道或任何共用輔助函式裡,而且五份手刻邏輯彼此不同款:

引句:「scratch = modelgate.recorded_scratch_ledger()」

file: `src/rtb/analyzer/narrate.py:236`(接著 `print(modelgate.SCRATCH_LEDGER_NOTICE.format(path=scratch), file=errors)`,`narrate.py:237`)——`_recorded_ledger(args, errors)` 在**還不知道最終模式**時就
先建暫存帳本並印通知(呼叫時機在 `open_gate()` 判定模式之前)。

引句:「errors.write(modelgate.SCRATCH_LEDGER_NOTICE.format(path=scratch) + "\n")」

file: `src/rtb/analyzer/runner.py:249-250`——把 `narrate.py` 的 `_recorded_ledger(args, errors)`
整支函式(同名、同邏輯、同呼叫時機)在另一個檔案重寫一遍,只差通知輸出用 `errors.write(...+"\n")`
而不是 `print(..., file=errors)`。

引句:「if scratch is not None and gate.ledger == scratch:」

file: `src/rtb/eval/investigation_eval.py:249-250`——`investigation_eval.py` 也在模式判定前
(`235` 行)就先建暫存帳本,但改成等 `open_gate()` 回來後,靠比對 `gate.ledger == scratch` **確認真的
用上**才印通知,是跟 `narrate.py`/`runner.py`「建了就無條件印」不同的第三種算法。

引句:「ledger = mc.live_ledger_path() if live else (args.ledger or mc.recorded_scratch_ledger())」

file: `src/rtb/eval/record.py:248`——這一支(Phase 10 評估)是先算出 `live` 再決定要不要建暫存帳本
(第四種時機,發生在模式已確定之後,結構同 `hypothesis.py:294` 的
`args.ledger or args.recorded_ledger or _scratch(shown)`),但**全檔案沒有任何一行印
`SCRATCH_LEDGER_NOTICE`**(`src/rtb/eval/record.py` 只在 383 行印既有的 `settings.notices`,
跟暫存帳本無關)——五個入口裡唯一完全不通知使用者「這趟改走暫存帳本」的一個。

引句:「shown["notices"].append(mc.SCRATCH_LEDGER_NOTICE.format(path=scratch))」

file: `src/rtb/ops/hypothesis.py:275-276`——第五種寫法,通知不印到 stderr,而是塞進 JSON 輸出的
`notices` 欄。

這五種寫法各自獨立判斷「該不該建暫存帳本」「建了要不要印/往哪印通知」,結果已經出現真的行為分歧,不
只是風格差異:`record.py` 的評估重播在錄製模式沒帶 `--ledger` 時會靜默改用暫存帳本,完全不印
`SCRATCH_LEDGER_NOTICE`,跟本輪關閉的事故([[Issues/錄製模式的原因假說寫進真帳本]])要求的「入口...
把路徑印到標準錯誤」不符。這個缺口目前也沒被測試攔住:`tests/model/test_shared_entry.py:509` 的
`test_recorded_entries_never_touch_the_account_ledger` 依序呼叫 `record.run(...)` 與
`investigation_eval.run(...)`,兩次呼叫共用同一個 `err` 緩衝區,最後只斷言
`"暫存帳本" in err.getvalue()`(file:`tests/model/test_shared_entry.py:523`)——這個字串是
`investigation_eval.run()` 那次印的,`record.run()` 完全沒印也照樣通過斷言,測試本身測不出
`record.py` 漏印。

判定為 major:同一個修正目標(錄製模式沒帶帳本時的暫存帳本與通知)在同一輪修正裡分五個入口各寫一份、
不同款,其中一份實際上漏做了規格要求的「印到標準錯誤」,符合本次嚴重度錨的「第二種做法」(此處是第
二至第五種)。
