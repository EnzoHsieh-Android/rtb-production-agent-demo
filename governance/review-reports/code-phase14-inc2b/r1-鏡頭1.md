## 試過、沒有翻紅的攻擊面(供其他席參考,不列為發現)

1. **暫停/異常先判**
   - `policy.steps` 的判斷順序是:新鮮度 → 可信現況要有合法狀態 → `_base_rule`(第 1/2 條、輸入建不起來)→ 配速 → 九條。
   - 配速正常的暫停案判「不值得加」,配速算不出的異常案判「證據不足」,都在 A 步結案、不提案。順序與計劃第 152 行一致。
2. **缺查詢一律證據不足**
   - 原始回應只在「收據不是 none」時才存。`_raw` 讀不到就是 None,領域 `decide` 會回 `QUERY_NO_RESULT`。
   - 收據建構丟 ValueError、改記 INVALID 的那條路也一樣不存原始回應,所以不會出現「收據說沒結果、規則卻拿到原始值」。
3. **A/C 之間有人改預算**
   - DSP 改預算、暫停都會升版本(`src/rtb/dsp/store.py:391-392`),`_changed` 比版本,會作廢重來。
   - 如果改動落在 C 讀完現況之後,提案帶的是 C 的版本,由執行端的版本守衛擋下。
4. **第 3 條的近期調整**
   - 三個來源都看:歷史列、截斷時摘要的旗標、過去調整的 `committed_at`。
   - 截斷時,`_summary_agrees` 與 `history_recent_agrees` 在讀取層已經核對過摘要,不合就記 invalid,結果是證據不足。
5. **第 4 條只看最近一次加額**
   - `check_adjustments` 要求 `days_ago` 由近到遠排序,不合就整份不收,所以 `_past_decision` 遇到第一筆加額就 break 是對的。
6. **跨輪混用**
   - `progress` 只取最新一輪;任何非續步事件、或任一步不是本政策版本,都算作廢。
   - `decide` 要求「這一列的序號」等於本輪該步最新的序號,否則回 `RESTART_NO_ROUND`。
   - `_decide` 的 B、C 都取同一輪。我沒構造出能讓舊輪 B 的收據或原始回應進到新輪定案的序列。
7. **證據參照**
   - 規則輪提案的參照是:C 的基本三筆,加上 B 的歷史與過去調整收據,加上 C 的長窗與逐日收據。符合 [S1107] 改寫。
   - 規則輪不會出現參照到沒有結果的收據就提案的情形,因為任一查詢缺就不提案。
8. **AI 退回**
   - `_fallback` 會走到的前提是前置過濾已過(新鮮、有現況、配速偏低)。這時候只剩兩種結果:要四查詢(回 `RuleContinue`),或暫停/異常/輸入不合法(`_rule` 以缺四查詢判,永遠產不出提案)。
   - 舊的「有投放就加」退路已經沒有了。
9. **已知留給增量 3 的部分(不報)**
   - 開 AI 時,暫停或異常但配速偏低的案件仍會進模型;AI 直接答 `propose` 時仍只用基本三筆建提案。
   - 這些是計劃第 160 行明列的增量 3 範圍,這份 diff 沒有讓它比 Phase 13 更差。
