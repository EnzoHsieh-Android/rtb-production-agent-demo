## 逐項核對結果

1. **說明文字不進提案/送件/執行端([S913][S914])**:`narrate.py` 只讀 `handed_off_rows()`,唯一寫入是 `store.record_narrative()` 寫進獨立的 `narrative_results` 表;`tasks`、`evidence`、`task_leases` 三張表在 `test_the_model_narrative_never_changes_the_submitted_proposal` 裡驗證逐位元組不變。執行端全套件(`grep -rn "narrative" src/rtb/executor/`)沒有任何一處提及 narrative,`Proposal.CHECKS` 也沒有 narrative 相關欄位,`test_the_model_narrative_never_reaches_the_executor` 掃過執行端原始碼確認不匯入 `rtb.analyzer`。

2. **同一情境重跑兩次,送出內容與錄製鍵逐位元組相同([S921])**:`narrate.prompt_for()`(排序後的 `requested_change`、依 `evidence_refs` 定序的證據、佔位符依出現順序替換)與 `hypothesis.build_input()`(`_related()` 過濾延遲/model_and_jev 樣本、`_examples()` 依 `(segment.at, index)` 排序)皆為確定性組法。`tests/model/test_modelclient.py::test_the_same_scenario_twice_gives_the_same_prompt_and_key` 用 F5 端到端(narrate)與調查實演(hypothesis)兩條真路各跑兩次比對通過;我自己的獨立二次真跑(見上)也得到逐位元組相同的結果。

3. **假說只在告警觸發時才產生([S910])**:`hypothesis._hypothesis()` 在 `fired(statuses)` 為空時直接印 `NO_ALERT`、回傳 `{"status": "no_alert", ...}`,不呼叫 `_ask()`,因此不記帳。我的獨立真跑確認:12 筆事件但未觸發告警時,假 claude 被呼叫 0 次。

4. **領取表、結果表只增不改,重跑不重複付費([S929])**:`task_store.py` 對 `narrative_claims`、`narrative_results` 只有 `INSERT`/`SELECT`,無任何 `UPDATE`/`DELETE`。`claim_narrative()` 的三段判斷(已有 OK 結果不再領 / 最新領取有失敗結果立刻再領 / 最新領取待結果且未過 10 分鐘就跳過)與 `record_narrative()` 的「仍是最新領取且尚無結果才寫入」圍籬,經 `test_two_narrators_call_the_model_once_per_proposal` 完整覆蓋(含 9 分 59 秒不可再領、10 分整可再領的邊界)。`narrate_pending()` 逐次呼叫前先 `has_narrative()` 短路,已完成的提案標 `already_done`,不重觸發模型呼叫。

5. **追蹤檢視標「模型產生、僅供參考」、輸出跳脫([S915][S930])**:`trace._narrative()` 對成功結果回傳 `{"label": MODEL_LABEL, "source", "text"}`,放在 `detail` dict 的最後一鍵(`test_the_trace_labels_the_model_narrative`、`_narrative_detail` 斷言 `list(detail)[-1] == "model_narrative"`);9 種非成功結果類別在 `NARRATIVE_SHOWN` 全數覆蓋、無成功結果顯示分類、無任何領取顯示「尚未產生」。輸出走 `json.dumps(..., ensure_ascii=False)`,而 `narrate.valid_narrative()` 已先擋掉不可列印字元(含換行、ESC 等控制字元),模型文字不可能帶進破壞 JSON 結構或終端機的跳脫序列。`narrate.py` 自己命令列的 stdout(`NarrationResult`)本身也不含說明文字欄位,進一步縮小曝露面。

## 補充觀察(非阻擋)

`narrate._narrate_one()` 呼叫 `store.record_narrative(...)` 未檢查回傳值(`src/rtb/analyzer/narrate.py:160`、`:169`);在極窄的競態(被接手的舊持有者在期限內仍拿到模型回應但寫入被拒)下,該次 `NarrationResult.outcome` 會回報模型呼叫本身的結果(如 `ok`),但沒有對應的持久化列。這與計劃 [S929] 明講的「至少一次,不是恰好一次」語意一致,`record_narrative` 的圍籬本身正確運作(不會覆寫、不會把過期資料寫成正式結果),因此不算違反合約,列為觀察而非缺陷。
