## Findings

### 1. 開頭的「有證據支持」比評估結果和同一份 README 的表格都說得強

severity: major
blocking: 是
引句:「AI 只留在有證據支持、或不碰決策的位置」
查證 file: `governance/eval/phase15-rule-mining.md:46`、`governance/eval/phase15-rule-mining.md:49`、`docs/rtb-production-agent-demo-knowledge/Projects/RTB_Phase15AI找規則模式_計劃.md:194`、`README.md:49`、`README.md:54`

問題:

- 找規則能留下,是因為事先定好的撤除條件「沒觸發」,不是評估證明 AI 有額外價值:
  - 召回和窮舉一樣,都是 2/2。
  - 兩批精確度略高,是因為 AI 挑中一條相關誘餌;依凍結規則,這條不算進分母。計劃第 194 行明寫「不是 AI 多找到真規律」。
- 同一次修改裡,表格那一列刻意寫成「目前不足以撤除」「受限的候選探索工具」,README 第 54 行也說明了差距來自哪裡。開頭這條卻把它歸成「有證據支持」,前後說法不一致。
- 面試官只要讀到第 54 行,就會看出「沒撤掉」被寫成了「有證據支持」,正好違反這份 README 自己主張的「沒證據不給權」。

建議改法:

- 標題改成跟表格同一個強度,例如「**AI 只留在沒被評估撤掉、或不碰決策的位置**」。
- 後句「找規則靠評估留下」改成「找規則沒觸發事先訂好的撤除條件,暫時保留為候選探索工具」。

### 2. 「通過/沒過」兩支把驗證器的結果說成宣稱本身成立或不成立

severity: minor
blocking: 否
引句:「沒過：CI 判紅，宣稱不成立」
查證 file: `tools/verify_claims.py:4`、`tools/verify_claims.py:8`

問題:驗證器自己寫明只做機械檢查,不判斷證據在語意上夠不夠(第 8 行)。它的結果有三種(第 4 行):

- 0 = 全通過
- 1 = 有擋下,包括只是程式改過、雜湊過時
- 2 = 無法判定,例如參數錯、清單讀不懂

所以:

- 通過只代表「證據都在、沒過時、測試全過」,不等於宣稱在語意上成立。
- 沒過也可能只是雜湊過時或無法判定,不等於宣稱被推翻。

CI 判紅這一半是對的。

建議改法:

- 「通過：證據齊全、測試全過」
- 「沒過：CI 判紅,這項宣稱在修好前不算數」

### 3. README 新的直式圖和讀者實際跑的展示頁流程圖、靜態圖文字互相矛盾

severity: minor
blocking: 否
引句:「提出建議（送進收件口）─────→ AI 寫說明（只給人看）」
查證 file: `src/rtb/demo/flow.py:150`、`src/rtb/demo/flow.py:152`、`src/rtb/demo/present.py:326`、`src/rtb/demo/page.py:1125`、`docs/assets/agent-flow.svg:74`、`src/rtb/demo/driver.py:1799`

README 的直式圖本身符合程式:說明命令列只讀已送出的提案,展示裡在整個情境跑完之後才跑。但讀者照「跑起來看看」打開的東西有三處跟它不一致:

1. **展示頁流程圖的順序相反。** 展示頁的流程定義是 `a_propose → a_narrate → a_submit`,邊的文字是「附上模型說明」再「送出」,也就是先寫說明、再送出建議。
2. **核可表單其實看不到說明。**
   - 表單的 `narrative` 寫死成 `None`(present.py:326),所以核可表單一律顯示「沒有 AI 說明」。
   - 表單文案卻寫「再閱讀 AI 產生的參考說明」(page.py:1125)。
3. **靜態流程圖的文字也對不上。** README 第 14 行連到的靜態圖寫「送件後供確認者參考」,但確認者在核可當下看不到說明。

README 這次把「只給確認的人看」改成「只給人看」是改對了;但面試官跑展示時,看到的順序和用途跟 README 對不上。

建議改法:這不是 README 能單獨修好的,要選一條:

- 修 `flow.py` 的邊,把說明改成送出後的旁支;並把靜態圖的「供確認者參考」與表單文案改成符合現況。
- 或在 README 這張圖下補一句:「展示裡說明在情境結束後才產生,核可表單不顯示。」
