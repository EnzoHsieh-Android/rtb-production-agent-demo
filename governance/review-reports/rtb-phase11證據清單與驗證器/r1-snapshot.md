# RTB_Phase11證據清單與驗證器_計劃

PRIOR-ART: 交接文件第 15 節的「政策 → 證據合約 → 固定規則驗證器 → 通過/擋下」;軟體供應鏈的出處證明(SLSA provenance、in-toto 的「宣稱要附可重算的材料雜湊」)只借概念,不引入套件(零依賴家規);測試結果讀 pytest 內建的 JUnit XML 輸出,用標準函式庫 xml.etree 解析。
RETIRE-IF: 專案改用外部的證據平台(例如 CI 內建的出處證明與政策引擎)並接上這五條宣稱時,撤掉這支驗證器,只留宣稱清單當輸入;或者連續半年沒有任何一次擋下是真問題(全是清單格式或雜湊重貼),重新評估值不值得留。

## 這份計劃在解決什麼

交接文件 Phase 11:把正式環境的安全政策轉成可證明的工程閘。完成條件五項:至少涵蓋冪等/結果不明、權限/護欄、並行、提示注入、總曝險;驗證器能因缺檔、測試沒跑、證據過期、宣稱範圍超過證據而擋下;故意只填「已完成」的自我宣稱無法通過;語意審查與機械驗證職責分離;驗證結果在本機與 CI 可重現。

這個階段要防的事故:系統宣稱「這件事已經處理好了」,但背後的證據已經過期、根本沒跑、或只是有人寫了一句「已完成」;所有人看到綠燈就以為安全。

## 使用者裁定(2026-09-24,使用者本人,清醒時)

- 情境題:證據是舊版本跑出來的、之後改過宣稱範圍內的程式 → 擋下。
- 方向:每條宣稱一份 JSON 證據清單;專案內一支驗證器,本機與 CI 同一個指令;驗證器自己在目前版本跑指定測試,不採信外部提供的測試結果;清單不准有「結果」欄;驗證器只做機械檢查,語意是否充分留給獨立審查員、驗證器不採信審查員結論;跟 lumos 各自獨立、互不依賴。

## 設計

### 宣稱清單(claims/*.json,每條宣稱一份)

- 欄位白名單,多一個不認得的鍵就擋(白名單以外的任何鍵都擋,所以 result、passed、status、verdict、done 這些「結果」的同義欄位自然被擋,不另列黑名單):
  - manifest_version(整數,目前 1)、claim_id(跟檔名一致)、policy(一句白話宣稱,給人讀,驗證器不解讀)。
  - scope:這條宣稱涵蓋的正式程式檔清單,每一項帶 sha256;另帶 harness:證據依賴的測試基礎設施檔(模擬 DSP、假物件、注入樣本、conftest)清單,每一項也帶 sha256。
  - enumerations(選填):宣稱裡「每一種」「所有」要從程式的登錄表機械列舉,寫成「來源檔:常數名」加過濾條件;驗證器用語法樹讀出字面常數,得到應涵蓋的項目。
  - evidence:每一項是一個 pytest 節點編號,帶 covers(它涵蓋列舉裡的哪幾項)與 kind(unit、concurrency、failure_injection、end_to_end);failure_injection 另帶注入手段(例如故障標頭模式、子行程死亡標記)。
  - symbols:宣稱依賴的關鍵函式,寫成「檔:名稱」。
- 清單不帶任何結果;結果一律由驗證器算。

### 驗證器(tools/verify_claims.py,指令:python tools/verify_claims.py claims/)

依序檢查,任一步不過就擋下並列出原因,全部通過才印通過;結束代碼 0 是全通過、1 是有擋下、2 是清單讀不懂:
1. 格式:白名單鍵、型別、claim_id 跟檔名一致;沒有任何清單、或少了五條必要宣稱之一也擋。
2. 存在:scope、harness、symbols 的檔案都存在;symbols 的名稱用語法樹在該檔找得到定義。
3. 新舊:scope 與 harness 每個檔重算 sha256,跟清單不一致就擋(「證據是舊版本的」)。不用 git 比較,因為 CI 只抓一層歷史。
4. 列舉覆蓋:每個 enumerations 讀出的項目,都要被至少一項證據的 covers 標到,少一項就擋並印出是哪一項;登錄表讀不出字面常數(動態組出來的)也擋,不放行。
5. 故障注入:kind 是 failure_injection 的證據,用語法樹確認那支測試(含它用到的 fixture 所在檔)真的引用了宣告的注入手段,而且測試本體有斷言。
6. 真的跑:把所有證據的節點編號交給 pytest(子行程、sys.executable -m pytest、關掉快取、加 `-o xfail_strict=true`、輸出 JUnit XML 到暫存檔),每個編號都要至少收集到一筆、全部通過;跳過、預期失敗、沒收集到、被取消選取都算擋;pytest 回「找不到測試」也擋。參數化的函式層編號展開成全部參數,全部要過。
   - JUnit 的限制(前掃實跑 pytest 9.1.1 確認):跳過與預期失敗都記成 skipped(type 分別是 pytest.skip、pytest.xfail);**預期失敗卻通過的測試在 JUnit 裡跟一般通過長得一樣**,所以要靠 `xfail_strict=true` 把它變成失敗;被取消選取的測試不出現在 JUnit 裡,靠「每個編號至少一筆」抓。
   - 任一個編號找不到時,pytest 回結束代碼 4 而且整批一支都不跑;驗證器要從 pytest 的輸出指出是哪一個編號,不能只說「有錯」。
   - JUnit 記的是 classname(路徑斜線換成點、去掉 .py,類別方法再接類別名)加 name(參數化帶方括號),驗證器照這個規則把節點編號對回 testcase。
- 驗證器不匯入 rtb 的任何模組(讀程式一律用語法樹與文字、跑測試用子行程),也不呼叫 lumos;rtb 的任何模組也不准匯入 tools。
- 驗證器只做機械檢查。「這組測試夠不夠代表這條宣稱」這種語意判斷不在驗證器裡,也不讀任何審查結論。

### 五條宣稱

- claims/idempotency-unknown-outcome.json:DSP 同一把冪等鍵最多套用一次;DSP 已提交但回應逾時時,執行端記成結果不明、用同一把鍵對帳,不換新鍵重送;提交後當機可從操作紀錄恢復。證據:F1 三支、F2、F6 端到端與 DSP 儲存層、收件口的單元與並行測試。
- claims/permission-guardrail.json:寫入要帶有效能力憑證,範圍(廣告、動作、租戶)對得上才放行;單次加額超過比例上限、決策過時、廣告版本已變一律擋下;人工核可只對它簽的那一份內容有效;故障注入要開旗標、只綁本機、分析端送不出故障標頭。沒有既有 ★INVARIANT★,證據節點在實作增量時從前掃列的測試檔逐支選定。
- claims/concurrency.json:同一份提案多個工作者同時處理只寫 DSP 一次;舊版本決策被擋、不寫進 DSP;分析端同一個任務併發推進只落地一次。證據:F3、F4 端到端與多工作者、版本衝突、租約測試。
- claims/prompt-injection.json:廣告名稱等不可信文字不影響決策、不流進提案;提案只收白名單欄位;可信證據不帶自由文字。證據:F5 端到端與信任邊界、提案、證據、DSP 用戶端白名單測試。
- claims/aggregate-blast-radius.json:總曝險到門檻就停、剛好到門檻放行;兩個工作者不能一起衝過門檻;超過的停在待核可、每筆都有紀錄。證據:F7 端到端與總曝險、核可測試。
- 冪等那條另帶列舉:DSP 會改廣告狀態的寫入動作,從 DSP 伺服器模組(路由那一層,不是儲存層)的 CAMPAIGN_WRITE_ACTIONS 列舉(update_budget、pause_campaign),不是從全部路由列舉——作廢只看鍵、不改廣告狀態,不在「版本不符拒收」的範圍。圖譜那條合約的措辭照這個改窄(寫明不含作廢),並附一句理由。

### CI 與本機

- CI 另開一個跟 checks 平行的工作:checkout、裝開發期工具、跑同一條指令;結束代碼不是 0 就紅。平行跑是為了不拉長 checks 那個工作的時間(F7 的 60 秒上限在那裡)。
- 本機用同一條指令;README 或 Systems 家寫清楚。

## 實務隱患

- 已排除:金流:驗證器不改任何產品程式行為,只讀程式與跑測試。
- 已排除:對外送出:驗證器只在本機跑測試,測試本身用的是本機模擬 DSP。
- 已排除:不可逆:清單與驗證器只是入庫檔案與一支唯讀工具。
- 未排除:守衛面:新舊判定靠清單裡的雜湊,作者可以改了程式之後直接重算雜湊寫回去,機器分不出「重看過證據還成立」還是「只是重貼」;唯一的效果是逼那次改動在同一個提交裡讓清單出現差異、讓審查員看得到。這是機械驗證的天花板,語意是否仍成立歸獨立審查員。
REVISIT:2027-03-31 若雜湊重貼沒被審查員抓到的情形發生過一次,改成「雜湊變動要附一行審查理由,驗證器檢查理由存在」。
- 未排除:covers 是作者自己標的,驗證器只查「有標、測試名對得上、測試真的跑過且通過」,不查那支測試真的測了那一項;同理故障注入只證明有注入、有斷言,不證明注入有意義。
- 未排除:列舉只對有登錄表的宣稱有效;「所有並行路徑」這類沒有登錄表的宣稱列舉不出來,只能靠審查員判斷證據是否充分。
- 未排除:驗證器每次跑證據測試約 45 秒到 1 分鐘(F7 那支占 30 秒),CI 多一個平行工作。
