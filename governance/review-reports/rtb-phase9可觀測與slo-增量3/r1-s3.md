severity: major

## F1 比例上限的「開始時目前預算」在第一筆操作上無法回頭重算

severity: major
blocking: 是 — 副作用核對函式若真的照這句字面實作,對每個廣告的第一筆已提交操作都會找不到判準所需的「開始時目前預算」,只能亂猜或漏判,而這正是目標為零的護欄違反率要防的那一種誤判。

引句:「加的量超過比例上限而沒有比例那一關的核可使用紀錄」

問題:比例上限 = `max(budget * 1 // 2, 1)`(`src/rtb/executor/guardrails.py:31` `increase_too_large`),這裡的 `budget` 是「處理一筆開頭讀到的現況」(同檔案第 30 行註解),也就是那次寫入送出前 DSP 廣告的當時預算。要在事後(增量 3 的核對函式)重算「加的量超不超過比例上限」,必須先知道「那次寫入之前」廣告的預算是多少。

- 這個「之前的預算」不是 DSP 操作紀錄(`src/rtb/dsp/store.py:38-42` 的 `operations` 表)裡的欄位;表裡只有 `version_after`、`expected_version`、`params_json`(新預算,不是舊預算)。要回推某個 `expected_version = E` 時的預算,唯一辦法是找同一個廣告 `version_after = E` 的那一筆操作,讀它的 `new_budget`(如果那筆是 `update_budget`;如果是 `pause_campaign`,`_next_state` 不改預算,見 `src/rtb/dsp/store.py:203-210`,要再往前追一筆)。
- 但當 `expected_version = 1` 時(這是任何廣告第一次真的被寫入時必然的值,因為 `seed_campaign` 建檔時 `version = 1`,見 `src/rtb/dsp/store.py:272-281`,而版本只在操作裡遞增,見同檔 209、210 行),`operations` 表裡不存在 `version_after = 1` 的列——那是建檔那一刻的狀態,建檔本身(`seed_campaign`)不是一筆操作,不進 `operations` 表,而且 DSP 沒有任何 HTTP 端點可以建檔(`src/rtb/dsp/server.py` 找不到建檔路由),`campaigns.budget` 欄位本身會被之後每一筆操作原地覆寫(`UPDATE campaigns SET budget = ...`,`src/rtb/dsp/store.py:418-421`),不留歷史。所以「這個廣告第一次真正提交的那筆寫入,寫入前的預算是多少」在事後完全查不到。
- 這不是稀有邊界情況:每一個廣告的「第一次真正提交」在生產與示範資料裡都會發生,不是舊資料庫遷移前才有的情況(遷移前後都一樣查不到)。
- 對照設計自己在同一段對「開始時已用額度」的處理方式(引句:「這個增量在嘗試紀錄第一列多記一欄『開始時已用額度』(開始一筆時本來就算過這個數,同一個交易寫下,只增不改)」)——設計已經承認「事後用查詢當下重算」對總曝險門檻是錯的、需要新增持久欄位才能回頭核對;但完全一樣的「查詢當下重算算不出過去某一刻的值」問題,同樣發生在比例上限的「處理一筆開頭讀到的現況」上,設計卻沒有給比例上限加上等價的持久欄位(例如在嘗試紀錄第一列多記「開始時的廣告預算」),[S663] 只補了總曝險那一項。

建議:比照 [S663] 的做法,在嘗試紀錄第一列(`begin()`,`src/rtb/executor/attempt_store.py:329-371`)多記一欄「開始時的廣告預算」(`view.budget`,呼叫 `begin` 之前就已經讀到,見 `src/rtb/executor/execution.py:474`、`597`),核對函式改成讀這一欄,不要求事後從 DSP 操作歷史回推;沒有這一欄的舊列(增量 3 之前寫的)照 [S663] 的「無法核對」處理。

## F2 DSP 操作紀錄裡舊資料的政策版本是空值,政策版本比對會把它們全部誤判成違規

severity: major
blocking: 是 — 只要窗內落進任何一筆政策版本欄位補齊之前寫的舊操作,字面實作會把它們每一筆都算成「未授權或違反護欄的副作用」,而這條指標的目標是零、不容許系統性誤報。

引句:「DSP 提交當下記下的政策版本(憑證帶的)跟提案自己的政策版本不同」

問題:
- 提案的 `policy_version` 是必填字串(`src/rtb/domain/proposal.py:58,177`),不可能是空值。
- DSP `operations` 表的 `policy_version` 欄位是後補的(`src/rtb/dsp/store.py:259-260`:「舊操作沒有紀錄政策版本,誠實留空值」),`ALTER TABLE operations ADD COLUMN policy_version TEXT` 沒有 `DEFAULT`,補欄位之前寫進去的每一筆操作,這一欄永遠是 `NULL`,不會被回填。
- 這樣一比對,任何補欄位之前提交的舊操作都會是「DSP 記下的政策版本(`None`)跟提案自己的政策版本(非空字串)不同」,被核對函式判成壞事件,而它們在當時完全是正常提交,不是護欄被繞過。
- 這條核對函式讀的是「窗內」DSP 提交(依提交時間歸窗),只要示範或正式環境的服務水準週期(30 天,或示範縮短的 12 小時)覆蓋到任何一筆政策版本欄位補齊之前的舊操作,這條目標為零的指標就會顯示非零,而且原因跟本文設計要防的「未授權或違反護欄」完全無關。

建議:核對函式對 DSP 記下的政策版本為空值的操作,比照增量 3 對「開始時已用額度」舊列的處理,另報「無法核對」(不算好也不算壞),不要直接判定為政策版本不同。

## 其餘檢查(確認沒問題)

- DSP 操作紀錄(`src/rtb/dsp/store.py` 的 `operations` 表)有 `idempotency_key`、`campaign_id`、`policy_version`、`expected_version`、`committed_at` 這些欄位,足夠支撐「冪等鍵是執行端鍵格式的」篩選與「政策版本」欄位本身的存在性(空值問題見 F2);沒有另外的資料缺口。
- 嘗試紀錄第一列(`src/rtb/executor/attempt_store.py` 的 `attempts` 表,`seq = 1`)確實帶租戶(`tenant`)、預留金額(`reserved_amount`)、完整提案快照(`proposal_json`)三樣;追蹤 `src/rtb/executor/execution.py:675-681` 確認每一次呼叫 `begin()` 都會傳入 `Reservation`(即使是暫停或減預算,`amount` 算出來是 0,`tenant` 仍照樣填),所以「第一列記的租戶跟寫入的廣告對不上」這個核對點永遠有值可比,不會因為 `tenant` 是空值而失去判斷力。設計增量 3 另加的「開始時已用額度」欄位(見 [S663])寫法與既有 `begin()` 裡本來就會算的 `used = aggregate_used(...)`(`attempt_store.py:351`)完全對得上,是同一個數字多存一次,可行。
- 核可使用表(`src/rtb/executor/inbox_store.py` 的 `approval_uses`)以 `(task_id, revision, content_hash, stage)` 為唯一鍵,`stage` 對應 `BlockCode.BUDGET_INCREASE_TOO_LARGE`(比例)與總曝險已滿兩種;追蹤 `execution.py:759-775` 的 `_audit()` 確認:比例那一關只要 `RATIO in live`(表示這次真的用到了一張此刻有效的核可)就會寫一列,總曝險那一關只在真的超過門檻又靠核可放行時才寫。核可使用紀錄「存在」等同「這一關真的被判定超過、而且有一張有效核可放行」,拿它當「有沒有核可紀錄」的核對依據是可行的,不會漏判也不會多判。
- 比例上限需要的「開始時目前預算」目前只活在處理一筆當下的記憶體變數(`view.budget`,由 `self.dsp.get_campaign` 之類即時讀出),不落地在任何資料庫欄位——這正是 F1 指出的缺口,程式裡確實找不到別的地方存了這個值。
- 別的寫入者的鍵怎麼認出來:`domain/attempt.py` 的 `operation_key()` 固定用 `KEY_PREFIX = "k1-"` 前綴加 sha256,執行端鍵的格式是「`k1-` + 64 個十六進位字元」,別的寫入者(不經過本系統)送出的冪等鍵不會湊巧符合這個格式(要湊巧撞上 sha256 值等於不可能),用格式比對篩「執行端鍵格式的」冪等鍵是可靠的,不會把別人的操作誤算進本系統的有效事件,也不會漏掉真正屬於本系統的操作(本系統每一次開始一筆都用這個函式算鍵,不會產生不符格式的鍵)。
- 冪等鍵對得上但嘗試在另一個資料庫、或同一份提案內容第二筆提交:追蹤 `operation_key()` 的組成欄位(`task_id, campaign_id, action_type, requested_change, campaign_version_observed`,不含 revision、不含內容雜湊本身)與 `begin()` 的邏輯(`key = operation_key(proposal); current = latest(tx, key); if current is not None: return Begun(current, created=False)`,`attempt_store.py:340-343`)可以確認:只要「同一份提案內容」的鍵沒變,重送會被 `begin()` 擋成「原樣回傳」,不會產生第二筆真正的 DSP 提交。真正會讓「同一份提案內容(任務、修訂、內容雜湊)」在 DSP 上出現兩筆提交的路徑,是鍵的計算結果變了但邏輯內容沒變——目前程式裡唯一會讓這件事發生的機制是 `KEY_PREFIX`(`"k1-"`,`attempt.py:16` 註解明寫「之後改算法換前綴,新舊鍵不會撞在一起」)版本升級後,對一份原本已經有舊鍵嘗試紀錄(可能已作廢/已失敗)的提案內容重新送出(例如 Phase 8 的死信重放,或分析端重新規劃出內容相同的提案):`begin()` 用新算法算出新鍵,`latest(tx, new_key)` 是 `None`,會建立一筆全新的嘗試、進而可能提交到 DSP,跟舊鍵底下(可能已作廢)的那筆是同一份提案內容的第二筆真實提交。這條路徑是真實存在、程式邏輯支持的,不是設計臆造的情境;「作廢後重送」單獨(鍵不變)不會發生第二筆提交,因為作廢過的鍵永遠被 `voided_keys` 擋住(`dsp/store.py:375-377`),必須合併「算法改版」才會真的落地成第二筆提交——設計文字把兩者並列為觸發條件,實際上是同一個機制的必要組合,不是兩條獨立成因,這點措辥可以更精確,但不影響核對函式的可行性(判斷邏輯只看「同一份提案內容有沒有第二筆以上的 DSP 提交」,不需要知道成因)。
- 兩個資料庫讀取不同步:F1/F2 討論的兩項核對(嘗試紀錄第一列存不存在、核可使用紀錄存不存在)在寫入順序上都保證先於 DSP 提交(`begin()` 與 `_audit()` 都在同一個交易裡,發生在真正呼叫 DSP 之前,見 `execution.py:671-698` 呼叫順序),所以核對函式即使兩個資料庫各自獨立查詢、時間點不完全對齊,也不會因為「DSP 已提交但執行端還沒寫完」而把正常寫入誤判成「找不到開始一筆」——這個方向的競態被既有的执行順序排除了;唯一要留意的是反過來讀(執行端顯示已提交但 DSP 查詢當下還沒讀到)理論上可能發生在核對函式對 DSP 分頁掃描期間有新提交進來,但這只會讓核對函式那一輪少看到最新幾筆(下一輪窗會補上),不會產生假的違規判定。
