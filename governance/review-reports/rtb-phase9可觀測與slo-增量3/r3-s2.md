severity: major

我這一鏡負責的是兩條「目標為零」副作用指標(未授權或違反護欄的副作用率、重複有害副作用率)端到端走一遍:DSP 依時間找起點 → 翻頁 → 執行端批量查第一列與核可使用 → 逐項核對 → 判好/壞/無法核對 → 週期違規狀態。逐步對照 `src/rtb/dsp/store.py`、`src/rtb/dsp/server.py`、`src/rtb/dsp/capability.py`、`src/rtb/executor/attempt_store.py`、`src/rtb/executor/inbox_store.py`、`src/rtb/executor/execution.py`、`src/rtb/domain/attempt.py` 之後,大部分資料真的在、也真的核對得出來(見文末「確認沒問題」段落),但找到兩個字面實作會做錯的洞、一個沒寫進實務隱患的成本缺口。

## F1 減預算會被誤判(或被永遠排除)成無法核對:排除清單漏了「減預算」

severity: major
blocking: 是 — 照字面實作,合法的減預算寫入會被判成違反總曝險護欄的壞事件,或被永遠歸類為無法核對而退出有效事件分母;兩種結果都是把正常寫入判錯。

引句:「排除:暫停(不加預算,只核對有沒有經過開始一筆)。」

「未授權或違反護欄的副作用率」的壞事件判法裡有一條:「第一列記下的開始時已用額度加這一筆超過第一列記下的總額上限,而沒有總曝險那一關的核可使用紀錄。剛好等於門檻算合法。」這條的字面寫法沒有排除「這一筆」等於 0 的情形,只有暫停被明文排除,減預算沒有被提到。

程式裡「加的量」(這一筆佔的總曝險)是 `guardrails.increase`:

```
def increase(proposal: Proposal, budget: int) -> int:
    """這筆提案加的量(也是它佔的總曝險):新預算減目前預算,小於 0 算 0;暫停是 0。"""
    if proposal.action_type is not ActionType.UPDATE_BUDGET:
        return 0
    return max(0, int(proposal.requested_change["new_budget"]) - budget)
```
(`src/rtb/executor/guardrails.py:21-25`)

暫停與減預算兩者的 `increase()` 結果都是 0,`attempt_store.begin()` 用的正是同一個 `reservation.amount`:

```
    over_limit = None
    if reservation is not None and reservation.amount > 0:
        used = aggregate_used(tx, reservation.tenant, now)
        if used + reservation.amount > reservation.limit:
            over_limit = AggregateLimitReached(used, reservation.limit)
            if not reservation.approved:
                raise over_limit
```
(`src/rtb/executor/attempt_store.py:349-355`)

也就是說,系統真正的護欄本來就是「金額大於 0 才檢查總曝險」,暫停與減預算在這一點上完全同等待遇 —— 兩者都從來沒有被拿去跟總曝險門檻比較過,也都不會產生核可使用紀錄(`_audit` 只在 `begun.over_limit is not None` 時才記,見 `src/rtb/executor/execution.py:770-773`)。

增量 3 的稽核卻只把「暫停」寫進排除清單。落到實作有兩種走法,結果都錯:
- 若第一列的「已用額度」欄照這一段字面(「依處理一筆開頭讀到的目前預算與當時的比例常數算出」「已用額度(判門檻用的那個數)」)不分動作類型一律寫下實際值,減預算寫入的 `used_at_start` 就會是真值。之後只要租戶當時剛好因為別的加預算逼近或超過總曝險門檻(不論有沒有核可),核對函式就會用「已用額度(0 加這一筆) 超過上限,而沒有核可使用紀錄」判這筆完全沒有加任何額度的減預算為壞事件——這是把一筆從沒被系統自己的護欄評估過的寫入,事後扣上「違反護欄」的帽子。
- 若照現有程式碼的既有寫法(只有 `amount > 0` 才算 `used`),減預算的第一列這個欄位會是空值,核對函式就會把每一筆減預算都判成「無法核對」,而不是好事件——同樣不對:減預算完全合法、可核對(沒有加任何額度),不應該被排除在有效事件分母外。

兩條路都會讓「減預算」這一類完全正常的寫入,在這條目標為零的指標上被系統性地誤判,不是單筆意外。排除清單應該跟「暫停」一樣明寫「減預算」(即 `guardrails.increase(...) == 0` 的 update_budget 寫入),只核對有沒有經過開始一筆、動作與新預算是否跟第一列相符,不進總曝險/比例檢查。

## F2 DSP「依時間找起點」端點沒定邊界,恰好卡在窗口起點的操作可能永遠掉出所有窗口

severity: major
blocking: 是 — 若這個端點對「之後」採嚴格大於(而不是照增量 2 既有的窗口慣例用「大於等於」),一筆 `committed_at` 剛好等於某個窗口起點的操作,會被這個窗口排除;如果它同時也是前一個窗口的結束邊界(慣例是 `[起, 迄)`,結束是排除的),就會兩邊都不算,永久性地從燒損評估與副作用核對的樣本裡消失。

引句:「某時間之後第一筆提交的操作編號」:路徑參數是時間,回一個操作編號(沒有就回空);用提交時間索引查。

這一句沒有講「之後」是 `>` 還是 `>=`。同一份設計在別的窗口查法上明確用的是起點含、迄點不含:

引句:窗 [起, 迄) 的候選是「第一次進結果不明」落在 [起 − 10 分鐘, 迄) 的鍵,用嘗試紀錄「進結果不明」的時間索引找

`src/rtb/executor/attempt_store.py` 裡既有的窗口查詢也是這個慣例,起點用 `>=`:
```
    part = (f"SELECT {_first_row_columns('f')} FROM attempts f WHERE f.seq = 1 AND {{}} "
            "AND f.written_at >= ? AND f.written_at < ?")
```
(`src/rtb/executor/attempt_store.py:451-452`)

但增量 3 給 DSP 新端點的描述是自然語言「某時間之後」,中文字面讀起來是嚴格大於,跟前面 `[起, 迄)` 的慣例(起點含)不一致。DSP 這一側「依提交時間找操作」是 `ORDER BY committed_at LIMIT 1` 這種單筆查詢,不是像其他窗口查詢那樣用範圍條件把整段一次撈出來,所以邊界怎麼定義會直接決定「起點那一刻剛好提交的操作」算不算進這個窗。若照字面實作成 `WHERE committed_at > ?`,一筆操作的 `committed_at` 恰好等於窗口起點時,會被這個端點排除;而它作為前一個窗口的結束時間(`< 迄`,不含)本來就已經被排除。兩頭都被排除,這筆操作在燒損評估器逐段查詢(週期切成不超過 24 小時的子窗相加)裡永遠不會被算到——不是單一窗口漏算之後補在另一個窗口,是徹底消失,直接影響「未授權或違反護欄的副作用率」與「重複有害副作用率」的有效事件分母與壞事件分子。

DSP 的 `committed_at` 用 `datetime.now(UTC).isoformat()` 取得(`src/rtb/dsp/store.py:65-66`、`src/rtb/dsp/store.py:382`),而寫入交易用 `begin_immediate` 全域序列化(`src/rtb/dsp/store.py:345-349`),所以操作編號遞增順序跟提交時間遞增順序一致這件事本身沒問題;缺的是「起點」端點的邊界要跟既有窗口慣例(起點含)對齊,並在文字裡明寫,不要留給實作者猜。

## 次要:重複有害副作用率的「往回查」沒有配索引,跟同一份設計裡其他類似查詢的做法不一致

severity: minor
blocking: 否 — 不會讓結果算錯,但沒有寫清楚成本、也沒有像其他類似查詢一樣配上索引或界定候選數上界,跟這份設計一貫「每一個窗口查詢都要配時間索引、工作量要有界」的做法不一致,值得補。

引句:另外核對「同一把冪等鍵對應到兩筆以上 DSP 操作」:DSP 的冪等鍵有唯一限制,正常路徑不會發生,是防禦性核對

「重複有害副作用率」的主判法是「用冪等鍵找第一列、再用提案內容往回查,不限窗」(同一段前文)。這個「往回查」要用第一列的(任務、修訂、內容雜湊)去找是否有別的鍵也對到同一份內容——但 `attempts` 表現有索引只有 `campaign_id`(`attempts_first_rows`、`attempts_terminal_rows`、`attempts_one_terminal_per_key`)與 `(tenant, written_at)`(`attempts_first_rows_by_tenant`),沒有任何按 `task_id`/`revision` 建的索引(`src/rtb/executor/attempt_store.py:53-74`)。因為 `operation_key` 的推導不含修訂序號(`src/rtb/domain/attempt.py:20-34`),同一份內容正常只會對到一把鍵,這個往回查詢在絕大多數呼叫裡注定找不到東西,但要「確認找不到」仍得掃描,沒有索引就沒有界。同一份設計在增量 1 特別為「找某份提案最後一個終點事件」加了專用的終點部分索引 [S626] 並要求測試斷言查詢計畫用到它;這裡對稱的往回查卻沒有配索引,也沒有寫進「實務隱患」段落(該段落已經對其他幾條窗口查詢的成本一一寫了 REVISIT,唯獨漏了這一條)。實作時應補一個以(任務、修訂)開頭、只收第一列的索引,或至少把成本寫進實務隱患。

## 確認沒問題的觀察

- 對帳同鍵重送:DSP `execute()` 靠 `idempotency_keys` 的唯一鍵去重,同鍵重送只回既有那一列(`_existing_operation`,`src/rtb/dsp/store.py:391-399`),`operations` 表永遠只有一列;重複有害副作用率不會把同鍵重送誤判成第二筆。
- 作廢後的鍵:作廢只寫進 `voided_keys` 表,不產生任何 `operations` 列(`src/rtb/dsp/store.py:351-367`);「窗內 DSP 提交的寫入」這個母體天然就不含被作廢的鍵,不會被誤判。
- 核可放行的寫入:比例與總曝險的核可使用紀錄各自只在真的超過門檻、而且核可有效放行時才寫(`src/rtb/executor/execution.py:764-775`),`approval_uses` 表本身就帶冪等鍵欄(`key TEXT NOT NULL`,`src/rtb/executor/inbox_store.py:185-190`),批量依冪等鍵查核可使用紀錄的規劃可行。
- 讀取順序(先讀 DSP、再開執行端快照):執行端在呼叫 DSP 之前已經在 `_take` 裡完成 `attempt_store.begin`(寫入第一列)並提交交易,`dsp.write` 是在那之後才呼叫(`src/rtb/executor/execution.py:432-436`),所以「DSP 看得到的每一筆執行端寫入,之後開的執行端快照一定看得到它的第一列」這個論證在程式裡站得住。
- 授權範圍核對用得到的欄位都真的在:DSP `operations` 表存了 `campaign_id`、`action`、`params_json`(含新預算)、`expected_version`、`policy_version`(`src/rtb/dsp/store.py:38-42`);執行端第一列存了 `campaign_id`、`action`、`expected_version`、完整 `proposal_json`(含 `policy_version`,見 `src/rtb/domain/proposal.py:58`),逐項比對可行。DSP 不記租戶這件事,設計文字已經照實寫「這裡核對不到」,跟程式一致。
- 同一把鍵被多份修訂共用:`operation_key` 不含修訂序號,`begin()` 鍵已存在時直接回既有第一列、不覆寫(`src/rtb/executor/attempt_store.py:341-343`),所以「內容」判斷用的是建立那把鍵的原始修訂,後續修訂共用同一把鍵不會產生第二筆 DSP 操作,不會被誤判成重複。
- 別的寫入者的鍵:執行端鍵一律帶 `k1-` 前綴(`src/rtb/domain/attempt.py:16`),用字首篩選就能把非本系統寫入者排除在有效事件外,跟設計文字一致。

以上兩點(F1、F2)跟我分派到的例子清單直接對上:F1 命中「減預算」,F2 命中「提交時間相同的兩筆」(窗口邊界上的一筆等同於兩個相鄰窗口在同一時刻各自處理一次,邊界定義不一致時等於漏算)。
