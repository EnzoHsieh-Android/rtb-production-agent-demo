本輪只判增量 3 第 2 輪折入之後(第 3 版)跟既有模組邊界/做法是否一致,範圍限定:DSP 兩支新唯讀端點、擁有模組的新批量讀取函式、第一列多記「比例允許加的量」、設定表。逐項核對如下,沒有找到「引入第二種做法」或「跨層直呼」等級的問題,故整篇 clean。

DSP 兩支新端點的路徑形狀跟現有路由一致。現有 `ROUTES` 全部是「GET/POST + 恰好一個路徑捕獲群組」的形狀(`/campaigns/([^/]+)$`、`/campaigns/([^/]+)/history$`、`/operations/([^/]+)$` 等,見 `src/rtb/dsp/server.py:80-88`),回應一律是 `asdict(...)` 或帶固定 key 的字典包列表(如 `_get_history` 回 `{"history": [...]}`,`src/rtb/dsp/server.py:132-136`)。快照第 3 版(r3-snapshot 274-278 行)把兩支端點都寫成「路徑參數恰好一個」(依時間找第一筆操作編號、依操作編號翻頁列操作),跟既有形狀相同,是同一種路由分派方式的延伸,不是第二種;分頁用路徑參數而不是查詢字串(既有 `_get_metrics` 用查詢字串 `?window=`,`src/rtb/dsp/server.py:141`),兩者共存不衝突,因為路由比對只看路徑、不看查詢字串。回應要帶的欄位(操作編號、冪等鍵、廣告、動作、新預算、預期版本、提交時間、政策版本)跟現有 `OperationResult`/`Operation` 已有的欄位完全對得上(`src/rtb/dsp/store.py:78-102`),不需要另建一套資料結構。新索引「操作表以提交時間開頭建索引」是加索引,不改既有查詢路徑,跟 `attempt_store.py` 既有的「先建表後補索引」慣例(`TENANT_INDEX` 常數,`src/rtb/executor/attempt_store.py:72-74`)同一種做法。

擁有模組的新批量讀取函式跟既有讀取函式的簽名與交易守衛一致。`attempt_store.py` 現有讀取函式(`latest`、`history`、`unresolved_keys`、`campaigns_with_unresolved`、`aggregate_holdings` 等,見 `src/rtb/executor/attempt_store.py:239-319,386-415`)一律第一參數是 `tx: ExecutorTransaction`、內部用模組級 `_conn(tx)` 做型別與開啟狀態守衛;快照第 3 版(279 行)要新增的「依一批冪等鍵回各自的第一列」只是同一種函式多一個「一批鍵」的輸入,跟既有 `aggregate_holdings`/`counted_first_rows_started` 一次查一批鍵、一次回一批結果的做法(同檔 386-472 行)同構,而且快照已明寫「每批不超過 SQLite 參數上限,不逐筆查」,跟該檔既有對「大量列逐鍵查詢會佔用寫入鎖時間」的顧慮(同檔 397-398、413-414 行註解)一致,不是另開一條查詢路徑。`inbox_store.py` 這邊要加的「依一批冪等鍵回核可使用紀錄」屬於 `InboxStore` 的方法,現有同類讀取方法(`stop_amount`、`latest_approval`、`awaiting`、`has_newer_revision`)一律用 `self._own(tx)` 守衛而不是 `attempt_store._conn`(因為 `InboxStore` 綁自己的連線,`src/rtb/executor/inbox_store.py:613-616,944-953`),快照沒有另外要求换一種守衛方式,延用 `self._own(tx)` 即符合現有邊界。兩支新函式各自留在自己模組(嘗試紀錄留 `attempt_store`,核可使用紀錄留 `inbox_store`),沒有出現維運套件跨層直接拼 SQL 或繞過擁有模組直讀資料表的寫法;快照 279 行本身也是這樣寫的理由。

第一列記「比例允許加的量」跟 `guardrails.py`、開始一筆的現有計算路徑相容,沒有另開一條算法。`guardrails.increase_too_large(proposal, budget)`(`src/rtb/executor/guardrails.py:29-32`)內部算的 `allowed = max(budget * MAX_INCREASE_NUMERATOR // MAX_INCREASE_DENOMINATOR, MIN_INCREASE_STEP)` 只用得到 `budget`(即 `process_one` 開頭讀到的 `view.budget`,`src/rtb/executor/execution.py:427`)一個輸入,是純函式,快照的「依處理一筆開頭讀到的目前預算與當時的比例常數算出」跟這個函式的輸入完全對得上,不需要另外接資料庫或呼叫 DSP。要注意的是現有呼叫鏈 `process_one` → `_gate`(算 `increase_too_large` 判斷用不用等核可)→ `_take`(呼叫 `attempt_store.begin` 寫第一列)這三層之間,目前只有 `amount`(`guardrails.increase` 的結果)被當參數往下傳(`execution.py:427-432`),`view.budget` 本身與 `guardrails.increase_too_large` 算出的 `allowed` 都沒有被傳到 `_take`/`begin`。要把「比例允許加的量」跟判比例用的是同一個數(`[S652]`「判法應只用寫入當時記下的資料」、`[S663]`「跟這一筆判比例與門檻用的是同樣的數」)落地,做法必須是照現有 `amount` 的路子——在 `process_one`/`_gate` 算好後,多一個參數跟著 `amount`、`held` 一起傳進 `_take`,再放進 `attempt_store.Reservation`(現有的 `Reservation` 已是「预算算好後打包傳進 `begin`」的容器,`src/rtb/executor/attempt_store.py:102-113`,`execution.py:675-681`)多帶三個欄位(比例允許量、單一廣告上限、總額上限;總額上限其實就是現有 `reservation.limit`/`signed.tenant.aggregate_limit`,已經在流程裡,不算新增)。這是延用既有「算好的數當參數往下傳、寫進 `Reservation`」的唯一路子,不是重新讀一次現況或另開一條計算路徑;快照本身也點名「比例需要的開始時預算原本只在記憶體裡」(r3-snapshot 272 行)並選擇存算出的量而非常數,跟這條唯一可用路子相符,沒有出現第二種做法。

設定表跟現有「用程式常數表示結構化表格」的慣例一致。快照(289 行)明寫「程式常數,測試從表讀,不在各處各寫一份」,不是真的資料庫表;`src/rtb/dsp/server.py` 已有同構的先例——`ERROR_TABLE`(80-91 行)就是一份「每一種例外類型對應一組固定欄位(狀態碼、代碼、可否重試)」的程式常數表,查表方式(逐項屬性、供多處引用而不各寫一份)跟服務水準設定表要做的事相同,所以這是延用既有慣例,不是引入新的組態承載方式。

综上,本輪鏡頭關注的四個對照點(DSP 端點形狀、批量讀取函式、比例允許量、設定表)都是既有做法的直接延伸,沒有發現需要擋推送的架構落差。
