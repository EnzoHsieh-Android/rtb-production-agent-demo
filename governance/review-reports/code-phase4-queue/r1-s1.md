`execution.py` 的 `_ack_terminal`(以及 `inbox_store.py` 的 `_settle_existing`、`execution.py` 的 `_take` 內兩處直接呼叫)呼叫 `ack_handed_off`/`ack_blocked` 都不檢查回傳的布林值——這兩個方法其實是「帶收據的條件寫入」,更新 0 列就代表收據失效、確認沒寫進去。同一支檔案裡 `_settle()` 與 `_release()` 對同一類條件寫入的回傳值都有檢查,失敗會回報 `Result.LEASE_LOST` 讓呼叫端知道這把鍵這一輪要放棄(S116 的精神);但 `_ack_terminal`、`_settle_existing`、`_take` 的終點確認分支沒有這道檢查,一旦條件寫入意外落空,呼叫端會誤以為「已交給執行/已擋下」確實寫進收件表了,實際上那一列可能仍停在處理中或已被別人接手,而且不會有任何錯誤或訊息浮現。
