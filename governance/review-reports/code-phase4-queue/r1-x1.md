### 1. 壞掉的處理中 payload 會繞過租約 fencing

severity: major  
blocking: 是 會讓未持有租約的對帳工作者寫入嘗試紀錄，直接破壞 S101/S116 的租約合約  
引句:「message = self.store.in_progress_for(tx, proposal.task_id, key) receipt = None if message is not None」

`in_progress_for()` 把「完全沒有處理中訊息」與「訊息存在，但 payload 無法解析」都回成 `None`；對帳因此把後者誤認為 Phase 3 舊資料，讓後續 `_write()`、`_verification_timeout()` 全部以 `receipt=None` 繞過租約檢查。

具體實驗：

- 輸入：一筆 `unknown` 嘗試；對應訊息仍是 `in_progress`，租約屬於 `w1`、尚未到期；只把收件列的 `payload` 改成無法解析的 `{`；接著由 `w2` 執行對帳。
- 預期：`w2` 找不到合法收據，應跳過該鍵，嘗試維持 `unknown/seq=2`。
- 實際：`w2` 取得 `receipt=None` 後照 legacy 路徑寫入，嘗試變成 `failed/seq=3`，即使資料庫裡仍有 `w1` 的有效租約。
- 實驗輸出：`before=unknown 2`、租約 `('in_progress', 'w1', 1, '2026-09-22T12:06:00.000000Z')`、`after=failed 3`。

這裡應區分「查無處理中列」與「有列但讀不回來」；後者至少必須停下或跳過，不能開啟 `receipt=None` 的相容旁路。現有 S101/S116 測試只覆蓋可正常解析的訊息，因此抓不到這條旁路。
