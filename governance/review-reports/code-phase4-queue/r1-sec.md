查了 `src/rtb/executor/inbox_store.py`(`receive`/`_lease`/`_held`/`_finish`/`extend`/`release`/`take_over`/`in_progress_for`/`_purge_finished_tasks`)、`execution.py`(`process_one`/`_process`/`_take`/`_write`/`_reconcile`/`reconcile_all`)、`attempt_store.py`(`begin`/`transition`/`campaigns_with_unresolved`/`unresolved_keys`)、`inbox_server.py`(`_accepted_body`)、`runner.py`(`_loop`/`owner` 產生)六支檔在 Phase4 增量1 後的完整邏輯,並對照 `RTB_Agent_Phase0架構.md` 的 lease fencing 裁定與 `RTB_Phase4佇列與重新投遞_計劃.md` 的 S95–S117 合約逐條核對,鎖定「分析行程只能透過收件口 HTTP 送不可信提案內容」這個攻擊面,分別驗證以下六點:

- **重複寫入 DSP**:`attempt_store.begin()` 是「有就回既有列、沒有才插入」的冪等操作,`_take()` 只在 `begun.created` 為真時才會往下呼叫 `dsp.write(...)`;既有鍵一律走 `ack_handed_off`/`ack_blocked`/`release` 分流,不重送。`process_one()` 是收件→處理一筆的同步直線流程,`_loop()` 每輪先 `reconcile_all()` 再 `process_one()`,單一執行者下沒有任何並發路徑,所以 `receive()` 與 `_take()`/`_reconcile()` 之間不存在能讓同一把鍵被兩條路徑同時開始嘗試的視窗。刻意檢查過「新修訂不取代 in_progress 舊修訂」這個第 4 版設計裡承認的落差([S108] 的取代機制)——它只讓同一任務最多多出一列 pending(下一個修訂送達時會把它取代掉,不會無限堆積),且新修訂真正被取件時一定會先讀到既有嘗試紀錄再分流,不會重送 DSP;測試 `test_a_proposal_superseded_before_taking_is_never_executed`、`test_a_lost_lease_skips_the_key_without_halting` 已覆蓋這條路徑。
- **訊息永遠卡住**:`receive()` 用 `campaigns_with_unresolved` 在同一交易內排除鎖住的廣告、`_held`/`_finish` 的收據條件寫入涵蓋過期收據與換人接手兩種情況,任何一項不符只會 0 列放棄(`Result.LEASE_LOST`/`DEFERRED`),不會讓收件表卡在無法再被取件的中間態;死信只打到「從沒開始過嘗試」的提案(`existing is not None` 一律先分流,不會跟死信檢查搶跑),已核對的收件表列因 `IN_PROGRESS`/`PENDING` 判斷互斥而不會漏轉。轉人工(ESCALATED)任務會被無限期續租、長期占用收件表總列數上限,但這是計劃「不做的事」段落已明寫且附 REVISIT 的既知限制,不是這批改動新引入的漏洞。
- **死信/保留期清除吃掉真實操作紀錄**:`attempts` 表本來就是只增不改(檔案開頭註解),`_purge_finished_tasks` 與 DLQ 邏輯自始至終只碰 `proposals` 表,從未 UPDATE/DELETE `attempts`;而且死信只會打到「沒有任何嘗試紀錄」的鍵,一旦 `begin()` 開過嘗試,`campaigns_with_unresolved` 就會把同廣告鎖住、收件也一律先讀嘗試紀錄再分流,不會出現「已有真實操作卻被死信或清除」的情況。
- **執行迴圈停機**:`_loop()` 只捕捉 `ExecutorHalted`/`InboxBusy`,理論上 `HistoryFull` 等其他 `AttemptRejected` 子類別未被捕捉,但沿 `MAX_SENDS`(3)、`MAX_VERIFICATION_TIMEOUTS`(5)與「進 ESCALATED 後 reconcile 直接 return False、不再寫入」的路徑回推,單一執行者下這些子類別在沒有真實行程重複當機的情況下無法被自動觸發到 50 列上限;而且不論哪種例外,交易層 `transaction()`「任何例外都回滾」保證不會留下半寫入的髒狀態,跟文件化的 `ExecutorHalted` 停機在資料完整性上沒有差別,不構成攻擊者可利用的新增面。
