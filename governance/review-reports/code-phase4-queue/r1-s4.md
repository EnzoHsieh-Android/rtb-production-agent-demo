## 預期值來源

多數關鍵斷言用程式自己的表/常數產生預期值,不是手抄字串:例如 `until == inbox_store._iso(h.clock() + VISIBILITY_TIMEOUT)`、`LEASE = VISIBILITY_TIMEOUT.total_seconds()`、`MAX_DELIVERIES` 直接從 `inbox_store` 匯入、`DISPOSITION_TRIGGERS`/`DEAD_LETTER_TRIGGERS`/`FAILURE_TRIGGERS` 都用 `assert set(...) == set(Enum)` 從程式的封閉列舉逐一核對(新增成員沒補觸發就紅)。少數手打的絕對值(如 S95 遷移測試的 `_proposal_rows(db) == [("t-old", 1, "handed_off", 0, 0), ...]`)屬於「驗證資料搬遷結果」這種本來就該用字面值釘住的場景,不算風險。

### 1. 兩段遷移相容性子驗證埋在同一支測試函式裡,不是獨立 pytest 案例
severity: minor
blocking: 否 —— 不影響測試是否守得住合約,純粹是失敗時的可追溯性問題
引句:「_migration_race_rebuilds_once(tmp_path, monkeypatch)」

`test_an_old_inbox_database_migrates_to_four_dispositions_without_losing_data` 在自己的函式體最後直接呼叫 `_migration_race_rebuilds_once(tmp_path, monkeypatch)` 與 `_only_the_old_constraint_also_triggers_a_rebuild(tmp_path)`(`tests/executor/test_queue.py` 第 573、574 行附近),這兩段其實各自覆蓋一個獨立情境(並行遷移只重建一次;只有資料庫層限制過期、欄位都在的情況也會觸發重建)。它們確實會執行、確實會在斷言失敗時拋錯,不是假綠——已用「拿掉 `lease_owner = ?` 清空」等變異間接證實這條路徑真的會被跑到。但因為沒有各自獨立成 `def test_...`,pytest 報告與 `-k` 過濾都看不到這兩個情境的名字,失敗時只會顯示成 `test_an_old_inbox_database_migrates_to_four_dispositions_without_losing_data` 這一個 ID,較難一眼看出是哪個子情境壞掉。建議之後拆成獨立測試函式或至少用 `pytest.mark.parametrize`/`subtests` 讓失敗定位更快,不需要現在補。
