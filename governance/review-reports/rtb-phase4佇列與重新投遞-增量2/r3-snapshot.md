# RTB_Phase4佇列與重新投遞_計劃

PRIOR-ART: 這是「至少送一次的佇列 + 可見性逾時 + 確認 + 死信」的標準解(SQS、RabbitMQ、Kafka 的消費者提交都是同一組概念),配上「確認要晚於持久結果」這條老規則。最小解在本專案既有的層就做得到:收件表本身就是一張有狀態的表,加租約欄位與投遞次數就是佇列;不引入外部佇列軟體(零依賴家規),也不自造訊息格式。採用:借用概念,在既有收件表上長出佇列語意。
RETIRE-IF: 若之後換成真的外部佇列(SQS 之類),這層的可見性逾時、投遞次數與死信改由它負責,本專案只留「確認晚於持久結果」與「重新投遞先讀持久狀態」兩條規則。

## 這份計劃在解決什麼

- 事故 F2(交接文件第 16 節):外部寫入與本地持久結果都已完成,工作者卻在送出確認之前當機。佇列沒收到確認就會重新投遞;處理錯的後果是同一筆預算被改兩次。
- 事故 F3:同一則訊息被投遞兩次以上(不同工作者、不同嘗試)。任務識別要穩定、狀態轉換要合法、重複投遞不能重複花分析的錢,也不能繞過執行閘。
- 範圍:交接文件 Phase 4「Queue、Redelivery 與 Checkpoint」。樂觀鎖與並行寫入是 Phase 5;權限、護欄與總曝險是 Phase 6;提示注入是 Phase 7。
- 驗收(交接文件 Phase 4 完成條件):F2、F3 通過(F3 的「不重複分析費用」由增量 3 補上,F3 整條在增量 3 完成後才轉正,見增量 2 的「F3 轉正的範圍與缺口」);當機點至少涵蓋外部寫入前、DSP 提交後但本地寫入前、持久結果已寫但確認前;重新投遞由持久事實恢復,不靠行程記憶;確認時機有測試與設計說明;佇列重試不造成重複的有害副作用。
- 已登記的預告合約 [[Verification/2026-09-22_事故-F2-工作者在副作用與持久結果都已完成-但送出確認前當機時-重新投遞後新的]] 與 [[Verification/2026-09-22_事故-F3-同一則訊息被投遞兩次以上時-任務識別維持不變-狀態轉換合法-重複投遞]](都最遲 2026-11-30)是這個階段要轉正的合約。

## 使用者情境題(2026-09-23)

- 題目:一則任務訊息被取出,工作者改了 DSP 的預算、成功了,也把結果寫進本地資料庫;正要送出確認時當機。佇列重新投遞,新的工作者拿到它。該怎麼做?a 重跑整個流程;b 先看本地持久狀態,已有結果就直接確認、不碰 DSP;c 先送確認再處理;d 一律用冪等鍵向 DSP 查證後再決定。
- 使用者答 d。回饋:抓到最重要的一點——不能用「訊息又來了」當成「還沒做」。但每次重新投遞都去問 DSP,是把本地已經確定的事也交給網路重問。正確順序是 b 打底、d 補充:**本地持久狀態是第一順位**(嘗試紀錄與結果在同一個交易裡寫下,終點狀態本地說了算),只有本地停在未結案時才走 Phase 3 的對帳去問 DSP。這也省下重複的分析費用(事故 F3 明講)。
- 這一題順帶帶出 Phase 4 真正的判斷點:**什麼時候送確認**。太早(選項 c)等於承認了沒做完的事,當機就沒人重做;太晚則會重複投遞。

## 三個增量(2026-09-23 使用者同意這個排法)

- 增量 1:佇列語意與確認規則。收件表長出租約(可見性逾時)、投遞次數與死信;取件不再等於確認,確認只在「這個邏輯操作有終點或提案被擋下」時才寫。
- 增量 2:重新投遞恢復與事故 F2、F3 端到端。重新投遞先讀持久狀態判定;三個當機點各一個測試。
- 增量 3:多工作者的租約與圍籬。同一則訊息被兩個工作者處理時,只有租約還有效的那個能寫;過期租約的寫入要被擋下,取代 Phase 3 的單一執行者鎖。另外補**分析側去重**:同一個任務的分析同一時間只有一個在跑(分析行程的租約或冪等),重複投遞不重複花分析的錢(2026-09-23 使用者決定排進這個增量)。

## 增量 1 設計:佇列語意與確認規則(2026-09-23,第 4 版:已折入第 1 到 3 輪設計審)

- 事故:取件就當成確認,當機在「取件之後、寫入之前」那一段,訊息再也不會被重投,提案默默消失;反過來,確認寫在持久結果之前,當機就會讓已經做完的事被重做一次。
- **第 1 版被推翻**:處置整個延後、提案留在待處理,會被到期標記與取代改壞、確認寫不進去(第 1 輪)。第 2 版改成取件當下寫「處理中」。
- **第 2 版被補強的地方**(第 2 輪 22 條,3 條 blocker):租約用投遞次數充當擋不住過期工作者,也沒管到嘗試紀錄的寫入,跟 Phase 0 已定的 lease 規則不一致;轉人工、人工處置、保留期清除三條路沒有程式接得上;既有的標過期、標擋下、清除動作還用「是否待處理」判斷,新流程下全部失效;死信原因與失敗脈絡的型別沒定義。
- **第 3 版補的接縫**(第 3 輪 9 條):取件的終點快路徑拿不到收據;接手後遇到嘗試中沒有出路;回退沒先排空處理中;取件要經嘗試紀錄模組的函式;被取代清單漏了讀 DSP 失敗與全表已滿兩條;收據對不上會落進既有的停機路徑。
- **照 Phase 0 的裁定走**:[[Projects/RTB_Agent_Phase0架構]] 早已寫明「lease 是到期時間加序號,同一把 lease 同時管訊息與嘗試中紀錄;寫結果與 ACK 一律以條件更新進行,條件含 key、owner 與 lease 序號,更新到 0 列就放棄並進入對帳;結果不明的操作不計入重試上限、不得直接進 DLQ」。第 2 版把這些簡化掉了,這一版補回來。
- 範圍:收件表的佇列語意(租約、投遞次數、死信)、處理一筆與對帳寫處置的時機、取件後先讀持久狀態的分流、嘗試寫入受同一把租約管。不動 DSP 回應判定表與對帳對 DSP 的判定邏輯;增量 2 做三個當機點的端到端;增量 3 做多工作者。
- **狀態(2026-09-23):已完成**。S95–S117 全部綁了會真跑的測試;設計審 3 輪、代碼審 3 輪(5、4、1 條全部折入,每條修正都做了變異檢查)。代碼審額外補上:處理中那一列讀不回來時不能當成沒有(先掃完、找不到才停,對帳先處理完健康的鍵再停)、確認寫入的回傳值要檢查(寫不進去就是失去租約)、啟動時資料庫忙碌要乾淨結束並放掉鎖、同一把鍵兩張收據靠開始一筆擋住的測試。卷證在 governance/review-reports/code-phase4-queue/。

### 處置從兩態變四態

- 處置列舉從兩個成員(已交給執行、已擋下)變成四個,多**處理中**與**死信**。
  - 處理中:取件當下寫,代表「這則訊息已經交出去,租約還在」。它不是待處理,也不是確認。
  - 死信:沒有任何嘗試紀錄、而投遞次數用完,不再交出去。
- 「已過期」維持是狀態、不是處置。處理中的提案被判已過期時,狀態改成已過期、處置清空、租約清空,從此不可取件。
- 處置欄位的資料庫層限制(CHECK 約束)只認兩個舊成員,加欄位改不了它。遷移照 SQLite 官方的重建表步驟(建新表、抄資料、換名),在同一個立即取得寫入鎖的交易裡做,拿到鎖後再查一次。這段只寫在收件表模組裡,不放進共用資料庫工具:專案裡只有這一處需要(第 2 輪相容席在暫存目錄實驗過:兩條連線同時開只重建一次;提交前被強制殺掉會整段回滾;這張表除了主鍵沒有別的索引或觸發器要重建)。

### 租約(照 Phase 0 的 lease)

- 收件表加四欄:**租約到期時間**、**租約序號**、**租約擁有者**、**投遞次數**。
  - 租約序號:每次取件或接手加 1,是「這一次交付」的身分。投遞次數只算真正交出去給處理一筆的次數,兩者分開(外家席指出拿投遞次數充當序號,租約過期但還沒人重新取件時,舊工作者仍能續租或確認)。
  - 租約擁有者:誰持有。增量 1 是單一執行者,擁有者就是執行迴圈這個行程的識別(行程編號加啟動時間);增量 3 換成每個工作者自己的識別。
- **收據**:取件或接手時回傳(任務編號、修訂序號、內容雜湊、租約擁有者、租約序號)。
- **所有帶收據的寫入**(延長租約、確認、以及下面講的嘗試寫入)的條件都是:處置是處理中、租約序號與擁有者等於收據、租約還沒到期。任何一項不符就更新 0 列,呼叫端放棄這次寫入(對帳會接手)。租約已過期的工作者不能續命,要重新取件、拿新序號(外家席與並行席指出)。
- **收據對不上是「放棄」,不是「停機」**:Phase 3 的寫結果與查證逾時遇到「沒有進展」一律停機,那是給「嘗試紀錄自己的序號被別人改過」用的(單一執行者下不該發生)。收據對不上在多工作者下是正常的租約競爭,所以另開一個結果:這把鍵這一輪放棄、跳過,執行迴圈繼續處理其他鍵;只有嘗試紀錄的序號對不上才照舊停機(第 3 輪租約席指出兩者要分開)。
- 單一執行者下,擁有者永遠是自己,所以對帳的原子接手條件恆成立,等於每輪無條件續租——這就是 Phase 0 要的續期機制(第 3 輪租約席指出這步推理沒寫出來)。
- **嘗試寫入也受同一把租約管**:處理一筆與對帳對嘗試紀錄做的每一個轉換(開始一筆、寫結果、查證逾時、重送),都在同一個交易裡先核對收件表那一列的收據仍有效,再寫嘗試紀錄;核對不過就不寫。兩張表在同一個資料庫檔,核對與寫入是同一個交易,不需要把租約欄位複製到嘗試紀錄。這樣過期的工作者醒來後不能把嘗試寫成已驗證(外家席指出第 2 版只保護收件表)。
- 可見性逾時暫用 60 秒,沒有實測校準。一輪處理最慢是幾次 DSP 呼叫(用戶端逾時暫用 5 秒)加本地寫入;對帳每輪會替仍在處理的訊息續租,所以慢的對帳不會讓活著的訊息過期。

### 取件

- **取件(receive)** 在一個交易裡做完(拿到寫入鎖之後才讀時鐘,比照既有的收件)。查嘗試紀錄一律經嘗試紀錄模組的既有函式(未結案計數、最新一列),必要時在那個模組加一支「有未結案嘗試的廣告」查詢;收件表模組不直接對嘗試表下 SQL(第 3 輪架構對齊席指出全專案迄今沒有例外):
  1. 在同一個交易裡算出「已有未結案嘗試的廣告」,排除它們。被排除的提案不交出去、不算投遞(第 2 輪並行席指出若分兩個交易,中間會有空窗)。
  2. 挑最舊的可取件提案:沒有處置的待處理提案,或處置是處理中而且租約已到期的提案。
  3. **先取得租約**:寫處置處理中、租約序號加 1、擁有者、到期時間,拿到收據。這一步還不算投遞。所有後續寫入都帶這張收據(第 3 輪外家席與相容席指出:原本的終點快路徑在拿到收據之前就要確認,跟「確認一律帶收據」互斥;挑中的又正是租約已過期的列,用舊租約確認必然 0 列)。
  4. **再看這把鍵有沒有嘗試紀錄**(用快照重算冪等鍵):
     - 有終點結果(已驗證、失敗)→ 用剛拿到的收據確認(已交給執行、或已擋下附「同一操作先前已失敗」),不交出去、不算投遞,改挑下一份。
     - 未結案 → 第 1 步已排除這種廣告,這一支走不到;留著當防線:放掉租約(到期時間設成現在)、不算投遞,改挑下一份。依 Phase 0:結果不明的操作不計入重試上限、不得直接進死信。
     - 沒有嘗試紀錄 → 往下。
  5. 投遞次數已經等於上限(暫用 5)→ 用收據寫死信(附原因與最後一次失敗),改挑下一份;死信那次不算投遞。所以「上限 5」就是最多交出去 5 次。
  6. 否則投遞次數加 1,回傳提案與收據。
- 取件在處理一筆的**最前面**,在讀 DSP 與執行前檢查之前。開始一筆(Phase 3 的取件交易)改成「核對收據仍有效 → 開始一筆」,不再挑件。
- **讀 DSP 失敗、全表未結案已滿**:Phase 3 是「不寫任何東西、提案留在待處理」,下一輪無限次重試。現在提案已經是處理中,所以改成:帶收據記下最後一次失敗、放掉租約(到期時間設成現在),下一輪就能再取;每取一次算一次投遞,5 次都失敗就進死信。這是刻意的改變——一直讀不到 DSP 的提案不該無限重試(第 3 輪相容席指出這兩條 Phase 3 合約的斷言已不成立)。
- 死信只會打到「沒有任何嘗試紀錄」的提案:讀 DSP 一直失敗、全表未結案已滿、或每次都在開始一筆前當機。一旦開始過嘗試,它就歸對帳管,不會進死信。所以不會有「死信之後才被證實成功」的情況(第 2 輪銜接席指出)。

### 死信原因與失敗脈絡

- 兩個封閉列舉都定義在收件表模組裡,不借執行迴圈的結果列舉:收件表是下層,反過來匯入上層會變成循環匯入(第 2 輪架構對齊席與可測性席指出)。
  - **死信原因**:目前只有一個成員「投遞次數達上限」。
  - **最後一次失敗**:處理一筆每次沒能開始嘗試就結束這一輪時,帶收據寫下原因,成員是「讀不到 DSP」「全表未結案已滿」「同廣告被鎖」「沒有回報(當機或租約過期)」。取件時若發現租約是過期回收的,記「沒有回報」。
- 死信記下原因與最後一次失敗,人看得出它卡在哪一步(第 1 輪外家席指出只記次數不夠)。

### 確認規則(這個增量的核心)

- **確認一定晚於持久結果**。處置寫「處理中」不算確認,只有下面這些是:
  - **已交給執行**:這把鍵的嘗試到了已驗證。
  - **已擋下**:執行前檢查沒過(附既有的擋下原因),或這把鍵的嘗試是失敗(附「同一操作先前已失敗」)。
  - **已過期**:提案自己過期(狀態改已過期、處置清空)。
  - **死信**:沒有嘗試紀錄、投遞次數用完。
- 確認一律帶收據做條件寫入。既有的「標過期」「標擋下」原本以「仍待處理」為條件,新流程下提案一定已經是處理中,所以條件換成收據(第 2 輪三段式席與相容席指出,照舊條件會永遠寫不進去)。
- **處理一筆**:取件之後,讀 DSP、執行前檢查、簽發、開始一筆、呼叫 DSP、寫結果;嘗試到終點就在同一個交易裡確認;停在未結案就不確認、延長租約、結束這一輪。
- **對帳接上收件表**(第 2 輪三段式席、可測性席、銜接席指出轉人工與人工處置接不上):
  - 對帳每一輪掃兩種鍵:「未結案的嘗試(含轉人工)」與「嘗試已到終點、但收件表那一列仍是處理中」。後一種涵蓋人工處置完成(人工處置只寫嘗試紀錄,不碰收件表)與任何中途當機留下的漏網。
  - 對每一把鍵,先**原子接手**租約:收件表那一列是處理中,而且租約已到期、或擁有者就是自己,才把序號加 1、擁有者改成自己、到期時間往後推,拿到新收據;否則(別人持有且未到期)跳過這一輪。對帳不讀現值充當收據(第 2 輪外家席與並行席指出現讀現填等於沒檢查)。
  - 接手之後:嘗試中 → 在新收據下先轉成結果不明,再照結果不明處理(過期工作者留下的嘗試中,接手者要能合法收拾;現況靠啟動時的重啟恢復,增量 3 移除單一執行者鎖後就只剩這條路,第 3 輪外家席指出);轉人工 → 只續租,不碰 DSP、不動嘗試狀態;結果不明與已提交待驗證 → 照 Phase 3 的對帳推進,推到終點就在同一個交易裡確認;已到終點 → 直接確認。

  - 同一把鍵可能對應多份修訂(只換到期時間的新修訂算出同一把鍵):對帳只處理「處置是處理中」的那一列;其餘修訂在取件時會讀到既有嘗試紀錄而直接確認或跳過。

### 實作時決定(增量 1,2026-09-23,代使用者裁定,待覆核)

- 死信原因與最後一次失敗各佔一欄(死信原因、最後一次失敗),加上租約四欄,收件表共多六欄;都在同一次重建表遷移裡補。
- 「最後一次失敗」拿掉「同廣告被鎖」這個成員:取件已在同一個交易裡排除鎖住的廣告,單一執行者下走不到;開始一筆撞到同廣告鎖住時仍放掉租約(防線),但不記原因。
- 續期機制做在每一筆嘗試寫入上:核對收據與續租是同一個條件寫入(延長租約),活著的工作者每寫一筆就把租約往後推。所以處理一筆結束時停在未結案,不必另外延長。
- 取件之後提案已是處理中,新修訂不能再取代它。[S108] 原本要驗的「已被取代就不開始」改由「收據已失效(被接手或過期)就不開始、不呼叫 DSP」來驗。
- 放掉租約時把擁有者清空;取件回收一列處理中時,擁有者還在就代表上一個持有者沒回報(當機或卡住),記「沒有回報」。
- 對帳找不到這把鍵對應的處理中那一列(Phase 3 時代留下的已交給執行、或收件表已被清掉)時,不帶收據、照 Phase 3 的方式對帳,也沒有訊息可確認;這種鍵若停在嘗試中,留給啟動時的重啟恢復。
- 嘗試到了失敗就確認成「已擋下」並附「同一操作先前已失敗」,這把鍵第一次投遞就失敗(例如版本衝突)也一樣;更細的失敗原因看嘗試紀錄的結果代碼。
- 啟動程式多一個可指定的擁有者參數(測試用,讓同一測試裡的處理一筆與啟動程式算同一個工作者);預設是行程編號加啟動秒數,重啟後是新的擁有者,上一次留下的租約要等到期才接手。
- 分析行程收件用戶端不受影響:它只看狀態碼。收件表模組多匯入冪等鍵函式與嘗試狀態列舉(取件分流用),「收件口不定義欄位驗證」那支既有測試的允許清單跟著加這兩個。

### 回退(增量 1)

- 回退前要先**排空處理中**:沒有嘗試紀錄的處理中列 → 清空處置與租約,回到待處理;有終點結果的 → 寫對應確認;有未結案嘗試的 → 寫已交給執行(回到 Phase 3 的語意,由對帳負責)。不先排空的話,Phase 3 的挑件只認「處置為空」,這些列會永遠選不到(第 3 輪外家席指出)。
- 排空之後才把處置改回 Phase 3 的兩態、拿掉租約與收據的判斷、拿掉對帳的接手與確認,保留期清除改回只看待處理。多出的欄位與處置成員留著不影響。既有的收件合約(同鍵重送、連號、上限、取代、到期標記)不改。

### 這批測試比既有測試多證明什麼

- 情境上跟既有測試重疊:對帳同鍵重送([S79])、對帳從操作紀錄恢復([S80])、取件後當機租約到期再投遞([S104])、接手時先轉結果不明([S117])。
- 既有測試裡的「當機」都是同一個行程內丟例外,會經過交易回滾與收尾程式碼;這批是**行程真的猝死**(沒有例外、沒有回滾、沒有收尾),再走**真的啟動程式**重啟(單一執行者鎖、重啟恢復、每輪先對帳)。補的是模擬與真實之間的落差。

### 怎麼造當機

- 每個當機測試開兩個子行程,先後跑(不同時):
  1. **會死的那個**:內嵌腳本在**類別上**換掉一個方法(執行迴圈的物件建好後不能改屬性,而且是在啟動函式裡面才建出來,測試拿不到那個物件;這一點跟既有猝死測試換在物件上不同),再呼叫執行迴圈的啟動函式。換上的函式在指定位置印一行「死點狀態」(交易是否還開著、嘗試紀錄最後一列的狀態、收件表那列的處置),然後 os._exit(9)。
  2. **重啟的那個**:內嵌腳本呼叫同一個啟動函式,但傳入往後撥的時鐘(真實時間加 5 分鐘)與有限輪數,跑完自己結束。
- 每個當機測試都做三道斷言(照抄既有猝死測試的雙重斷言,再加一道):
  - 會死的子行程退出碼是 9:證明真的死在換掉的函式裡,不是正常跑完。函式日後被改名或合併,換上的東西不會被呼叫、行程正常結束,測試就會紅,不會悄悄失效。
  - 死點狀態恰為預期那一格:證明死在指定的縫隙,不是前一步或後一步。
  - DSP 收到的寫入請求數:由測試行程裡的 DSP 伺服器計數(伺服器跑在測試行程的執行緒裡,子行程死掉計數也還在)。模擬 DSP 對同一把冪等鍵的第二次寫入會直接回原結果、不留痕跡,所以「只套用一次」證明不了「沒有重送」,要另外數請求。
  - 計數掛在請求處理器、照路由名稱分三類:改狀態的寫入(用 DSP 伺服器現成的「會改廣告的動作」清單判定)、作廢、其他(讀取不算)。不能掛在 DSP 儲存層真正套用變更那一步:同鍵重送在更前面就回原結果,走不到那裡,會漏數。沿用既有端到端測試換請求處理器的做法。
- **撥時鐘,不縮租約**:
  - 租約留正式的 60 秒;增量 1 的「租約要遠大於一次 DSP 呼叫」那條不變量照樣成立,測試不會因為機器慢而在半路丟租約。
  - 重啟的子行程時鐘往後撥 5 分鐘:舊租約(60 秒)已到期、可以合法接手。
  - 測試行程裡的 DSP 伺服器時鐘用「真實時間加一個可調偏移」:第一個子行程跑時偏移 0,重啟前設成 5 分鐘。不能沿用既有端到端測試那個停在固定日期的假時鐘:子行程拿不到它、只能用真實時間,兩邊差好幾小時,而 DSP 只容許 30 秒的時鐘誤差,憑證會被當成「簽發時間在未來」或已過期拒收。
  - 提案有效期限:要能恢復的情境設 30 分鐘(撥 5 分鐘後仍有效);要驗「重啟後已過期」的情境設 2 分鐘(第一個子行程時還有效、撥 5 分鐘後已過期)。兩個條件都跟機器快慢無關。
- 內嵌腳本只透過命令列參數拿資料庫路徑等設定,不經環境變數;金鑰照既有啟動測試,只放進那一次子行程專用的環境字典。

### 四個當機點

照成功路徑的持久步驟切:嘗試中(提交)→ 呼叫 DSP → 已提交待驗證(提交)→ 讀 DSP 驗證 → 已驗證加確認(同一個交易提交)。

1. **寫完嘗試中、還沒呼叫 DSP**:死點狀態是嘗試中、處理中;DSP 收到 0 次寫入。重啟恢復轉結果不明;對帳用冪等鍵查不到,重跑執行前檢查通過,用同一把鍵重送。預期:DSP 共收到 1 次寫入、套用 1 次、嘗試最終已驗證、訊息已交給執行。
   - 同一個死點,提案在重啟時已過期:對帳查不到、檢查不過,先請 DSP 作廢這把鍵再判失敗。預期:DSP 收到 0 次寫入、1 次作廢,廣告不變,訊息已擋下。
2. **DSP 已提交、本地還沒寫結果**:死點狀態是嘗試中;DSP 收到 1 次寫入且已套用。重啟恢復轉結果不明;對帳查到操作紀錄,不重送,驗證後確認。預期:DSP 共收到 1 次寫入、最終已驗證、訊息已交給執行。
3. **已提交待驗證已寫、還沒驗證**(這就是事故 F2「持久結果已寫、確認還沒送」的形狀:本地有結果、收件表還沒確認):死點狀態是已提交待驗證、處理中,交易已關。重啟恢復不動它(只轉嘗試中);對帳接手後照執行後驗證走完。預期:DSP 共收到 1 次寫入、最終已驗證、訊息已交給執行。
4. **終點結果與確認的交易邊界**(已驗證與確認在同一個交易裡,Phase 0 的 ACK 規則):
   - 死在提交**之前**(換掉的是交易內寫確認的那一步:先照常寫,再印狀態並死):死點狀態是交易還開著。整筆回滾,重啟後看到的是已提交待驗證,照第 3 點恢復。預期同第 3 點。
   - 死在提交**之後**(換掉的是執行後驗證整段:先照常跑完,再印狀態並死):死點狀態是已驗證、已交給執行。重啟後什麼都不做。預期:DSP 共收到 1 次寫入、0 次作廢,嘗試紀錄與處置都不變。
- 換掉的函式有的是私有方法(例如交易內寫確認那一步)。選擇照抄既有猝死測試的做法(它也是換掉私有方法),不在正式程式碼的交易入口加「提交前回呼」:那會為了測試改正式程式碼;而退出碼斷言已經擋住「方法改名後測試悄悄失效」。

### 事故 F3:同一則訊息投遞兩次以上

- 同一則訊息先交給第一個執行迴圈,它在取件之後、開始嘗試之前死掉;第二個執行迴圈(撥過時鐘)重新取件。預期:
  - 第二次取件投遞次數是 2,拿到的是同一列、同一個任務與修訂。
  - 整個過程只有一把冪等鍵、只開一筆嘗試;嘗試紀錄相鄰兩列的狀態轉換每一步都合法(用程式自己的合法轉換表逐對核對)。這兩點結構上本來就成立(重新投遞沿用同一列;每一次寫嘗試都經合法轉換檢查),這裡把它寫成明文斷言,轉正審計時有東西可對。
  - DSP 共收到 1 次寫入、最後已交給執行。
- **重做分析也不能繞過執行閘**:同一個任務的第一版提案已執行(預算改成 150,DSP 版本因此往前走一格),分析行程重做分析送來第二版:新修訂、目標不同(預算改成 160),但它看到的廣告版本是舊的。預期:測試先斷言兩版的冪等鍵不同;第二版照樣重跑執行前檢查,被「版本已變」擋下;DSP 共收到 1 次寫入。
  - 目標必須不同:冪等鍵只由任務、廣告、動作、要改成多少、看到的版本五樣算出,修訂序號、理由、證據、期限都不算。只改理由的第二版會算出同一把鍵。
- **只改理由的新修訂靠已完成紀錄安全跳過**:第二版目標與看到的版本都跟第一版相同,只改理由。預期:兩版冪等鍵相同,取件時查到這把鍵已驗證,直接確認第二版、不讀 DSP、不跑執行前檢查;DSP 共收到 1 次寫入。這不是「過執行閘」,是「同一件事已做完不再做」,分開列才不會把它當成執行閘的證據。
- 分析行程重送同一份提案(同任務同修訂、同內容)照收件口既有合約回目前狀態、不新增一筆,這裡在端到端裡順帶驗一次。

### F3 轉正的範圍與缺口

- 交接文件的 F3 原文是「重複投遞不會重複**分析費用**或副作用」;已登記的預告合約只寫「不會重複副作用」,少了分析費用。這個落差在登記預告合約時就存在,這裡點明,不讓它悄悄傳下去。
- 第 1 版說「不重複分析費用屬於 Phase 2(已有任務佇列與檢查點)」是錯的:Phase 2 範圍明寫不加佇列;分析行程目前沒有租約或去重,而檢查點只防「同一行程重啟後重做已提交的步驟」,擋不住兩次呼叫同時跑時外部分析各呼叫一次。
- 2026-09-23 使用者決定:分析側去重排進增量 3。所以:
  - 增量 2 交出 F3 執行側的測試(任務識別不變、狀態轉換合法、不重複副作用、重做分析不繞過執行閘),但**不轉正 F3**。
  - 增量 3 補上分析側去重與它的測試後,F3 整條一次轉正。
- 轉正工具是機械的:它把預告合約「預告的合約:」那一行原文照抄成正式合約,沒有地方縮小範圍或加註。所以轉正前要先把那行補回「不重複分析費用」,跟交接文件一致;不補就照抄,讀起來會是 F3 整條通過。這一步排在增量 3 開工時做。

### 確認時機的說明(交接文件要求「ACK 時機有測試與設計說明」)

- 取件寫「處理中」不是確認。確認只在跟**終點**結果同一個交易裡寫(已交給執行、已擋下、已過期、死信),所以「終點結果已寫、確認沒送」這一格不存在(第 4 點證明兩個邊界)。
- 但「持久結果已寫、確認沒送」這個形狀仍會出現在非終點的狀態:嘗試中、結果不明、已提交待驗證。這些都不確認,讓租約到期後由對帳接手推進:
  - 嘗試中(第 1、2 點):重啟恢復轉結果不明,對帳用冪等鍵查 DSP。
  - 已提交待驗證(第 3 點):對帳重跑執行後驗證,只讀不寫。
- 第 1 版說「剩下的危險窗口只有 DSP 已提交、本地結果還沒寫」,漏了已提交待驗證那一段;已更正。
- 這段說明同步寫進 [[Systems/執行迴圈]]。
