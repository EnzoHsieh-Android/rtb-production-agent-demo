### 1. 「必須使用交接時存下的冪等鍵」測試是假綠

severity: major  
blocking: 是 拿掉存鍵讀取仍然全綠，無法防止演算法升版後把已成功操作誤判成未寫入。  
引句:「assert store.operation_key_for("t1") == operation_key(proposal)」

測試只證明「目前存入的鍵剛好等於目前演算法重算的鍵」，沒有證明 DSP 查詢真的使用該存值。我將 `_from_dsp` 等價變異成完全忽略 `store.operation_key_for()`、永遠呼叫 `operation_key(proposal)`；S311、S317 兩組參數、S321，以及這支名為 stored-key 的測試共五項仍全部通過。

具體例子：任務交接時存下 `k1-old` → 之後演算法升版，提案重算為 `k2-new` → 預期查詢 `k1-old` 並找到已成功操作 → 變異後實際查詢 `k2-new`、得到查無操作，錯誤建立接續任務。測試應在交接後把重算函式改成不同鍵，或直接把已存鍵設成與重算結果不同，再斷言 lookup 收到已存鍵。

### 2. DSP 操作查詢把不可能合法的版本 0 當成有效紀錄，永久誤判冪等衝突

severity: major  
blocking: 是 單次格式不合法的外部回應會讓任務不可逆地轉成 BLOCKED，而非依 S312 留在 HANDED_OFF 重試。  
引句:「return value is None or _is_int_between(0, value)」

`expected_version` 與 `new_budget` 的領域下限都是 1，但共用檢查以 0 為下限。實驗輸入 DSP 200 回應：

`campaign_id=c1, action=update_budget, new_budget=150, expected_version=0`

預期：用戶端判定欄位讀不懂、丟 `DspRequestFailed`；流程吞下查詢失敗、釋放租約，任務維持 `HANDED_OFF`。實際：用戶端產生 `DspOperation(... expected_version=0)`，流程將它視為內容不符，任務永久轉成 `BLOCKED`，錯誤為 `inbox_purged;idempotency_conflict`。

現有 malformed-response 參數只測了負數、布林值與超上限值，漏掉零這個邊界。`expected_version` 應使用正整數檢查；`new_budget` 也應依動作驗證完整參數形狀與正整數範圍。
