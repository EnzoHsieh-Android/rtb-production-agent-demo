### 2. 「已有接續關係、直接沿用不再寫」的防線,漏了代數用完那個子情況,重跑會拋例外而非設計承諾的沿用

`_write_follow_up` 用 `self.follow_up_to(task_id)`(即 `SELECT follow_up_task_id FROM follow_ups WHERE original_task_id = ?`)來判斷「原任務已有接續關係」。但代數用完(`LIMIT_REACHED`)那條路寫入 `follow_ups` 時 `follow_up_task_id` 是 `NULL`(`recorded_child = None`),`follow_up_to()` 對這種列一樣回傳 `None`,跟「完全沒有關係」無法區分。實驗直接呼叫 `_write_follow_up` 兩次模擬「已寫過 LIMIT_REACHED、又被重跑一次」:

```
first call note: version_changed;replan_limit_reached=3

second call raised: IntegrityError UNIQUE constraint failed: follow_ups.original_task_id
```

第二次呼叫直接撞 `follow_ups.original_task_id` 主鍵,丟 `sqlite3.IntegrityError`,不是設計承諾的「直接沿用、不再寫」。目前這個函式只從 `commit_step` 呼叫一次,而 `commit_step` 只被 `_advance_holding` 呼叫一次,`advance()` 對終點狀態一律直接返回(`if row.state in TERMINAL_STATES: return row.state`),所以在現有呼叫路徑下不可達;若之後有任何程式改動繞過這個終點檢查重跑同一個已經代數用完的任務,會從「防線,正常不會發生」直接變成未捕捉例外。
