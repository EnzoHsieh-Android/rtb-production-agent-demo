## 回歸掃描(沒有問題)

- **掃描器不會誤判合法回覆**
  - 隨機產生 20000 份合法 JSON 做比對:字串裡混括號、引號、反斜線、控制字元、零寬字元、中文,`ensure_ascii` 開關與縮排都換著試。`nesting_depth` 算出的深度與解析後實際深度全部相同,不符 0 筆。
  - 逐一手驗下面幾種,深度都正確:
    - 字串裡的 `[[`
    - `"[[[[`
    - 以 `\\` 結尾的字串,後面再接陣列
    - `\"[` 放在字串與鍵裡
    - 說明是 40 組 `"[`(逸出後)
- **合法回覆一定在上限內**
  - 封閉結構最深 5 層,縮排或空白不會加深。
  - 所以 64 層的上限不會擋掉任何計劃允許的回覆。
- **掃描器不會少算,json 解析器不可能比它更深**
  - json 只會在前綴合法時往下遞迴。前綴合法時,字串的起訖、括號的配對都跟掃描器看到的一樣。
  - 會讓掃描器深度變負的多餘 `]`,json 在那個位置就會報「Extra data」或語法錯,走不到後面更深的地方。
  - 所以解析器的實際遞迴深度不會超過 64,`RecursionError` 那道防線在正常輸入下走不到。
- **新原因沒有越過計劃的分界**
  - 計劃第 57 行說「頂層格式或解析錯誤」整份拒絕。[S1504] 已經把 4301 位整數這種「解析器上限」歸在解析錯、整份拒絕。深度上限屬於同一類。

  - 下游只用 `invalid_count` 與 `reasons()`,沒有地方依原因字串分支(`rg` 過 src 與 tests)。新原因同樣記 1 筆無效提交,n=0。
