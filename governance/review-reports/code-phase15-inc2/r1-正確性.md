## 1. 回覆裡的陣列只要平衡地巢狀 500 層,解析器就丟 RecursionError 崩潰

severity: major
blocking: 是
引句:「return all(_finite(item) for item in value)」
查證 file: `src/rtb/eval/rule_mining_check.py:123`(呼叫點在 `:135`,在 `:133` 的 try 外面)

**問題**
- `_load` 只把 `json.loads` 包在 `except (ValueError, RecursionError)` 裡。解析完才做的 `_finite(data)` 是遞迴函式,每一層巢狀要兩個 Python 框(函式本身加 generator),而且它在 try 的外面。
- C 版 json 解析器吃得下 500 層,`_finite` 卻會先爆遞迴上限。例外直接穿出 `parse_reply`,再穿出 `rule_mining_eval.run`。
- 計劃要求「巢狀過深」與解析錯一樣整份拒絕、記 1 筆無效提交,並且「不讓命令列崩潰」。現在的行為是整個種子的核對崩潰。如果這份回覆是第一次 `ok` 的錄製,它會被鎖定入庫([S1508]),那一批就永遠算不出「窮舉勝」。
- 模組 docstring 自己也宣稱「巢狀過深」會整份拒絕,和實際行為不符。

**重現**(PYTHONPATH=src,Python 3.14.6)
```
from rtb.eval import rule_mining_check as c
c.parse_reply("[" * 500 + "]" * 500)                                   # RecursionError(1000 位元組)
c.parse_reply('{"version":1,"suggestions":' + "[" * 500 + "]" * 500 + "}")  # RecursionError(1028 位元組)
```
- 用二分找到的最小崩潰深度是 500,只佔 1000 位元組,遠低於 6000 位元組的回覆上限。
- traceback 停在 `_finite` 的 `return all(...)` 那一行。

**弱測試**
- 測試用的 `"[" * 5000` 括號不平衡,在 `json.loads` 階段就丟錯被接住,根本走不到 `_finite`。所以這個 bug 測試抓不到。

**建議修法**
- `parse_float` 與 `parse_constant` 已經擋掉所有非有限數,`_finite` 其實是多餘的。可以刪掉它,或改成用顯式堆疊的迭代版。
- 至少要把 `_finite` 移進 try,讓 RecursionError 也轉成 `UNPARSABLE`。
- 補一個平衡的深巢狀測例,例如 `"[" * 500 + "]" * 500`,以及放在 `suggestions` 裡的版本,斷言結果是整份拒絕、`invalid_count == 1`。

## 2. 說明欄是孤立代理字元(`\ud800`)時,解析器丟 UnicodeEncodeError 崩潰

severity: major
blocking: 是
引句:「and len(value.encode("utf-8")) <= v.NOTE_BYTES」
查證 file: `src/rtb/eval/rule_mining_check.py:176`(同類問題還有 `:128` 的 `text.encode("utf-8")`,也在 try 外面)

**問題**
- `json.loads` 會把 `"\ud800"` 這種逸出解成含孤立代理字元的 str。`_note` 先過了型別與字數檢查,接著對它做 `value.encode("utf-8")`,就丟出 `UnicodeEncodeError`。
- 這個例外沒有被接住,從 `_suggestion` 一路穿出 `parse_reply`。
- 計劃把「信心欄型別或長度錯誤」列為只丟該條,不是崩潰。提示雖然要求模型不要用 `\uXXXX`,但解析器不能假設模型一定照做。
- 同理,如果模型用戶端交回的原始文字本身就含孤立代理字元(例如信封 JSON 解出來的),`_load` 第一行的 `text.encode` 也會在 try 外面崩潰。

**重現**
```
good = {"clauses":[{"condition":"raise_pct","threshold":"raise_pct:band_2"}],"direction":"improve",
        "support":1,"counterexample":0,"confidence_note":"\\ud800"}
c.parse_reply(json.dumps({"version":1,"suggestions":[good]}))
# UnicodeEncodeError: 'utf-8' codec can't encode character '\ud800' ... surrogates not allowed
```

**建議修法**
- 在 `_note` 裡把 `unicodedata.category(ch) == "Cs"` 當成不合法(只丟該條、記 `BAD_NOTE`),或用 try/except UnicodeEncodeError 回 False。
- `_load` 的大小檢查也包進 try,編碼失敗就整份拒絕(`UNPARSABLE`)。
- 補對應的測例。

## 3. 探勘執行器把探索側和保留側對調,所有測試仍全綠

severity: major
blocking: 是
引句:「return Prepared(seed, history, c.Recounter(history, sides.explore),」
查證 file: `src/rtb/eval/rule_mining_eval.py:51`、`src/rtb/eval/rule_mining_eval.py:52`、`src/rtb/eval/rule_mining_eval.py:53`

**問題**
- `prepare` 是真正組出送模型彙總表、再決定用哪一側重算的地方。它沒有沿用增量 1 已受測的 `preflight_seed` 組表路徑,而是自己重寫一份。
- 目前的程式碼是對的。但我在臨時副本做了兩個突變,測試都翻不紅:
  - M1:保留側重算器也用探索側。
  - M2:彙總表改用保留側建、探索重算器用保留側、保留重算器用探索側。這等於把保留集送給模型,同時用保留集核對。
- 對 M2 跑 `-k rule_mining` 的 tests/eval、tests/model、test_spawn_boundary,結果 16 passed;兩支新測試檔 7 passed。

- [S1503] 的「不送保留側」和 [S1505] 的「同一探索集重算」,在實際送出的路徑上沒有測試保護。

**重現**
- 在副本裡把 `rule_mining_eval.py` 第 51–53 行改成用 `sides.holdout` 建表與探索重算器、用 `sides.explore` 建保留重算器。
- 跑 `pytest -q tests/eval/test_rule_mining_model.py tests/eval/test_rule_mining_check.py`,結果 7 passed。

**建議修法**
- 補兩條斷言:
  - `prepared.table == rp.summary_table(rb.summarize(h, split.explore))`
  - `prepared.prompt_bytes == rp.preflight_seed(SEED).prompt_bytes`(也就是 PREFLIGHT_RECORD 的 B=6057)
- 用 `rh.split` 抽幾條條件,斷言 `prepared.explore.stats(k)` 等於探索側彙總、`prepared.holdout.stats(k)` 等於保留側彙總。
- 更好的做法是讓 `prepare` 與 `preflight_seed` 共用同一支建表函式,避免兩份實作分歧。

## 4. 4301 位整數要不要整份拒絕,取決於直譯器的 int_max_str_digits 設定

severity: minor
blocking: 否
引句:「assert sys.get_int_max_str_digits() in (0, 4300)」
查證 file: `src/rtb/eval/rule_mining_check.py:133`、`tests/eval/test_rule_mining_check.py:94`

**問題**
- [S1504] 寫死「4301 位整數解析錯 → 整份拒絕」。實作完全靠標準函式庫在預設 4300 位上限時丟 ValueError。
- 只要執行環境設了 `PYTHONINTMAXSTRDIGITS=0` 或 `-X int_max_str_digits=0`,同一份回覆就會被解析成功,變成單條 `bad_count`。
- 整份拒絕和單條丟棄的分界因此會隨環境改變。
- 測試容許 `0`,但在 0 的環境下,後面的 `UNPARSABLE` 斷言一定失敗。這條前置斷言本身前後矛盾。

**重現**
```
python -X int_max_str_digits=0 -c "...parse_reply(含 support 為 4301 個 9 的回覆)"
# → rejected=None, dropped=(Invalid(index=0, reason='bad_count', ...),)
```

**建議修法**
- 給 `json.loads` 加 `parse_int` hook:去掉負號後超過 4300 位就 `raise _Rejected(UNPARSABLE)`。這樣分界就不看環境。
- 測試的前置斷言改成只接受 4300,或直接刪掉。

## 6. 說明欄另擋 Cf,但提示沒告訴模型,等於沒公告就記誤報

severity: minor
blocking: 否
引句:「unicodedata.category(ch) in ("Cc", "Cf")」
查證 file: `src/rtb/eval/rule_mining_check.py:177`;提示原文在 `src/rtb/eval/rule_mining_prompt.py:44`

**問題**
- 計劃與系統提示都只禁「控制字元、引號、反斜線」。Unicode 的控制字元是 Cc。
- 實作另外擋 Cf(格式字元),包含 ZWJ U+200D、軟連字號 U+00AD、方向標記 U+200E/200F 等。例如一個含 ZWJ 的家庭 emoji 說明,會被丟成 `bad_note` 並計 AI 誤報。
- 這條規則會影響 AI 誤報的分子與分母,卻沒有出現在提示裡,也不在 `version_params()` 的凍結清單裡。模型無從得知,改動時也不會觸發換評估版本。
- 說明欄本來就不進人讀報告([S1509]),所以另擋 Cf 的安全收益有限。

**建議修法**
二選一:
- 拿掉 Cf,回到計劃的字面。
- 保留 Cf,但同時做三件事:把「格式字元」寫進系統提示(這會換錄製鍵,這一增量還沒有真錄製,成本低)、把說明字元規則列進 `version_params()`、在計劃補一條代使用者裁定並寫明對雙方的影響。
