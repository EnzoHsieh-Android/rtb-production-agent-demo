## 1. 深巢狀要整份拒絕還是只丟該條,仍取決於執行緒的 C 堆疊大小

severity: minor
blocking: 否
引句:「except (ValueError, RecursionError, MemoryError) as broken」
查證 file: `src/rtb/eval/rule_mining_check.py:160`、`tests/eval/test_rule_mining_check.py:265`

**問題**
- 新裁定寫「深巢狀出現在單條欄位裡時照『型別錯只丟該條』處理」,也寫「整份/單條分界不能隨環境漂移」。
- 可是單條丟棄有個前提:`json.loads` 本身要吃得下那個深度。吃不下時,RecursionError 會被第 160 行收成整份 `unparsable`。
- 在 Python 3.14,C 版 json 解析器的深度保護看的是實際剩餘的 C 堆疊,不是 `sys.setrecursionlimit`。所以同一份不超過 6000 位元組的回覆,換一個堆疊大小,判決就不同。
- 模組 docstring 第 8 行把「任何深度的巢狀」列在整份拒絕,這又和裁定、測試(2900 層放在欄位裡要只丟該條)互相矛盾。
- 這和 c_4 是同一類問題:c_4 修了整數位數,巢狀深度還沒修。

**影響範圍**
- 主執行緒(8 MiB)與 macOS 次執行緒預設的 512 KiB,可解析深度都超過 6000 位元組能寫出的約 3000 層,所以目前不會發作。
- 只要改在較小堆疊的執行緒裡跑,就會發作,例如 musl 預設的 128 KiB,或自訂 `threading.stack_size`。新測試在那種環境也會變紅。

**重現**(`PYTHONPATH=src`,Python 3.14.6)
```
wrap = '{"version":1,"suggestions":[{"clauses":[],"direction":%s,"support":1,"counterexample":0,"confidence_note":"a"}]}'
field = wrap % ("[" * 2900 + "]" * 2900)          # 5910 位元組
c.parse_reply(field)                               # 主執行緒 → rejected=None, dropped=[clause_count]
threading.stack_size(256 * 1024); 在新執行緒裡跑 c.parse_reply(field)
                                                   # → rejected='unparsable'(json 在 1647 層就丟 RecursionError)
```
- 各堆疊大小下 json 可解析的最大深度:256 KiB 是 1647,512 KiB 是 3468,1 MiB 是 7109,主執行緒是 116209。
- `sys.setrecursionlimit(100)` 不影響這個深度。

**建議修法**
- 在 `json.loads` 之前先做一次線性掃描:跳過字串內容,算出最大括號深度。
- 超過一個寫死的上限就整份拒絕。上限要遠低於任何實際堆疊能撐的深度,例如 64;合法回覆最深只有 4 層。
- 這樣分界就跟 4300 位整數一樣由解析器自己決定。
- 同步修正 docstring 與裁定文字:深巢狀是固定深度以上整份拒絕,不再是「欄位裡只丟該條」。
- 測試用這個上限的邊界值(上限層、上限加一層)斷言,不要用 2900 這種依賴堆疊的深度。

## 2. 整數位數把負號也算進去時,測試不會紅

severity: minor
blocking: 否
引句:「digits = len(text.lstrip("-"))」
查證 file: `src/rtb/eval/rule_mining_check.py:129`、`tests/eval/test_rule_mining_check.py:113`、`tests/eval/test_rule_mining_check.py:114`

**問題**
- 超出上限的測例用的是負號加 4301 位,剛好在上限內的測例用的是不帶負號的 4300 位。
- 所以把 `_int` 突變成 `digits = len(text)`(負號也算一位)時,兩支測試檔仍然 10 passed。
- 突變後,負號加 4300 位的整數會從「單條 `bad_count`」變成「整份 `unparsable`」,違反 [S1504] 以位數(4301 位)為界。
- 現行程式碼是對的,這是測試缺口。

**重現**
- 在副本裡把第 129 行改成 `digits = len(text)`。
- 跑 `pytest -q tests/eval/test_rule_mining_check.py tests/eval/test_rule_mining_model.py`,結果 10 passed。

**建議修法**
- 在 `for limit in (0, 640, 4300)` 迴圈裡,再加一條負號加 4300 位的測例,斷言結果是只丟該條(`bad_count`)、不整份拒絕。
