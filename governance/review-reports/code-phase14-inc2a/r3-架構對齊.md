## 發現 1:DSP 每日上限常數繞過既有的 `SQLITE_INTEGER_MAX` 命名常數,改回寫字面量

severity: minor
blocking: 否

`src/rtb/dsp/store.py:71` 既有 `SQLITE_INTEGER_MAX = 2**63 - 1`,同檔案裡已被
`store.py:260`、`store.py:268`、`store.py:275`、`store.py:601` 及 `server.py:248`
(`from rtb.dsp.store import SQLITE_INTEGER_MAX` 後使用)共五處引用,是這個數值在 `rtb.dsp`
這一側的既有唯一命名來源。這次新增的 `DAILY_MAX_COUNT` 沒有沿用它,而是在同一個檔案裡往下
26 行重新寫一次同樣的字面量:

引句:「DAILY_MAX_COUNT = (2**63 - 1) // DAILY_DAYS」

file: `src/rtb/dsp/store.py:97`(新增行,對照 `src/rtb/dsp/store.py:71` 的既有
`SQLITE_INTEGER_MAX = 2**63 - 1`)

註解本身也是用字面量描述、不是點名常數:

引句:「這樣任何合計都還在分析端讀取白名單的上限內(金額整數 13 位、計數 2**63-1),不會「每天都存得進、」

file: `src/rtb/dsp/store.py:94`

跟 `DAILY_MAX_CENTS = MAX_CENTS // DAILY_DAYS`(`src/rtb/dsp/store.py:96`)沿用同檔既有命名
常數 `MAX_CENTS` 的寫法對比,`DAILY_MAX_COUNT` 這一行沒有做同樣的事,屬於命名引用上的不一致
(不是重新定義出第二套「整數上限是多少」的判斷邏輯,兩處數值仍相同、不會產生分歧結論,所以判
minor 而非 major)。修法建議:改成 `SQLITE_INTEGER_MAX // DAILY_DAYS`。
