# 架構對齊審查:r1-snapshot.patch(code-phase14-inc2a)

比對範圍:origin/main..HEAD,對照既有檔 src/rtb/dsp/store.py(`_apply`)、src/rtb/analyzer/dsp_client.py 對照 inbox_client.py / instrumented.py、src/rtb/domain/metrics.py 對照 evidence.py / _checks.py、src/rtb/analyzer/investigation.py 對照 instrumented.py。

## 問題一:分層與依賴方向

沒有查到跨層直呼——analyzer 這幾支檔沒有新增對 `rtb.dsp`(DSP 模擬器)內部模組的匯入,分析端仍只透過 HTTP 讀 DSP,跟既有慣例(`dsp_client.py`/`inbox_client.py` 只匯入 `rtb.domain.*`、`rtb.httpclient`)一致;`store.py` 這次新增的三段遷移(`_migrate_budget_before`、`_migrate_money_columns`、`_migrate_daily_dates`)也都包在既有 `_migrate_columns` 的同一個 `begin_immediate` 交易裡,寫入路徑一路延用 `_apply`/`_seed_transaction` 的既有交易寫法,沒有另起一套。

但這次改動把 `dsp_client.py` 對 domain 層的依賴深度改淺了一塊:原本 `dsp_client.py` 用 `from rtb.domain.metrics import exact_value` 取得「精確金額值」,現在這行被拿掉,改成在 analyzer 層自己重寫一份幾乎等價的邏輯(見發現 1)。同一支檔案其餘六個判斷(`is_id`、`is_count_or_none`、`is_finite_or_none`、`is_int_between`)仍照舊呼叫 `rtb.domain._checks`,只有「金額精確值」這一種判斷被拉出 domain 層自己刻——依賴方向在同一支檔案內不一致。

## 問題二:命名與錯誤處理

`domain/metrics.py` 既有的 `Exact = Fraction | Reason` 三態慣例(`INVALID_DATA`/`MISSING_DATA`/`NO_DENOMINATOR`,可分辨「值不合理」與「值缺漏」)被 `dsp_client.py` 新寫的 `_fraction()` 拋棄,改成二態 `Fraction | None`,呼叫端因此分不出「這欄缺值」跟「這欄型別不合法」(細節見發現 2)。三處新增的「固定兩位小數金額字串」判準彼此正負號規則不一致(細節見發現 1),命名上也各自取名(`_MONEY_PATTERN` / `_FIXED_AMOUNT` / 沒有名字的內嵌正則),沒有共用一個名字。

## 問題三:第二種做法

這是本次最主要的落差:「金額用固定兩位小數字串表示、要不要收負號、怎麼加總」在這個 patch 裡至少出現四套互不相同的實作,而不是延伸 `domain/_checks.py` 開宗明義講的「同一個規則只有一份定義」慣例,也沒有沿用同檔案原本已匯入的 `domain.metrics.exact_value`。細節見發現 1、3。
