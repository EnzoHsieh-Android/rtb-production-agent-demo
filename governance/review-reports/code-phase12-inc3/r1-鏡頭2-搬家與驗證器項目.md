## 發現 3:「底線名字加公開別名」是專案裡第二種做法;用明確的 ids 可以直接改成公開名字
severity: minor
blocking: 否

引句:「only_says_done = _only_says_done」

**跟專案既有做法比:**
- r3 a1 的先例是把跨檔用到的名字直接改成公開名字(render_flow、validate_flow 等),沒有留底線本名再加別名。
- 在整個 src、tools、tests 裡,「`x = _x` 模組層別名」只出現在 `tools/forgery_demos.py:308`–`312` 這一處,等於是第二種做法。
- 測試端「import 公開名字 as 底線名字」有一個前例:file: `tests/demo/test_page.py:25`。
- 另外,專案已經有 26 處 parametrize 使用 `ids=`,例如 file: `tests/kit/test_migration_failure_closes_the_connection.py:26`。所以「用明確的 ids 讓項目 id 不依賴函式名」本來就是既有做法。

**更好的解法,我實測過:**
- 做法:把五個函式直接改成公開名字、拿掉別名,parametrize 改成從 `FORGERIES` 展開,再加上 `ids=[f"_{f.forge.__name__}-{f.expected}" for f in FORGERIES]`。
- 結果:收集到的項目清單跟 836eb27 逐行 diff 完全相同(278 項);造假和天花板相關的 6 支測試全部通過;ruff 只剩 2 個 import 排序的問題,可以自動修。
- 附帶好處:目前測試的 parametrize 表和 `FORGERIES` 各自抄了一份「預期原因字串」(result、src/rtb/kit.py、void 等),一起改之後只剩一份。發現 1 那支測試也不再需要。

**結論:**
- 這個折衷不會做出錯誤的行為,可以接受。
- 但它多出第二種慣例,還附帶了發現 1、2 的問題。改成「公開名字加明確 ids」比較乾淨。

3 條,blocking 0。
