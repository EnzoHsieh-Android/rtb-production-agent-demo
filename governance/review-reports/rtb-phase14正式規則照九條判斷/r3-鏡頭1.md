## 發現 1:過去調整端點用「查詢時的 now」篩掉 3 天內加額,第 3 條卻用「決策時的 now」;加額剛好滿 3 天時兩條都看不到它,照舊提案

severity: major
blocking: 是

引句:「端點只回提交時刻距查詢 `now` 至少 3 天的最近一筆加額，仍維持最多 5 列白名單，3 天內的調整由 `check_change_history` 交第 3 條判」
引句:「以做出最終決策的 `now` 為準，與新鮮度檢查用同一時間」
引句:「最近 3 天的歷史切點沿用原函式的嚴格 `committed_at > now - 3 days`，剛好滿 3 天不算近期」
引句:「若加額恰滿 3×24 小時但 D+3 尚未完，也維持 null」

佐證:
- file: `src/rtb/analyzer/dsp_client.py:231` 過去調整每列的 `days_ago` 必須 ≥ 3,否則整包不收。所以「只回 3 天以前」只能由端點依它收到請求時的時間先篩。
- file: `src/rtb/analyzer/dsp_client.py:239-246` 歷史列只有動作、版本、時間戳,沒有調整前後預算。領域層從歷史看不出某筆 `update_budget` 是加額還是減額,也就無法自己補回被端點篩掉的加額。
- file: `src/rtb/eval/investigation_cases.py:118-124` 標準答案的第 4 條看的是「最近一筆加額」。

問題在哪:
- B 步驟在時間 `t_B` 讀歷史與過去調整,最終決策在稍後的 `t_D`。依第 88 行,兩者最多可相差 15 分鐘(新鮮度上限)。
- 一筆加額 R2 若在 `t_B − 3d` 與 `t_D − 3d` 之間提交:
  - 對端點(用 `t_B`)來說它還不滿 3 天,所以不回。
  - 對第 3 條(用 `t_D`、嚴格大於)來說它已滿 3 天,所以不算近期。

失敗場景:
- 輸入:某廣告在 40 天前有一筆加額 R1,前後轉換 10→20;本系統或另一方在 `t_B − 3d + 1 分鐘` 又加額 R2。逐日平穩,1 小時有轉換,配速偏低。B 在 `t_B` 讀,C 與決策在 `t_B + 2 分鐘`。
- 第 3 條:R2 的提交時刻不大於 `t_D − 3d`,不命中。
- 第 4 條:端點只回 R1,轉換有增加,不命中。
- 第 5 條不命中,第 8 條判值得加,**建立加預算提案**。
- 依 spec 自己的設計,R2 才是最近一次加額,而且它的 D+3 一定還沒過完(它提交在 D 日,此刻最多到 D+3),應回 null、第 4 條判證據不足。
- 若 R1 不存在,端點回 `rows=[]`,結果同樣是提案。

後果:
- 本系統自己的加額在滿 3 天那一刻,就可能被再加一次。這正是本計劃要防的「剛調完預算仍提案」。
- [S1415] 的範例只測 D+4 與 D+3 未完兩種情形,照字面實作可以全綠。

需要擇一明訂:
- 端點不做 3 天篩選,回最近一筆加額;同時放寬 `MIN_ADJUSTMENT_AGE_DAYS` 白名單,由領域層以決策 `now` 判切點;或
- 領域層在第 3/4 條發現歷史裡有比過去調整更新的預算事件時,判證據不足。

兩種做法都要補一條「B 在 3 天前一刻、決策在滿 3 天後」的驗收例。
