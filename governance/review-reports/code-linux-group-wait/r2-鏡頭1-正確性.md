### 1. 自我檢查擋不住最常見的「沒有另掛 /proc 的 PID 命名空間」:自己的編號剛好撞到宿主的核心執行緒,檢查照樣通過,又判成沒有活的而漏殺
severity: major
blocking: 是
引句:「if mine is None or mine[1] != os.getpgrp():」
file: `src/rtb/modelclaude.py:245-246`

- **問題:** 自我檢查只比兩件事:`/proc/<os.getpid()>/stat` 讀不讀得到,以及裡面的 pgrp 是不是等於 `os.getpgrp()`。這裡的 `os.getpid()` 是命名空間裡的編號,/proc 卻是宿主的。
- **撞號的過程:** 以 `unshare -pf bash -c 'pytest'` 為例,沒加 `--mount-proc`:
  - 非互動的 bash 不會另開群組,pytest 在命名空間裡是 pid 2。
  - pytest 的群組在命名空間外面,所以核心讓 `getpgrp()` 回 0。
  - 宿主的 `/proc/2` 是 kthreadd,它的 pgrp 也是 0,自我檢查就通過了。
  - 核心執行緒佔掉宿主的 pid 2 到幾百號,pgrp 全是 0,命名空間裡編號小的行程幾乎一定撞到。
- **另一種撞法:** 行程在命名空間裡先做過 setsid,pid 和 pgrp 都是 1,也會撞上宿主 systemd 的 pgrp 1。
- **後果:** 接著拿命名空間裡的群組編號去宿主的 /proc 找,當然找不到,結果回 False。這正是 r1 第 1 條「只補殺一次、不記日誌」的漏殺方向。
- **註解言過其實:** 註解說這個檢查能擋「另一個命名空間」,但作者自己的 `other_namespace` 測試只放了 pid 1 這一種情況。
- **重現:** 在複本裡把 `PROC_ROOT` 換成假的宿主行程表,內容如下:
  - `1 S pgrp1`、`2 S pgrp0`、`3 I pgrp0`、`57 I pgrp0`
  - `40057 D pgrp40057`:claude 群組在宿主的編號,還卡在 D 狀態
  - 把 `os.getpid` 換成回 2、`os.getpgrp` 換成回 0,再呼叫 `cc._proc_group_members(57)`,結果是 `False`,不是 `None`。
  - 同一支探針跑 r1 那三種情況,都回 `None`。
- **建議:**
  - 改用核心本身的判斷:`os.readlink(PROC_ROOT / "self")` 要等於 `str(os.getpid())`。/proc/self 是依這份 procfs 掛載所屬的命名空間算出來的,讀的人不在那個命名空間時,會回宿主編號或 ENOENT,兩種都判成 None。
  - pgrp 比對可以留著當第二道檢查。
  - 另外 `os.getpgrp() == 0` 表示群組在命名空間外面,這時直接回 None。
  - 把上面的 kthreadd 撞號情況加進 `test_a_proc_that_does_not_look_like_ours_falls_back_to_signals` 的參數。

### 2. pop 金鑰常數只看變數名、不看它綁的值:同一個名字綁成 HOME 或 PATH 就放行;popitem 也不抓
severity: minor
blocking: 否
引句:「if isinstance(key, ast.Name) and key.id in POPPABLE_CONSTANTS:」
file: `tests/test_suite_isolation.py:132-141`(核對只在 `:197`)

- **問題:** 放行只看 `ast.Name.id` 是不是 `KEY_ENV`、`APPROVAL_KEY_ENV`、`AUDIT_KEY_ENV` 這三個名字。
  - `:197` 只核對 `capabilitykit` 模組裡這三個常數的值。
  - 被掃描的檔案裡,同名變數實際綁到什麼,完全沒有檢查。
- **重現:** 在複本裡對 `env_offenders` 餵下面四種寫法,都回 `[]`,也就是不算違規:
  - 在檔內寫 `KEY_ENV = 'HOME'`,再 `env.pop(KEY_ENV, None)`
  - `from os import sep as KEY_ENV`,再 `env.pop(KEY_ENV, None)`
  - `for KEY_ENV in ('HOME', 'PATH'): env.pop(KEY_ENV, None)`
  - `env.popitem()`
- **影響範圍:** 要故意或巧合地重用這個名字才會踩到,屬於守門的缺口,目前沒有真實用法觸發。現有的兩處用法(`tests/dsp/conftest.py:35`、`tests/executor/test_runner.py:69`)都是從 `rtb.capabilitykit` 匯入的。
- **建議:**
  - 放行時,同時要求檔內有 `from rtb.capabilitykit import <那個名字>`,而且檔內沒有其他地方再綁同一個名字(賦值、for 迴圈變數、import 別名)。
  - `popitem`、`popitem()` 一律視為刪鍵。

### 已查無問題(不列為 finding)
- **正常 Linux 上不會誤退回送訊號:**
  - 同一個命名空間裡,`/proc/<tgid>/stat` 第 5 欄就是 `task_pgrp_nr_ns`,跟 `getpgrp()` 相同。
  - 從非主執行緒呼叫時,`getpid` 仍是 tgid。
  - hidepid 開著也看得到自己的行程。
  - 每次輪詢多讀一次 stat,成本可以忽略。
- **共用的 `alive()` 在 macOS 上行為不變:** 讀不到 /proc,就退回 `kill(pid, 0)`,ESRCH 和 EPERM 都算不在。
