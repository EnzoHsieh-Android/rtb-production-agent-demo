# Phase 15 增量 3 代碼審 r1:正確性席

範圍:凍結的 `r1-snapshot-src.patch`、`r1-snapshot-tests.patch`(HEAD 跟凍結 patch 逐行相同)。
實驗都在 scratchpad 的臨時目錄,用測試檔裡的假後端 `Live`、`honest_answer` 跑完整的「三種子錄製 → 驗收 → 入庫 → 報告」流程。沒有呼叫 claude、沒有設行程環境的即時開關、沒有碰 ~/.rtb。

## 查過、沒發現問題的地方

- **比較指標**:逐條對過計劃 RETIRE-IF、〈模型建議…〉與 [S1506],實作都照規格。
  - 召回用窮舉前 K;精確度與誤報用同名額前 n。
  - 無效提交進 AI 可計誤報的分子與分母,保留後也照算;整份拒絕記 1 筆。
  - 相關誘餌只在保留側成立時另列,不進分母;純噪音、只探索側誘餌、部分重疊、反方向都計誤報。
  - 名單先取定再過保留側,不遞補。
  - n=0 或任一方同名額分母為零,判「窮舉勝」,並寫「未量」。
  - 精確度用 Fraction 精確比較,平手算窮舉不輸。
- **RETIRE-IF 門檻**:三批沒全量就寫「未判」。
- **洩漏**:模型的 `confidence_note` 塞了 Markdown 標題、未知欄位名與門檻塞了注入字串,重播後報告裡都沒有這些文字。無效條目只顯示固定原因代碼與正規化鍵。
- **重產穩定**:同一份入庫目錄用 PYTHONHASHSEED 1/2/3/7/99、不同工作目錄、帶或不帶 `--ledger`、`--verify` 或預設模式分別重產,報告逐字相同;現行「等錄製」版也跟入庫報告逐字相同。
- **批次清單的機檢**:
  - 序號遞增、不重用;非 ok 記呼叫失敗、可換序號重錄;有待驗收的錄製時擋新錄製。
  - 入庫後擋再錄;錄製鍵集合恰等於預期的一個鍵;每份錄製要是 rule_mining 且 ok。
  - 錄製目錄放在入庫根底下時,閘道的 `check_recordings_dir` 本來就會擋。
- **測試**:`tests/eval` 共 130 過;只有刻意留紅的 `test_committed_rule_mining_recordings_replay_all_three_seeds` 紅。

## 1. 驗收失敗不分原因都永久記成「驗收沒過」:打錯目錄就能丟掉第一次成功錄製,改入庫下一次(每種子只准第一次 ok 的規則被繞過)
severity: major
blocking: 是
引句:「if args.check_in and problems:」
查證 file: src/rtb/eval/rule_mining_eval.py:393

**問題**:`_check_in` 把所有問題一視同仁,只要有問題就把嘗試改寫成 `REJECTED`,寫進批次清單。這些問題包括:

- `--recordings-dir` 不存在或打錯;
- 入庫目錄已存在;
- 重播環境造成的讀不到錄製。

`_seed_problems` 算「第一次 ok」時又刻意排除 `REJECTED`(rule_mining_recordings.py:231)。結果是,不論錄製內容本身多乾淨,操作者只要把 `--check-in` 指向錯的目錄一次,就能把這個種子第一次 ok 的錄製作廢。之後重錄、入庫第二次錄製,清單機檢仍然全過。

計劃 RETIRE-IF 與 [S1508] 的「每種子只准第一次成功錄製入庫」就是要擋挑批,這裡被繞過了。批次清單另外沒記錄製當時的 staging 目錄,驗收時也就無從核對「驗的是不是那一次的目錄」。報告的嘗試表只顯示「驗收沒過」,不顯示原因。

**重現**(scratchpad `sim/sim_a.py`):

1. 用 `record(...)` 錄 15001 第 1 次,結果 ok、待驗收。
2. 執行 `--check-in --demo-id phase15-seed-15001-1 --recordings-dir <不存在的目錄>`,結束代碼 1,清單記成「驗收沒過」,原因是「錄製目錄不存在:typo-dir」。
3. 改用正確目錄再入庫,被拒絕(狀態已是驗收沒過)。
4. 錄第 2 次(換一份不同的回覆),入庫通過。
5. `manifest_problems` 回 `[]`,清單是 `[('…-1','驗收沒過','ok'), ('…-2','已入庫','ok')]`。

**建議修法**:

- 分開兩類問題:
  - 操作或環境問題(目錄不存在、入庫目錄已存在、重播環境錯)只拒絕,結束代碼 2,不改清單。
  - 只有目錄內容本身的驗收失敗(批次、鍵集合、呼叫者或結果、失敗類)才記 `REJECTED`。
- 即時錄製時把錄製目錄的絕對路徑與錄製檔的 sha256 記進 Attempt;驗收與入庫要求兩者都相符。
- `first_ok` 的排除條件改成「內容驗收失敗」,不要排除所有 `REJECTED`。

## 2. 入庫搬檔不是原子操作:複製中途失敗或中斷後,重試會把有效的第一次 ok 記成「驗收沒過」,之後每次入庫都被「入庫目錄已經存在」擋下(死結)
severity: major
blocking: 是
引句:「shutil.copyfile(path, target / path.name)」
查證 file: src/rtb/eval/rule_mining_eval.py:398

**問題**:入庫的順序是:先 `target.mkdir` 建出最終目錄,逐檔 `copyfile`,最後才 `_save` 改清單。

- **複製途中失敗**(磁碟滿、權限、Ctrl-C):OSError 沒被 `command` 接住,直接丟 traceback。最終目錄留下殘缺的內容,清單仍是待驗收。
- **複製完、存清單前中斷**:最終目錄是完整的,但清單仍是待驗收。報告把這個種子當成等錄製,也不會提示有孤兒目錄。

這兩種情況下,重試 `--check-in` 都會撞到第 385 行「入庫目錄已經存在」,再被第 1 條的邏輯永久記成 `REJECTED`。之後同種子每次重錄入庫,也都因為同一個殘留目錄被記成 `REJECTED`,還平白花掉模型呼叫費用,只能手動刪目錄才解得開。

**重現**(scratchpad `sim/sim_b.py`):

1. 錄 15002 第 1 次,結果 ok。
2. 把 `rme.shutil.copyfile` 換成會丟 `OSError(28)` 的版本,再執行 `--check-in`:丟出例外,清單仍是待驗收,`committed/15002/` 已存在但是空的。
3. 還原 `copyfile` 再重試,結束代碼 1,清單記成「驗收沒過」,原因是「入庫目錄…已經存在」。
4. 錄第 2 次再入庫,同樣被「入庫目錄已經存在」拒絕,也記成驗收沒過。

**建議修法**:

- 先複製到入庫根底下的暫存兄弟目錄(例如 `.<seed>.<pid>.tmp`),逐檔 fsync。
- 用 `os.rename` 一次換成 `<seed>`,再原子地寫清單。
- 入庫目錄已存在時:如果內容跟這次嘗試的 staging 逐位元相同、清單仍是待驗收,就補寫清單,不要退回。
- 報告與 `--verify` 要把「有目錄但清單沒有入庫紀錄」列為問題。
- 入庫目錄已存在應該屬於「只拒絕、不改清單」那一類(見第 1 條)。

## 3. 入庫批次驗收沒過時,報告照樣用它判 RETIRE-IF「成立」
severity: minor
blocking: 否
引句:「elif all(r.verdict.retire_holds for r in reports):」
查證 file: src/rtb/eval/rule_mining_report.py:426(另見 src/rtb/eval/rule_mining_eval.py:267)

**問題**:`_seed_ai` 只要重播讀得到錄製,就回傳 `MEASURED`。它不管兩類驗收問題:

- 這批自己的 `batch_problems`;
- 清單層的 `manifest_problems`,例如「入庫的不是第一次成功的錄製」。

`_summary` 又只看是否三批都 `MEASURED` 就下 RETIRE-IF 判定。計劃要求判定批次是「第一次 ok 且有效入庫」。驗收沒過的那一批不該進判定,報告卻在同一份文件裡同時寫「撤除條件…成立」與「驗收:沒過」。`--verify` 會以結束代碼 1 擋住 CI,但用預設模式重產、提交給人讀的報告會帶著這個自相矛盾的結論。

**重現**(scratchpad `sim/sim_d.py`):

1. 三種子都照流程入庫。
2. 在 `committed/15002/` 放一個 `notes.txt`。
3. 執行 `--verify`,結束代碼 1,但輸出同時出現:
   - 「撤除條件(RETIRE-IF):程式可判的部分成立——三批窮舉都不輸 AI」
   - 「15002:沒過(已量)」
4. 另外,`sim/sim_f.py` 產生「入庫的不是第一次成功的錄製」的清單,報告照樣拿第 2 次錄製量分數。

**建議修法**:

- `_seed_ai` 有任何 `problems`,或清單整體有 `overall` 問題時,AI 欄改成「驗收沒過,未量」,不給 verification。
- 或是 `_summary` 在驗收沒過時一律寫「未判(驗收沒過)」。

## 4. 批次清單沒把入庫錄製的內容綁住:同版本另錄一份替換入庫檔,`--verify` 仍全過(「成功後不得同版本替換」無法機檢)
severity: minor
blocking: 否
引句:「if attempt.recording_key not in (None, expected):」
查證 file: src/rtb/eval/rule_mining_recordings.py:280

**問題**:同一個評估版本、同一個種子、同一個模型的每一次錄製,錄製鍵都相同。清單只記了錄製鍵(跟預期鍵一樣,而且允許 None),沒有記錄製檔的內容雜湊。

- 已入庫目錄裡的檔被換成同鍵、同批次的另一次錄製,驗收完全看不出來。
- `attempt.expected_key` 也從沒跟重算的預期鍵比對。
- 已入庫的嘗試允許 `recording_key=None`。

**重現**(scratchpad `sim/sim_d.py` 前半):

1. 三種子都入庫。
2. 在另一個臨時入庫根錄一份 15001(6 條建議,入庫的那份是 2 條)。
3. 用 `shutil.copyfile` 蓋掉 `committed/15001/<key>.json`。
4. `--verify` 的結果是「15001:通過(已量)」,報告顯示 AI 有效 6 條。

**建議修法**:

- 入庫時把錄製檔的 sha256 記進 Attempt;`batch_problems` 核對雜湊。
- 已入庫的嘗試要求 `recording_key == expected` 而且不是 None。
- 另外核對 `attempt.expected_key == expected`。

## 5. 「呼叫中」的嘗試不擋同種子新錄製:同一種子可以同時送兩次模型呼叫,先入庫的若不是第一次,清單會永久壞掉
severity: minor
blocking: 否
引句:「pending = [a.demo_id for a in r.attempts_of(manifest, seed) if a.status == r.PENDING]」
查證 file: src/rtb/eval/rule_mining_eval.py:293

**問題**:`_manifest_for` 只擋「待驗收」,不擋「呼叫中」,而且清單的讀、改、寫之間沒有鎖。

第 1 次還在等模型的 60 秒內,在另一個終端錄同種子第 2 次,會被放行。這樣就有兩次付費呼叫。如果第 2 次先入庫,第 1 次之後又回 ok,就出現兩種壞狀態之一:

- 「入庫的不是第一次成功的錄製」;
- 「入庫後又錄了一次」。

兩種狀態命令列都沒有辦法收拾:待驗收的那次因為種子已入庫,無法驗收也無法退回。只能手改清單,或換評估版本。

**重現**(scratchpad `sim/sim_f.py`,在第 1 次的 `run` 裡巢狀跑第 2 次的錄製與入庫):最後清單是 `[('…-1','待驗收','ok'), ('…-2','已入庫','ok')]`,`manifest_problems` 回 `['15001:入庫的不是第一次成功的錄製']`。

**建議修法**:

- 在入庫根放一個排他鎖檔(`O_CREAT|O_EXCL`),包住整段「讀清單 → 記呼叫中 → 送出 → 記結果」與入庫流程。
- 或者讓 `_manifest_for` 遇到呼叫中也拒絕,並提供明確的「把中斷的呼叫中標成呼叫失敗」操作。

## 6. 閘道預檢開在一個用完就丟的閘道上:真正送出時換了一個新後端,會再做一次登入檢查,時間從 60 秒呼叫期限裡扣
severity: minor
blocking: 否
引句:「login = gate.preflight_login()」
查證 file: src/rtb/analyzer/rule_mining_model.py:85

**問題**:

- `check_gate` 在自己開的閘道上做 `preflight_login`,設好後端的已登入旗標後,就把這個閘道丟掉。
- `suggest` 再開一個新閘道。新後端的旗標是 False,所以 `ClaudeCodeBackend.send` 會在呼叫期限內再跑一次 `claude auth status`(modelclaude.py:663),花掉的時間從 60 秒逾時裡扣([S1514] 的 60 秒不再完整)。
- 如果這次登入檢查失敗,「呼叫中」已經存了,序號照樣被用掉。這跟 `check_gate` docstring 說的「不用掉展示編號序號」不一致。

**重現**:讀程式碼可確認。`check_gate` 回傳的 `GateCheck` 不含閘道;`suggest` 的第 102 行一定重開閘道。modelclaude.py:660-665 在旗標沒設時,會拿 `call.timeout_seconds` 做登入檢查,再把剩下的時間給模型。

**建議修法**:

- `check_gate` 回傳已預檢的 `Gate`,`suggest` 接受一個已開好的閘道來送出(窄入口仍然只送一次)。
- 或者 `suggest` 開閘道後先做一次 `preflight_login`,再送出。
