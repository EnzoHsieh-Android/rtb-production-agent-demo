## 新發現

### 1. 暫存目錄裡有非錄製檔名的檔時,錄製收尾或 `--abandon` 會把它記進清單,之後清單就「讀不懂」,所有命令都拒絕,命令列沒有辦法救
severity: major
blocking: 是
引句:「files = r.file_hashes(Path(attempt.staging_dir))」
查證 file: `src/rtb/eval/rule_mining_eval.py:383`(另見同檔 `:438` 的 `_finished`,以及 `src/rtb/eval/rule_mining_recordings.py:190`)

**問題**:寫入和讀回用的是兩套標準,彼此對不上。

- **寫入時照單全收**:`_finished` 與 `_abandon` 用 `file_hashes` 把暫存目錄裡的每個一般檔都寫進這次嘗試的 `files`,不管檔名。
- **讀回時嚴格擋**:`loads` 的 `_values_problem` 要求 `files` 的每個鍵都符合 `[0-9a-f]{64}\.json`,不符就丟 `ManifestUnreadable`。

所以只要暫存目錄在收尾那一刻多了一個非錄製檔名的檔,清單照樣寫得出去,但下一次就讀不回來。可能的來源:

- macOS 用 Finder 打開目錄時留下的 `.DS_Store`;
- 錄製寫到一半被硬殺,留下 `.<鍵>.json.<uuid>.tmp`;
- 協調者自己放進去的筆記檔。

讀不回來之後:

- `_load` 對每個命令都丟「批次清單讀不懂」:錄製、`--check-in`、`--abandon`、`--verify`、預設報告全部是結束代碼 2。
- 其他已經判定可入庫的種子也一起不能驗收、不能重產報告。
- 命令列沒有出口,只能手改批次清單。手改會破壞清單本來該有的可稽核性。

最自然的觸發路徑就在 README 自己教的流程上:行程中斷後,先打開暫存目錄看看有沒有東西,再照 README 跑 `--abandon --demo-id`。

**重現**(scratchpad `sim/sim2.py`):

1. 15002 正常錄好,判定可入庫。
2. 錄 15001 第 1 次,送出途中 Ctrl-C,清單停在「呼叫中」。
3. 在它的暫存目錄放一個 `.DS_Store`(模擬用 Finder 看過)。
4. `--abandon --demo-id phase15-seed-15001-1` 結束代碼 0。清單的 `files` 變成 `{'.DS_Store': '6e34…'}`。
5. 之後全部是結束代碼 2、「批次清單讀不懂:嘗試的 files 值不合格式」:
   - 錄 15001-2;
   - 對 15002 重跑 `--check-in`;
   - 再跑一次 `--abandon`;
   - `--verify`。
6. 錄製當下也一樣(`sim/sim.py E`):錄製途中在暫存目錄放 `.DS_Store`。這次錄製收尾照樣寫出清單,下一次讀就讀不懂。

另外,錄製途中暫存目錄冒出子目錄時,`file_hashes` 會丟 `Unhashable`,`files=()`。一次 ok、鍵也對的呼叫就被記成「驗收沒過」,同種子可以再錄。這是 c_1 那一類「操作問題被記成內容沒過」的殘留。

**建議修法**:

- 寫進 `files` 的只收 `RECORDING_NAME` 形狀的一般檔,跟讀取時的格式檢查用同一條規則。
- 其他項目(非錄製檔名、子目錄、符號連結)只寫進 `problems`,用固定字樣,不帶檔名,或檔名先逸出。
  - 錄製收尾時不能據此把 ok 的呼叫判成「驗收沒過」。
  - 判定時由 `_bound` 當參數錯拒絕,提示協調者清掉多的檔再判。
- 補一條測試:錄製途中與 `--abandon` 前都在暫存目錄放 `.DS_Store`,之後清單還讀得回來,同種子的流程照走。

### 4. `--verify --demo-id` 對已判定可入庫的嘗試一律結束代碼 0,入庫目錄缺了或內容不符也是
severity: minor
blocking: 否
引句:「done = not _committed_problems(io.root / str(attempt.seed), attempt)」
查證 file: `src/rtb/eval/rule_mining_eval.py:528-534`

**問題**:

- `_judge` 碰到可入庫的嘗試,就交給 `_already_accepted`。那裡不管 `done` 是真是假,都回 `EXIT_OK`。

### 5. 判斷鎖檔主人還在不在的依據不可靠:pid 被重用時 `--abandon` 永遠不清;空鎖檔會被當成殘留清掉
severity: minor
blocking: 否
引句:「if pid is not None and _alive(pid):」
查證 file: `src/rtb/eval/rule_mining_eval.py:371`(另見同檔 `:340-345`、`:354-361`)

**問題**:

- **活著的判斷太寬**:只看 pid。`os.kill(pid, 0)` 遇到 `PermissionError`(別的使用者或 root 的行程)也當成活著。
  - 硬殺之後重開機,或過一段時間 pid 被別的行程重用,`--abandon` 就一直回「鎖檔的主人還在執行:不清」。
  - 錄製和判定的拒絕訊息又叫人去用 `--abandon`,兩邊互相指,只能手動刪鎖檔,README 沒有寫這一步。
- **空鎖檔會被當殘留清掉**:鎖是先 `O_EXCL` 建立空檔,再寫 token。這段空窗裡另一個終端跑 `--abandon`,讀到的是「讀不懂」(pid 為 None),就把活著的鎖刪了。
- **兩個 `--abandon` 同時跑**:清殘留鎖「讀、判、刪」不是原子的。兩者都讀到死鎖時,可能刪掉第三個行程剛拿到的新鎖。

後兩者的空窗很窄。

**重現**(scratchpad `sim/sim.py H`):

1. 放一個空的 `.recording.lock`,`--abandon` 結束代碼 0,訊息是「清掉殘留鎖檔(讀不懂)」。
2. 放 `{"pid": 1, …}` 的鎖檔(pid 1 是 launchd,屬於 root),`--abandon` 結束代碼 2,訊息是「主人還在執行」。

**建議修法**:

- 鎖內容先寫進暫存檔,再用 `os.link` 放到鎖的路徑。這樣建鎖一樣是原子的,而且鎖一出現就帶著內容。
- token 加記行程開始時間或開機識別,判斷活著時一起比對。
- 清殘留鎖時,先把鎖檔 `rename` 成唯一名字,再確認內容還是剛讀到的那一份,才刪。
- 拒絕訊息與 README 補上「確定是殘留、但 pid 被重用時」的手動處理步驟。
