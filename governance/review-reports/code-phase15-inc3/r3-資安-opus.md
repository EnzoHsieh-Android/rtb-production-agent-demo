## 沒有發現洞的面向(簡述)

- **即時模式的花費帳路徑**:即時模式帶 `--ledger` 會被閘道拒絕(PoC X4,結束代碼 2、沒送出)。帳本位置從帳號資料庫算,不看 HOME 或任何環境變數,命令列改不到。
- **鎖檔預放、刪除、搶佔**:
  - 預放一個鎖檔,或拿著 flock 不放:只能讓人錄不了。`--abandon` 看 flock 判斷主人還在不在,不會清掉活著的鎖。
  - 刪掉活著的鎖檔再開第二個行程:第二個行程會在送出前,被清單重讀或花費帳查詢擋下(N3b 重跑)。
  - 收尾時 `_still_mine` 會拒絕覆蓋別人記的那筆。
- **快照的 lstat 到 open 之間換檔、硬連結**:
  - `read_regular` 會比 inode、大小和修改時間,讀到的位元組還要跟清單記的雜湊相等。
  - 判定開始之後再換暫存目錄的檔、加子目錄,都不影響結果(PoC X5 照常判定可入庫)。
  - 硬連結只是另一個名字,內容照樣被雜湊綁住,本身沒有可利用之處。

## X1 即時錄製途中按 Ctrl-C,往暫存目錄放一份自己寫的錄製,--abandon 就把它轉成待驗收,判定可入庫,CI 驗收通過

severity: major
blocking: 是
引句:「recording = r.usable_recording(data, attempt)」
查證 file: `src/rtb/eval/rule_mining_eval.py:438`(另見 `:435`、`:440-447`;`src/rtb/eval/rule_mining_recordings.py:387-399`;`src/rtb/modelrecording.py:364`)

**問題**
- `--abandon` 看到暫存目錄裡有「預期鍵、rule_mining、ok、模型與批次相符」的檔,就轉成待驗收,雜湊記的是這一刻讀到的位元組。
- 它沒有核對這份檔是不是這次呼叫產生的:
  - 花費帳裡這個展示編號有沒有已結算、結果 ok 的那一筆;
  - 原價、token 數跟帳上對不對得上;
  - 檔是不是在開始時間之後才寫的。
- 錄製檔沒有簽章。「正式後端錄的」只看檔裡的 `backend` 欄位,所以照任何一份錄製的格式就能自己寫一份。
  - 例如同種子失敗嘗試留下的逾時錄製:鍵、批次、模型都一樣。
- 中斷的方式不必搶時間。Ctrl-C 讓 `KeyboardInterrupt` 往外丟,閘道放掉佔位,鎖也放掉,清單停在呼叫中,暫存目錄是空的,可以慢慢放檔。

**攻擊重現**(PoC `test_x1_abandon_accepts_forged_recording`)
1. 即時錄 `phase15-seed-15001-1`,送出途中按 Ctrl-C。
   - 結果:清單停在呼叫中,暫存目錄空的,沒有鎖檔。
2. 在暫存目錄寫一份 `<清單記的預期鍵>.json`:欄位照一份錄製抄,`text` 換成攻擊者自己寫的建議(PoC 寫的 `confidence_note` 是「攻擊者手寫,不是模型回的」)。
3. 執行 `--abandon --demo-id phase15-seed-15001-1`:
   - 預期:這次沒有經過驗證的模型回覆,應該判成呼叫失敗或拒絕;
   - 實際:結束代碼 0,「暫存目錄已有成功的錄製:轉待驗收」;清單 `status=待驗收`、`outcome=ok`,`files` 綁的是手寫內容的雜湊。
4. `--check-in` 回 0、判定可入庫;照印出的指令手動搬。
5. `--verify` 的驗收行是「15001:通過(已量)」,`manifest_problems == []`,入庫檔的 text 就是手寫的那份。
6. 花費帳裡這個展示編號只有一筆沒結算的預留(`outcome=None`)。機檢沒有任何一條看它。

**影響**
- 報告的「AI 找到的規則」可以整份換成人寫的,入庫、CI 全綠。
- 在送出前的一瞬間中斷,連模型花費都不用。
- 這比 r2 N1 的「挑一次好的」嚴重:錄製不再保證是模型回的。

**建議修法**(擇一,前者最小)
- `--abandon` 一律判成呼叫失敗,不轉待驗收(回到 r2 的行為)。
  - 代價:r2 N2b「kill 之後作廢成功的錄製」會回來。
  - 補法:把「中斷後 abandon」在嘗試表標成獨立的狀態(例如「中斷」),報告明列;`_seed_problems` 把「中斷而且暫存目錄有 ok 錄製」的嘗試當成第一次成功,後面的序號不准入庫。
- 要保留轉待驗收,就要把錄製綁到帳上:
  - 閘道結算時,把回覆文字(或錄製檔)的 SHA-256 寫進花費帳那一筆;
  - `--abandon` 只在帳上有這個展示編號已結算、`ok`、原價與雜湊都跟檔相符時才轉待驗收,其他一律呼叫失敗。

## X6 判定用的「私有」快照目錄,同一個使用者照樣寫得進去:判定途中往 $TMPDIR/rule-mining-judge-* 丟一個檔,好錄製就被記成驗收沒過,可以重抽(N1 換個目錄重現)

severity: major
blocking: 是
引句:「with tempfile.TemporaryDirectory(prefix="rule-mining-judge-") as private:」
查證 file: `src/rtb/eval/rule_mining_eval.py:693`(另見 `:694-696`、`:719-721`、`:705-708`)

**問題**
- 快照目錄是 0700,但攻擊者就是跑判定的那個使用者(r2 的 N1 也是同一個前提)。0700 擋不住他。
- 目錄在 `$TMPDIR` 底下,前綴固定,很好找。
- 快照寫好之後,`_judge_snapshot` 先跑 `prepare()`(約 0.45 秒)才跑 `batch_problems`。這段時間往快照目錄丟一個檔,`batch_problems` 就回報「錄製目錄不是只有這一批的錄製檔」。
- 這是目錄層級的雜音,不是錄製內容的問題,卻被當成「錄製內容沒過」,記成驗收沒過。
- 驗收沒過的嘗試不算第一次成功,所以之後重抽的那次可以入庫,清單機檢全過。

**攻擊重現**(PoC `test_x6_private_snapshot_dir_writable_forces_reject`)
1. 即時錄 `phase15-seed-15002-1`,待驗收。看過暫存目錄裡的回覆,覺得不好看。
2. 開一個終端跑 `while :; do for d in $TMPDIR/rule-mining-judge-*; do touch "$d/notes.txt"; done; done`,再跑 `--check-in --demo-id phase15-seed-15002-1 --recordings-dir <記下的目錄>`:
   - 預期:錄製檔的雜湊等於清單記的,內容沒問題,應該判定通過;就算判定被干擾,也該拒絕(參數或環境錯),清單不動。
   - 實際:結束代碼 1,狀態記成驗收沒過,原因是「錄製目錄裡有不是錄製檔的東西:notes.txt」。暫存錄製檔的雜湊跟清單記的完全一樣。
3. 錄 `-2`,判定、搬檔,結果是可入庫,`manifest_problems == []`。
4. 第 2 到 3 步可以一直重複,挑最好的一次入庫。

**建議修法**
- 快照不要落地。直接把記憶體裡的位元組交給判定:
  - 用一個只接受單一檔的 `batch_problems` 變體,例如直接對位元組呼叫 `validated` 再核對欄位;
  - 重播改用記憶體裡的錄製,或讀完快照立刻驗一次目錄只有那一個檔,之後就不再列目錄。
- 或者:`_judge_snapshot` 回報的任何目錄層級問題(`錄製目錄不是只有這一批`、`錄製鍵集合`、`錄製目錄是空的`)一律丟 `Refused`、清單不動;只有錄製檔本身的欄位不對(呼叫者、結果、模型、批次、失敗類、後端)才准記驗收沒過。
- 另補一條測試:判定途中往快照目錄丟檔,要拒絕、清單不動。

## X3 兩個 checkout 同時開錄,都趕在對方預留之前查完花費帳:同一個展示編號兩次真呼叫,任選一邊入庫

severity: minor
blocking: 否
引句:「stray = [demo for demo in used if (r.demo_parts(demo) or (0, 0))[0] == seed」
查證 file: `src/rtb/eval/rule_mining_eval.py:489`(另見 `:568-574`、`src/rtb/modelclient.py:557`)

**問題**
- 查帳(`_ledger_clean`)到預留(`ledger_db.reserve`)之間沒有鎖。這段時間要建目錄、寫清單、開閘道。
- 「有沒有用過」只比展示編號在不在清單裡,不比次數。所以兩邊用同一個編號,帳上兩筆 `phase15-seed-15001-1`,兩份清單都認得這個編號,查不出來。
- 判定和 `--verify` 都不看帳。r2 建議的「判定時帳上的呼叫數要等於清單的嘗試數」沒有做。

**攻擊重現**(PoC `test_x3_concurrent_checkouts_bypass_ledger_check`)
1. worktree A 和 B 同時開錄 `phase15-seed-15001-1`。
   - 真實世界的做法:用 fswatch 看 A 的暫存目錄一建出來(`_fresh` 就在查帳之後),就 `kill -STOP A`;跑完 B,再 `kill -CONT A`。
2. 第 1 步的結果:
   - 預期:後查帳的那個,應該因為帳上已經有這個編號而拒絕。
   - 實際:兩邊都 ok,後端各被呼叫 1 次;帳上有兩筆同編號的列。
3. 任選一邊判定、入庫,再提交那一邊的清單:只有 1 次嘗試,`manifest_problems == []`。

**影響與限制**
- 要刻意開兩個 checkout,還要掐時間停行程,跟 r2 N3 同級。
- 備註:把 `~/.rtb` 的帳本暫時改名也能讓查帳放行。但那等於連花費上限一起重設,屬於蓄意破壞帳本,不另列。

**建議修法**
- 查帳改成「有這個種子、不在清單裡的編號,或同編號的列數大於清單記的次數,就拒絕」。
- 查帳到預留之間,用帳號家目錄下的一把鎖(或在帳本裡原子地「查無此編號才預留」)包起來。
- `--check-in` 時再查一次帳:這個種子在帳上的規則模式探索呼叫數,要等於清單的嘗試數,否則拒絕判定。

## X2 暫存目錄驗完是空的之後、閘道佔檔名之前放一份錄製:閘道直接讀它(共用重播)、不呼叫模型,記成即時 ok、待驗收,判定可入庫

severity: minor
blocking: 否
引句:「if not (reply.ok and reply.mode == "live"):」
查證 file: `src/rtb/eval/rule_mining_eval.py:535`(另見 `:569`、`src/rtb/modelclient.py:544-546`、`:522-526`)

**問題**
- 閘道佔檔名時發現檔已經在,而且是同一批的完整錄製,就走 `_existing`,回共用重播(`shared=True`)。
- 這時回覆的 `mode` 還是閘道判的 live。`_finished` 只看 `reply.ok and reply.mode == "live"`,沒看回覆來源是不是真的即時呼叫,所以記成待驗收。

**攻擊重現**(PoC `test_x2_preplant_after_fresh_no_model_call`、`test_x2_window`)
1. 即時錄 `phase15-seed-15002-1`。暫存目錄一建出來(`_fresh` 驗完是空的),就放進一份手寫的同批錄製。
2. 第 1 步的結果:
   - 預期:暫存目錄在送出前多了檔,應該拒絕;或者至少這次不能算成即時 ok。
   - 實際:結束代碼 0,狀態待驗收,`outcome=ok`,後端呼叫 0 次,原價 0。
3. `--check-in` 回 0,判定可入庫。

**影響與限制**
- 時間窗只有約 0.8 毫秒(從 `_fresh` 回來到佔檔名),要用 kqueue 或 fswatch 加 SIGSTOP 搶,門檻比 X1 高很多。
- 修掉 X1 之後,這是剩下唯一的偽造路,所以一起列出。

**建議修法**
- `_finished` 要求回覆來源是真的即時呼叫(`source == live`,不是 recorded 或 shared 重播),而且原價大於 0;否則記呼叫失敗。
- 或是即時錄製把 `recordings` 目錄交給閘道之前,閘道自己在鎖內建目錄(`O_EXCL` 建目錄,驗空跟建立之間不留縫)。
