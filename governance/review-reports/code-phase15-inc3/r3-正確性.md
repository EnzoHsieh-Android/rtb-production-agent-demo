## 新發現

### 1. 換評估版本之後,同一本家目錄花費帳裡上一版的呼叫會被當成「清單沒記的呼叫」,新版的每個種子都錄不了
severity: minor
blocking: 否
引句:「stray = [demo for demo in used if (r.demo_parts(demo) or (0, 0))[0] == seed」
查證 file: `src/rtb/eval/rule_mining_eval.py:489`(另見同檔 `:327-328` 的 `LOST`、`src/rtb/eval/rule_mining_recordings.py:257-260` 的 `next_sequence`)

**問題**:三個設計疊在一起,就互相卡住:

- 展示編號只有 `phase15-seed-<種子>-<序號>`,不帶評估版本。
- 新版的入庫目錄是新目錄、新清單,序號又從 1 起。
- `_ledger_clean` 看的卻是跨版本共用的家目錄帳本,而且只按種子過濾。

所以只要 v3 對某個種子送出過任何一次,換成 v4 之後,那個種子的 `phase15-seed-<種子>-1` 在帳本裡已經有,新清單裡卻沒有,錄製就被拒。v4 的清單又不准跳號,命令列沒有出口。

- 這正好把計劃給的唯一出口堵死:第一次成功錄製遺失、或要換批時,程式與 README 都說「須換評估版本」。
- 拒絕訊息寫的是「可能在別的 checkout 錄過」,會把人引到錯的方向。
- 這也跟 Systems 筆記的 WHY 相矛盾:那裡說目錄名綁版本,「就不用在清單裡管跨版本」。
- 附帶:跨版本重用同一個展示編號,也會讓每次展示 1 美元的上限跨版本累加。這是既有的設計,不是這輪才有。

列 minor、不擋的理由:換評估版本本來就要改 `EVAL_VERSION` 並重新過審,現行 v3 的錄製流程不受影響。

**重現**(`sim3r/sim.py ver`):

1. 用入庫目錄 `v3/` 錄 15001-1,結束代碼 0。
2. 同一本 tmp 家目錄帳本,改用入庫目錄 `v4/`(模擬換版後的新目錄與新清單)錄 15001-1:結束代碼 2,訊息是「拒絕開始:花費帳顯示種子 15001 有批次清單沒記的呼叫 ['phase15-seed-15001-1'](可能在別的 checkout 錄過):不送出」。
3. 同一個 `v4/` 錄 15002-1 則是結束代碼 0:只有送出過的種子會被卡住。

**建議修法**:擇一。

- 讓展示編號(或批次編號)帶評估版本,例如 `phase15-v3-seed-15001-1`,帳本查詢只比同版本的。
- 或者清單記下這一版開始的時間,查帳時只看預留時間在那之後的列。

另外在計劃〈換評估版本〉補一句:換版時要一併處理這條跨 checkout 的防線。
