# 架構對齊審查:r1-snapshot.patch(Phase 14 增量 4:調查評估報告改寫)

審查範圍:`src/rtb/eval/investigation_report.py`、`src/rtb/eval/investigation_eval.py` 的改寫,對照鄰居
`src/rtb/eval/scoring.py`、`src/rtb/eval/record.py`、`src/rtb/eval/adoption.py` 既有寫法。只判「跟既有做法

## 問 1:分層與依賴方向

`src/rtb/eval/*.py` 現有的依賴方向是:`record.py`、`scoring.py`、`adoption.py`、`model_candidate.py` 一律
只經 `rtb.analyzer.policy` 拿正式規則的答案,domain 層只用來拿型別(`WorthCell`、`WorthInput`)。調查評估
這條線(`investigation_cases.py`)本來就有例外先例:它直接 `import rtb.domain.nine_rules`,並且已經封裝出
`rule_decision(case)` 這個唯一對外的存取點(含 `worth_input` 失敗時的例外防護、以及 paused/anomaly 提早
判完就不追加四查詢的短路)。這次 diff 在 `investigation_report.py` 另開一條 `from rtb.domain import
nine_rules as rules` 的新依賴,自己直接呼叫 `rules.decide(...)`,繞過了 `investigation_cases.rule_decision`
這個既有存取點——細節見問 3。

## 問 2:命名與錯誤處理

新增的 `CaseRun.no_answer`(`investigation_report.py`)把「沒有有效答案」的原因,混合了三種構造:
①原樣的 fallback 代碼字面值(`off_menu`、`timeout`,跟既有 `CellStats.fallbacks` 同一套);
②新湊的前綴字串 `f"preflight:{self.preflight}"`;③常數 `NO_CONCLUSION = "no_conclusion"`。鄰居模組對「沒
量、缺原因」一律用單一固定字面常數(如 `record.py` 的 `NOT_INTRODUCED = "未導入"`、`adoption.py` 的
`Measure.not_measured(reason)` 只收一個 reason 字串,不會有些是純代碼、有些是加前綴的組字串)。這裡三種
構造混在同一個欄位、同一個 `Counter` 分組裡顯示,跟既有「原因就是一個扁平字串」的寫法不完全一致,但沒
有既有反例能直接判它錯——列為 minor、判不準。

### 發現 1:另寫一套「案例 → 九條判斷」的存取路徑,繞開既有的 `rule_decision`
severity: major
blocking: 是

`investigation_cases.py` 已經有 `rule_decision(case) -> rules.RuleDecision`(`src/rtb/eval/
investigation_cases.py:158-166`),是這個評估集裡「案例過九條判斷」的唯一封裝:先擋 `worth_input` 可能丟的
`KeyError`/`TypeError`/`ValueError`,再判斷 paused/anomaly 是否已經用基本資料判完(判完就不追加四查詢的
`rule_evidence`)。`investigation_report.py` 已經在 import 這個模組的 `rule_evidence`、`worth_input`
(`src/rtb/eval/investigation_report.py:45` 一帶),但新加的 `rule_reason` 沒有呼叫 `rule_decision`,而是自
己重新 `import rtb.domain.nine_rules`、自己重新組一次一模一樣的呼叫:

引句:「同一次九條判斷的細因(命中的格,或九格之外的證據不足原因與查詢代碼):派生否決列的否決原因。」

file: `src/rtb/eval/investigation_report.py:34`(新增 `from rtb.domain import nine_rules as rules`)

rule_evidence(case), NOW)`,略過 `rule_decision` 的例外防護與 paused/anomaly 短路)
