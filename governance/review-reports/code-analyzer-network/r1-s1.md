### 1. S43:dsp_client 兩個 `_get` 之間「先成功後失敗」的情境完全沒有測試覆蓋到

severity: minor
blocking: 否 理由:程式本身沒有殘留副作用(見下方分析),純屬測試覆蓋的缺口,不是行為錯誤。
引句:「state = _get(base_url, f"/campaigns/{task.campaign_id}", timeout_seconds)」

`dsp_client.fetch()` 依序呼叫兩次 `_get`:先讀 campaign state,再讀 metrics。S43 條款與這次審查特別點名要看的,是「第一個成功、第二個失敗」時有沒有殘留副作用。從程式碼看,`dsp_client.py` 完全不碰 `TaskStore`,兩次 `_get` 之間只是本地變數,函式一路往外丟例外時沒有任何持久化寫入——這件事本身是對的。

但 `tests/analyzer/test_dsp_client.py` 裡對應 S43 的兩個測試都不是這個情境:
- `test_a_nonexistent_campaign_makes_the_whole_call_raise`:campaign_id="ghost",**第一個** `_get`(讀 state)就先炸(`CampaignNotFound` → 404),第二個 `_get` 根本沒機會執行。
- `test_the_dsp_being_unreachable_makes_the_whole_call_raise`:整台主機打不通,兩次呼叫都會失敗,一樣沒有區分順序。

實際上 DSP 端本來就存在「campaign 存在但 metrics 沒 seed」的合法情境(`CampaignStore.get_metrics` 在查無資料時丟 `MetricsNotFound`,見 file: `src/rtb/dsp/store.py:217`-`218`),可以直接拿來寫一個「state 成功、metrics 失敗」的測試,但這次 patch 沒有補上。條款文字「不回傳只含一部分的結果」在程式行為上成立,但測試從未真正逼出這個排列組合,屬於覆蓋缺口。

### 3. S46/S46a:409 錯誤代碼分類窮盡性核對——clean

severity: clean

核對方式:列出收件口 `InboxRejected` 的全部子類別與各自的 HTTP 狀態碼(file: `src/rtb/executor/inbox_server.py:45`-`54`,`src/rtb/executor/inbox_store.py:54`-`93`),confirm 409 只對應三種代碼——`content_conflict`、`revision_out_of_order`、`too_many_revisions`——沒有第四種。再對照 `inbox_client.py` 的 `_handle_rejection`:

引句:「if code == "too_many_revisions": raise SubmitRejectedPermanently(str(code))」

三種 409 代碼全部被 `inbox_client._handle_rejection` 涵蓋(`too_many_revisions` → `SubmitRejectedPermanently`,其餘兩種在 `_STALE_CODES` → `SubmitStale`),沒有漏網的 409 代碼。萬一未來收件口新增第四種 409 代碼卻忘了同步 `inbox_client.py`,會落進 `raise RuntimeError(...)` 這一支,被 `flow.py` 既有的「未定義例外視為可重試」接住(當成暫時性、無限重試),而不是誤判成 `SubmitStale` 或漏掉——這正是 S48/設計文件「其他狀態碼或連線失敗一律讓例外原樣往外傳」講好的行為,不是這次 patch 的疏漏。目前的三個 409 代碼本身是窮盡的,S46b(FAILED 轉換合法性)也用 `task_state.py` 的轉換表核對過,`PROPOSED → FAILED` 是自動附加的合法轉換(file: `src/rtb/domain/task_state.py:51`),沒有問題。

### 4. policy.py 的 `has_delivery` 判斷沒有排除布林值,跟 domain 既有慣例不一致

severity: minor
blocking: 否 理由:目前 DSP 只會回傳真正的整數 impressions/clicks,這條路徑在現有資料來源下打不到,是防禦性一致性問題,不是已知會發生的錯誤行為。
引句:「isinstance(impressions, int | float) and isinstance(clicks, int | float)」

`rtb.domain._checks.is_plain_number` 特地把 `bool` 排除在外(因為 Python 的 `True`/`False` 也是 `int` 的子類別),`pacing()` 用的正是這個函式來擋掉 bool 型別的 spend/budget。但 `policy.py` 自己手寫的 `has_delivery` 判斷用的是原生 `isinstance(x, int | float)`,不會排除 bool——如果 metrics payload 裡 `impressions`/`clicks` 是 `True`(等於 1),`has_delivery` 會誤判為「有在投放」。目前 DSP 的 metrics 表欄位是 SQLite `INTEGER`,序列化出來不會是 bool,所以這條路徑在現有資料流下摸不到,列為 minor 而非 major。

### 5. `Evidence.payload` 的型別守門沒有擋 NaN/Infinity,實際上是靠 dsp_client 的 hash 步驟順便擋下

severity: minor
blocking: 否 理由:實際生產路徑(dsp_client)因為呼叫順序關係不會讓 NaN 進到 Evidence,是 Evidence 這個型別自己的守門不夠嚴謹,不是目前會被觸發的錯誤。
引句:「isinstance(item, str | int | float | bool)」

`evidence.py` 新增的 `_is_payload` 只檢查型別跟項目數上限,沒有排除 `float("nan")` 或 `float("inf")`(`isinstance(nan, float)` 是 `True`,一樣會通過)。而 `dsp_client._content_hash` 用的是 `json.dumps(..., allow_nan=False)`,真的遇到 NaN 會在雜湊步驟就丟 `ValueError`,而且雜湊計算的時機剛好排在 `Evidence(...)` 建構之前,所以走 `dsp_client` 這條路徑不會真的把 NaN 存進 `Evidence.payload`。但這只是巧合順序擋下,`Evidence` 這個型別本身的不變量沒有真正涵蓋「payload 必須是合法 JSON 數字」這件事——任何繞過 `dsp_client`、直接建構 `Evidence` 的呼叫端(測試以外的未來程式碼)都能夾帶 NaN,寫進 `task_store.py` 的 `payload_json` 欄位時也沒有 `allow_nan=False`(file: `src/rtb/analyzer/task_store.py` 的 `commit_step`,`json.dumps(dict(item.payload), sort_keys=True, ensure_ascii=True)` 這行沒帶 `allow_nan=False`),會把不合法 JSON 的 `NaN` 字面值寫進資料庫。
