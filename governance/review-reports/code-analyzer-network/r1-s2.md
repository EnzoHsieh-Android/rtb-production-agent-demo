### 1. dsp_client.py 自己承諾的「不吞、不回傳半套」契約,完全沒有測試會咬到違反它的變異

severity: major
blocking: 是 這是模組自己文件化的核心資料完整性契約(餵給自動調預算決策的證據來源),不是
單純觀感問題;變異證實現有測試套件(`test_dsp_client.py` + `test_boundaries.py` 全跑)對這個
契約被破壞完全沒有反應,回歸會無聲溜過。
引句:「任一個失敗(逾時、連線失敗、4xx/5xx)整個函式往外丟例外,」

驗證方式:把 `fetch()` 裡抓 metrics 的呼叫包一層 `try/except DspRequestFailed: metrics = {}`
(模擬「拿掉兩階段失敗檢查、吞掉第二個端點的失敗」),`tests/analyzer/test_dsp_client.py`
9 個、`tests/analyzer/test_boundaries.py` 相關測試全部維持綠燈(`9 passed in 0.31s`)。
另外把 `_get()` 裡 `if status != 200: raise DspRequestFailed(...)` 整段拿掉,或改成
`if status >= 500:`(4xx 不再視為失敗),同樣全綠(各 `6 passed`)。

現有測試(`test_a_nonexistent_campaign_makes_the_whole_call_raise`、
`test_the_dsp_being_unreachable_makes_the_whole_call_raise`)之所以測不出來,是因為 DSP 對
不存在的廣告回 `{"error": "campaign_not_found"}`(無 `version` 欄位),拿掉狀態碼檢查後,
程式改成把這個錯誤 body 直接當成 `state` 用,執行到 `state["version"]` 才意外炸出
`KeyError`——測試只驗證「有丟例外」(見 finding 2),剛好被這個意外的 `KeyError` 頂過去,不是
因為狀態碼判斷真的被驗證到。而「state 成功、metrics 失敗」這個情境(兩階段檢查真正要防的
案例)完全沒有測試覆蓋:目前所有 fixture 的 campaign 一律同時 seed 了 state 與 metrics
(`store.seed_campaign(...)` 後緊接 `store.seed_metrics(...)`),沒有任何測試建一個「有現況、
沒有 1h 指標」的廣告來驗證第二個端點失敗時整包 evidence 不能悄悄回傳。metrics 端點缺資料時
DSP 會回 404 `metrics_not_found`(`src/rtb/dsp/store.py:210` 起的 `get_metrics`、`ERROR_TABLE`
裡的 `MetricsNotFound: (404, "metrics_not_found", False)`),這條路徑目前程式碼是對的(有檢查
第二個端點的狀態碼),但完全沒有測試守著它,回歸風險是真的。

（下游 `policy.decide()` 今天恰好會把空 payload 當成 `MISSING_DATA` 而安全地回 `NoAction`,
`flow.py` 的 evidence-collection 步驟也對任何例外一視同仁地重試,見
`src/rtb/analyzer/flow.py:146`——這讓「吞掉第二階段失敗」今天不會立刻造成錯誤決策,但那是
下游剛好夠保守,不是這支檔案自己守住了它文件裡寫的契約;之後任何一個新的 EvidenceSource
或 policy 邏輯若少了同樣的保守判斷,這個洞就會被踩到。）

### 2. `test_a_nonexistent_campaign_makes_the_whole_call_raise` 用泛用 `Exception` 斷言,測不出真正該驗的 `DspRequestFailed`

severity: minor
blocking: 否 這是測試斷言力道不夠的問題,不是程式本身現在的行為錯誤——目前程式碼對
「廣告不存在」正確地丟 `DspRequestFailed`,只是測試驗不到「丟的是哪一種」。
引句:「pytest.raises(Exception):  # noqa: B017 - 只驗證會整個丟例外,不驗證是哪一種」

跟 finding 1 是同一組變異暴露出來的:因為斷言只檢查「有沒有丟例外」,不檢查型別,
finding 1 提到的 `KeyError` 意外路徑才能瞞過測試。`test_the_dsp_being_unreachable_...`
用同樣寫法是合理的(連線失敗的例外型別本來就不受這支檔案控制),但「廣告不存在」是
`_get()` 自己判斷、自己丟 `DspRequestFailed` 的情境,應該可以也應該去驗證
`pytest.raises(dsp_client.DspRequestFailed)`,現在沒有驗證,等於這條映射邏輯本身沒有專屬測試。

### 5. `Evidence.payload` 驗證沒有擋 NaN/Infinity,跟同檔案其他數值驗證的做法不一致

severity: minor
blocking: 否 目前兩個實際呼叫端(`dsp_client._content_hash` 用 `allow_nan=False`、
`policy.py` 透過 `pacing()` 的 `math.isfinite` 防護)都剛好擋下這個情況,今天不會造成錯誤
決策或明顯資料損壞,但網域層自己的驗證邊界本身有洞,且完全沒有測試涵蓋。
引句:「isinstance(key, str) and (item is None or isinstance(item, str | int | float | bool))」

在複本上直接呼叫 `Evidence(...)`,`payload=MappingProxyType({"budget": float("nan"), "inf":
float("inf")})` 可以成功建構(不丟 `ValueError`);接著模擬 `TaskStore.commit_step` 存入時
用的 `json.dumps(dict(item.payload), sort_keys=True, ensure_ascii=True)`(沒有
`allow_nan=False`),會把 `NaN`、`Infinity` 這種不是合法 JSON 的字面值寫進
`payload_json` 欄位,`json.loads` 讀回來又能還原(Python 兩端都用同一套非標準擴充語法掩蓋
了問題,但欄位型別命名為 `PayloadValue`、測試名稱也自稱「json safe primitives」——見
`tests/domain/test_evidence.py::test_payload_values_must_be_json_safe_primitives_not_nested_containers`
——實際上沒有真的做到 JSON-safe)。同一支檔案裡 `_is_positive_finite`
(`src/rtb/domain/evidence.py:98,102`)已經在用 `math.isfinite`,`_is_payload` 沒有比照辦理,
是遺漏而非刻意設計;`tests/domain/test_evidence.py` 目前也沒有任何 NaN/Infinity 的測項。

### 6. `test_boundaries.py` 的 S52 測試把兩個伺服器的建構放在 `try` 外面,第二個建構失敗時第一個伺服器的 socket 不會被關

severity: minor
blocking: 否 需要 `InboxServer(...)` 建構本身丟例外才會觸發,以目前傳入的固定參數
(`max_pending=4, fault_injection=False`)幾乎不會發生,屬於低機率的資源清理疏漏,不是
會經常發生的不穩定來源。
引句:「inbox = InboxServer(tmp_path / "inbox.db", max_pending=4, fault_injection=False)」

`test_the_agent_cannot_reach_fault_injection_on_production_style_servers` 依序建構
`dsp = DspServer(...)`、`inbox = InboxServer(...)`,兩個 `threading.Thread(...).start()`,
之後才進 `try: ... finally: dsp.shutdown(); dsp.server_close(); inbox.shutdown();
inbox.server_close()`。`KitServer.__init__` 在建構當下就已經 `bind()`+`listen()`
(`src/rtb/httpkit.py:56` 的 `super().__init__((host, 0), handler_class)`),所以如果
`InboxServer(...)` 建構或任一個 `.start()` 丟例外,`dsp` 已開的監聽 socket 不會經過
`finally` 被關掉,要等 Python GC 回收才會釋放。跟 `test_dsp_client.py` 用 pytest fixture
(`yield` + `finally` 等效的 teardown)的寫法比,`test_boundaries.py` 這裡把兩個外部資源的
建構都放在保護傘外面,兩個都要成功才安全。

**逾時、埠衝突的風險另外查證為乾淨**:`KitServer.__init__` 一律綁 `(host, 0)`
(`src/rtb/httpkit.py:56`),由作業系統配埠,不會有測試之間搶同一個固定埠的問題;
`ThreadingHTTPServer` + `daemon_threads = True` + `serve_forever`/`shutdown`/`server_close`
是這個專案既有的標準組合(`test_dsp_client.py`、`test_httpclient.py` 的 fixture 都用同一套),
沒有額外風險。`hang_seconds=0.2` 只有在 `fault_injection=True` 且真的送 `X-Fault` 標頭時才會
觸發睡眠(`src/rtb/httpkit.py:196-197` 的 `if not self.server.fault_injection: raise
RequestRejected(400, "fault_injection_disabled")`),`test_boundaries.py` 兩個測試都明確把
`fault_injection=False`,不會被這個參數拖慢或卡住。
