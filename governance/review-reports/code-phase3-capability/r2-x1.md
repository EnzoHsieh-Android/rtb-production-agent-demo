severity: major

### 1. 金鑰檢查仍不是第一關，時鐘會先被讀取

severity: major  
blocking: 是 修正只延後了憑證標頭，仍違反固定驗證順序；時鐘異常會掩蓋「沒有可用金鑰」，回傳錯誤的 500。  
引句:「claims = verified_claims(lambda: self.single_header(CAPABILITY_HEADER),」

Python 會先求值所有引數，因此下一行的 `int(self.server.clock())` 仍在 `verified_claims()` 檢查金鑰前執行。這代表原本的引數求值問題只修了一半。

file: `docs/rtb-production-agent-demo-knowledge/Systems/Mock-DSP.md:17`

實際重現：

- 輸入：`capability_key=None`，時鐘函式拋出 `RuntimeError("clock unavailable")`。
- 實際：`RuntimeError`；HTTP 路徑會落到未預期例外並回 500。
- 預期：第一關直接拋 `CapabilityNotConfigured`，回 503 `capability_not_configured`，完全不讀時鐘。

實跑輸出：

```text
actual_exception= RuntimeError clock unavailable
events= ['clock-read']
expected_exception= CapabilityNotConfigured
```

修正方向是把「取得現在時間」也延後到 `verified_claims()` 內，且放在金鑰、標頭、格式、簽章及聲明型別之後；或把金鑰檢查移到呼叫端、所有其他引數求值之前。

### 2. 共用整數檢查的測試只禁止舊函式名稱，重複實作仍會假綠

severity: major  
blocking: 是 判準明列「讓測試能用弱寫法通過」屬 major；此測試無法證明 DSP 兩個模組真的共用同一份檢查。  
引句:「assert not hasattr(dsp_capability, "_plain_int")」

測試只確認 `_plain_int` 這個舊名稱不存在。作者只要把相同邏輯改名為 `is_plain_int` 或 `_integer_check` 並留在 `capability.py`，就能完全繞過測試；行為測試也會因重複實作暫時相同而全綠。

實際以等價的本地重複函式取代 `dsp_capability.is_plain_int`，再直接執行新增守衛：

```text
guard_result=PASS
uses_shared_function= False
duplicate_name_present= False
```

- 輸入：`capability.py` 使用自己定義、語意暫時相同的整數檢查，且沒有名為 `_plain_int` 的屬性。
- 實際：新增測試通過。
- 預期：既然測試聲稱守護「DSP 內共用一份」，只要 `dsp_capability.is_plain_int is not store.is_plain_int` 就應失敗。

應直接斷言兩個模組使用同一個函式物件，或用原始碼／AST 守衛禁止 `capability.py` 再定義整數型別判斷。
