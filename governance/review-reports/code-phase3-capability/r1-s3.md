severity: major

### 1. 驗證憑證的「金鑰已設定」檢查會被引數求值順序繞過,duplicate header 邊界案例回錯代碼
severity: major
blocking: 是 這條「順序固定」是計劃增量 2、過三輪設計審的合約(Mock-DSP.md RULE 明講「金鑰已設定 → 標頭存在 → …」),實作沒有照這個順序執行,在特定輸入下會回傳錯誤的錯誤代碼,屬於「做出錯的行為 / 破壞計劃裡的合約」。
引句:「claims = verified_claims(self.single_header(CAPABILITY_HEADER),」

說明:`_authorized_write`(`src/rtb/dsp/server.py`)呼叫 `verified_claims(self.single_header(CAPABILITY_HEADER), self.server.capability_key, int(self.server.clock()))`。Python 對函式呼叫的引數是先求值再進函式本體,所以 `self.single_header(CAPABILITY_HEADER)` 會在 `verified_claims` 內部「金鑰已設定」那一行檢查之前先執行。而 `single_header` 對同名標頭出現兩次以上會直接丟 `RequestRejected(400, "duplicate_header")`。結果是:當 DSP 完全沒有設定金鑰(`capability_key=None`,應該所有寫入一律 503 `capability_not_configured`),但客戶端剛好送了兩個 `X-Capability` 標頭時,實際回的是 `400 duplicate_header`,不是文件與合約(對應 `docs/rtb-production-agent-demo-knowledge/Systems/Mock-DSP.md` 新增的 RULE:「順序固定:金鑰已設定 → 標頭存在 → 格式與簽章 → …」)所保證的順序與代碼。

實測重現(在 `/Users/enzo/rtb-production-agent-demo` 用 `.venv/bin/python`,`PYTHONPATH=src`,起一個 `capability_key=None` 的 `DspServer`,用原始 socket 手動送兩個 `X-Capability` 標頭到 `POST /campaigns/c1/budget`):

輸入:金鑰未設定的 DSP + 請求帶兩個 `X-Capability` 標頭(值隨意,例如 `aaa`、`bbb`)
實際輸出:
```
HTTP/1.0 400 Bad Request
{"error": "duplicate_header", "retryable": false}
```
預期輸出(依文件順序,金鑰未設定應該先被擋下):
```
503 {"error": "capability_not_configured", "retryable": false}
```
對照組(同一個未設定金鑰的 DSP,只送 0 或 1 個 `X-Capability` 標頭)實測確實回 `503 capability_not_configured`,證明問題只出在「標頭重複」這個分支搶先於「金鑰已設定」判斷之前執行。

影響:寫入本身仍然被正確拒絕(不會被誤放行、不會資料損壞),但錯誤代碼分類錯了——維運或呼叫端若靠代碼分辨「DSP 完全沒配好金鑰」(整條寫入路徑全面中斷、該找人裝金鑰)跟「請求格式錯誤」,在這個邊界情境會誤判成後者,掩蓋掉更嚴重的設定問題;同時也直接違反了合約裡明寫、過三輪審查的固定順序。

修法方向(僅供參考,不代表已驗證是唯一解):把 `self.single_header(CAPABILITY_HEADER)` 的呼叫移進 `verified_claims` 內部、放在「金鑰已設定」檢查之後,而不是當成呼叫端的引數提前求值。
