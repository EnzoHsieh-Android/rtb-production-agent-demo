severity: major

### 1. 執行行程簽發器讀租戶設定檔時,若設定檔路徑是具名管道(FIFO),會永久掛住而不是依合約拒絕簽發

severity: major
blocking: 是 因為它違反 RULE/[S29] 明白承諾的行為(「設定檔讀不到或格式不對…簽發函式應拒絕簽發」);FIFO 情況下函式既不簽發也不拒絕,永遠不回傳(掛住整個呼叫端執行緒),不是效能或風格問題,是函式沒能履行「一定會回應」這個合約
引句:「os.open(path.name, os.O_RDONLY | os.O_NOFOLLOW, dir_fd=dir_fd)」

說明:`src/rtb/executor/capability_signer.py` 的 `_read_config_securely()` 開設定檔本身時只加了 `O_NOFOLLOW`(擋符號連結),沒加 `O_NONBLOCK`。POSIX 對 FIFO 的規則是:用 `O_RDONLY`(不含 `O_NONBLOCK`)開啟一個目前沒有任何行程以寫入模式開著的具名管道,`open()` 會一直阻塞到有人用寫入模式打開它為止。目錄的那段有刻意帶 `O_DIRECTORY`,所以路徑若是 FIFO/一般檔以外的東西會立刻失敗(已驗證,見下);但檔案本身那段沒有等效防線。一旦設定檔路徑(或曾經是設定檔的路徑,例如清檔重建時中間被換成 FIFO)變成具名管道,`_read_config_securely` → `load_tenants` → `CapabilitySigner.sign()` 這條呼叫鏈會卡死,不丟例外、不逾時、不回傳,和文件裡「權限設錯」「符號連結」「擁有者不對」等其他異常一視同仁地被「拒絕簽發」的承諾不符——這裡連拒絕都做不到。因為每筆寫入都要重新呼叫 `sign()`(RULE:「租戶設定每次簽發都重讀」),一旦命中就會卡住呼叫端,且目前程式庫裡沒有任何呼叫處對這段加逾時保護。

實際重現(在臨時目錄跑,未動專案檔案):

```python
# /private/tmp/.../scratchpad/fifo-test/run.py

sys.path.insert(0, "/Users/enzo/rtb-production-agent-demo/src")

```


這證明目錄有被 `stat.S_ISREG` 擋下,唯獨 FIFO 這種「open 本身就會阻塞」的特殊檔案沒被擋到,兩者行為不一致,確認缺口就在 `O_NONBLOCK` 沒加上,而不是別的地方。

補充:`tests/executor/test_capability_signer.py` 目前只測了符號連結、擁有者、目錄與檔案的可寫權限(見 `test_a_symlinked_config_is_refused`、`test_a_config_owned_by_someone_else_is_refused`、`test_a_config_file_writable_by_others_is_refused`、`test_a_config_in_a_directory_writable_by_others_is_refused`),沒有任何一支測到「路徑不是一般檔案」這類會在 `open()` 本身卡住的情形,所以 S29「設定檔讀不到或格式不對應拒絕簽發」這條合約在 FIFO 這個子情境下沒有防回歸測試守著。

file: `src/rtb/executor/capability_signer.py:817-819`(`_read_config_securely` 開檔那段)、`src/rtb/executor/capability_signer.py:768-771`(`load_tenants`/`sign` 呼叫鏈)

修法方向(供作者參考,不算本次發現範圍):開檔時加 `os.O_NONBLOCK`,拿到 fd 後用 `stat.S_ISREG` 檢查、非一般檔案就直接 `SigningRefused`,再視需要 `os.set_blocking(fd, True)` 恢復成阻塞讀取;這樣可以在不放寬符號連結防線的前提下,把「非一般檔案」全部擋在 open 階段就地失敗,不會卡住。
