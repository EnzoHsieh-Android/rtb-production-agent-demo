審查鏡頭:邊界與輸入。方法:把工作樹複製到臨時目錄(工作樹的 `inbox_store.py` 與 patch 內容經 diff 確認一致),起真的伺服器用 http.client 實送請求。

### 1. 解析器接受的極端時間讓內容雜湊丟 OverflowError,呼叫者收到永久 500
severity: major
blocking: 是 解析器認為合法的提案無法被收下也無法乾淨拒收,回 500 且 retryable=false,違反「錯誤只回固定代碼」的合約,且任何呼叫者可穩定觸發
引句:「moment = getattr(proposal, field).astimezone(UTC)」
實測:`decision_expires_at="9999-12-31T23:00:00-05:00"`(換成 UTC 是 10000 年)回 500 internal_error;`decision_created_at="0001-01-01T00:00:00+05:00"` 加上 expires `0001-01-01T01:00:00+05:00`(換成 UTC 是 0 年)同樣 500。伺服器印出 `OverflowError: date value out of range`,堆疊起點在 content_hash(在 `accept` 的交易內,已回滾,無資料損壞)。原因:`parse_proposal` 只要求帶時區與 expires 晚於 created,沒限制年份範圍,而 `astimezone(UTC)` 在日期範圍邊緣會溢位。建議在解析器或 content_hash 前限制年份範圍(或捕捉 OverflowError 轉成 invalid_proposal),並補測試樣本進 `REJECTED_OVERRIDES`。
查證: 解析時間處 `src/rtb/domain/proposal.py:105`

### 2. max_pending 為 0 或負數時伺服器照常啟動,但所有新提案永遠回可重試的 503
severity: minor
blocking: 否 只影響錯誤設定的營運者,不會損資料;但錯誤訊號誤導呼叫者無限重試
引句:「parser.add_argument("--max-pending", type=int, default=DEFAULT_MAX_PENDING)」
實測:max_pending=0 與 -1 時,第一份新提案 503 `inbox_full` retryable=true,同任務的修訂序號 2 回 409(因為序號 1 從未被收下),整個收件口等於全關。`main` 已有 `except ValueError` 做「拒絕啟動」,卻沒有對 max_pending 做驗證。建議 <1 直接拒絕啟動。
查證: `main` 的啟動檢查 `src/rtb/executor/inbox_server.py:386`(patch 內 ValueError 只來自 host 檢查)

### 3. 重送一份已過期的提案回 200 且 status 仍是 "accepted"
severity: minor
blocking: 否 狀態欄位有寫 expired,呼叫者若看 state 可判斷;但只看狀態碼或 status 的分析行程會誤以為提案仍有效
引句:「return Accepted(proposal.task_id, proposal.revision, existing[1], digest, True)」
實測:提案在剛好到期的時刻重送,回 200 `{"status":"accepted","state":"expired"}`。重送分支不看提案已不再有效,也沒有回 422。這與新提案「過期回 422」不一致,契約應明確寫出(或重送過期/已被取代者回不同 status)。

### 4. 無效請求每次都寫事件,可用來沖掉有價值的事件紀錄
severity: minor
blocking: 否 事件紀錄本就是盡力而為且文件已標註沒有速率限制,但 1000 筆上限會被垃圾請求輪替掉衝突與滿載的事件
引句:「store.record_event("invalid_proposal", None, self.server.clock())」
實測:連續送 3 個無效請求產生 3 筆 `invalid_proposal` 事件(task_id/hash 皆空,不含請求內容)。因為無任何認證,一個迴圈就能在 1000 筆內把先前的 `content_conflict`、`revision_out_of_order` 記錄全部擠掉,失去事後追查價值。建議無效事件合併計數或另設較小的上限。
