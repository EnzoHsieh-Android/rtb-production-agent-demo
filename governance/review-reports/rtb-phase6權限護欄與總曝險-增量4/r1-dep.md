severity: major

## F1 查詢五(總曝險稽核明細)沒有按種類過濾,會混進表滿延後、增量3後再混進比例過大

severity: major
blocking: 是 — 照字面實作,查詢五會把「表滿延後」(甚至增量 3 之後的「比例過大」)跟「總曝險已滿」混在同一份「總曝險稽核明細」裡,答錯 F7 要的「哪些被阻擋」。

引句:「停下紀錄表這個租戶在範圍內的每一列(種類、任務、修訂、廣告、金額、當時已用、當時門檻、時間)」

停下紀錄表(`write_stops`)目前有兩種 `kind`:`AGGREGATE_LIMIT_REACHED`(總曝險已滿)與 `TABLE_FULL`(表滿延後),查詢一(總曝險停下次數)明確只算「種類是總曝險已滿」的列(見 [S360]、也見查詢一本文「這是「被停下的次數」…不在這支裡分」那句只是在講停下 vs 最後結果,不是在講種類);但查詢五的設計文字與合約 [S367] 都只寫「這個租戶在範圍內的每一列」,沒有任何 `kind` 過濾。實測 `write_stops` 建表語句(`inbox_store.py:153-158`,`StopKind` 定義在同檔 94-98)確認表裡本來就會混著總曝險已滿與表滿延後兩種列。已在 `phase6-inc2-impl` 分支(`git grep budget_increase_too_large / write_stop`)確認增量 2 的比例上限擋下目前完全不寫 `write_stops`,所以查詢五「暫時」只混到表滿延後;但增量 3 第 1 版已經寫明可核可的兩種擋法(總曝險已滿、比例過大)進「待核可」時都「同時照增量 1 寫一列停下紀錄」(本節第 321 行引述的主線轉達,第 2 版會替 `write_stops` 加上「比例過大」種類)。增量 3 一併,查詢五會再混進比例過大的列,而查詢五的名字與 F7 完成條件(「稽核可說明哪些通過、哪些被阻擋及剩餘額度」)明確是在講總曝險,不是護欄比例或排隊延後。這個增量 4 節既有查詢一、查詢二把兩種種類分開列的先例,查詢五卻沒有比照,是本節內部前後矛盾。綁定測試 [S365]/[S367] 的情境只用到總曝險已滿一種,測不出這個混淆。
建議:查詢五明確加 `kind = 總曝險已滿` 的過濾(比照查詢一),或者在完成前先把「增量 2 的比例擋下、表滿延後要不要進總曝險稽核明細」列成待使用者裁定的分岔,而不是預設全收。

## F2 查詢三「已核可放行數」的租戶/廣告篩選,增量 3 目前的欄位撐不住

severity: major
blocking: 是 — 現有 [S355] 定義的核可稽核欄位裡沒有任務、修訂、廣告,查詢三卻假設可以直接依廣告篩「核可使用表」,字面實作會做不出來或答錯。

引句:「已核可放行數:核可使用表(增量 3 第 2 版,帶租戶)的列數,可給時間範圍與租戶、廣告篩。」

增量 3 第 1 版的合約 [S355] 是:「當核可生效,執行端應在同一個交易裡寫一列核可稽核(核可編號、核可人、放行金額、當時已用額度與門檻)。」——沒有任務、修訂、廣告欄位。主線轉達給增量 4 的第 2 版變更(本節 321 行:「停下紀錄加「比例過大」種類、核可使用表帶租戶欄」)只承諾補租戶欄,沒有提到廣告欄或任務/修訂欄。查詢三的「待核可數」那一段已經示範了正確做法——收件表沒有租戶欄,就「用任務、修訂、內容雜湊接到停下紀錄那一列…取租戶與廣告」;但「已核可放行數」那一段沒有寫同樣的 join 方法,語氣上直接假設核可使用表本身就能篩廣告。若增量 3 第 2 版真的只加租戶欄(如主線轉達的範圍),查詢三的廣告篩選這部分做不出來;若要靠 join 停下紀錄表做到,核可使用表至少要多帶任務與修訂(或雜湊)才能 join,這一條增量 4 沒有寫進去,增量 3 第 2 版的設計者也看不到這個需求。
建議:把「已核可放行數」的廣告篩選方法明寫成跟「待核可數」一樣的 join(核可使用表補任務、修訂),或者把「增量 3 第 2 版要補的欄位」清單同步加上任務、修訂(甚至廣告本身),別只停在「帶租戶」。

## F3(次要,關聯發現)查詢五「通過的」清單未比照 aggregate_used 把舊資料(租戶為空)算進每個租戶

severity: major
blocking: 是 — 查詢四的「已用」與查詢五的「通過的」清單若一個算進舊資料、一個不算,稽核對不上帳,直接違反 F7「稽核可說明…剩餘額度」。

引句:「通過的:嘗試紀錄裡這個租戶、第一列開始時間在範圍內、帶預留金額的每一把鍵(冪等鍵、廣告、預留金額、開始時間、目前狀態),依時間排序。」

`attempt_store.aggregate_used`(`src/rtb/executor/attempt_store.py:355-372`)算「已用」時,對 Phase 6 之前沒有租戶的舊列是 `(f.tenant = ? OR f.tenant IS NULL)`——保守地把每一筆舊列都算進「每一個租戶」的已用額度(增量 1 設計「舊資料(第 3 版改寫)」一節也明講「租戶不知道 → 算進每一個租戶的已用額度」)。查詢五「通過的」清單卻只寫「這個租戶」,沒有提到舊列(租戶為空)也要一起列出。若字面實作只用 `tenant = ?` 過濾嘗試紀錄,遇到升級後 24 小時內還沒出窗的舊列,查詢四回報的「已用」會比查詢五「通過的」清單加總要高,稽核者看不出那筆差額是哪裡來的(既不在「被停下的」也不在「通過的」清單裡)——這正是 F7 要求「稽核可說明哪些通過…及剩餘額度」要解決的問題,增量 1 的實務隱患也已經承認「升級後多擋」但沒接到查詢五要不要把這類舊列一併列出。
建議:查詢五「通過的」明寫比照 `aggregate_used` 的口徑(`tenant = ? OR tenant IS NULL`),或者在查詢五旁邊補一句解釋「已用與通過清單之間可能有舊資料造成的差額,不在清單裡」,免得稽核者誤以為清單窮盡了已用額度的來源。

## 已核對、沒有問題的部分

- **查詢一的「停下」與「最後結果」不會混**:本節已經在查詢一定義裡明講「這是「被停下的次數」,增量 3 之後其中有些會進待核可、之後被核可放行,最後結果看查詢三;不在這支裡分」,並且 [S360] 只鎖種類是總曝險已滿的列數,不涉及後續是否被核可放行。字面實作不會把「進待核可」跟「最終被擋」混為一談。

- **舊資料庫補索引的做法跟既有補欄位/重建做法一致,而且是對的做法**:專案的 `connect()`(`src/rtb/sqlitekit.py:23-38`)每次開連線都會對整份 `schema` 字串跑 `conn.executescript`,`CREATE TABLE IF NOT EXISTS` 與 `CREATE INDEX IF NOT EXISTS` 都是冪等的,所以新索引只要照 `attempt_store.SCHEMA` 既有的寫法(`attempts_first_rows`、`attempts_verified_by_time` 等,`attempt_store.py:53-59`)加進 `inbox_store.SCHEMA` 字串,舊資料庫下次開啟時就會自動補上,**不需要**用 `_migrate_columns`/`_rebuild_proposals` 那一套(那一套是給「加欄位」與「CHECK 約束要換」用的,因為 SQLite 的 `ALTER TABLE ADD COLUMN` 與表重建做不到用 `executescript` 冪等處理)。本節「索引:…(建表語句裡寫「不存在才建」,舊資料庫開啟時補上)」的寫法正是這個既有模式,寫得對、也夠清楚,[S366] 的測試方向也對。

- **回退「索引留著無害」屬實**:新索引只是 `(租戶, 種類, 時間)` 的一般索引(非唯一),不影響 `write_stops` 既有的 `UNIQUE (kind, task_id, revision, content_hash)` 限制,也不改變任何寫入路徑的語意,純粹加速查詢;拿掉查詢函式後索引留著確實無害,跟既有 `attempts_*` 索引留著無害是同一個道理。

- **增量 3 的三項假設(待核可處置、停下紀錄加「比例過大」種類、核可使用表帶租戶欄)本身寫得夠清楚**:本節第 300、321 行都明白標出這是「主線轉達」「屆時對齊」,前提也寫了「查詢三要等增量 3 實作」,沒有把增量 3 還沒定的細節當成本節的錯這點做得到位。真正的問題不是「假設不清楚」,而是這三項假設本身**不夠完整**(如 F2 所述,只提租戶、沒提任務/修訂/廣告),以及查詢五完全沒有把「增量 2、增量 3 之後 write_stops 種類變多」這件事考慮進過濾條件(如 F1 所述)。增量 3 第 2 版真正改結構時,除了「查詢三的細節屆時對齊」這句已知要重看之外,**查詢五「被停下的」那一段**(因為它沒有種類過濾)也會跟著在增量 3 合併後產生新的錯誤行為,但本節目前沒有把查詢五列進「等增量 3 對齊」的範圍,是遺漏。

- **增量 2 的擋下(比例過大)目前不用、也不能進這些查詢**:已用 `git grep` 確認 `phase6-inc2-impl` 分支完全沒有寫 `write_stops`,所以在增量 3 合併之前,查詢一、二、五都天然看不到比例上限擋下,這與現況相符,不是本節的錯;需要處理的只是「增量 3 合併之後查詢五要不要把它濾掉」(F1)。
