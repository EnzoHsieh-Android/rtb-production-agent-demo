## F1 門檻為 0 時使用率無法計算，完成條件仍未兌現
severity: major
blocking: 是 — 合法設定允許門檻為 0，設計卻把比例計算交給呼叫端且未定義除以 0 的語意；照字面實作會無法回報完成條件要求的額度使用率

引句:「回整數不回比例,比例由呼叫端算。」

引句:「額度使用率應回已用、門檻、剩餘;已用應等於同一時刻 `aggregate_used` 的結果」

租戶缺少 `aggregate_limit` 時，現行解析器會合法地把門檻設為 0，而不是拒絕設定，見 file: `src/rtb/executor/capability_signer.py:103`。因此至少有兩個合法輸入沒有答案：

- 輸入：門檻 0、已用 0 → 查詢回 `(0, 0, 0)`；呼叫端計算 `0 / 0` 沒有定義。
- 輸入：門檻 0、仍佔額度的舊列 500 → 查詢回 `(500, 0, 0)`；呼叫端計算 `500 / 0` 同樣失敗。

預期：設計必須明定零門檻時的可觀測結果，例如另外回傳「禁止加額／不適用」狀態或定義比例的封閉語意，並在 [S363] 加入門檻為 0 的驗收案例。否則實作即使完整回傳三個整數，仍答不了它宣稱交付的「額度使用率」。

## F2 查詢五缺少共同的「現在」輸入，窗口邊界會讓明細與已用額度對不上
severity: major
blocking: 是 — 查詢五明列的輸入沒有現在時刻，但「目前是否計入」、目前佔額度清單及剩餘額度都依賴 24 小時窗口；合約也未要求查詢四與查詢五使用同一時刻，照字面實作可能在窗口邊界答出互相矛盾的結果

引句:「輸入租戶、門檻(呼叫端照查詢四的做法用 `load_tenants` 取得後傳入;設計審第 2 輪外家席)與時間範圍(一定要給,不給就拒絕)。」

引句:「目前佔額度的:不分時間範圍(不吃呼叫端給的範圍),現在構成已用額度的每一把鍵」

現行 `aggregate_used` 明確要求呼叫端傳入 `now`，並用它計算窗口起點，見 file: `src/rtb/executor/attempt_store.py:355`、file: `src/rtb/executor/attempt_store.py:369`。具體例：

- 輸入：一筆已驗證預留的驗證時間是 `2026-09-22T00:00:00Z`。
- 查詢四以 `now=2026-09-23T00:00:00Z` 執行，依現行 `>= now-24h` 規則仍計入。
- 查詢五若自行讀鐘並在一微秒後執行，該筆已出窗口，不會出現在「目前佔額度的」，剩餘額度也不同。
- 預期：兩支查詢應能接收並共用同一個帶時區的 `now`；至少查詢五內所有四項輸出必須以一次捕捉的同一時刻計算，[S365]/[S367] 應釘住窗口邊界與同時刻對帳。

第 2 輪的五項阻擋修正均已在本版落地：舊列歸入每個租戶時的例外文字、查詢五的門檻輸入、通過清單不受 24 小時窗口裁切、最新狀態另查，以及 `begin()` 繼續呼叫 `aggregate_used`。索引建置順序亦已補上「租戶欄新增後才建立部分索引」，並有 [S366]/[S370] 覆蓋舊庫路徑。
