具體例:照設計字面實作,展示伺服器子類別只「多寫一個回 HTML 的處理器」,`_dispatch`/`reply` 這條共用管線不動。那麼任何在 `handle_request` 執行「之前」或「之外」被共用基底攔下的狀況——Host 標頭檢查失敗、`handle_request` 丟出未預期例外(例如渲染流程圖時真的踩到 bug、驅動程式狀態檔還沒寫出來就被讀到不完整資料等)——都會落到 `_reply_unexpected`/`reply_error`,回應一律是 `application/json` 的 JSON 字串,沒有內容安全政策標頭、也不是 HTML。使用者在瀏覽器看到的不是設計要求的「好讀好看」的錯誤畫面,而是原始 JSON 文字;這正是「照設計字面實作會做出錯的行為」。若改成子類別覆寫 `_dispatch` 本身來繞過這個問題,等於把共用基底的例外處理、Host 檢查、故障注入攔截整段複製一份到展示套件,才是真正的「沿用 httpkit」被架空成第二套實作,牴觸鏡頭判準「引入第二種做法…才算 major」。
建議:設計文字應明講怎麼在不複製 `_dispatch` 的前提下讓 HTML 路徑走完共用的錯誤處理——例如讓 `handle_request` 一律回 `(status, dict)`,由展示頁面渲染函式把這個 dict 轉成 HTML 字串,`reply()` 才依 handler 宣告的內容類型分流序列化與加 CSP 標頭;或明講 `check_host`/`_reply_unexpected` 這類共用例外路徑在展示伺服器上要不要、如何也帶 CSP 與 HTML 外觀,不要只寫一句「加一個出口、不改既有路徑」帶過。
