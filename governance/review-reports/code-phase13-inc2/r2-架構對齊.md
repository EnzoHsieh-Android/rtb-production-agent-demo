## 發現 1:_passes 在既有「每支檢查自己不丟例外」之外,另加一層吞例外的外殼
severity: minor
blocking: 否

**既有機制**:白名單的每支 Check 自己負責對任何型別只回真假。
- `is_finite_or_none` 在函式內接 OverflowError(file: `src/rtb/domain/_checks.py:40`)。
- STATE_FIELDS 的 status 先檢查 `isinstance(value, str)` 再做集合查找。
- `_trusted` 與 `_window_body` 都直接呼叫 check,不另外包 try(file: `src/rtb/analyzer/dsp_client.py:72`、`src/rtb/analyzer/dsp_client.py:303`)。

**這次的修法**:修正裡已經用既有做法把 action 那支改好(加了 isinstance),又在 `_rows_ok` 外面另包一層吞 TypeError、ValueError、OverflowError 的 `_passes`。

引句:「        return bool(check(value))」
引句:「and all(_passes(check, row[name]) for name, check in fields.items()) for row in rows)」

**問題**:
- 目前三張逐列白名單的每一支檢查都不會丟例外,所以這層外殼是用不到的防線。
- 外殼只包了逐列白名單,`_trusted` 與 `_window_body` 沒包,形成兩種慣例並存。
- 以後有人在 METRICS_FIELDS 寫出會丟例外的檢查,會以為有外殼保護,但較長時間窗那條路徑其實沒有。
- 檢查函式本身寫錯而丟出 TypeError 時,會被靜默判成「欄位不合格」。

**例子**:history 列的 action 是 `["x"]`。
- 預期:判為不合格。
- 實際:光靠 `HISTORY_ROW_FIELDS["action"](["x"])` 就回 False,拿掉 `_passes` 結果也一樣。

**重現**:把 src 複製到 /tmp,設好 PYTHONPATH=src 後呼叫上面那支檢查,實測回 False。

**建議**:刪掉 `_passes`,維持「檢查函式本身不丟例外」這一種慣例。
