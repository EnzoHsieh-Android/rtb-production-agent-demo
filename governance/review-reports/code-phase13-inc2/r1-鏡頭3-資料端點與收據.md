## 發現 1:收據數字字串長度沒有上限，DSP 回傳的極端金額會讓整步一直失敗
severity: major
blocking: 是

用戶端的逐欄白名單只要求金額是有限數，沒有上限，也允許非常接近 0 的值。收據把比率算成精確分數，再展開成完整的十進位字串，所以字串長度也沒有上限。收據要存成可信證據，而可信證據的每個字串都要符合識別碼格式，最多 128 字元。字串一超過，建收據證據就丟出 `ValueError`。

問題在於，這批資料已經通過白名單，不會記成「沒有結果 invalid」。例外直接從證據來源往外丟，整步不寫入，下次重讀同一批資料又同樣失敗，這件工作就卡死了。這違反 [S1132]「整步應不失敗」，也不合計劃「欄位不合格記 invalid、不讓整步失敗」的精神。計劃 R3-6 只把金額量化溢位歸成「資料不合理」；比率與變化百分比的字串長度，沒有任何地方收斂。

引句:「tenths = round(value * 1000)  # 分數的 round 是四捨五入到偶數」
引句:「**dict.fromkeys(_AMOUNT_FIELDS, is_finite_or_none),」
引句:「receipts.append(inv.receipt_evidence(task.task_id, task.seq, option, read.raw,」

- file: `src/rtb/domain/_checks.py:13`(`ID_PATTERN` 是 `{1,128}`)
- file: `src/rtb/domain/evidence.py:121`(可信證據的每個字串都要過 `is_id`)
- file: `src/rtb/analyzer/instrumented.py:154`

具體例子:
- 輸入:廣告的逐日成效，第 1–3 天營收 1e300，第 4–7 天營收 1e-300。兩個值都是有限的非負浮點數，種子與用戶端都照收。
- 預期:`revenue_change` 寫 `na`(資料不合理)，或整份收據記成 invalid 的沒有結果，這一步照常往下走。
- 實際:`revenue_change` 是約 600 位數的字串，`receipt_evidence` 丟出 `ValueError: 證據欄位不合法:payload`。

重現方式:
1. 在 /tmp 複本用 `seed_platform_history` 種上面這份資料。
2. 起真的 `python -m rtb.dsp.server --db …`。
3. 用 `make_query_reader(base, 2.0)(task, "check_daily_trend")` 讀，得到 reason=None、raw 有值，也就是白名單通過。
4. 再呼叫 `investigation.receipt_evidence(..., QueryOption.CHECK_DAILY_TREND, q.raw, None, now)`,會丟出上面的例外。這是實測結果。

`base` 收據的配速比也一樣:花費 1e308、預算 1 時也沒有上限，只是它不經過證據驗證。

建議:在精確比率函式或 `percent_text` 設上限。例如整數部分超過固定位數，或寫出來超過 128 字元時，歸成「資料不合理」寫 `na`,並補一條 [S1147] 的殺傷測試。

## 發現 2:涉及金額的比率用浮點的二進位值算，跟「金額是唯一經過浮點的一段」矛盾
severity: minor
blocking: 否

計劃寫金額要先 `Decimal(repr(x))`,並聲明「這是收據裡唯一經過浮點的一段」。但營收變化、配速比這類以金額為輸入的比率，在 `_exact_input` 直接做 `Fraction(float)`,算的是二進位近似值。結果在十進位剛好落在 .x5 的邊界上，會捨到跟收據上金額字串推得出的值不同的方向。

引句:「這是收據裡唯一經過浮點的一段」
引句:「return Fraction(value)」

- file: `src/rtb/domain/metrics.py:179`

具體例子:
- 輸入:`receipt_change(0.16, 0.17)`。收據上的金額寫成 `"0.16"`、`"0.17"`,依十進位算，精確變化是 +6.25%。
- 預期:銀行家捨入後是 `"6.2"`。
- 實際:`"6.3"`。

同一類的還有 0.16→0.15 得到 `"-6.3"`、0.16→0.13 得到 `"-18.7"`。

重現方式:把 `percent_text(Fraction(Decimal(repr(a)))/Fraction(Decimal(repr(b)))-1)` 跟 `receipt_change(b, a)` 做雙迴圈比對，範圍是 0.01–3.99 的兩位小數，會列出一批不一致。

標準答案也走同一支函式，所以評分不會兩邊對不上。影響只在邊界上差 0.1。

## 發現 3:追加查詢的呼叫紀錄把 404 與 4xx/5xx 都記成 ok
severity: minor
blocking: 否

`_read` 先把 outcome 設成 `"ok"`,只有丟例外時才改寫。狀態碼判斷在 `finally` 之後才做，所以 404 與 4xx/5xx 都用 `"ok"` 記進 tool_calls。基本讀取的 `_get` 會記例外名稱，`InstrumentedOperationLookup` 查不到時也記 `"not_found"`,這裡跟兩者都不一致。追蹤檢視會把失敗的呼叫顯示成成功。

另外還有兩個邊角(模擬 DSP 一律回 JSON,所以只算邊角):
- 404 帶非 JSON 本文時，會以 `UnreadableResponse` 往外丟，不是記成 not_found。
- 5xx 帶非物件 JSON 時，會丟 `AttributeError`,不是 `DspRequestFailed`。

引句:「if status == _NOT_FOUND:」
引句:「raise DspRequestFailed(f"{path} 回 {status}:{body.get('error', '未知錯誤')}")」

- file: `src/rtb/analyzer/dsp_client.py:320`、`src/rtb/analyzer/dsp_client.py:336`
- file: `src/rtb/analyzer/instrumented.py:120`

具體例子:假伺服器回 503(store_busy)。
- 預期:呼叫紀錄記 `DspRequestFailed`。
- 實際:記成 `('dsp:daily', 'ok')`,接著才往外丟 `DspRequestFailed`。

真的 DSP 對未種資料的廣告回 404 時，同樣記成 `ok`。

重現方式:對真 DSP 與假伺服器(回 503、404 HTML、503 `[1,2]`)跑 `make_query_reader(..., on_call=收集)`,每一種都實測過。

## 發現 4:種子寫法不是全有或全無，重種會留下舊列，調整前預算也沒有驗
severity: minor
blocking: 否

這條有三個互相獨立的小問題:

1. **整體不是一個交易。** `seed_platform_history` 先逐一廣告提交逐日成效與過去調整，最後才呼叫 `seed_past_operations`。如果平台已經有操作，最後一步被拒絕，但前面種的過去調整已經寫進去了，資料就違反 [S1127]。
2. **重種會留下舊列。** `seed_past_adjustments` 依序號用 INSERT OR REPLACE 寫入。重種成較少筆時，序號較大的舊列還留著，順序也跟著亂掉。
3. **調整前後的預算沒有驗。** `budget_before` 與 `budget_after` 直接寫進資料庫，負數、字串、小數都收。

引句:「store.seed_past_operations(changes, now)」
引句:「"INSERT OR REPLACE INTO past_adjustments VALUES "」

- file: `src/rtb/dsp/seed.py:100`
- file: `src/rtb/dsp/store.py:444-446`

具體例子(三個都實測過):
- 先 `execute` 一筆真寫入，再 `seed_platform_history` 一份帶 1 筆調整的資料:最後一步被拒，`get_past_adjustments` 仍有 1 筆，`consistency_problems` 回報「過去調整筆數不等於…」。
- 先種天數 3、5、7 的三筆，再種天數 9 的一筆:讀回 `[9, 5, 7]`。預期是 `[9]`。這時端點回傳的順序不是由新到舊，用戶端會判成 invalid。
- `PastAdjustment(4, -5, …)` 與 `PastAdjustment(5, "abc", 1.5, …)` 都照存。

展示每個情境都重建資料庫，所以正常流程碰不到，只是守不住。

## 發現 5:昨天缺資料時，較長時間窗整個查詢變成 not_found,7 天的資料看不到
