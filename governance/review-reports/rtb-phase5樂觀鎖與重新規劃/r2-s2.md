severity: major

### 1. 「DSP 沒有這筆但收件口已交給執行」不是「不該發生」的異常,是這個設計自己會製造出來的正常時序,會把真正成功的任務永久誤判成擋下

severity: major
blocking: 是 這格判斷把「查詢時序碰巧沒對齊」跟「真的資料矛盾」混為一談,照字面實作會把已成功執行的任務判定成終點狀態的 BLOCKED,永遠回不去,不是可以下一輪自我修正的暫時誤判。
引句:「已交給執行(DSP 卻沒有這筆:不該發生)」

這一步(第 1 步查 DSP、第 3 步才問收件口)是兩次分開的外部呼叫,中間沒有任何鎖或交易保護,而執行端「DSP 寫入成功」到「收件口確認已交給執行」之間本來就有真實的間隔(寫入 → 執行後驗證再讀一次 DSP → 才確認 disposition,見 `src/rtb/executor/execution.py:360`、`:468-470`、`:505-516`)。DSP 這一側操作紀錄一寫入交易就已提交可查(`src/rtb/dsp/store.py:332-343` 與 `src/rtb/dsp/server.py:146-152` 的 `_get_operation` 直接查 `operations` 表)。

輸入 → 預期(照字面實作會錯判的例子):
- t1:分析端查 DSP 操作紀錄(第 1 步)→ 這一刻執行端還沒開始寫或還在等 DSP 回應,查不到,合理落到第 3 步。
- t2(仍在同一次 `advance()` 呼叫要走完第 3 步之前):執行端(另一個行程)剛好在這個空檔完整跑完寫入 DSP、執行後驗證、確認收件口 disposition = 已交給執行。
- t3:分析端接著送出第 3 步的重送問收件口,拿回 disposition = 已交給執行。
- 照這張表:落入「已交給執行(DSP 卻沒有這筆)→ 轉擋下,記『處置與 DSP 不一致』,不重新規劃,留給人看」。
- 實際上:DSP 已經正確套用了這個決策(預算與版本都對),任務應該轉完成,不是擋下。

因為 `BLOCKED` 是任務狀態機的終點(`src/rtb/domain/task_state.py:36-38` `S.BLOCKED: frozenset()`),`advance()` 一進入終點狀態就直接短路返回(`src/rtb/analyzer/flow.py:143-144`),沒有任何下一輪能自己修正——一個真正成功的任務會被永久貼上「處置與 DSP 不一致」等人工介入,而不是被判定完成。這張表把「兩次查詢之間本來就有落差」當成「不該發生的資料矛盾」,判準本身站不住。

### 2. 執行端「版本衝突確認寫版本已變」只改了 execution.py 兩處,漏掉收件口自己的第三個「鍵已存在」確認點,S308/S309 的重新規劃在這條路徑上不會觸發

severity: major
blocking: 是 這是「漏掉該有的合約」:S310 沒有覆蓋到的這個分支,會讓版本衝突造成的擋下被誤記成「同一操作先前已失敗」,依這張處置表就不會重新規劃,直接跟使用者裁定的選項 B(衝突後要重新規劃)對不上。
引句:「Phase 3 增量 3 的鍵已存在分流、Phase 4 增量 1 的終點確認」

計劃在「被取代的既有合約」一節只點名兩處要把 `BlockCode.OPERATION_PREVIOUSLY_FAILED` 改成依嘗試結果代碼分流:`_take()` 的鍵已存在分流與 `_ack_terminal()` 的終點確認。但收件表自己的 `receive()` 在取件時如果發現這把鍵已經有嘗試紀錄,是走 `_settle_existing()`,不是走 `execution.py` 那兩處:

file: `src/rtb/executor/inbox_store.py:481-492`

```
elif state is AttemptState.FAILED:
    done = self.ack_blocked(tx, receipt, now, BlockCode.OPERATION_PREVIOUSLY_FAILED)
```

這是第三個硬編碼 `OPERATION_PREVIOUSLY_FAILED` 的地方,計劃逐字對照的兩處清單沒提到它。更具體的是,呼叫端目前只把 `existing.state` 傳進 `_settle_existing`,連判斷所需的 `existing.code`(是不是版本衝突)都沒有傳進去:

file: `src/rtb/executor/inbox_store.py:466`

```
self._settle_existing(tx, receipt, existing.state, now)
```

這條路徑不是憑空假設:「同一把鍵的兩份修訂可能各拿一張收據」是既有 Phase 4 文件已經承認、也有測試在守的場景(`docs/rtb-production-agent-demo-knowledge/Systems/執行迴圈.md` 佇列代碼審第 1 輪那條 PITFALL 與 `test_two_receipts_for_the_same_key_still_write_the_dsp_once`)。

輸入 → 預期:同一把操作鍵 K 有兩筆處理中的收件表列(兩份修訂各拿到一張收據);第一筆先跑完,DSP 回 409 版本衝突,依 S310 正確改法應確認擋下原因為「版本已變」。第二筆之後被 `receive()` 取件,在 `_settle_existing()` 發現鍵 K 已有終點狀態的嘗試(失敗),照現在的程式碼只會確認擋下原因為「同一操作先前已失敗」,不會是「版本已變」,即使只照計劃文字改掉那兩處也不會修到這裡。分析端之後對第二筆這個任務重送收件口,拿回的是「已擋下的其他原因」,依處置表走「轉擋下,不重新規劃」,不會走「已擋下,原因版本已變 → 重新規劃」——這條路徑上真正的版本衝突不會觸發接續任務。
