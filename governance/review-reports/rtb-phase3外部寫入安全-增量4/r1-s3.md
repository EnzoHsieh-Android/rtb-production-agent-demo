### 1. 「時間用 DSP 同一個注入時鐘」這句話跟現在的程式碼對不上——server 的時鐘從沒被傳進 store

severity: major
blocking: 是 這是合約 S78 能不能被確定性測到的前提,不解決就沒辦法照設計寫出這段檢查,也沒辦法穩定測。
引句:「時間用 DSP 同一個注入時鐘」

說明(白話):這句話假設 DSP 只有一個「可以被測試控制的時鐘」,提交當下的檢查沿用它就好。但我實際讀了程式碼並跑了實驗,發現 DSP 這邊其實有兩支互不相通的時鐘:

- `server.py` 的 `DspServer.clock`(用來驗憑證的時間窗,型別是回傳浮點/整數秒的 `Callable[[], float]`,測試裡可以固定或竄改它來做故障注入)。
- `store.py` 的 `CampaignStore._clock`(用來寫 `received_at`/`committed_at`,型別是回傳 ISO 8601 字串的 `Callable[[], str]`,預設是真實牆鐘 `_utc_now`)。

而 `server.py` 每次處理請求時建構 `CampaignStore` 完全沒有把 `self.server.clock` 傳進去:
file: `src/rtb/rtb/dsp/server.py:103`(實際路徑 `src/rtb/dsp/server.py:103-105`)
```
store = CampaignStore(
    self.server.db_path, busy_timeout_seconds=self.server.busy_timeout_seconds
)
```
我用專案的 venv 實際跑了一段實驗(建一個帶假時鐘的 `DspServer`,同時建一個預設的 `CampaignStore`),結果:
```
store._clock() 回傳型別與值: <class 'str'> 2026-09-22T17:08:19...
server.clock() 回傳型別與值: <class 'int'> 1800000000
```
兩支時鐘既不是同一個物件,回傳型別也不同(`str` vs `int`)。我再直接試了一次「字串時鐘 < 憑證到期時間(int)」的比較,結果是 `TypeError: '<' not supported between instances of 'str' and 'int'`。也就是說,照字面「時間用 DSP 同一個注入時鐘」去實作,如果隨手借用 `store` 現成的 `self._clock()` 來比對,程式會直接壞掉;如果改用 `time.time()` 另開一支牆鐘,那又不是「同一個注入時鐘」,S78 要求的「收到時有效、提交當下已過期」這種精確時序,測試將沒有任何管道去控制(店裡目前也沒有任何一支測試對兩個時間點回傳不同值的時鐘 stub,`tests/dsp/test_capability.py` 的 `Clock` 是固定值,除非測試手動改 `clock.now`,而目前完全沒有介面能讓 `store.execute()` 內部再讀一次那個可控的時鐘)。

要接得起來,這段設計至少要交代:`CampaignStore` 需要多收一個獨立於 `_clock`(字串)之外的「到期比對用」時鐘參數(型別要跟 `claims.exp`/`server.clock` 一致),`server.py` 建構 `CampaignStore` 時要把 `self.server.clock` 傳進去。這件事現在的設計文字完全沒寫,而且不能直接重用既有的兩支時鐘裡的任何一支(字串的用途是 `received_at`/`committed_at` 的排序,已有測試 `entry.committed_at >= entry.received_at` 綁住,不能改型別;浮點的那支現在根本沒有接到 store)。

### 2. 「提交當下再驗」沒交代 `Operation` 要不要帶到期時間、缺了要怎麼辦——這正是「沒帶憑證的舊路徑」,而且現在就有

severity: major
blocking: 是 現在就有大量既有測試踩在這條「舊路徑」上,照字面實作若把檢查做成無條件、或把欄位改成必填,會直接打壞這批既有測試而不是「新增」對帳能力。
引句:「模擬 DSP 應拒收(憑證過期)並不寫廣告、操作紀錄與冪等紀錄」

說明:增量 4 這段沒有提到 `Operation`(`store.py` 的資料類別)要不要新增一個「憑證到期時間」欄位、由誰(server.py 的 `_authorized_write`)填進去、以及這個欄位缺席時該怎麼辦。但我檢查了現況:`store.execute()` 目前只有一個呼叫點是走 HTTP 層(`_authorized_write` → 一定先過憑證驗證),但**測試**裡大量直接繞過 HTTP 層呼叫 `CampaignStore.execute()`:
file: `src/rtb/rtb/dsp/store.py`(實際路徑 `tests/dsp/test_store.py:33-39`)
```
def budget_op(key="k1", budget=150, expected_version=1, campaign="c1"):
    return Operation(
        campaign_id=campaign, action="update_budget",
        params={"new_budget": budget}, expected_version=expected_version,
        idempotency_key=key,
    )
```
`tests/dsp/test_store.py` 裡至少有 30 處這樣直接建構 `Operation` 並呼叫 `store.execute()`,完全不帶任何憑證資訊——這正是你問的「沒帶憑證的舊路徑」,而且它不是理論上的邊角,是現在就存在、而且要留著(店這一層本來就刻意獨立於憑證層測,增量 2 的 PR 說明也是這樣分工的)。設計文字沒說:
- 這個新欄位是不是選填、預設值是什麼;
- 選填時,`None`(沒帶到期時間)要不要跳過這段新檢查、還是要當成「已過期」拒收;
- 如果照字面把檢查寫成「不成立就整筆不寫」而沒有排除「沒有到期時間」這個情況,那 30 幾支既有的 store 層測試會全部因為多出的比較而炸掉(不管是型別錯誤還是被誤判成過期)。

這跟第 1 點是同一個缺口的兩面:一個是「時鐘從哪來」,一個是「這個值從哪來、缺了怎麼辦」,兩者都要在設計裡把 `Operation` 的欄位與預設行為講清楚,否則實作者要嘛猜錯、要嘛打壞既有測試。

### 3. 提交當下檢查跟版本檢查誰先誰後沒寫,兩者同時不成立時回哪個代碼不確定

severity: minor
blocking: 否 目前沒有任何既有測試或已列出的合約(S70–S84)會撞到「版本已不符,同時提交當下也過期」這個組合,不影響現有行為,只是新合約本身不夠精確。
引句:「寫入的資料庫交易裡、真的改之前,再比一次」

說明:設計只講「真的改之前」再比一次到期時間,沒說這一步要放在 `_execute_in_transaction` 裡的哪個位置——是緊接在冪等重放判斷之後、版本檢查之前,還是版本檢查通過之後、`_apply` 之前。從「同鍵重放照舊回原結果,不受這條影響」這句可以確定它必須排在冪等重放分支「之後」(重放分支要原樣跳過這個新檢查),但跟版本檢查的先後順序沒有交代。兩種放法都能滿足現有列出的合約,但如果將來(例如對帳重送時)真的出現「版本已經前進、且提交當下也過期」這種雙重不成立的情境,回應會是 `409 version_conflict` 還是 `401 capability_expired`,取決於實作者選的順序,而設計沒有給出裁定,也沒有對應測試把它釘住。建議在增量 4 定案時補一句「先版本後到期」或反過來,並各補一條窮舉式的合約防止之後漂移。
