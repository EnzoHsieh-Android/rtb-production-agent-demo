### 1. 重啟恢復在歷史列已達上限時會整批失敗,連未受影響的健康鍵也一起卡住
severity: major
blocking: 是 破壞計劃第 92-101 行「筆數上限」規則與合約 S13 的字面承諾(重啟恢復應「一律」把嘗試中轉成結果不明),且經實測會讓同一次重啟裡其他健康的鍵也連帶恢復失敗。
引句:「for key in keys:
+        row = latest(conn, key)
+        assert row is not None  # noqa: S101

`recover_in_flight`(`src/rtb/executor/attempt_store.py:287`)呼叫 `_append(conn, row, AttemptState.UNKNOWN, now)` 時沒有帶 `capped=False`,所以沿用 `_append` 的預設值 `capped=True`(見 `governance/review-reports/code-phase3-attempts/r1-snapshot.patch` 的 `_append` 定義:「capped: bool = True」)。計劃第 101 行明講筆數上限只豁免「進入轉人工的那一列與人工處置那一列」,沒有豁免重啟恢復;但同一段落與合約 [S13] 都描述重啟恢復是「一律」要成功的安全操作(交接文件 F1 事故的核心手段)。若某把鍵的歷史列已達上限(暫用 50)但目前仍是「嘗試中」——例如資料庫是舊資料搬遷進來的、或未來增量調整 MAX_SENDS/MAX_VERIFICATION_TIMEOUTS 後可觸達——重啟恢復會對這把鍵丟出 `HistoryFull` 且不被任何地方接住;更嚴重的是,因為所有鍵的恢復都在同一個 `store.transaction()`/`BEGIN IMMEDIATE` 交易內完成,一把鍵炸掉會讓整個交易回滾,連同一批裡完全健康、本該被恢復的其他鍵也留在「嘗試中」沒被轉成「結果不明」。

重現(已實際執行,輸出如下):
- 輸入:兩把鍵都是「嘗試中」——一把正常(`healthy`),一把用跟作者自己 S18 測試同款手法(`_fill_history` 的直寫技巧)把歷史灌到 `MAX_ROWS_PER_KEY`(50)列、狀態仍是嘗試中(`atcap`)。呼叫 `attempt_store.recover_in_flight(conn, NOW)`。
