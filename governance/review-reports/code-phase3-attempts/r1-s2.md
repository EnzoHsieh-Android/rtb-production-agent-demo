### 1. `_unresolved_count()` 的全域檢查是全表掃描,`attempts` 表沒有任何清除機制,會拖慢/阻塞收件口既有的 accept

severity: major
blocking: 是 每次成功的 begin() 都會執行這個全表掃描,且掃描發生在收件口資料庫唯一一條連線的 BEGIN IMMEDIATE 交易鎖持有期間,會延遲/阻塞完全無關的 proposals 收件與事件寫入,而且沒有任何清除機制讓它自然恢復——這是會做出錯的行為(違反作者自己宣稱的「資料量受…20 把未結案約束」),不是風格問題。

引句:「SELECT COUNT(*) FROM attempts a WHERE {_LATEST_ONLY} 」

說明:
`begin()` 在正常成功路徑上一定會呼叫兩次 `_unresolved_count`:一次帶 `campaign_id`(用得到 `attempts_by_campaign` 索引,便宜),一次不帶(`if _unresolved_count(conn) >= MAX_UNRESOLVED`)。後者的 SQL 是
```
SELECT COUNT(*) FROM attempts a WHERE a.seq = (SELECT MAX(b.seq) FROM attempts b WHERE b.key = a.key) AND a.state IN (...)
```
沒有任何 WHERE 條件能讓查詢規劃器用索引縮小範圍,`EXPLAIN QUERY PLAN` 證實是 `SCAN a`(全表掃描,對每一列都跑一次相關子查詢)。`attempts` 表是「只增不改」的歷史表,VERIFIED/FAILED 這些終態列**永遠不會被清除**(不像同一支模組的鄰居 `proposals` 表有 `RETENTION`/`_purge_finished_tasks`),所以這個查詢的成本是「這個執行行程自誕生以來曾經寫過的所有 attempts 列數」,不是作者宣稱的「50 列/鍵、20 把未結案」——那兩個上限只限制*未結案*的資料量,對*已結案、但保留在表裡的歷史*完全沒有約束力。

實測(`/Users/enzo/rtb-production-agent-demo/.venv/bin/python`,腳本建同樣 schema 的臨時 SQLite,20 把未結案不變,只增加已結案歷史列數):

```
finished_keys=      0  per_call=  0.017ms   SCAN a
finished_keys=   2000  per_call=  0.068ms   SCAN a
finished_keys=  20000  per_call=  0.548ms   SCAN a
finished_keys= 100000  per_call=  3.563ms   SCAN a
```

成本隨歷史列數線性成長,與「20 把未結案」上限無關(未結案一直固定 20 把)。這個查詢是在 `InboxStore.transaction()`(`immediate_transaction`)持有 `BEGIN IMMEDIATE` 寫入鎖的期間執行的,而這條連線是整個執行行程資料庫唯一開連線、開交易的地方——`proposals`、`inbox_events` 都在同一個檔案、同一把鎖上。表越長,`begin()` 這個熱路徑操作扣住鎖的時間就越長,會延遲甚至(逾 `BUSY_TIMEOUT_SECONDS=5.0`)讓完全不相關的 `accept()`(收新提案)與 `record_event()` 收到可重試的忙碌錯誤——這違反了收件口自己宣稱的設計意圖「全表同時未結案 20 把,滿了就停下所有新寫入」:實際上寫入會被「歷史多寡」而不是「真的卡了幾把鍵」拖慢,而後者才是文件上唯一被承認的節流機制。

作者對五題效能檢核的表態只涵蓋「每把鍵 50 列、全表未結案 20 把、提案 16KB 上限」這些*單次請求/單一鍵*的界限,沒有涵蓋「表本身隨行程存活時間無上限增長」這個維度,所以這個缺口作者應該沒看到。
