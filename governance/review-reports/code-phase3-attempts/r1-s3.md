severity: major

### 1. `now` 沒有時區會讓 `written_at` 悄悄寫錯,不丟例外
severity: major
blocking: 是 這是資料損壞:歷史列的時間欄位被寫成錯的值卻沒有任何錯誤提示,而 written_at 正是稽核歷史表存在的核心欄位。
引句:「return moment.astimezone(UTC).strftime」

`_iso()` 對 `now` 直接呼叫 `astimezone(UTC)`,但沒有檢查 `now` 是否已帶時區。Python 對 naive datetime 呼叫 `.astimezone()` 會假設它是「系統本地時區」的牆上時間再換算成 UTC,而不是照字面值當 UTC。`begin`、`transition`、`record_verification_timeout`、`resolve`、`recover_in_flight` 全部共用這支函式,五個公開寫入口都會中招。

重現(已實際執行):
- 輸入:呼叫端傳 `naive_now = datetime(2026, 9, 22, 12, 0, 0)`(沒有 tzinfo,呼叫端以為就是 12:00 UTC),機器所在時區是 UTC+8。
- 實際:`attempt_store.begin(conn, prop, naive_now)` 不丟任何例外,寫入的 `written_at` 是 `2026-09-22T04:00:00.000000Z`——比呼叫端傳入的值早了整整 8 小時,而且沒有任何跡象顯示出錯。
- 預期:要嘛照字面值當 UTC 存(`2026-09-22T12:00:00.000000Z`),要嘛在 `now` 沒有時區時直接拒絕(丟明確例外),不該是「看伺服器時區決定要偏移多少小時」這種無聲行為。

實測輸出:
```
system local tz offset: 8:00:00
stored written_at: ('2026-09-22T04:00:00.000000Z',)
naive_now the caller passed: 2026-09-22 12:00:00
```
`now` 是這支歷史表唯一沒有經過領域層驗證形狀的輸入(提案本身的時間欄位有 `parse_proposal` 把關,`now` 完全沒有),而歷史表的正確性正是「查證逾時窗口是否已過」「重啟恢復判斷」未來要依賴的東西。

### 2. `snapshot()` 讀到損毀的 `proposal_json` 時丟出未包裝的 `json.JSONDecodeError`,不是設計宣稱的 `CorruptedAttemptRow`
severity: major
blocking: 是 這是「會做出錯的行為」:模組自己定義的例外分類法在這一種毀損情境下沒有生效,呼叫端照設計只會接 `CorruptedAttemptRow`,遇到這個情況會被未預期的例外型別打穿。
引句:「parsed = parse_proposal(json.loads(record[0]))」

`CorruptedAttemptRow` 的 docstring 明講是「歷史列讀不回來(格式毀損)」,`_row()` 對 `state`/`code` 欄位毀損也確實把 `ValueError` 包成 `CorruptedAttemptRow`。但 `snapshot()` 只有在 `record[0] is None` 或 `parse_proposal(...)` 回傳 `proposal is None` 時才轉成 `CorruptedAttemptRow`；如果 `proposal_json` 這欄本身不是合法 JSON(例如位元腐化、手動竄改、寫入中斷截斷成半截字串),`json.loads(record[0])` 會直接丟 `json.JSONDecodeError`,這行不在 `parse_proposal` 的 try/except 保護範圍內(`parse_proposal` 只包住 `_parse(raw)`,不包住呼叫端自己做的 `json.loads`)。

重現(已實際執行):把第 1 列的 `proposal_json` 竄改成 `"{not valid json!!"` 後呼叫 `snapshot()`:
```
BUG: got unexpected exception type: json.decoder JSONDecodeError Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
```
預期:應該跟 `state`/`code` 毀損一樣,統一包成 `CorruptedAttemptRow`(這也是計劃裡「proposal_json 壞掉」這種毀損列要驗的情境,`_row()` 那條路已經做對,`snapshot()` 這條路沒做到)。

### 3. `expected_seq` 傳布林或浮點數時,靠 `==` 比對會被 Python 的數值等價悄悄放行
severity: minor
blocking: 否 目前程式碼裡所有呼叫端都是把 `row.seq`(真正的 int)原樣傳回來,不會自然產生這個輸入;沒有破壞合約或弄壞資料,只是型別防線不夠嚴謹。
引句:「row.seq == expected_seq else None」

`_current()` 用 `row.seq == expected_seq` 判斷是否為最新序號。Python 的 `bool` 是 `int` 子類,`True == 1`;所以呼叫端不小心傳 `True` 而不是 `1`,在 `row.seq == 1` 時會被誤判成「序號吻合」而真的寫入一筆新列,跟傳負數或 0(设计裡「沒有進展就回 None」)的安全失敗行為不一致。

重現(已實際執行):對剛 `begin()` 完(`seq=1`)的鍵呼叫 `transition(conn, key, True, AttemptState.UNKNOWN, now)`,結果不是回 `None`,而是真的寫入了 seq=2 的新列。若上層 API 之後某處把 `expected_seq` 從外部（例如反序列化的 JSON payload,其中 `true`/`false` 會變成 Python 的 `bool`）帶進來,就可能繞過 S9 想要的「序號不符就不寫入」保護。建議在 `_current()` 加一道 `isinstance(expected_seq, int) and not isinstance(expected_seq, bool)` 的型別檢查。
