severity: major

### 1. `now` 被呼叫端重用而非逐步重讀時鐘時,decide() 會把剛蒐到的證據誤判為「年齡是負的」過期,分析流程卡死重複退回蒐證

severity: major
blocking: 是 這會讓正常流程在合理、甚至更接近專案既有慣例的呼叫方式下永久卡住,不是邊角案例
引句:「self, task: TaskRow, evidence: tuple[Evidence, ...], now: datetime」

說明:這支 patch 把 `Decide` 的 `now` 從「`policy.decide()` 自己讀系統時鐘」改成「`advance()` 手上的 `now` 一路往下傳」。問題是 `now` 只被 `advance()` 讀一次(呼叫端決定何時讀),但 `EvidenceSource` 的真實實作 `dsp_client.py` 在蒐證那一步是**自己另外**呼叫 `datetime.now(UTC)` 來設 `observed_at`(`src/rtb/analyzer/dsp_client.py:68,76,83`),完全不理會 `advance()` 傳進來的 `now`。而 `check_freshness()` 對年齡的判斷是「小於 0 就直接過期,不看差多少」(`src/rtb/domain/evidence.py:129-130`:`age = (now - evidence.observed_at).total_seconds(); if age < 0 or age > max_age_seconds: return EXPIRED`)。

只要呼叫端把同一個 `now`(例如「這個批次/這個 tick 的時間戳」)重用在同一個任務的連續兩次 `advance()` 呼叫上——這正是這支 patch 修改前,`tests/analyzer/test_boundaries.py` 原本的寫法(一個 `now` 從建立任務用到最後一步),也是很自然、甚至更貼近專案裡 `TaskStore.commit_step`/`record_tool_call` 那種「整批動作共用一個時間戳」慣例的寫法——蒐證步驟內部用即時時鐘寫入的 `observed_at` 就會比呼叫端手上那個「稍早讀到」的 `now` 還晚,下一步 `decide()` 算出的年齡就是負的,被判定過期,退回 `COLLECTING_EVIDENCE` 重新蒐證,而不是進入 `PROPOSED`/`NO_ACTION`。如果驅動迴圈在同一個 tick 內反覆呼叫 `advance()` 把任務跑到底(`advance()` 的文件本身就是設計成「呼叫端負責重複呼叫直到終點」),這個任務會在這個 tick 內永遠在 `COLLECTING_EVIDENCE`⇄`ANALYZING` 之間彈跳,分析永遠做不出決策。

在改動前,`policy.decide()` 是自己讀即時系統時鐘(不理會傳進來的 `now`),所以即使呼叫端重用同一個 `now`,新鮮度判斷仍然正確——這正是防止這個問題的唯一安全網,而這支 patch 把它拆掉了,卻沒有在 `Decide`/`advance()` 任何地方寫下「`now` 必須不早於這一輪證據的 `observed_at`,呼叫端不能重用/快取時間」這個新增的隱含合約(`src/rtb/analyzer/flow.py:53-57` 只寫了「不自己讀系統時鐘」,沒提「多早都不行」)。作者確實在 `tests/analyzer/test_boundaries.py` 把 e2e 測試改成每步重讀 `datetime.now(UTC)`(patch 裡的註解「不能整個流程共用一個」),但那只是修掉這一支測試會踩到的症狀,沒有堵住這個介面本身的坑——目前專案裡還沒有真正的「增量 4 驅動迴圈」實作(只有測試在扮演呼叫端),下一個把它寫出來的人很可能會踩上同一個坑。

驗證方式:在 `/tmp/review-s2`(專案副本,未改動任何專案檔案)寫了 `repro_negative_age.py`,模擬「driver 一個 tick 只讀一次時鐘、重用給同一任務連續兩次 `advance()` 呼叫」,`EvidenceSource` 比照 `dsp_client.fetch()` 用即時時鐘設 `observed_at`。實際跑出:

```
after step1: collecting_evidence
after step2: analyzing
after step3 (decide): collecting_evidence   # 預期應該是 proposed 或 no_action
```

不需要任何延遲(即使拿掉 `time.sleep`,單純即時鐘的微秒差就足以觸發),因為 `check_freshness` 對負齡是直接判過期、不看幅度。

### 2. `Decide.__call__` 新增的 `now` 說明字串位置錯了,不會變成任何地方的 docstring

severity: minor
blocking: 否 不影響執行期行為,只是這段本來該補上的合約說明被靜默丟掉
引句:「決策層不自己讀系統時鐘」

說明:patch 在 `class Decide(Protocol)` 裡加了一段字串,想說明 `now` 的來源與規則:

```python
class Decide(Protocol):
    def __call__(
        self, task: TaskRow, evidence: tuple[Evidence, ...], now: datetime
    ) -> Decision: ...
    """`now` 是 `advance()` 手上、也會寫進歷史列的同一個時間;決策層不自己讀系統時鐘。"""
```

但 `__call__` 的函式體是 `...`(寫在 `def` 同一行內結束),緊接著的三引號字串在語法上落在**類別本體**、不是函式本體的第一敘述,所以它不會變成 `Decide.__call__.__doc__`,也不會變成 `Decide.__doc__`(它不是類別本體第一個敘述,前面已經有 `def __call__`)。這段字串會被求值後直接丟棄,`help(Decide)`、IDE 工具提示、之後任何自動產生的文件都看不到它,只有讀原始碼的人看得到。

驗證方式:同一份副本內執行
```python
from rtb.analyzer.flow import Decide
print(repr(Decide.__call__.__doc__))  # None
print(repr(Decide.__doc__))           # None
```
兩者都是 `None`,證實這段說明沒有真的掛上去——恰好就是第 1 點裡「合約沒寫清楚」所需要的那段說明,結果連寫都沒寫成功。
