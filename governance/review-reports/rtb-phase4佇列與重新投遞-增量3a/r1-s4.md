### 2. F2 已轉正合約綁定的當機測試,3a 改完後的斷言只有一句話帶過,細節沒交代
severity: major
blocking: 是 理由:S118、S119、S123 是已經獨立審計通過、寫進 ★INVARIANT★ 的事故 F2 合約的綁定測試;计劃只用一句籠統的話帶過要怎麼改,沒有指名是哪幾支、也沒交代排序時間戳斷言要不要搬,實作者字面照做很可能讓這幾支測試斷言失敗,或者把防「排序回歸」的斷言覆蓋悄悄弄丟。
引句:「改完後它們死點留下的嘗試中都有處理中訊息,重啟恢復不再動它們,由對帳接手轉結果不明」

`tests/executor/test_crash_recovery.py` 的 `World.recover_only()`(`tests/executor/test_crash_recovery.py:156`)預設 `expected="unknown"`,只啟動一次、跑 0 輪就檢查嘗試紀錄最後一列狀態,是不是被重啟恢復轉成了 `unknown`。三支已轉正的 F2 合約測試都用了預設值:S118(`tests/executor/test_crash_recovery.py:268`)、S119(`:302`)、S123(`:281`)——這三個死點的死點狀態都是「嘗試中、處理中」(收件表那列還在,只是租約過期),照 3a 的 [S127]「有對應處理中訊息的,不論租約到期沒有,一律不動」,重啟恢復完全不會碰它們。

輸入 → 預期:3a 上線後跑 `test_crash_before_the_dsp_call_is_recovered_by_a_same_key_resend`,`world.recover_only()` 讀到的 `last_attempt()` 仍是 `"in_flight"` 不是 `"unknown"`,`recover_only()` 裡 `assert state == expected`(用預設 `"unknown"`)會直接斷言失敗——要讓測試過,得把這三支個別改成 `recover_only(expected="in_flight")`。更關鍵的是 `recover_only()` 第 169–170 行那段時間戳斷言(`if expected == "unknown": assert started <= ... <= finished`)防的是另一條獨立 PITFALL——「重啟恢復轉結果不明時寫下的時間,決定這把鍵在對帳『先舊後新』裡的排序;算錯三小時全專案都看不出來」(`docs/rtb-production-agent-demo-knowledge/Systems/執行迴圈.md:97`)。這段窗口檢查現在綁在「重啟恢復做轉換」這件事上;3a 把轉換動作搬到對帳接手之後,如果沒人把等價的時間戳窗口斷言也搬到「對帳接手轉換」那一步,這條排序不變量就會失去測試覆蓋而不自知。計劃全文只有「那幾支『只啟動一次』的斷言要改成驗『重啟恢復不動、對帳接手後才轉』」這一句,沒有點名是哪幾支(S118/S119/S123)、也沒提時間戳窗口斷言要不要跟著搬。
