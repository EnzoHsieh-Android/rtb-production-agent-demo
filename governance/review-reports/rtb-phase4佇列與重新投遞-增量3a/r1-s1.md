### 1. 「重啟恢復只碰沒人持有的嘗試中」的不變量只證到 `begin()` 那一刻,沒證到後續對帳重送;receipt 為 None 的鍵在多工作者下會讓「一把鍵放棄」變成「整個工作者停機」

severity: major
blocking: 是 因為這個停機不是重啟恢復本身的問題,而是拿掉單一執行者鎖之後,既有的「序號不對就停機」防線第一次真的會被兩個活著的工作者同時踩到,而 S127–S133 全部沒涵蓋這個情況,必須先補規則或改防線再進實作。
引句:「所以新時代的每一筆嘗試中,在它存在的每一刻都有一則處理中訊息」

說明:
這段論證只證明了「開始一筆」(`attempt_store.begin`)那一次寫入是在核對收據的同一個交易裡做的,所以第一次進入嘗試中一定有處理中訊息。但增量 1/2 早就留了一條「沒有處理中訊息」的鍵仍可能被寫入嘗試紀錄的路:對帳在 `_reconcile` 裡,當 `_take_over` 找不到這把鍵對應的處理中列(收件表已被清掉,或是 Phase 3 時代留下的舊資料)時,回傳 `receipt = None`,但只對「目前狀態是嘗試中」的分支做了防護(`if receipt is None: return False`,交給重啟恢復);其餘狀態(結果不明、已提交待驗證)完全沒有這條防線,照樣往下走進 `_reconcile_unknown → _reconcile_not_found`、`_found`、`_verify` 等函式,最終呼叫 `_write(row, target, receipt=None, ...)`。

`_write` 裡收據檢查是 `if receipt is not None and not self.store.extend(...)`——receipt 是 None 時這一整段直接跳過,沒有任何互斥檢查,單靠 `attempt_store.transition(tx, row.key, row.seq, target, now, ...)` 內部的樂觀序號比對(`_current()` 核對 `row.seq == expected_seq`)。而這個 `row`(連同它的 `seq`)是在 `_reconcile` 的第一段交易裡讀出來、交易就關閉了,之後才在另一個交易裡帶著這個舊序號去寫。

單一執行者下這條路徑確實「不該發生」(程式自己的註解也這樣寫),因為同一時間只有一個執行緒在跑對帳。但拿掉單一執行者鎖之後,兩個工作者的 `reconcile_all()` 都會用 `attempt_store.unresolved_keys()` 掃到同一把沒有收據可管的孤兒鍵(這把鍵沒有租約,誰都能撿),各自帶著自己讀到的舊序號走到 `_write`。先寫進去的那個工作者順利把序號往前推;後寫的那個工作者發現序號對不上,`attempt_store.transition` 回 `None`,`_write` 就丟 `ExecutorHalted("no_progress")`。這個例外不是 `LeaseLost`(只有 receipt 存在時才可能丟),`reconcile_all()` 的迴圈也只接住 `LeaseLost` 與 `CorruptedInboxRow`,所以 `ExecutorHalted` 會一路往上炸穿 `_loop`,讓整個工作者行程以非零代碼結束——這正是 S116/S132 想避免的「健康的一方被別人打掛」,只是這次不是被重啟打掛,而是被另一個活著的對帳打掛,而且是在完全正常的對帳輪次裡,不需要任何工作者真的當機。

具體例子:鍵 K 的嘗試紀錄目前是「結果不明」,收件表沒有它對應的處理中列(可能是人工處置過收件表,或 Phase 3 舊資料——3a 自己在同一節列的正是這兩種情境)。工作者 A、B 同時在跑,兩者的 `reconcile_all()` 都掃到 K,都在 `_take_over` 得到 `receipt=None`,都各自讀到 `row.seq = N`。DSP 目前查不到這把鍵的操作紀錄,兩邊都通過執行前檢查、都簽出新憑證、都呼叫 `_write(row, IN_FLIGHT, receipt=None, ...)`。A 先提交,`attempts` 表這把鍵的最新序號變成 N+1。B 帶著 `expected_seq=N` 進 `attempt_store.transition`,`_current()` 發現目前最新序號是 N+1,回 `None`;`_write` 判斷 `new is None`,丟 `ExecutorHalted("no_progress")`。B 的 `_loop` 接住這個例外,寫「停機:no_progress」到 stderr,以 `EXIT_HALTED` 結束——B 這個工作者整個退出,不是放棄這把鍵、繼續處理別的鍵。要注意的是,B 在丟出例外之前並沒有呼叫過 `self.dsp.write(...)`(那一行在 `_write` 成功回傳之後才會執行),所以這不會造成重複寫入 DSP、不打壞 F2/F3;純粹是可用性問題——但因為兩個工作者都在正常運作、沒有任何一方真的當機,這個停機完全是無謂的,而且只要這把孤兒鍵一直沒被人工收拾,下一輪還會再發生同樣的事。
