# 獨立審查:增量 3 設計(分析行程的流程與檢查點)—— 正確性與可測性鏡頭

### 1. 九個狀態裡,FAILED 在這份設計的驅動函式裡完全沒有寫入路徑

severity: major
blocking: 是 理由:狀態機明講「任何非終點狀態都可以 → 失敗」(且 `TRANSITIONS` 是自動幫每個非終點狀態補上 FAILED,見查證),但 S20~S36 逐條列完 RECEIVED/COLLECTING_EVIDENCE/ANALYZING/PROPOSED/HANDED_OFF 五個非終點狀態各自「怎麼推進」之後,沒有任何一條的結果是寫入 FAILED。這是漏掉合約:照字面實作,`advance()` 永遠不會產生 FAILED 列,狀態機保留的這個逃生口變成死路,遇到不可恢復的錯誤時只能無限卡在原狀態被重試,不會是「錯的行為」馬上炸掉,但屬於「漏掉合約」的 major。

引句:「當任務狀態是終點狀態或 HANDED_OFF,`advance()` 應是空操作,不呼叫任何介面。」

推演:
- 逐條核對 S23~S32:RECEIVED→COLLECTING_EVIDENCE(S23,無條件);COLLECTING_EVIDENCE 的兩個結果是 ANALYZING(S24)或「不寫入,留在原狀態」(S25);ANALYZING 的三個結果是 NO_ACTION(S26)、PROPOSED(S27)、COLLECTING_EVIDENCE(S28),三個結果窮舉了 `Decide` 的三選一回傳型別,沒有第四種;PROPOSED 的三個結果是 HANDED_OFF(S30)、COLLECTING_EVIDENCE(S31)、「不寫入,留在原狀態」(S32)。九個狀態裡,FAILED 從頭到尾沒有以「新狀態」的身分出現在任何一條的右手邊。
- 就算 EvidenceSource(S25)與 Submit(S32 的 Busy)的失敗語意都已明確定義,這兩條給的答案都是「留在原狀態,等下次重試」,不是「轉 FAILED」——也就是說,即使不看「介面丟未預期例外」這種未定義情況,單看設計裡**已經寫清楚**的失敗分支,也沒有一條會走到 FAILED。這代表 FAILED 不只是「碰到沒想到的例外時沒人管」,而是這份設計根本沒有替它安排任何觸發條件,即便是最基本、已經考慮到的失敗情境也不會用到它。
- 對照組:COMPLETED/BLOCKED/SUPERSEDED 三個終點雖然在增量 3 也沒有寫入路徑,但那是明講「留到增量 2 與 Phase 3 定義」、由執行行程那一側寫入,增量 3 的「不做的事」也沒有跟它們牴觸,屬於刻意延後、有交代的缺口。FAILED 不同:它是分析行程這一側自己的狀態機成員,任何非終點狀態(含 RECEIVED、COLLECTING_EVIDENCE、ANALYZING、PROPOSED、HANDED_OFF)理論上都能轉過去,卻在「這是分析行程唯一負責寫 `tasks` 表」的增量 3 裡整段隻字未提會不會用到、誰來觸發、觸發條件是什麼。
- 查證(審材外):`src/rtb/domain/task_state.py:50-53` 的 `TRANSITIONS` 是用 `targets if state in TERMINAL_STATES else targets | {S.FAILED}` 自動把 FAILED 併進每個非終點狀態的合法目標,證實 FAILED 在狀態機層級是「隨時可轉」,不是要特別解鎖的稀有路徑;但增量 3 的驅動函式完全沒有任何分支呼叫 `transition(現在狀態, TaskState.FAILED)`。

建議:在「每個狀態怎麼推進」補至少一條(或一個通則):什麼情況下 `advance()` 應該把任務轉成 FAILED(例如:介面丟出未預期例外時 vs. 重試次數/時間超過某個上限時),由誰(驅動函式本身、還是增量 4 呼叫端另外呼叫一個 `fail_task()`)負責寫這一列;沒有這條,FAILED 這個終點狀態在增量 3 的範圍內實質上是不可達的。

### 2. 「單一交易內先查後寫」的 PRIOR-ART 聲稱與驅動函式實際描述的順序矛盾,並行呼叫 `advance()` 的正確性與序號決定方式全文未交代

severity: major
blocking: 是 理由:PRIOR-ART 明講沿用的是「單一交易內先查後寫」,但「驅動函式」段落自己描述的順序是讀 → 呼叫外部介面 → 才提交,中間夾了一次外部呼叫,不可能真的是同一個交易內先查後寫;兩種讀法(照 PRIOR-ART 的字面 vs. 照驅動函式段落的字面)實作出來的行為天差地遠,而且沒有任何一條 S 款處理「同一任務被並行呼叫 advance() 兩次」,序號怎麼決定也完全沒寫,照字面實作很容易做出會寫壞歷史表的行為,是漏掉合約的 major。

引句:「讀這個任務目前(序號最大)的狀態列,依狀態呼叫對應的可替換介面,把結果連同新狀態列一起提交」

推演:
- PRIOR-ART 那句話是「同一種做法已經在 DSP 與收件口用過:單一交易內先查後寫」——對照收件口的真實做法,`src/rtb/executor/inbox_store.py:165-188` 的 `_accept_in_transaction` 是在同一個 `with immediate_transaction(self._conn):` 區塊裡先 `SELECT`(查收件鍵)再 `INSERT`(寫入),中間沒有任何外部呼叫,整段話成立是因為查與寫真的鎖在同一個交易裡。
- 但增量 3「驅動函式」段落自己描述 `advance()` 的順序是:先讀目前狀態列(讀),再依狀態呼叫 `EvidenceSource`/`Decide`/`Submit`(增量 4 是真的網路呼叫,即使增量 3 是假物件也代表這一步在設計意圖上是「可能慢」的),最後才把結果與新狀態列一起提交(寫)。這跟收件口「查、寫之間沒有外部呼叫」的做法本質不同:如果真的把「讀」搬進同一個 `BEGIN IMMEDIATE` 交易、且交易要撐到外部呼叫回來才提交,等於讓整個 SQLite 檔案在等網路回應期間被寫鎖佔住,會拖住系統裡所有其他任務的 `advance()`;如果「讀」發生在交易之外(更合理的做法),就代表讀到的「目前狀態」在呼叫外部介面、開交易寫入之間,有一段沒有鎖保護的空窗期。設計文字沒有明講走哪一條,也沒有交代空窗期怎麼處理。
- 這個空窗期不是紙上談兵:假設同一個 `task_id` 被並行呼叫兩次 `advance()`(例如當機重啟時舊行程還沒真的死透、新行程已經起來,這正是這份設計開宗明義要防的「事故」的一種變形)。兩次呼叫各自讀到同一列「目前狀態」ANALYZING,各自呼叫 `Decide`,一個拿到 `ProposalDecision`(依 S27 該寫 PROPOSED)、另一個拿到 `NeedsFreshEvidence`(依 S28 該寫 COLLECTING_EVIDENCE)。`task_state.transition()` 只是純函式比對兩個列舉值,`ANALYZING → PROPOSED` 與 `ANALYZING → COLLECTING_EVIDENCE` 個別看都合法(`src/rtb/domain/task_state.py:34`),不會丟 `IllegalTransition`。若序號是各自在寫入當下用 `MAX(seq)+1` 算(不會撞主鍵,但也不會擋下這次並行),兩次呼叫都會成功提交,歷史表就會出現「同一個任務,序號 N 是 PROPOSED、序號 N+1 是又回到 COLLECTING_EVIDENCE」這種同一次分析被拆成兩個互相矛盾結論、各自都合法通過檢查的紀錄——這正是設計開頭「事故」段落想防的「重複決策」的另一種寫法,而且不會被目前任何一條 S 款的測試抓到,因為 S34/S35 測的是**單一呼叫者**「提交前/後中斷再重呼叫」,不是**兩個呼叫者同時**呼叫。
- 序號本身怎麼決定也沒寫清楚:是在讀取當下就決定「下一個序號」、還是在寫入交易內重新用 `MAX(seq)+1`?兩種寫法在並行情境下的行為不一樣(前者更容易撞主鍵、後者更容易出現上一段的「都合法但互相矛盾」)。這件事全文沒有一句話交代,而「主鍵是(任務編號, 序號)」這句話本身沒有回答「序號的值從哪裡來」。

建議:在「儲存」或「驅動函式」段落補一句明確的並行規則,例如「同一個 task_id 的 `advance()` 呼叫必須序列化(呼叫端保證,或驅動函式自己用 `BEGIN IMMEDIATE` 內重新核對『讀到的目前狀態』與『交易內最新一列』一致,不一致就中止重試)」,並明講序號是讀取時決定還是交易內 `MAX+1` 決定;同時比照 S9(收件口的並行同鍵測試)補一條「同一任務並行呼叫 advance() 兩次」的 S 款與測試。

### 3. `tasks` 歷史表的欄位(schema)沒有定義,提案快照存在哪裡不明

severity: minor
blocking: 否 理由:不會讓任何一條 S 款的斷言寫不出來(斷言可以只靠「存取器回傳正確的提案」這種黑盒方式驗證,不需要知道底層欄位),純粹是設計文件本身的完整度落差,不擋門。

引句:「當任務狀態是 ANALYZING、`Decide` 回傳 ProposalDecision,`advance()` 應在同一個交易內把提案快照與一列 PROPOSED 一起提交。」

推演:
- 「儲存:只增不改」對 `evidence` 表明講「存增量 1 的 `Evidence`」,是哪個既有 dataclass 講得很清楚;但對 `tasks` 表只講「主鍵是(任務編號, 序號)」,沒有列出其餘欄位。S21(create_task 帶不同廣告編號要拒收)暗示 `tasks` 至少還存了廣告編號;S27/S29(提案快照要跟著 PROPOSED 一起提交、之後原封不動重送)暗示某處存了整份提案快照——但兩者存在 `tasks` 表自己的欄位裡、還是另開一張表(像 `evidence` 那樣單獨一張),設計沒有交代。
- 這個落差跟 `evidence` 表的明確度形成對比,容易讓實作者在「該不該把提案快照序列化進 `tasks` 的一個 JSON 欄位」與「該不該像 evidence 一樣另開一張表」之間各自猜測,兩種選擇都能讓 S27/S29 的測試通過,但後續(例如增量 4 要讀「歷史上每次提案快照的內容」做稽核或除錯)會因為兩個實作團隊猜的結構不同而難以對齊。

建議:比照 `evidence` 表的寫法,明講 `tasks` 表除了(任務編號, 序號, 狀態)之外還存哪些欄位(至少列出廣告編號、提案快照怎麼存),或者明講「提案快照另開一張只增不改的表,結構待實作時定」。

### 4. `create_task` 首次成功建立 RECEIVED 列這條「主線」沒有對應的 S 條款

severity: minor
blocking: 否 理由:行為可以從 S20(重複呼叫是空操作)反推出來,不太可能被實作者做錯,只是設計文件本身沒有把最基本的成功路徑明講成一條可測條款,拿掉也不影響其他條款成立,不擋門。

引句:「當 `create_task` 被呼叫、這個任務編號已經有歷史列,驅動函式應當作空操作,不新增任何列。」

推演:
- S20 講的是「已經有歷史列」的重送情境,S21 講的是「帶不同廣告編號」的衝突情境。兩條都是邊界/例外情況,唯獨「這個任務編號第一次被呼叫、成功建立」這條最基本的路徑沒有自己的編號與 test 名稱——沒有任何一條明講「`create_task` 首次呼叫時應該新增一列 RECEIVED」,連 RECEIVED 是不是 `create_task` 寫入的都要從上下文(「## 任務狀態機」一節「狀態:收到、蒐集證據……」與 S23「當任務狀態是 RECEIVED」)反推。
- 這跟收件口那份設計(增量 2)的寫法不同:增量 2 對「首次接受」有明講的 201 與欄位(見「重送結果」段),增量 3 對「create_task 首次成功」卻只寫了它的兩個異常分支。

建議:補一條 S 款,例如「當 `create_task` 被呼叫、這個任務編號沒有歷史列,`advance()` 應新增一列 RECEIVED,欄位含任務編號與帶入的廣告編號」,並給對應的 test 名稱,讓「主線」跟「例外」一樣有明確的合約與測試錨點。

### 5. S34/S35 需要的「提交前/提交後中斷」故障注入機制,增量 3 自己的文字沒有講清楚

severity: minor
blocking: 否 理由:可以靠 PRIOR-ART 那句「同一種做法已經在 DSP 與收件口用過」類推出要沿用 `inbox_store.py` 的 `before_commit` 鉤子模式,不是無跡可循,只是增量 3 這一段自己沒有明講,屬於文件完整度問題,不擋門。

引句:「當任一步驟在提交前中斷後重新呼叫 `advance()`,結果應與沒有中斷時一致。」

推演:
- 對照增量 2:「共用基礎」段落明講「故障注入沿用 DSP 的做法……收件口新增兩種:提交前中斷、提交後回應前中斷,讓『提交前』在測試中可以被製造」,且 `InboxStore.accept()` 真的帶了一個 `before_commit: Callable[[], None] | None` 參數給測試用(`src/rtb/executor/inbox_store.py:154,165-171`)。
- 增量 3 的 S34/S35 用詞跟增量 2 的故障注入語言幾乎一樣(「提交前中斷」「提交後……中斷」),但「儲存」與「驅動函式」段落都沒有講 `advance()` 要不要、要怎麼提供類似 `before_commit` 的鉤子,也沒有講「一步」指的是交易邊界的哪個位置(例如 S24 把證據列與 ANALYZING 一起提交,「這一步提交前中斷」精確是指這個 `BEGIN IMMEDIATE` 交易 COMMIT 之前的任何時間點,這件事只能從沿用 `immediate_transaction` 這句話反推,沒有明講)。

建議:比照增量 2,補一句「`advance()` 內部的寫入交易接受測試用的中斷鉤子,語意與收件口的 `before_commit` 相同」,並明講 S34/S35 裡「一步」對應的交易邊界(哪一段程式碼在同一個 `BEGIN IMMEDIATE` 裡)。
