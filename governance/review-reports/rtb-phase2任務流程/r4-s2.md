severity: blocker

審查範圍:r4-snapshot.md「## 增量 4 設計:真的網路呼叫、最小決策規則與 trace」整段(核心概念延伸、三個用戶端、事件與 trace、S42~S53、不做的事)。鏡頭:站在攻擊者這邊找能被利用的洞,兼看邊界情況。輔助讀了 `src/rtb/httpkit.py`、`src/rtb/dsp/server.py`、`src/rtb/executor/inbox_server.py`、`src/rtb/executor/inbox_store.py`、`src/rtb/analyzer/flow.py`、`src/rtb/sqlitekit.py`,以及 `docs/rtb-production-agent-demo-knowledge/Projects/RTB_Agent_Phase0架構.md`。以下五條,第一條 blocker、二到四 major、第五條 minor。

### 1. dsp_client 與 inbox_client 完全沒有訂逾時,而「對方掛了就永遠卡住」正是這個增量最該擋的事

severity: blocker
blocking: 是 這個增量的整個賣點就是把假物件換成真的網路呼叫,而 DSP 自己就有一種故障模式是「接受連線後刻意不回應、不提交」;沒有逾時,urllib.request 在這種情境下預設會無限期卡住,不是靠故障旗標才會發生,一般網路壅塞或 DSP 過載就足以自然重現。整條 advance() 單任務推進的安全語意,建立在每一步都會回來這個假設上,一旦卡死就沒有任何機制能把它救回來,必須訂下逾時值才能開工。
引句:「任一個失敗(逾時、連線失敗、4xx/5xx)整個函式往外丟例外,不吞、不回傳半套」

這句話把「逾時」列為 dsp_client 應該處理的失敗類型之一,但整段設計裡沒有任何地方說逾時「怎麼被觸發」。標準函式庫 `urllib.request.urlopen()` 在不傳 `timeout` 參數時會無限期等待連線與讀取(不會自動逾時),而增量 4 的 PRIOR-ART 明講「採用:標準函式庫 urllib.request」,卻完全沒有配一個逾時值或沿用共用基礎的逾時常數。

- file: `src/rtb/httpkit.py:20`-`26` — 共用基礎只定義了**伺服器端**的逾時常數(`SOCKET_TIMEOUT_SECONDS`、`REQUEST_DEADLINE_SECONDS`),模組裡沒有任何客戶端逾時常數、也沒有 `urllib.request` 的匯入或輔助函式可讓 dsp_client/inbox_client 引用。
- file: `src/rtb/dsp/server.py:168`-`170` — DSP 的 `timeout_before_commit` 故障模式就是「先 `time.sleep(hang_seconds)`,再 `raise NoResponse`(刻意不回應)」;這正是 urllib.request 沒設 `timeout` 時會被卡住的那種連線型態,而且不需要 `--fault-injection` 也能自然發生(DSP 忙、網路慢)。
- 全庫掃過一遍(`grep -rn "urllib.request\|urlopen\|timeout=" src/rtb`)目前完全沒有任何客戶端逾時的既有寫法可以援引,說明這不是「設計沒寫但實作自然會補上」的小事,是這個增量第一次真的要面對這個問題,而設計文本對此保持沉默,也沒有像其他風險一樣附上 REVISIT。

### 2. too_many_revisions 被 S46 的「409 或 422 一律轉 SubmitStale」吸進同一桶,是一個攻擊者可誘發、沒有出口的重試迴圈

severity: major
blocking: 是 一旦被觸發,advance() 會對同一個 task_id 永遠重複真的 HTTP 呼叫(蒐證 + 送出),不會自然停止;增量 4 的「不做的事」明講不引入新的重試策略,所以沒有其他機制能接住它,是可以被操弄指標數字誘發的資源耗盡路徑。
引句:「409(`content_conflict`/`revision_out_of_order`)或 422(`expired_proposal`/`expiry_too_far`/`created_in_future`)轉 `SubmitStale`」

收件口的 409 實際上有三種代碼,不是兩種:`ContentConflict`、`RevisionOutOfOrder`,以及 `TooManyRevisions`(同一任務修訂數超過上限 50,見 `src/rtb/executor/inbox_store.py:22` 的 `MAX_REVISIONS_PER_TASK = 50`,註解寫「要更多就得換任務編號」)。`TooManyRevisions` 對應的 HTTP 狀態同樣是 409(`src/rtb/executor/inbox_server.py:51`),但增量 4 這段文字列舉 409 底下只寫了 `content_conflict`/`revision_out_of_order`,沒提 `too_many_revisions`;而 S46 的判準是照 HTTP 狀態碼分類(「當收件口回應 409 或 422」),不是照錯誤代碼,所以字面上 `too_many_revisions` 一樣會被歸進 `SubmitStale`。

問題在於 `SubmitStale` 目前只有一種處理方式:`src/rtb/analyzer/flow.py:167-168` 的 `_from_proposed` 收到 `SubmitStale` 一律回 `COLLECTING_EVIDENCE` 重新蒐證、重新分析、重新送出下一個修訂。但 `too_many_revisions` 的意思不是「證據過期、換個修訂就好」,是這個 task_id 已經沒有下一個可用修訂——重新分析只會產生修訂 51、52……,再送一次還是同一個錯誤,永遠回不到終點狀態,也永遠不會被判定成 FAILED。若攻擊者(或單純不巧的指標)讓配速訊號在 0.5 門檻附近反覆震盪(見下方「核心概念延伸」與 S49 的配速規則),就能讓同一任務反覆進出 `ANALYZING → PROPOSED → 送出`,把修訂數推過上限,觸發這個沒有出口的迴圈,持續消耗真實的 DSP 讀取與收件口寫入呼叫。這正是增量 3 自己在「已知限制」承認過的「反覆重新規劃沒有次數上限」風險,但這裡是這個增量親手把它從「理論風險」變成「收件口設了 50 次上限、分析端卻沒有對應的放棄路徑接住」的必然結果。

### 3. 「不小心讓分析端連得到故障注入」這句話涵蓋兩個伺服器,但 S44/S52 只替 DSP 寫了合約,inbox 的 X-Fault 沒有對稱保證

severity: major
blocking: 是 inbox_server 跟 DSP 一樣有故障注入標頭(`crash_before_commit`/`crash_after_commit`),而且它保護的是整個系統裡權限最高的一段(唯一有權寫 DSP 的執行行程的收件交易);分析端(被劫持機率最高的一側,見 Phase0 決策 d9/d10)一樣是呼叫它的那一方,卻沒有任何一條 S 編號要求 inbox_client 不能送 X-Fault,也沒有「inbox 沒開故障旗標時整套流程全部成功」這種等價於 S52 的機械斷言。
引句:「不小心讓分析端連得到故障注入」

這句話出現在增量 4「事故」段落,描述的是這個增量要補的三類新風險之一,語意上沒有限定只指 DSP;但緊接著的合約段落只寫了 S44(dsp_client 原始碼與公開介面不出現 X-Fault)與 S52(DSP 不開旗標時全程成功、沒有任何請求帶 X-Fault),兩條都只提 dsp_client / DSP。inbox_client 對應的 S45~S48 只講狀態碼怎麼對應到 Accepted/SubmitStale/SubmitBusy,完全沒有這一類保證。

- file: `src/rtb/executor/inbox_server.py:44` — `FAULT_MODES = frozenset({"crash_before_commit", "crash_after_commit"})`,證實 inbox 端確實存在跟 DSP 對等的 X-Fault 攻擊面,且同樣由啟動旗標 `fault_injection` 控制(`src/rtb/httpkit.py:58`、`src/rtb/executor/inbox_server.py` 的 `read_fault` 沿用共用基礎)。

若照增量 4 現在的文字實作,inbox_client 有沒有能力送 `crash_before_commit`/`crash_after_commit`,沒有任何一條測試會去檢查——這條邊界從增量 2 引入 inbox 故障注入以來,一直沒有被任何一輪合約明確承諾過。

### 4. S44「原始碼與公開介面都不出現 X-Fault」的「沒有公開介面」半句,目前只有文件宣稱,講不出機械驗證的做法

severity: major
blocking: 是 「原始碼不含這個字串」跟「公開介面沒有辦法送出這個標頭」是兩個不同強度的保證,只有前者能被單純的字串掃描機械驗證;後者需要對函式簽章或呼叫行為做檢查(例如用 `inspect.signature` 斷言公開函式沒有 headers/kwargs 這類參數,或嘗試以自訂標頭呼叫並斷言被拒絕)。設計文字只承諾了結論,沒有承諾驗證方式,S44 掛的測試名稱本身也看不出用哪一種做法,若之後有人替 dsp_client 加一個「額外標頭」之類的通用參數,字串掃描類的測試不會發現。
引句:「程式碼裡完全不出現 `X-Fault` 字樣,也不提供任何插入自訂標頭的公開參數」

這正是「如果 dsp_client 把整個 headers dict 開放給呼叫端自訂,理論上還是繞得過去」這條顧慮:文字本身已經意識到這個風險並排除了它,但排除的方式停在「不提供」這句宣稱,沒有指定要用什麼機械手段去證明「不提供」這件事本身沒有被之後的改動破壞。相較之下,增量 2 的 S16 用了更嚴格的寫法(「收件口模組不得自帶欄位驗證」,並且用「增量 1 解析器拒絕的每一份樣本收件口都得回 4xx」這種可重現的行為測試去逼近它),S44 目前的可驗證強度明顯較弱。

### 5. dsp_client/inbox_client 是否重用連線,設計完全沒交代

severity: minor
blocking: 否 這一版的 advance() 一次只推進一個任務(增量 3、4 都明講不做多任務併發排程),對本機 loopback 而言每次呼叫都新建連線的成本很低,不構成立即的安全或可用性風險;只是效能/資源面的空白,等 Phase 3 之後真的要多任務併發或跨行程長時間輪詢時才會變重要,而且不影響任何一條既有合約的正確性。
引句:「採用:標準函式庫 `urllib.request`,trace 是既有 SQLite 表格模式的延伸,不引入新依賴」

`urllib.request.urlopen()` 在最簡單的用法下不會重用底層 TCP 連線,每次呼叫都是獨立的 connect;設計裡沒有提到要不要用 `http.client.HTTPConnection` 搭配 keep-alive 或某種連線池。目前不是漏洞,但若 Phase 3 之後把「一次只推進一個任務」的限制拿掉,沒有連線重用配合 `httpkit.py:26` 的 `MAX_CONNECTIONS = 64` 上限,短時間內大量任務同時推進時,客戶端這一側新建連線的開銷會比伺服器端的連線數上限更早成為瓶頸,屆時要記得回頭看這條。

## 其他已檢查、沒有發現問題的項目

- **tool_calls 表存的內容**:欄位明確限定為「任務編號、對應的檢查點序號、呼叫的端點、狀態碼或例外類型、耗時、時間戳」,沒有「回應內容」或「請求內容」這類欄位,跟收件口既有事件表「絕不存請求原文」的紀律一致,沒有意外存進敏感資訊的設計缺口。
- **S52 的機械可驗證性**:確認 `DspHandler.handle_request`(`src/rtb/dsp/server.py:81`)對每一個路由都無條件呼叫 `self.read_fault(FAULT_MODES)`,旗標關閉時任何帶 X-Fault 的請求一律先被拒絕(400 `fault_injection_disabled`),不會被個別路由繞過;所以「整套正常流程全部成功」確實可以間接證明「沒有任何一次請求帶 X-Fault」,S52 這個等價關係本身是站得住的(但見上面第 3 條,這個保證目前只替 DSP 寫,沒有替 inbox 寫)。
- **trace 查詢(S51)跨任務洩漏**:這段設計裡的 trace 查詢是本機依 task_id 兜三張表,增量 4 沒有替它開任何 HTTP 端點對外曝露,現有程式庫裡也沒有發現任何一處用字串組合(f-string/`.format()`)拼 SQL 的先例(掃過 `inbox_store.py`、`task_store.py`、`dsp/store.py` 全部用 `execute()` 帶參數),沒有看到可被外部呼叫者觸發的跨任務洩漏路徑;風險僅止於「文件沒有明講查詢一定要用參數化 SQL」這種弱提醒,不構成成立的 finding。
- **policy.py 操弄指標誘導提案**:在增量 4 現有範圍內,DSP 的指標資料沒有描述任何外部可寫入的管道(只有執行行程能寫 DSP),配速公式本身的輸入不是攻擊者能直接餵入的欄位;能找到的可乘之機收斂到上面第 2 條「反覆震盪誘發 too_many_revisions 無限迴圈」,已經另列一條,不重複計。
