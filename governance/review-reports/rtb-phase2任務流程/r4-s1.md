severity: major

審查範圍:r4-snapshot.md「## 增量 4 設計:真的網路呼叫、最小決策規則與 trace」整段(核心概念延伸、三個用戶端、事件與 trace、S42~S53、不做的事)。鏡頭:正確性與可測性。輔助讀了 `src/rtb/dsp/server.py`、`src/rtb/executor/inbox_server.py`、`src/rtb/executor/inbox_store.py`、`src/rtb/dsp/store.py`、`src/rtb/domain/evidence.py`、`src/rtb/domain/proposal.py`、`src/rtb/domain/metrics.py`、`src/rtb/analyzer/flow.py`、`src/rtb/analyzer/task_store.py`。以下五條,前四條 major、第五條 minor。

### 1. dsp_client 的 content_hash 正規化演算法完全沒定義,S42~S53 也沒有對應的等價性測試

severity: major
blocking: 是 沒有定義好的演算法,實作者寫不出一條「等價寫法得到同一個雜湊」的紅燈測試;增量2對提案雜湊有完整演算法(轉基本型別、UTC、鍵排序、無多餘空白、禁 NaN),這裡完全沒有對應描述。
引句:「`content_hash` 是回應內容正規化後的 SHA-256」

對照增量 2 的 `content_hash()`(`src/rtb/domain/proposal.py:294-306`):明確定義「轉成基本型別、時間換 UTC、以固定鍵排序、無多餘空白、不允許 NaN 的 JSON 序列化」,並且有專屬合約 [S17]「內容雜湊應與時區表示法無關…並且欄位順序、空白不同的等價 JSON 得到同一個雜湊」與對應測試。

`dsp_client` 的 content_hash 只有一句「回應內容正規化後的 SHA-256」,沒有說「正規化」包含哪些步驟(哪些欄位參與、鍵序、時間格式、是否包含 HTTP 層無關的雜訊如標頭)。S42/S43([S42]「當 DSP 的現況與指標兩個請求都成功,應回傳兩筆證據」、[S43]「任一個請求失敗,應整個丟出例外」)只測「回傳幾筆/失不失敗」,完全沒有任何一條測試對應增量2的 S17 等級的雜湊一致性要求。`Evidence.content_hash` 欄位本身在 `src/rtb/domain/evidence.py:55,67,74-75` 只驗證格式(64 位小寫十六進位),不驗證語意,所以這個坑不會被機械擋住。即使目前 content_hash 沒有被拿去做相等比對(不像提案雜湊用來判斷 409 衝突),它仍是 S51 trace 要拿來佐證「有沒有讀到同一份現況」的關鍵欄位;沒有明確演算法,兩個不同時期或不同人寫的 `dsp_client` 對同一份真實狀態可能算出不同雜湊,trace 對不上時查不出是「內容真的變了」還是「雜湊寫法不同」。

### 2. policy.py 的配速公式沒處理除以零與缺值,字面實作會用例外打破 S49 承諾的 NoAction,且沒有重用 domain/metrics.py 已有的「沒有值」設計

severity: major
blocking: 是 DSP 的指標欄位本來就允許 None(空值),初始或未進流量的廣告是很自然會撞到的情境;字面實作會丟未捕捉的例外或把「不知道」誤判為「有」,直接違反 S49 自己承諾的「其餘情況應回傳 NoAction」。
引句:「規則:用指標算配速(過去一小時花費 ÷ (預算/24))」

三個具體坑:
1. **除以零**:`預算/24` 當預算為 0 時整條公式除以零。DSP 的 `campaigns.budget` 只有在 `update_budget` 這條寫入路徑才驗證 `0 < budget`(`src/rtb/dsp/store.py:121-124`),`seed_campaign(...)` 建立初始資料時完全不驗證(`src/rtb/dsp/store.py:183-186`),0 預算的廣告是可達狀態。
2. **缺值當非零**:「曝光、點擊都不是 0」若字面寫成 `impressions != 0 and clicks != 0`,而 DSP 的 `impressions`、`clicks`、`spend` 全部是可為 None 的欄位(`src/rtb/dsp/store.py:93-94,96`,且 `_checked_metric` 明講「沒給的欄位維持 None,不補成 0」`src/rtb/dsp/store.py:139-140`),`None != 0` 在 Python 是 `True`,會把「不知道有沒有曝光」誤判成「真的有在投放」,恰好違反這句話本來想防的事(避免把設定壞了/沒資料當成真實投放)。
3. **與既有設計脫節**:`src/rtb/domain/metrics.py` 已經有現成的 `pacing(spend, budget, elapsed_fraction)`(`src/rtb/domain/metrics.py:132-152`),用 `MetricResult`(`src/rtb/domain/metrics.py:29-61`)把「分母為零」「資料缺漏」「資料不合理」三種「沒有值」分開,且 `elapsed_fraction=1/24` 剛好對應這裡「過去一小時」的用法。增量 4 這段完全沒提要不要重用它,也沒有等效地處理這三種空值,等於在 policy.py 另開一條沒有防護的除法。

S49([S49]「當配速明顯偏低且曝光與點擊都不是零…其餘情況應回傳 NoAction」)沒有列出「預算為 0」「指標缺值」這兩種輸入該怎麼辦,而按目前字面寫法它們會拋例外而不是回傳 NoAction——這正是 S49 自己劃給「其餘情況」的承諾範圍,卻被字面實作打破。

### 3. inbox_client 的 409 分類漏掉 too_many_revisions,而且這個狀態不管分類成哪一邊都會讓任務卡進無限重試迴圈

severity: major
blocking: 是 too_many_revisions 是收件口真實會回的第三種 409,且是「永久不可能成功」的錯誤;不管把它歸進 SubmitStale 還是讓它原樣往外傳(未分類/可重試),increment 3 既有的狀態機都沒有一條路能讓任務終止,會無限迴圈重試。
引句:「409(`content_conflict`/`revision_out_of_order`)或 422」

收件口的 409 實際上有三種代碼:`ContentConflict`(`content_conflict`)、`RevisionOutOfOrder`(`revision_out_of_order`)、以及 `TooManyRevisions`(`too_many_revisions`,見 `src/rtb/executor/inbox_store.py:83,86,109-110`,對應 HTTP 狀態在 `src/rtb/executor/inbox_server.py:51`「`TooManyRevisions: 409`」),上限是 `MAX_REVISIONS_PER_TASK = 50`(`src/rtb/executor/inbox_store.py:22`,註解明講「要更多就得換任務編號」)。增量 4 的 inbox_client 段落只列了前兩個代碼歸 `SubmitStale`,完全沒提 `too_many_revisions`。

這不是可以事後補一行分類就解決的小事:
- 若把它也歸進 `SubmitStale`:`_from_proposed` 對 `SubmitStale` 的處理是「回 COLLECTING_EVIDENCE 重新蒐證分析」(`src/rtb/analyzer/flow.py:167-168`),但這個任務的問題不是證據過期,是修訂數已經到頂——重新分析只會產出下一個修訂(51、52…),再送一次還是同一個 too_many_revisions,永遠回不到終點。
- 若照字面「其餘一律讓例外原樣往外傳」不分類:落進 `_from_proposed` 最後的 `except Exception: return None`(`src/rtb/analyzer/flow.py:171-172`),狀態留在 PROPOSED 當作暫時性,一樣永遠重試同一份必敗的提案。

不管走哪一條,都跟增量 3 自己在「已知限制」承認的「COLLECTING_EVIDENCE 到 ANALYZING 或 PROPOSED 之間反覆重新規劃的迴圈沒有次數上限」的風險正面相撞,而且是這個增量親手把它從「理論風險」變成「一定會發生的無限迴圈」(收件口本來就設了 50 次上限來擋失控,分析端卻沒有對應的「放棄並轉 FAILED」路徑接住)。S46~S48 都沒有涵蓋這個狀態,無法寫出一條紅燈測試對應它。

### 4. S51「重建 trace」沒有具體介面設計,查詢方式與 tool_calls 的「對應檢查點序號」語意都是空的

severity: major
blocking: 是 S51 掛著測試名稱但沒有可依據的函式簽章、回傳形狀或連接鍵定義;在並行衝突（S37）或蒐證中途失敗（S26）時,tool_calls 該記哪一個序號完全沒講,無法把 test 寫成會翻紅的具體斷言。
引句:「給定一個任務編號,應該能從 tasks、evidence、tool_calls 三張表重建出一條連結證據」

段落原文只說「trace 是查詢,不是新表」(引句:「trace 是查詢,不是新表:給定一個任務編號,把 tasks(狀態史)、evidence(證據)、tool_calls(呼叫記錄)三張表用任務編號兜起來」),沒有給出:
- 這個查詢住在哪個模組、叫什麼名字、簽章長怎樣(輸入 task_id,輸出是什麼型別?)。
- tasks/evidence 的連接鍵是 `task_seq`(有 schema 可查,`src/rtb/analyzer/task_store.py:23-31`),但 tool_calls 的「對應的檢查點序號」連接到哪個序號沒有定義清楚:呼叫發生在 `commit_step` 之前(`src/rtb/analyzer/flow.py:121-125`),當時還不知道新列會不會真的寫入(`commit_step` 核對 `expected_seq` 失敗會回 `False`,不寫入,見 `src/rtb/analyzer/task_store.py:191-192`,對應 S37)。若外呼成功但這次 `commit_step` 因為並行衝突沒有真的提交(S37 場景),或外呼失敗導致整個 `_from_collecting_evidence` 不寫入(S26 場景,`src/rtb/analyzer/flow.py:139-140`),tool_calls 那一列該標記成呼叫發生時的現有序號、還是「原本想達成」但沒發生的下一個序號?兩種選擇都合理,但沒有任何一句話裁定,S51 的測試因此寫不出明確的斷言(重試多次會產生多筆 tool_calls,但只有一組 evidence 真正落地,測試要斷言「查得到」還是「查到的筆數對得上」,現在沒有依據)。

### 5. tool_calls 寫在交易外,但這筆寫入自己失敗時要怎麼辦沒有合約

severity: minor
blocking: 否 不會造成資料損毀或狀態機出現非法轉換,最壞情況只是這次外呼被 `_from_collecting_evidence`/`_from_proposed` 既有的「未定義例外視為可重試」機制吞掉、多重試一次,不影響最終正確性,所以是可以之後再補的空白,不是現在就會做錯事的漏洞。
引句:「寫入這張表不跟狀態推進同一個交易(呼叫本身在交易外,失敗要能記下來,不能因為這筆記錄失敗而讓整個檢查點卡住)」

增量 2 對「事件寫入失敗」有明確合約:[S14]「事件紀錄應只存固定欄位…且事件寫入失敗時對呼叫者的回應不變」。增量 4 的 tool_calls 只說「失敗要能記下來,不能因為這筆記錄失敗而讓整個檢查點卡住」,但沒有像 S14 那樣把它寫成一條可測的合約(tool_calls 寫入本身拋例外時,呼叫端的行為該固定成什麼)。實務上這個空白會被 `_from_collecting_evidence`/`_from_proposed` 既有的外層 `except Exception` 蓋住(當成外呼失敗、safe retry),所以不會做出錯的行為,只是浪費一次重試——因此定為 minor,建議補一條對應 S14 風格的合約,但不構成擋審的理由。
