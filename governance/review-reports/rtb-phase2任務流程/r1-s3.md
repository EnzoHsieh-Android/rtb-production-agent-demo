# r1-s3 安全鏡頭審查(增量 2 設計:提案收件口)

範圍:快照「## 增量 2 設計」到「## 回退」。攻擊者模型:被 prompt injection 誘導的分析行程,或任何能連到回送埠的程式與網頁。

### 1. 高修訂序號搶位:一次呼叫就永久卡死該任務
severity: major
blocking: 是 S3 只比大小,沒有「只准 +1」或「前一份須已處理」的限制;解析器上限是一百萬,攻擊者送 revision=1000000 即可讓該任務之後所有正常修訂被拒;S8 讓已過期的提案照樣被收下,所以連「過期」也不能釋放這個位置;任務編號可任意造,攻擊者可預先為尚未出現的任務編號搶位。設計沒有任何撤銷或釋放路徑。
引句:「當收件口收到修訂序號低於同一任務已收最高序號的請求,收件口應拒收。」
file: `src/rtb/domain/proposal.py:154`

### 2. 在途上限可被洪水填滿,且沒有釋放條件與每任務配額
severity: major
blocking: 是 上限是全域常數、不做身分認證,攻擊者用不同任務編號各送一份合法提案即可佔滿,之後所有正常提案得到 503,而收件口是唯一入口。設計沒定義「在途」何時結束(過期算不算、Phase 3 才會處理),也沒有每任務或每來源的配額;若已過期的提案不算在途,S8 又變成不受上限限制的無界寫入(磁碟填滿)。
引句:「若收件表的在途提案數已達上限,收件口應回明確的 503 且不寫入。」

### 3. 衝突事件記錄:無界寫入,且內容來源未限定
severity: major
blocking: 是 每個衝突請求都寫一筆事件,S5 的上限只算在途提案、不算事件,攻擊者重複送衝突請求就能無界增長磁碟並拖慢單一 SQLite 寫入者。設計也沒說事件記什麼:若記原始本文或使用者可控欄位(例如 unknown_field 的鍵,解析器回傳前 64 字元原樣帶出),攻擊者內容會進入日誌,被日後人或模型讀取時成為二次注入通道。須明訂只記雜湊、任務編號、修訂序號與固定代碼,並設事件筆數上限或聚合。
引句:「收件口應以 409 拒收、不改動已收的那一份,並記一筆衝突事件。」
file: `src/rtb/domain/proposal.py:223`

### 4. S7 只擋 DNS rebinding,擋不住瀏覽器跨站直接 POST(CSRF)
severity: major
blocking: 是 使用者瀏覽器中的任何網頁可對 http://127.0.0.1:埠 發出 text/plain 的簡單 POST,Host 標頭恰為合法回送位址,S7 全數放行;S4 沒有要求 Content-Type 或檢查 Origin,埠可被掃描。這讓「不做身分認證」的已知限制從「本機行程」擴大到「任何開著的網頁」,並可用來執行洞 1 與洞 2。範圍節只承認缺認證,沒承認這條。另 `_check_host` 對 HTTP/1.0 缺 Host 直接放行,若收件口沿用,S7 的「拒絕 Host 不是回送位址」對缺 Host 沒有定義。
引句:「收件口應只綁定本機回送位址,並拒絕 Host 標頭不是回送位址的請求。」
file: `src/rtb/dsp/server.py:137`

### 5. 內容雜湊的序列化參數未釘死
severity: minor
blocking: 否 只說「固定的鍵排序」,沒定案 ensure_ascii、分隔符、時間格式(同一瞬間的 Z 與 +08:00 經 isoformat 會產生不同字串,導致合法重送被誤判成衝突)。雜湊輸入取自解析後的 to_primitives,鍵順序與空白差異已被消除,且提案欄位有白名單,未見能讓兩份不同提案碰撞的路徑,所以只影響誤拒,不構成越權;實作時把序列化參數寫進測試即可。
引句:「以固定的鍵排序序列化後取 SHA-256;這個雜湊函式增量 2 新增」
file: `src/rtb/domain/proposal.py:76`

## 檢查過但不成立
- 雜湊碰撞:SHA-256 無實用碰撞;JSON 重複鍵後者覆蓋、new_budget 只收純整數,無雙重序列化歧義。
- 錯誤訊息洩漏:解析錯誤只含欄位名與固定代碼,未見內部路徑或堆疊;伺服器未預期例外回泛型 internal_error。但 S1 的「回上次的結果」與 S2 的 409 本文內容未定義,實作不得回傳已收提案內容。
- S3/S5 檢查與寫入的競態:若以資料表唯一約束加同一交易處理,最壞只是略超上限,無越權;建議設計明寫「檢查與寫入同一交易」。
