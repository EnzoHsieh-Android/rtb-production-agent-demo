## F1 超大整數預算讓伺服器無回應斷線,永久錯誤被偽裝成模糊逾時

severity: major
blocking: 是 客戶端可控輸入造成永久性失敗卻不回型別化錯誤,呼叫端無法分辨,與設計的「型別化錯誤」目的相反。

- 位置:store.py 的 `_validate` 與 server.py 的 `_dispatch`。
- 引句:「if not isinstance(budget, int) or isinstance(budget, bool) or budget <= 0:」
- 引句:「except DspError as exc:」
- 輸入:POST /campaigns/c1/budget,body `{"new_budget": 1180591620717411303424, "expected_version": 1}`(2**70)。
- 路徑:`_validate` 通過(是 int、>0)。`_apply` 的 UPDATE 拋 `OverflowError: Python int too large to convert to SQLite INTEGER`。`execute` 的 `except BaseException` 有 ROLLBACK,狀態沒被改(store 層正確)。例外不是 DspError,`_dispatch` 沒有對應分支,只跑 finally。`handle_error` 又被覆寫成 `pass`,連日誌都沒有。
- 重現(h.py 對真行程):`overflow ('RemoteDisconnected', 'Remote end closed connection without response')`。store 直接呼叫:`OverflowError`。
- 後果:agent 看到的是連線被斷、沒有回應,與「提交後逾時」的表象相同,依設計會拿同一把鍵重送,永遠得到同樣的斷線。永久性錯誤被當成需要對帳的模糊逾時。
- 建議:`_validate` 加上界(SQLite INTEGER 為 2**63-1),並在 `_dispatch` 對非 DspError 的例外回 500 JSON 而不是靜默斷線。

## F3 冪等指紋含 expected_version:同鍵、同 payload、不同預期版本得到 422,不是重放

severity: minor
blocking: 否 與已通過的設計相容(指紋定義如此),但對重試流程有實際後果,需確認是設計意圖。

- 位置:store.py 的 `Operation.fingerprint`。
- 引句:「body = [self.campaign_id, self.action, self.params, self.expected_version]」
- 輸入:k1 以 expected_version=1 提交成功(版本變 2)。呼叫端逾時後重新讀取,見版本 2、預算 150,以 k1、同預算、expected_version=2 重送。
- 路徑:`_existing_operation` 找到鍵,指紋(含 2)不等於紀錄(含 1),拋 `IdempotencyConflict`,回 422 不可重試。實際上該操作早已套用。
- 重現(exp.py):`B -> IdempotencyConflict`。
- 相關:expected_version 沒有型別驗證。JSON 的 1.0 通過版本檢查(`1 != 1.0` 為 False)並提交,之後同鍵以整數 1 重送得 `IdempotencyConflict`(exp.py `C float ev: 2` 接著 `C retry int -> IdempotencyConflict`)。缺 expected_version 時預設 0,回 409 version_conflict,不是 400 的驗證錯誤(h.py `no expected_version (409, ...)`)。
- 建議:重送必須沿用原提案的 expected_version 要寫進呼叫端契約。expected_version 應驗證為整數(非 bool),缺少時回 422。
