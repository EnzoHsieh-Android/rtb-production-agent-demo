# r1-c2 併發與資源鏡頭

基準:25 條測試全綠(本人重跑確認)。實驗檔在 /private/tmp/c2x 底下,repo 未動。

## 已驗證沒問題的假設

- BEGIN IMMEDIATE 自己失敗時,例外在 try 之外,不會接著 ROLLBACK,路徑正確。
- 別的連線持有寫鎖時,新連線 `PRAGMA journal_mode=WAL` 加 executescript 不會被擋(實測 0.0 秒),GET 照常 200(0.0 秒)。
- 寫鎖被佔超過 5 秒時,POST 回 503 store_busy retryable,耗時 5.3 秒,符合設計。
- 故障注入的 sleep 期間沒有開著的交易:timeout_before_commit 在 execute 之前睡,timeout_after_commit 在 COMMIT 之後睡。只有一條空閒連線(沒有讀取快照、沒有鎖),不擋別人的寫入與 checkpoint。
- daemon_threads=True 正確,慢請求不會拖住關閉。

## findings

severity: minor
blocking: 否 錯誤仍是 OperationalError,只是訊息被蓋掉,不改變資料正確性,屬診斷品質問題。

檔案 src/rtb/dsp/store.py 的 execute。引句:「self._conn.execute("ROLLBACK")」。

問題:except BaseException 裡的 ROLLBACK 沒有保護。SQLite 在 SQLITE_FULL 這類錯誤時會自行回滾整個交易,之後顯式 ROLLBACK 會丟 `cannot rollback - no transaction is active`,把真正的原因(磁碟滿)蓋掉。COMMIT 失敗後同理:只要 ROLLBACK 再丟,原始例外就只在例外鏈裡,而不是主例外。

重現(/private/tmp/c2x/e1.py):對 store 設 `PRAGMA max_page_count` 為目前頁數,填滿後呼叫 execute。
輸出:`execute err 36 OperationalError cannot rollback - no transaction is active | in_tx: False`。
預期看到的是 `database or disk is full`。

建議:ROLLBACK 包 try/except sqlite3.Error 後 pass,或用 `if self._conn.in_transaction`,讓原始例外原樣拋出。

severity: minor
blocking: 否 只在 BEGIN IMMEDIATE 遇到非忙碌類錯誤時發生,mock 環境罕見,且會把永久錯誤標成可重試。

檔案 src/rtb/dsp/store.py 的 execute。引句:「raise StoreBusy(str(exc)) from exc」。

問題:BEGIN IMMEDIATE 的所有 sqlite3.OperationalError 都被當成 StoreBusy(503,retryable=true),不只是 `database is locked`。唯讀資料庫、IO 錯誤等永久性故障會被告知呼叫端「同一把冪等鍵可以安全重試」,與型別化錯誤要分辨可重試與永久的目的相反。

重現(/private/tmp/c2x/e2.py):連線設 `PRAGMA query_only=1` 後 execute。
輸出:`query_only -> StoreBusy attempt to write a readonly database`。

建議:只有訊息含 locked 或 busy(或 sqlite_errorcode 為 SQLITE_BUSY/SQLITE_LOCKED)才轉 StoreBusy,其餘原樣拋出。

severity: minor
blocking: 否 只影響異常路徑的回應形態(斷線而不是 500),資料不受影響。

檔案 src/rtb/dsp/server.py 的 _dispatch。引句:「except _NoResponse:」。

問題:except 鏈只接 RequestRejected、DspError、_NoResponse,沒有兜底。任何其他例外(store.execute 內的 OperationalError、Content-Length 非數字造成的 ValueError)都讓處理執行緒直接結束,handle_error 又被覆寫成 pass,所以連日誌都沒有,客戶端只看到連線被關。這和 timeout_before_commit 的「刻意不回應」在客戶端看來無法區分,寫入結果是否已提交也無從判斷。

重現(/private/tmp/c2x/e3.py):
- `Content-Length: abc` 的 POST 得 `RemoteDisconnected: Remote end closed connection without response`。
- 對 chmod 444 的資料庫 POST,同樣得 RemoteDisconnected(store 端丟 OperationalError)。

建議:加一個 except Exception 回 500 並寫一行 stderr。

severity: minor
blocking: 否 僅回送位址上的自傷型輸入,不持有交易或鎖,客戶端一走就釋放。

檔案 src/rtb/dsp/server.py 的 _read_json。引句:「length = int(self.headers.get("Content-Length") or 0)」。

問題:負數長度通過 `length > MAX_BODY_BYTES` 檢查,`rfile.read(-1)` 會讀到客戶端關閉連線為止。處理器也沒有 socket 逾時(BaseHTTPRequestHandler.timeout 為 None)。因此一條連線可以無限期佔住一個執行緒和一條已開啟的資料庫連線(_dispatch 一開頭就建了 store)。

重現(/private/tmp/c2x/e3.py):`Content-Length: -1` 且不送 body,客戶端 2 秒逾時,伺服器在客戶端離開前一直阻塞。
輸出:`negative CL: ('TimeoutError', 'timed out') 2.0`。

建議:length 小於 0 回 400,並在 handler 設 `timeout = 10` 之類。

severity: minor
blocking: 否 只發生在測試的例外路徑,正常路徑 teardown 都會收乾淨。

檔案 tests/dsp/conftest.py 的 start_dsp 與 DspProcess。引句:「started.append(proc)」。

問題:DspProcess 在 __init__ 裡 Popen 之後才 readline 與 assert,而 started.append 在建構子回傳之後。因此:
- 子行程若先印出別的 stdout 行(例如 warning),assert 失敗,子行程仍活著,卻沒被登記,teardown 不會殺它。
- readline 沒有逾時。子行程存活但不印 PORT 時,測試會永遠卡住。
- 失敗時 stdout 管道沒有關閉。
- stop() 中 kill 後 wait(timeout=5) 若丟 TimeoutExpired,不會呼叫 stdout.close(),teardown 迴圈也在第一個例外就中斷,後面的行程不再處理。

重現(/private/tmp/c2x/t/test_orph.py):用 sh 包一層先 echo 一行雜訊再 exec 真正的伺服器,呼叫 DspProcess(db),assert 失敗。同一個 pytest 行程中的下一個測試對該 pid 做 os.kill(pid, 0) 成功。
輸出:`ORPHAN pid alive: 62699`。
補充:伺服器之後不再寫 stdout,所以 pytest 結束後不會因 SIGPIPE 死掉,可能變成孤兒行程(我的短實驗中 PORT 寫入時管道已關,子行程因此自己死了,長 session 則不會)。

建議:Popen 之後立即登記,或在 __init__ 用 try/except 失敗時 kill;readline 改用帶逾時的讀法。

severity: minor
blocking: 否 只在資料庫檔壞掉這類異常時依賴 GC 才關閉連線。

檔案 src/rtb/dsp/server.py 的 _dispatch。引句:「store = CampaignStore(self.server.db_path)」。

問題:建構在 try 之外,而 CampaignStore.__init__ 自己在 connect 之後還會跑 PRAGMA 與 executescript。這一段失敗時,連線物件不會被任何人 close,只能等垃圾回收。

重現:資料庫檔內容是垃圾文字,呼叫 CampaignStore("bad.db")。
輸出:`DatabaseError file is not a database`,接著 `ResourceWarning: unclosed database in <sqlite3.Connection object ...>`。

建議:__init__ 內用 try/except 在失敗時 self._conn.close() 後再 raise。

severity: minor
blocking: 否 只在數百個同時連線時出現,mock 的測試負載遠低於此。

檔案 src/rtb/dsp/server.py 的 DspServer。引句:「class DspServer(ThreadingHTTPServer):」。

問題:沒有調高 request_queue_size,預設 listen backlog 為 5。實測對本機 DSP 同時開 200 個執行緒各送 5 次請求(e4.py),約每兩次跑就有一次出現連線階段逾時。
輸出:`Counter({409: 743, 200: 200, 'TimeoutError:[Errno 60] Operation timed out': 57})`。
另一次跑全部成功(`{409: 800, 200: 200}`),所以是機率性。25 條測試用 20 個並行,未觸及。

建議:設 `request_queue_size = 128`。
