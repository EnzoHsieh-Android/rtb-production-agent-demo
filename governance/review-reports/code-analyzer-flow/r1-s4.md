### 1. `commit_step` 完全不理會、也不核對傳入證據自己的 `task_id`,會悄悄把別的任務的證據記成這個任務的

severity: major
blocking: 是 資料損壞——歷史表(審計紀錄)可以在沒有任何錯誤、沒有任何警告的情況下,把不屬於這個任務的證據悄悄記成屬於這個任務,之後讀回來也查不出曾經錯位過。
引句:「(item.evidence_id, task_id, next_seq, item.kind.value, item.source,」

寫入時用的是 `commit_step()` 自己的 `task_id` 參數,不是 `item.task_id`;讀回時 `evidence_for()` 也是直接用查詢參數 `task_id` 建構 `Evidence(...,task_id=task_id,...)`,完全沒有 SELECT 出實際存的 `task_id` 欄位來核對或還原。換句話說,`Evidence.task_id` 這個欄位從 `commit_step` 進來之後就被忽略、覆寫,不會被拿來檢查「這筆證據真的是這個任務的嗎」。

在臨時目錄實測(建一筆 `task_id="t2"` 的證據,傳給 `store.commit_step("t1", ...)`):

```
committed: True
fetched under t1: (Evidence(evidence_id='e-foreign', task_id='t1', ...)
original item.task_id was: t2
stored/fetched task_id is now: t1
```

`create_task`/`commit_step` 這一支歷史表存在的理由就是「只增不改,查得到事故當時真的發生了什麼」(見 task_store.py 檔首說明);如果 `EvidenceSource`(增量 4 真的去蒐證的實作)有任何配對錯誤的 bug,或呼叫端不小心把別的任務的證據混進來,這裡不會擋、也不會留下任何痕跡,審計紀錄本身就已經是錯的。建議:`commit_step` 在寫入前核對 `item.task_id == task_id`,不符就丟型別化例外,而不是靜默接受。

### 2. `evidence` 表的主鍵是全域唯一的 `evidence_id`(不是按任務或步驟區分),同一個 evidence_id 在任何時候再出現一次,`commit_step` 會整包沒接住地當機,任務永久卡住

severity: major
blocking: 是 破壞 flow.py 自己在檔首宣告的合約(「重複呼叫 advance() 在中斷後恢復是安全的」),而且是在 `NeedsFreshEvidence → COLLECTING_EVIDENCE` 這條設計裡明講會走到的重試路徑上會發生,不是邊緣情境。
引句:「evidence_id TEXT PRIMARY KEY, task_id TEXT NOT NULL, task_seq INTEGER NOT NULL,」

`evidence` 表的主鍵只有 `evidence_id` 一欄,沒有跟 `task_id`/`task_seq` 組成複合鍵。這代表同一個 `evidence_id` 只要在資料庫存在過一次,不論是同一個任務的下一步、還是完全不同的任務,都不能再插入第二次,否則違反 `PRIMARY KEY` 唯一限制。`commit_step()` 沒有針對這個 `sqlite3.IntegrityError` 做任何處理或轉型別(對照 `TaskAlreadyExists`/`TaskNotFound` 兩個自訂例外,這裡完全沒有對應的邊界例外)。

在臨時目錄實測(同一個 `evidence_id` 在第一次 COLLECTING_EVIDENCE 步驟提交後,模擬 `NeedsFreshEvidence` 繞回去再蒐證一次、蒐到的證據 id 沒變):

```
after first commit, seq: 2 state: collecting_evidence
EXCEPTION on duplicate evidence_id across steps: IntegrityError UNIQUE constraint failed: evidence.evidence_id
```

這個例外是未定型別的 `sqlite3.IntegrityError`,會直接從 `commit_step()`/`advance()` 冒出去,不會被 `flow.py` 裡任何 `except` 接住(`_from_collecting_evidence` 只接一般的 `Exception` 來自 `evidence_source` 呼叫本身,不含 store 端的 commit)。因為交易失敗會整包回滾,任務狀態不會前進;如果蒐證來源是決定性生成 `evidence_id`(例如用內容雜湊當 id,這在本專案別處是常見手法,見 `content_hash()`/收件口的冪等鍵設計),那麼只要蒐到的內容沒變,每次重呼叫 `advance()` 都會撞上同一個唯一鍵衝突、永遠當機,沒有自動復原的路。就算蒐證來源用隨機 id,只要有兩個不同任務剛好撞了同一個 `evidence_id`(在真的接上外部系統之前無法排除),也是同樣的當機。建議:主鍵至少改成 `(evidence_id, task_id, task_seq)` 或另加代理鍵,並且明確定義撞鍵時 `commit_step` 該怎麼回應呼叫端。

### 3. `create_task` 對 `task_id`/`campaign_id` 沒有任何格式或長度驗證,跟增量 1 `parse_proposal` 的嚴格白名單風格不一致

severity: minor
blocking: 否 目前沒有任何呼叫端把外部輸入直接餵給它(增量 4 的網路入口還沒接上),不會立刻造成錯誤行為;但這是這批程式碼裡唯一一個直接收原始字串(不是先建構已驗證過的網域物件)的公開寫入介面,缺的是縱深防禦而不是眼前就會炸的路。
引句:「def create_task(self, task_id: str, campaign_id: str, now: datetime) -> None:」

對照 `rtb.domain.proposal.parse_proposal` 對 `task_id`/`campaign_id` 都套用 `ID_PATTERN`(`[A-Za-z0-9._:-]{1,128}`,見 file: `src/rtb/domain/_checks.py:11`,在 `parse_proposal` 的 `CHECKS` 表裡對 `task_id`/`campaign_id` 都用它,見 file: `src/rtb/domain/proposal.py:164`、`src/rtb/domain/proposal.py:166`),`create_task` 完全沒有等價檢查。在臨時目錄實測:

```
empty ok: received                      # 空字串 task_id/campaign_id 直接接受
huge accepted, len stored: 5000000      # 5MB 的 task_id 也直接接受、直接寫進 SQLite
```

`InboxStore.accept()`/`CampaignStore` 的寫入口都是收「已經驗證過的網域物件」(`Proposal`、或測試用的 `seed_*`),不是像這裡一樣直接收裸字串當主鍵材料。等增量 4 真的把外部觸發(例如 DSP 事件)接上 `create_task` 時,這裡會是第一個、也是唯一一個沒有格式/長度上限的輸入口,值得在那之前先補上跟 `ID_PATTERN` 對齊的檢查,或至少在文件裡明講「validation 留給呼叫端做」是刻意決定。

### 4. `evidence_for()` 用 `ORDER BY evidence_id` 排序讀回,不保留原始蒐證/提交順序

severity: minor
blocking: 否 目前沒有任何 `Decide` 實作依賴證據順序(增量 4 才會真的寫 `decide()`),不影響這批程式碼本身的行為;但這是個容易在下一個增量被忽略的隱性行為,值得先點出來。
引句:「"ORDER BY evidence_id",」

`commit_step()` 寫入時是照 `evidence` 參數(呼叫端/`EvidenceSource` 回傳的順序)逐筆 INSERT,順序有被保留在寫入這一步;但 `_from_analyzing()` 決策前重新呼叫的 `store.evidence_for(row.task_id, row.seq)` 卻是照 `evidence_id` 字典序重新排序讀出來,不是插入順序、也不是原始蒐證順序。實測(蒐證回傳「先 metrics 後 campaign_state」,`evidence_id` 分別是 `z-metrics`、`a-state`):

```
original order (as returned by evidence_source): ['z-metrics', 'a-state']
order after round-trip through evidence_for():    ['a-state', 'z-metrics']
order preserved? False
```

空結果沒有問題:沒有任何一筆符合的 `evidence` 列時,`evidence_for()` 回傳空 tuple `()`,不會出錯。多筆結果排序本身是「穩定」的(同樣輸入永遠得到同樣順序),但穩定的是字典序,不是語意順序,如果之後 `Decide` 的實作(增量 4)隱含假設「evidence 的順序反映蒐證順序或重要性」,這裡會悄悄餵給它一份重排過的順序。建議在 `evidence_for` 的文件或簽章上明講「順序只保證確定性、不保證跟蒐證順序一致」,或改成照插入序(例如另開一個 rowid/自增欄位排序)。

### 5. `TaskStore.__init__` 沒有把 `connect()` 可能丟出的 `DatabaseBusy` 轉成自己的例外型別(跟 `CampaignStore`/`InboxStore` 不一致)——但確認不是連線洩漏

severity: minor
blocking: 否 不是資源洩漏(下面有查證),只是例外型別跟手足類別不一致,呼叫端要多認一種例外。
引句:「self._conn = connect(path, busy_timeout_seconds, SCHEMA)」

先澄清:`TaskStore.__init__` 建構失敗**不會**留下沒關的連線。`connect()` 自己在 PRAGMA/建表失敗時就會 `conn.close()` 再往外丟(file: `src/rtb/sqlitekit.py:33`、`src/rtb/sqlitekit.py:38`),`TaskStore` 有沒有包 `try/except` 不影響這件事。真正的差異是:`InboxStore.__init__`(file: `src/rtb/executor/inbox_store.py:142`-`145`)跟 `CampaignStore.__init__`(file: `src/rtb/dsp/store.py:175`-`178`)都把 `connect()` 丟出的 `DatabaseBusy` 接住、轉成自己的 `InboxBusy`/`StoreBusy`,讓呼叫端只需要認自己那個模組的例外;`TaskStore` 沒有對應的轉換,`DatabaseBusy` 會原樣從 `sqlitekit` 冒出去。屬於介面一致性的小落差,不是資料或行為上的錯誤,修不修都不影響正確性。

### 6. `_proposal_to_json`/`_proposal_from_json` 往返:時區、微秒、`requested_change` 巢狀結構、`reason_codes`/`evidence_refs` 順序都保真

severity: clean

檢查方式:在臨時目錄用非 UTC 時區(+08:00)、非零微秒(123456)、有值的 `requested_change`、刻意不照字母序排列的 `reason_codes`/`evidence_refs` 建一個 `Proposal`,跑過 `_proposal_to_json` → `_proposal_from_json` 後跟原物件比對:

```
equal overall: True
created tz preserved: 8:00:00 -> 8:00:00
created microsecond preserved: 123456 -> 123456
reason_codes order preserved: ('low_ctr', 'high_spend') -> ('low_ctr', 'high_spend')
evidence_refs order preserved: ('e2', 'e1') -> ('e2', 'e1')
requested_change equal: True <class 'mappingproxy'>
```

原因:`to_primitives()` 對時間欄位用 `.isoformat()`(保留原始時區與微秒,不像 `evidence` 那邊的 `_iso()` 會先轉 UTC),`_proposal_from_json` 對應用 `datetime.fromisoformat()`,兩者互為逆運算;`json.dumps(..., sort_keys=True)` 只排序字典的鍵,不會動到 list 的元素順序,`reason_codes`/`evidence_refs` 存成 list 後順序原樣保留;`requested_change` 現階段的網域規則(`_valid_change`)只允許 `{}` 或 `{"new_budget": int}`,本來就是平的,不是巢狀結構,`dict(...)` → JSON → `MappingProxyType(dict(...))` 的往返沒有損耗。這一段是乾淨的。
