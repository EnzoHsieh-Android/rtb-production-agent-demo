### 1. `advance()` 自己輸掉並行競爭時,回傳值完全沒被測試保護

severity: major
blocking: 是 這正是 `task_store.py` 註解講的「並行呼叫 advance() 時的最後一道防線」;這一行如果壞掉,呼叫端會被告知「這次呼叫已經把任務推進到新狀態」,但實際上這次呼叫什麼都沒寫入(輸給了另一次並行呼叫),下游可能因此誤判已完成而重複動作或漏做後續步驟。
引句:「return outcome.new_state if committed else row.state」

把這行改成永遠回傳 `outcome.new_state`(不管 `committed` 是不是 `False`)之後,`tests/analyzer` 26 個測試
原封不動全過。

`test_two_concurrent_advance_calls_on_the_same_task_never_both_commit_conflicting_outcomes`(S37)和
`test_the_next_sequence_number_is_decided_inside_the_write_transaction`(S38)都只直接呼叫
`store.commit_step(...)`,驗證的是「資料庫層沒有寫入第二列」,從沒有任何測試透過 `flow.advance()`
本身去製造一次「這次呼叫輸了並行競爭」的情境,再檢查 `advance()` 的回傳值有沒有老實退回 `row.state`。

崩潰恢復的兩個測試(S39/S40)也踩不到這條分支:它們用 `before_commit` 讓整個交易直接丟例外
(`immediate_transaction` 因此整包回滾),流程是「`commit_step` 根本沒有正常返回」,不是「`commit_step`
正常執行完、回傳 `False`」——這兩種失敗路徑不一樣,S39/S40 驗證的是前者,`return ... if committed else
...` 這行守護的是後者,兩者都沒人覆蓋。

### 2. `evidence_for()` 用 `task_seq` 隔離不同檢查點的證據,這件事沒有測試咬到

severity: minor
blocking: 否 SQL 濾掉錯的一批證據是資料正確性問題,但套件本身能正確運作,不是這批 patch 引入的行為錯誤;而且不屬於 rubric 點名要拉高等級的並行防護或崩潰恢復本身,是測試覆蓋深度不足。
引句:「WHERE task_id = ? AND task_seq = ?」

把 `evidence_for()` 這條 SQL 的 `AND task_seq = ?`(連同對應參數)拿掉,`tests/analyzer` 26 個測試
仍然全過。

`test_a_successful_evidence_fetch_commits_evidence_and_the_next_state_together`(S25)和
`test_a_failing_evidence_fetch_leaves_no_trace_and_the_task_stays_ready_to_retry`(S26)都只在單一
seq 底下操作;`test_analyzing_that_needs_fresh_evidence_goes_back_to_collecting_evidence`(S29)造成
「回到 COLLECTING_EVIDENCE 重新蒐證」之後,也沒有測試回頭確認舊一輪(舊 seq)的證據不會混進新一輪
`decide()` 的輸入。目前沒有任何測試讓同一個 `task_id` 在兩個以上的 `seq` 底下各自留下不同證據,
再驗證 `evidence_for()` 真的只回傳「這一個 seq」那一批——這條隔離規則完全靠 SQL 本身正確,沒有回歸測試守著。

### 3. `decide()`/`evidence_source()` 實際收到什麼引數,從來沒有測試斷言過

severity: minor
blocking: 否 目前程式碼呼叫本身是對的,拉不出實際錯誤行為或資料損壞,是斷言鬆散,不是並行防護或崩潰恢復合約失守。
引句:「decision = c.decide(row, evidence)」

`Counting` 假物件每次被呼叫都會把引數記進 `self.calls`,但 S27~S30(`analyzing` 分支的四個測試)沒有
一個去檢查 `decide` 收到的 `evidence` 真的是剛從 `store.evidence_for()` 撈出來的那一批;同樣地,
`evidence_source(row)` 收到的 `row` 引數也沒有任何測試查過。

實驗:把 `decision = c.decide(row, evidence)` 改成 `c.decide(row, ())`(讓決策永遠只拿到空證據),或把
`evidence = c.evidence_source(row)` 改成 `c.evidence_source(None)`,兩種各自單獨改動後 `tests/analyzer`
都是 26 個全過。對照 S31(`test_proposed_always_resubmits_the_stored_snapshot_never_a_freshly_built_one`)
明確用 `s.calls == [(proposal,)]` 斷言 `submit()` 收到正確的提案快照——同一招沒有套用在 `decide` 或
`evidence_source` 上。S27~S30 的名字都對得上「決策層根據證據做決定」的意圖,但實際斷言只停在「回傳的
狀態值對不對」,沒有驗證「決策真的是根據對的證據做的」。

### 4. `NOOP` 是模組層級單例,`.calls` 跨測試累積,會把 bug 誤判成別的測試壞掉,單獨跑觸發到的那個測試甚至完全看不出來

severity: minor
blocking: 否 這是測試孤立性/可診斷性問題,不是產品行為或資料損壞;NOOP 守的是「這一步不該呼叫這個協作者」,不是並行寫入鎖或崩潰恢復本身,不落在 rubric 點名要拉高等級的兩個例外。
引句:「NOOP = Counting()」

`tests/analyzer/test_flow.py` 裡 `NOOP = Counting()` 整個模組只建立一次,26 個測試共用,沒有任何
fixture 幫它在測試之間重置 `.calls`。

實驗:在 `_from_collecting_evidence()` 裡故意塞一行多餘呼叫 `c.decide(row, evidence)`(模擬「這一步
提早偷跑呼叫了 decide」這種 bug),然後:

- 跑全套 `tests/analyzer`:失敗的**不是**真正踩到這條路徑的
  `test_a_successful_evidence_fetch_commits_evidence_and_the_next_state_together`(它自己完全沒檢查
  `NOOP.call_count`,照樣綠燈)——而是兩個完全不相關的後面測試
  (`test_advancing_a_terminal_or_handed_off_task_calls_no_collaborator`、
  `test_advancing_a_handed_off_task_calls_no_collaborator`)因為 `NOOP.call_count` 累積到 13、不是 0
  才炸開(`assert 13 == 0`)。
- 用 `pytest -k test_a_successful_evidence_fetch_commits_evidence_and_the_next_state_together`
  單獨只跑真正該抓到這個 bug 的那個測試:結果是 `1 passed`——bug 完全隱形。

目前專案 `requirements-dev.txt` 沒有裝 `pytest-randomly` 之類的亂序外掛(見
file:`/Users/enzo/rtb-production-agent-demo/requirements-dev.txt:1-11`),預設 pytest 照定義順序跑,
所以現況下這類 bug 最終還是會被後面的測試意外炸出來,不會真的變成整套全綠。但這個「靠別人幫你擋、不是
靠自己的斷言擋」的設計,一旦有人改測試順序、用 `-k`/CI 分片只挑子集跑,或把 `NOOP` 搬到 `conftest.py`
給別的檔案共用,就會從「污染式假警報」變成真正的假綠燈。
