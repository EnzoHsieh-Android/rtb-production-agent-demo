### 1. 同一任務多次進出 COLLECTING_EVIDENCE 時,`evidence` 表的 `evidence_id` 單鍵設計會讓 `commit_step` 在第二輪炸掉未捕捉例外

severity: major
blocking: 是 理由:實測證實一個完全合法的重試迴圈(ANALYZING 要求 NeedsFreshEvidence 後回到 COLLECTING_EVIDENCE 再蒐證一次)在 `EvidenceSource` 兩次都給出相同 `evidence_id`(例如以 `content_hash` 或廣告快照決定性地產生 id,這正是模組自己在文件裡強調的「重試安全」精神下很自然的實作方式)時,`commit_step` 的 `INSERT INTO evidence` 會撞 `evidence_id TEXT PRIMARY KEY` 唯一鍵,丟出 `sqlite3.IntegrityError`,並且這個例外沒有在 `advance()` 或 `_from_collecting_evidence` 裡被接住,直接穿出到呼叫端——與模組文件宣稱的「重複呼叫 `advance()` 在中斷後恢復是安全的」矛盾:這不是中斷後恢復,而是完全正常、沒中斷過的第二輪蒐證也會讓任務從此卡死在 COLLECTING_EVIDENCE,除非呼叫端換一個不會撞 id 的 `EvidenceSource` 實作。

引句:「evidence_id TEXT PRIMARY KEY, task_id TEXT NOT NULL, task_seq INTEGER NOT NULL,」

實測(在臨時複本上執行,節錄):
```
step1: collecting_evidence
step2: analyzing row: TaskRow(..., seq=3, state=ANALYZING, ...)
step3: collecting_evidence row: TaskRow(..., seq=4, state=COLLECTING_EVIDENCE, ...)
step4 RAISED: IntegrityError('UNIQUE constraint failed: evidence.evidence_id')
final latest: TaskRow(..., seq=4, state=COLLECTING_EVIDENCE, ...)
```
第一輪 ANALYZING(seq=3)把證據 `e1` 寫進 `evidence` 表(`task_seq=3`);`decide` 要求重新蒐證後任務回到 COLLECTING_EVIDENCE(seq=4);第二輪 `evidence_source` 再次回傳 `evidence_id="e1"` 的證據,`commit_step` 要把它寫進 `task_seq=5` 的列時撞鍵,整個 `advance()` 呼叫未捕捉地拋出例外。

`immediate_transaction` 本身的回滾路徑沒有問題(見 clean 項第 6 條),資料沒有損毀,latest 列仍停在 seq=4;但只要 `EvidenceSource` 的實作是決定性的(這是本專案在 `rtb.domain.evidence.Evidence` 用 `content_hash` 當欄位、且模組文件把「重試安全」當賣點的自然結果),同一個任務只要進入這條迴圈就會永久卡住,`advance()` 每次重呼叫都會用同樣方式再炸一次——不會自己轉 FAILED(因為例外不是從 `Decide` 丟出來的,不會被 `_from_analyzing` 的 `except Exception` 接住),也不會再進展。建議:`evidence` 表的唯一鍵應該是 `(evidence_id, task_seq)` 或 `(task_id, task_seq, evidence_id)` 之類的複合鍵,讓同一份證據可以在不同輪次重複出現;或者在寫入前先用 `INSERT OR IGNORE` / 去重邏輯處理「同一輪內容再次出現」的情況。

### 2. `commit_step` 本身不檢查目標狀態合不合法,FAILED「是終點」只靠 `flow.advance()` 這一個呼叫端的紀律

severity: minor
blocking: 否 理由:目前唯一的驅動函式 `flow.advance()` 在呼叫 `commit_step` 之前一定先過 `row.state in TERMINAL_STATES` 的提早返回、以及 `transition(row.state, outcome.new_state)` 的合法性檢查(非法轉換會拋 `IllegalTransition`,不會靜默寫壞資料),經測試證實 FAILED 任務再呼叫 `advance()` 完全不會呼叫任何協作介面、也不會寫新列。這條路徑目前不會被觸發,是「防禦縱深」的缺口,不是現行行為的錯誤。

引句:「if row.state in TERMINAL_STATES or row.state is TaskState.HANDED_OFF:」

但 `TaskStore.commit_step()` 是公開方法(而且測試檔本身就示範直接呼叫它,例如 S37/S38 的兩個並行測試),它只核對 `expected_seq` 是否仍是最新列,完全沒有核對「這個狀態轉換合不合法」——這層檢查只存在於 `flow.py` 的 `_STEPS`/`transition()`,不存在於 `task_store.py`。實測:

```python
# t1 已經因為 decide 丟例外而進了 FAILED(seq=4)
committed = store.commit_step("t1", failed_row.seq, TaskState.ANALYZING, NOW)
# committed = True,latest 變成 seq=5, state=ANALYZING
```
只要日後任何第二個呼叫端(補救工具、另一支驅動函式、或未來重構時漏掉呼叫 `transition()`)直接用 `commit_step` 寫列,FAILED 就不再是真正的終點。`task_state.py` 的 `TRANSITIONS` 雖然用 `MappingProxyType` 保證「唯讀」,但那只保證記憶體裡的轉換表不能被改寫,不保證所有寫入路徑都會去查這張表——查表這件事是 `flow.advance()` 主動做的,不是 `commit_step` 強制的。file: `src/rtb/domain/task_state.py:50`(`TRANSITIONS` 的唯讀保證只在 `transition()`/`can_transition()` 被呼叫時才生效,見同檔 `:75`)。建議:至少在 `commit_step` 內部也核對一次 `current_state not in TERMINAL_STATES`(或直接呼叫 `transition()`)作第二道防線,不要只靠上層紀律。

### 3. `commit_step` 對真正並行寫入的防護:實測通過

severity: clean

用兩種方式實測(不是只讀程式碼推論):

- **多執行緒**:同一個 SQLite 檔案、8 條各自開獨立連線的 thread,用 `threading.Barrier` 逼它們同時對同一個 `expected_seq` 呼叫 `commit_step`,重複 20 輪。每一輪都是「剛好 1 個 True、7 個 False、0 個例外,最終 `seq` 只前進 1」。
- **多行程**:6 個獨立 process(`multiprocessing` spawn,各自開自己的連線)用事件同步逼近同時起跑,重複 10 輪,結果同樣是「剛好 1 個 True、其餘 False、0 個例外」。

沒有出現重複寫入、沒有出現兩個呼叫都成功、沒有出現例外洩漏。`BEGIN IMMEDIATE` 在交易一開始就取寫鎖,讓「核對 `MAX(seq)==expected_seq`」與「真的寫入」在同一個原子交易裡,確實擋得住並行寫入,不只是理論上看起來安全。

引句:「新列的序號在寫入交易內用目前最大序號加一決定」

### 4. `before_commit` 鉤子的呼叫時機:實測確認是真正的「提交前」,不是提交後才假裝

severity: clean

用兩條連線(寫入者連線 `writer_store` 與旁觀連線 `outside_store`)驗證 SQLite 交易隔離下 `before_commit` 到底在哪個時間點跑:

```
committed: True
seen by same connection INSIDE hook (before commit): 2   # 寫入者自己的連線能看到剛 INSERT 但還沒 COMMIT 的新列
seen by a DIFFERENT connection INSIDE hook (before commit): 1   # 另一條連線看不到,證明還沒 COMMIT
seen by outside connection AFTER commit_step returns: 2   # commit_step 回傳之後,COMMIT 已完成,外部連線也看得到
```

這證實 `before_commit()` 確實是在 `INSERT` 已執行、但 `COMMIT` 尚未執行之間被呼叫——`commit_step` 裡它是 `with immediate_transaction(...)` 區塊內最後一行程式碼,執行完才會離開 `with`、觸發隱含的 `COMMIT`。既有測試 `test_resuming_after_a_crash_before_commit_at_every_step_converges_to_the_uninterrupted_outcome` 也印證了鉤子丟例外時整筆交易(含新狀態列)都沒有落地。

引句:「if before_commit is not None:」

### 5. `evidence_for` 用 `task_seq` 過濾:多輪 COLLECTING_EVIDENCE/ANALYZING 不會誤讀舊證據

severity: clean

追蹤寫入與讀取的配對:`_from_collecting_evidence` 拿到的證據,是跟著「即將成為 ANALYZING 那一列」一起提交,`task_seq` 用的是那一列**自己**的新序號(`commit_step` 裡的 `next_seq`);而 `_from_analyzing` 讀證據時用的是 `store.evidence_for(row.task_id, row.seq)`,這個 `row` 正是同一列(`advance()` 一開始 `store.latest()` 讀到的當前 ANALYZING 列)。因為序號在整個任務生命週期內單調遞增、不重用(由第 3 條驗證過的交易保護保證),不同輪次的 ANALYZING 列一定有不同的 `seq`,`evidence_for` 精確匹配 `task_seq` 就不會把前一輪(舊 `seq`)的證據讀進這一輪。第 1 條實測的重播(兩輪 COLLECTING_EVIDENCE→ANALYZING)裡,第一輪證據存在 `task_seq=3`、第二輪本應存到 `task_seq=5`(只是因為 `evidence_id` 撞鍵而寫入失敗,不是讀取邊界的問題)。讀取面本身沒有找到誤讀舊證據的路徑。

引句:「rows WHERE task_id = ? AND task_seq = ?」

### 6. `immediate_transaction` 的回滾路徑:用第 1 條的真實例外驗證,交易與連線都乾淨復原

severity: clean

借第 1 條實際觸發的 `IntegrityError` 當回滾測試:例外發生在 `with immediate_transaction(self._conn):` 區塊內,`immediate_transaction`(file: `src/rtb/sqlitekit.py:60`)的 `except BaseException` 會檢查 `conn.in_transaction`(`src/rtb/sqlitekit.py:61`)再 `ROLLBACK`,重新拋出原例外。實測確認:
- 例外發生後 `store.latest("t1")` 仍是撞鍵前的那一列(seq=4,COLLECTING_EVIDENCE),沒有半筆壞資料落地,`evidence` 表也沒有殘留第二輪的 `e1`。
- `store._conn.in_transaction` 在例外之後是 `False`,交易確實乾淨結束,不是卡在半開狀態。
- 同一個 `store`(同一條連線)換一個不會撞鍵的 `evidence_id`(`e2`)後可以立刻再成功推進一步——連線本身沒有因為前一次失敗而變得不可用。

引句:「with immediate_transaction(self._conn):」

# 小結

最高等級 `major`,來自第 1 條:`evidence` 表用單一 `evidence_id` 當主鍵,在「任務多次進出 COLLECTING_EVIDENCE」這個模組自己就支援、也在文件裡明講的正常流程下,只要 `EvidenceSource` 的證據 id 是決定性產生(很自然的實作選擇),第二輪蒐證就會讓 `commit_step` 丟出未捕捉的 `IntegrityError`,任務卡死且不會自動轉 FAILED,違反「重複呼叫 `advance()` 安全」的核心承諾。第 2 條(FAILED 只靠呼叫端紀律,`commit_step` 本身不擋)列為 minor/防禦縱深建議。並行寫入防護(第 3 條)、`before_commit` 時機(第 4 條)、`evidence_for` 讀取邊界(第 5 條)、交易回滾與連線復原(第 6 條)五項都經過真實多執行緒/多行程/跨連線實測,沒有發現問題。
