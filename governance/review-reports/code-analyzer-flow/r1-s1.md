# r1-s1 審查:條款符合度(S20~S41 逐條核對)

審查對象:`governance/review-reports/code-analyzer-flow/r1-snapshot.patch`(`src/rtb/analyzer/flow.py`、`task_store.py`)。對照:`docs/rtb-production-agent-demo-knowledge/Projects/RTB_Phase2任務流程_計劃.md` 增量 3 設計,S20~S41 逐條核對。

方法:把專案複製到臨時目錄(`git -C` 唯讀,未動 `/Users/enzo/rtb-production-agent-demo` 任何檔案),裝 `pytest`/`ruff` 跑過現有 26 條測試(全綠)與 `ruff check src/rtb/analyzer/`(乾淨,`rtb.dsp` 禁止匯入規則實測有效)。另外在臨時目錄自行加測試,驗證下面幾條 finding 是否為真的可觸發行為(不是臆測),細節見各條「實驗」段。

`advance()` 的狀態去處逐一核對:`RECEIVED/COLLECTING_EVIDENCE/ANALYZING/PROPOSED` 四個經 `_STEPS` 字典各自處理;`HANDED_OFF` 與 `TERMINAL_STATES`(`COMPLETED/FAILED/BLOCKED/NO_ACTION/SUPERSEDED`,見 `src/rtb/domain/task_state.py:31-44`)六個經同一段提前 `return row.state` 擋下,不呼叫任何介面——十個狀態都有明確去處,沒有漏接的狀態會落到 `_STEPS[row.state]` 而 `KeyError`。`transition()` 確實被 `advance()` 呼叫且非法轉換會往外炸(monkeypatch 測試證實接線正確),但目前 `_STEPS` 四個函式回傳的目標狀態全部落在 `_FLOW` 合法範圍內,所以這條防線在現有程式碼裡永遠不會真的觸發——這點沒問題,只是提醒它目前是「接線正確但沒被地板考驗過」。以上兩點是條款符合度查核裡沒有問題的部分。

以下是查到的問題。

## Findings

### 1. `Submit` 的回傳值完全不驗證,任何非 `Accepted` 的正常回傳都會被當成已交接
severity: major
blocking: 是 照字面實作,`Submit` 忘記回傳或回傳錯型別時任務照樣被標記 HANDED_OFF,提案永久不會再重送,S32 的前提條件沒有守住
引句:「c.submit(row.proposal)」
`_from_proposed` 呼叫 `c.submit(row.proposal)` 後直接捨棄回傳值,只靠是否丟出例外分支;只要沒丟例外,不論回傳什麼都會落到 `return _Step(TaskState.HANDED_OFF, proposal=row.proposal)`。但介面契約明寫 `Submit:(proposal) -> Accepted`,S32 的前提是「`Submit` 回傳 `Accepted`」,不是「`Submit` 沒丟例外」。實驗:在臨時目錄用回傳 `None`(不丟例外)的假 `Submit` 呼叫 `advance()`,結果仍是 `HANDED_OFF`,任務從此不會再被推進、也不會再呼叫 `Submit`——若增量 4 接的真實收件口用戶端漏寫 `return Accepted(...)` 或回傳了別的物件,這份提案就悄悄消失,沒有任何錯誤訊息。測試套件裡沒有一條會傳入「不丟例外但回傳非 `Accepted`」的假物件,所以這個洞沒有測試會抓到。

### 2. `Decide` 回傳非三選一物件時被誤判為 `NeedsFreshEvidence`,不會轉 FAILED
severity: major
blocking: 是 決策端型別錯誤(例如漏包裝、打錯字)不會被當成程式錯誤處理,而是被吞成正常的重新規劃,永遠不會停止、也不會留下錯誤細節
引句:「return _Step(TaskState.COLLECTING_EVIDENCE)」
`_from_analyzing` 只用 `isinstance` 檢查 `NoAction` 與 `ProposalDecision` 兩種,其餘一律當成 `NeedsFreshEvidence` 處理(包含 `None`、字串、甚至未來新增的第四種型別)。但計劃的論證是:`Decide` 對已到手的證據做純計算,若它「自己丟出例外」代表輸入或決策邏輯本身有問題,要直接轉 FAILED、不能當暫時性重試;回傳型別錯誤同樣是決策邏輯本身的問題(不是外部狀態造成的暫時失敗),照計劃的論證邏輯也該轉 FAILED,而不是被吞成 S29 的「證據不夠新」。實驗:在臨時目錄用回傳裸字串(不是任何 Decision 子型別、也不丟例外)的假 `Decide` 呼叫 `advance()`,結果是 `COLLECTING_EVIDENCE`——會不斷重新蒐證、重新呼叫這個壞掉的 `Decide`,不會停在 FAILED,也不會留下 `error_detail`,跟 S30 想擋的「不得重試同一份證據」精神相反。

### 3. S41「只增不改」的守衛測試,篩選邏輯會漏掉獨立新增的 `UPDATE`/`DELETE` 敘述
severity: major
blocking: 是 這條測試存在的唯一目的就是擋「歷史表被改成可原地修改」,但獨立新增一句 `UPDATE`/`DELETE` 反而不會被它看見,守衛形同虛設
引句:「node.value.strip().upper().startswith(("INSERT", "CREATE"))」
`test_the_history_table_has_no_update_or_delete_statements` 先篩出「內含 SELECT」或「以 INSERT/CREATE 開頭」的字串常數,再從這個子集裡找 `UPDATE `/`DELETE `。問題是:一句全新的 `"UPDATE tasks SET state = ? WHERE task_id = ? AND seq = ?"` 或 `"DELETE FROM evidence WHERE task_id = ?"` 既不含 `SELECT`,也不是以 `INSERT`/`CREATE` 開頭,根本不會被收進 `sql_literals`,於是 `assert not any(...)` 對一個空集合(或不含該字串的集合)恆真,測試照樣綠燈。實驗:在臨時目錄用同一段篩選邏輯餵一個只含這兩句 `UPDATE`/`DELETE` 常數的模組,`sql_literals` 篩出結果是空清單,守衛沒有偵測到任何東西。目前 `task_store.py` 本身確實沒有 UPDATE/DELETE(這點是乾淨的),但這條測試沒有能力擋下未來任何一次真的違規。

### 4. S37/S38 的並行測試是同一連線循序呼叫兩次,不是真正交錯的並行,證明力不足
severity: minor
blocking: 否 我用兩條真連線、兩個執行緒實際跑過同一段 `commit_step` 邏輯,結果正確(一個成功一個失敗、序號不重複),所以這是測試證明力的缺口,不是目前程式碼有並行 bug
引句:「模擬兩個呼叫端都讀到同一列(seq=1)之後,其中一個先提交」
`test_two_concurrent_advance_calls_on_the_same_task_never_both_commit_conflicting_outcomes` 只是在同一個 `TaskStore`/同一條連線上依序呼叫兩次 `commit_step`,兩次呼叫之間沒有任何交錯,連「先讀後寫」的檢查是否真的發生在 `BEGIN IMMEDIATE` 之後都測不出來——就算把序號檢查搬到交易外面(先 `SELECT` 再另開交易 `INSERT`),這條測試字面上還是可能通過,因為呼叫本來就是循序的。我另外用兩個真的 `TaskStore` 連線、兩條執行緒對同一顆 `t1` 真的同時呼叫 `commit_step`(中間插 `sleep` 拉開競爭窗口),重覆五次都是「一個 `True`、一個 `False`,最終序號 2」,沒有出現雙寫或序號跳號。結論:目前 `commit_step` 的實作(檢查與寫入都在同一個 `immediate_transaction` 內)是對的,但 S37/S38 附的這條測試本身沒有實際證明這件事,只是巧合地跟正確實作同一個答案。

### 5. S39 的測試名稱宣稱「每一步」,實際只覆蓋 RECEIVED→COLLECTING_EVIDENCE 這一步
severity: minor
blocking: 否 我自己在臨時目錄補了「蒐證步驟」「送出提案步驟」兩處的提交前中斷實驗,結果都正確收斂(交易整個沒提交、重跑後結果跟沒中斷一致),所以這是測試覆蓋率與名稱不符,不是功能缺陷
引句:「flow.advance(store, "t1", NOOP, NOOP, NOOP, NOW, before_commit=boom)」
`test_resuming_after_a_crash_before_commit_at_every_step_converges_to_the_uninterrupted_outcome` 的名稱明寫「at_every_step」(對應 S39 條文的「任一步驟」),但整條測試只在 RECEIVED→COLLECTING_EVIDENCE 這一步注入 `before_commit` 中斷,沒有驗證「蒐證寫入 ANALYZING 連同證據列」、「決策寫入 PROPOSED 連同提案快照」、「送出寫入 HANDED_OFF」這幾個更複雜(帶額外資料要一起提交)的步驟在提交前中斷後是否一樣安全收斂。我用同一手法對「蒐證→ANALYZING」與「決策→PROPOSED」兩步各自補了一次提交前中斷實驗:兩次都確認中斷後該列序號沒有新增、附帶資料(證據/提案快照)沒有半寫入,重跑後結果跟沒中斷過一致——程式本身是對的(因為 `before_commit` 統一包在 `commit_step` 同一個 `immediate_transaction` 裡,寫法上沒有理由某一步會例外),但這是我自己補的實驗才確認,不是這條測試提供的證據。

### 6. `evidence` 寫入時捨棄 `Evidence.task_id`,不核對是否與目前任務一致
severity: minor
blocking: 否 目前寫入時一律改用 `commit_step` 自己的 `task_id`,不會存錯資料表,但也不會發現呼叫端傳來的證據其實標記著別的任務
引句:「(item.evidence_id, task_id, next_seq, item.kind.value, item.source,」
`commit_step` 寫入 `evidence` 表時,`task_id` 欄位用的是方法自己的 `task_id` 參數,不是 `item.task_id`(`Evidence` 物件自帶的欄位);讀回時 `evidence_for` 同樣用查詢參數重建 `task_id`,不讀資料庫裡的值。這代表如果 `EvidenceSource` 的實作(增量 4 才接真的)因為 bug 回傳了另一個任務的 `Evidence`(例如混用快取鍵或複製貼上打錯任務編號),`commit_step` 不會拒絕、也不會發出任何警訊,只會把它靜默地记到目前任務底下——`Decide` 之後會用「看似合法、實際來源錯誤」的證據做決策。這不會讓資料表本身不一致(欄位仍然內部自洽),但等於少了一層「這份證據真的是這個任務的」交叉核對,S25 的往返測試因為 fixture 剛好也是 `t1` 而看不出這個缺口。
