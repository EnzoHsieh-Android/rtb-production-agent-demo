### 1. `dsp_client.py` 對 DSP 回應的整數欄位沒有上界檢查,寫入後版本一旦超過 SQLite 64 位元整數範圍會讓整個執行迴圈以未設計的例外崩潰(跳過唯一的停機路徑 ExecutorHalted)

`dsp_client.py` 的 `_positive_int`(對應到 patch 內 `src/rtb/executor/dsp_client.py` 新增的 `_positive_int` 函式)只檢查值「是不是不含布林的整數、且大於 0」,對數值大小完全沒有上界。這個函式同時用在讀取(`budget`、`version`)與寫入回應(`version_after`)的欄位解析上。寫入回應解析出的 `version_after` 會一路流進 `execution.py` 的 `_committed()` 判斷式(只檢查 `is_plain_int(version) and version > 0`,同樣沒有上界)、`react()` 判成 `Reaction(A.COMMITTED_UNVERIFIED)`,最後交給 `attempt_store.py` 的 `_send_fields()`(`if not is_plain_int(written_version) or written_version < 1:` 同樣只檢查下界)寫進 `attempts.written_version` 這個 SQLite `INTEGER` 欄位。

SQLite 的 `INTEGER` 欄位是 64 位元有號整數(DSP 自己的 `store.py` 定義了 `SQLITE_INTEGER_MAX = 2**63 - 1` 並在寫入 metrics 時特意做上界檢查),但 Python 的 `int` 沒有上限、JSON 數字也沒有上限;一旦 DSP 回應的 `version_after` 是個超過 `2**63-1` 的整數(合法 JSON、大小遠低於 64KB 回應上限,一個 20 幾位數字就夠),`sqlite3` 綁參數時會直接丟出 `OverflowError: Python int too large to convert to SQLite INTEGER`。這個例外不是 `OSError`/`ValueError`,不會被 `dsp_client.py` 的例外處理接住;也不是 `ExecutorHalted`/`InboxBusy`,不會被 `runner.py` 的 `_loop`(`except (ExecutorHalted, InboxBusy) as halted:`)接住,於是整個執行迴圈行程直接以未預期的 traceback 崩潰,跳過模組文件明講的合約:「系統故障(設定檔壞掉、本地請求錯誤、條件寫入沒有進展):這一輪停下,啟動程式以非零代碼結束」——這個新的例外類別完全沒被納入已列舉的系統故障範圍,也沒有走 `sys.stderr.write(f"停機:{halted}\n")` 那條唯一設計出來的停機訊息路徑。
