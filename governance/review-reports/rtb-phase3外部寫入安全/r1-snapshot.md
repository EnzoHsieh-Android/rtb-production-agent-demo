# RTB_Phase3外部寫入安全_計劃

PRIOR-ART: 世界上這件事的標準解是「冪等鍵 + 發出前先落地的嘗試紀錄(transactional outbox 的變體)+ 結果不明時向事實來源對帳」,Stripe 等支付 API 的冪等鍵、分散式交易的 saga 補償都是同一套想法。最小解在本專案既有的層就做得到:SQLite 的唯一約束與 BEGIN IMMEDIATE(沿用 [[Systems/共用行程基礎]])、DSP 既有的「同鍵只套用一次」與「用鍵查操作」介面。採用:借用概念,自建最小的嘗試紀錄表,不引入工作流程引擎或訊息佇列軟體(佇列是 Phase 4)。
RETIRE-IF: 若 Phase 4 以後的 F1~F3 自動測試持續只靠 DSP 端的冪等就全數通過、嘗試紀錄與對帳從沒擋到一次重複或誤判,就檢討這層是否過度設計、能否併回單純的「同鍵重送」。

## 這份計劃在解決什麼

- 事故 F1(交接文件第 16 節):DSP 已經提交,回應卻在呼叫端收到前逾時或斷線。呼叫端不知道結果:可能 DSP 沒收到,也可能已經改好。處理錯的後果:以為沒成功就換新鍵重送,預算被改兩次;以為失敗就釋放額度,並行的工作合起來超額。
- 範圍:交接文件 Phase 3「Safe Side Effect、Idempotency 與 Reconciliation」,只做單一執行者、一次處理一筆。佇列與多個工作者(lease、fencing、重新投遞)是 Phase 4;總曝險預留與人工核准是 Phase 6;提示注入是 Phase 7。
- 驗收(交接文件 Phase 3 完成條件):提交前逾時與提交後逾時被不同地對帳;F1 自動測試通過,遠端成功只套用一次;同一把冪等鍵搭配不同內容被拒;執行後比對預期狀態與 DSP 實際狀態;事實來源是 DSP 的操作紀錄,不以例外類型推論結果。
- 已登記的預告合約 [[Verification/2026-09-22_事故-F1-的執行面-執行行程遇到外部結果不明-逾時-連線中斷-時標記為結果不明]](最遲 2026-11-15)就是這個階段要轉正的合約。

## 核心概念(使用者已在 2026-09-22 對話中作答並收到回饋)

- 逾時只代表「不知道」,不代表「沒成功」。正確做法是標成結果不明、額度繼續佔著、同一個廣告的其他寫入先停,再用同一把鍵向 DSP 查證;查不到不能直接當成沒做,要等過一段窗口、重跑完整執行前檢查,才用同一把鍵重送。使用者第一次選了「用同一把鍵立刻重送」:抓到了「絕不換新鍵」這個最重要的點,但少了「先查證、重跑檢查、留下結果不明這個事實」。
- 「嘗試中」紀錄必須在呼叫 DSP 之前寫進資料庫並提交;重啟後看到「有開始、沒結果」就先對帳。寫嘗試中與寫結果是兩個短交易,呼叫 DSP 期間不得開著任何交易。使用者答對。

## 交接文件 18.3 節的十題失敗語意(答案)

1. 請求還沒送出就失敗:本地已有嘗試中紀錄、DSP 查不到該鍵;走「查不到」那條路(等窗口、重跑檢查、同鍵重送)。
2. 遠端提交前逾時,怎麼知道:不能從逾時知道;對帳時用鍵查 DSP,查不到且窗口已過,才判定沒做。
3. 遠端提交後逾時:標成結果不明,用鍵查 DSP 的操作紀錄,查到就標成功並驗證實際狀態。
4. 遠端提交後、本地寫結果前當機:重啟後看到嘗試中紀錄,一律轉成結果不明,走對帳,不直接重送。
5. 訊息重新投遞時邏輯操作的身分:冪等鍵由任務、廣告、動作、內容與預期版本決定性算出,同一個邏輯操作永遠同一把鍵(佇列本身是 Phase 4)。
6. 並行的其他人改過廣告:寫入一律帶預期版本,由 DSP 的版本檢查擋下(已是 Mock-DSP 的合約);被擋就標失敗,舊提案過期,回分析行程重新分析。
7. 什麼條件下用同一把鍵重試:只有在「查不到該鍵、等待窗口已過、完整執行前檢查重跑通過」之後;其他情況一律不重試。
8. 執行後怎麼驗證:重讀 DSP 現況,比對預算與狀態是否等於提案的意圖,不符就轉人工。
9. 事實來源:DSP 的操作紀錄與目前狀態,不是本地例外類型。
10. 必須擋下、對帳或轉人工而不是重試的情況:執行前檢查任一項沒過就擋;結果不明一律對帳;對帳查詢本身反覆逾時超過上限、或執行後驗證不符,一律轉人工。

## 四個增量(2026-09-22 使用者裁定排法:寫入能力憑證放最後)

- 增量 1:嘗試紀錄與冪等鍵。執行行程自己的資料表,只是資料層,不呼叫 DSP。
- 增量 2:執行一筆。從收件口取一份待處理提案,重讀 DSP 現況,做最小執行前檢查(提案沒過期、版本一致、廣告仍在投放),寫嘗試中、呼叫 DSP、寫結果;逾時標結果不明;執行後比對實際狀態。
- 增量 3:對帳。照判定表處理;F1 自動測試用 DSP 故障注入造出提交前、提交後逾時。待答:模擬 DSP 的操作查詢只記成功的操作,被拒的請求不留紀錄,判定表「查到被拒」這一格要怎麼處理。
- 增量 4:寫入能力憑證。DSP 只接受綁定廣告、動作、金額上限、有效期的簽章憑證;同時回答 [[Projects/RTB_Agent_Phase0架構]] 留下的必答清單(兩個行程要不要分不同系統帳號、用測試證明分析行程拿不到金鑰、租戶與上限的來源)。
- 排法偏離 Phase 0 的原文(原文寫憑證在 Phase 3 開頭):先把「嘗試中→呼叫→結果不明→對帳」主線做對再加憑證,出錯時好分層;代價是前三個增量期間 DSP 寫入沒有憑證保護,但目前只有執行行程會呼叫 DSP 寫入。

## 增量 1 設計:嘗試紀錄與冪等鍵(2026-09-22,第 1 版)

- 事故:執行行程呼叫 DSP 之後當機,重啟時不知道哪些寫入已經發出;或同一個邏輯操作被重跑時拿到不同的鍵,DSP 擋不住重複。
- 範圍:只做資料層與純判斷,不呼叫 DSP、不做執行前檢查、不做對帳判定(那是增量 2、3)。

### 冪等鍵(純函式,放在領域層)

- 由提案的任務編號、廣告編號、動作類型、要求的變更、觀察到的廣告版本五樣,正規化成固定鍵序、無多餘空白、不允許 NaN 的 JSON,取 SHA-256 十六進位字串(沿用增量 2 收件口內容雜湊的正規化規則,見 [[Systems/任務流程領域模型]])。
- 刻意不含修訂序號與決策建立/到期時間:同一個邏輯操作重新提案、換了到期時間,仍是同一件事,應該拿到同一把鍵,讓 DSP 與本地都當成同一筆。
- 刻意包含觀察到的廣告版本:DSP 判斷同鍵是否同一件事時會比對預期版本,不含的話「同一把鍵、不同預期版本」會被 DSP 當成衝突拒收。
- 租戶目前不在提案裡,增量 4 決定租戶來源時再決定是否納入鍵;納入會改變鍵的算法,屆時本地沒有需要相容的舊資料。

### 嘗試狀態機(純資料,放在領域層)

- 狀態:嘗試中、成功、失敗、結果不明、轉人工。終點:成功、失敗、轉人工。
- 合法轉換:嘗試中 → 成功、失敗、結果不明;結果不明 → 成功、失敗、嘗試中(對帳判定可以同鍵重送之後)、轉人工。終點沒有出路。轉換表是一張唯讀表,比照 [[Systems/任務流程領域模型]] 的任務狀態機寫法。

### 嘗試紀錄表(執行行程自己的 SQLite)

- 兩張表,放在執行行程自己的資料庫檔:嘗試表(以鍵為主鍵;任務編號、修訂、廣告編號、動作、要求的變更、預期版本、目前狀態、送出次數、錯誤細節、建立與更新時間)與只增不改的轉換紀錄表(鍵、從哪個狀態、到哪個狀態、時間、細節)。沿用 [[Systems/提案收件口]]「現況列加只增不改事件表」的做法,連線與交易沿用 [[Systems/共用行程基礎]]。
- 開始一筆:單一 BEGIN IMMEDIATE 交易內,鍵已存在就原樣回傳既有紀錄與狀態、不新增也不改狀態(呼叫端依狀態分支,絕不因此直接再送);同一個廣告已有另一把鍵的未結案嘗試(嘗試中或結果不明)就拒絕(同範圍互斥,交接文件 7.3 節第 2 步);否則寫入嘗試中與一筆轉換紀錄並提交,提交後才回傳。
- 轉換:條件更新,只有目前狀態等於呼叫端預期的狀態、而且轉換表允許時才寫;不符就不寫入、回傳沒有進展,呼叫端不得覆寫(單一執行者下的最後一道防線,比照分析行程 commit_step 的序號核對)。
- 重啟恢復:單一執行者的前提下,啟動時所有嘗試中的紀錄一律轉成結果不明(誰都不在送,留著嘗試中就是「有開始沒結果」)。Phase 4 有多個工作者時,這條改由 lease 判斷。

### 合約

- [S1] 當兩份提案的任務編號、廣告編號、動作、要求的變更與觀察到的版本都相同,冪等鍵函式應回傳相同的鍵,修訂序號與決策時間不同也一樣。[test:test_the_operation_key_is_the_same_for_the_same_logical_operation]
- [S2] 當任務編號、廣告編號、動作、要求的變更或觀察到的版本任一項不同,冪等鍵函式應回傳不同的鍵。[test:test_any_substantive_difference_changes_the_operation_key]
- [S3] 冪等鍵函式應只產出 DSP 冪等鍵格式接受的字串。[test:test_the_operation_key_is_accepted_by_the_dsp_key_format]
- [S4] 當開始一筆遇到新鍵,嘗試紀錄表應在單一交易內寫入一筆嘗試中與一筆轉換紀錄,提交後才回傳。[test:test_beginning_a_new_attempt_commits_it_before_returning]
- [S5] 當開始一筆遇到已存在的鍵,嘗試紀錄表應回傳既有紀錄與它目前的狀態,不新增、不改動任何東西。[test:test_beginning_an_existing_key_returns_the_existing_record_unchanged]
- [S6] 當同一個廣告已有另一把鍵的未結案嘗試,開始一筆應被拒絕且不寫入任何東西。[test:test_a_second_operation_on_a_campaign_with_an_unresolved_attempt_is_refused]
- [S7] 嘗試的狀態轉換應只允許轉換表裡的轉換,終點狀態沒有任何出路。[test:test_attempt_state_transitions_follow_the_table_exactly]
- [S8] 當轉換時目前狀態不等於呼叫端預期的狀態,嘗試紀錄表應不寫入任何東西並回報沒有進展。[test:test_a_transition_from_a_stale_expected_state_writes_nothing]
- [S9] 每一次狀態轉換應在同一個交易內留下一筆只增不改的轉換紀錄。[test:test_every_transition_leaves_an_append_only_record]
- [S10] 當重啟恢復執行,嘗試紀錄表應把所有嘗試中的紀錄轉成結果不明,不得轉成失敗或成功。[test:test_attempts_in_flight_at_restart_become_unknown_outcome]
- [S11] 當兩個並行請求用同一把鍵開始一筆,嘗試紀錄表應恰好建立一筆。[test:test_concurrent_begins_for_the_same_key_create_exactly_one]
- [S12] 寫入嘗試紀錄的錯誤細節應有長度上限。[test:test_error_detail_is_capped]
- [S13] 嘗試紀錄模組不應匯入任何網路或 HTTP 模組。[test:test_the_attempt_store_does_not_reach_the_network]

### 不做的事(範圍)

- 不呼叫 DSP、不做執行前檢查、不做對帳判定、不從收件口取提案(增量 2、3)。
- 不做 lease、owner 與 fencing:單一執行者;多個工作者是 Phase 4,屆時「重啟時嘗試中一律轉結果不明」要改成看 lease。
- 不做總曝險預留(Phase 6)。

## 實務隱患

- 未排除:金流:這個階段的最終目的就是對 DSP 發出改預算的寫入;增量 1 雖然只是資料層,它的鍵與互斥規則直接決定之後會不會重複扣預算。
- 未排除:對外送出:增量 2 起會對 DSP 發出寫入;增量 1 本身不送。
- 未排除:不可逆:DSP 端的預算變更對 Demo 而言可逆(可以再改回來),但「已被重複套用」這件事在稽核上收不回來。
- 未排除:守衛面:執行行程是唯一有寫入能力的行程,嘗試紀錄與互斥是防重複寫入的守衛。

## 回退

增量 1 只新增執行行程的兩張表、領域層的冪等鍵函式與嘗試狀態機,沒有修改任何既有介面,也還沒有任何呼叫端;回退就是刪掉新增的模組與測試,計劃改回「增量 1 未做」。增量 2 起若設計證明不成立,同樣只新增、不改既有合約,回退方式相同。
