severity: major

### 1. 狀態機沒有給「DSP 已確認成功、但執行後驗證不符」留出路,直接牴觸設計自己在十題裡的答案

severity: major
blocking: 是 這會讓增量 2 按十題的字面答案實作時,撞上已凍結的 S7 轉換表,不修表就做不出十題要求的行為
引句:「查到就標成功並驗證實際狀態」

說明:十題 Q3 的答案是「查到就標成功並驗證實際狀態」,Q8 是「重讀 DSP 現況,比對預算與狀態是否等於提案的意圖,不符就轉人工」。也就是說:對帳查到 DSP 已提交 → 先標「成功」→ 再驗證實際狀態 → 不符的話要轉人工。但增量 1 凍結的狀態機明寫「終點:成功、失敗、轉人工…終點沒有出路」,「成功」是終點,合法轉換表裡完全沒有「成功 → 轉人工」這條邊。

具體例子:嘗試 K 的 DSP 呼叫逾時 → 標「結果不明」→ 對帳用鍵查到 DSP 已提交、budget=5000 → 依 Q3 標「成功」→ 執行後驗證重讀 DSP,發現實際 budget 是 4000(例如同時有另一支付流程覆寫,或版本判斷有誤差)。依 Q8 應轉人工,但「成功」已是終點狀態,S7 要求「終點沒有出路」的測試(test_attempt_state_transitions_follow_the_table_exactly)恰恰會擋下 transition(K, expected=成功, to=轉人工)——這正是它該做的事,卻讓設計自己承諾的行為變得不可實作。增量 2 要嘛違反 S7(改凍結的轉換表,牴觸計劃書自己說的「回退…同樣只新增、不改既有合約」),要嘛被迫把「驗證失敗」硬塞進「結果不明」這個語意上專指「不知道」的狀態(核心概念明寫「逾時只代表『不知道』,不代表『沒成功』」)——但這裡是「已經知道成功,只是不符預期」,兩者是不同的失敗語意,混用會讓增量 3 的對帳判定表（依 Q7「查不到該鍵才能同鍵重送」）對這筆誤判成「可能沒做」而錯誤地嘗試重送一個其實已經套用成功的操作。

### 2. 「轉人工」是終點又不在互斥集合內,人工還沒處理就解除同廣告的寫入保護

severity: major
blocking: 是 這會直接放行 F1 事故想擋的「同一廣告並行寫入」,且發生在增量 2、3(HITL 工具要到 Phase 6 才有)這段期間內
引句:「同一個廣告已有另一把鍵的未結案嘗試(嘗試中或結果不明)就拒絕」

說明:同廣告互斥只擋「嘗試中」或「結果不明」這兩個狀態(「未結案」);「轉人工」是終點狀態,不在這個集合裡,所以一旦一筆嘗試被判定要轉人工,它立刻「解除」對該廣告的保護。但「轉人工」本身就是因為系統無法自動判定安全,才交給人——在人真的處理之前,對這支廣告的認知仍是不明確的。

具體例子:嘗試 A(鍵 K1)在廣告 C 上因對帳查詢反覆逾時超過上限而轉人工(結果不明 → 轉人工,合法轉換)。人工尚未介入。此時分析行程重新對廣告 C 產生新提案,得到新鍵 K2,呼叫「開始一筆」。依 S6 字面,K1 已是終點(轉人工),不算「未結案」,所以 K2 會被接受,增量 2 會照常對 DSP 發出新的預算寫入——在嘗試 A 的疑點還沒釐清前,就疊加了第二筆寫入。這直接違反交接文件 7.3 節第 2 步「暫停相同 scope 的危险後續寫入」,也違反計劃書核心概念自己說的「同一個廣告的其他寫入先停」。由於狀態機規定「終點沒有出路」,轉人工的紀錄永遠無法被結構性地「解除」或重新納入互斥,這個保護缺口不是實作疏忽,是凍結的合約本身沒有留出路。

### 3. S1/S2 冪等鍵測試允許用單一抽樣通過,不要求窮舉五個維度分別變動

severity: major
blocking: 是 弱測試會放過雜湊輸入包含不該包含欄位的實作錯誤,直接破壞冪等鍵的核心承諾
引句:「當任務編號、廣告編號、動作、要求的變更或觀察到的版本任一項不同,冪等鍵函式應回傳不同的鍵。」

說明:S1 要求「兩份提案…都相同…修訂序號與決策時間不同也一樣」,S2 要求「任一項不同…回傳不同的鍵」。兩條契約字面都可以用單一個例子滿足(例如只改 revision 一項、只改 action_type 一項),不要求對五個維度(task_id、campaign_id、action_type、requested_change、observed_version)逐一獨立變動測試,也不要求驗證 decision_created_at 與 decision_expires_at 分別單獨變動時鍵不變。requested_change 本身還是巢狀字典(例如 `{"new_budget": 5000}`),值本身的差異是否被窮舉也沒有明文要求。

具體例子:實作若不慎把 decision_created_at 也編進雜湊輸入(而不是像設計文字要求的「刻意不含…決策建立/到期時間」),一支只驗證「改 revision、不改決策時間」的弱測試仍會通過 S1;一支只驗證「改 action_type」的弱測試仍會通過 S2。但這個 bug 會讓 Q1 描述的行為(「同一個邏輯操作重新提案、換了到期時間,仍是同一件事,應該拿到同一把鍵」)整個失效——DSP 會把窗口過後的合法重試(同一邏輯操作、只是到期時間更新)當成全新操作接受,造成預算被改兩次,正是本計劃要擋的事故。本專案在姊妹模組 `task_state.py` 已經因為「非法轉換原本只抽樣 9 組,漏了一條照樣測試綠燈」被稽核抓到(見下一條),S1/S2 的契約文字沒有把這個教訓帶進來。

### 4. S6「未結案」涵蓋兩個狀態,契約與測試命名卻是單數,允許只驗其中一態就過關

severity: major
blocking: 是 若實作漏掉「結果不明」那一支互斥檢查,對帳期間會放行第二筆寫入,弱測試抓不到
引句:「當同一個廣告已有另一把鍵的未結案嘗試,開始一筆應被拒絕且不寫入任何東西。」

說明:「未結案」定義為「嘗試中或結果不明」兩個狀態,但 S6 契約與對應測試名稱(test_a_second_operation_on_a_campaign_with_an_unresolved_attempt_is_refused)都是單數形式,字面上一支只涵蓋其中一種狀態(例如只建一筆「嘗試中」的既有紀錄去驗證新鍵被拒)就能滿足契約,完全不要求也對「結果不明」狀態的既有紀錄重複驗一次。

具體例子:若實作把互斥查詢寫成 `WHERE status = 'in_progress'`(漏了 `'unknown_outcome'`),只涵蓋「嘗試中」狀態的弱測試依然全綠,但實際運作時:嘗試 A(鍵 K1)在廣告 C 上處於「結果不明」(對帳中,尚未確認 DSP 是否真的執行),新提案帶新鍵 K2 呼叫「開始一筆」會被錯誤地接受,增量 2 對同一支廣告發出第二筆寫入——這正是核心概念「逾時只代表不知道…額度繼續佔著、同一個廣告的其他寫入先停」要擋的情境,也是事故 F1 的翻版。

### 5. S10 沒有要求「非嘗試中紀錄不受影響」與「多筆同時嘗試中全部被轉換」,弱測試無法抓到掃描範圍錯誤

severity: major
blocking: 是 若重啟復原誤把終點狀態掃成結果不明,會打破 S7「終點沒有出路」的保證,並讓已完成操作被錯誤地重新對帳
引句:「當重啟恢復執行,嘗試紀錄表應把所有嘗試中的紀錄轉成結果不明,不得轉成失敗或成功。」

說明:契約只斷言「嘗試中的紀錄變結果不明」,沒有要求驗證「非嘗試中的紀錄(尤其是已在終點的成功、失敗、轉人工)完全不受影響」,也沒有要求測試「同時存在多筆嘗試中紀錄時,全部都被轉換」。一支只建一筆嘗試中紀錄、斷言它變結果不明的弱測試就能滿足契約字面。

具體例子:資料庫裡同時有 X=嘗試中、Y=成功(終點)、Z=嘗試中三筆紀錄,重啟恢復執行。預期是 X、Z 變結果不明,Y 完全不動(狀態、更新時間都不變)。若實作的 SQL 少寫了 WHERE 條件(例如 `UPDATE attempts SET status='unknown_outcome'` 忘了加 `WHERE status='in_progress'`),把 Y 也一起掃成結果不明,前述弱測試(只建一筆嘗試中紀錄)仍會通過,但這會打破 S7「終點沒有出路」——一筆已經成功套用的操作被打回結果不明狀態,增量 3 的對帳邏輯會對一個其實已經完成的操作重新走查證流程,增加不必要的對帳負擔與稽核混亂,若鍵定義未來有任何缺口,直接後果就是對已完成操作誤判並重送。

### 6. 設計文字承諾「轉換表是唯讀表、比照任務狀態機寫法」,但 13 條合約沒有對應的防竄改合約

severity: major

引句:「終點沒有出路。轉換表是一張唯讀表」
