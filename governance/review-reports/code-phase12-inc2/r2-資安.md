第 1 輪 v2 的修法只顧到「收到一次訊號，而且那一刻 `_current` 已經指到這個情境」的情形。子行程都用 `start_new_session=True` 起，父行程死了也不會跟著死。所以只要驅動執行緒沒收完行程主行程就先結束，子行程就一直跑下去。這種情形有三條路會發生：

- **(a) 第二次 Ctrl-C 或 SIGTERM。**
  - `stop()` 在 `thread.join` 等驅動執行緒收尾時，SIGINT 的處理器還在，`_terminate` 也還掛著。
  - 使用者再按一次 Ctrl-C，`join` 就被 KeyboardInterrupt 打斷，主行程直接結束，daemon 驅動執行緒跟著死在收尾途中。
  - 收尾期間沒有任何「收尾中」的提示，使用者很容易再按一次。
- **(b) 取消落在「檢查 stop」與「`self._current = world`」之間。**
  - `Driver.run` 先檢查 `self.stop`，接著在 `run_one` 裡寫 `start_scenario`、建 World，最後才設 `_current`。
  - 如果 `cancel()` 發生在這段時間，它讀到的 `_current` 是 None，新建的 `world.stop` 就永遠不會被設。情境會照跑到結束或跑到時限（F7 是 300 秒，還不含等確認）。
  - 伺服器只等 60 秒就結束，daemon 執行緒被砍，子行程成為孤兒。
  - 平常這段時間只有幾毫秒，但 `start_scenario` 是一次 SQLite 寫入。核可簽發正握著展示狀態庫的寫入鎖時，這段時間會被拉長。
- **(c) 已經在處理中的 POST /run。**
  - `server_close()` 只關監聽埠，不等處理中的請求（`daemon_threads = True`）。
  - 處理器可能在 `stop()` 讀完 `self.current` 之後才呼叫 `service.start()`。那一次新的展示不會被取消，也不會被等到。
