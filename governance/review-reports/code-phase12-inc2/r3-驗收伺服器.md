## 發現 1:從殼層關掉終端機,收尾路徑自己丟 EIO 打斷等待,11 支子行程照樣變孤兒
severity: major
blocking: 是

引句:「print("正在收尾:停掉展示、收掉它起的行程,請稍候", file=sys.stderr, flush=True)」

引句:「stdout=subprocess.PIPE, stderr=subprocess.DEVNULL, text=True)」

file: `src/rtb/demo/server.py:493-496`、`src/rtb/demo/server.py:516-520`、`tests/demo/test_server.py:877-880`

**問題**
- 真的關掉終端機時,核心會把 SIGHUP 送給前景行程,也就是伺服器。zsh 自己收到 SIGHUP 後,會再轉送一次 SIGHUP 給它的工作。
- 第二個 SIGHUP 落在收尾中,進到 `_cleaning_up`。這時終端機已經掛斷,`print(..., file=sys.stderr)` 會丟 `OSError: [Errno 5] Input/output error`。
- 例外從訊號處理函式冒出來,打斷 `service.stop()` 裡的 `thread.join`。主執行緒結束,daemon 驅動執行緒跟著消失,`world.close()` 沒有跑。
- 第 2 輪建議「收尾中只印一行」,本輪照做了,但印的那一行在掛斷的終端機上反而成了新的中斷來源。

**例子**
- 輸入:zsh 裡跑伺服器,F7 等人確認(11 支子行程),關掉終端機。
- 預期:收尾做完,0 支殘留,F7 記「展示被停止」。
- 實際:伺服器 0.1 秒就結束,5 秒後剩 11 支 PPID=1,F7 停在 `awaiting_confirmation`。3 次裡 3 次都這樣。

**對照組**
- 同樣經過 zsh,但 stderr 導到檔案:3 次都是 0 支。其中 2 次檔案裡有「正在收尾」,表示第二個 SIGHUP 真的來了。
- 直接把伺服器當成終端機的 session leader(沒有殼層,只收到一次 SIGHUP):0 支。

**隔離驗證**
- 在假終端機裡裝上 `server._cleaning_up`,讓主執行緒 `join(10)`,關掉 master 後再送一個 SIGHUP。
- 結果是 `join interrupted by OSError: [Errno 5] Input/output error`。

**重現**
- 用 `pty.fork()` 在子行程裡 exec `zsh -f -i -o monitor -c "<python> -m rtb.demo.server --work-dir W --reports W/reports; echo exited $?"`。
- 從 master 讀到 `PORT=` 之後,POST `/run/scenario` F7,等到 `GET /approve` 回 200,再 `os.close(master)`。
- 5 秒後 `ps -axo pid,ppid,command | grep W`。

**測試漏網**
- `test_hanging_up_or_signalling_twice_still_leaves_no_child_processes` 把 stderr 導到 DEVNULL,也只直接送一個 SIGHUP,所以抓不到這條路徑。

**建議**
- `_cleaning_up` 裡吞掉 `OSError`,例如 `contextlib.suppress(OSError)`;或者收尾中直接改成 `SIG_IGN`。
- `service.stop()` 外面再包一層,等待被任何例外打斷時再補 join 一次。
- 測試改成經過 zsh 的假終端機關 master,或者至少讓 stderr 指向已經關掉的管道。

## 發現 2:SIGTERM 和 SIGHUP 幾乎同時到時,第二個訊號在換處理函式之前就打斷收尾
severity: minor
blocking: 否

引句:「for signum in (signal.SIGINT, signal.SIGTERM, signal.SIGHUP):」

file: `src/rtb/demo/server.py:511-520`

**問題**
- 兩個訊號同時待處理時,CPython 會先跑一個 `_terminate`。另一個 `_terminate` 在下一次檢查點就跑,可能落在 `finally` 已經開始、但還沒換成 `_cleaning_up` 的時候(包括逐一 `signal.signal` 的那個迴圈中間)。
- 這時再丟一次 `SystemExit`,會跳過 `service.stop()`。

**例子**
- 輸入:F7 等人確認時 `os.kill(pid, SIGTERM); os.kill(pid, SIGHUP)`,間隔 0。
- 預期:0 支殘留。
- 實際:4 次裡 2 次在 0.0 秒結束(結束代碼 143),留下 11 支 PPID=1。另外 2 次正常。
- SIGINT 加 SIGTERM 同時送,3 次都正常。

**重現**
- 起伺服器、跑 F7,等 `/approve` 回 200,再連續送這兩個訊號。

**建議**
- 在 `serve_forever()` 之前就用一個旗標式的處理函式:第一次設旗標並丟例外,之後只設旗標不丟;或者在處理函式裡先改掉三個訊號的處理再丟例外。
- 窗口很窄。本機展示通常只會碰到發現 1 那種情況,所以列為 minor。

## 發現 3:簽發中剛好跨過期限而且簽失敗:驅動程式白等 60 秒,最後記成「沒有人確認」
severity: minor
blocking: 否

引句:「return row is not None and (row[0] is not None or row[1] is not None)」

引句:「APPROVED_WRITE_SECONDS = 60.0  # 關窗前一刻才簽的核可:再等它寫進平台這麼久(核可本身最多 300 秒)」

file: `src/rtb/demo/state_store.py:392-403`、`src/rtb/demo/driver.py:966-981`、`src/rtb/demo/driver.py:928`

**問題**
- 關窗時把「簽發中」當成已經有人確認,這個方向是對的。但如果簽發後來失敗,例如收件口忙碌,`signing_at` 會退回空的,驅動程式卻已經拿到 True。
- 驅動程式接著等 `APPROVED_WRITE_SECONDS` 等一張不存在的核可,時間到了才丟「沒有人確認」。
- 人其實在期限內按了確認,只是簽發失敗。紀錄沒有照實寫出這一點。

**例子**
- 輸入:縮小版 F7,確認上限 4 秒。收件口被鎖住,期限前約 3.5 秒送出正確表單。
- 預期:照實記「簽發失敗」,或者窗退回後就判定。
- 實際:POST 等了 5.4 秒回 503 busy,窗記成 `closed_at` 有值、`signing_at` 空的、`approved_at` 空的。F7 在 POST 之後 64.6 秒才結束,原因是「沒有人確認」,核可 0 張。
- 對照:期限過後 1 秒才放開收件口,簽發成功,F7 在 5.7 秒後判 done,核可 1 張。

**重現**
- 在複本的 tests/demo 加一支探針:沿用 `f7` 夾具的寫法,但 `confirm_cap_seconds=4`。
- 用 `BEGIN EXCLUSIVE` 鎖住 F7 的 inbox.db,再 POST `/approve`。

**建議**
- 退回「簽發中」時留一個「簽發失敗」標記,`_wait_for_confirmation` 輪詢時看到就不再等。
- 或者至少把 F7 的原因寫成「有人確認但簽發失敗」。

## 發現 4:連按兩次時第一次簽發失敗,瀏覽器最後停在 `/#current`,看起來像已經確認了
severity: minor
blocking: 否

引句:「if closed.code not in _DONE_HERE:」

**問題**

**例子**

- 預期:使用者知道還沒確認成功。
- 實際:第二次回 303 `/#current`,第一次 5.4 秒後回 503 busy,收件口 0 張核可。主頁上的確認入口還在,重按可以恢復。

- 用 `BEGIN EXCLUSIVE` 鎖住 inbox.db,開一條執行緒 POST `/approve`,0.8 秒後再 POST 一次。

**建議**
