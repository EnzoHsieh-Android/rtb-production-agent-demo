## 第 1 部分修正有沒有帶進新錯

**1. 舊列直接走原算法**
- 便宜偵測判定為候選的條件是：窗內已驗證，或還沒有終點。這和精確偵測的已驗證、未結案兩段篩選相同。
- 偵測判到候選時，直接回傳原算法的結果，所以答案必然一樣。
- 偵測判不出來時，照舊由加總那一趟的精確偵測來判，答案還是以原算法為準。
- 可能的誤判只有一種：全表未結案數被多餘的終點列抵成 0。這時偵測說有候選、原算法卻不查未結案那段。但因為直接交給原算法，答案一樣，只多花一次偵測的工作。
- 所以不會出錯，只有效能上的問題，見發現 1。

**2. 時間欄型別異常時退回**
- 只有這個租戶的列會被標成異常，別的租戶的列本來就不在候選範圍。
- 會被標成異常、但原算法其實不會失敗的列（例如金額 ≤ 0，或只有一筆，不需要排序），會多退回一次，結果照樣相同，屬於保守。
- `key` 和 `written_at` 兩欄都是 `TEXT NOT NULL`，所以實際上只有二進位值會被判成異常，見發現 2。

**3. 溢位判斷集中處理**
- `is_integer_overflow` 放在 `src/rtb/sqlitekit.py:35`，全專案只有 file: `src/rtb/executor/attempt_store.py:707` 這一處在用。
- 已驗證和未結案兩段都在同一個 try 裡。`_legacy_candidate_seen` 在 try 外面，但它沒有 SUM，不會溢位。
- 把判斷改成「一律是」，查詢寫錯的測試會翻紅；改成「一律否」，溢位測試會翻紅。
- 手動建立的 `OperationalError` 沒有 `sqlite_errorcode`，會丟 AttributeError。不過這跟既有的 `_is_lock_contention` 做法一致，資料庫丟出來的例外一定帶這個欄位，所以不列為發現。

## 發現 1：便宜偵測只看最新 64 筆舊列，比它們更早開始的舊列查不到，而且會一直查不到
severity: minor
blocking: 否
引句:「"WHERE f.seq = 1 AND f.tenant IS NULL ORDER BY f.written_at DESC LIMIT ?",」

- **位置：** file: `src/rtb/executor/attempt_store.py:658`
- **為什麼會一直查不到：**
  - 舊列都是 Phase 6 以前留下的，不會再長出新的第一列。
  - 所以，只要一把卡住的舊鍵（轉人工、一直沒結案）比最新 64 筆舊列還早開始，偵測就永遠看不到它。
  - 另一種情形：舊鍵很早開始、最近 24 小時內才人工結案成已驗證，這 24 小時內也看不到。
  - 系統在 Phase 6 前跑過一段時間，舊列就會有上千筆。卡住的那把通常反而是最舊的，所以這很可能是最常見的情形。
- **這段時間每次呼叫都會：** 先把窗內已驗證那段整個加總一遍，再退回原算法。這正是第 1 輪 s1 要修的「白掃一遍」，而且是在寫入鎖裡。
- **例子：**
  - 輸入：4000 筆這個租戶窗內已驗證的列；1 把 800 天前開始、還在轉人工的舊鍵；另外 64 把 400 天前開始、已結案的舊鍵。
  - 預期：偵測查到那把舊鍵，直接走原算法，步數不超過原算法 +5（跟 `test_falling_back_on_a_legacy_row_does_no_more_work_than_the_reference` 的門檻一樣）。
  - 實際：偵測回 False。兩邊答案都是 181040，但快路徑的虛擬機步數 4655，原算法 2215，約 2.1 倍。
- **重現：** 在複本新增一支測試，照上面的輸入建列，用檔案裡的 `_vm_steps` 量兩邊步數。輸出是 `probe_seen False fast 181040 4655 reference 181040 2215`，斷言失敗 `AssertionError: (4655, 2215)`。
- **為什麼是 minor：**
  - 計劃第 208 行有寫「舊列超過 64 筆而且最近的都不是候選時判不出來」，是已知的限制，也沒有算錯。
  - 但驗收紀錄的殘餘風險寫的是舊列「有獨立的便宜偵測,先查、查到直接走原算法」（file: `docs/rtb-production-agent-demo-knowledge/Verification/F7效能驗收紀錄.md:52`），讀的人會以為舊列的情況已經解決。
  - 計劃的說法是「最近的都不是候選」，沒有點出「最舊的那把卡住」是常態，而且會一直持續。
- **建議：**
  - 在殘餘風險寫明這種形狀。
  - 或者把偵測改成從「未結案的舊鍵」出發：舊鍵總數固定、不會再增加，可以由終點列的部分索引反查。

## 發現 2：時間欄異常的隨機值有 2/3 被資料庫轉成文字，`odd_started_integer` 沒測到它想測的情況
severity: minor
blocking: 否
引句:「ODD_STARTED = (b"\x00", 12345, 1.5)  # 第一列時間欄型別異常(原算法排序時比不了)」

- **位置：** file: `tests/executor/test_aggregate_fast_path.py:98`、`tests/executor/test_aggregate_fast_path.py:150`
- **原因：** `written_at TEXT NOT NULL` 是 TEXT 型別親和，寫進 `12345`、`1.5` 時會轉存成 `'12345'`、`'1.5'`。原算法照樣能排序，快路徑也不會退回。
- **例子：**
  - 輸入：`odd_started_integer` 這份資料。
  - 預期（照註解）：型別異常，走退回。
  - 實際：存成 `('text', '12345')`，快路徑不退回，回 `('value', 11)`，跟原算法一樣。
  - 對照：`odd_started_time` 存的是 `('blob', b'\x00')`，兩邊都丟 TypeError，有真的比到。
- **影響：**
  - 時間欄的型別檢查整個只靠二進位值在守。M8 被抓到，只是因為 `odd_started_time` 那一例。
  - 另外，`NOT NULL` 讓 NULL 這條分支根本造不出來。
  - 這跟第 1 輪報的 `"12"` 問題是同一類。
- **建議：** 把 `ODD_STARTED` 改成二進位值為主，例如 `b"\x00"`、`b"z"`。刪掉 `odd_started_integer`，或把註解改成「會被轉成文字，不算異常」。

2 條，blocking 0。
