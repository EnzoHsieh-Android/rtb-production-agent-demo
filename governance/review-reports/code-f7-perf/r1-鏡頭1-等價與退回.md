severity: minor

鏡頭1（等價與退回）的結論：兩種算法我在兩萬份以上的對抗資料上比對，一份答案都沒有不同；需要退回的情況也沒有漏掉。以下 4 條都是 minor：兩條是測試的斷言比實際寬，一條是型別守衛缺了、目前的呼叫端走不到，一條是 S19 測試本來就有的漏洞。

**查過、沒問題的部分**
- **為什麼兩邊一定等價：** 新舊算法共用同一份篩選片段（`_verified_candidates`、`_open_candidates`）。所以窗口邊界、時間字串比較、同一操作鍵多次嘗試、最新狀態怎麼取，這些在結構上兩邊必然一樣，差異只可能出在「怎麼加總」。
- **加總的規則對得上：**
  - 快路徑只加「屬於這個租戶、型別是整數、而且大於 0」的列。
  - 原算法 `_counted` 對這類列就是 `int(amount)`，之後 `_counted_rows` 也只留大於 0 的，所以負數和 0 兩邊都不算。
  - 沒記租戶的舊列、屬於這個租戶的文字、小數、BLOB 金額都會觸發退回。
  - 退回時直接呼叫原算法本身，所以丟出的例外、訊息、還有例外先後順序都跟原算法一樣。
- **型別親和：** 欄位是 INTEGER affinity，`'12'`、`' 12'`、`'12.0'`、`2.0`、`True` 寫進去時就轉成整數存了，兩種算法讀到的是同一個值，不會出錯。`1e20` 這種轉不了的會存成小數，走退回。
- **溢位：** 因為只加正整數，部分和只增不減，所以資料庫報溢位等於總和真的超過上限。兩段在 Python 裡相加，不受上限影響。溢位判斷同時要求錯誤碼是一般錯誤碼、訊息完全相符，查詢寫錯的錯誤會照舊往外丟。
- **對抗隨機測試：** 我自己寫了生成器（`/tmp/f7-lens1/scratch/fuzz.py`），比測試附的更刁：
  - 租戶欄有 NULL、`'T-A'`、`'t-a '`、BLOB、整數、空字串。
  - 金額從 −2^63 到 2^63−1，加上各種文字、小數、BLOB、布林。
  - 同一把鍵有 0 到 3 列中間狀態；時間有剛好 24 小時、少 1 微秒、`+00:00` 格式、沒有小數秒、未來時間、亂碼。
  - 終點狀態混在一起；舊列快照壞掉或預算不是整數。

  結果：種子 1 跑 20000 份、種子 7 跑 5000 份，差異都是 0。種子 7 那 5000 份裡，走快路徑的 2113 份、退回的 2887 份，兩邊都有真的比到。
- **變異測試：** 對快路徑做了 13 種變異，只跑 `test_aggregate_fast_path.py`。
  - 抓到 9 種：拿掉 `>0`、忽略舊列、忽略型別異常、把文字當成正常型別、SUM 改 TOTAL、拿掉租戶篩選、溢位時回 0、跳過未結案那一段、未結案那段退回時沒有作廢整次結果。
  - 沒抓到的 4 種裡，3 種是等價變異（一律查未結案那段、SUM 也收小數，後者重複跑了一次），結果本來就不會變。
  - 剩下窗口 `>=` 改 `>`：這是兩種算法共用的片段，等價測試天生抓不到，但 F7 和可觀測查詢的 3 支既有測試會翻紅。
- **查詢計畫：** 已驗證那段是 `SEARCH v USING INDEX attempts_verified_by_time (written_at>?)` 接 `SEARCH f USING INDEX sqlite_autoindex_attempts_1 (key=? AND seq=?)`，符合 S683。

**4. S19 綁定測試收窄這件事本身精確；但測試原本就有一個漏洞**
severity: minor
blocking: 否
引句:「if node.module == "rtb.sqlitekit" and names <= SQLITEKIT_PURE_CHECKS:」
`tests/executor/test_attempt_store.py:624`
- 對實作者要求判的收窄，我的判斷是可以接受：
  - 只有 `from rtb.sqlitekit import` 而且只取 `is_integer_overflow` 才會放行。
