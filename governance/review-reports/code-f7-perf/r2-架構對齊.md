## 範圍（架構對齊席，第 2 輪）

這一輪只比對寫法跟專案既有做法一不一樣。材料以 r2-delta.patch 為主，對照的既有程式都在 be19aad。實驗都在 `/tmp/架構對齊-f7cr2` 複本上跑，用 python3.14；跑完已刪掉複本，也沒有留下行程。

**四個重點的結論**

- **`InboxBusyNotStarted` 用子類別：** 跟專案做法一致。
  - 它沿用 `InboxRejected` 家族「類別屬性 `code`／`retryable`」的慣例，繼承到 `code = "busy"`、`retryable = True`，不另記旗標。
  - 但收件口伺服器的 HTTP 對應表是用「確切型別」查的，子類別查不到（見發現 2，minor）。
- **`Executor` 注入 `sleep`：** 不算第二種做法，不列為發現。
  - 兩支 runner 的慣例是：入口的 `run(..., sleep=time.sleep)` 接真的睡眠，往下一路用參數顯式傳。見 `src/rtb/executor/runner.py:154`、`src/rtb/analyzer/runner.py:148`。
  - 這次入口照樣把同一支 `sleep` 傳進 `Executor`（`src/rtb/executor/runner.py:196`）。
  - `Executor` 用 dataclass 欄位接 `sleep`，跟同一個類別的 `clock: Callable[...]` 欄位同一種形狀。
  - 跟慣例唯一不同的是：這個欄位預設是「不睡」，而 runner 內部的輔助函式都要求必傳。整個 src 裡用 `default=lambda` 的欄位只有這一個。設計第 94–95 行已經明文裁定「其他建構點預設不睡」，而且退避只是禮讓、不影響正確性，所以歸為風格，不列。
- **`lease_until` 放在收件表模組：** 分層沒問題。
  - 租約欄在收件表，讀它的函式跟 `extend`、`_held` 放在同一個類別，執行迴圈照舊只透過 store 碰資料庫，沒有跨層。
  - 問題出在它的例外處理：它把所有資料庫錯誤都吞掉，這是專案原本沒有的第二種分類法（見發現 1，major）。
- **重試常數放在 `execution.py`：** 一致，不列。
  - 放法跟同一個檔的 `MAX_PENDING_CALLS`、runner 的 `BUSY_LIMIT` 一樣，都是「用的模組持有自己的政策常數」。
  - 等鎖上限直接取 `sqlitekit.BUSY_TIMEOUT_SECONDS`，不另抄一份，有前例：`src/rtb/executor/inbox_server.py:42`。
  - 執行迴圈的邊界測試只禁止匯入 DSP 和網路模組（`tests/executor/test_executor_boundaries.py:30`），沒有禁止匯入 sqlitekit。
  - 附帶一點：`InboxStore` 其實可以用別的 `busy_timeout_seconds` 開啟，常數跟實際等鎖時間理論上可能不同。不過執行端每個 `InboxStore(...)` 建構點都用預設值（`src/rtb/executor/runner.py:141`），現在不會出錯，不列。

**附帶查過：** 新增的 `legacy_candidate_query` 照 `*_query` 慣例寫：只回語句加參數、不執行，測試拿它跑 EXPLAIN（`tests/executor/test_aggregate_fast_path.py:405`）。一致。

## 發現 1:`lease_until` 把所有資料庫錯誤都當成「讀不到租約」，把永久故障改報成忙碌，是專案原本沒有的第二種分類法
severity: major
blocking: 是
引句:「讀本身出錯也回 None——呼叫端當作」
引句:「        except sqlite3.Error:」
引句:「其他資料庫錯誤照舊往外丟,不退回(不然查詢寫錯會被悄悄吞掉)」

**專案原本只有一種做法：只接「忙碌」，其他錯誤原樣往外丟。**
- 共用資料庫模組開頭第一句就是「忙碌與永久故障分得開」，而且 `begin_immediate` 只把鎖競爭轉成 `DatabaseBusy`，其他原樣丟出。見 `src/rtb/sqlitekit.py:1`、`src/rtb/sqlitekit.py:62`。
- 執行迴圈補寫呼叫紀錄時，也只接住忙碌，「其他資料庫錯誤照舊往外丟」。
- 同一份改動的快路徑，只接整數溢位，其他照丟，理由就是上面第三句引句。
- 整個 src 裡，只有 `src/rtb/executor/inbox_store.py:1312` 這一處用 `except sqlite3.Error` 把錯誤吞掉。

**吞掉之後會發生什麼：**
- `lease_until` 回 None，`_lease_allows` 就回 False（`src/rtb/executor/execution.py:984`）。
- 接著 `_retry_busy_begin` 往外丟的是原本那個 `InboxBusyNotStarted`（`src/rtb/executor/execution.py:976`），真正的錯誤就不見了。
- 啟動程式用 `except InboxBusy` 把它當成正常的鎖競爭：這一輪休息、忙碌次數加 1（`src/rtb/executor/runner.py:76`）。
- 結果是：本來應該讓行程帶著錯誤原因停下來的永久故障（查詢寫錯、表不見、磁碟 I/O、連線已關），被改報成「資料庫忙碌」；連續 3 輪以後停機訊息寫的是「資料庫連續 3 輪忙碌」。

**具體例子：**
- 輸入：寫結果時開交易鎖不到；接著讀租約時碰到非忙碌的永久錯誤，例如 `no such table: proposals`。
- 預期：照專案慣例，這個永久錯誤原樣往外丟，不重試，也不當成忙碌。
- 實際：`lease_until` 回 None，往外丟的是 `InboxBusyNotStarted database is locked`，啟動程式把它算成一輪忙碌。

**重現（在 /tmp 複本跑；造表不見的方式是把 `proposals` 改名）：**
```
$ PYTHONPATH=src:. python3.14 exp.py
正常查無: None
同一句直接跑: OperationalError no such table: proposals
lease_until 回: None
連線已關,lease_until 回: None
$ PYTHONPATH=src:. python3.14 exp2.py   # 同一個 store 接進 Executor,attempt 丟 InboxBusyNotStarted
往外丟: InboxBusyNotStarted database is locked | sleeps: []
```
- 「查無」「表不見」「連線已關」三種情形，回傳值都是 None，分不出來。
- 永久錯誤最後被換成了忙碌。

**為什麼不是設計允許的：**
- 設計第 112 行寫的「讀不到也不再試」，指的是租約已經被別人接手、或已經不是處理中，也就是查無這一列。它沒有說讀的時候出錯也吞掉。
- 這句「讀本身出錯也回 None」只寫在 docstring 裡：沒登記在設計的〈落點〉，家筆記沒記，也沒有測試守它。我用 `grep lease_until tests/` 找過。

**建議：**
- 拿掉 `except sqlite3.Error`，讓永久錯誤照舊往外丟。
- 如果真的要容忍讀取時忙碌，只接鎖競爭那一種（比照 `sqlitekit._is_lock_contention`），跟專案唯一的分類法對齊。

## 發現 2:`InboxBusyNotStarted` 查不到收件口伺服器的 HTTP 對應表；docstring 說「照舊抓得到」，對這張表不成立
severity: minor
blocking: 否
引句:「class InboxBusyNotStarted(InboxBusy):」
引句:「既有抓收件口忙碌的地方照舊抓得到」

**哪裡查不到：**
- 收件口伺服器把拒收對應成 HTTP 狀態時，是用確切型別查表：`REJECTION_STATUS[type(exc)]`（`src/rtb/executor/inbox_server.py:122`）。
- 表裡只登記了 `InboxBusy`（`src/rtb/executor/inbox_server.py:46` 到 `:55`）。
- `except InboxBusy`、`isinstance` 這些抓法，子類別照舊抓得到；只有這張按型別查的表抓不到。

**現在會不會出事：** 不會，所以只列 minor。
- 收件口伺服器走的是 `accept`，它自己開交易，忙碌時自己丟 `InboxBusy`（`src/rtb/executor/inbox_store.py:937` 到 `:945`），不經過 `transaction()`。
- 所以現在沒有路徑會把新類別送到 HTTP 層。
- 但這是 `InboxRejected` 家族第一個兩層的子類別，也沒有測試檢查「每個拒收類別都登記在對應表裡」（我找過 `REJECTION_STATUS` 和 `__subclasses__`）。

**具體例子：**
- 輸入：`InboxHandler.map_exception(None, InboxBusyNotStarted("x"))`。
- 預期：跟父類別一樣回 `(503, 'busy', True)`。
- 實際：丟 `KeyError`；如果真的走到 HTTP 處理，會變成 500。

**重現（/tmp 複本）：**
```
InboxBusy -> (503, 'busy', True)
InboxBusyNotStarted -> KeyError <class 'rtb.executor.inbox_store.InboxBusyNotStarted'>
```

**建議（三選一）：**
- 把新類別加進 `REJECTION_STATUS`。
- 或者把查表改成照 MRO 找第一個有登記的類別。
- 或者至少把 docstring 那句限縮成「用 except 抓的地方」。

2 條，blocking 1。
