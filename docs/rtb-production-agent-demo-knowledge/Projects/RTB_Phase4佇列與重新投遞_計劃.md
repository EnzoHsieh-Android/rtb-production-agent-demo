# RTB_Phase4佇列與重新投遞_計劃

PRIOR-ART: 這是「至少送一次的佇列 + 可見性逾時 + 確認 + 死信」的標準解(SQS、RabbitMQ、Kafka 的消費者提交都是同一組概念),配上「確認要晚於持久結果」這條老規則。最小解在本專案既有的層就做得到:收件表本身就是一張有狀態的表,加租約欄位與投遞次數就是佇列;不引入外部佇列軟體(零依賴家規),也不自造訊息格式。採用:借用概念,在既有收件表上長出佇列語意。
RETIRE-IF: 若之後換成真的外部佇列(SQS 之類),這層的可見性逾時、投遞次數與死信改由它負責,本專案只留「確認晚於持久結果」與「重新投遞先讀持久狀態」兩條規則。

## 這份計劃在解決什麼

- 事故 F2(交接文件第 16 節):外部寫入與本地持久結果都已完成,工作者卻在送出確認之前當機。佇列沒收到確認就會重新投遞;處理錯的後果是同一筆預算被改兩次。
- 事故 F3:同一則訊息被投遞兩次以上(不同工作者、不同嘗試)。任務識別要穩定、狀態轉換要合法、重複投遞不能重複花分析的錢,也不能繞過執行閘。分析費用這一半只保證同一時間只有一個持有有效租約的一方花錢;持有者花完錢、寫入前當機,或一步做超過租約被接手時,會再分析一次(至少一次的代價,見增量 3b〈保證什麼、不保證什麼〉)。
- 範圍:交接文件 Phase 4「Queue、Redelivery 與 Checkpoint」。樂觀鎖與並行寫入是 Phase 5;權限、護欄與總曝險是 Phase 6;提示注入是 Phase 7。
- 驗收(交接文件 Phase 4 完成條件):F2、F3 通過(F3 的「不重複分析費用」由增量 3 補上,F3 整條在增量 3 完成後才轉正,見增量 2 的「F3 轉正的範圍與缺口」);當機點至少涵蓋外部寫入前、DSP 提交後但本地寫入前、持久結果已寫但確認前;重新投遞由持久事實恢復,不靠行程記憶;確認時機有測試與設計說明;佇列重試不造成重複的有害副作用。
- 已登記的預告合約 [[Verification/事故F2_確認前當機不重複副作用]] 與 [[Verification/事故F3_重複投遞不重複分析與副作用]](都最遲 2026-11-30)是這個階段要轉正的合約。

## 使用者情境題(2026-09-23)

- 題目:一則任務訊息被取出,工作者改了 DSP 的預算、成功了,也把結果寫進本地資料庫;正要送出確認時當機。佇列重新投遞,新的工作者拿到它。該怎麼做?a 重跑整個流程;b 先看本地持久狀態,已有結果就直接確認、不碰 DSP;c 先送確認再處理;d 一律用冪等鍵向 DSP 查證後再決定。
- 使用者答 d。回饋:抓到最重要的一點——不能用「訊息又來了」當成「還沒做」。但每次重新投遞都去問 DSP,是把本地已經確定的事也交給網路重問。正確順序是 b 打底、d 補充:**本地持久狀態是第一順位**(嘗試紀錄與結果在同一個交易裡寫下,終點狀態本地說了算),只有本地停在未結案時才走 Phase 3 的對帳去問 DSP。這也省下重複的分析費用(事故 F3 明講)。
- 這一題順帶帶出 Phase 4 真正的判斷點:**什麼時候送確認**。太早(選項 c)等於承認了沒做完的事,當機就沒人重做;太晚則會重複投遞。

## 三個增量(2026-09-23 使用者同意這個排法)

- 增量 1:佇列語意與確認規則。收件表長出租約(可見性逾時)、投遞次數與死信;取件不再等於確認,確認只在「這個邏輯操作有終點或提案被擋下」時才寫。
- 增量 2:重新投遞恢復與事故 F2、F3 端到端。重新投遞先讀持久狀態判定;三個當機點各一個測試。
- 增量 3:多工作者的租約與圍籬。同一則訊息被兩個工作者處理時,只有租約還有效的那個能寫;過期租約的寫入要被擋下,取代 Phase 3 的單一執行者鎖。另外補**分析側去重**:同一個任務的分析同一時間只有一個在跑(分析行程的租約或冪等),重複投遞不重複花分析的錢(2026-09-23 使用者決定排進這個增量)。
  - 2026-09-23 使用者同意拆成兩半:**增量 3a** 執行側多工作者(重啟恢復不碰別人持有的嘗試、拿掉單一執行者鎖、真並行驗證);**增量 3b** 分析側任務租約與事故 F3 整條轉正。

## 增量 1 設計:佇列語意與確認規則(2026-09-23,第 4 版:已折入第 1 到 3 輪設計審)

- 事故:取件就當成確認,當機在「取件之後、寫入之前」那一段,訊息再也不會被重投,提案默默消失;反過來,確認寫在持久結果之前,當機就會讓已經做完的事被重做一次。
- **第 1 版被推翻**:處置整個延後、提案留在待處理,會被到期標記與取代改壞、確認寫不進去(第 1 輪)。第 2 版改成取件當下寫「處理中」。
- **第 2 版被補強的地方**(第 2 輪 22 條,3 條 blocker):租約用投遞次數充當擋不住過期工作者,也沒管到嘗試紀錄的寫入,跟 Phase 0 已定的 lease 規則不一致;轉人工、人工處置、保留期清除三條路沒有程式接得上;既有的標過期、標擋下、清除動作還用「是否待處理」判斷,新流程下全部失效;死信原因與失敗脈絡的型別沒定義。
- **第 3 版補的接縫**(第 3 輪 9 條):取件的終點快路徑拿不到收據;接手後遇到嘗試中沒有出路;回退沒先排空處理中;取件要經嘗試紀錄模組的函式;被取代清單漏了讀 DSP 失敗與全表已滿兩條;收據對不上會落進既有的停機路徑。
- **照 Phase 0 的裁定走**:[[Projects/RTB_Agent_Phase0架構]] 早已寫明「lease 是到期時間加序號,同一把 lease 同時管訊息與嘗試中紀錄;寫結果與 ACK 一律以條件更新進行,條件含 key、owner 與 lease 序號,更新到 0 列就放棄並進入對帳;結果不明的操作不計入重試上限、不得直接進 DLQ」。第 2 版把這些簡化掉了,這一版補回來。
- 範圍:收件表的佇列語意(租約、投遞次數、死信)、處理一筆與對帳寫處置的時機、取件後先讀持久狀態的分流、嘗試寫入受同一把租約管。不動 DSP 回應判定表與對帳對 DSP 的判定邏輯;增量 2 做三個當機點的端到端;增量 3 做多工作者。
- **狀態(2026-09-23):已完成**。S95–S117 全部綁了會真跑的測試;設計審 3 輪、代碼審 3 輪(5、4、1 條全部折入,每條修正都做了變異檢查)。代碼審額外補上:處理中那一列讀不回來時不能當成沒有(先掃完、找不到才停,對帳先處理完健康的鍵再停)、確認寫入的回傳值要檢查(寫不進去就是失去租約)、啟動時資料庫忙碌要乾淨結束並放掉鎖、同一把鍵兩張收據靠開始一筆擋住的測試。卷證在 governance/review-reports/code-phase4-queue/。

### 處置從兩態變四態

- 處置列舉從兩個成員(已交給執行、已擋下)變成四個,多**處理中**與**死信**。
  - 處理中:取件當下寫,代表「這則訊息已經交出去,租約還在」。它不是待處理,也不是確認。
  - 死信:沒有任何嘗試紀錄、而投遞次數用完,不再交出去。(2026-10-02 更正:Phase 8 起人可以重放死信,放回待處理、投遞次數歸零後會再被交出去,見 [[Systems/提案收件口]] 的重放方法)
- 「已過期」維持是狀態、不是處置。處理中的提案被判已過期時,狀態改成已過期、處置清空、租約清空,從此不可取件。
- 處置欄位的資料庫層限制(CHECK 約束)只認兩個舊成員,加欄位改不了它。遷移照 SQLite 官方的重建表步驟(建新表、抄資料、換名),在同一個立即取得寫入鎖的交易裡做,拿到鎖後再查一次。這段只寫在收件表模組裡,不放進共用資料庫工具:專案裡只有這一處需要(第 2 輪相容席在暫存目錄實驗過:兩條連線同時開只重建一次;提交前被強制殺掉會整段回滾;這張表除了主鍵沒有別的索引或觸發器要重建)。

### 租約(照 Phase 0 的 lease)

- 收件表加四欄:**租約到期時間**、**租約序號**、**租約擁有者**、**投遞次數**。
  - 租約序號:每次取件或接手加 1,是「這一次交付」的身分。投遞次數只算真正交出去給處理一筆的次數,兩者分開(外家席指出拿投遞次數充當序號,租約過期但還沒人重新取件時,舊工作者仍能續租或確認)。
  - 租約擁有者:誰持有。增量 1 是單一執行者,擁有者就是執行迴圈這個行程的識別(行程編號加啟動時間);增量 3 換成每個工作者自己的識別。
- **收據**:取件或接手時回傳(任務編號、修訂序號、內容雜湊、租約擁有者、租約序號)。
- **所有帶收據的寫入**(延長租約、確認、以及下面講的嘗試寫入)的條件都是:處置是處理中、租約序號與擁有者等於收據、租約還沒到期。任何一項不符就更新 0 列,呼叫端放棄這次寫入(對帳會接手)。租約已過期的工作者不能續命,要重新取件、拿新序號(外家席與並行席指出)。
- **收據對不上是「放棄」,不是「停機」**:Phase 3 的寫結果與查證逾時遇到「沒有進展」一律停機,那是給「嘗試紀錄自己的序號被別人改過」用的(單一執行者下不該發生)。收據對不上在多工作者下是正常的租約競爭,所以另開一個結果:這把鍵這一輪放棄、跳過,執行迴圈繼續處理其他鍵;只有嘗試紀錄的序號對不上才照舊停機(第 3 輪租約席指出兩者要分開)。
- 單一執行者下,擁有者永遠是自己,所以對帳的原子接手條件恆成立,等於每輪無條件續租——這就是 Phase 0 要的續期機制(第 3 輪租約席指出這步推理沒寫出來)。
- **嘗試寫入也受同一把租約管**:處理一筆與對帳對嘗試紀錄做的每一個轉換(開始一筆、寫結果、查證逾時、重送),都在同一個交易裡先核對收件表那一列的收據仍有效,再寫嘗試紀錄;核對不過就不寫。兩張表在同一個資料庫檔,核對與寫入是同一個交易,不需要把租約欄位複製到嘗試紀錄。這樣過期的工作者醒來後不能把嘗試寫成已驗證(外家席指出第 2 版只保護收件表)。
- 可見性逾時暫用 60 秒,沒有實測校準。一輪處理最慢是幾次 DSP 呼叫(用戶端逾時暫用 5 秒)加本地寫入;對帳每輪會替仍在處理的訊息續租,所以慢的對帳不會讓活著的訊息過期。

### 取件

- **取件(receive)** 在一個交易裡做完(拿到寫入鎖之後才讀時鐘,比照既有的收件)。查嘗試紀錄一律經嘗試紀錄模組的既有函式(未結案計數、最新一列),必要時在那個模組加一支「有未結案嘗試的廣告」查詢;收件表模組不直接對嘗試表下 SQL(第 3 輪架構對齊席指出全專案迄今沒有例外):
  1. 在同一個交易裡算出「已有未結案嘗試的廣告」,排除它們。被排除的提案不交出去、不算投遞(第 2 輪並行席指出若分兩個交易,中間會有空窗)。
  2. 挑最舊的可取件提案:沒有處置的待處理提案,或處置是處理中而且租約已到期的提案。
  3. **先取得租約**:寫處置處理中、租約序號加 1、擁有者、到期時間,拿到收據。這一步還不算投遞。所有後續寫入都帶這張收據(第 3 輪外家席與相容席指出:原本的終點快路徑在拿到收據之前就要確認,跟「確認一律帶收據」互斥;挑中的又正是租約已過期的列,用舊租約確認必然 0 列)。
  4. **再看這把鍵有沒有嘗試紀錄**(用快照重算冪等鍵):
     - 有終點結果(已驗證、失敗)→ 用剛拿到的收據確認(已交給執行、或已擋下附「同一操作先前已失敗」),不交出去、不算投遞,改挑下一份。
     - 未結案 → 第 1 步已排除這種廣告,這一支走不到;留著當防線:放掉租約(到期時間設成現在)、不算投遞,改挑下一份。依 Phase 0:結果不明的操作不計入重試上限、不得直接進死信。
     - 沒有嘗試紀錄 → 往下。
  5. 投遞次數已經等於上限(暫用 5)→ 用收據寫死信(附原因與最後一次失敗),改挑下一份;死信那次不算投遞。所以「上限 5」就是最多交出去 5 次。(2026-10-02 更正:核可放回待處理(Phase 6)與死信重放(Phase 8)都會把投遞次數歸零,所以一份提案前後總共可能交出去超過 5 次,見 [[Systems/提案收件口]])
  6. 否則投遞次數加 1,回傳提案與收據。
- 取件在處理一筆的**最前面**,在讀 DSP 與執行前檢查之前。開始一筆(Phase 3 的取件交易)改成「核對收據仍有效 → 開始一筆」,不再挑件。
- **讀 DSP 失敗、全表未結案已滿**:Phase 3 是「不寫任何東西、提案留在待處理」,下一輪無限次重試。現在提案已經是處理中,所以改成:帶收據記下最後一次失敗、放掉租約(到期時間設成現在),下一輪就能再取;每取一次算一次投遞,5 次都失敗就進死信。這是刻意的改變——一直讀不到 DSP 的提案不該無限重試(第 3 輪相容席指出這兩條 Phase 3 合約的斷言已不成立)。
- 死信只會打到「沒有任何嘗試紀錄」的提案:讀 DSP 一直失敗、全表未結案已滿、或每次都在開始一筆前當機。一旦開始過嘗試,它就歸對帳管,不會進死信。所以不會有「死信之後才被證實成功」的情況(第 2 輪銜接席指出)。

### 死信原因與失敗脈絡

- 兩個封閉列舉都定義在收件表模組裡,不借執行迴圈的結果列舉:收件表是下層,反過來匯入上層會變成循環匯入(第 2 輪架構對齊席與可測性席指出)。
  - **死信原因**:目前只有一個成員「投遞次數達上限」。
  - **最後一次失敗**:處理一筆每次沒能開始嘗試就結束這一輪時,帶收據寫下原因,成員是「讀不到 DSP」「全表未結案已滿」「同廣告被鎖」「沒有回報(當機或租約過期)」。取件時若發現租約是過期回收的,記「沒有回報」。(2026-10-02 更正:實作時拿掉了「同廣告被鎖」,現況只有讀不到 DSP、全表未結案已滿、沒有回報三個成員,見下方〈實作時決定(增量 1)〉與 [[Systems/提案收件口]])
- 死信記下原因與最後一次失敗,人看得出它卡在哪一步(第 1 輪外家席指出只記次數不夠)。

### 確認規則(這個增量的核心)

- **確認一定晚於持久結果**。處置寫「處理中」不算確認,只有下面這些是:
  - **已交給執行**:這把鍵的嘗試到了已驗證。
  - **已擋下**:執行前檢查沒過(附既有的擋下原因),或這把鍵的嘗試是失敗(附「同一操作先前已失敗」)。
  - **已過期**:提案自己過期(狀態改已過期、處置清空)。
  - **死信**:沒有嘗試紀錄、投遞次數用完。(2026-10-02 更正:死信之後人仍可重放放回待處理,見 [[Systems/提案收件口]])
- 確認一律帶收據做條件寫入。既有的「標過期」「標擋下」原本以「仍待處理」為條件,新流程下提案一定已經是處理中,所以條件換成收據(第 2 輪三段式席與相容席指出,照舊條件會永遠寫不進去)。
- **處理一筆**:取件之後,讀 DSP、執行前檢查、簽發、開始一筆、呼叫 DSP、寫結果;嘗試到終點就在同一個交易裡確認;停在未結案就不確認、延長租約、結束這一輪。
- **對帳接上收件表**(第 2 輪三段式席、可測性席、銜接席指出轉人工與人工處置接不上):
  - 對帳每一輪掃兩種鍵:「未結案的嘗試(含轉人工)」與「嘗試已到終點、但收件表那一列仍是處理中」。後一種涵蓋人工處置完成(人工處置只寫嘗試紀錄,不碰收件表)與任何中途當機留下的漏網。

  - 接手之後:嘗試中 → 在新收據下先轉成結果不明,再照結果不明處理(過期工作者留下的嘗試中,接手者要能合法收拾;現況靠啟動時的重啟恢復,增量 3 移除單一執行者鎖後就只剩這條路,第 3 輪外家席指出);轉人工 → 只續租,不碰 DSP、不動嘗試狀態;結果不明與已提交待驗證 → 照 Phase 3 的對帳推進,推到終點就在同一個交易裡確認;已到終點 → 直接確認。

  - 同一把鍵可能對應多份修訂(只換到期時間的新修訂算出同一把鍵):對帳只處理「處置是處理中」的那一列;其餘修訂在取件時會讀到既有嘗試紀錄而直接確認或跳過。

### 實作時決定(增量 1,2026-09-23,代使用者裁定,待覆核)

- 死信原因與最後一次失敗各佔一欄(死信原因、最後一次失敗),加上租約四欄,收件表共多六欄;都在同一次重建表遷移裡補。
- 「最後一次失敗」拿掉「同廣告被鎖」這個成員:取件已在同一個交易裡排除鎖住的廣告,單一執行者下走不到;開始一筆撞到同廣告鎖住時仍放掉租約(防線),但不記原因。
- 續期機制做在每一筆嘗試寫入上:核對收據與續租是同一個條件寫入(延長租約),活著的工作者每寫一筆就把租約往後推。所以處理一筆結束時停在未結案,不必另外延長。
- 取件之後提案已是處理中,新修訂不能再取代它。[S108] 原本要驗的「已被取代就不開始」改由「收據已失效(被接手或過期)就不開始、不呼叫 DSP」來驗。
- 放掉租約時把擁有者清空;取件回收一列處理中時,擁有者還在就代表上一個持有者沒回報(當機或卡住),記「沒有回報」。
- 對帳找不到這把鍵對應的處理中那一列(Phase 3 時代留下的已交給執行、或收件表已被清掉)時,不帶收據、照 Phase 3 的方式對帳,也沒有訊息可確認;這種鍵若停在嘗試中,留給啟動時的重啟恢復。
- 嘗試到了失敗就確認成「已擋下」並附「同一操作先前已失敗」,這把鍵第一次投遞就失敗(例如版本衝突)也一樣;更細的失敗原因看嘗試紀錄的結果代碼。
- 啟動程式多一個可指定的擁有者參數(測試用,讓同一測試裡的處理一筆與啟動程式算同一個工作者);預設是行程編號加啟動秒數,重啟後是新的擁有者,上一次留下的租約要等到期才接手。
- 分析行程收件用戶端不受影響:它只看狀態碼。收件表模組多匯入冪等鍵函式與嘗試狀態列舉(取件分流用),「收件口不定義欄位驗證」那支既有測試的允許清單跟著加這兩個。

- 既有測試裡的「當機」都是同一個行程內丟例外,會經過交易回滾與收尾程式碼;這批是**行程真的猝死**(沒有例外、沒有回滾、沒有收尾),再走**真的啟動程式**重啟(單一執行者鎖、重啟恢復、每輪先對帳)。補的是模擬與真實之間的落差。

### 怎麼造當機

- 每個當機測試開兩個子行程,先後跑(不同時):
  1. **會死的那個**:內嵌腳本在**類別上**換掉一個方法(執行迴圈的物件建好後不能改屬性,而且是在啟動函式裡面才建出來,測試拿不到那個物件;這一點跟既有猝死測試換在物件上不同),再呼叫執行迴圈的啟動函式。換上的函式在指定位置印一行「死點狀態」(交易是否還開著、嘗試紀錄最後一列的狀態——還沒有任何一列就印「無」、收件表那列的處置),然後 os._exit(9)。
  2. **重啟的那個**:內嵌腳本呼叫同一個啟動函式,但傳入往後撥的時鐘(真實時間加 5 分鐘)與有限輪數,跑完自己結束。
- 每個當機測試都做三道斷言(照抄既有猝死測試的雙重斷言,再加一道):
  - 會死的子行程退出碼是 9:證明真的死在換掉的函式裡,不是正常跑完。函式日後被改名或合併,換上的東西不會被呼叫、行程正常結束,測試就會紅,不會悄悄失效。
  - 死點狀態恰為預期那一格:證明死在指定的縫隙,不是前一步或後一步。
  - DSP 收到的寫入請求數:由測試行程裡的 DSP 伺服器計數(伺服器跑在測試行程的執行緒裡,子行程死掉計數也還在)。模擬 DSP 對同一把冪等鍵的第二次寫入會直接回原結果、不留痕跡,所以「只套用一次」證明不了「沒有重送」,要另外數請求。
  - 計數掛在請求處理器、照路由名稱分三類:改狀態的寫入(用 DSP 伺服器現成的「會改廣告的動作」清單判定)、作廢、其他(讀取不算)。不能掛在 DSP 儲存層真正套用變更那一步:同鍵重送在更前面就回原結果,走不到那裡,會漏數。沿用既有端到端測試換請求處理器的做法。
- **撥時鐘,不縮租約**:
  - 租約留正式的 60 秒;增量 1 的「租約要遠大於一次 DSP 呼叫」那條不變量照樣成立,測試不會因為機器慢而在半路丟租約。
  - 重啟的子行程時鐘往後撥 5 分鐘:舊租約(60 秒)已到期、可以合法接手。
  - 測試行程裡的 DSP 伺服器時鐘用「真實時間加一個可調偏移」:第一個子行程跑時偏移 0,重啟前設成 5 分鐘。不能沿用既有端到端測試那個停在固定日期的假時鐘:子行程拿不到它、只能用真實時間,兩邊差好幾小時,而 DSP 只容許 30 秒的時鐘誤差,憑證會被當成「簽發時間在未來」或已過期拒收。
  - 提案有效期限:要能恢復的情境設 30 分鐘(撥 5 分鐘後仍有效);要驗「重啟後已過期」的情境設 2 分鐘(第一個子行程時還有效、撥 5 分鐘後已過期)。兩個條件都跟機器快慢無關。
- 內嵌腳本只透過命令列參數拿資料庫路徑等設定,不經環境變數;金鑰照既有啟動測試,只放進那一次子行程專用的環境字典。

### 四個當機點

照成功路徑的持久步驟切:嘗試中(提交)→ 呼叫 DSP → 已提交待驗證(提交)→ 讀 DSP 驗證 → 已驗證加確認(同一個交易提交)。

1. **寫完嘗試中、還沒呼叫 DSP**:死點狀態是嘗試中、處理中;DSP 收到 0 次寫入。重啟恢復轉結果不明;對帳用冪等鍵查不到,重跑執行前檢查通過,用同一把鍵重送。預期:DSP 共收到 1 次寫入、套用 1 次、嘗試最終已驗證、訊息已交給執行。
   - 同一個死點,提案在重啟時已過期:對帳查不到、檢查不過,先請 DSP 作廢這把鍵再判失敗。預期:DSP 收到 0 次寫入、1 次作廢,廣告不變,訊息已擋下。
2. **DSP 已提交、本地還沒寫結果**:死點狀態是嘗試中;DSP 收到 1 次寫入且已套用。重啟恢復轉結果不明;對帳查到操作紀錄,不重送,驗證後確認。預期:DSP 共收到 1 次寫入、最終已驗證、訊息已交給執行。
3. **已提交待驗證已寫、還沒驗證**(這就是事故 F2「持久結果已寫、確認還沒送」的形狀:本地有結果、收件表還沒確認):死點狀態是已提交待驗證、處理中,交易已關。重啟恢復不動它(只轉嘗試中);對帳接手後照執行後驗證走完。預期:DSP 共收到 1 次寫入、最終已驗證、訊息已交給執行。
4. **終點結果與確認的交易邊界**(已驗證與確認在同一個交易裡,Phase 0 的 ACK 規則):
   - 死在提交**之前**(換掉的是交易內寫確認的那一步:先照常寫,再印狀態並死):死點狀態是交易還開著。整筆回滾,重啟後看到的是已提交待驗證,照第 3 點恢復。預期同第 3 點。
   - 死在提交**之後**(換掉的是執行後驗證整段:先照常跑完,再印狀態並死):死點狀態是已驗證、已交給執行。重啟後什麼都不做。預期:DSP 共收到 1 次寫入、0 次作廢,嘗試紀錄與處置都不變。
- 換掉的函式有的是私有方法(例如交易內寫確認那一步)。選擇照抄既有猝死測試的做法(它也是換掉私有方法),不在正式程式碼的交易入口加「提交前回呼」:那會為了測試改正式程式碼;而退出碼斷言已經擋住「方法改名後測試悄悄失效」。

### 事故 F3:同一則訊息投遞兩次以上

- 同一則訊息先交給第一個執行迴圈,它在取件之後、開始嘗試之前死掉;第二個執行迴圈(撥過時鐘)重新取件。預期:
  - 第二次取件投遞次數是 2,拿到的是同一列、同一個任務與修訂。
  - 整個過程只有一把冪等鍵、只開一筆嘗試;嘗試紀錄相鄰兩列的狀態轉換每一步都合法(用程式自己的合法轉換表逐對核對)。這兩點結構上本來就成立(重新投遞沿用同一列;每一次寫嘗試都經合法轉換檢查),這裡把它寫成明文斷言,轉正審計時有東西可對。
  - DSP 共收到 1 次寫入、最後已交給執行。
- **重做分析也不能繞過執行閘**:同一個任務的第一版提案已執行(預算改成 150,DSP 版本因此往前走一格),分析行程重做分析送來第二版:新修訂、目標不同(預算改成 160),但它看到的廣告版本是舊的。預期:測試先斷言兩版的冪等鍵不同;第二版照樣重跑執行前檢查,被「版本已變」擋下;DSP 共收到 1 次寫入。
  - 目標必須不同:冪等鍵只由任務、廣告、動作、要改成多少、看到的版本五樣算出,修訂序號、理由、證據、期限都不算。只改理由的第二版會算出同一把鍵。
- **只改理由的新修訂靠已完成紀錄安全跳過**:第二版目標與看到的版本都跟第一版相同,只改理由。預期:兩版冪等鍵相同,取件時查到這把鍵已驗證,直接確認第二版、不讀 DSP、不跑執行前檢查;DSP 共收到 1 次寫入。這不是「過執行閘」,是「同一件事已做完不再做」,分開列才不會把它當成執行閘的證據。
- 分析行程重送同一份提案(同任務同修訂、同內容)照收件口既有合約回目前狀態、不新增一筆,這裡在端到端裡順帶驗一次。

### F3 轉正的範圍與缺口

- 交接文件的 F3 原文是「重複投遞不會重複**分析費用**或副作用」;已登記的預告合約只寫「不會重複副作用」,少了分析費用。這個落差在登記預告合約時就存在,這裡點明,不讓它悄悄傳下去。
- 第 1 版說「不重複分析費用屬於 Phase 2(已有任務佇列與檢查點)」是錯的:Phase 2 範圍明寫不加佇列;分析行程目前沒有租約或去重(2026-10-02 更正:增量 3b 已加分析側任務租約,見 [[Systems/分析行程流程與檢查點]]),而檢查點只防「同一行程重啟後重做已提交的步驟」,擋不住兩次呼叫同時跑時外部分析各呼叫一次。
- 2026-09-23 使用者決定:分析側去重排進增量 3。所以:
  - 增量 2 交出 F3 執行側的測試(任務識別不變、狀態轉換合法、不重複副作用、重做分析不繞過執行閘),但**不轉正 F3**。
  - 增量 3 補上分析側去重與它的測試後,F3 整條一次轉正。
- 轉正工具是機械的:它把預告合約「預告的合約:」那一行原文照抄成正式合約,沒有地方縮小範圍或加註。所以轉正前要先把那行補回「不重複分析費用」,跟交接文件一致;不補就照抄,讀起來會是 F3 整條通過。這一步排在增量 3 開工時做。

### 確認時機的說明(交接文件要求「ACK 時機有測試與設計說明」)

- 取件寫「處理中」不是確認。確認只在跟**終點**結果同一個交易裡寫(已交給執行、已擋下、已過期、死信),所以「終點結果已寫、確認沒送」這一格不存在(第 4 點證明兩個邊界)。
- 但「持久結果已寫、確認沒送」這個形狀仍會出現在非終點的狀態:嘗試中、結果不明、已提交待驗證。這些都不確認,讓租約到期後由對帳接手推進:
  - 嘗試中(第 1、2 點):重啟恢復轉結果不明,對帳用冪等鍵查 DSP。
  - 已提交待驗證(第 3 點):對帳重跑執行後驗證,只讀不寫。
- 第 1 版說「剩下的危險窗口只有 DSP 已提交、本地結果還沒寫」,漏了已提交待驗證那一段;已更正。
- 這段說明同步寫進 [[Systems/執行迴圈]]。

### 預告合約轉正

- 轉正工具的實際限制(讀過工具程式確認):
  - 它照預告合約的「守護對象」欄位找家,再到那一篇找一字不差的預告行,換成正式合約。F2、F3 的欄位和預告行現在都在 [[Systems/提案收件口]]。(2026-10-02 更正:F2、F3 已轉正並搬到 [[Systems/執行迴圈]],提案收件口已沒有它們)
  - 「守護對象」欄位不在改欄位指令的白名單裡,指令改不了。
  - 轉正一次只綁一支測試,其餘要用補綁指令逐一加。
  - 審計指令只認得已轉正的合約;轉正會把狀態直接改成已通過,沒有指令能退回。
- 所以照 Phase 3 轉正事故 F1 的前例做(那次也是從提案收件口搬到執行迴圈):
  1. 在原來那篇轉正 F2,綁 [S118] 的測試;再補綁 [S123]、[S119]、[S122]、[S120]、[S124] 的測試。
  2. 把轉正後的合約行從 [[Systems/提案收件口]] 搬到 [[Systems/執行迴圈]],守護對象欄位手改成執行迴圈(工具不支援改這個欄位;F1 當時同樣手改)。
  3. 派一個不知道脈絡的代理審「F2 是不是真合約、測試夠不夠格」,用審計指令蓋章。
  4. 以上同一個提交。審計不同意就在推送前撤掉這個提交、修好再來。這比「先審再轉」弱:工具排不出那個順序,推送前的撤回是唯一的回頭路。
- F3 等增量 3:開工時先把預告合約檔的「預告的合約:」那一行和提案收件口裡的預告行一起補回「不重複分析費用」(兩處要一字不差,工具才找得到);做完後照上面四步轉正,綁分析側去重的測試,補綁 [S121]、[S125]、[S126]。

## 增量 3a 設計:執行側多工作者(2026-09-23,第 4 版:已折入第 1 到 3 輪設計審)

- 使用者情境題(2026-09-23):A、B 兩個執行迴圈同時在跑;A 剛寫下嘗試中、正在等 DSP 回應,租約還有 50 秒;B 重新部署而重啟,照現在的做法把 A 那筆也轉成結果不明。會怎樣、怎麼改?a 沒事;b A 寫結果時序號對不上而整個停機,改成重啟恢復只處理沒人持有的;c B 啟動後先等所有租約到期;d 維持單一執行者鎖。使用者答 b,答對。回饋:A 寫結果時先核對收據(租約還是 A 的,過)、再用自己記得的序號寫嘗試紀錄,B 已在後面多加一列,序號對不上就走「系統錯誤停機」,健康的 A 被別人的重啟打掛;c 讓每次重啟白等一整段租約、一則卡住的訊息拖住整台;d 放棄 Phase 4 的要求。補一個細節:租約已過期的嘗試中,對帳接手時本來就會自己轉結果不明(增量 1 的規則、增量 2 已驗),所以重啟恢復要處理的比 b 還少,只剩「收件表沒有對應處理中訊息」的舊資料。
- PRIOR-ART: 多消費者佇列的標準做法——訊息的歸屬只看租約(SQS 可見性逾時、Kafka 消費者群組的分區指派),消費者不做「全域清場」;過期的由下一個取件者接手。本專案增量 1 已照 Phase 0 裁定做好租約、收據與條件寫入,這裡只把最後一個全域動作(重啟恢復)收窄、補上「沒有收據的舊鍵」的競爭規則,並拿掉單一執行者鎖。不引入新機制。並行測試沿用本專案既有做法:同一個行程裡多執行緒、各自開自己的資料庫連線、用執行緒柵欄逼同時下手(嘗試紀錄、Mock DSP、分析行程的並行測試都是這樣寫)。
- RETIRE-IF: 換成外部佇列軟體、訊息歸屬由它管時,撤掉收件表的租約與這裡的重啟恢復規則。
- **狀態(2026-09-23):已完成**(設計審 3 輪,13、8、7 條;代碼審 3 輪,9、1、6 條,全部修正)。S127–S136、S138、S139 綁了會真跑的測試(S137 撤回),二十八道變異檢查全紅。代碼審第 2 輪證偽了一個設計前提(「沒有處理中訊息的嘗試中沒人在做」),補 S138;第 3 輪補 S139(DSP 逾時與租約的比例擋在啟動時)。第 3 輪的修正沒有再經下一輪審查。卷證在 governance/review-reports/code-phase4-multiworker/。

### 重啟恢復只碰沒人持有的嘗試中

- 改成只轉「收件表沒有對應處理中訊息」的嘗試中(Phase 3 時代留下、或收件表被人工處置過的舊資料)。有對應處理中訊息的,不論租約到期沒有,一律不動:
  - 還沒到期:別人正在做,不能碰。
  - 已到期:對帳接手時會在同一個交易裡先原子取得租約、再轉結果不明(增量 1 的規則);重啟恢復不取租約就改,會跟同時接手的工作者搶。
- 為什麼「沒有處理中訊息」就等於沒人持有:開始一筆(寫第一列嘗試中)是在核對收據的同一個交易裡做的,所以新時代的每一筆嘗試中,在它存在的每一刻都有一則處理中訊息;沒有的只可能是舊資料。
- 實作後更正(代碼審第 2 輪外家席):舊資料不等於沒人在做——對帳舊鍵時也會先寫嘗試中再呼叫 DSP。舊鍵沒有租約可看,改看那一列寫下多久:重啟恢復與對帳都只收寫下超過一個租約時間的舊鍵嘗試中([S138])。
- 哪些鍵有處理中訊息,用收件表模組現成的「所有處理中列的鍵」查詢,跟轉換在同一個立即取得寫入鎖的交易裡做,讀到的是一致的快照。嘗試紀錄模組不反過來依賴收件表模組(收件表模組已依賴它):由呼叫端把「要略過的鍵」傳進重啟恢復。
- 有讀不回來的處理中列時(算不出它的鍵),重啟恢復一把都不轉並回報:任何一把嘗試中都可能正屬於那則讀不回來的訊息。對帳本來就會在每一輪結尾因為讀不回來的列停機讓人看(增量 1 的規則),所以這不是默默卡住:第一輪就停,孤兒嘗試等人修好壞列後的下一次重啟再轉。

### 沒有收據的舊鍵:序號輸家放棄這把鍵,不停機

- 對帳遇到「收件表沒有對應處理中訊息」的鍵(舊資料)拿不到收據:嘗試中那一支本來就留給重啟恢復,但結果不明、已提交待驗證那幾支照樣往下查 DSP、寫嘗試紀錄,寫入只靠嘗試紀錄的序號比對。單一執行者下序號對不上「不該發生」,所以一律停機;多工作者下兩個工作者會同時對帳同一把這種鍵,序號輸家是正常競爭(第 1 輪三席各自抓到,含外家席)。
- 改成:**沒有收據時,嘗試紀錄序號對不上等同失去租約——放棄這把鍵、這一輪不再碰它,不停機。**有收據時照舊:收據對不上放棄,收據對得上而序號對不上仍是系統錯誤停機(那代表有人繞過租約寫了嘗試紀錄)。寫嘗試紀錄與記查證逾時兩條寫入路徑都照這條;這兩段在程式裡是各自獨立的判斷,兩邊都要改,各有一條合約守([S134]、[S136])。
- 為什麼安全:每一次呼叫 DSP 寫入之前,都先有一筆成功的「轉嘗試中」寫入(帶序號比對),所以兩個工作者之中最多一個能走到 DSP 寫入。作廢在寫嘗試紀錄之前呼叫,兩邊都可能送出作廢,但作廢是冪等的,送兩次跟送一次一樣。
- 不另開認領表:舊鍵只會越來越少(新時代的嘗試都有收據),為它們加一套機制不划算。

### 拿掉單一執行者鎖

- 啟動程式不再持有鎖;互斥交給租約與收據(增量 1:同一則訊息同一時間只有一張有效收據,每一筆寫入都核對它)。
- **新舊版本不能混跑**(第 2 輪外家席):舊版啟動時照樣拿單一執行者鎖、把所有嘗試中轉結果不明,它看不到新版工作者,會改掉新版手上收據仍有效的嘗試,新版寫結果時序號對不上而停機——重演 3a 要防的事故。
  - 處理方式是部署規則:**3a 上線前一次停掉所有舊版執行迴圈,之後不再啟動舊版**(回退也對稱:先停掉所有新版,見回退節)。監督程式或開機腳本裡的舊版啟動指令要在同一次部署裡換掉。
  - 不做機械圍籬(已知限制):舊版的程式已經寫死,不會去看新版留下的任何標記,所以任何圍籬都擋不住「新版在跑時有人或監督程式重啟舊版」這個方向(第 3 輪外家席)。第 2 版曾想讓新版啟動時探一下舊版的鎖,第 3 輪三席指出它只保護啟動那一刻、兩個新版同時啟動會把對方誤判成舊版、而且 SQLite 等鎖用真睡眠讓測試真的等 5 秒——三個問題都出在探鎖本身,拿掉,不留一道看起來有、實際上擋不住的防線。
  - 這是 demo,只有一台機器、不做滾動升級,這條規則的代價很小;符合「防忘記、不防刻意繞過」。
REVISIT:2026-12-31 若之後要支援滾動升級或多台機器,改用資料庫版本標記加舊版也會檢查的圍籬(那時舊版已是 3a 之後的版本,能加檢查)。
- 保留「資料庫檔有硬連結就拒絕啟動」:它防的是同一個資料庫被兩組 WAL 檔開啟而損壞,跟有幾個工作者無關。原本「先拿鎖才用 SQLite 開資料庫」的順序理由(硬連結)改由這道檢查單獨承擔。
- 資料庫忙碌改成:**這一輪休息、下一輪再試;連續 3 輪都忙才停機**。啟動時的開庫與重啟恢復照同一條:忙碌就稍等再試,連續 3 次都忙才以「資料庫忙碌」的代碼結束(第 2 輪忙碌停機席:多個工作者同時啟動時,開庫加重啟恢復握鎖最久、最容易撞忙碌)。單一執行者時等鎖 5 秒還等不到很罕見,停機讓人注意是對的;多工作者共用一顆寫入鎖,排隊等鎖是正常事件,工作者越多、健康的越容易被自己人擠到逾時而停機,正好抵銷開多工作者的目的,而且沒有自動重啟接得住(第 1 輪銜接席)。休息一輪之前這一輪的交易已回滾或已提交,不會留下半筆。
REVISIT:2026-12-31 有多工作者壓力測試時,量忙碌逾時的觸發頻率與「連續 3 輪」這個門檻合不合理。

### 真並行驗證

- 沿用本專案既有的並行測試做法:同一個行程裡開多個執行緒,每個執行緒各自建自己的收件表連線與執行迴圈物件(不同擁有者名稱、各自注入時鐘、共用同一個資料庫檔與同一個假 DSP),用執行緒柵欄在指定位置讓兩邊同時放行。第 1 版寫的「用檔案當信號、兩個子行程同時活著」撤掉:單向信號只能做出「B 等 A 做完」,造不出真正的同時搶;而且共用一個 DSP 時鐘偏移會讓還活著的那一個憑證過期,測試會因為錯的原因綠(第 1 輪可測性席、架構對齊席)。
- 各合約的會合點:
  - S130:兩個執行緒在呼叫取件之前的柵欄一起放行。
  - S131:兩份同廣告提案:兩邊都取完件、都還沒開始嘗試時的柵欄一起放行,才測得到開始嘗試那一道互斥;取件那一道(已有嘗試的廣告不交出去)是增量 1 已測過的另一道。
  - S132:工作者 A 在假 DSP 的寫入攔截點等信號;B 的時鐘撥過 A 的租約後接手、推進到終點再放行 A。假 DSP 不驗憑證時間,A 被擋的原因只可能是收據對不上。
  - S129:A 同樣停在假 DSP 的寫入攔截點;另一個執行緒跑啟動程式(只啟動、不跑任何一輪,等同重啟),完成後放行 A。
  - S134:兩個執行緒對帳同一把沒有處理中訊息的舊鍵,在寫嘗試紀錄之前的柵欄一起放行。
- 真的跨行程只剩 [S133] 需要:兩個啟動程式用子行程**同時**啟動(兩個都先啟動、再一起等就緒訊號,不是一個就緒了才啟動另一個;第 3 輪架構對齊席指出「沿用增量 2 的先後做法」會測不到同時啟動),驗兩個都在做完重啟恢復後印出就緒。
- 柵欄一律放在進入資料庫交易之前(第 2 輪可測性席實驗):開始一筆與寫嘗試紀錄都包在一個立即取得寫入鎖的交易裡,柵欄若放在交易裡面,先拿到鎖的那個等柵欄、另一個拿不到鎖進不來,兩邊互等。照嘗試紀錄既有並行測試的寫法,柵欄緊貼在進交易之前。
- 假 DSP 要先對齊真 DSP(第 2 輪架構對齊席):現在同一把鍵的第二次寫入會再套用一次、也沒有鎖。真 DSP 同鍵重送回第一次的結果;失去租約的工作者醒來補送的舊請求本來就會晚到,假 DSP 不去重就會變成假的「套用兩次」。改法(第 3 輪外家席、假 DSP 席):
  - 兩段式順序:測試用的寫入攔截點先執行,而且不握假 DSP 的狀態鎖;之後才用一把鎖把「查作廢、查同鍵、同鍵內容相同就回原結果、內容不同就回衝突、否則套用並記紀錄」包成一段。攔截點若在鎖裡面,失去租約那支測試的 A 停在攔截點時握著鎖,接手的 B 永遠寫不進去,兩邊卡死。
  - 同鍵內容不同回衝突,對齊真 DSP 的冪等衝突。
  - 並行測試的等待都加逾時,卡住時測試失敗而不是掛著。
  - 假 DSP 所在的測試檔掛到 [[Systems/Mock-DSP]] 那篇,寫一條「假 DSP 的冪等語意要跟真 DSP 對齊,改真 DSP 的冪等判斷時回頭改假 DSP」(第 3 輪架構對齊席)。
  - 假 DSP 席在臨時目錄改過後跑執行側 295 支測試全綠,並用 500 輪真執行緒競態確認只套用一次。
- 每支並行測試都做變異檢查:把被測的那一道互斥拿掉,測試必須變紅。

### 不做的事(增量 3a 範圍)

- 不做新舊版本混跑:升級與回退都先停掉另一版(見「拿掉單一執行者鎖」)。
- 不做跨機器部署:工作者都在同一台機器、共用同一個資料庫檔(SQLite 的限制)。
- 不做自動擴縮容、不做工作者健康檢查。
- 不做分析側(增量 3b)。

### 為什麼租約不照抄收件表的「改欄位」

- 執行側的租約是收件表上的欄位,每次取得、續租、放掉都是改那一列(UPDATE)。分析行程的任務表不能這樣做:
  - 任務模組的規則是歷史表只增不改,而且有一支既有測試掃整個任務模組的原始碼,只要出現任何「改」或「刪」的資料庫敘述就紅(Phase 2 的 S41)。把租約欄位加在歷史表上、或在同一個模組開一張會被改的表,都會踩到它。
  - 歷史表每一步都是新的一列,「目前那一列」一直在換,租約綁在某一列上也沒有意義。
- 所以在同一個資料庫檔、同一個任務模組裡開一張**只增不改的租約紀錄表**:每取得一次、放掉一次,都新增一列;「目前的租約」就是這個任務序號最大的那一列(跟歷史表「目前狀態就是序號最大那一列」同一個讀法)。沿用的是增量 1 的概念(租約序號、擁有者、到期時間、收據、條件寫入),換的只是寫法(新增列代替改欄位)。
- 遷移:新表放進任務模組既有的建表敘述(`CREATE TABLE IF NOT EXISTS`),舊資料庫下次開啟時自動多出這張空表,既有的歷史、證據、呼叫紀錄都不動;不需要增量 1 那種重建表,因為沒有動到任何既有表的欄位或限制。

### 租約紀錄表

- 欄位:任務編號、租約序號、擁有者、到期時間;主鍵是(任務編號、租約序號)。主鍵本身也是一道防線:兩個交易就算都算出同一個下一號,也只有一個插得進去。
- 兩種列:
  - **取得列**:擁有者是這次呼叫的識別,到期時間是呼叫端的現在時間加租約長度。
  - **放掉列**:擁有者空白、到期時間等於現在。有這種列,下一次呼叫才不必等租約到期(既有測試大量用同一個時間連續推進同一個任務,沒有放掉列它們全都會卡住)。
- 「現在有沒有人持有」:目前那一列(序號最大的)有擁有者,而且到期時間晚於呼叫端的現在時間。
- **收據**:取得時回傳(任務編號、租約序號、擁有者)。之後的寫入都帶它。
- **放掉一律帶條件**:不管是哪一步放掉(第 3、5、6、7 步),都在一個立即取得寫入鎖的交易裡先核對「目前那一列正是這張收據的取得列」,是才寫放掉列;已被別人接手就什麼都不寫。否則舊持有者遲來的放掉列會排在接手者的取得列之後,讓「目前那一列」變成沒人持有,第三個呼叫端就能在接手者還在花錢時拿到租約,接手者自己的提交也會因為目前那一列不是它的取得列而被擋(第 1 輪並發席排出這條交錯)。
- 擁有者:比照執行側,由推進函式的呼叫端傳入(預設 "analyzer",往後由啟動程式傳工作者身分),只是標籤。圍籬靠租約序號:每次取得都新增一列、序號不同,所以同一個行程裡的多條執行緒共用同一個擁有者也分得開(既有的並行測試就是這樣跑)。代碼審改過兩次:第一版每次推進產生隨機碼、第二版在推進函式裡讀行程編號加執行緒加序號,架構席都指出是專案沒有的第二種做法;第 2 輪確認「擁有者不必唯一」後改成現在這樣。因為每次推進只做一步,不需要跨呼叫沿用同一個擁有者。

### 推進函式怎麼用租約

照順序:
1. 讀目前那一列:沒有這個任務照舊丟「找不到」;已經是終點或已交接,照舊直接回傳,不取租約(這兩種不會呼叫任何外部介面)。
2. **取得租約**(一個立即取得寫入鎖的交易):目前沒人持有(沒有租約列、目前那一列是放掉列、或已過期),就新增一列取得列、拿到收據;有人持有就什麼都不寫。
   - **拿不到**:直接回傳第 1 步讀到的狀態,跟「這一步沒有進展」回的一樣;不呼叫蒐證、分析、送件任何一個外部介面,不寫任何一列。呼叫端不用分辨是被擋還是沒進展:兩者都是「過一會兒再推進一次」。
3. **拿到租約之後重讀目前那一列**;重讀到的序號跟第 1 步不同(另一個呼叫端在第 1 步和第 2 步之間做完一步、提交、放掉租約),就放掉租約、回傳重讀到的狀態,這一輪不呼叫任何外部介面。原因:拿第 1 步的舊列去呼叫外部,寫入時一定被序號核對擋掉,錢白花;而且呼叫端傳進來的送件包裝是用它自己在呼叫前讀到的那一列建的(既有 PITFALL:工具呼叫紀錄要綁「呼叫發生當下」讀到的列,不能事後改綁),推進函式內部換成新列去送件,紀錄會記到錯的序號。所以不在同一輪改用新列,交回呼叫端用新列重建協作介面再推進一次(第 1 輪銜接席與可測性席指出)。第 1 輪第 1 版原本寫「用重讀到的列做下一步」,已改掉。租約有效期間沒有別人能提交(帶收據的要是目前那一列、不帶收據的要沒人持有,見下),所以重讀到的列在放掉租約或租約過期之前不會再變。租約過期後,不帶收據的提交可能先寫進一列;這時持有者的租約核對仍過,但序號核對會擋下(見下一小節最後防線)。
4. 照舊做這一步(可能呼叫外部介面)。
5. 這一步結果是「不寫入、留在原狀態」(蒐證失敗、送件忙碌等)→ 放掉租約,回傳原狀態。
6. 有結果 → 帶收據提交(見下一小節);提交與放掉租約在同一個交易。
7. 行程內的例外(提交前鉤子丟例外、協作介面回了合約之外的型別、非法轉換)往外傳之前,先放掉租約(照上面的條件)。放掉本身失敗(資料庫忙碌或其他資料庫層錯誤)時吞掉放掉的錯誤、照舊丟出原本的例外,租約留到到期由別人接手;吞的範圍比照既有「記一筆對外呼叫」那支只吞資料庫層錯誤的做法,程式錯誤不吞(第 1 輪外家席指出放掉失敗會蓋掉原本的例外)。行程真的猝死時放不掉,租約留到到期,別人才接得手——這正是「當機後重做一次」那條限制的來源。
- **不續租**:推進函式一次只做一步,每一步最多是兩次讀 DSP(證據來源有兩個端點)(2026-10-02 更正:Phase 14 規則輪的 C 步最多讀 5 次,守衛照每一步的讀取次數分開算,見 [[Systems/模型用戶端]] 的 RULE_STEP_READS)、一次純計算的決策、或一次送件;一步做完就放掉。所以不需要續租,只要租約長度大於一步最慢的時間(見下)。一步超過租約長度還沒做完,就可能被接手、寫不進去——這是花兩次錢的第二種情況,靠租約長度留足倍數壓低機率,不靠續租。
  - 跟 [[Projects/RTB_Agent_Phase0架構]] 的對照:Phase 0 寫 lease「必須長於 DSP 呼叫逾時上限加安全邊際,並有續期機制,讓延遲回應不會把活著的 worker 變成疑似當機」,那是給執行側一則訊息要跑好幾次 DSP 呼叫與對帳的整段處理用的(執行側增量 1 把續期做在每一筆嘗試寫入上)。分析側一次推進只有一步、步內沒有可以插續租的寫入點,續期的替代是「一步做完就放掉、下一步重新取得」;前半句「長於逾時上限加安全邊際」照做(見〈租約長度與外部呼叫逾時〉)(第 1 輪銜接席指出沒交代)。

### 提交怎麼核對租約

- 提交函式多一個可選的「收據」參數,在既有的寫入交易裡、核對序號之前,先核對租約:
  - **帶收據**:目前那一列必須正是這張收據的取得列(租約序號與擁有者都相符),否則回「沒有寫入」、不寫任何一列。寫入成功時,在同一個交易裡新增放掉列。
  - **不帶收據**(既有的直接呼叫端,多數在測試裡):目前沒人持有才照舊寫;別人持有有效租約時回「沒有寫入」。這樣往後有新的呼叫端忘了帶收據,也蓋不過正在花錢的持有者(防忘記);舊呼叫端在沒人持有時行為不變。
- **核對的是號碼,不是時間**:帶收據的提交只看「目前那一列還是不是我的取得列」,不看到期時間。
  - 原因:租約判斷用的時間只有推進函式手上的現在時間(既有 RULE:決策與證據來源共用它、不自己讀時鐘;工具呼叫紀錄的時間戳是那條 RULE 刻意留的例外,讀系統時鐘,跟租約無關);持有者在步驟開頭拿到的時間,在提交時已經不準,拿它判斷自己過期沒有,判不出來。
  - 後果(跟執行側增量 1 刻意不同):持有者過期、但還沒有人接手時,它仍寫得進去。這沒有害處:沒有第二個人花錢,寫進去的就是唯一那份結果。一旦有人接手(新增了取得列),舊持有者的收據就不是目前那一列,一定寫不進去。
  - 為什麼執行側 [S101] 要擋「過期但沒人接手」、這裡不擋(第 1 輪架構對齊席要求正面對照):執行側有續租,而且續租、確認、嘗試寫入都是同一把收據的條件寫入;不看到期的話,一個卡住很久才醒來的工作者可以靠一次續租把已經過期的租約救活,再接著寫 DSP 相關的嘗試紀錄,等於過期工作者繼續對外寫入。執行側的現在時間是拿到寫入鎖之後才讀的真時鐘,判得出自己過期。分析側兩個前提都不在:沒有續租(一次提交就放掉,救不活),現在時間是步驟開頭傳進來的、判不出過期。放寬的唯一後果是那一次提交寫得進去,而這時沒有第二個人花過錢。
  - 撤回條件:分析側若改成拿到寫入鎖之後讀真時鐘、或加入續租,改回跟 [S101] 一樣核對到期。
- **保留既有的序號核對**當最後防線,順序在租約核對之後、不變。租約管「誰可以花錢」,序號管「接的是不是最新一列」;兩道都過才寫。
- 帶收據的提交遇到租約不符,跟序號不符一樣回「沒有寫入」,推進函式照舊回傳原狀態,不停機、不丟例外(比照執行側「收據對不上是放棄,不是停機」)。

### 保證什麼、不保證什麼

- 保證:同一個任務在同一時間只有一個**持有有效租約**的呼叫端會呼叫外部蒐證、分析、送件;拿不到租約的一律不呼叫。注意「持有有效租約」:舊持有者的租約過期被接手後,它手上那次呼叫可能還沒回來,這時兩邊的外部呼叫在時間上重疊([S152] 就是這個形狀),只是舊持有者寫不進去。所以不能說「同時進行的重複一定只花一次」,只能說「同一時間只有一個有效持有者」(第 1 輪外家席指出)。
- 保證:租約過期被接手後,舊持有者醒來寫不進任何一列。
- **不保證**:持有者花完錢、提交前行程猝死,租約到期後接手者會再呼叫一次(至少一次的代價)。一步做太久超過租約、被接手,也會花兩次。這兩種用測試固定下來,轉正後的 F3 合約措辭要照實寫出來(見下)。
- 不保證分析結果相同:重做的那次看到的是新的證據,可能做出不同的決策;這由執行側的執行閘兜底(增量 2 的 [S125])。

### 怎麼測

- 真並行([S150]):照既有「二十條執行緒同時推進」那支測試的做法,每條執行緒自己的資料庫連線、同步屏障後一起出發;決策介面在被呼叫時等一個事件,等另一條執行緒回報之後才放行,確保「持有者正在分析時,另一邊真的試過」。數的是決策被呼叫幾次與歷史表多幾列,不數回傳值(既有 PITFALL:讀得晚的執行緒看到新列、原地回傳,會被誤數成贏家)。
- 過期接手([S152]):持有者 A 用時間 T 取得租約、卡在分析;B 用 T 加 61 秒接手、也卡在分析;先放 A,A 的提交要被擋(這時序號仍相符,只有租約核對擋得住,拿掉租約核對這支就會紅);再放 B,B 寫入。決策共被呼叫兩次,照實斷言。
- 取得前被搶先([S154]):照既有「讓提交函式直接回沒寫入」那支測試換掉任務模組方法的做法,把取得租約的方法包一層:第一次被呼叫時先用另一個呼叫端把同一個任務推進一步並提交,再交給真的取得。斷言三個協作介面都沒被呼叫、回傳的是新列的狀態、租約已放掉;重讀到終點也用同一招(另一個呼叫端把任務推到終點)。不需要為測試改正式程式碼(第 1 輪可測性席指出第 1 版沒交代測法)。
- 遲來的放掉([S159]):A 取得、卡在蒐證;B 用過期後的時間接手、卡在分析;放 A,讓 A 的蒐證失敗(沒有進展)或丟例外;斷言沒有新增放掉列、目前那一列仍是 B 的取得列、第三個呼叫端 C 拿不到租約;再放 B,B 寫得進去。拿掉放掉的條件這支就紅。
- 放掉失敗不蓋例外([S160]):決策丟一個自訂例外,同時把放掉租約的方法換成丟資料庫忙碌;斷言往外傳的是自訂例外。
- 行程猝死([S153]):照增量 2 的子行程做法,子行程用內嵌腳本開同一個資料庫檔、呼叫推進函式,決策介面在記下一筆呼叫之後 `os._exit(9)`;不能用丟例外代替,因為行程內例外會走第 7 步放掉租約。斷言子行程退出碼是 9、呼叫紀錄一筆;測試行程用 T 加 30 秒推進不呼叫、用 T 加 61 秒推進呼叫第二次並寫入。
