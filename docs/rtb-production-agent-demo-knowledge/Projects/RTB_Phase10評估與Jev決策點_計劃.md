# RTB_Phase10評估與Jev決策點_計劃

PRIOR-ART: 機器學習評估的常規做法——固定且版本化的評估集、事先寫好的評分標準(rubric)、依切片報告精確率與召回率而不只報總平均、每片最少樣本數、評估集與訓練或規則作者隔離以免外洩;模型路由的「只在驗證過的範圍啟用,範圍外退回可靠路徑」。不引入評估套件(零依賴家規)。
RETIRE-IF: 接上真實流量與人工標註之後,這份以合成情境與代理標註做的評估集要換成以正式環境紀錄抽樣、人工標註的版本;或者「值不值得加預算」這個判斷點被移除(例如改成由人工核可)。

## 這份計劃在解決什麼

交接文件 Phase 10:只在有證據的窄決策點評估 Jev。完成條件五項:評估資料與正式提示/測試的外洩風險有記錄;依重要切片報精確率/召回率,不只報總分;跟 LLM/程式基準比品質、成本、延遲;範圍外或信心不足會退回;沒達門檻時明確不採用 Jev,不調低標準。

這個階段要防的事故:因為某個便宜的模型「總體準確率夠高、又快又便宜」就換上去,但它在某一類輸入錯得離譜,總平均把問題蓋掉;而錯的那一類正好是最危險的。

## 使用者裁定(2026-09-24,使用者本人,清醒時)

- Phase 0 已裁定:不導入 Jev、不做假的 Jev 整合;沒有正式環境紀錄與人工標註,這個階段的產出是「評估機制 + 有根據的不採用 + 缺哪些證據」。
- 情境題:候選在總體達標、但某一片不達標時,「只在達標的切片用;看不出屬於哪片的輸入一律退回現行做法」。
- 評估對象:不評整支決策函式(新鮮度、配速門檻、金額都是交接文件 4.1 規定必須由程式處理的,評了只會得到「程式全對」),只評「配速偏低時,這個廣告值不值得加預算」這一個判斷。
- 標準答案:配速偏低、有曝光有點擊、但一小時內零轉換零營收 → 「證據不足、不判」,這類一律不加。所以標準答案是三類:值得加、不值得加、證據不足。

## 現況(2026-09-24 前掃,main e8b26f6)

- 分析端決策函式(src/rtb/analyzer/policy.py 的 decide)只有三種結果:任一筆證據過期 → 退回重新蒐證;配速算不出或不偏低、或曝光點擊不是正數 → 不做;新鮮、配速低於 0.5、曝光點擊都大於零 → 提案調高一成。實質上只有一個是非判斷(提不提案),動作種類與金額都是算術。
- 「值不值得加」現在用一行粗略代理:曝光與點擊都大於零。它不看轉換與營收,也不看廣告狀態(暫停中的廣告最近一小時有殘量也照樣提案,靠執行端護欄擋)。
- 「不做」不帶原因;決策函式目前沒有正式行程呼叫,只在測試與端到端測試裡接線。
- 決策當下分析端有的事實:預算、狀態(啟用/暫停)、版本、最近 1 小時的曝光、點擊、轉換、花費、營收、證據年齡、有無不可信廣告文字。沒有:廣告上線天數、租戶、動作種類(只有調預算一種)。
- 一次呼叫純程式、零模型成本、零網路;前掃在本機量過一次:提案那條中位約 18 微秒、不做那條約 7 微秒(單次量測,只當量級參考)。

## 設計

### 增量 1:把「值不值得加」抽成可插入的判斷點,行為不變

- 在決策函式裡,把「曝光與點擊都大於零」這行抽成一支獨立的判斷(輸入:這次決策用的可信現況與指標;輸出:值得加 / 不值得加 / 證據不足,三類)。現行程式規則照舊只產出「值得加」或「不值得加」(維持原本的行為:曝光點擊都大於零就值得加),決策函式對外的行為一字不變。
- 路由閘(程式,不是模型):先由程式依事實算出這筆輸入屬於哪個切片;只有「有候選、而且這個切片在已驗證清單上」才交給候選判斷,其餘一律走現行程式規則。切片算不出來(缺值、配速算不出、欄位型別不對)也走現行規則。正式行程的已驗證清單是空的、也沒有候選,所以正式行程永遠走現行規則。
- 候選判斷的介面:一支函式,輸入同上、輸出三類之一或「不知道」;丟例外、回傳型別不對、回「不知道」一律退回現行規則。候選不准拿到不可信的廣告文字(信任邊界,沿用 [S210])。
- 決策函式另外多回一個「不做的原因」給評估用(不改決策結果本身),讓評估可以依原因切片。

### 增量 2:評估集、評分、切片報告與採用決定

- 切片鍵(全部是決策當下就有的事實):配速區間(0 到 0.25、0.25 到 0.5)× 有無曝光點擊 × 有無轉換或營收 × 廣告狀態(啟用/暫停)× 預算量級(小額會觸發保底 +1、一般、逼近整數上限)。每一片最少樣本數 30(暫用、待使用者覆核),不足的片不算驗證過。
- 情境生成:一支生成器依切片分層抽樣造情境,每片至少 30 筆;生成器不讀決策函式的程式與測試,只依切片定義造數字;種子固定。
- 標準答案:派一個乾淨的代理只讀交接文件的業務描述與本計劃的評分標準(下一節),不給程式與測試,替每個情境標三類之一並寫一句理由;標準答案與生成的情境一起版本化入庫,用雜湊釘住。
- 評分標準(使用者 2026-09-24 裁定「證據不足」那條,其餘照業務常識、待使用者覆核):
  - 值得加:廣告啟用中、有曝光有點擊、而且有轉換或營收。
  - 不值得加:廣告暫停中;或沒有曝光、沒有點擊。
  - 證據不足:啟用中、有曝光有點擊、但一小時內零轉換零營收。
  - 「值得加」以外的兩類都是「不提案」。
- 指標:主指標是「提案加預算」的精確率(說要加的時候真的該加的比例:判錯就是多花錢);次指標是「值得加」的召回率(該加的有加到多少)。每片各自算、各自比門檻;另報三類的混淆表與總平均(總平均只當參考,不當採用依據)。
- 門檻(暫用、待使用者覆核):某片的精確率 ≥ 0.95 且召回率 ≥ 0.80,且樣本數 ≥ 30,這片才算「驗證過」。
- 比較表:品質(依片)、成本(每次呼叫)、延遲(中位、p95)。現行程式規則實測;LLM 與 Jev 沒有候選可量,照實寫「沒量、原因:未導入」,不編數字、不做假呼叫。
- 採用決定:寫成一份決定紀錄。這次的結論是明確不採用 Jev,並列出缺的證據:正式環境的決策紀錄抽樣、人工標註、候選模型在每一片的實測、上線後依片監測的機制。
- 外洩紀錄:評估集是誰寫的、看過什麼;規則作者不得看評估集的逐筆答案後回頭調規則(看過就換一批);評估集雜湊由測試釘住,改了測試就紅。
- 現行規則的評估結果照實報:預期它在「證據不足」與「暫停中」這幾片的精確率很低——那是規則的缺陷,記進缺陷清單,不改標準答案遷就規則,也不在這個階段修規則(修規則會改變 Phase 2 起的既有合約,另開計劃)。
