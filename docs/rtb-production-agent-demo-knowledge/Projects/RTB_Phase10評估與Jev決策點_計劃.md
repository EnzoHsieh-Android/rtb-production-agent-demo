# RTB_Phase10評估與Jev決策點_計劃

PRIOR-ART: 機器學習評估的常規做法——固定且版本化的評估集、事先寫好的評分標準(rubric)、依切片報告精確率與召回率而不只報總平均、每片最少樣本數、評估集與訓練或規則作者隔離以免外洩;模型路由的「只在驗證過的範圍啟用,範圍外退回可靠路徑」。不引入評估套件(零依賴家規)。
RETIRE-IF: 接上真實流量與人工標註之後,這份以合成情境與程式算的標準答案做的評估集要換成以正式環境紀錄抽樣、人工標註的版本;或者「值不值得加預算」這個判斷點被移除(例如改成由人工核可)。

## 這份計劃在解決什麼

交接文件 Phase 10:只在有證據的窄決策點評估 Jev。完成條件五項:評估資料與正式提示/測試的外洩風險有記錄;依重要切片報精確率/召回率,不只報總分;跟 LLM/程式基準比品質、成本、延遲;範圍外或信心不足會退回;沒達門檻時明確不採用 Jev,不調低標準。

這個階段要防的事故:因為某個便宜的模型「總體準確率夠高、又快又便宜」就換上去,但它在某一類輸入錯得離譜,總平均把問題蓋掉;而錯的那一類正好是最危險的。

## 使用者裁定(2026-09-24,使用者本人,清醒時)

- Phase 0 已裁定:不導入 Jev、不做假的 Jev 整合;沒有正式環境紀錄與人工標註,這個階段的產出是「評估機制 + 有根據的不採用 + 缺哪些證據」。
- 情境題:候選在總體達標、但某一片不達標時,「只在達標的切片用;看不出屬於哪片的輸入一律退回現行做法」。
- 評估對象:不評整支決策函式(新鮮度、配速門檻、金額都是交接文件 4.1 規定必須由程式處理的,評了只會得到「程式全對」),只評「配速偏低時,這個廣告值不值得加預算」這一個判斷。
- 標準答案:配速偏低、有曝光有點擊、但一小時內零轉換零營收 → 「證據不足、不判」,這類一律不加。所以標準答案是三類:值得加、不值得加、證據不足。
- 評分表加「資料自不自洽」(2026-09-24,使用者本人,評分表原意對照後):程式判得出的資料異常一律判「證據不足」;數字合不合理(點擊率九成、花費過低這類)不判,太主觀。評分表改成由上而下第一個成立的:①暫停中 → 不值得加;②啟用中、資料異常 → 證據不足,異常指任一計數或金額是負數或缺值、點擊多於曝光、轉換多於點擊;③啟用中、曝光或點擊是零 → 不值得加;④啟用中、曝光點擊都是正數、轉換或營收有正數 → 值得加;⑤啟用中、曝光點擊都是正數、轉換營收都是零 → 證據不足。原本「缺值與負數比照零判證據不足」「有曝光沒點擊判不值得加」兩條暫用值改照這條。
- 評估對象跟 Phase 0 路由表(2026-09-24,使用者本人,設計審第 1 輪後):保留評估對象,照實寫結論。不採用的兩個理由:①照評分表這個判斷可以由程式精確算出,本來就該是程式;現行規則在某些格判錯,這件事記成現行規則的程式缺陷(不是需要換判斷者的理由);②缺正式環境紀錄、人工標註與候選實測。Phase 0 路由表加註「這次不回答『證據夠不夠』『下一步查什麼』『繼續或停止』三個 Jev 候選點」。

## 現況(2026-09-24 前掃,main e8b26f6)

- 分析端決策函式(src/rtb/analyzer/policy.py 的 decide)只有三種結果:任一筆證據過期 → 退回重新蒐證;配速算不出或不偏低、或曝光點擊不是正數 → 不做;新鮮、配速低於 0.5、曝光點擊都大於零 → 提案調高一成。實質上只有一個是非判斷(提不提案),動作種類與金額都是算術。
- 「值不值得加」現在用一行粗略代理:曝光與點擊都大於零。它不看轉換與營收,也不看廣告狀態(暫停中的廣告最近一小時有殘量也照樣提案,靠執行端護欄擋)。
- 「不做」不帶原因;決策函式目前沒有正式行程呼叫,只在測試與端到端測試裡接線。
- 決策當下分析端有的事實:預算、狀態(啟用/暫停)、版本、最近 1 小時的曝光、點擊、轉換、花費、營收、證據年齡、有無不可信廣告文字。沒有:廣告上線天數(整個系統沒有這個欄位)、租戶(DSP 表有,但分析端用戶端的白名單不收)、動作種類(DSP 也支援暫停,但決策函式只會提案調預算,切不出來)。
- 一次呼叫純程式、零模型成本、零網路;前掃在本機量過一次:提案那條中位約 18 微秒、不做那條約 7 微秒(單次量測,只當量級參考)。

## 評估對象跟 Phase 0 路由表的關係

- 照〈使用者裁定〉「評估對象跟 Phase 0 路由表」那條:[[Projects/RTB_Agent_Phase0架構]] 的路由表把「要不要提案調整」那列的未來候選寫成 LLM,標 Jev 的是另外三列(都還沒實作)。這份計劃只證明評估機制做得出來、在這個判斷點上怎麼跑,不回答那三列適不適合 Jev;採用決定與驗收紀錄都要寫這句限制與兩個不採用理由。
- 實作時用決策指令記一筆決策,並在 Phase 0 路由表那列加註指向這份計劃。

## 設計

### 增量 1:把「值不值得加」抽成可插入的判斷點,行為不變

- 狀態(2026-09-24):4 格版實作完成、代碼審兩輪修完(分支 phase10-inc1)。**評分表改成 5 格(使用者裁定加資料自洽)後需重新實作與代碼審**:評分格型別加「資料異常」,歸格函式依序判暫停 → 資料異常(含花費、點擊多於曝光、轉換多於點擊)→ 沒投放 → 有價值/沒價值;[S711] 的測試窮舉加花費軸、造兩種「多於」、斷言 5 格都到得了。[S700] 正式路徑行為不變的承諾照舊:路由在沒有候選時不看格,決策函式對外結果不受格的定義影響。凍結舊規則與 625 筆存下的結果在第一次改決策函式之前先跑綠。

- 型別放領域層(比照證據種類、信任標記、動作種類這類分類型別;領域層的匯入規則禁止模型用戶端,多一層把關):
  - 判斷點輸入:不可變資料型別,七個欄位——狀態是封閉列舉(啟用、暫停);其餘六欄逐欄跟分析端 DSP 用戶端白名單用同一支共用檢查:預算是 0 到資料庫整數上限的整數;曝光、點擊、轉換是缺值或絕對值不超過上限的整數;花費、營收是缺值或任意有限數;全部拒布林與錯型別。結構上沒有放廣告文字或整批證據的位置,候選拿不到不可信文字是型別保證。
  - 輸出:四值列舉——值得加、不值得加、證據不足、不知道。
- 「正數」:建構驗證通過、而且大於零。缺值、零、負數都不是正數。
- 「資料異常」(照使用者裁定的評分表):曝光、點擊、轉換、營收、花費任一個是負數或缺值,或點擊多於曝光,或轉換多於點擊。預算經白名單一定是 0 以上的整數,不在這一條。看瀏覽後轉換(轉換多於點擊)也算異常,照使用者裁定。花費缺值或負數在正式路徑會先被配速計算攔下(判不做、原因是配速算不出),到不了判斷點,所以正式環境隱藏集裡這格的分母只由另外四種異常構成;花費異常只由合成集與直連判斷點的單元測試驗。
- 候選介面比照決策函式的介面用型別協定定義,多收一個截止時間。逾時用專案既有的合作式做法:候選的實作必須經共用 HTTP 用戶端呼叫、把截止時間換成它的逾時參數(跟現有 DSP 呼叫同一種);不另開執行緒或子行程去強制中斷(專案沒有這種做法,而且執行緒逾時只是呼叫端不等、不會停下候選)。所以不收截止時間、或不經共用 HTTP 用戶端的候選一律不得採用。包裝層:候選逾時、丟例外、回傳不是那個列舉、回「不知道」,一律退回現行規則;回「證據不足」照「不做」處理。逾時值由使用者在接上第一個候選時裁定,沒定之前不得採用任何候選。
- 現行程式規則照舊:曝光與點擊都是正數就回「值得加」,否則「不值得加」;不產出「證據不足」。決策函式把「值得加」對應成提案、其餘對應成不做,所以現行規則下對外行為不變。
- 路由函式(程式):輸入是一筆已建構的判斷點輸入、候選、「這次允許呼叫候選的格」。先把輸入歸到評分格(評分表對每一筆可建構的輸入恰好給一格,見增量 2);只有「有候選、而且這格在允許清單上」才經包裝交給候選,其餘走現行規則;回傳「最後有效的答案」與「走了哪條路」(現行規則、候選、候選退回及原因)。允許清單有兩種來源、是兩個不同型別:正式路徑傳「已驗證清單」,只有採用函式產生得出來;評估入口傳「待測格清單」,只在那次評估裡用,不會被輸出或存成已驗證清單。
- 「歸不了格」只指判斷點輸入建構失敗(值驗證不過),發生在路由之前,走現行規則。建構失敗丟判斷點型別自己的專用例外(資料錯誤類的子類),決策函式只接這一種;不用廣義的例外攔截,其他例外照舊往外丟(流程層照舊轉 FAILED)。正式路徑上 DSP 用戶端白名單已經擋掉同樣的值,所以這條與「沒有候選」「清單上沒有」「配速算不出」一樣,只能靠直接呼叫判斷點與路由函式的單元測試證明,不宣稱決策函式的端到端測試涵蓋到。
- 決策函式簽名不變(不改流程層的決策協定與既有呼叫端):內部以「沒有候選、空清單」呼叫路由函式。所以任何決策函式的呼叫者都走現行規則。
- 「不做的原因」不放進決策結果:另給一支評估用的診斷函式,輸入跟決策函式相同,回「決策結果 + 不做的原因」;決策函式對某筆輸入丟例外時,診斷函式丟同一種例外(不吞、不另立原因)。原因是封閉列舉:證據過期、缺可信現況或指標、配速算不出、配速不偏低、判斷點回不值得加、判斷點回證據不足。
- 行為不變的比對基準(不靠提交先後,CI 只取最新一個提交、看不到歷史;也不動態執行字串化的原始碼,專案把那類寫法當危險模式禁止):把改動前的決策規則檔原樣複製成測試目錄裡一支普通的 Python 模組(凍結的舊規則,照常匯入),測試寫死它的雜湊(等於 main e8b26f6 上決策規則檔的雜湊,審查時對一次);另存一批輸入與舊規則對它們的決策結果(樣本模組,比照既有樣本模組)。測試三步,各自分開報:①凍結舊規則檔的雜湊等於寫死的值;②凍結舊規則對那批輸入的結果等於存下的結果——這一步紅代表它匯入的六個相依模組(流程層決策型別、任務列、領域層小檢查、證據、指標、提案)行為變了,不是抽判斷點抽壞;③新決策函式對那批輸入的結果等於存下的結果(決策型別的相等比較,提案逐欄相同)——這一步紅才是抽壞了。增量 1 不改那六個相依模組既有函式的行為。輸入是既有決策測試的全部輸入,加上依評分格與配速、預算邊界分層造的輸入。

### 增量 2:評估集、評分、報告與採用決定

- 狀態(2026-09-24):5 格版實作完成、待代碼審(分支 phase10-inc2,已合入增量 1 到 fa4559c)。決定紀錄 governance/eval/phase10-worth-adoption.md(第三版評估集 300 筆):不採用;現行規則暫停格誤提案 42/60、資料異常格類別 0/60 對、沒價值格 60/60 判成值得加,沒投放與有價值兩格全對。原意對照第 3 批(governance/eval/rubric-intent-check.md):沒價值格代理 3/3 判「不值得加」,跟使用者裁定的「證據不足」不一致,使用者本人確認維持原裁定(一小時窗太短、轉換常有延遲);有價值格 1/3、資料異常格 2/3 一致,其餘不一致照「數字合不合理不判」照實列;評分表沒改。
- 實作解讀:①比較表的「品質」欄用現行規則在合成集上的整體類別正確率(逐格見報告),延遲量的是判斷點經路由的一次呼叫,不含證據讀取與整支決策函式;②最少樣本不另寫檢查,由 Wilson 下界本身擋住(全對時少一筆就過不了);③非「值得加」的三格只比類別正確率下界,因為每次誤提案也是一次類別錯誤,誤提案率照樣逐格報;④合成集 5 格各 60 筆(20 組 × 3 變體),不到 73 不影響,因為合成集本來就不能驗證;⑤決定紀錄與原意對照放 governance/eval,由 `python -m rtb.eval.record` 產生,延遲數字每次跑會變,紀錄裡的是 2026-09-24 那一次。

- 放哪:新開 `src/rtb/eval/` 套件。匯入方向:評估套件可以匯入分析端的判斷點與路由函式、領域層的型別;分析端、執行端、DSP、領域層、維運套件都不准匯入評估套件。比照維運套件的雙層防線:這五個目錄各自的匯入規則檔加一條禁令,再加一支邊界測試先驗這五份禁令真的擋得住、再掃原始碼補漏。規則作者的程式在結構上讀不到評估集。
- 合成評估集是評估套件裡的一個 Python 模組(情境與標準答案寫成常數),比照專案既有的樣本模組做法,不用資料檔、不進任何資料庫(它只是合約案例、不隱藏;正式環境隱藏集另見下文,不進程式庫);生成器是同套件裡另一支模組,產出這個常數模組。生成器只依評分格定義與欄位型別造數字:正常的格照漏斗順序造(點擊不多於曝光、轉換不多於點擊,沒有負數與缺值),資料異常那格專門造負數、缺值、點擊多於曝光、轉換多於點擊各種異常;評分表改了就照規則換批,換批用決策指令記一筆。新開一篇 Systems 家「評估與Jev決策點」管這個套件,程式落地前先開。
- 評分表(全部是使用者本人裁定;由上而下第一個成立的):
  - 暫停中 → 不值得加(不看其他欄位,資料異常也一樣)。
  - 啟用中、資料異常 → 證據不足。
  - 啟用中、曝光或點擊是零 → 不值得加。
  - 啟用中、曝光點擊都是正數、轉換或營收至少一個是正數 → 值得加。
  - 啟用中、曝光點擊都是正數、轉換與營收都是零 → 證據不足。
  - 邊界例:曝光正、點擊零、轉換零 → 沒投放、不值得加;曝光正、點擊零、轉換正 → 轉換多於點擊、資料異常、證據不足。
  - 對每一筆可建構的判斷點輸入恰好給一類,由測試窮舉(狀態兩值 × 曝光、點擊、轉換、營收、花費各取正數、零、負數、缺值,正數再分大小以涵蓋點擊多於曝光、轉換多於點擊)驗證互斥與完整;不可建構的值(布林、NaN、無限大、超界)由建構驗證的測試另外守。
- 標準答案由程式照評分表算,不派代理標註。另派一個乾淨的代理(只讀交接文件的業務描述,不看評分表、程式與測試)對一小批情境寫它認為的答案,跟評分表不一致的格列給使用者,檢查評分表是不是使用者原意,不當標準答案。評分表任何一次改動都要重跑一批原意對照才定案;這次 5 格版在增量 2 重新實作時重跑。
- 評分格:暫停;資料異常(啟用中);沒投放(啟用中、曝光或點擊是零);有價值;沒價值(轉換營收都是零),共 5 格,跟評分表的五條一一對應。配速與預算不影響答案,不當切片鍵;改成「無關欄位擾動檢查」:同一筆輸入只改配速(偏低範圍內)或預算,被評對象的最後有效答案應不變。
- 逐筆評分走跟正式路徑相同的組合:判斷點輸入經路由函式(含包裝、逾時與退回),依「最後有效的答案」計分,不是依候選原始回答計分。另報每格的「不知道」、非法回傳、例外、逾時與退回次數。
- 指標(每格事先指定,分母是那一格的樣本數,不會是零):「值得加」格報召回率;其他四格同時報誤提案率(不該加卻提案的比例,判錯就是多花錢)與類別正確率(最後有效答案等於標準答案的比例;標準答案是三類,答「證據不足」的格被答成「不值得加」也算錯)。退回現行規則的筆以現行規則的答案計類別。每格都報分子、分母與錯誤的子型(例如「暫停中卻提案」「證據不足卻提案」「證據不足答成不值得加」);另報三類混淆表與總平均(只當參考)。
- 現行規則照同樣方式逐筆跑、逐格報分子分母與錯誤子型(同一格內它的答案會隨曝光點擊變,例如暫停格裡有投放的會被提案、沒投放的不會),並列出造成錯誤的規則差異(不看廣告狀態、不看轉換營收、不看資料是否自洽)。
- 合成評估集的定位:它是有限的合約案例(等價類、邊界值、無關欄位擾動),不是從某個母體獨立抽樣,**不套統計信賴宣稱**,報告寫「合成集通過/不通過」與精確分子分母。合成集不能產生已驗證清單。
- 已驗證清單只能來自之後的正式環境抽樣集:從正式決策紀錄依格抽樣、人工標註、跟候選開發隔離的隱藏集。隱藏集不進程式庫:由獨立、有存取控制的評估執行器在評估時注入;程式庫只存它的版本、雜湊、抽樣與標註的出處說明和彙總結果,不存逐筆情境與答案。候選版本必須早於那一批隱藏集被揭露;揭露過的一批不得再拿來驗證新候選。那時才用 95% Wilson 信賴下界比門檻(暫用、待使用者覆核):「值得加」格召回率下界 ≥ 0.80,最少 16 筆(全對時下界過 0.80 所需);其他四格「1 − 誤提案率」與類別正確率的下界都 ≥ 0.95,最少 73 筆(全對時下界過 0.95 所需;30 筆全對下界只有約 0.886)。
- 採用決定逐格下,一格要同時滿足才進已驗證清單:①正式環境抽樣集上品質下界過門檻;②成本、延遲(中位與 p95)、格式失敗率、例外率、逾時率、退回率都有量測、而且各自不超過事先定好的門檻(門檻由使用者在接上第一個候選時裁定,沒定之前不得採用);比較表裡任何「沒量」的欄位都擋採用。這次沒有候選、也沒有正式環境抽樣集,所以已驗證清單是空的、結論是不採用(兩個理由見〈使用者裁定〉),並列出缺的證據:正式環境的決策紀錄抽樣、人工標註、候選模型在每一格的實測(品質、成本、延遲、失敗率)、上線後逐格監測的機制。
- 報告與採用決定都是純函式的輸出:輸入是結構化的逐筆評分結果與比較表,輸出是結構化的逐格報告與逐格採用決定;人讀的決定紀錄由這份輸出產生,並記下它依據的評估集雜湊。
- 比較表是結構化資料:每一格「品質、每次呼叫成本、延遲中位與 p95」各是一個儲存格,帶「有沒有量、數值、沒量的原因」三欄;現行規則實測,LLM 與 Jev 寫「沒量、原因:未導入」。交接文件完成條件「跟 LLM/程式基準比較」在這個階段的完成判準就是這樣,實作時用決策指令記一筆,連到 Phase 0「不導入 Jev」的裁定。
- 外洩紀錄:評估集是誰寫的、看過什麼;規則作者看過逐筆答案後回頭調規則,就要換一批。評估集雜湊由測試釘住;換批要同時用決策指令記一筆理由與時間,測試只驗雜湊。
- 現行規則的評估結果照實報:預期它在暫停、資料異常、沒價值三格有錯——那是規則缺陷,記進缺陷清單,不改評分表遷就規則,也不在這個階段修規則(修規則會改變 Phase 2 起的既有合約,另開計劃)。
