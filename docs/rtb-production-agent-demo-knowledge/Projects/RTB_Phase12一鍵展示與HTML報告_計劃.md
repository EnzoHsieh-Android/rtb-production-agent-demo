# RTB_Phase12一鍵展示與HTML報告_計劃

PRIOR-ART: 交接文件 Phase 12(F1–F7 故障注入展示、狀態時間線、DSP 真實狀態、追蹤、稽核、驗證器結果);本專案既有的只綁本機 HTTP 伺服器外殼(共用行程基礎,標準函式庫的 ThreadingHTTPServer);標準函式庫 html.escape 做純文字插入;內容安全政策(CSP)用回應標頭設;進度更新沿用最老的做法:頁面用 meta refresh 定時整頁重讀,不用前端框架(零依賴家規);故障情境的組法照 F1–F7 端到端測試既有做法(伺服器端排故障、子行程猝死、時鐘偏移)。否決過的做法:讓展示直接去跑 F1–F7 的 pytest 並撈它們的暫存資料庫(測試的資料庫在 pytest 的暫存目錄、跑完即刪,要改動每支測試的夾具,而且把展示綁死在測試實作細節上);F1–F7 的通過或失敗改由驗證器跑證據測試提供(驗證器本來就會跑它們)。
RETIRE-IF: 使用者決定不再需要本機展示(或改成有正式部署的儀表板時),撤掉展示伺服器、驅動程式與展示啟動器,分析端驅動命令列照樣保留(它是正式入口);或連續三次展示都有情境因展示本身(不是被測系統)失敗,就回頭重審驅動程式的做法。

## 這份計劃在解決什麼

交接文件 Phase 12:用事故證據展示系統的價值。完成條件六項:F1–F7 全部有確定性的通過或失敗斷言;展示畫面顯示狀態時間線、DSP 真實狀態、追蹤、稽核與驗證器結果;有無 Skill Contract 的前後比較使用相同任務、環境、評分表與測試並記錄差異與限制;不只展示順利流程或模型解釋,而是展示擋下、恢復與對帳;README 給可重現步驟、預期輸出與已知限制;最終證據清單全部通過,沒證明的項目標成擋下或已知缺口。

使用者本人要求把這份展示做成 HTML:在頁面上按一下觸發整套,即時看到每個任務走到哪個階段、系統怎麼處置、結果與報告。需求原文見 [[Issues/Phase12需要可看任務階段與處置的HTML報告]]。

這個階段要防的事故:
- 展示畫面變成新的攻擊面:模型文字或廣告名稱裡的腳本、連結、雙向控制字元在頁面上被當成指令或誤導核可者。
- 展示本身的故障被當成系統故障(或反過來,系統失敗被展示吞掉):看到綠燈但其實情境沒跑完。
- 展示啟動器把「只給測試用的故障手段」帶進正式程式。
- 展示行程拿到使用者環境裡的秘密(子行程繼承整份環境)。

## 使用者裁定(2026-09-24,使用者本人;只抄需求 Issue 與 Phase 11B 計劃已記的)

- 要一份 HTML,能明確看到每個任務走到哪個階段(狀態時間線)、系統怎麼處置(擋下、待核可、對帳、重放、退回等)、最後結果與報告。交接文件第 19 節把「漂亮 dashboard 或複雜前端」列為非目標,使用者已決定要;照第 19 節,本計劃寫明最小做法與額外成本(見〈設計〉與〈實務隱患〉)。
- 一鍵展示做在 HTML 上:頁面上按按鈕觸發整套(起模擬 DSP、收件口、執行迴圈、分析端驅動、注入 F1–F7),頁面即時看到各任務的階段、處置與結果;不是另外下指令。
- 不做長駐上線部署。
- 模型相關(Phase 11B 使用者裁定):供應商 Anthropic Claude、預設模型 Sonnet 5;花費上限每次展示 1 美元、每月 20 美元,到上限顯示「已達上限」不默默繼續;沒開即時模式時用錄製回應並清楚標示「錄製回應,不是即時呼叫」;模型後端走本機 Claude Code 非互動模式;接入點 2 的說明給人工核可的人看,標明「模型產生、僅供參考」,程式算的數字放在它前面。

## 現況(2026-09-24 前掃,phase11-design 5963b6b)

- 命令列入口共九支:模擬 DSP、評估紀錄、核可、收件口、重放、執行迴圈、指標、服務水準、追蹤。**分析端沒有正式啟動程式**:流程推進函式只在測試裡由測試組裝呼叫(分析行程流程筆記有「呼叫次數 × 逾時 × 2 < 租約」的 REVISIT,至今沒有機械守衛)。
- **沒有展示驅動程式**。F1–F7 各自只存在於端到端測試,而且都靠只在測試裡的手段:
  - F1(提交前後逾時):DSP 伺服器那一側由測試排定故障(執行端的共用用戶端送不出故障標頭);
  - F2、F3(猝死、重複投遞):子行程跑內嵌腳本,把執行迴圈類別上的方法換成「印出死點、os._exit(9)」;重啟時把時鐘往後撥 5 分鐘;
  - F4(舊版本):另一個寫入者在兩個時點搶先改廣告;
  - F5(提示注入):廣告名稱換成對抗性素材;
  - F6(死信重放):執行端時鐘往後推 16 分鐘、讀不到 DSP 用連不上的位址;
  - F7(總曝險):行程內假 DSP、3000 個廣告、8 個工作者,本機約 30 秒(CI 偶爾超過 60 秒,見 [[Issues/F7端到端在CI上偶爾超過60秒]])。
- 共用行程基礎的伺服器外殼只綁回送位址、有主機標頭檢查、連線數上限、請求期限;處理器只回 JSON,沒有回 HTML 的寫法;故障注入要啟動時開旗標才存在。
- 唯讀出口已有:追蹤檢視(三個來源組時間線,唯讀開法)、指標、服務水準、稽核查詢(可觀測查詢)、DSP 操作歷史;Phase 11 的驗證器(輸出印驗證器與清單雜湊、提交編號、通過或擋下原因)。
- Phase 11B 計劃(第 6 版,尚未實作):模型入口三支命令列(模型說明命令列在分析端、假說命令列在維運、評估紀錄);即時模式要「開啟即時呼叫環境變數、命令列帶展示編號、找得到 claude」三者齊備,否則走錄製;展示編號由一鍵展示每按一次產生一個、傳給所有模型入口,共用 1 美元;模型說明命令列在送件之後由一鍵展示呼叫。**Phase 12 依賴 Phase 11B 先實作完**。
- 需求 Issue 寫「啟動非模型行程一律用模型用戶端的『不含模型金鑰的子行程環境』函式」;但 Phase 11B 第 5 版起模型後端改走 Claude Code、沒有 API 金鑰,那支刪金鑰函式不做了。所以本計劃自己定一份子行程環境白名單(見〈設計〉),需求的意圖(展示行程拿不到使用者環境裡的秘密)照做。
- 交接文件 Phase 12 完成條件的「有無 Skill Contract 的前後比較」與「README」,需求 Issue 沒提;本計劃列進範圍,做法待使用者裁定。

## 設計

### 分工(新開三支、動一支)

- src/rtb/analyzer/runner.py(新,正式入口):分析端驅動命令列。反覆領取待推進的任務、用正式的 DSP 用戶端與收件口用戶端呼叫流程推進函式,直到沒有可推進的任務或收到停止訊號。跟測試用同一支流程推進函式、同一套租約;它是正式程式,不帶任何故障手段。
- src/rtb/demo/launch.py(新,只給展示):展示啟動器。用子行程啟動各角色(模擬 DSP、收件口、執行迴圈、分析端驅動),在正式入口外面包上展示需要的手段:DSP 伺服器端的故障排程、執行迴圈的猝死點、時鐘偏移。這些手段照 F1–F7 端到端測試的組法,只存在展示套件裡;正式程式與其他套件都不准匯入展示套件。
- src/rtb/demo/driver.py(新):驅動程式。依序跑 F1 到 F7,每個情境:建暫存目錄與資料庫、產生這次展示的金鑰、用展示啟動器起行程、造資料、排故障、等結果、用唯讀出口收集時間線與稽核、寫進度事件。
- src/rtb/demo/server.py 與 src/rtb/demo/page.py(新):展示伺服器與頁面產生。伺服器沿用共用行程基礎的伺服器外殼(只綁回送位址、主機標頭檢查),另寫回 HTML 的處理器;頁面用標準函式庫組字串,所有動態文字經同一支逸出函式。
- 共用行程基礎(動):伺服器外殼的處理器基底目前只回 JSON;加一個回 HTML 的出口(帶內容安全政策標頭),不改既有 JSON 路徑。

### 展示伺服器與觸發

- 路由:首頁(說明與「開始展示」按鈕)、觸發(送出表單)、展示頁(某一次展示的進度與結果)、報告(展示結束後的整份報告)。
- 觸發用表單送出,不用腳本;伺服器只綁回送位址、檢查主機標頭,另加兩道防跨站觸發:表單帶一個伺服器每次啟動時產生的隨機值,送出時比對;來源標頭不是本機就拒。
- 同時只准一次展示在跑:第二次觸發回「已有展示在跑」並給那一次的展示頁;上一輪沒跑完不准開新的。
- 每按一次產生一個展示編號(隨機、URL 安全),它同時是:暫存目錄名稱、傳給所有模型入口的展示編號(Phase 11B 的 1 美元上限以它為單位)、頁面網址的一段。
- 頁面與進度讀取不寫任何資料庫;只有觸發會啟動驅動程式,驅動程式照正式程式寫它自己的暫存資料庫。展示用的資料庫放暫存目錄、每次重建。
- 進度更新:展示頁用 meta refresh 每 2 秒整頁重讀(沒有腳本;見〈待使用者裁定〉第 3 條)。展示結束後不再重讀。

### 驅動程式:依序跑 F1–F7

- 每個情境一段獨立的暫存子目錄、自己的一組資料庫與行程,前一個情境的行程全部結束才開下一個;不共用狀態。
- 每個情境寫「開始、每一步、結束」的進度事件到展示目錄下一份只追加的進度檔(每行一筆 JSON);伺服器只讀這份檔。
- 每個情境的組法照對應的端到端測試:
  - F1:DSP 啟動時載入一份故障排程(提交前逾時、提交後逾時、延遲提交),執行迴圈遇到結果不明、對帳、同鍵重送。
  - F2、F3:執行迴圈經展示啟動器在指定死點猝死,重啟時時鐘往後撥,從持久事實恢復;F3 把同一則訊息投遞兩次。
  - F4:驅動程式扮另一個寫入者,在提案形成後搶先改廣告,舊提案被擋、接續任務照現況重排。
  - F5:廣告名稱換成一份對抗性素材(從既有的對抗樣本取一份),DSP 上發生的事跟名稱正常時一樣。
  - F6:提案進死信、之後改廣告版本,重放被擋並另開接續任務。
  - F7:多個廣告各加一成,總曝險到門檻停在待核可(規模見〈待使用者裁定〉第 2 條)。
- 每個情境結束後用唯讀出口收集:追蹤檢視(每個任務的時間線)、稽核查詢(擋下與核可)、DSP 操作歷史(真實狀態)、指標與服務水準;存成情境的結果檔,頁面讀它。
- 展示自己的失敗(行程起不來、情境逾時)跟被測系統的結果分開標:情境結果只有「情境照預期跑完」「情境沒跑完(展示故障)」兩種,不會把展示故障顯示成系統擋下,也不會把沒跑完顯示成綠燈。每個情境有總時限,逾時就整組結束行程、標「沒跑完」。
- F1–F7 的「確定性通過或失敗斷言」不由驅動程式判:展示最後一步跑一次驗證器(它會自己跑 F1–F7 的證據測試),頁面顯示驗證器的輸出。驅動程式只負責讓人看到過程。

### 子行程的環境與金鑰

- 驅動程式啟動任何非模型行程,環境一律從白名單組:PATH、HOME、LANG、USER,加上該角色需要的鍵(能力金鑰、稽核金鑰、核可金鑰),值由驅動程式在每次展示開始時用 secrets 產生、只存在這次展示;使用者環境裡的其他變數一律不帶。
- 模型入口(模型說明命令列、假說命令列)照 Phase 11B:驅動程式傳展示編號;即時與否照 Phase 11B 的三個條件判,驅動程式不另外開關。

### 頁面分區

- 頂端:展示編號、開始時間、模型模式(錄製或即時,錄製時標「錄製回應,不是即時呼叫」)、這次的花費(從花費帳唯讀開法讀,Phase 11B)、驗證器版本雜湊與提交編號。
- 情境列表:F1–F7 各一列,顯示狀態(待跑、進行中、照預期跑完、沒跑完)與一句白話「這個情境在測什麼事故」。
- 每個情境展開:
  - 任務時間線:照追蹤檢視的事件順序,每一列一個階段(領取、分析、提案、送件、執行前檢查、寫入、結果不明、對帳、擋下、待核可、重放、接續任務、完成);時間用 UTC 顯示。
  - 處置說明:每個擋下原因、處置、死信原因都對到一句白話說明,這張對照表是程式常數,每個列舉成員都要有一句(沒有就測試紅)。
  - DSP 真實狀態:廣告最後的預算、版本、狀態與 DSP 操作歷史。
  - 稽核:擋下、核可、重放紀錄。
- 模型那一步:在提案那一列之後顯示「模型說明」(Phase 11B 接入點 2):先列程式算的數字(金額、關卡、租戶),再列模型文字,標「模型產生、僅供參考」與來源;沒有成功結果就顯示結果類別(例如「已達上限」「尚未產生」)。服務水準告警響時另顯示假說(接入點 1),同樣標示。
- 驗證器結果:最後一區,原樣顯示驗證器的輸出(每行一段純文字),通過或擋下用文字標明,擋下原因逐條列。
- 已知限制:固定一區,列出這次展示沒證明的事(沿用各階段驗收紀錄的天花板)。

### 模型文字與不可信文字的顯示規則

- 所有動態文字(模型文字、廣告名稱、錯誤訊息、驗證器輸出)一律經同一支逸出函式插入文字節點:html.escape 加引號逸出,再把雙向控制字元(U+202A–U+202E、U+2066–U+2069)與其他不可見控制字元換成看得見的代碼;不插進屬性值、網址或樣式。
- 模型文字不產生連結、按鈕、表單或任何動作;頁面上的動作只有「開始展示」與(依裁定)核可,兩者的文字都是程式常數。
- 回應標頭設內容安全政策:不准任何腳本、不准內嵌樣式以外的外部資源、表單只准送回本站、不准被別的頁面框住。

### 核可畫面(依〈待使用者裁定〉第 4 條)

- 若裁定在頁面上核可:核可頁先列程式算的數字(金額、關卡、租戶),核可者要逐項勾選確認這些數字才能送出;模型說明放在數字之後、跟核可控制分開;送出時伺服器重新核對勾選的數字等於程式算的數字,不等就拒絕。核可簽章沿用既有核可命令列的簽法(核可金鑰由驅動程式產生、只在這次展示)。
- 顯示收據:核可者看到模型說明的那一刻,伺服器追加一筆只增不改的收據(提案雜湊、模型文字雜湊、來源、顯示時間);執行端不讀它,只給事後查核「核可當時看到什麼」。

### 報告與 README

- 展示結束後產生一份靜態 HTML 報告(同一支頁面產生程式、同一套逸出與內容安全政策),存在展示目錄(是否另外保存見〈待使用者裁定〉第 5 條)。
- README 寫:怎麼啟動展示伺服器、預期看到什麼(每個情境的預期處置)、錄製與即時模式、已知限制。

1. **一鍵的範圍**:(a)一顆按鈕跑完 F1–F7 全部;(b)一顆「全部」加每個情境各一顆單獨重跑。推薦 (a):符合「一鍵觸發整套」原話,也最省;單獨重跑可以之後再加。
2. **F7 的規模**:(a)照端到端測試 3000 個廣告、8 個工作者(本機約 30 秒);(b)縮成約 300 個廣告、門檻等比例縮小(幾秒內跑完),頁面註明「規模縮小,完整規模見驗證器跑的 F7 測試」。推薦 (b):展示重點是「到門檻就停、剩下的待核可」,等 30 秒對看展示的人很長;完整規模本來就由驗證器跑。
3. **進度更新方式**:(a)不用任何腳本,頁面每 2 秒整頁重讀(會有閃一下);(b)一支同源的小腳本局部更新(內容安全政策放行本站腳本)。推薦 (a):頁面完全沒有腳本,模型文字與廣告名稱就沒有機會被當成腳本跑,也最簡單;代價是畫面每 2 秒閃一下。
4. **核可在哪裡做**:(a)頁面上做(逐項確認數字才能送出、留顯示收據);(b)頁面只顯示待核可,核可照舊用命令列;(c)展示不核可,待核可的讓它逾期變成擋下。推薦 (a):需求 Issue 已寫了核可畫面與收據的要求,展示也才看得到「人核可後放行」;代價是展示伺服器要持有這次展示的核可金鑰(只綁本機、每次展示新產生)。
5. **報告要不要留下來**:(a)只在展示伺服器開著時看;(b)每次展示另存一份靜態 HTML 報告到專案外的固定目錄(例如 ~/.rtb/demo-reports/),可以之後打開或給別人看。推薦 (b):「結果與報告」要能留;代價是要定報告保留幾份(建議最近 20 份)。
6. **有無 Skill Contract 的前後比較怎麼做**:(a)用既有的造假示範當比較——同一份「只寫已完成」的清單,沒有驗證器時被當成完成、有驗證器時被擋下,頁面並排顯示;(b)真的讓模型在「有與沒有 Skill Contract 提示」兩種條件下產出同一個任務的程式或清單,用同一份評分表與測試評(會花模型額度,每次展示 1 美元上限內);(c)這個階段不做,列為已知缺口。推薦 (a) 加一句寫明它比較的是「有沒有機械驗證」而不是模型寫程式的品質;(b) 最貼近交接文件原意,但評分表要另設計、結果也不穩定。
