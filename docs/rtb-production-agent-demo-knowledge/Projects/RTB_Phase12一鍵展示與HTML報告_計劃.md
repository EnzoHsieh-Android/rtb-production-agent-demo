# RTB_Phase12一鍵展示與HTML報告_計劃

PRIOR-ART: 交接文件 Phase 12(F1–F7 故障注入展示、狀態時間線、DSP 真實狀態、追蹤、稽核、驗證器結果);本專案既有的只綁本機 HTTP 伺服器外殼(共用行程基礎,標準函式庫的 ThreadingHTTPServer);標準函式庫 html.escape 做純文字插入;內容安全政策(CSP)用回應標頭設;進度更新沿用最老的做法:頁面用 meta refresh 定時整頁重讀,不用前端框架(零依賴家規);故障情境的組法照 F1–F7 端到端測試既有做法(伺服器端排故障、子行程猝死、時鐘偏移)。否決過的做法:讓展示直接去跑 F1–F7 的 pytest 並撈它們的暫存資料庫(測試的資料庫在 pytest 的暫存目錄、跑完即刪,要改動每支測試的夾具,而且把展示綁死在測試實作細節上);F1–F7 的通過或失敗改由驗證器跑證據測試提供(驗證器本來就會跑它們)。
RETIRE-IF: 使用者決定不再需要本機展示(或改成有正式部署的儀表板時),撤掉展示伺服器、頁面、驅動程式與展示啟動器,分析端驅動命令列照樣保留(它是正式入口);或連續三次展示都有情境因展示本身(不是被測系統)失敗,就回頭重審驅動程式的做法。

## 這份計劃在解決什麼

交接文件 Phase 12:用事故證據展示系統的價值。完成條件六項:F1–F7 全部有確定性的通過或失敗斷言;展示畫面顯示狀態時間線、DSP 真實狀態、追蹤、稽核與驗證器結果;有無 Skill Contract 的前後比較使用相同任務、環境、評分表與測試並記錄差異與限制;不只展示順利流程或模型解釋,而是展示擋下、恢復與對帳;README 給可重現步驟、預期輸出與已知限制;最終證據清單全部通過,沒證明的項目標成擋下或已知缺口。

使用者本人要求把這份展示做成 HTML:在頁面上按一下觸發整套,即時看到每個任務走到哪個階段、系統怎麼處置、結果與報告。需求原文見 [[Issues/Phase12需要可看任務階段與處置的HTML報告]]。

這個階段要防的事故:
- 展示畫面變成新的攻擊面:模型文字或廣告名稱裡的腳本、連結、雙向控制字元在頁面上被當成指令或誤導核可者。
- 展示本身的故障被當成系統故障(或反過來,系統失敗被展示吞掉):看到綠燈但其實情境沒跑完。
- 展示啟動器把「只給測試用的故障手段」帶進正式程式。
- 展示行程拿到使用者環境裡的秘密(子行程繼承整份環境)。

## 使用者裁定(2026-09-24,使用者本人;需求 Issue、Phase 11B 計劃與協調者轉達)

- 要一份 HTML,能明確看到每個任務走到哪個階段(狀態時間線)、系統怎麼處置(擋下、待核可、對帳、重放、退回等)、最後結果與報告。交接文件第 19 節把「漂亮 dashboard 或複雜前端」列為非目標,使用者已決定要;照第 19 節,本計劃寫明最小做法與額外成本(見〈設計〉與〈實務隱患〉)。
- 一鍵展示做在 HTML 上:頁面上按按鈕觸發整套(起模擬 DSP、收件口、執行迴圈、分析端驅動、注入 F1–F7),頁面即時看到各任務的階段、處置與結果;不是另外下指令。不做長駐上線部署。
- 模型相關(Phase 11B 使用者裁定):供應商 Anthropic Claude、預設模型 Sonnet 5;花費上限每次展示 1 美元、每月 20 美元,到上限顯示「已達上限」不默默繼續;沒開即時模式時用錄製回應並清楚標示「錄製回應,不是即時呼叫」;模型後端走本機 Claude Code 非互動模式;接入點 2 的說明給人工核可的人看,標明「模型產生、僅供參考」,程式算的數字放在它前面。
- 第 1 版列的六件待裁定(2026-09-24 使用者本人拍板):
  1. 一鍵範圍:全部跑一次,再加每個情境單獨重跑。每一顆按鈕都走同一套觸發防護、同時只准一次展示。
  2. F7 規模:縮到約 300 個廣告、門檻等比例縮小,頁面註明「規模縮小,完整規模由驗證器跑的 F7 測試證明」。
  3. 進度更新:不用腳本,每 2 秒整頁重讀。
  4. 核可:在頁面上核可,逐項確認程式算的數字、留顯示收據;展示伺服器持有這次展示新產生的核可金鑰。
  5. 報告保存:每次另存一份靜態 HTML 到 ~/.rtb/demo-reports/,保留最近 20 份。
  6. 前後比較:拿既有造假示範並排對照,寫明比的是「有沒有機械驗證」。
- 頁面由 Codex 實作(原話「頁面我想讓codex來做」「做完你再串接」):增量 2 拆成 2a(頁面本身,Codex 實作)與 2b(串接,我們實作,2a 過代碼審後),見〈拆增量〉。
- 頁面要「可讀性、美觀兼具」:見〈版面與視覺〉;驗收由使用者本人看截圖確認。
- 畫面要呈現每一段 agent flow 做了什麼判斷、走進哪一個分支,呈現 DAG 的意涵:頁面畫整個流程的 DAG(判斷點、分支條件),每個情境高亮實際走過的路徑,附判斷紀錄表(在哪裡、判成什麼、走哪條分支、為什麼)。
- 流程在跑的時候也要非常清楚:執行中標出目前在哪個節點、已經在這一步多久、上一個判斷;驅動程式每跑到一個節點就更新展示狀態,不只情境結束才更新。
- 頁面文字一律白話(原話「上面有太多看不懂的術語,死信、猝死、總曝險,通篇呈現全部讓codex校正過一次」):使用者看得到的文字——標題、情境名、在測什麼、流程節點名、分支條件、處置說明、狀態、結果一句話——沒有背景的人也看得懂;內部術語非用不可時旁邊加一句白話解釋;頁面底部有「名詞小辭典」,列保留下來的專有名詞各一句解釋。2b 的流程圖定義與處置說明對照表,顯示文字照同一標準寫,跟程式裡的列舉名稱分開(列舉名稱不改,只改顯示字)。

## 現況(2026-09-24 前掃,phase11-design 5963b6b)

- 命令列入口共九支:模擬 DSP、評估紀錄、核可、收件口、重放、執行迴圈、指標、服務水準、追蹤。**分析端沒有正式啟動程式**:流程推進函式只在測試裡由測試組裝呼叫(分析行程流程筆記有「呼叫次數 × 逾時 × 2 < 租約」的 REVISIT,至今沒有機械守衛)。
- **沒有展示驅動程式**。F1–F7 各自只存在於端到端測試,而且都靠只在測試裡的手段:
  - F1(提交前後逾時):DSP 伺服器那一側由測試排定故障(執行端的共用用戶端送不出故障標頭);
  - F2、F3(猝死、重複投遞):子行程跑內嵌腳本,把執行迴圈類別上的方法換成「印出死點、os._exit(9)」;重啟時把時鐘往後撥 5 分鐘;
  - F4(舊版本):另一個寫入者在兩個時點搶先改廣告;
  - F5(提示注入):廣告名稱換成對抗性素材;
  - F6(死信重放):執行端時鐘往後推 16 分鐘、讀不到 DSP 用連不上的位址;
  - F7(總曝險):行程內假 DSP、3000 個廣告、8 個工作者,本機約 30 秒(CI 偶爾超過 60 秒,見 [[Issues/F7端到端在CI上偶爾超過60秒]])。

## 設計

### 分工

- src/rtb/analyzer/runner.py(新,正式入口):分析端驅動命令列。反覆領取待推進的任務、用正式的 DSP 用戶端與收件口用戶端呼叫流程推進函式,直到沒有可推進的任務或收到停止訊號。跟測試用同一支流程推進函式、同一套租約;它是正式程式,不帶任何故障手段。
- 分析端(動,小改動):決定不提案時,把不提案原因(NoActionReason)存進分析端資料庫(只增的欄位或事件,不改既有欄位),驅動程式讀得到;現在正式的決策函式把原因丟掉,展示無從知道「不調整」是哪一種。
- src/rtb/demo/faults/(新,展示專用的故障套件):DSP 伺服器端的故障排程、執行迴圈的猝死點、時鐘偏移,照 F1–F7 端到端測試的組法搬過來。
  - 只有展示啟動器准匯入它。守法兩道:一支掃描測試掃 src 全部(不含 tests),抓匯入與字串裡出現 rtb.demo.faults(子行程用 -m 字串啟動也算);ruff 的禁止匯入規則放在 src/rtb/demo/ruff.toml,啟動器放在自己的子目錄 src/rtb/demo/launcher/,那裡的 ruff.toml 重列上一層的全部禁令、只少故障套件那一條(ruff 子目錄設定會整張蓋掉禁令表,所以不能用檔案層級關掉整條規則,那會連禁止動態匯入一起放掉);另有一支測試比對兩份禁令表只差這一條。
  - 故障套件與啟動器都沒有命令列入口。故障手段跑在子行程裡(DSP 伺服器、執行迴圈),所以跨行程交付:啟動器在這次展示的暫存根目錄寫一份故障設定檔,另產生一次性隨機值,經白名單環境(RTB_DEMO_FAULT_NONCE)只傳給那一個子行程;故障程式在子行程啟動時核對三件事——設定檔路徑落在根目錄內、隨機值跟設定檔記的相符、根目錄是這次展示建的(根目錄裡有展示伺服器寫的標記檔)——任一不符就拒絕啟動故障。所有目標路徑必須落在那個根目錄內。驅動程式經啟動器排故障,不直接碰故障套件。
- src/rtb/demo/launcher/(新,只給展示):展示啟動器。用子行程啟動各角色(模擬 DSP、收件口、執行迴圈、分析端驅動、模型入口),在正式入口外面包上故障套件的手段。
- src/rtb/demo/driver.py(新):驅動程式,是展示伺服器行程內的一條執行緒(不是子行程)。依序跑 F1 到 F7(或單一情境),每個情境:建暫存目錄與資料庫、用伺服器交給它的這次展示金鑰、經啟動器起行程、造資料、排故障;一邊跑一邊從系統紀錄觀察走到哪、寫進展示狀態;情境結束後拿觀察到的路徑比預期路徑,再比 DSP 真實狀態。
- src/rtb/demo/flow.py(新):正式的流程圖定義(節點、判斷點、分支、白話顯示字)與列舉對應表,照系統實際流程寫;取代頁面測試用的示範圖。
- src/rtb/demo/state.py、src/rtb/demo/page.py、src/rtb/demo/static/demo.css(新,增量 2a,Codex 實作):展示狀態資料結構、頁面產生純函式、同源樣式表。
- src/rtb/demo/server.py(新,增量 2b):展示伺服器。沿用共用行程基礎的伺服器外殼,處理器宣告回 HTML。
- 共用行程基礎(動):出口加表單入口。
  - 出口:處理器可以回一個回應物件(狀態碼、內容類型、額外標頭、內文),至少涵蓋 application/json(既有路徑照舊)、text/html、text/css 與 303 加 Location;宣告 HTML 的伺服器,HTML 回應與錯誤頁一律帶內容安全政策標頭;主機標頭檢查、未預期例外這些共用路徑,在宣告 HTML 的伺服器也回 HTML 錯誤頁。
  - 入口:加一支讀 urlencoded 表單的方法,沿用讀 JSON 那支的長度與上限檢查,同一個欄位出現兩次一律拒。
  - 不複製請求分派那段。

### 展示伺服器與觸發

- 路由:首頁與展示頁(同一頁:沒在跑時顯示按鈕,在跑時顯示進度)、全部跑一次(POST /run)、單一情境重跑(POST /run/scenario,帶情境代碼)、確認頁(GET /approve,獨立一頁)、送出確認(POST /approve)、報告(展示結束後的整份報告)、樣式表(同源)。
- 所有路由(含 HTML 頁與樣式表)對非本機的主機標頭一律拒絕,回帶內容安全政策標頭的 HTML 錯誤頁。
- 每一個 POST(/run、/run/scenario、/approve)都走同一套防護:表單帶一個伺服器每次啟動時產生的隨機值,送出時用 hmac.compare_digest 比對;來源標頭不是本機就拒;情境代碼只收七個列舉值之一。POST 處理完一律回 303 轉到 /#current,瀏覽器之後都用 GET 讀頁。
- 同時只准一次展示在跑:伺服器用一把 threading.Lock 包住「檢查有沒有在跑 + 標記開始」這一段,兩個真的同時到的請求只會有一個啟動;「在跑」一直持續到整次展示結束(含自動查核與報告另存),在跑時其他觸發都回「已有展示在跑」並顯示那一次的進度;單一情境重跑也算一次展示。「在跑」旗標只在驅動執行緒的 finally 裡放掉,驅動程式出例外也不會卡住,其他地方都不放。
- 每按一次產生一個展示編號(隨機、URL 安全),它同時是:暫存目錄名稱、傳給所有模型入口的展示編號(Phase 11B 的 1 美元上限以它為單位)、報告檔名的一段。
- 頁面與進度讀取不寫任何資料庫。唯一例外:GET /approve 顯示確認頁時追加一筆顯示收據,寫進收據檔(見〈核可畫面〉),不是資料庫;而且只在請求的 Sec-Fetch-Site 是 same-origin 或 none、Sec-Fetch-Dest 是 document 時才記(別的網站讓瀏覽器先打一次不會留下假收據),不符照樣顯示頁面但不記。只有觸發會啟動驅動程式,驅動程式照正式程式寫它自己的暫存資料庫。展示用的資料庫放暫存目錄、每次重建。
- 伺服器持有「目前顯示的展示狀態」:全部跑一次整份換新;單一情境重跑只替換那一個情境,其他六個情境、流程圖、已知限制原樣保留。每個情境帶自己的出處(展示編號、時間、模型模式),頁面逐情境顯示;上一次全部跑一次的花費在它結束時算好、存進伺服器狀態,重跑時跟「這次重跑的花費」分開列。
- 單一情境重跑不啟動驗證器;頁面的驗證器結果旁標明「取自 某時 那次全部跑一次(展示編號 X)」;從來沒有全部跑一次過就先重跑時,那一格顯示「還沒有完整執行過」。
- 進度更新:展示在跑時頁面用 meta refresh 每 2 秒整頁重讀(沒有腳本)。重讀網址帶一個每次都不同的查詢值(例如 /?tick=<序號>#current,伺服器忽略這個值),瀏覽器才會真的重新 GET,不會只當成同頁跳錨點;錨點讓畫面停在目前節點。展示結束後不再重讀。
- 等你確認:F7 停在等人確認時,主頁不自動重讀,改放一個「去確認」連結與一個手動「重新整理」連結;確認表單在 GET /approve 的獨立頁,這一頁也不重讀,勾選不會被洗掉。確認逾時之後只清掉確認表單,確認頁與 POST /approve 從此一律拒絕並說明已逾時;鎖照樣握著,等自動查核與報告另存做完才放。
- 切換情境:沒有腳本,情境清單每列是連到 /?scenario=F3 這種網址的連結;伺服器照查詢參數產生頁面,查詢參數只接受七個情境代碼之一,其他值(含空值、重複參數)當沒選。展示在跑時一律跟著目前情境,不看查詢參數。

### 驅動程式:依序跑 F1–F7

- 每個情境一段獨立的暫存子目錄、自己的一組資料庫與行程,前一個情境的行程全部結束才開下一個;不共用狀態。
- 展示狀態存在一顆暫存 SQLite(用共用的 SQLite 工具開):驅動執行緒寫,伺服器用唯讀開法讀;不自創檔案協定。
- 判斷紀錄是「驅動程式從系統紀錄觀察到的事」:驅動程式輪詢各暫存資料庫的生命週期事件、停下紀錄、分析端歷史與 DSP 操作歷史,每觀察到一個新節點就在 3 秒內寫進展示狀態(即時顯示的「上一個判斷」就是它)。每筆判斷帶來源(哪一顆資料庫的哪個事件編號或哪一列),白話原因取自流程圖對應表;系統沒有保存原因的節點,判斷紀錄寫「無法還原(系統沒有保存原因)」,不留白也不臆測。
- F7 有 8 個工作者並行,單一「目前節點」說不清:F7 的「目前」改成情境層的彙總——每個節點目前有幾筆停在那裡、已放行幾筆、等人確認幾筆——頁面在流程圖節點旁顯示筆數徽章;其他情境照舊只有一條路徑。
- 情境結束後的交叉核對:
  - 預期路徑分兩部分:「必經節點與邊」(順序要對)與「允許出現的回頭」。回頭清單裡的節點出現與否、出現幾次都不算對不上,除非它是這個情境要證明的——例如 F1 的同編號重送是必經;多一次稍後再查或放回排隊,情境照樣照預期跑完。
  - 觀察到的路徑對必經部分,再拿 DSP 真實狀態(獨立來源)比預期寫入。
  - F7 逐廣告核對:平台真實狀態裡被放行的廣告與加額,要跟依門檻算出的那一批一一對上,不只比總數;停在等人確認的筆數另外比。
  - 對不上就標「沒跑完」並寫哪一步對不上。
- 每個情境的組法照對應的端到端測試,結束時由驅動程式自己斷言預期處置,斷言全過才標「照預期跑完」;沒過標「沒跑完」並寫哪一條沒對上:
  - F1:DSP 啟動時載入一份故障排程(提交前逾時、提交後逾時、延遲提交)。斷言:出現不知道有沒有寫進去、回頭去平台查、同編號重送,DSP 上只套用一次。
  - F2、F3:執行迴圈經展示啟動器在指定死點猝死;重啟時執行迴圈與模擬 DSP 子行程一起重啟,由啟動器外殼帶同樣的時鐘偏移(DSP 的資料在它的資料庫裡,重啟不丟),平台才不會因時間對不上拒收寫入許可;從持久事實恢復。F3 把同一則訊息投遞兩次,另外用兩個真的並行分析工作者對同一個任務推進(柵欄逼兩邊同時卡在付費呼叫前,比照分析端租約測試的手法)。斷言:恢復後 DSP 上只套用一次、平台沒有拒收寫入許可;F3 另斷言只有一方進入付費判斷、那件工作只被分析一次。
  - F4:驅動程式扮另一個寫入者,在提案形成後搶先改廣告。斷言:舊提案以版本已變被擋、開一件新工作並照現況重排。
  - F5:廣告名稱換成一份對抗性素材(從既有的對抗樣本取一份)。斷言:DSP 上發生的事跟名稱正常時一樣。
  - F6:提案進「停下等人處理」、之後改廣告版本。重放放回待處理的是同一則訊息(不是新的一版),執行前檢查以版本已變擋下、另開新工作。斷言:重放被擋、新工作建立,DSP 上沒有舊決策的值。
  - F7:約 300 個廣告各加一成、門檻等比例縮小,由 8 個工作者打一個真的模擬 DSP 子行程(F7 端到端測試用的是行程內假 DSP,展示改用真的,「DSP 真實狀態」才收得到)。門檻以內的放行(約 123 筆),其餘約「廣告數 − 放行數」筆全部停在等人確認。驅動程式指定最早停下的那一筆做確認展示,情境進「等你確認」狀態;這段等待不算進 F7 的總時限,但有自己的上限:min(那筆提案的決策到期 − 1 分鐘餘裕, 10 分鐘)。到期沒人確認就標「沒跑完:沒有人確認」、清掉確認表單、繼續跑自動查核(鎖照樣握到整次展示結束)。完成條件:確認的那筆寫進平台,其餘維持等人確認或到期結案,都算照預期。頁面註明「規模縮小,完整規模由驗證器跑的 F7 測試證明」。
- 每個情境結束後用唯讀出口收集:追蹤檢視(每個任務的時間線,含每筆提案的處置與擋下原因)、稽核查詢(總上限稽核明細與確認次數,F7 用)、DSP 操作歷史(真實狀態)、指標與服務水準。
- 展示自己的失敗(行程起不來、情境逾時)跟被測系統的結果分開標:情境結果只有「照預期跑完」「沒跑完」與 F7 的「等你確認」;「沒跑完」一律寫原因(展示故障、斷言沒過、交叉核對對不上、沒有人確認),不會把展示故障顯示成系統擋下,也不會把沒跑完顯示成綠燈。每個情境有總時限(不含等你確認的時間),逾時就整組結束行程、標「沒跑完」並寫原因。
- 驗證器結果另外顯示:全部跑一次的最後一步跑一次驗證器(它會自己跑 F1–F7 的證據測試),頁面原樣顯示輸出;它跟驅動程式的情境斷言是兩件事,各自標示。

### 流程圖與判斷路徑

- 流程圖定義(src/rtb/demo/flow.py)照系統實際流程:分析端(領取、蒐集證據、證據新鮮度判斷、資料齊不齊、花費速度、由誰判斷、值不值得加、產生提案、模型說明旁支、送件)、收件口(收件驗證)、執行端(領取、執行前檢查、權限與上限、總上限、等人確認、寫入 DSP、平台回覆、回頭查、比對、轉人工、重送、停下等人處理、重放)、DSP、人工;判斷點畫菱形、步驟畫圓角矩形、結束點另一種形狀,分泳道。每個節點與分支另有給人看的白話顯示名稱(例如「停下等人處理」顯示成「試太多次都沒能開始,先停下等人處理」,「總上限」顯示成「全部廣告加起來會不會超過總上限」)。
- 流程圖是有向無環圖,有環就丟例外。已知的「回頭」轉換全部列在流程圖定義裡的一份常數清單,每一條展開成新的節點(「再來一次」的那一份,標籤寫明回到哪一步),不畫回原節點:
  - 分析端任務狀態:分析中 → 回去蒐集證據、已提案 → 回去蒐集證據;
  - 分析端:被擋或過期 → 開一件新工作;
  - 執行端:確認後放回待處理、重放放回待處理(同一則訊息)、前一個處理者沒回報被接手、放掉處理權後重新投遞、這一輪先不處理放回排隊;
  - 執行端寫入:不知道有沒有寫進去 → 同編號重送、這次查不出結論 → 稍後再查。
  一個情境同一條回頭走了不只一次時,流程圖只畫一份展開節點,判斷紀錄表逐次列出。
- 回頭清單照測試核對兩份程式來源:任務狀態與嘗試狀態轉換表裡每一條往回走的轉換,以及執行端生命週期事件裡代表放回待處理的種類(確認後放回、重放放回、被接手、放掉處理權),都要對到清單裡的一個展開節點。
- 系統的結果列舉每一個成員,在流程圖裡都要對得到一條邊或一個節點;對應表的鍵一律是(列舉類別, 成員名),不同列舉的同名成員不會互相蓋掉。對應清單:
  - 執行端:處置、擋下原因、死信原因、停下種類、生命週期事件種類、重放結果、處理待確認的結果、最後失敗原因;
  - 執行端真正控制平台回覆與轉人工的型別:嘗試狀態、結果代碼、作廢結果、執行迴圈結果;
  - 分析端:任務狀態、重新規劃原因、證據新鮮度、值不值得加的判定、沒提案原因、路由路徑。
  原則是「流程圖上每個判斷點都綁一個列舉」:除了流程圖定義裡列名並寫明理由的「往下走」分支之外,每條分支至少對到那個列舉的一個成員(對到這條邊或它通往的節點);例外清單每一項都要是這個判斷點真的分支。用測試守,缺一個就測試紅,所以系統新增一種擋下原因卻沒補圖,測試會擋。
- 白話顯示字覆蓋同一份對應清單:清單上每個列舉的每個成員都要有白話顯示字,缺一個測試紅。

### 子行程的環境與金鑰

- 驅動程式啟動的所有行程(含模型入口命令列本身),環境一律從白名單組:PATH、HOME、LANG、USER、PYTHONPATH,加上該角色需要的鍵(能力金鑰、稽核金鑰、核可金鑰;有排故障的那一個子行程另加故障隨機值 RTB_DEMO_FAULT_NONCE);PYTHONPATH 的值固定為專案 src 的絕對路徑(專案沒有安裝成套件,子行程要靠它找到程式),不從使用者環境轉;使用者環境裡的其他變數一律不帶。
- 模型入口另外多帶 RTB_MODEL_LIVE、RTB_MODEL、RTB_MODEL_RECORD 三個變數(照使用者環境轉,只給模型入口)。模型入口再往下開 claude 時的環境,由 Phase 11B 的 [S905] 管;兩層分開,本計劃只管第一層。
- 金鑰每次展示一組(能力、稽核、核可三把),由伺服器在觸發時用 secrets.token_urlsafe 產生文字,長度讓它的 UTF-8 至少 MIN_KEY_BYTES(目前 32 位元組)。環境變數只裝得下文字,子行程照既有讀法 read_key 把文字轉回 UTF-8 位元組;伺服器行程內簽發一律用同一條路(text.encode("utf-8")),兩邊的金鑰值才相同。經記憶體交給驅動執行緒,啟動子行程(例如 F7 的執行迴圈)時經白名單環境傳入。金鑰的文字與位元組都不寫進展示狀態資料庫、報告或收據檔;展示結束即丟。
- 模型入口照 Phase 11B:驅動程式傳展示編號;即時或錄製由入口自己判(Phase 11B 的條件不只三個:即時開關、展示編號、找得到 claude,還有價目表沒過期、沒有管理政策檔、即時模式實測紀錄有效,真家目錄隔離時還要沒有記憶內容),驅動程式不另外開關,頁面只顯示入口實際判出的模式與原因。
- 花費帳:沒開即時開關時,驅動程式給模型入口帶 --ledger 指到這次展示的暫存目錄,錄製重播的 0 元紀錄不進使用者的真帳;開了即時開關,照 Phase 11B 用家目錄下的真帳。「有沒有開即時開關」直接呼叫模型用戶端的同一支判定(值要等於 1),驅動程式不自己解析,RTB_MODEL_LIVE=true 這種值兩邊判法一致。天花板:開了即時開關、但入口因其他條件不齊改走錄製時,那幾筆 0 元紀錄照 Phase 11B 記進真帳。

### 頁面分區

- 頂端摘要:展示編號、開始時間(UTC)、模型模式(照入口實際判出的結果與原因;錄製時寫「錄製回應,不是即時呼叫」)、花費(從花費帳唯讀開法按展示編號加總;單一情境重跑時分開列「這次重跑的花費」與「上一次全部跑一次的花費」)、驗證器版本雜湊與提交編號、目前進度(幾個情境跑完、共幾個)。
- 展示在跑時最上方固定一條「現在進度」:第幾個情境、情境名、目前節點、已經在這一步多久(伺服器產生當下算好)、上一個判斷;F7 改顯示各節點的筆數彙總(已放行、等人確認)。
- 主流程圖:整頁一張橫向的流程圖(泳道換行排,整張圖不用橫捲),高亮「正在跑的情境」或「選看的情境」實際走過的完整路徑;目前節點帶固定錨點,每 2 秒重讀時畫面停在那裡;F7 在節點旁顯示筆數徽章。
- 情境清單:F1–F7 每列一行(代碼、標題、狀態、一句結果),每列是切換選看情境的連結;正在跑或選看的那一列標明。
- 選看情境的細節:這個情境在測什麼、出處(展示編號、時間、模型模式)、判斷紀錄表(每筆附來源)、任務時間線、處置說明、DSP 真實狀態、稽核、模型那一步、假說;「沒跑完」時寫原因。
- 處置說明:流程圖對應清單上每個列舉成員都對到一句白話說明,這張對照表是程式常數,鍵是(類別, 代碼)兩欄(頁面的處置說明也照這兩欄查,不用裸字串),缺一句就測試紅。說明文字照〈版面與視覺〉的白話標準寫,列舉名稱本身不改。
- 名詞小辭典:頁面底部固定一區,列頁面上保留下來的專有名詞(例如 DSP、核可、錄製回應),每個一句白話解釋。
- 模型那一步:先列程式算的數字(金額、關卡、租戶),再列模型文字,標「模型產生、僅供參考」與來源;沒有成功結果就顯示結果類別(例如「已達上限」);模型入口還沒接上時顯示「尚未產生」。服務水準告警響時另顯示假說,同樣標示。
- 驗證器結果:原樣顯示驗證器的輸出(每行一段純文字,預設收合),通過或擋下用文字標明,擋下原因逐條列;標明取自哪一次全部跑一次(時間與展示編號);沒有完整執行過就寫「還沒有完整執行過」。
- 前後比較:並排表(造假手法、沒有驗證器時、有驗證器時),寫明比的是「有沒有機械驗證」。
- 已知限制:固定一區,列出這次展示沒證明的事(沿用各階段驗收紀錄的天花板;含「展示的 F7 用真 DSP、規模 300;驗證器的 F7 用行程內假 DSP、規模 3000」)。

### 版面與視覺(使用者本人要求可讀性、美觀兼具)

- 白話(使用者本人 2026-09-24 裁定):

  - 顯示文字跟程式裡的列舉名稱分開:流程圖節點與分支的顯示名稱、處置說明對照表都是另外一份顯示字,列舉名稱不改。

  - 頁面底部「名詞小辭典」列保留下來的專有名詞,每個一句白話;辭典本身的詞條名不受禁用清單限制。

- 可讀性:
  - 一眼看出目前在哪個情境、哪一步、結果是什麼;狀態(待跑、進行中、等你確認、照預期跑完、沒跑完;驗證器通過、擋下)一律顏色加文字雙重標示,不只靠顏色,配色色盲友善。
  - 每一步的處置說明用白話短句。
  - 長內容(驗證器輸出、追蹤、各情境細節)預設收合,用 details 與 summary(不需要腳本)。
  - 數字右對齊、等寬字;中文行高約 1.7、段距舒適、閱讀欄寬約 72 個字元寬;lang 設 zh-Hant。
  - 流程圖三種狀態分得清:已走過(粗線強調色、節點打勾)、目前這一步(醒目外框加「目前在這一步」文字;呼吸閃爍用純樣式,prefers-reduced-motion 時關掉)、還沒走到(淡色);沒走的分支更淡加虛線;走過的判斷點標序號。判斷紀錄表最新一列標「剛剛」。
  - 每 2 秒整頁重讀時畫面位置穩定(圖區用固定高度或最小高度)。
- 美觀:
  - 一份自帶的樣式表,不引外部字型、CDN 或圖片;色彩、間距、圓角、字級用 CSS 變數定義成一套系統。
  - 支援深色模式(prefers-color-scheme);深淺兩組配色的文字與背景對比都至少 4.5 比 1。
  - 系統字型堆疊;窄螢幕(約 400 像素寬)也能讀,表格可橫向捲動,流程圖泳道換行、用 viewBox 縮放。
- 限制照舊:內容安全政策不准任何腳本;樣式只從同源樣式表載入;流程圖是伺服器端產生的內嵌 SVG,裡面同樣不准腳本、事件屬性、外部連結與 foreignObject;模型文字一律純文字。

### 模型文字與不可信文字的顯示規則

- 所有動態文字(模型文字、廣告名稱、錯誤訊息、驗證器輸出、節點標籤、判斷原因)一律經同一支逸出函式插入文字節點:html.escape 加引號逸出,再把雙向控制字元(U+202A–U+202E、U+2066–U+2069、U+200E、U+200F)與其他不可見控制字元換成看得見的代碼;不插進屬性值、網址或樣式。唯一例外:表單隨機值與情境代碼放進隱藏欄位的值,仍經逸出,情境代碼只能是列舉值。
- 模型文字不產生連結、按鈕、表單或任何動作;頁面上的動作只有全部跑一次、單一情境重跑與核可,文字都是程式常數。
- 回應標頭設內容安全政策:default-src 'none'、script-src 'none'、style-src 'self'、form-action 'self'、frame-ancestors 'none'、base-uri 'none'、img-src 'none'。

### 核可畫面

- 確認頁(GET /approve)先列程式算的數字(金額、關卡、租戶),每個數字一個必勾的確認框(欄位名固定、值固定為 1,數字本身不放進任何屬性),另帶一個隱藏欄位「顯示當下的數字摘要雜湊」;模型說明放在數字之後、跟確認控制分開。這一頁不自動重讀。
- 送出時(POST /approve)伺服器核對:表單隨機值、來源標頭(同其他 POST)、每個確認框都勾了、表單帶的展示編號等於等人確認的那一次、提案雜湊對得上那一筆、表單帶的數字摘要雜湊等於驅動程式在 F7 停下時記下的數字快照算出的雜湊;任一不對就拒絕。簽之前在同一步從 F7 的執行端暫存資料庫重讀那筆建議的現況:仍在等人確認、修訂與內容雜湊相同、還沒過期,才簽;否則拒絕並在頁面顯示原因(例如「這筆已經到期結案」)。
- 簽一張確認要的全部來源由驅動程式在 F7 停下時記進展示狀態:task_id、revision、提案雜湊、租戶設定檔路徑、關卡、最大加額、提案決策到期時間。伺服器行程內直接呼叫既有的簽發函式(approval.issue)再寫進 F7 的執行端暫存資料庫(add_approval),不另開核可命令列子行程;到期時間取 min(提案決策到期, 現在 + 固定秒數);確認人固定寫「demo-operator」(符合編號格式檢查)。
- 顯示收據:GET /approve 顯示模型說明的那一刻(而且請求的 Sec-Fetch-Site 是 same-origin 或 none、Sec-Fetch-Dest 是 document),伺服器追加一筆收據(提案雜湊、模型文字雜湊、來源、顯示時間),寫進 ~/.rtb/demo-reports/ 旁邊一個只增不改的收據檔,不隨報告的 20 份輪替刪除,並寫進當次靜態報告;同一份(提案雜湊、模型文字雜湊)只記一次。執行端不讀它,只給事後查核「確認當時看到什麼」。

### 報告與 README

- 展示結束後用同一套版面產生一份靜態 HTML 報告(沒有任何表單、沒有自動重讀),樣式內嵌在報告自己裡面(從 ~/.rtb/demo-reports/ 用 file:// 直接打開也有版面;報告不經伺服器,不受內容安全政策標頭管)。七個情境各一張縮小的主流程圖高亮自己的路徑,加各自的判斷紀錄表與出處(展示編號、時間、模式),另附這次的顯示收據。
- 另存到 ~/.rtb/demo-reports/(檔名含展示編號與時間);全部跑一次的報告只保留最近 20 份,多的從最舊的刪;單一情境重跑的報告檔名另外標記,不佔那 20 份的額度(另有自己的保留上限,同樣 20 份)。
