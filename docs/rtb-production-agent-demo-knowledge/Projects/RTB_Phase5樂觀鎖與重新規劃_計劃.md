# RTB_Phase5樂觀鎖與重新規劃_計劃

PRIOR-ART: 樂觀鎖衝突後「重讀現況、重新決策」是樂觀並行控制的標準處理(HTTP 的 If-Match/412、資料庫的 compare-and-swap 失敗後重試讀改寫);本專案的版本比對兩層已經做完(執行前檢查、DSP 端預期版本),缺的只是衝突後的回報與重新規劃。重新規劃沿用「一次決策一個任務」的既有狀態機:原任務結案,另開一個接續任務,不改狀態機的終點規則。
RETIRE-IF: 換成外部工作流引擎(它自己管重試與重新規劃)時,撤掉接續任務這套機制。

## 這份計劃在解決什麼

- 事故 F4(交接文件第 16 節):提案形成之後,另一方先更新了廣告。執行時帶著舊預期版本的寫入要被拒、不能覆蓋較新的值,而且系統要重新取現況再規劃。
- 範圍:交接文件 Phase 5「Optimistic Locking 與 Concurrency」。完成條件:F4 通過;並行寫入的測試能重現衝突;舊提案不覆蓋較新狀態;衝突可查(軌跡、稽核);文件講清楚版本檢查、新鮮度、冪等三者的分工。
- 預告合約 [[Verification/事故F4_舊版本寫入被拒不覆蓋]](最遲 2026-12-15)是這個階段要轉正的合約。它的摘要寫「把觀察到的版本一路帶進執行寫入、衝突後重新規劃屬 Phase 5,還沒開工」,核對後前半句不準:版本已經一路帶進執行寫入(見現況),真正沒做的只有衝突後重新規劃。開工時照程式訂正那句摘要。

## 使用者情境題(2026-09-23)

- 題目:分析行程看到廣告版本 4,算出提案「預算 100→110」送進收件口;執行迴圈寫入前重讀,發現版本已變成 5。怎麼處理?a 直接用舊預期版本 4 送 DSP,讓 DSP 判斷;b 執行前檢查把觀察版本改成 5 繼續執行;c 版本不符就擋下、不呼叫 DSP,分析端之後要有機制重新讀廣告與證據、重新決策,不能讓任務卡死;d 重試三次都衝突才放棄。
- 使用者答 c,答對。回饋:擋下這一步已經做到(執行前檢查與 DSP 端兩層);重點在後半句「不能卡死」——現在提案被擋下後分析端完全不知道,任務停在已交給執行、永遠不再推進。a 把判斷丟給 DSP,失去「先檢查、不打擾外部」的防線,結果一樣卡住;b 用根據舊狀況算出的決策覆蓋別人剛改好的值,正是 F4 要防的事故;d 版本衝突是前提變了,重試不會消失。
- 設計分岔(2026-09-23 使用者裁定 B):任務狀態機有一條正式合約「終點沒有出路,交接之後不能退回蒐證」([[Systems/任務流程領域模型]])。A 放寬這條合約,讓版本已變時從已交給執行退回蒐證;B 不動合約,原任務結案、另開一個接續任務重新規劃。使用者選 B:一個任務對應一次決策,軌跡乾淨,合約不動。

## 現況(2026-09-23 開檔核對)

- 版本一路帶進執行寫入:提案必填觀察到的廣告版本;執行前檢查重讀 DSP,版本不符就擋下(版本已變)、不呼叫 DSP;DSP 端寫入也比對預期版本,不符回 409、執行端記失敗(版本衝突)。兩層都有端到端測試([[Projects/RTB_Phase3外部寫入安全_計劃]] 的 [S52],測試 test_f4_a_stale_proposal_never_overwrites_a_newer_value,包含執行前檢查通過之後、寫入之前被搶先改的情況)。
- 回報管道有一半:分析行程把同一份提案(同任務同修訂同內容)再送一次是安全的(收件口回目前狀態、不新增一筆);收件口的回應本文已經帶著提案目前的處置(已交給執行、已擋下、過期、死信、處理中、被取代),但沒帶擋下原因,分析端的用戶端也把回應本文丟掉、只看有沒有收下。
- 分析行程的任務一進入已交給執行就不再推進:推進函式沒有這個狀態的下一步;狀態機允許它轉成完成、擋下、被取代,但沒有任何程式會觸發。

## 最小設計(第 1 版)

- **狀態(2026-09-23):設計中**。

### 收件口回報擋下原因

- 收件口對重送的回應本文多帶「擋下原因」(只有處置是已擋下時才有值;其餘為空)。收件表本來就存著擋下原因代碼,只是沒放進回應。
- 分析端的收件口用戶端讀回應本文的處置與擋下原因,放進「已收下」結果;原本只看有沒有收下的呼叫端不受影響。

### 分析行程:已交給執行之後的下一步

- 推進函式替「已交給執行」加一步:把存著的那份提案快照原樣重送一次(同一份提案重送永遠安全),依回報的處置決定:
  - 已交給執行(執行端已驗證寫入)→ 任務轉完成。
  - 處理中或待處理 → 這一輪沒有進展,回原狀態。
  - 已擋下、原因是版本已變 → 重新規劃(見下)。
  - 已擋下的其他原因、過期、死信 → 任務轉擋下,錯誤說明記下處置與原因;不重新規劃。
  - 被新修訂取代 → 任務轉被取代。目前沒有真實觸發路徑:分析行程每個任務永遠只送修訂 1([[Systems/分析行程流程與檢查點]] 的已知缺口),同一個任務不會被自己的新修訂取代;接續任務是另一個任務編號,也不會取代原任務。這個分支是防線,合約只能用替身協作者觸發,等修訂序號補上才有真實路徑(前掃第 ③ 項)。
  - 收件口拒收「提案已過期」或「修訂不連號」→ 任務轉擋下,記原因。收件表保留期(2 小時)長於提案最長壽命(1 小時,模組載入時有自我檢查),所以保留期清掉的提案重送會被判過期——前提是修訂號是 1(目前永遠是 1);修訂號不是 1 時收件口會先判修訂不連號,一併當成已結案處理,避免任務卡住(前掃第 ④ 項)。
- 這一步照 Phase 4 增量 3b 的任務租約走(先取得租約才呼叫收件口)。

### 重新規劃:接續任務

- 原任務轉擋下之前,先建一個接續任務:編號是原任務編號加「.r」加代數(原任務 t1 的接續是 t1.r2,t1.r2 的接續是 t1.r3),同一個廣告,從收到開始走完整流程(重新蒐證、重新分析)。建任務本來就是冪等的(同編號同廣告再建一次什麼都不做),所以先建接續、再結案原任務:兩步之間當機,下一次推進原任務會重送、再看到版本已變、再建一次(什麼都不做)、再結案。
- 接續關係存在任務模組一張只增不改的小表(接續任務編號、原任務編號),原任務轉擋下那一列的錯誤說明也寫上接續任務編號,查軌跡時兩邊都看得到。
- 接續任務的提案是新任務的第一個修訂;它看到的是重讀後的新版本,送進收件口後照一般流程過執行前檢查。
- 代數上限暫用 3(t1、t1.r2、t1.r3):同一個廣告一直被別人搶先改,重新規劃三次仍衝突就不再接續、原任務只轉擋下,等人看。
REVISIT:2026-12-31 有真實衝突頻率數據時,重新評估代數上限。

### 衝突可查

- 任務歷史:原任務擋下那一列記處置、擋下原因、接續任務編號;接續關係表可以雙向查。
- 指標與告警屬 Phase 9,這個階段不做。

### 版本檢查、新鮮度、冪等的分工(寫進 [[Systems/分析行程流程與檢查點]] 與 [[Systems/執行迴圈]])

- 版本檢查(執行端):決策形成時看到的廣告版本,跟執行當下的版本一樣才寫;不一樣就擋下。防的是「根據過時現況做的決策覆蓋新值」。
- 新鮮度(分析端):證據夠不夠新、版本有沒有變,決定能不能拿來分析;防的是「用過期證據做決策」。
- 冪等(執行端與 DSP):同一個操作重送只套用一次;防的是「同一個決策被套用兩次」。三者互補,不能互相取代:冪等擋不住舊決策覆蓋新值(那是不同的操作),版本檢查擋不住重送(同一版本重送兩次)。

### 不做的事

- 不改任務狀態機(使用者裁定 B)。
- 不做過期、死信、其他擋下原因的自動重新規劃(只做版本已變,F4 的範圍)。
- 不做分析行程的啟動程式與多任務排程;接續任務由呼叫端推進,跟原任務一樣。
- 不做指標與告警(Phase 9)。
