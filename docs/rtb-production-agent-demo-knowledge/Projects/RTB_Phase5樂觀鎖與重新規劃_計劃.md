# RTB_Phase5樂觀鎖與重新規劃_計劃

PRIOR-ART: 樂觀鎖衝突後「重讀現況、重新決策」是樂觀並行控制的標準處理(HTTP 的 If-Match/412、資料庫的 compare-and-swap 失敗後重試讀改寫);本專案的版本比對兩層已經做完(執行前檢查、DSP 端預期版本),缺的只是衝突後的回報與重新規劃。重新規劃沿用「一次決策一個任務」的既有狀態機:原任務結案,另開一個接續任務,不改狀態機的終點規則。
RETIRE-IF: 換成外部工作流引擎(它自己管重試與重新規劃)時,撤掉接續任務這套機制。

## 這份計劃在解決什麼

- 事故 F4(交接文件第 16 節):提案形成之後,另一方先更新了廣告。執行時帶著舊預期版本的寫入要被拒、不能覆蓋較新的值,而且系統要重新取現況再規劃。
- 範圍:交接文件 Phase 5「Optimistic Locking 與 Concurrency」。完成條件:F4 通過;並行寫入的測試能重現衝突;舊提案不覆蓋較新狀態;衝突可查(軌跡、稽核);文件講清楚版本檢查、新鮮度、冪等三者的分工。
- 預告合約 [[Verification/事故F4_舊版本寫入被拒不覆蓋]](最遲 2026-12-15)是這個階段要轉正的合約。它的摘要寫「把觀察到的版本一路帶進執行寫入、衝突後重新規劃屬 Phase 5,還沒開工」,核對後前半句不準:版本已經一路帶進執行寫入(見現況),真正沒做的只有衝突後重新規劃。開工時照程式訂正那句摘要。

## 最小設計(第 2 版:已折入第 1 輪設計審)

- **狀態(2026-09-23):設計中**。

### 真相從哪裡來:先問 DSP,再問收件口

- 「決策有沒有真的寫進 DSP」問 DSP 本身:用提案算出的冪等鍵(執行端寫 DSP 用的同一把,由領域層的同一支函式算)查 DSP 的操作紀錄。查到就是寫進去了,這件事不會因為時間過去而消失。分析端的 DSP 用戶端新增這一個唯讀查詢(DSP 已經有這個端點),照分析端讀 DSP 既有的白名單與大小上限做。
- 收件口只用來問「為什麼沒寫」:它的處置與擋下原因只在收件表保留期(2 小時)內存在,保留期一過整個任務被清掉,重送只會拿到過期或修訂不連號(第 1 輪架構對齊席、外家席:只靠收件口,已經成功的任務會在保留期後被誤判成過期擋下,已記下的版本衝突也會被抹掉)。
- 所以判斷順序是:先查 DSP;DSP 沒有這筆,才重送提案問收件口。

### 執行端:DSP 端的版本衝突也回報成「版本已變」

- 版本衝突有兩層:執行前檢查發現(收件表記版本已變),或檢查通過後、寫入前被另一方搶先改(DSP 回 409,嘗試紀錄記版本衝突)。第二層現在確認時一律寫成「同一操作先前已失敗」,把原因蓋掉(第 1 輪外家席、銜接席、可測性席、處置對照席各自抓到)。
- 改成:嘗試結果是版本衝突時,確認寫「版本已變」;其他失敗照舊寫「同一操作先前已失敗」。開始一筆撞到既有失敗的鍵時同樣依既有嘗試的結果代碼分流。這改到 Phase 3、4 已完成的確認寫法,列在「被取代的既有合約」。

### 收件口回報擋下原因

- 收件口對重送的回應本文多帶「擋下原因」(只有處置是已擋下時才有值)。收件表本來就存著。
- 分析端的收件口用戶端讀回應本文的處置與擋下原因,放進「已收下」結果;新欄位都有預設值(空),既有只看有沒有收下的呼叫端與測試替身不受影響(第 1 輪可測性席:五處測試用單一參數建構這個結果)。

### 分析行程:已交給執行之後的下一步

- 推進函式現在對「已交給執行」寫死了直接返回(不只是缺一個步驟函式),要拿掉這個提前返回、補上步驟函式(第 1 輪 F4 席)。既有一支測試斷言「交接後推進不會再送第二次」,語意上被這一步取代,列在「被取代的既有合約」。
- 這一步照 Phase 4 增量 3b 的任務租約走(先取得租約才呼叫外部)。依序:
  1. 查 DSP 的操作紀錄:查到 → 任務轉完成。
  2. 查詢失敗(逾時、斷線、讀不懂)→ 這一輪沒有進展,回原狀態。
  3. DSP 沒有這筆 → 重送提案問收件口,依結果:

| 收件口回的 | 任務怎麼走 |
|---|---|
| 已交給執行(DSP 卻沒有這筆:不該發生) | 轉擋下,記「處置與 DSP 不一致」,不重新規劃,留給人看 |
| 處理中、待處理 | 這一輪沒有進展 |
| 已擋下,原因版本已變 | 重新規劃(接續任務) |
| 過期(處置),或拒收「提案已過期」「修訂不連號」(保留期已清掉) | 重新規劃:決策已經過期,本來就該重讀現況再決定(第 1 輪外家席) |
| 已擋下的其他原因、死信 | 轉擋下,記處置與原因,不重新規劃(死信重放是 Phase 8) |
| 被新修訂取代 | 轉被取代(目前只能用替身觸發:每個任務永遠只送修訂 1,是防線) |
| 拒收「內容衝突」或其他永久拒收 | 轉擋下,記原因(防線:同一份快照重送不該發生) |
| 收件口忙碌、其他未定義失敗、網路失敗 | 這一輪沒有進展(照「送出提案」那一步既有慣例,第 1 輪處置對照席) |

- 收件口的「提案已過期」「修訂不連號」「內容衝突」在分析端用戶端被歸成同一種例外,旁邊「送出提案」那一步把它處理成退回蒐證;這一步**不能**照抄——已交給執行退回蒐證違反狀態機(第 1 輪 F4 席)。這一步要看拒收代碼分流。

### 重新規劃:接續任務

- 接續任務編號由原任務編號算出、固定長度、放在保留的命名空間:「fu-」加原任務編號雜湊的前 24 個十六進位字元。不再用字串拼接(第 1 輪外家席、接續任務席、銜接席:拼接會撞到呼叫端自己取的名字、會超過 128 字元上限,公式和範例也對不上)。一般的建任務拒絕「fu-」開頭的編號,這個命名空間只給接續任務用。
- 建接續任務與寫接續關係是同一個交易:任務的第一列與接續關係表一列(原任務編號為主鍵、接續任務編號、代數)一起寫。重跑時看到原任務已有接續關係就直接用它,不再寫(第 1 輪架構對齊席、接續任務席、可測性席:關係表沒有去重,重跑會重複寫或丟主鍵衝突的例外)。接續任務編號已存在、卻沒有指到這個原任務的接續關係 → 不建立,原任務轉擋下並記「接續編號衝突」(防線)。
- 先建接續(含關係)、再把原任務轉擋下;兩步之間當機,重跑時第一步看到已有關係直接沿用,第二步照常結案。原任務擋下那一列的錯誤說明寫上接續任務編號。
- 代數記在接續關係表:原任務自己沒有接續關係就是第 1 代,接續任務的代數是原任務代數加 1。代數上限暫用 3,達到就不再接續、原任務只轉擋下並記「重新規劃次數用完」。

### 版本檢查、新鮮度、冪等的分工(寫進 [[Systems/分析行程流程與檢查點]] 與 [[Systems/執行迴圈]])

- 版本檢查(執行端):決策形成時看到的廣告版本,跟執行當下的版本一樣才寫;不一樣就擋下。防的是「根據過時現況做的決策覆蓋新值」。
- 新鮮度(分析端):證據夠不夠新、版本有沒有變,決定能不能拿來分析;防的是「用過期證據做決策」。
- 冪等(執行端與 DSP):同一個操作重送只套用一次;防的是「同一個決策被套用兩次」。三者互補,不能互相取代:冪等擋不住舊決策覆蓋新值(那是不同的操作),版本檢查擋不住重送(同一版本重送兩次)。這個階段還多了一件:冪等鍵同時是分析端查「有沒有寫進去」的鑰匙。

### 被取代的既有合約

- 執行端確認時,嘗試因版本衝突失敗一律寫「同一操作先前已失敗」:改成寫「版本已變」(Phase 3 增量 3 的鍵已存在分流、Phase 4 增量 1 的終點確認)。既有斷言「同一操作先前已失敗」的測試逐支核對:由版本衝突觸發的改驗新代碼,其他失敗維持。
- 分析行程「交接後推進不會再送第二次」那支測試(tests/analyzer/test_flow.py 當機後重跑那支):語意被 [S301] 取代,改驗「交接後推進會查 DSP、必要時重送同一份快照」。
