# RTB_Phase5樂觀鎖與重新規劃_計劃

PRIOR-ART: 樂觀鎖衝突後「重讀現況、重新決策」是樂觀並行控制的標準處理(HTTP 的 If-Match/412、資料庫的 compare-and-swap 失敗後重試讀改寫);本專案的版本比對兩層已經做完(執行前檢查、DSP 端預期版本),缺的只是衝突後的回報與重新規劃。重新規劃沿用「一次決策一個任務」的既有狀態機:原任務結案,另開一個接續任務,不改狀態機的終點規則。
RETIRE-IF: 換成外部工作流引擎(它自己管重試與重新規劃)時,撤掉接續任務這套機制。

## 這份計劃在解決什麼

- 事故 F4(交接文件第 16 節):提案形成之後,另一方先更新了廣告。執行時帶著舊預期版本的寫入要被拒、不能覆蓋較新的值,而且系統要重新取現況再規劃。
- 範圍:交接文件 Phase 5「Optimistic Locking 與 Concurrency」。完成條件:F4 通過;並行寫入的測試能重現衝突;舊提案不覆蓋較新狀態;衝突可查(軌跡、稽核);文件講清楚版本檢查、新鮮度、冪等三者的分工。
- 預告合約 [[Verification/事故F4_舊版本寫入被拒不覆蓋]](最遲 2026-12-15)是這個階段要轉正的合約。它的摘要寫「把觀察到的版本一路帶進執行寫入、衝突後重新規劃屬 Phase 5,還沒開工」,核對後前半句不準:版本已經一路帶進執行寫入(見現況),真正沒做的只有衝突後重新規劃。開工時照程式訂正那句摘要。

### 真相從哪裡來:先問收件口,收件口清掉了才問 DSP

- 收件口的處置是執行端**驗證過**的結果:只有嘗試走到「已驗證」才確認成已交給執行;寫入後重讀不符會轉人工,轉人工的列一直算處理中。DSP 有操作紀錄只代表「寫進去了」,不代表驗證通過(第 2 輪外家席)。所以第一個問的是收件口:把存著的那份提案快照原樣重送,讀回應本文的處置與擋下原因。
- 收件口只在一個任務「沒有待處理也沒有處理中、而且最後一次收件超過保留期(2 小時)」時整個清掉。清掉之後重送只會拿到「提案已過期」或「修訂不連號」的拒收。只有這時才去問 DSP(第 1 輪架構對齊席、外家席:只靠收件口會把成功誤判成過期)。
- 為什麼這個順序沒有競態:收件口清掉一個任務時,執行端早就處理完了(處理中與轉人工都不會被清),DSP 那邊不會再有新寫入。第 2 版「先查 DSP、再問收件口」兩次查詢中間,執行端可以剛好寫完並確認,正常時序會被誤判成不一致(第 2 輪 s2 席、外家席),第 3 版的順序沒有這個空檔。
- 被清掉之後 DSP 查得到、而且內容相符 → 一定是已交給執行:轉人工不會被清;寫入被 DSP 拒絕不會有操作紀錄;作廢的鍵沒有操作紀錄。所以轉完成是安全的。
- 被清掉之後 DSP 查不到 → 從來沒寫進去,但已經分不出當初是版本已變、過期、其他擋下、還是死信。這時**重新規劃**,接續任務的錯誤說明記「結果已過保留期、DSP 沒有寫入」(第 3 輪 s2 席、外家席:收件口在重送時會先把過了保留期的已結案任務清掉,執行前檢查擋下的版本已變只記在收件表;第 3 版在這裡不重新規劃,只要分析端晚兩小時才推進,F4 的版本衝突就永遠不會重新規劃)。
  - 為什麼安全:決策從來沒寫進 DSP,接續任務會重讀現況、用當下版本重新決策,執行端照樣做版本檢查;最壞情況是一個本來會被擋下的提案(例如超過預算上限)再被擋一次,受代數上限約束,整條鏈最多 3 代(原任務加兩次重做)。
  - 代價:收件表還留著時,死信與其他擋下不重新規劃;清掉之後會。兩者不一致,但清掉之後本來就分不出原因,選「重讀現況再決定」比「全部交給人」更貼近 F4 的要求。

### 用哪一把鍵查 DSP、查到後核對什麼

- 冪等鍵一旦用過就只用存下來的那把,不從提案重算(嘗試紀錄那一側的既有規則;算法改版時前綴會換)。分析端在任務轉「已交給執行」的那一列,一併存下用領域層函式算出的冪等鍵(任務表新增一個可空欄位,舊資料庫開啟時補欄,比照既有的補欄做法)。之後查 DSP 一律用這把存下的鍵(第 2 輪外家席)。
- 舊列(Phase 5 之前就交給執行的任務)沒有存鍵:從提案用目前的函式算。這只在冪等鍵算法還是第一版(前綴 k1-)時正確;用一支測試把「目前前綴是 k1-」釘住,改算法的那次改動會先撞到這支測試,測試訊息寫明要先替舊列回填鍵(第 3 輪 s1、s2 席:第 3 版承諾記進實務隱患卻沒記)。
- DSP 查得到時,要核對操作紀錄的廣告編號、動作、新預算、預期版本跟提案一致,跟執行端既有的對帳核對同一組欄位。任何一項不符 → 轉擋下記「冪等衝突」,不轉完成(第 2 輪外家席:查到不等於是這份提案寫的)。
- 分析端的 DSP 用戶端新增這一個唯讀查詢(依冪等鍵查操作,DSP 已經有這個端點),照分析端讀 DSP 既有的白名單、大小上限做;查詢不存在回 404 是「查不到」,其他失敗是「查詢失敗」。
- 呼叫紀錄:這個查詢跟既有的讀現況、讀指標一樣,由記錄外部呼叫的那層包起來寫進呼叫紀錄表,用戶端本身不碰任務模組(第 2 輪架構對齊席;分析行程筆記既有規則)。重送收件口本來就經過那層。

### 推進函式怎麼拿到新的查詢

- 推進函式新增一個具名參數「操作查詢」,預設是空。沒有給 → 已交給執行的任務照 Phase 4 的行為直接返回,不呼叫任何協作者;有給 → 走下面那一步(第 2 輪 s1 席:推進函式目前的三個協作者沒有一個扮得了這個角色,直接改簽章會牽動八十多個呼叫點)。
- 怎麼接進既有結構(第 3 版沒寫,第 3 輪架構對齊席):
  - 推進函式開頭那行「終點或已交給執行就直接返回」拆開:終點照舊返回;已交給執行只在沒給操作查詢時返回。
  - 協作者組合多一個可選欄位「操作查詢」;步驟分派表多一格「已交給執行」,跟其他四步一樣走同一段「先取租約、呼叫、帶收據提交、失敗放租約」的共用程式,不另開一條路。其他四步不讀這個欄位。
- 好處:既有的兩支「交接後推進不會再呼叫協作者、不會再送第二次」的測試不用改,仍然成立(沒給查詢時);Phase 5 的新測試都給查詢。被取代的既有合約因此少一條。
- 壞處:呼叫端忘了給查詢,任務會像今天一樣停在已交給執行。這跟今天的行為一樣,不是新的退步;分析行程還沒有啟動程式,等接上時要記得給。

### 執行端:DSP 端的版本衝突也回報成「版本已變」

- 版本衝突有兩層:執行前檢查發現(收件表記版本已變),或檢查通過後、寫入前被另一方搶先改(DSP 回 409,嘗試紀錄記版本衝突)。第二層現在確認時一律寫成「同一操作先前已失敗」,把原因蓋掉(第 1 輪四席)。
- 改成:嘗試結果是版本衝突時,確認寫「版本已變」;其他失敗照舊寫「同一操作先前已失敗」。一共**三處**寫死同一個代碼,三處都改(第 2 輪 s1、s2 席抓到第三處):
  - 執行端確認終點時。
  - 執行端開始一筆、撞到既有失敗的鍵時。
  - 收件口取件時發現這把鍵已經有嘗試紀錄(當機後重新投遞、或同一把鍵兩張收據)。這一處現在只拿到嘗試狀態、拿不到結果代碼,要把結果代碼一起傳進去。
- 三處共用一個小函式「失敗嘗試對應的擋下原因」,不各寫一份。

### 收件口回報擋下原因

- 收件口對重送的回應本文多帶「擋下原因」(只有處置是已擋下時才有值)。收件表本來就存著。
- 分析端的收件口用戶端讀回應本文的處置與擋下原因,放進「已收下」結果;新欄位都有預設值(空),既有只看有沒有收下的呼叫端與五處測試替身不受影響。

### 分析行程:已交給執行之後的下一步(有給操作查詢時)

- 照 Phase 4 增量 3b 的任務租約走(先取得租約才呼叫外部)。先重送提案問收件口。
- 收件口回應本文帶的任務編號、修訂、內容雜湊,必須跟送出的快照一致,處置與擋下原因的組合也必須合法(只有已擋下才有原因);任何一項不符都當成「查詢失敗」,這一輪沒有進展(第 3 輪外家席:不核對的話,一份屬於別的提案的回應就能替這個任務結案)。

| 收件口回的 | 任務怎麼走 |
|---|---|
| 已交給執行 | 轉完成 |
| 處理中、待處理 | 這一輪沒有進展 |
| 已擋下,原因版本已變 | 重新規劃(接續任務) |
| 過期(處置;收件表還留著) | 重新規劃:決策過期,本來就該重讀現況再決定(第 1 輪外家席) |
| 已擋下的其他原因、死信 | 轉擋下,記處置與原因,不重新規劃(死信重放是 Phase 8) |
| 被新修訂取代 | 轉被取代(目前只能用替身觸發:每個任務永遠只送修訂 1,是防線) |
| 拒收「提案已過期」「修訂不連號」(收件表已清掉) | 去問 DSP,見下表 |
| 拒收「內容衝突」或其他永久拒收 | 轉擋下,記原因(防線:同一份快照重送不該發生) |
| 收件口忙碌、其他未定義失敗、網路失敗 | 這一輪沒有進展(照「送出提案」那一步既有慣例) |

- 收件表已清掉時用存下的鍵查 DSP:

| DSP 回的 | 任務怎麼走 |
|---|---|
| 查得到、內容相符 | 轉完成 |
| 查得到、內容不符 | 轉擋下,記冪等衝突 |
| 查不到 | 重新規劃(接續任務),記「結果已過保留期、DSP 沒有寫入」 |
| 查詢失敗 | 這一輪沒有進展 |

- 收件口的「提案已過期」「修訂不連號」「內容衝突」在分析端用戶端被歸成同一種例外,旁邊「送出提案」那一步把它處理成退回蒐證;這一步**不能**照抄(已交給執行退回蒐證違反狀態機),要看拒收代碼分流。

### 重新規劃:接續任務

- 接續任務編號由原任務編號算出、固定長度、放在保留的命名空間:「fu-」加原任務編號雜湊的前 24 個十六進位字元。
- 保留命名空間怎麼守(第 2 輪 s3 席:只有一個建任務入口,照字面加檢查會連接續任務自己都擋掉):
  - 一般的建任務入口拒絕「fu-」開頭的**任務編號**;這條只加在建任務入口對任務編號那一個參數,不改全專案共用的識別碼格式檢查(第 3 輪架構對齊席:那支檢查同時管廣告編號、證據編號、可信證據裡的短代號,掛在那裡會誤擋無關的值)。
  - 任務模組新增一支「建接續任務」,只從推進函式呼叫;它自己寫第一列,不經過一般入口的命名空間檢查(格式檢查照做)。

### 版本檢查、新鮮度、冪等的分工(寫進 [[Systems/分析行程流程與檢查點]] 與 [[Systems/執行迴圈]])

- 版本檢查(執行端):決策形成時看到的廣告版本,跟執行當下的版本一樣才寫;不一樣就擋下。防的是「根據過時現況做的決策覆蓋新值」。
- 新鮮度(分析端):證據夠不夠新、版本有沒有變,決定能不能拿來分析;防的是「用過期證據做決策」。
- 冪等(執行端與 DSP):同一個操作重送只套用一次;防的是「同一個決策被套用兩次」。三者互補,不能互相取代:冪等擋不住舊決策覆蓋新值(那是不同的操作),版本檢查擋不住重送(同一版本重送兩次)。這個階段還多了一件:收件表清掉之後,冪等鍵是分析端查「有沒有寫進去」的鑰匙。

### 被取代的既有合約

- 執行端確認時,嘗試因版本衝突失敗一律寫「同一操作先前已失敗」:三處都改成寫「版本已變」。既有斷言「同一操作先前已失敗」的測試逐支核對:由版本衝突觸發的改驗新代碼,其他失敗維持。
- 分析行程兩支「交接後推進不再呼叫協作者/不再送第二次」的測試:**不取代**,在沒給操作查詢時仍然成立(見上)。

### 不做的事

- 不改任務狀態機(使用者裁定 B)。
- 收件表還留著時,死信不自動重新規劃(Phase 8);清掉之後分不出原因,統一重新規劃(見上)。
- 不做分析行程的啟動程式與多任務排程;接續任務由呼叫端推進,跟原任務一樣。
- 不做告警與儀表板(Phase 9)。
