# RTB_Agent_Phase0架構

PRIOR-ART: 最小解是「行程內函式加本地檔案」,但它測不出外部寫入的真實失敗;世界上已有現成的至少一次佇列與伺服器型資料庫,但本專案是教學與驗證用 Demo,自建的部分只限「能重現失敗語意」的最小替身。執行期只用 Python 標準函式庫(sqlite3、http.server、urllib);開發期工具 pytest 與 ruff 是明確的例外,見決策 d6、d8。
RETIRE-IF: 若 Phase 1 到 Phase 4 做完後,SQLite 模擬的佇列與獨立行程 DSP 仍抓不到任何一個 F1 到 F3 事故,而換成真實外部系統才抓得到,這套替身就該換掉。
RETIRE-IF: 「執行期只用標準函式庫」這條例外邊界,以一支掃描測試機械檢查(見 Phase 1 驗收);該測試若連續出現誤報而被跳過,就代表邊界失守,要重審例外清單。
RETIRE-IF: pytest 這個例外,若 Phase 1 到 Phase 4 的測試裡從未用到參數化或 fixture 的優勢,就換回標準函式庫的 unittest 以恢復零依賴。

## 這份計劃在解決什麼

- 名詞:DSP 是廣告需求方平台,也就是真實世界裡實際接受改預算、暫停廣告的外部系統,本專案用模擬器代替;CTR 是點擊率、CVR 是轉換率、ROAS 是廣告投資報酬率、Pacing 是預算花費進度,都由純程式計算。EXTERNALLY-MANAGED 是 Python 安裝目錄裡的標記檔,代表這個 Python 由系統套件管理器管理,不准 pip 直接安裝套件。
- 專案來源是交接文件 `~/Downloads/RTB_PRODUCTION_AGENT_DEMO_HANDOFF.md`(在 repo 之外,計劃引用它的章節號),目標是做一個能在逾時、當機、重送、並行、提示注入、過期 DLQ 決定與總曝險下安全運作的廣告 Agent,並用證據清單加機械式檢查程式證明。
- 這一篇只管 Phase 0:定最小架構、信任邊界、決策紀錄,並約定 Phase 1 的範圍。**不含任何程式碼。**

## 元件與信任邊界

```
   即時流程畫面 / 指標後台(只讀:兩個資料庫檔都用唯讀模式開,DSP 走它的唯讀查詢介面)
        │ 讀                                   │ 讀 DSP 查詢介面
        ▼                                      ▼
  ┌── 分析行程 ──────────────────┐   ┌── 執行行程 ─────────────────────────┐
  │ 自己的 SQLite:任務佇列、證據、 │   │ 自己的 SQLite:提案佇列、嘗試中、     │
  │ 提案、事件                    │   │ 額度、結果、稽核、事件               │
  │ 持有:模型金鑰、DSP 讀取令牌   │   │ 持有:簽章金鑰、能力憑證簽發          │
  │ 沒有:任何寫入相關的金鑰       │   │ 政策閘=這個行程內的函式庫            │
  │                              │   │ 自己讀提案(對方的檔,唯讀),不信任它, │
  │ 只產出「提案」──────────────────▶ │ 自己重讀 DSP 現況、自己重跑整套檢查   │
  └──────┬───────────────────────┘   └──────┬────────────────┬────────────┘
         │ HTTPS                            │ HTTP(業務介面)   │ 讀核准
         ▼                                  ▼                  ▼
     模型 API(外部)        ┌── Mock DSP(獨立行程,自己的儲存)─┐  核准檔(獨立 SQLite,
                           │ 業務介面:廣告狀態 / 版本 /        │  由核准指令寫入、簽章)
   測試程式碼 ─(帶故障標頭)─▶│         操作紀錄 / 冪等鍵紀錄     │
                           │ 故障注入:啟動旗標開啟才接受標頭    │
                           └───────────────────────────────────┘
```

- **行程切分(已決,決策 d9):** 分析與執行是兩個獨立行程。
  - 資料所有權:每個行程擁有自己的 SQLite 檔,對方只能用唯讀模式讀。分析行程的檔裡有任務佇列、證據、提案;執行行程的檔裡有提案佇列、嘗試中紀錄、額度、結果與稽核。這樣分析行程不能改寫額度、嘗試中或稽核。
  - 提案怎麼交過去:分析行程把提案寫進自己的檔;執行行程以唯讀方式讀到提案,把它登記進自己的提案佇列,之後全部以自己的檔為準。任務狀態也一分為二:提案產生前歸分析行程,之後的操作狀態歸執行行程。交接細節(領取、去重、交接後的分析端如何得知結果)在 Phase 3 開工前定稿,事件入口就是 Phase 3 的設計審。
  - 金鑰只傳給該持有的行程(例如透過環境變數),分析行程的環境與可讀檔案裡不含簽章金鑰與寫入相關憑證。
  - 這個切分的限制:Demo 裡兩個行程仍是同一個作業系統使用者,所以「分析行程讀不到簽章金鑰」靠的是金鑰只傳給執行行程,不是作業系統的帳號隔離。作業系統層級的隔離(不同帳號、容器)列入已知限制。
- **不可信的輸入**:廣告名稱、素材文字、落地頁、DSP 中繼資料、工具回傳內容。一律當資料,不能變成權限。這條同時管兩個方向:
  - 往決策的方向:不能變權限。
  - 往顯示的方向:進事件表時帶信任標記與來源,顯示層跳脫並限制長度。
  - 工具回傳的型別化解析、大小限制、白名單正規化(交接文件第 12 節)與 Evidence 層的 provenance 與信任分類,留到 Phase 7 補;事件層的信任標記從 Phase 2 起先固定。
- **可信的來源**:政策引擎的規則、由執行端從可信上下文綁定的租戶身分(tenant)、資源身分、金額上限與有效期。
- **授權閘的位置**:授權閘是執行行程內的函式庫。分析端只產出提案,提案是不可信輸入;執行端拿到提案後,用自己的讀取令牌重新讀 DSP 現況,自己重跑整套檢查,通過才發出寫入。這就是交接文件第 5 節說的「執行端只驗證並執行獲授權動作」。
- **寫入能力(capability)**:DSP 的寫入令牌不是單一個「寫」,而是由政策閘簽發、綁定租戶、廣告、動作、金額上限、有效期與政策版本的憑證,DSP 驗證簽章與範圍才執行(交接文件 11.1 節)。分析端沒有簽發金鑰。這在 Phase 3 開頭(Side Effect Gate 之前)實作,Phase 1 的 DSP 不含令牌驗證。
- **Phase 3 到 5 之間的閘**:閘採「關閉式預設」,尚未實作的檢查一律回傳 BLOCK;這幾個階段的寫入只在測試環境、且明確使用測試政策時才會放行,測試政策的放行清單寫在測試裡。這樣「所有寫入都通過第 8 節的檢查」這句話在每個階段都不是假的。
- **DSP 是外部事實來源**:agent 只能走公開介面加查詢介面。「不能開 DSP 的儲存檔案、不能 import DSP 的內部模組」寫成掃描測試:掃 agent 端程式的匯入與檔案路徑,發現就紅。這支測試在 agent 端第一次有 DSP 客戶端時才有意義,所以從那一階段開始驗收,並在之後每個階段重跑。
- **故障注入怎麼隔離**:不另開連接埠。故障模式由請求標頭指定(以單一請求為單位,避免全域狀態讓並行請求互相污染),而且 DSP 必須用啟動旗標開啟故障注入才會接受這個標頭;旗標關閉時收到標頭一律回 400 且不改任何狀態。DSP 只綁定本機回送位址。agent 端的客戶端程式碼不會設定這個標頭,由掃描測試證明。
- **唯讀怎麼保證**:畫面與後台以唯讀模式(SQLite URI 的 mode=ro)開啟 agent 的資料庫,搭配 WAL,讓讀者不擋寫入者;要看 DSP 操作歷史時,走 DSP 的唯讀查詢介面,不讀它的儲存檔案。
- **核准通道(HITL)**:核准存在獨立的「核准檔」(另一個 SQLite 檔),不與 agent 資料庫同檔。每筆核准帶簽章,簽章金鑰只有核准指令與執行端持有,分析端沒有;紀錄綁定核准者身分、動作範圍、租戶與資源、金額上限、提案雜湊、政策版本與有效期。執行端驗簽與有效期才採信。核准者身分在 Demo 裡是本機操作員帳號,不是真正的身分認證,這一點寫進已知限制。實作在 Phase 6。
- **分析端會對外連線**:分析端要呼叫模型 API,所以「agent 不連任何外部網路」只描述 Phase 0 與 Phase 1 的狀態。分析端持有模型金鑰與 DSP 讀取令牌,它處理不可信文字,所以它的環境變數與可讀檔案範圍要限縮,寫入相關的金鑰不放在它可讀的位置,並列入 Phase 7 的注入測試。

### 七項元件各自的最小設計

- **State store(狀態儲存):** 一個 SQLite 檔。任務狀態用一張明確的轉換表定義哪些轉換合法;檢查點只記「可安全恢復的進度」,不代表外部事實。
- **Queue(佇列):** 有兩段,各在自己行程的資料庫裡:任務佇列由分析行程領取,提案佇列由執行行程領取。兩段的機制相同:用資料表模擬至少一次投遞。訊息有唯一的一把 `lease`(到期時間加 lease 序號)和 `attempt` 計數;這把 lease 同時管佇列訊息與「嘗試中」紀錄,不存在兩把。超過重試上限或永久錯誤才進 DLQ 表並保留失敗脈絡與 trace 連結;**結果不明的操作不計入重試上限、不得直接進 DLQ**,必須先對帳結案,或在 DLQ 信封上明確標記結果不明。
  - **ACK 規則:** 把訊息標為已處理,與寫入 durable 結果放在同一個交易。要注意這只涵蓋本地那一半:「DSP 已提交、本地結果還沒寫」的危險視窗不在這個交易裡,它由「嘗試中」紀錄加對帳來處理。
- **Mock DSP:** 見上圖與 Phase 1。
- **Analysis(分析):** 依交接文件第 4 節分流:確定性計算與規則走純程式;模糊的多證據推理才給 LLM;外部資訊與動作走工具。分析端只輸出符合 schema 的提案。LLM 的失敗一律走回退(重試、降級、轉人工),不放行。
- **Policy(政策):** 交接文件第 8 節的十一項檢查分兩類:
  - 執行前的判斷(權限、guardrail、新鮮度、版本、冪等、總曝險、HITL 是否有效等)是純函式,需要 DSP 或資料庫現況時,現況由執行端讀好以參數傳入,或透過小型介面注入,政策本身不 import sqlite3。
  - 執行後驗證(第 10 項)與稽核(第 11 項)是執行端的步驟,不屬於執行前政策。
  - 總曝險預留是一張以「租戶、批次、時間窗、政策或模型 rollout」為鍵的額度表;預留動作本身是資料層的一個單一寫入交易,由政策呼叫、不在政策內。
  - **預留的生命週期:** 預留在送出前建立;成功後轉為已用;確定失敗才釋放;**結果不明時維持占用,直到對帳結案**,避免 DSP 其實已套用的變更被算成沒用掉額度而讓並行 worker 超額。
- **Execution(執行):** 呼叫前先提交「嘗試中」紀錄;呼叫期間不持有交易;寫入一律帶預期版本;結果不明時走對帳,期間對同一廣告加互斥。細節見下節。
- **Observability(可觀測):** 每個邏輯任務一個 `trace_id`,兩個行程各自的事件表都帶它,畫面與後台把兩邊的事件依 `trace_id` 串起來;事件表欄位含 `trace_id`、`task_id`、`tenant_id`、`campaign_id`、`decision_id`、`operation_id`、`idempotency_key`、`worker_id`、`attempt`、`policy_version`、`trust_class`(信任標記)、`source`(來源)。稽核表只追加、不修改。指標標籤只用低基數欄位(租戶、工具、錯誤類別、階段),`campaign_id` 與 `trace_id` 留在事件裡不進指標標籤。

## 外部寫入的失敗語意(交接文件 18.3 節的答案要點)

- **冪等鍵怎麼產生:** 由 `tenant_id`、`task_id`、`campaign_id`、動作類型與正規化後的 payload 決定性導出(雜湊),不是隨機值。同一個邏輯操作無論重送、重試、重跑,拿到的永遠是同一把鍵。**DLQ 重放與重新領取沿用原本的 `task_id`**(建立新的 attempt,不建立新的 task),否則會得到新鍵而失去 DSP 的冪等保護。
- **「嘗試中」表:** 對邏輯操作有唯一約束;第二個 worker 或重送的插入撞到唯一鍵時,取回舊紀錄、不新增,並**依舊紀錄的狀態分支**:結果不明就走對帳、進行中就等、已結案就直接採用;絕不在取回後直接再發一次 HTTP。
- **payload 變了:** 重新分析後內容不同,鍵就不同,視為新的邏輯操作,舊提案標記為過期。DSP 端對同鍵不同內容會拒絕。agent 端也放一道同樣的守衛,但因為鍵已含 payload 雜湊,它實際守的是雜湊碰撞與實作錯誤,不是常態路徑,只能靠人為注入來測。
- **交易邊界:** 「寫嘗試中」是一個短交易,提交後才發 HTTP 請求;「寫結果」是另一個短交易。**HTTP 呼叫期間不得持有任何開著的交易**,否則延遲回應會鎖住所有其他寫入者,而且回滾會抹掉「嘗試中」紀錄。每個 worker 用自己的連線,設定 WAL、`busy_timeout`,**所有寫入交易一律用 `BEGIN IMMEDIATE` 開始**(延遲交易升級寫入會直接回 `database is locked`,已實測)。
- **owner、lease 與 fencing:**
  - 紀錄帶 owner 與 lease(到期時間加序號)。lease 必須長於「DSP 呼叫逾時上限加安全邊際」,並有續期機制,讓延遲回應不會把活著的 worker 變成疑似當機。
  - **寫結果與 ACK 一律以條件更新進行:** 條件包含 key、owner 與 lease 序號;更新到 0 列就放棄這次寫入並進入對帳。這樣 lease 到期後才醒來的原 worker 不能覆蓋接手者的結果、也不能 ACK 掉已被重新投遞的訊息。
  - 別的 worker 看到「有開始沒結果」時,先確認 lease 已到期才可接手對帳。
- **結果不明期間暫停同範圍寫入(交接文件 7.3 節第 2 步):** 只要某個廣告存在結果不明的操作,對同一廣告的其他寫入必須等待或被序列化;寫入一律帶預期版本,作為 DSP 端的最後防線。
- **對帳判定表**(細節在 Phase 3 前定稿,並要先答完交接文件 18.3 節的十題):
  - DSP 查得到同鍵且成功 → 標記成功,驗證實際狀態符合意圖。
  - DSP 查得到同鍵且被拒 → 標記失敗,依錯誤類別處理。
  - DSP 查無此鍵 → 不能直接當成沒做(請求可能還在途)。等待窗口必須大於「DSP 最大處理時間加客戶端逾時加時鐘誤差」,窗口過後才判定;判定後如果要重送,**必須先重跑完整授權閘**(決策有效期、核准有效性、額度、政策版本),通過才以**同一把鍵**重送,由 DSP 冪等擋住重複。
  - DSP 版本已被別人推進 → 舊提案過期,重新讀取並重新分析,不強制覆寫。
  - 需要補償或放棄的情況 → 走 compensate 或 abandon,並升級人工。
  - 對帳查詢本身逾時 → 維持結果不明,超過上限升級人工。
- **來源:** DSP 的操作紀錄與目前狀態是事實來源,不是本地例外類型。

## 決策(細節與四欄在筆記的 decisions 欄位)

- WHY: agent 狀態存 SQLite。因為要靠交易讓「狀態、檢查點、稽核」一起提交,用唯一鍵擋重複冪等鍵,用版本欄位做樂觀鎖。出處:對話 2026-09-21。
- WHY: DSP 用獨立行程加 HTTP,儲存也獨立。因為共用資料庫或行程內呼叫,會讓「DSP 已寫入但 agent 沒收到回應」這個事故測不出來。出處:對話 2026-09-21。
- WHY: agent 呼叫外部系統前,先寫入並提交「嘗試中」紀錄(含冪等鍵)。因為沒有這筆紀錄,行程當掉後 agent 不知道曾經嘗試過,會用新鍵重做。出處:對話 2026-09-21。
- WHY: 即時畫面與後台只讀不寫指令。因為能觸發執行的介面會變成繞過安全檢查的第二條路。出處:對話 2026-09-21。
- WHY: 事件與狀態變更放同一個交易。因為稽核與畫面都要反映 agent 真正記下的事實,不是事後補的敘述;這條的理由來自交接文件 14.3 節的稽核要求,畫面只是額外受益者。出處:對話 2026-09-21。
- WHY: 測試用 pytest 加 .venv。出處:對話 2026-09-21,見 d6。
- WHY: 程式要乾淨、不寫成義大利麵,並接 ruff。出處:對話 2026-09-21,見 d7、d8。

## 程式結構原則(clean code)

- **純判斷和外部動作分開。** 「這個動作准不准做」是純函式,輸入資料、輸出結果,不碰網路和資料庫;真正去改 DSP、寫資料庫是另一層。理由是安全規則可以不啟動任何行程就測完(交接文件第 8 節)。
- **只在有需求的地方才切介面。** DSP 客戶端要切介面,因為測試需要替身;資料庫**不預先**切介面,因為本專案只有 SQLite 一種儲存,預先抽象是交接文件 18.5 節點名的多餘抽象。
- **依賴方向往內。** 領域規則與政策不 import 資料庫或網路模組;由 ruff 的禁用匯入規則檢查(它只能禁用指定的模組清單,見下)。
- **一個模組一件事。** 政策的檢查各是一個有名字的小函式;不寫上百行、滿是 if 的大函式。
- **狀態機是資料。** 合法的狀態轉換寫成一張表,不散落在各處的條件判斷。
- **命名說明意圖。** 例如「結果不明」,不叫 flag。
- **驗證方式與它的限制:**
  - ruff 能查:函式的敘述數上限、分支與複雜度上限、領域層的禁用匯入清單(例如 sqlite3、socket、http.client、urllib、以及模型客戶端)。
  - ruff 查不了:「只用標準函式庫」。這條靠一支掃描測試:用 Python 的 `sys.stdlib_module_names` 檢查執行路徑模組的頂層匯入,凡是不在標準函式庫也不是專案自己的模組就紅。
  - 沒有機械判準的部分(命名好不好、切分合不合理)留給設計審與代碼審。REVISIT:2026-11-21 回頭看命名與切分的問題是否在審查中反覆出現;若是,就補機械規則。

## Phase 1 範圍與驗收

- 範圍
  - 獨立行程的 Mock DSP(用 `ThreadingHTTPServer`),提供四個必要介面加冪等鍵查詢與廣告歷史查詢,以及型別化的錯誤(暫時性、永久、版本衝突可被呼叫端區分)。
  - 廣告版本單調遞增;記錄操作歷史、冪等鍵結果、收到時間、提交時間與回應行為。
  - DSP 的儲存持久化(重啟後冪等紀錄仍在);冪等紀錄與廣告狀態變更在 DSP 端放在同一個交易裡原子提交。
  - 故障注入:正常、提交前逾時、提交後逾時、延遲回應、暫時性 5xx、永久驗證錯誤、版本衝突、同鍵同內容重送、同鍵不同內容。以請求標頭指定,需啟動旗標開啟。
  - 純程式的指標計算:CTR、CVR、ROAS、Pacing,涵蓋零分母與缺資料。
  - 不使用 LLM 做任何確定性計算。
  - 開頭步驟:用 3.14 直譯器建 `.venv`(安裝套件需要下載,這是開發期的對外連線,不算 agent 執行期)、建立 `.gitignore`、固定 pytest 與 ruff 版本(依賴清單)、把 lumos 的測試指令改成指向 `.venv` 內的 pytest 並限定專案的測試目錄、補上 lumos 的 linter 宣告檔、先跑 http.server 最小實驗。
  - 不含:令牌驗證與能力憑證(Phase 3 開頭)、agent 端任何程式(Phase 2 起)。
- 驗收(每條都是機械斷言)
  - 四個必要介面加兩個查詢介面都有合約測試。
  - 每一種故障模式各有一條測試,涵蓋版本衝突、5xx、延遲回應;型別化錯誤可被區分。
  - 版本單調:連續多次操作後版本嚴格遞增;操作歷史每筆有收到時間與提交時間,且提交時間不早於收到時間。
  - 「提交前逾時」:呼叫端確實觀察到逾時,且 DSP 的操作歷史長度與版本都沒有增加。
  - 「提交後逾時」:呼叫端確實觀察到逾時,且 DSP 的操作歷史多一筆、版本加一,`getOperationByIdempotencyKey` 查得到成功結果。
  - 同鍵同內容重送:回傳原結果,預算與版本不變,歷史沒有第二筆。
  - 同鍵不同內容:被拒絕。
  - **並行同鍵只套用一次:** 用柵欄讓 20 個請求同時放行,並讓 DSP 在提交前延遲,確保請求必然在 DSP 內重疊;斷言歷史剛好一筆、版本加一、其餘回應都是重送結果;整組重複 50 次。另有一個「故意拿掉唯一約束」的對照實作,測試必須能抓出它的雙寫。同鍵不同內容並行時,其中一個必須被拒絕。
  - DSP 原子提交:在「改廣告狀態」與「寫冪等紀錄」兩步之間注入當機、重啟 DSP,不得出現「狀態已改但鍵紀錄不在」。
  - DSP 重啟後,冪等紀錄仍在。
  - 故障注入隔離(DSP 端):旗標關閉時收到故障標頭一律回 400 且不改狀態;DSP 只綁定本機回送位址。
  - 指標計算有正常值、零分母、缺資料、邊界值測試;指標計算模組沒有匯入任何模型客戶端(以 ruff 禁用匯入規則機械檢查)。
  - 「只用標準函式庫」掃描測試通過;ruff 檢查通過。
  - http.server 最小實驗判準:同一種故障模式連續執行 50 次,DSP 端最終狀態 100% 符合宣告;不過就改用具名退路(自寫 socket 伺服器、asyncio 伺服器),不硬撐。
  - pytest fixture 保證測試失敗與逾時路徑也會關閉伺服器與行程,埠一律由系統動態分配,每個測試用獨立的暫存資料庫。
