## 第二輪全讀與防治機制(2026-10-01)

使用者 2026-10-01 要求全讀,目的是「能夠防止這些漂移,或發生後直接有機制偵測並修復」。第二輪補讀計劃正文 18 篇與驗證紀錄 32 篇全文(14 個唯讀稽核員),到這裡全圖譜每一行都讀過。第二輪又找到約 190 處,20 多處高誤導;逐筆在 `governance/audits/2026-10-01-drift-sweep/findings.md`〈第二輪〉。

第二輪新增的形狀(上一節表格沒有的):
- 合約層:撤除條款仍掛活的 [test:](12 條,3 條綁的是斷言反面的測試);列舉自我參照綁定(條款寫死「恰好 N 種」,測試用 `set(列舉)`,程式加成員測試照綠);列舉含已刪成員;條款旁括號註記描述的測試內容已過期;全稱句被後期功能開的例外推翻(「死信後永不再取件」被重放推翻,測試沒測那個成員)。
- 回頭條件:寫下當下條件就已成立;觸發代理錯位(條件綁的檔存在,但它不代表那件事發生了)。這兩種有四條是本會談 2026-09-30 改寫回頭條件時自己造成的。
- 翻案與取代:裁定被實作悄悄繞開(沒有翻案紀錄);下游砍範圍或刻意偏離,上游架構沒回指(讀取令牌、分析側死信、畫面只讀),幽靈機制還被抄進後來的合約;取代或撤除標記只蓋到一處(照名字補註,同機制的白話句沒補)。
- 計劃:設計句沒落地(計劃 done、設計寫了的功能從沒做出來,例如展示頁花費欄永遠是「—」);計劃被後續改版繞過(改版只寫進 Systems 與驗證紀錄);設計段的施工前「現在」;職責住址漂移(拆檔後功能搬家,舊路徑還在所以路徑檢查會過)。
- 可執行內容:重查指令只剩查已刪符號;重跑配方的前提過期(`mv` 到已存在的目錄會變成子目錄)。
- 驗證紀錄與索引:預告殼(驗證紀錄 pass 但只有預告內容);驗收效期欄空白;索引裡抄的狀態落後;正文宣告「以這節為準」蓋過開頭欄位。
- 修補自己造成的漂移:本會談的修補有三處留下新漂移——條件式改寫寫下時已成立、兩條回頭註判決互相矛盾、驗證紀錄改了開頭欄位狀態但正文還寫待定。結論:任何修補(drift fix、set、補撤除標記)做完都要整篇重讀一次。

防治機制(依「防住最多、做起來最便宜」排序;每項寫預防、偵測、修復):

1. **合約層完整性檢查**(全機械,推送前擋)。涵蓋:殺傷力配方失配、懸空 [test:](含從沒存在過的)、撤除條款仍掛綁定、列舉自我參照、列舉含已刪成員、綁定註記過期。
   - 預防:新寫或改寫 [test:] 時當場驗測試存在;合約條款寫成員名或引用列舉,不寫「恰好 N 種」。
   - 偵測:改到配方目標檔的推送算 `old` 出現次數,不是 1 就擋;所有筆記(不只計劃)的 [test:] 都驗存在;條款子項含「撤除」而本文還有 [test:] 就擋;條款寫死 N 而綁定測試用 `set(列舉)` 時比 N 與成員數;綁定測試的最後修改晚於條款註記就提醒。
   - 修復:配方失配→對照現行程式重寫並重跑殺傷力驗證;懸空綁定→用 git 找改名或刪除提交,改名換新名、刪除改純文字並註明(可做成 drift fix 的一種)。

2. **狀態連動**(全機械,在 `lumos set`/計劃收尾當下與推送前)。涵蓋:已完成計劃的現況段沒標快照、設計句沒落地、lands_in 與〈落點〉不符、轉正後計劃沒回頭、階段性驗收沒收尾、預告殼、驗收效期欄空白、索引狀態副本落後、Systems 節點狀態落後。
   - 預防:計劃轉 done 時自動在「現況/已知缺口/會卡住的既有程式」類小節插快照橫幅;要求設計段每個小節對到一條合約或明寫「不做」;索引不抄狀態,改由工具產生。
   - 偵測:計劃 done 而設計段點名的欄位或函式在 src 沒有生產者就列;驗證紀錄轉正或 pass 時反查 plan_refs 計劃的「預告/待轉正」句;pass 而 valid_under、revalidate_when 都空就列。
   - 修復:drift fix 新增種類(插快照橫幅、補轉正說明、索引重產)。

3. **會過期的斷言一律條件化**(預防為主,偵測沿用 probe)。涵蓋:撤除條件已成立的 RULE、revalidate_when 已觸發、死觸發、散文回頭條件、「等 X 時」的待辦。
   - 預防:`[retire:]`、`revalidate_when`、計劃的 RETIRE-IF 都收條件式(比照 REVISIT 的 when-file/when-symbol/when-status);新寫的條件在提交時當場求值,已成立就擋(防「寫下時已成立」);when-file 可選帶 `[expect:符號]`,檔存在但符號不在就不算成立(防觸發代理錯位)。
   - 偵測:drift scan 現有 probe 機制直接涵蓋。
   - 修復:drift fix probe(改歷史說法/改回日期式/照留)。

4. **翻案與取代鏈**(半機械)。涵蓋:裁定被翻案、裁定被實作繞開、下游砍範圍上游沒回指、取代標記只蓋一處、取代回標漏條。
   - 預防:改裁、取代、刻意偏離時寫 `supersedes:` 指到被翻的那條(節點加條目或合約編號),工具要求被指的那篇回標。
   - 偵測:有 supersedes 而被指處沒回標就擋;某行加上「已撤除/已取代」時,同篇與 supersedes 指到的筆記裡同一機制關鍵詞或符號的未標行列成候選。
   - 修復:drift fix supersede:在所有候選行補撤除或取代標記,人逐條確認。

5. **整篇重讀判定者**(LLM,量最大的一類)。涵蓋:同篇後蓋前、雙生句、撤除橫幅混裝、設計段施工前現在式、指稱分裂與術語改義、守衛換手、前提消解、職責住址漂移、計劃被改版繞過、程式註解跟筆記一起過期。
   - 預防:v1.2 回頭重讀的觸發條件擴大——不只「程式改了且家筆記也改了」,筆記自己被追加或被修補(drift fix、set、補撤除標記)時也觸發,判定者整篇讀、只問「哪些舊句被後段或這次改動推翻」;判定材料加上改到程式檔的模組說明。

   - 修復:判定者每條給改寫建議,人確認後套用;修完同篇再跑一次判定者。

6. **程式側變更反查**(機械,推送前提醒;m1 的延伸)。涵蓋:新增了 X 舊句說沒有(工具組已排)、數量或值變了、全稱句被後期例外推翻、產物重產、歷史段指向會變的常數、重查指令只剩查已刪符號、重跑配方前提過期。
   - 偵測:常數改值或 tuple/列舉長度變了→列引用它的句子;新增會把狀態放回或歸零的寫入→反查含「永不/最多/之後不再」又點名同一欄位的句子;入庫產物在引用它的筆記行之後改過就列;實跑筆記裡的 DEP 重查指令,命中全是否定斷言就列;程式碼區塊的 `mv/cp -r` 目標已是目錄就列。

7. **開頭欄位自動化**(全機械)。涵蓋:updated 戳記落後、responsibility 沒涵蓋新職責、正文宣告蓋過開頭欄位。

### 標籤提案:讓會過期的句子帶上機器判得了的標準寫法(2026-10-01)

使用者 2026-10-01 提議:多訂一些標籤並給標準寫法,讓機械檢查能用在防漂移上。思路是:句子寫的當下就把「它靠什麼成立」寫成標籤,之後程式一變,工具直接判這句還成不成立,不必等判定者讀。格式沿用既有的 `[鍵:值]`,值的路徑寫法跟回頭條件一樣是 `路徑::名稱`;只在正文與摘要的可見行生效(圍欄、表格、行內程式碼不算),跟現有規則一致。

| 標籤(標準寫法) | 防的形狀 | 機器怎麼檢查 |
|---|---|---|
| `[count:路徑::名稱=N]`、`[value:路徑::常數=字面值]` | 數量或值變了(「三個模型變數」「上限 60 秒」「七張表」) | 讀那個名稱的成員數或常數值,跟 N 或字面值不同就報 |
| `[enum:路徑::列舉]` | 列舉漏新成員、列舉含已刪成員、列舉自我參照綁定 | 這句宣稱列出全部成員:句中反引號名稱跟列舉成員兩邊比,多或少都報 |
| `[retire-when-file:…]`、`[retire-when-symbol:…]`、`[retire-when-status:…]` | RULE 撤除條件已成立還保有效力 | 沿用 probe 評估,成立時 drift scan 點名,而且這條 RULE 失去挑戰程式碼的效力 |
| `[expect:路徑::名稱]`(跟 when-file 同一行) | 觸發代理錯位 | 檔存在但名稱不在,條件不算成立;另外新寫的條件提交時當場求值,已成立就擋 |
| `[id:短名]`、`[supersedes:節點#錨]`、`[superseded-by:節點#錨]` | 裁定被翻案、下游砍範圍上游沒回指、取代回標漏條 | 錨可以是合約編號、決策編號或 `[id:]`;兩端要成對,只有一端就擋;被取代的那條所在篇,同一機制關鍵詞的未標行列成候選 |
| `[retired:日期 提交或計劃]`(放在小節標題下第一行) | 撤除橫幅混裝或少算、撤除條款仍掛綁定 | 撤除小節裡不准有 `[test:]`,要改成 `[test-gone:名稱@提交]`;小節外提到撤除小節裡宣告撤除的符號就報 |
| `[test-gone:名稱@提交]` | 懸空 [test:] | 明標刪除的跳過存在檢查;其他 `[test:]` 一律驗存在(所有筆記,不只計劃) |
| `[snapshot:日期@提交]`(放在小節標題下第一行) | 已完成計劃現況段沒標快照、設計段的施工前「現在」 | 計劃 done 時,現況類小節沒有 snapshot 就報;done 計劃裡 snapshot 外的「現在/目前」加反引號識別字列候選 |
| `[from:路徑@提交]` | 產物快照過期、歷史段指向會變的常數 | 引用的產物或常數檔在那個提交之後改過就報 |
| `[same-as:節點#錨]` | 雙生句只修一半、理由複製錯貼 | 刻意重複的兩句互相指;一邊改了(git blame 較新)另一邊就報 |
| `[lives:路徑::名稱]` | 職責住址漂移 | 「功能在檔 X」的句子,名稱不在那支檔就報 |
| `[deliver:S編號]` 或 `[deliver:none 理由]`(計劃設計段每個小節) | 設計句沒落地、done 計劃未交付項沒去處 | 計劃轉 done 時每個設計小節要有一個;`[todo:…]` 要帶 `[home:[[Issues/…]]]` 才准 done |
| `[recheck:指令]` | 重查指令只剩查已刪符號、驗證指令漏新守衛 | 工具實跑,沒有命中或命中全是否定斷言就報 |

搭配一條寫法規則(提交時提醒,跟 v1.1 否定句提醒同一套):Systems 筆記的摘要與正文裡,含「只有/唯一/恰好 N/N 個/N 支/目前沒有/還沒」的句子,要帶 `[count:]`、`[enum:]`、條件式回頭條件或 `[snapshot:]` 其中之一,否則提醒。

粗估效果(依這次巡檢的分類筆數,不是實測):數量/列舉類約 50 處、撤除與懸空綁定約 80 處、快照約 28 處、翻案取代約 25 處、刻意重複約 15 處,如果當初寫的時候就帶標籤,大約六成的發現會變成機器直接判。剩下的同篇後蓋前、術語改義、前提消解要靠整篇重讀判定者。存量要補標籤,工具可以從句中反引號名稱自動提議 `[count:]`、`[enum:]`,人確認。

建議先做的核心五個:`[count:]`/`[enum:]`、`[retired:]` 加 `[test-gone:]`、`[snapshot:]`、`[supersedes:]`/`[superseded-by:]`、`[retire-when-*]` 加 `[expect:]`。標籤一多寫的人會嫌煩,其餘的看核心五個用起來的狀況再加。

試標結果(2026-10-01,照工具鏈建議只試 `[count:]` 與 `[retired:]`+`[test-gone:]`,5 篇 Systems,報告 `governance/audits/2026-10-01-drift-sweep/tag-trial.md`):115 句帶數量的現況句標得上 21 句(18%),全部機器判得出,其中 6 句當場抓到已過期、誤報 0;標不上的主因是純量數字(加 `[value:]` 可到約四成)與程式組出來的集合(最常過期的那群,例如流程圖節點數)。19 個撤除小節只有 3 個能整節標,45 個懸空綁定全卡在「部分撤除」的小節,撤除標籤要改成逐條。最大的成本與風險是挑對集合(同詞多個候選,挑錯就誤報)。上面的粗估「約六成」是分類推算,試標實測比它低,以試標為準。

PRIOR-ART: 需求追蹤工具 Doorstop 的「可疑連結」(上游改了下游標可疑)、Swimm 的程式碼耦合文件(文件綁程式片段,片段變了就標)、Sphinx 的 literalinclude 與 doctest(文件內容直接從程式抽或拿去跑)、ADR 的 superseded 鏈。這組標籤是同一個形狀:作者明寫依賴,工具判定。
RETIRE-IF: 某個標籤上線八週內零觸發,或誤報多過真報,就撤掉那個標籤;寫的人普遍不帶(新寫句子帶標籤比例低於三成)就改回靠判定者。

另外兩件程式本身的事,不是筆記漂移,交給使用者決定:展示頁的「本次 AI 費用」永遠顯示「—」(設計寫了按展示編號加總,程式寫死空值,沒人呼叫加總函式);程式註解與測試名有幾處跟筆記一起過期(見清單 C1)。
