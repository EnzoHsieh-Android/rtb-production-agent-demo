# F7端到端在CI上偶爾超過60秒

**2026-09-24 使用者本人改裁:改走做法 1,實作 [[Projects/F7效能_計劃]]。** 觸發:同一天 CI 兩次因 F7 超過 60 秒而紅(65–67 秒),其中一次在宣稱驗證器那一關。

## 發生什麼事

- 2026-09-24 推送 Phase 6 驗收紀錄(只有文件),CI 的測試步驟紅燈:`test_f7_many_small_increases_stop_at_the_aggregate_limit` 最後一行斷言整支測試不超過 60 秒,實際 67 秒。同一次 CI 全套跑了 211 秒,平常是 90 到 115 秒。
- 重跑同一個提交:全套 109 秒,這支通過。程式沒有變,判定是 CI 機器那一趟慢。

- 2026-09-24 第二次:合併 Phase 8 收尾後補一個只改文件的提交推送,CI 上這支跑了 74 秒(全套 172 秒);重跑同一個提交全套 114 秒、通過。兩次都在 CI 機器慢的那一趟,本機同時期 27 到 29 秒。已達下面回頭條件的「兩次以上」,列為使用者醒來優先裁定的事項。

- 2026-09-24 Phase 9 推送(cfc5d1a):CI 全套 168 秒、這支沒超時、沒重跑(CI run 35937520540)。

## 為什麼不自己改

- 60 秒寫在事故 F7 的合約 [S340] 裡,是當初設計定的效能邊界;放寬等於改合約,要使用者裁定。

## 可以選的做法(使用者 2026-09-24 選了維持現狀、紅燈重跑,見〈使用者裁定〉)

- 維持 60 秒,CI 紅燈時重跑一次;代價是偶爾要人工重跑。
- 放寬成 90 秒或改成「本機 60 秒、CI 只驗正確性不驗時間」;代價是效能退化在 CI 上看不出來。
- 縮小端到端的規模(例如 3000 個廣告改 1500 個,門檻等比例縮小);代價是跟交接文件「3,000 campaigns」的原始描述不同。

## 原因調查(2026-09-24)

只量不改:沒有動測試、程式或合約;量測在 phase9-inc4 工作樹用一支暫存的分段計時腳本(照測試的步驟跑、共用測試自己的輔助函式)與 cProfile。

### 量到的數字(本機,10 核 macOS,Python 3.14.6)

- pytest 直接跑這支:29.4、29.9、29.9 秒(增量 3 實作前);30.3、30.9、30.3 秒(增量 3 之後)。
- 分段(8 個工作者,兩次):收件 3000 份 5.0 秒;8 個工作者第一輪 27.1 到 27.6 秒;租約到期重投 0 到 0.2 秒;處理待核可結案 0.3 秒。忙碌退避只有 0 到 3 次、共睡 0 到 0.15 秒——鎖競爭不是主因。
- 工作者數:1 個 25.4 秒、8 個 27.6 秒。寫入本來就是 SQLite 單一寫入者,8 個工作者只多了約 2 秒的競爭成本。整趟約 21,700 個寫入交易,平均每個約 1.2 毫秒。
- 磁碟同步:把同步關掉 25.3 秒、設成一般 25.8 秒、預設 27.6 秒。本機同步只佔約 2 秒(macOS 的同步不強制落到磁碟,Linux 上會貴一些,我沒在 Linux 量)。
- 規模:750、1500、3000 個廣告,工作者那一段 2.5、7.6、27.0 秒——規模加倍、時間變三倍多,成長接近平方。
- cProfile(單一工作者,開著量測器共 40 秒):總曝險已用額度的計算 15.5 秒(每處理一筆就把這個租戶窗內所有預留整批讀出來加總,整趟讀了約 294 萬列);簽發時讀租戶設定檔 7.8 秒(每次簽發都重讀、重驗整份設定檔,這支測試的設定檔有 3000 個廣告,整趟驗了約 900 萬次編號格式);取件時的候選掃描 3.3 秒;收件 5.3 秒。前兩項都是「每一筆的成本跟累積的量成正比」,合起來佔六成以上。

### CI 那一邊(只讀 gh run view,沒有重跑、沒有推)

- 設定:ubuntu-24.04,Python 3.14,`python -m pytest -q` 單一行程跑全套,沒有平行跑測試(ruff、mypy 在前面的步驟,不同時跑)。這個儲存庫是私有的,依 GitHub 文件標準 Linux 執行器是 2 核(我沒從紀錄裡直接讀到核數);本機 10 核。檔案系統 ext4(本機 APFS)。
- 兩次紅燈的第一次嘗試:這支 73.8 秒(那一趟測試步驟 175 秒)、67.4 秒(那一趟 215 秒);重跑同一個提交的測試步驟 115、111 秒,都過。
- 測試步驟的時間一路變長:2026-09-22 約 28 到 46 秒,2026-09-23 下午以後約 90 到 116 秒(測試變多);慢的那幾趟是平常的 1.5 到 1.9 倍。

### 最可能的原因

這支測試的成本隨規模接近平方成長,主要花在兩件每筆都重做、而且量越積越多的事(總曝險已用額度整批重讀、每次簽發重讀整份設定檔),是 CPU 活,不是等鎖或等磁碟。本機約 30 秒。CI 通過時這支的時間沒有留紀錄(`pytest -q` 不印各支時間);用全套時間的比例推估(CI 通過的全套 111 到 116 秒 ÷ 本機全套 97 秒,約 1.2 倍),CI 平常約 35 到 37 秒,慢的那一趟再乘 1.5 到 1.9 倍是 53 到 70 秒,跟實際紅燈的 67、74 秒對得上。

### 可以選的做法(三選一;使用者 2026-09-24 選做法 2,見〈使用者裁定〉)

1. 把兩處「每筆重做整批」改成不隨累積量變大(例:設定檔沒變就不重驗、總曝險已用額度改用依時間索引的加總或維護中的合計)。
   - 好處:正式環境也受惠(同一租戶窗內預留越多、設定檔越大,每筆越慢);估計能省掉工作者那一段的一半以上(依 cProfile 比例推估,沒實作不知道實際數字),CI 會回到有餘裕。
   - 壞處:動到簽發讀設定檔(安全檢查、改設定立即生效)與總曝險判斷(金流),要走設計審與代碼審,不是小改。
   - 合約:[S340] 的 60 秒不動;總曝險與簽發既有的合約都要照樣綠。
2. 維持現狀,CI 紅燈時重跑一次(現在的做法)。
   - 好處:不動任何東西。
   - 壞處:每次 CI 慢就要人工重跑;測試越加越多、CI 越慢,紅燈會越來越常見。
   - 合約:不動。
3. 改合約:縮小規模(例如 3000 改 1500,門檻等比例縮小,本機量到約 9 秒)或把時間上限分成「本機 60 秒、CI 只驗正確性」。
   - 好處:立刻不再紅燈。
   - 壞處:偏離交接文件「3,000 campaigns」的原描述,或 CI 上看不到效能退化;平方成長本身還在。
   - 合約:要改 [S340],只有使用者能決定。
