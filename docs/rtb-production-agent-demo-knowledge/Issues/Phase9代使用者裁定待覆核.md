# Phase9代使用者裁定待覆核

來源:[[Projects/RTB_Phase9可觀測與SLO_計劃]] 全文、[[Projects/F7效能_計劃]]、[[Issues/F7端到端在CI上偶爾超過60秒]]、增量 1 到 4 各代碼審的收貨紀錄(governance/review-reports/code-phase9-inc1 到 inc4)。以「代使用者裁定」與「駁回」全文搜尋後逐條核對原文。

「改動大小」的意思:小=改一兩個常數或一段文字、測試跟著改數字;中=改一個模組的行為與它的測試;大=跨模組、改格式或要重排劇本。

## 一、碰金流、安全、合約數字

1. **F7 的 60 秒上限怎麼處理(沒有代裁,等你選)。** 選項:①做 F7 效能設計(下一條),60 秒不動;②維持現狀、CI 紅燈重跑;③改合約 [S340](放寬或只在本機驗時間)。為什麼沒代裁:60 秒是合約寫定的數值,授權的例外。已在 CI 紅過兩次,達到回頭條件。改哪裡:[[Issues/F7端到端在CI上偶爾超過60秒]] 選定後照做。大小:①大(見下條)、②零、③小(改合約與一行斷言)。
2. **F7 效能設計:已用額度改資料庫端加總、溢位/舊列/型別異常退回原算法;這是翻 Phase 6 的決策。** 選項:照 Phase 6 在程式裡整數累加(慢,F7 時間隨規模平方長) vs 資料庫加總加退路。為什麼:實驗 26.4 秒降到 14.0 秒、3000 次比對新舊 0 差;退路保住原本擔心的溢位停機。已過設計審三輪,沒實作。不同意:不採用即可,只有設計筆記。大小:零(未實作);採用則是中偏大(已用額度、共用資料庫模組、合約 [S680]–[S686]、要改寫 [S378] 的測試)。出處:[[Projects/F7效能_計劃]]〈核心裁定〉、[[Projects/RTB_Phase6權限護欄與總曝險_計劃]] 增量 1。
3. **F7 效能設計:租戶設定檔的解析結果快取在簽發器上,內容一個位元組都沒變才沿用,安全讀檔每次照做。** 選項:每次重解析(現況) vs 快取。為什麼:簽發的安全檢查一道都不略過,只省解析。不同意:同上,不採用即可。大小:零(未實作)。
4. **DSP 列操作兩支端點要帶另一把唯讀稽核金鑰,不沿用寫入憑證。** 選項:不驗(原實作,回全租戶明細) / 沿用寫入憑證 / 另給稽核金鑰。為什麼:寫入憑證綁一個廣告、一把鍵、一個動作,而且是簽發金鑰簽的;維運套件要能簽就得拿到能簽寫入的那把。沒帶 401、帶錯 403、DSP 沒設 503;專用標頭、base64url。不同意改哪裡:[[Systems/寫入能力憑證]]、[[Systems/Mock-DSP]]、[[Systems/服務水準與燒損告警]] 讀窗那段與它們的測試、[[Systems/調查實演]] 的佈置。大小:中偏大(跨三個模組)。出處:增量 3 代碼審第 1、2 輪。
5. **稽核金鑰長度上限 1024 位元組。** 選項:不設上限 / 設上限。為什麼:HTTP 標頭一條最長 64 KB,沒上限時兩端設定一致卻永遠送不到;超長在 DSP 啟動與評估器入口當設定錯誤。不同意:改 [[Systems/寫入能力憑證]] 的上限常數。大小:小。出處:增量 3 代碼審第 3 輪。
6. **服務水準命令列:任一條缺資料或出錯回新的結束代碼 8「不完整」,優先於不穩定 5。** 選項:照舊回 0 / 回 8。為什麼:回 0 會讓依結束代碼判斷的排程把稽核沒跑到當成功。不同意:改 [[Systems/服務水準與燒損告警]] 的結束代碼與它的測試;下游監控若已接要一起改。大小:小到中。出處:增量 3 代碼審第 2 輪。
7. **寫 DSP 呼叫紀錄撞到資料庫忙時不往外丟,先放執行器的待寫清單,下一次處理前補寫。** 選項:往外丟(第一版) / 待寫清單。為什麼:往外丟時忙碌例外會蓋掉已經發生的 DSP 結果、違反「寫入、作廢不丟例外」、對帳整輪被放棄;代價是行程當機(或結束時還忙)那幾筆呼叫紀錄會少記,照實寫在執行迴圈筆記。不同意:改 [[Systems/執行迴圈]]。大小:中。出處:增量 1 代碼審第 1 輪。第 2、3 輪再代裁三件:①清單上限 50 列(暫用值),到上限就不開始新的處理與對帳,補寫連續忙照舊算進啟動程式的忙碌次數;②結束時仍欠著就在標準錯誤印出少記幾列與哪些冪等鍵,退出碼照舊(選項:無聲放掉 / 印出 / 改退出碼);③補寫先把這一批從清單拿出來再開交易,交易沒成原樣放回最前面,寫完之後才到的中斷不放回,不加呼叫編號(選項:加呼叫編號去重 / 不加)。不同意:同樣改 [[Systems/執行迴圈]] 與啟動程式;①是一個常數、②③是小改動。出處:增量 1 代碼審第 2、3 輪(2026-09-24 整合時補進這份清單)。
8. **DSP 埠每支方法改收必填的呼叫回呼,每個呼叫點顯式傳綁好提案身分的回呼;拿掉模組層級範圍變數。** 選項:模組層級變數 / 建構時綁回呼 / 每次呼叫傳。為什麼:共用用戶端配多工作者時,建構時綁會把紀錄寫錯庫;漏傳由必填參數擋。不同意:改 [[Systems/執行迴圈]] 的 DSP 埠與所有呼叫點。大小:中。出處:增量 1 代碼審第 1 輪(第 2 輪架構席再挑戰、被駁回,見第四節)。

## 三、命名、格式與設計取向

15. **追蹤的根用任務編號,不新增追蹤編號;交接文件的 decision_id 用「任務、修訂、內容雜湊」三件組代替。** 為什麼:任務編號已經一路帶到 DSP;新增追蹤編號要改提案格式、收件口、DSP 用戶端三邊。代價:同一任務多份修訂共用一條追蹤。不同意:[[Systems/追蹤檢視]] 與提案格式;合約 [S604]。大小:大。
16. **指標從只增不改的紀錄即時算,不另存計數器;為此補一張不隨收件表清除的生命週期事件表。不寫 log 行當追蹤。** 為什麼:另存會跟紀錄對不上(沿用 Phase 6 增量 4)。不同意:[[Systems/有界標籤的指標]]、[[Systems/提案收件口]];合約 [S602]。大小:大。
17. **服務水準指標一律建在「事件型」指標上,壞事件只用事件當下寫下的資料判。** 為什麼:同一個過去的窗之後再查答案要不變,才能拿來判告警。不同意:[[Systems/服務水準與燒損告警]]。大小:大。
18. **政策版本標籤用版本字串本身,只收只增不刪的已知政策版本清單,其他歸「其他」。** 選項:「目前/其他」(原設計) / 版本字串。為什麼:「目前/其他」跟查詢當下比,改版後同一個過去的窗標籤會變。附帶一條規則:改政策版本常數時同一次提交把新值加進已知清單、舊值不刪([[Systems/任務流程領域模型]])。不同意:[[Systems/有界標籤的指標]]、[[Systems/任務流程領域模型]];合約 [S631]。大小:中。出處:增量 2 代碼審第 1 輪。

## 四、照規格駁回、留使用者覆核

審查員提出、編排者判定「程式照規格寫、重現不到錯誤行為」而駁回;規格本身可能才是該改的地方。

- **時鐘倒退時 DSP 提交時間墊高到上一筆(增量 3 代碼審第 1 輪外家席)。** 審查員的顧慮:墊高後重查一個已過去的窗,可能多出後來的寫入。駁回理由:合約 [S667] 明定墊高,依編號翻頁才等於依時間翻頁;計劃〈實務隱患〉已列為未排除風險。若你認為該改:改 [S667] 與 [[Systems/Mock-DSP]],副作用核對的翻頁跟著重想。大小:中。
- **DSP 埠每次呼叫傳回呼的「形狀」(增量 1 代碼審第 2 輪架構席)。** 審查員判它是專案第三種做法。駁回理由:辯方查分析端與執行端都是每次呼叫顯式傳身分,只差形狀;改成建構時綁在多工作者下會寫錯庫。若你認為該統一:改 [[Systems/執行迴圈]] 的 DSP 埠。大小:中。
- **版本衝突率不用既有的版本衝突計數(增量 2 代碼審第 1 輪架構席)。** 駁回理由:合約 [S645] 經設計審明定完全從 DSP 呼叫紀錄算;分子分母不同表會在窗界超過百分之百,既有計數也不收時間窗。若你認為該共用:改 [S645] 與 [[Systems/有界標籤的指標]]。大小:小到中。
