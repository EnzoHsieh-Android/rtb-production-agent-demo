# 執行迴圈

三支檔:`src/rtb/executor/execution.py`(處理一筆與 DSP 回應對照表)、`src/rtb/executor/dsp_client.py`(執行行程的 DSP 讀寫用戶端,經 [[Systems/共用行程基礎]] 的共用 HTTP 用戶端)、`src/rtb/executor/runner.py`(啟動程式與單一執行者鎖)。收件表與嘗試紀錄的儲存規則在 [[Systems/提案收件口]] 與 [[Systems/外部寫入嘗試紀錄]],簽發在 [[Systems/寫入能力憑證]]。

## 處理一筆的順序

1. 挑提案:依收到時間由舊到新,跳過同廣告已有未結案嘗試的。
2. 提案已過期就標已過期(不讀 DSP);否則重讀 DSP,讀不到(不含廣告不存在)就這一輪什麼都不寫。
3. 執行前檢查:廣告存在、仍在投放、版本等於提案觀察到的、簽發器願意簽;任一不過就在「仍待處理且內容雜湊沒變」的條件下標已擋下。
4. 同一個交易裡核對仍待處理、開始一筆、標已交給執行;鍵已存在就依既有那把鍵的狀態分流(失敗 → 擋下「同一操作先前已失敗」)。
5. 帶憑證與冪等鍵寫 DSP,回應經唯一一份對照表轉成嘗試狀態;憑證過期時重讀、重跑檢查、重讀時鐘重簽、同鍵重送一次。
6. 已提交待驗證就立刻做執行後驗證;之後的對帳是增量 4。

## 代碼審第 1 輪修正(2026-09-23)

- PITFALL: 提案到期只在讀 DSP 之前判一次,讀取或簽發(要讀設定檔)剛好跨過到期時間就會照樣寫入;到期要在「開始一筆」的同一個交易裡再判一次,這是寫 DSP 之前最後一個本地步驟。出處:增量 3 代碼審第 1、2 輪外家席實驗。防回歸:[test:test_a_proposal_that_expires_while_the_dsp_is_read_is_not_executed]、[test:test_a_proposal_that_expires_while_signing_is_not_executed]。
- PITFALL: 啟動程式要先拿單一執行者鎖、才用 SQLite 開資料庫;先開再鎖時,經硬連結以別的檔名開會用另一組 WAL 檔,可能損壞資料(SQLite 官方〈How To Corrupt〉列為多重連結)。防回歸:[test:test_a_locked_out_runner_never_opens_the_database_with_sqlite]。
- PITFALL: 就算只有一個執行迴圈,它若用硬連結檔名、收件口用正式檔名開同一個資料庫,SQLite 仍會各用一組 WAL 檔;資料庫檔有硬連結就拒絕啟動(結束代碼 5)。出處:增量 3 代碼審第 3 輪外家席。防回歸:[test:test_a_hard_linked_database_is_refused_before_sqlite_opens_it]。
- PITFALL: 讀 DSP 後的到期判斷要排在其他執行前檢查之前:讀取期間過期又同時不在投放時,要記「已過期」不是「不在投放」。防回歸:[test:test_an_expiry_during_the_read_wins_over_other_failed_checks]。
- PITFALL: 單一執行者鎖的檔名若含資料庫檔名,同目錄的硬連結會算出第二把鎖;鎖名只用裝置與 inode。防回歸:[test:test_the_runner_holds_a_single_instance_lock_and_recovers_before_ready](含硬連結)。
- PITFALL: 回應對照的測試若從程式自己的對照表產生案例,刪掉一列時案例跟著消失而假綠;預期值要手抄一份。防回歸:[test:test_every_dsp_answer_maps_to_the_documented_state_and_code]、[test:test_the_documented_answers_reach_every_row_of_the_response_table]。
- PITFALL: DSP 回的版本號若超過 64 位元整數上限,寫進資料庫時會丟非預期例外、繞過停機路徑;用戶端解析時超過上限就當讀不懂。防回歸:[test:test_an_oversized_version_from_the_dsp_is_treated_as_unreadable]。
- WHY: 時鐘用 Callable 不用 Protocol:專案慣例是單一動作的簡單回呼用 Callable(見 [[Systems/分析行程流程與檢查點]] 的流程檔頭說明)。出處:增量 3 代碼審架構對齊席。
