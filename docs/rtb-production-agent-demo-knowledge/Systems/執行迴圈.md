# 執行迴圈

三支檔:`src/rtb/executor/execution.py`(處理一筆與 DSP 回應對照表)、`src/rtb/executor/dsp_client.py`(執行行程的 DSP 讀寫用戶端,經 [[Systems/共用行程基礎]] 的共用 HTTP 用戶端;會發哪幾種寫入以程式碼為準:`rg -n '"POST"' src/rtb/executor/dsp_client.py`)、`src/rtb/executor/runner.py`(啟動程式)。收件表與嘗試紀錄的儲存規則在 [[Systems/提案收件口]] 與 [[Systems/外部寫入嘗試紀錄]],簽發在 [[Systems/寫入能力憑證]]。

## 處理一筆的順序

1. 挑提案:依收到時間由舊到新,跳過同廣告已有未結案嘗試的。
2. 提案已過期就標已過期(不讀 DSP);否則重讀 DSP,讀不到(不含廣告不存在)就這一輪什麼都不寫。
3. 執行前檢查:廣告存在、仍在投放、版本等於提案觀察到的、簽發器願意簽;任一不過就在「仍待處理且內容雜湊沒變」的條件下標已擋下。
4. 同一個交易裡核對仍待處理、開始一筆、標已交給執行;鍵已存在就依既有那把鍵的狀態分流(失敗 → 擋下,原因依嘗試結果代碼:版本衝突寫「版本已變」,其他寫「同一操作先前已失敗」)。
5. 帶憑證與冪等鍵寫 DSP,回應經唯一一份對照表轉成嘗試狀態;憑證過期時重讀、重跑檢查、重讀時鐘重簽、同鍵重送一次。
6. 已提交待驗證就立刻做執行後驗證;之後的對帳是增量 4。

## 人工核可與待核可(Phase 6 增量 3,2026-09-23)

- 處理一筆的順序:執行前檢查(三條硬規則)→ 簽發(不屬於租戶、超過單一廣告上限兩條硬規則)→ 比例上限(可核可)→ 開始一筆時的總曝險(可核可)。可核可的一關沒有有效核可就停在待核可:處置寫待核可、擋下原因記是哪一關、同一個交易裡寫一列停下紀錄,不開嘗試、不呼叫 DSP。硬規則有核可也照樣擋下結案。
- 核可在執行行程驗(驗章、任務修訂與內容雜湊、關卡、範圍指紋、提案政策版本等於共用常數、到期、金額上限),同一份提案同一關只看最後寫進核可表的那一張,最新那張不算數就整件不算數。開始一筆前先查好可能用到的核可(總曝險那一張只在照當下已用額度會超過門檻時才留,用不到的核可不壓短憑證),用到就重簽一次、憑證到期封頂在核可到期;重簽被硬規則拒簽就照硬規則擋下,重簽讀到的租戶設定跟第一次不同就放掉租約下一輪重來。開始一筆的交易裡再核一次:查好的那張已不是最後寫進核可表的那張就放掉租約下一輪重判,用當下時間判到期、過期就回待核可(代碼審第 1 輪)。核可生效時同一個交易寫一列核可使用紀錄(比例那一關有核可就記;總曝險那一關只在真的超過門檻時記)。
- 每輪先對帳、再處理待核可、再處理一筆。處理待核可只讀這一輪有事做的(到期、有更新修訂、這一關有人簽過核可、同任務開過嘗試),待核可堆積不讓每一輪變慢;逐筆各自一個交易:提案到期就確認成已擋下(擋下原因是原本那一關);同任務有更新的修訂就確認成被取代;同一把鍵已由另一份修訂開過嘗試(兩份都取到收據的競態)就放回待處理,取件照那把鍵的狀態確認,不要求第二張核可(事故 F3);有這一關的有效核可(金額用停下紀錄記的那一筆)就放回待處理、投遞次數歸零;寫入條件都是「這一列仍是待核可」,沒有租約可比,這就是並行防線。
- 同鍵重送(憑證過期後、對帳查不到後)也重判比例與這份提案用過的核可:比例超過而沒有有效核可,或用過的核可已不算數(當初用過的那張過期,就算之後補簽了足額的新核可也一樣;重送兩次簽發之間租戶設定改了、或又有人簽了更新的核可,也算不算數;最後一次「仍是最新」的核對跟轉嘗試中在同一個交易,之後才呼叫 DSP——跟處理一筆在開始一筆交易裡的核對是同一個判斷點),就照既有做法不重送(送過一次直接判失敗、送過多次先作廢再判失敗);總曝險不重判,預留在開始一筆時已寫下。
