# 規則模式探索模型入口

Phase 15 增量 2(計劃 [[Projects/RTB_Phase15AI找規則模式_計劃]]〈拆增量〉2)。AI 在這裡的角色只是「離線提候選規則」:回覆只到評估端的核對與(增量 3 的)人讀報告,不進分析行程、提案、收件口、執行端或 DSP。

## 這支檔

- `src/rtb/analyzer/rule_mining_model.py`:`suggest(system, table, config)` 開閘道、送一次;`GateConfig` 是閘道設定(環境、展示編號、帳本、錄製目錄、批次、錄製帳本);`Reply` 帶結果類別、模式、原始文字(成功才有)、來源、錄製鍵、原價與失敗原因;`PromptTooLarge` 是呼叫前的位元組拒絕。
- 常數:輸出上限 6144 token、逾時 60 秒、完整提示 20480 位元組。評估版本的同名常數在評估端的語彙模組([[Systems/規則模式探索評估]]),兩邊由 [S1514] 的測試核對一致;分析端不准匯入評估套件,所以只能各寫一份。
- 增量 3 加 `check_gate(config)`:開一次閘道判模式、做即時模式的登入預檢,**不送出、不記帳**,回 `GateCheck`(含那個閘道);命令列在記下一次嘗試之前先呼叫它,判成錄製就拒絕、不用掉展示編號序號。WHY 放在窄入口:評估端不准匯入模型閘道,而模式只有閘道判得出來。
- 代碼審 r1 正確性 6:`suggest(…, gate=)` 收 `check_gate` 已預檢的閘道直接送出、不另開;否則新閘道的後端沒登入預檢過,Claude Code 後端會在 60 秒呼叫期限裡再查一次登入。給的閘道不是規則模式探索開的就丟 `ForeignGate`、不送。modelgate 語意沒改。
- 閘道注入點 `open_gate=`:測試用它換成綁假後端的閘道(不呼叫真的 claude);產品碼一律用閘道本身。

## 實作者解讀(2026-09-27)

- 預留額檢查不另寫一份算式:計劃要求「呼叫前用 repo 預留函式與當時價目、已用額重算,須 ≤ 每展示及每月剩餘上限」,花費帳的預留本來就在單一寫入交易裡做這件事(用 `reservation_nanousd`、讀已用、判兩個上限),只要 `RULE_MINING` 列進計入上限名單。另在窄入口重算一次既會重複、也有「先查後寫」的競爭空窗;併行預留由 [S1514] 的測試證明也守得住。
- 失敗一律收成 `Reply`、不往外丟:評估端要把非 ok 記成「呼叫失敗」而且不重試,收成值比每個呼叫端各自接例外不容易漏。閘道拒絕(入口參數跟模式對不上)、不認得的模型與停止訊號不是模型呼叫的結果類別,照原樣往外丟。
