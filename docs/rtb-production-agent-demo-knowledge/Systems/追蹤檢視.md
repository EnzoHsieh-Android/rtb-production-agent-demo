# 追蹤檢視

本篇管 `src/rtb/ops/trace.py`:給一個任務編號,把分析端(任務歷史、證據編號、對外呼叫,沿接續關係串進接續任務)、執行端([[Systems/提案收件口]] 的生命週期事件與死信信封、稽核,[[Systems/外部寫入嘗試紀錄]] 的嘗試紀錄與 DSP 呼叫紀錄)與 DSP(唯讀的操作紀錄端點)組成一條時間線。命令列入口 `python -m rtb.ops.trace --task-id … --analyzer-db … --executor-db … --dsp-url …` 印出 JSON;`build_trace` 回結構化結果。設計與合約 [S604]–[S606]、[S608]、[S613]–[S615]、[S617]、[S619] 見 [[Projects/RTB_Phase9可觀測與SLO_計劃]] 增量 1。

- 每一段帶齊關聯欄位(任務、修訂、內容雜湊、冪等鍵、租戶、廣告、工作者、政策版本、第幾次嘗試、DSP 操作編號),缺的標成「missing」,不留白裝作沒有。交接文件的 decision_id 以「任務、修訂、內容雜湊」三件組代替;operation_id 就是 DSP 操作編號。
- 一份提案的身分一律是(任務、修訂、內容雜湊)三件組,不用任務加修訂:收件表清掉之後同任務同修訂可能再來一份內容不同的,用兩件組會吞掉其中一份(代碼審第 1 輪外家席)。嘗試歸屬用嘗試第一列快照算出的內容雜湊;DSP 呼叫紀錄沒存雜湊,用同任務同修訂下的冪等鍵接回。防回歸:[test:test_a_reused_task_and_revision_with_new_content_is_traced_separately]。
- 維運套件不准用字串動態取屬性(getattr、attrgetter、methodcaller 之類):名字掃描看不到字串裡的方法名,維運套件本身也用不到(代碼審第 1 輪測試席)。
- 冪等鍵:每一份修訂的鍵優先用分析端交給執行時存下的,沒有才從分析端的提案用目前算法重算,再沒有才用執行端事件寫下時記的;每一份都標明鍵從哪來(分析端 Phase 5 就防過「算法改版後重算對不上」)。同一把鍵被多份修訂共用時,嘗試只列一次、歸建立它的修訂(嘗試第一列記的任務與修訂),其他修訂標「由這把鍵的既有結果確認」。防回歸:[test:test_a_shared_operation_key_is_attributed_to_the_revision_that_created_it]。
- DSP 讀不到(逾時、斷線、非 200/404、讀不懂)就整個 DSP 來源標缺,分析端與執行端照樣組。防回歸:[test:test_a_trace_marks_the_missing_dsp_segment]。執行端 DSP 用戶端讀操作紀錄時會丟掉操作編號與提交時間,所以這裡另用共用 HTTP 用戶端讀同一個唯讀端點。
- 執行前就被擋下、沒開過嘗試的提案,收件表清掉之後仍查得到廣告、冪等鍵與政策版本:事件寫下時就從提案內容算出存下。防回歸:[test:test_a_proposal_blocked_before_any_attempt_is_still_traceable_after_the_purge]。
- 結束代碼:0 成功(不穩定也回 0,結果裡標明);2 資料庫檔不存在;3 資料庫還沒升級(請先啟動一次執行迴圈,分析端資料庫則先跑一次分析行程;追蹤檢視只讀、不替它補)。防回歸:[test:test_a_read_only_open_of_an_old_database_fails_cleanly]。
- 租戶:簽發前就結束的事件沒有租戶,時間線照實標缺;依租戶切片時用查詢當下的租戶設定反查,是增量 2 指標的事,這裡不做。
- 不是即時監看:系統一直在忙時可能三輪都不同,照實標明。依賴:[[Systems/共用行程基礎]] 的共用 HTTP 用戶端。
