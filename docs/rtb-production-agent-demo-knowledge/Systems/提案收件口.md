# 提案收件口

`src/rtb/executor/inbox_store.py` 是收件表與所有判斷;`src/rtb/executor/inbox_server.py` 是 HTTP 收件口(建立在 [[Systems/共用行程基礎]] 之上,用增量 1 的 `parse_proposal` 與 `content_hash`,見 [[Systems/任務流程領域模型]])。

已知缺口(如實標明):
- **收件鍵只在保留期限內唯一:** 舊任務被清掉之後,同一個(任務編號, 修訂序號)可以用不同內容再被收下(那是全新的提案)。所以 Phase 3 的執行端不能只靠這個組合當跨時間的唯一識別,要用提案內容雜湊或收件時的流水號。
REVISIT:2026-10-20 Phase 3 設計執行端的操作鍵時確認這一點。
- 總列數上限與保留期限是我暫定的數字(5000 列、2 小時、每任務 50 修訂),沒有實測依據;上限被灌滿時,合法提案要等最舊的任務過了保留期限才有空間,這和名額佔用是同一類拒絕服務(影響分析行程自己的流程),解法同樣要等呼叫者身分與配額。
REVISIT:2026-10-20 與名額配額一起決定這幾個數字。
- 事件去重只比對最新一筆,但每種事件代碼各有筆數上限,所以單一種類的洪水洗不掉別種事件;同一種類內的新舊事件仍會被輪替(事件表是盡力而為的紀錄,不是稽核依據,真正的稽核要等有認證的呼叫者身分之後)。
REVISIT:2026-10-20 與速率限制一起評估,是否改成每個任務或每種事件代碼各留固定筆數。
- **名額佔用是已知且未解的風險:** 呼叫者不需認證,每小時送 8 份有效期一小時的提案(不同任務編號)就能持續佔滿名額,讓合法提案拿到「可重試」的 503。決策有效期上限(1 小時)只是壓低佔用時間,不是解法;真正的解法要有呼叫者身分與每來源配額(Phase 3 的能力憑證與政策層)。影響是分析行程自己的流程被癱瘓(它是唯一的呼叫者),不是越權寫入:提案仍要通過 Phase 3 的執行前授權。
REVISIT:2026-10-20 Phase 3 開始前決定名額配額或速率限制的做法。
- 沒有請求速率限制:用不同任務編號輪流送新提案,仍能在「待處理上限加上到期時間」的範圍內持續佔滿名額。
REVISIT:2026-10-20 Phase 3 開始前,決定要不要在收件口加請求速率限制,或交給 Phase 3 的政策層。
- 沒有收件表清理與保留期限:已被取代與已過期的提案會累積。
REVISIT:2026-10-20 決定保留期限與清理方式(可與 Phase 8 的死信處理一起做)。
- 重送一份已過期的提案,回應的 status 仍是 accepted(代表「收過了」),真正的狀態看 state(expired 代表它已經不能被執行);這是有意的,契約以 state 為準。
- 沒有身分認證,租戶相符檢查也還沒做(Phase 3 的能力憑證與執行前授權)。
- 收件表的三個狀態(待處理、已被取代、已過期)是執行行程這一側的小表,與分析行程那一側的任務狀態機(見 [[Systems/任務流程領域模型]])的對應關係要在增量 3 定義,現在不宣稱一致。
- 重啟保留的測試是「同一個資料庫檔、新的伺服器」,沒有真的殺行程;真正猝死的語意由資料庫交易本身保證,在 Phase 4 的當機測試再驗。
REVISIT:2026-10-20 Phase 4 當機恢復測試時補上殺行程的版本。
- 拒收的例外型別放在收件表檔、HTTP 狀態碼對照表放在伺服器檔:與 DSP 的做法一致(DSP 的錯誤型別在錯誤檔、對照表在伺服器檔),這樣儲存層不必知道 HTTP。收件口走共用基礎的 map_exception 與 error_extras,沒有第二套錯誤對應。
- 另有一批「實作與代碼審補上的規則」(有效期上限 1 小時、到期時間離現在最多一小時、無效請求不碰資料庫、Host 必須存在、整個請求總期限與連線上限)寫在上面的規則與共用行程基礎節點;設計計劃本身不再修改,以免動到已凍結的設計審判定。
