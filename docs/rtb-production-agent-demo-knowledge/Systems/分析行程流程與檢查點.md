# 分析行程流程與檢查點

`src/rtb/analyzer/task_store.py` 是歷史表與 `commit_step`;`src/rtb/analyzer/flow.py` 是三個可替換介面(`EvidenceSource`、`Decide`、`Submit`)與驅動函式 `advance()`。增量 3 這兩個介面都是測試假物件,增量 4 才接真的 DSP 用戶端與 [[Systems/提案收件口]] 用戶端。

已知缺口(如實標明):
- `tasks` 與 `evidence` 兩張表只增不改,長時間運作會無界成長,尤其重新規劃的迴圈沒有次數上限;解法留給與提案收件口一起決定的保留期限。
REVISIT:2026-10-20 與 [[Systems/提案收件口]] 的保留期限一起決定分析行程歷史表的清理方式。
- `policy.py` 的示範規則永遠把新提案的修訂序號當成 1,不會追蹤同一個任務先前送過幾次修訂;一個提案被收件口退回(`SubmitStale`)之後重新分析,示範規則不會自動送出正確的下一個修訂序號,會一直送修訂 1 而持續被 `revision_out_of_order` 拒收。這不影響 S49 的合約(規則本身的判斷邏輯經過測試),但整條流程在「重新規劃」這條路徑上目前示範不完整。
REVISIT:2026-10-20 接上真正的決策邏輯時,一併設計修訂序號的追蹤方式(可能要讓 TaskRow 或另一張表記住「這個任務目前送到第幾個修訂」)。
- FAILED 狀態目前只有一個觸發點(`Decide` 丟例外);`EvidenceSource`、`Submit` 的失敗都視為暫時性、永遠重試,沒有「重試次數上限後轉為永久失敗」的機制,理論上一個一直失敗的外部呼叫會讓任務永遠卡在原狀態。
REVISIT:2026-10-20 增量 4 接上真的網路呼叫後,評估是否需要重試上限或逾時轉 FAILED。
