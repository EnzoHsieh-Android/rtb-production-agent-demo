# 確定性指標計算

(2026-09-22 起,「數字不含布林」的判斷改用領域層共用的 [[Systems/任務流程領域模型]] 管的共用小檢查,行為不變。)`src/rtb/domain/metrics.py` 是這一層唯一的模組:四個指標函式、`MetricResult` 結果型別,以及列舉 `Reason`(沒有值的三種原因,只用 `Reason.X` 一種寫法引用)。

四個指標的定義:CTR=點擊/曝光;CVR=轉換/點擊(轉換可以多於點擊,例如瀏覽後轉換,所以不算不合理);ROAS=營收/花費;Pacing=實際花費/(預算 x 已過去的時間比例),1.0 剛好符合預期、小於 1 落後、大於 1 超前,已過去的時間比例必須在 0 到 1 之間。

## 已知缺口(如實標明)

- ruff 的禁用匯入是黑名單,擋不住 `__import__("...")`、逐行的 `# noqa: TID251` 與清單沒列的模組。2026-09-22 合約審計實測確認這個洞(在領域層寫 `import sqlite3  # noqa: TID251`,整套測試原本都抓不到),已補一支直接解析原始碼的白名單測試 [test:test_domain_layer_imports_only_an_allowlist_of_pure_standard_library_modules],它不看 noqa 註解、也禁止 `__import__`/`eval`/`exec`;這條保證現在掛在 [[Systems/任務流程領域模型]] 的合約上。ruff 禁令保留當第一道、編輯器就看得到的提醒。
- 清單只在這個目錄的 `ruff.toml`;若之後有第二個受限層(例如 agent、client),要另放一份並複製清單,子設定裡的禁用清單是覆寫,不是與別處合併。
REVISIT:2026-11-21 或新增第二個受限層時,決定是複製清單還是抽共用。
- 整數與浮點混用時,超出浮點範圍的整數(例如 `ctr(1.0, 10**400)`)會被判成資料不合理,即使輸入本身合法;極小值相除會下溢成 0.0(`roas(5e-324, 1e10)` 回 0.0)。方向是保守的,不會產生假的大數字,屬已知的極端輸入取捨。
- `cvr` 允許轉換多於點擊(瀏覽後轉換是合理情況),所以不像 `ctr` 那樣把它視為不合理;`pacing` 在時間比例為 0 時回分母為零,即使已經花了錢,不另立「不合理」類別。這兩個是語意取捨。
REVISIT:2026-11-21 決策端開始使用這些指標時,回頭確認這兩個取捨是否符合實際需求。
- `MetricResult` 只擋了排序比較與真值判斷,`==` 與 `hash` 仍可用;兩個「沒有值」的結果若原因相同會相等,這是刻意的。

型別檢查:2026-09-22 起通過 mypy 嚴格模式。四個指標函式內部改用 `_checked` 一次回傳「已確定非空的數字或問題原因」,取代原本的 `_classify` 加空值假設,型別檢查因此能驗證;對外行為與所有測試結果不變。

## 收據的精確比率與固定字串(Phase 13 增量 2,2026-09-25)

出處 [[Projects/RTB_Phase13AI參與決策_計劃]]〈收據的算法與格式〉。

- `exact_ratio` 回分數或三態原因代碼之一(不合理 > 缺漏 > 分母為零,輸入可以是前一次比率的結果);`exact_change`、`exact_click_rate` 都經它。收據格式化(`receipt_ratio`、`receipt_change`、`receipt_click_rate`、`percent_text`)把分數寫成百分比刻度 1 位小數、四捨五入到偶數,負零寫 `0.0`;金額 `receipt_amount` 先 `Decimal(repr(x))` 再量化到 2 位,溢位歸資料不合理;計數 `receipt_count` 照寫整數;算不出一律寫 `na`。
- 既有的 `MetricResult` 不動(它只收整數與浮點);既有 `ctr`、`cvr` 用浮點除法,247/2000 會捨成 `12.3`,收據要的是 `12.4`,所以另開精確的一支。標準答案產生函式(Phase 13 增量 3)也要經 `exact_ratio`,不另算。

WHY: 收據一律是字串、算不出寫 `na` 而不是 `n/a`:可信證據的字串只准識別碼字元,斜線過不了既有驗證。出處:[[Projects/RTB_Phase13AI參與決策_計劃]] 代使用者裁定 R2-3、R2-4、R2-5、R3-6。防回歸:[test:test_receipt_values_are_fixed_strings_computed_in_the_domain]、[test:test_one_exact_ratio_function_feeds_receipts_and_the_answer_key]。

WHY: [2026-09-25 Phase 13 增量 2 代碼審 r1] 收據字串寫出來超過可信證據的上限(領域層識別碼長度 `MAX_ID_LENGTH`,128 字)就歸資料不合理、寫 `na`(極端但有限的金額會算出幾百位數,建證據時丟例外、整步卡住);比率的浮點輸入先照收據金額的寫法 `Decimal(repr(x))` 轉十進位再轉分數,0.16 到 0.17 得 `6.2`、跟收據上的金額推得的一致;(r2)另開 `exact_value` 給收據的加總、平均與大小比較用,不經浮點;`exact_click_rate` 收加總出來的分數也照擋點擊多於曝光。r1 加的 `exact_conversion_rate` 在 r2 撤回:轉換多於點擊是瀏覽後轉換,合法(同 `cvr`)。防回歸:[test:test_a_receipt_value_too_long_for_trusted_evidence_is_na]、[test:test_money_ratios_use_the_decimal_value_written_on_the_receipt]。
