# 有界標籤的指標

本篇管 `src/rtb/ops/metrics.py`。兩個入口:`collect_window(起, 迄, ...)` 窗內統計、`collect_snapshot(現在, ...)` 現況快照;命令列 `python -m rtb.ops.metrics --executor-db … --analyzer-db … --tenants-config … --since … --until …`(或 `--now …`)印 JSON。設計與合約 [S630]–[S649] 見 [[Projects/RTB_Phase9可觀測與SLO_計劃]] 增量 2。

- 資料來源一律經擁有模組的讀取函式:[[Systems/提案收件口]] 的窗內事件、最後終點事件、待處理現況;[[Systems/外部寫入嘗試紀錄]] 的窗內 DSP 呼叫、窗內終點列、未結案鍵;[[Systems/分析行程流程與檢查點]] 的窗內對外呼叫與接續關係;[[Systems/可觀測查詢]] 的總曝險使用率。窗口讀取函式都走時間索引(防回歸:[test:test_every_window_reader_uses_its_time_index],新加一支窗口讀取函式沒登記索引就翻紅)。
- 比率的分母是跟它「分組標籤」相同的母體,類別標籤切分子;每一項的分組與類別寫在模組各計算函式旁。例:DSP 呼叫比率依呼叫類別分組(分母是同一呼叫類別的窗內呼叫數),依結果類別切分子;租戶與程式版本看次數那一項。
- 最終結果率的查法:窗內有終點事件的提案才逐一用終點部分索引取全域最後一個終點事件,工作量跟窗內候選數成正比,不掃窗外歷史(防回歸:[test:test_stale_rejections_dead_letter_wait_and_bounded_final_result_lookup] 數查詢次數)。
- 執行端處理(代碼審第 1 輪改):窗內實際出現的每個終點事件各成一段,從對應的那次開始(第一次取件,或最近一次重放放回之後的第一次取件)到這個終點事件,扣掉段內的人工核可等待與死信等待,依這個終點事件的時間歸窗。死信後重放成功的提案貢獻兩段(死信前、重放後),窗過去之後再查不變。
- 讀到穩定為止只套在端到端(代碼審第 1、2 輪改):執行端的完整讀取只做一次,報告全部數字都出自第一輪;之後端到端每輪只重讀它要的(窗內事件、涉及任務的事件、最後終點,加分析端接續鏈),只拿來跟第一輪比。系統持續寫入不影響端到端時,不會被標不穩定;影響到時標不穩定,但不改用較新的結果。
- 擋下、進待核可、核可放回、過時決策拒絕是事件次數,跟 [[Systems/可觀測查詢]] 停下紀錄的提案數(同提案同種類只記一次)定義不同;樣本的附註寫明,兩邊數字不要拿來互相核對。
- 時間一律要帶時區:命令列 --since、--until、--now 共用一支解析器,沒帶時區由參數解析報錯;兩個入口也檢查,丟 ValueError。判斷本身呼叫 [[Systems/任務流程領域模型]] 的共用檢查,不自己寫(代碼審第 2 輪)。
- 未結案現況的「最久持續時間」是那把鍵進入目前狀態的時間(最後一段同狀態連續列的第一列)到「現在」;查證逾時會在同一狀態多寫幾列,用最新一列會把卡住的時間歸零。
- 模型與 Jev 那一項照實標不適用(分析是確定性計算、沒有呼叫模型),不造假數字。
- 結束代碼:0 成功;2 資料庫檔不存在;3 資料庫還沒升級(含缺這一版新加的時間索引);4 窗超過 24 小時或迄不在起之後;5 讀取不穩定(照樣印最後一輪);6 租戶設定檔讀不了;7 參數錯(缺參數、參數組合不對、時間沒帶時區;參數解析預設的 2 跟資料庫檔不存在撞號,解析器跟 [[Systems/追蹤檢視]] 共用)。防回歸:[test:test_the_command_line_reports_fixed_exit_codes]、[test:test_metric_times_must_carry_a_time_zone]、[test:test_missing_or_mismatched_flags_exit_with_the_bad_arguments_code]。
- 維運套件共用 [[Systems/追蹤檢視]] 那一份讀取白名單(寫在邊界測試裡):這個模組加了窗口讀取函式、現況快照的讀法、總曝險使用率與租戶設定檔的讀取;邊界測試機械判定的範圍跟著加上可觀測查詢與簽發兩支模組,白名單裡每一支仍要判成非寫入函式。
