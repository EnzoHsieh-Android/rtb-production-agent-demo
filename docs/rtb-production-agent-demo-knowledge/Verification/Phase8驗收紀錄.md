## 偏離與缺口

- 新鮮度沒有排在簽發之前:核可例外要驗核可的範圍指紋,租戶要簽發時才讀到;判斷點是判比例時、開始一筆的交易、重跑轉回嘗試中的交易(計劃〈實作狀態〉)。
- 「有它停下那一關的有效核可」落成「這一次真的需要、而且此刻有效的核可」,過時的決策不停進待核可等新核可(代使用者裁定,理由寫在計劃;代碼審三席各自找到任一核可都能免的漏洞)。
- 證據新鮮度以決策建立時間代理:執行端看不到證據本身;決策建立時間由分析端填,收件口只容許比現在晚 5 分鐘,所以被劫持的分析行程最多讓過時判斷晚 5 分鐘(代碼審第 1 輪資安席,重現後駁回「永遠通不了」)。
- 死信只有「還沒開始嘗試、投遞次數用完」一種;轉人工的嘗試不進死信、沒有重放(使用者裁定)。沒有自動、排程或批次重放,沒有網頁介面,沒有告警(Phase 9)。(2026-10-02:告警那半條件已成立——Phase 9 已有 dead_letter_rate 等死信指標與服務水準燒損告警,見 Systems/有界標籤的指標 筆記、Systems/服務水準與燒損告警 筆記;自動或批次重放仍沒有。)
- 分析端停機跨過收件表保留期時,過期死信照 Phase 5 清表路徑重新規劃,不是結案;安全(舊決策不寫),多花一次分析。
- 原本 Phase 5 的「死信就結案」改成決策沒過期時等待;回退前要先查沒有待重放的死信(查法在 [[Systems/提案收件口]])。
- 代碼審第 3 輪的修正沒有再開一輪全面審,只由發現那條的外家席驗收。
- 「只能由管理指令重放」「只增不改」兩句的守衛是掃原始碼的結構檢查,屬於防忘記:照專案一般寫法寫出的修改(含把 SQL 拆成相鄰字串、用 + 串起來、f-string)會被抓到;刻意用變數組表名、把關鍵字拆碎可以繞過。轉正後的補審審查席實測兩種繞法、並指出原本的配方跟檢查用同一種寫法所以「全紅」是循環的;已補強拼字串與換寫法的配方,限制照實寫在這裡。另有「定期入口加重送不改回死信」的行為測試擋在後面。
- 第 1 次審計時審計員違反派工單,在真的 repo 裡提交了一次(連同不准進版控的捷徑檔);發現後改寫本機歷史移除那個提交,內容由編排者重新提交,沒有推送。
- 代碼審期間全套測試有一次出現 1 條失敗,之後連跑多次沒重現、沒查出是哪一條;回頭條件寫在 governance/review-reports/code-phase8/r3-intake.md。
- Phase 6 留下的「寫入停下紀錄時不檢查時區」已在這條分支統一:收件口每個寫時間的地方都走嘗試紀錄模組的轉換,沒帶時區就拒絕。
