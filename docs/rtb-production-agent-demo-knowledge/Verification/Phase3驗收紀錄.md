## 已知缺口與偏離

- 對帳判「沒發生」之前要先請 DSP 作廢那把鍵(墓碑)。這是模擬 DSP 才有的能力,是本專案對外部系統下的前提;真實 DSP 沒有的話,只能退回「轉人工」。
- 作廢的墓碑以鍵為主鍵、全域共用,簽發端不驗這把鍵是否真由該提案算出。持有任一廣告合法作廢權、又知道別的廣告某把未提交的鍵的人,可以先把它封死。鍵是內容雜湊、要先知道對方的鍵,而且要有簽章金鑰,所以在「防忘記不防繞過」的威脅模型內接受;記在 [[Systems/寫入能力憑證]]。
- 作廢紀錄永久保留、沒有筆數或保留期上限(REVISIT:2026-11-30 盤點)。
- 一把鍵被作廢之後,同一任務只換到期時間的新修訂會算出同一把鍵、被擋下,要等廣告版本改變或分析行程算出不同內容才解得開(REVISIT:2026-12-31)。
- 分析行程還不知道提案被擋下或嘗試失敗,沒有回饋迴圈(之後的階段)。(2026-10-02 更正:Phase 5 起分析端會讀收件口回覆的擋下原因,版本已變這類原因就重新規劃開接續任務,見 `src/rtb/analyzer/flow.py` 的 _REPLAN_ON_BLOCK 與 Systems/分析行程流程與檢查點 筆記。)
- 人工處置只有程式介面,沒有命令列或網頁工具。
- 對帳迴圈的時間上限只有「這輪有 DSP 失敗就休息一輪」加上每把鍵的查證逾時上限,沒有針對整輪的秒數預算。
- 執行迴圈是單一執行者,靠一個以資料庫實體身分命名的 SQLite 鎖;資料庫檔有硬連結就拒絕啟動。多工作者是 Phase 4。(2026-10-02 更正:Phase 4 增量 3a 起可以同時跑多個執行迴圈,互斥改由收件表的租約與收據負責,不再拿單一執行者鎖;硬連結拒啟動仍在,見 `src/rtb/executor/runner.py` 檔頭與 [[Systems/執行迴圈]]。)
- 治理流程本身的兩個疏失如實記在卷證:增量 3 與增量 4 的代碼審各有一輪,編排者在席位還沒收齊時就動了工作目錄;增量 4 代碼審第 3 輪的記帳把「沒有需要處置的發現」寫成字面的 none,導致該輪的處置閘過不了,所以那個迴圈沒有凍結判定(收斂依據是第 2 輪的 PASS)。
